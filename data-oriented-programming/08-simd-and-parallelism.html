Chapter 8

SIMD and Parallelism

A dot product of two 4,096-float arrays fits in the L1 cache with room to spare. Written the obvious way, in any of our three languages, it runs at about 1.2 ns per element. That is roughly four clock cycles per multiply-add, on a core that can start two vector loads and two 8-wide floating-point operations every cycle. The data is already in the fastest memory the machine has. The loop is slow because every addition waits for the previous one to finish. Change one line so the additions no longer depend on each other and the same loop runs 7× to 27× faster. This chapter is about the two kinds of width a modern CPU offers, lanes inside one core and cores inside one chip, and about the data layouts and code shapes that let you use them.

Chapters 3 to 7 made data smaller, put it in columns and made loops uniform. That pays off here: SIMD (single instruction, multiple data) wants contiguous runs of one field, which SoA gives you (Chapter 4), and threads want disjoint chunks with no shared writes, which flat arrays give you. We will measure both, and find where they buy nothing.

One accumulator is a queue

Here is the loop, in the form you would write it without thinking:

/// 1. The obvious loop: one accumulator, strict left-to-right order. Each add waits for the previous one.
fn dot_naive(a: &[f32], b: &[f32]) -> f32 {
    a.iter().zip(b).map(|(x, y)| x * y).sum()
}
/// 1. The obvious loop: one accumulator, strict left-to-right order. Each add waits for the previous one.
fn dotNaive(a: []const f32, b: []const f32) f32 {
    var s: f32 = 0;
    for (a, b) |x, y| s += x * y;
    return s;
}
// 1. The obvious loop: one accumulator, strict left-to-right order. Each add waits for the previous one.
dot_naive :: proc(a, b: []f32) -> f32 {
	s: f32
	#no_bounds_check for x, i in a {
		s += x * b[i]
	}
	return s
}

Each iteration does a multiply and an add. The multiplies are independent: a[7] * b[7] does not care about a[6] * b[6]. The adds are not. The sum after element 7 is the sum after element 6 plus one product, so the add for element 7 cannot start until the add for element 6 has produced its result. A floating-point add on recent Intel cores has a latency of about four cycles and a throughput of two per cycle[1]. The hardware could start eight adds in the time this loop finishes one. An out-of-order core can run ahead on loads and multiplies, but every one of them ends up waiting in the same queue: the one register called s.

The fix is to keep several running sums. With eight accumulators, element i goes into sum i mod 8, and the eight chains are independent. Now two things happen. The out-of-order core can overlap the chains, and, better, the eight sums fit exactly in one 256-bit register, so one vaddps instruction advances all eight at once. With four such registers (32 partial sums) there are four independent vector chains, which is enough to hide the four-cycle latency completely. At that point the loop is limited by how fast it can load data, two 32-byte loads per cycle, which is the ceiling we want to hit.

If the eight-accumulator version is so much better, why doesn’t the compiler just rewrite the naive loop into it?

Because it would change the answer. Floating-point addition is not associative: (a + b) + c and a + (b + c) can round differently. Splitting one sum into eight and adding them up at the end is a reassociation, so a compiler that promises to give you exactly what you wrote is not allowed to do it. The next section shows this is not a theoretical worry: every variant in this chapter returns different bits.

When compilers vectorize

An auto-vectorizer turns a scalar loop into one that handles W elements per iteration (plus a scalar tail). LLVM, which all three of our compilers use, has two of them: the loop vectorizer, which widens whole loops, and the SLP (superword-level parallelism) vectorizer, which packs similar straight-line operations into one vector instruction. Before either one may touch a loop it has to prove three things (alignment is not one of them: compilers emit unaligned loads and move on).

  1. No aliasing that matters. If out might overlap in, writing eight results at once could clobber inputs a later lane still needs. Rust's &mut and & rules give the compiler this for free (an &mut [f32] cannot overlap anything else). Zig has noalias for pointer parameters. In C, and in Odin for raw pointers, the compiler may add a runtime overlap check or give up.
  2. A countable trip count. The loop must run a number of times known on entry: a for over a slice is fine, a while that exits when it finds a sentinel is not, because lane 5 might be past the end. Early breaks and calls to functions the compiler cannot see also stop it.
  3. The reordering is legal. For integers, a + b + c in any order gives the same bits (wrapping arithmetic is associative), so integer sums vectorize with no help. For floats it does not, so a float reduction stays scalar unless you either write the reassociation yourself or tell the compiler that you allow it.

The third rule is why xs.iter().sum::<f32>() in Rust compiles to a chain of scalar addss instructions, even with -C target-cpu=native, while the same code over i32 compiles to packed paddd. We checked the assembly for every variant in this chapter (cargo rustc --release -- --emit asm, zig build-obj -femit-asm, odin build -build-mode:asm). Here is what each compiler did:

Two cells in the Zig column need explaining, and they are the same explanation.

Zig 0.17.1 ships with LLVM's loop vectorizer switched off (Chapter 4 has the details[2]), so a plain Zig loop stays scalar, and so does one under @setFloatMode(.optimized): the permission to reassociate is there, but the pass that would use it is not. LLVM still applies contraction, fusing each multiply and add into one vfmadd, which rounds once instead of twice, so that variant returns different bits from the naive loop at the same speed. In Zig, writing @Vector yourself is the idiom.

Reassociating by hand: eight accumulators

The portable fix, which works in every language and every compiler, is to write the eight sums yourself. Rust's as_chunks::<8>() (stable since 1.88) splits a slice into &[[f32; 8]] plus a tail, so the chunk length is in the type and the inner loop has no bounds checks. Zig and Odin write the index arithmetic out; Zig's inline for unrolls the eight lanes at compile time.

/// 2. Eight accumulators: we reassociate by hand, so the compiler may put `acc` in SIMD lanes.
fn dot_acc8(a: &[f32], b: &[f32]) -> f32 {
    let (ca, ta) = a.as_chunks::<8>();
    let (cb, tb) = b.as_chunks::<8>();
    let mut acc = [0.0_f32; 8];
    for (x, y) in ca.iter().zip(cb) {
        for ((s, x), y) in acc.iter_mut().zip(x).zip(y) {
            *s += x * y;
        }
    }
    let mut s = 0.0;
    for v in acc {
        s += v;
    }
    for (x, y) in ta.iter().zip(tb) {
        s += x * y;
    }
    s
}
/// 2. Eight accumulators: we reassociate by hand. (Zig 0.17.1 has LLVM's loop vectorizer off;
/// the SLP vectorizer may still pack the eight independent adds into one register.)
fn dotAcc8(a: []const f32, b: []const f32) f32 {
    var acc: [8]f32 = @splat(0);
    var i: usize = 0;
    while (i + 8 <= a.len) : (i += 8) {
        inline for (0..8) |j| acc[j] += a[i + j] * b[i + j];
    }
    var s: f32 = 0;
    for (acc) |v| s += v;
    while (i < a.len) : (i += 1) s += a[i] * b[i];
    return s;
}
// 2. Eight accumulators: we reassociate by hand, so the compiler may put `acc` in SIMD lanes.
dot_acc8 :: proc(a, b: []f32) -> f32 {
	acc: [8]f32
	i := 0
	#no_bounds_check for ; i + 8 <= len(a); i += 8 {
		for j in 0 ..< 8 {
			acc[j] += a[i + j] * b[i + j]
		}
	}
	s: f32
	for v in acc {
		s += v
	}
	#no_bounds_check for ; i < len(a); i += 1 {
		s += a[i] * b[i]
	}
	return s
}

Notice the final combine: for v in acc { s += v } rather than acc.iter().sum() or @reduce(.Add, ...). An ordered left-to-right combine is spelled the same way in all three languages, so the three programs return the same bits, which is how we check that they really compute the same thing. Zig's @reduce(.Add, v) on floats, by contrast, does not promise an order.

Giving permission: algebraic_add, @(fast_math), @setFloatMode

The other route is to keep the simple loop and tell the compiler that you accept a different rounding. Each language scopes the permission differently, which matters: a global -ffast-math in C also assumes there are no NaNs or infinities anywhere in the program, which is a correctness hazard far from the loop you meant.

/// 4. The naive loop with algebraic ops (stable 1.98): the compiler may reassociate, so it vectorizes.
fn dot_algebraic(a: &[f32], b: &[f32]) -> f32 {
    a.iter().zip(b).fold(0.0, |s, (x, y)| s.algebraic_add(x.algebraic_mul(*y)))
}
/// 4. The naive loop with reassociation (and contraction) allowed for this one function.
fn dotReassoc(a: []const f32, b: []const f32) f32 {
    @setFloatMode(.optimized);
    var s: f32 = 0;
    for (a, b) |x, y| s += x * y;
    return s;
}
// 4. The naive loop with reassociation allowed for this one procedure.
@(fast_math = {.Allow_Reassoc})
dot_reassoc :: proc(a, b: []f32) -> f32 {
	s: f32
	#no_bounds_check for x, i in a {
		s += x * b[i]
	}
	return s
}

f32::algebraic_add, algebraic_sub, algebraic_mul, algebraic_div and algebraic_rem (and the f64, f16, f128 versions) were stabilized in Rust 1.98.0 (#[stable(feature = "float_algebraic", since = "1.98.0")] in core/src/num/f32.rs), and are const-stable too[3]. They are per-operation: only the adds and multiplies you wrote this way may be reassociated or contracted, and the rest of your program keeps IEEE semantics. On 1.100 the fold above compiles to packed addps; in this run it happened to pick the same 8-way split as our hand-written version, so at L1 size the two return identical bits (at DRAM size they differ by one ulp; see below). That is a coincidence of this compiler version, not a promise. Odin's @(fast_math = {.Allow_Reassoc}) is per-procedure and lets you choose flags one by one (.No_NaNs, .Allow_Contract, …). Zig's @setFloatMode(.optimized) is per scope and enables the whole fast-math set.

Explicit SIMD in three languages

Auto-vectorization is a negotiation with the optimizer. Explicit SIMD skips the negotiation: you name a vector type, load eight floats into it, and do arithmetic on all eight. All three languages can do this; how they spell it says a lot about each language.

Zig: @Vector is a builtin type

In Zig a vector is a first-class type, @Vector(8, f32), with the ordinary operators. An array coerces to a vector of the same length, so a[i..][0..8].* (slice to array to vector) is one unaligned 256-bit load. Comparisons give @Vector(8, bool), and @select, @reduce and @shuffle cover the rest. std.simd.suggestVectorLength(f32) tells you the width the standard library considers native: 8 here. The CPU has AVX-512, but LLVM's model of it sets prefer_256_bit, and std.simd only suggests 512-bit vectors when that flag is absent. Our fixed width of 8 matches it, and the three programs do the same work.

const V = @Vector(8, f32);

/// 3. Explicit SIMD: four @Vector(8, f32) accumulators (32 partial sums), four adds in flight at once.
fn dotSimd(a: []const f32, b: []const f32) f32 {
    var acc: [4]V = @splat(@splat(0));
    var i: usize = 0;
    while (i + 32 <= a.len) : (i += 32) {
        inline for (0..4) |k| {
            const va: V = a[i + 8 * k ..][0..8].*; // slice → array → vector: one unaligned load
            const vb: V = b[i + 8 * k ..][0..8].*;
            acc[k] += va * vb;
        }
    }
    const lanes: [8]f32 = ((acc[0] + acc[1]) + acc[2]) + acc[3];
    var s: f32 = 0;
    for (lanes) |l| s += l; // ordered, so the bits match Rust and Odin
    while (i < a.len) : (i += 1) s += a[i] * b[i];
    return s;
}

Odin: #simd and core:simd

Odin's vector type is #simd[8]f32, also with built-in operators, and the core:simd package wraps the intrinsics: lanes_gt, select, reduce_add_ordered, masked_load, gather and more [5]. There are two Odin-specific details. First, #simd[8]f32 has 32-byte alignment while a []f32 element is only 4-byte aligned, so casting &a[i] to ^V and dereferencing it would assume an alignment you do not have. Use intrinsics.unaligned_load (or simd.from_slice, which copies through an array). Second, Odin's default target is x86-64-v2 (“close to Nehalem”, SSE4.2, no AVX)[6], so a #simd[8]f32 is lowered to two 128-bit halves unless you opt in. The opt-in is a procedure attribute, @(enable_target_feature = "avx2"), which compiles one procedure for AVX2 while the rest of the program stays portable. The caller checks the CPU once with core:sys/info:

V :: #simd[8]f32

// 3. Explicit SIMD: four #simd[8]f32 accumulators (32 partial sums), four adds in flight at once.
// Written once; the AVX2 wrapper below compiles the same body with 256-bit registers.
dot_lanes :: #force_inline proc "contextless" (a, b: []f32) -> f32 {
	acc: [4]V
	i := 0
	#no_bounds_check for ; i + 32 <= len(a); i += 32 {
		#unroll for k in 0 ..< 4 {
			// slice elements are only 4-byte aligned, #simd[8]f32 wants 32: use unaligned loads
			va := intrinsics.unaligned_load((^V)(&a[i + 8 * k]))
			vb := intrinsics.unaligned_load((^V)(&b[i + 8 * k]))
			acc[k] += va * vb
		}
	}
	lanes := simd.to_array(((acc[0] + acc[1]) + acc[2]) + acc[3])
	s: f32
	for l in lanes {
		s += l // ordered, so the bits match Rust and Zig
	}
	#no_bounds_check for ; i < len(a); i += 1 {
		s += a[i] * b[i]
	}
	return s
}

@(enable_target_feature = "avx2")
dot_avx2 :: proc "contextless" (a, b: []f32) -> f32 {
	return dot_lanes(a, b)
}

// Odin's default target is x86-64-v2 (SSE4.2), so #simd[8]f32 is two 128-bit halves unless we opt in.
// Runtime dispatch: checked once at startup, because cpuid is slow (and traps in a VM).
has_avx2: bool

dot_simd :: proc(a, b: []f32) -> f32 {
	return has_avx2 ? dot_avx2(a, b) : dot_lanes(a, b)
}

dot_lanes is #force_inline, so each caller gets its own copy compiled with its own target features: inside dot_avx2 it becomes 256-bit vaddps ymm; in the fallback it becomes pairs of SSE addps. One body, two instruction sets.

Rust: std::arch, #[target_feature], runtime detection

Stable Rust has no portable vector type. What it has is std::arch::x86_64: every Intel intrinsic, by its Intel name (_mm256_add_ps), working on opaque register types like __m256. You compile a function for AVX2 with #[target_feature(enable = "avx2")], check at run time with is_x86_feature_detected!("avx2"), and fall back to portable code otherwise. Calling the AVX2 function is unsafe, because calling it on a CPU without AVX2 would execute illegal instructions; the runtime check is what makes the call sound.

/// 3a. Explicit AVX2: four 8-lane accumulators (32 partial sums) so four adds are in flight at once.
#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
fn dot_avx2(a: &[f32], b: &[f32]) -> f32 {
    use std::arch::x86_64::*;
    let (ca, ta) = a.as_chunks::<32>();
    let (cb, tb) = b.as_chunks::<32>();
    let mut acc = [_mm256_setzero_ps(); 4];
    for (x, y) in ca.iter().zip(cb) {
        for (k, acc) in acc.iter_mut().enumerate() {
            // SAFETY: x and y are [f32; 32], so lanes 8k..8k+8 are in bounds; loadu needs no alignment.
            let (vx, vy) = unsafe { (_mm256_loadu_ps(x.as_ptr().add(8 * k)), _mm256_loadu_ps(y.as_ptr().add(8 * k))) };
            *acc = _mm256_add_ps(*acc, _mm256_mul_ps(vx, vy)); // value-only intrinsics are safe here (1.87+)
        }
    }
    let v = _mm256_add_ps(_mm256_add_ps(_mm256_add_ps(acc[0], acc[1]), acc[2]), acc[3]);
    let mut lanes = [0.0_f32; 8];
    // SAFETY: `lanes` has room for 8 f32; storeu needs no alignment.
    unsafe { _mm256_storeu_ps(lanes.as_mut_ptr(), v) };
    let mut s = 0.0;
    for l in lanes {
        s += l;
    }
    for (x, y) in ta.iter().zip(tb) {
        s += x * y;
    }
    s
}

/// 3. Runtime dispatch: AVX2 if this CPU has it, the portable version otherwise.
fn dot_simd(a: &[f32], b: &[f32]) -> f32 {
    #[cfg(target_arch = "x86_64")]
    if is_x86_feature_detected!("avx2") {
        // SAFETY: we just checked at run time that the CPU supports AVX2.
        return unsafe { dot_avx2(a, b) };
    }
    dot_acc32(a, b)
}

Since 1.86, a #[target_feature] function may itself be a safe fn; only calling it from code without the feature needs unsafe. Since 1.87, intrinsics that only take and return values (_mm256_add_ps, _mm256_mul_ps) are safe to call inside such a function. What remains unsafe is what should be: raw-pointer loads and stores (_mm256_loadu_ps) and the dispatch call[4]. Older code wraps the whole body in unsafe { }; you no longer need to.

The scalar fallback, dot_acc32, keeps the same 4×8 accumulator layout and the same combine order, and the program asserts that it returns the same bits as dot_avx2. That assertion is worth having in real code: a SIMD path that silently disagrees with its fallback is a bug that only shows up on someone else's machine.

Rust's portable SIMD module, std::simd, is #[unstable(feature = "portable_simd", issue = "86656")] in 1.100 and does not compile on stable[7]. It looks like this. The snippet is shown for comparison only; it is not part of the book's compiled code, because it needs a nightly toolchain:

// nightly only: rustup run nightly cargo run   (not built by run_all.sh)
#![feature(portable_simd)]
use std::simd::prelude::*;

fn dot(a: &[f32], b: &[f32]) -> f32 {
    let (ca, ta) = a.as_chunks::<8>();
    let (cb, tb) = b.as_chunks::<8>();
    let mut acc = f32x8::splat(0.0);
    for (x, y) in ca.iter().zip(cb) {
        acc += f32x8::from_array(*x) * f32x8::from_array(*y);
    }
    acc.reduce_sum() + ta.iter().zip(tb).map(|(x, y)| x * y).sum::<f32>()
}

It is close to Zig's @Vector and Odin's #simd. Until it stabilizes, stable Rust code either uses std::arch as above, or writes the accumulator arrays and lets LLVM vectorize them, or uses a crate such as wide.

Which width? AVX-512 here, AVX2 as the baseline

This orb is an Ice Lake server and has AVX-512 (16 floats per register, plus mask registers). The book still targets AVX2 (8 floats) for explicit code. AVX2 (part of the x86-64-v3 level) is in almost every desktop, laptop and server x86-64 CPU since Haswell (2013), though some low-end Atom-based Pentium and Celeron chips still lack it, which is why the code keeps a runtime check and a fallback. AVX-512 is missing from most Intel client chips and differs across AMD generations (Chapter 2 has the table). And as the measurements show, 8 lanes are already enough to hit the load limit.

If you only run on the machine you compile on, you can let the compiler use everything it has: RUSTFLAGS="-C target-cpu=native" for Rust, -mcpu=native for Zig (its default when you compile for the host, which is why Zig's column above says Ice Lake), and -microarch:native for Odin. The binaries may then crash on an older CPU: Rust's default is the most portable (SSE2), Odin's is in the middle (SSE4.2), Zig's assumes the host.

Measured: four dot products at three sizes

The program computes the same dot product four ways over arrays of three sizes: 4,096 floats per array (32 KiB for both arrays, inside the 48 KiB L1d), 65,536 floats (512 KiB, inside the 1.25 MiB L2), and a DRAM control of 16 M floats per array (128 MiB, far past any L3). Small sizes are repeated so every measurement does the same 16 M multiply-adds. The harness is the one from Chapter 2: one warm-up, median of seven, and the result is kept alive. Data comes from the same integer hash in all three languages, so the inputs are bit-identical.

A worked example with real numbers

Take the Rust row at L1 size. The naive loop takes about 7× as long as eight accumulators and about 13× as long as explicit AVX2. In absolute terms the naive loop took 1.21 ns per element. This orb's clock is not exposed (no performance counters), but at 2.6 to 3.5 GHz that is about 3 to 4 cycles: one add latency per element, as the chain predicts.

Now the explicit SIMD loop. Per 32 elements it does 8 loads of 32 bytes, 4 multiplies and 4 adds. Ice Lake can issue two loads per cycle, so the loads alone need 4 cycles per 32 elements, or 0.125 cycles per element: about 0.04 ns at 3 GHz. Zig's explicit loop measured 0.044 ns per element, within about 1.5× of that ceiling. Rust's and Odin's explicit loops came in at 0.095 ns and 0.14 ns. For Odin the assembly shows why: @(enable_target_feature = "avx2") enables the instructions but keeps the x86-64-v2 tuning, which treats unaligned 32-byte loads as slow, so LLVM splits each one into a 16-byte vmovups plus vinsertf128. That doubles the load count and halves the ceiling, to about 0.08 ns. Rust's gap we did not track down. The solid ratio is the one all three agree on: breaking the chain is worth about an order of magnitude, and 32 AVX2 lanes are worth another 1.1× (Odin) to 3.2× (Zig) while the data is in L1.

At DRAM size the picture flattens. Each element is 8 bytes of input (one float from each array), and explicit SIMD sits at about 0.77 ns per element in Rust: roughly 10 GB/s from one core for this two-stream read (other workloads in this book reach different rates). The naive loop is still slower (1.4 ns), because four cycles per element is slower than DRAM can feed one core, but explicit AVX2 is now no faster than eight accumulators. About 1.8× is all SIMD buys when the loop is memory-bound. This is the same lesson as Chapter 2's bandwidth section from the other direction: SIMD makes computation cheap, and once computation is cheap, the bytes are all that is left. The layout work of Chapters 3 and 4, fewer bytes per element, is what helps a memory-bound loop.

Two things to notice. First, reassociation did not make the answer worse; at 16 M elements the single accumulator is about nine times less accurate than eight, because a running sum that has grown large loses the low bits of every small product added to it. Splitting the sum into partial sums is a crude form of pairwise summation. Second, “reassociation allowed” is not a stable spec: Rust's algebraic version matched the 8-accumulator bits at L1 size and missed by one ulp at DRAM size, because LLVM is free to pick a different split. If you need reproducible results (lockstep networking, golden test files), write the accumulators yourself and fix the combine order, as the programs do. If you only need a good answer, any of the vectorized variants is better than the naive one.

Branches become masks

So far every lane did the same thing. Real loops have conditions. Say we want the sum and the count of the positive values. The scalar version is a branch per element, and with random signs that branch is a coin flip the predictor cannot learn (Chapter 7 measures exactly how much that costs). A vector loop cannot branch per lane at all, since all eight lanes run one instruction stream. So it does what Chapter 7 calls branch-free selection, eight times at once: compute a mask (all ones in each lane where x > 0, all zeros elsewhere), then use the mask to keep x or replace it with zero, and add everything. The work for the lanes that “didn't take the branch” is wasted, and that is the price of having no branch to mispredict.

In code the mask is a compare instruction whose result is a vector, not a flag. Zig's v > zero has type @Vector(8, bool) and goes straight into @select. Odin's simd.lanes_gt returns an integer vector of all-ones/all-zeros, so the count is m & 1. In Rust's AVX2 version the mask is a __m256 of bit patterns; ANDing it with x keeps x or gives +0.0, and since all-ones is −1 as an integer, subtracting the mask counts.

/// Branch-free lanes, AVX2: compare makes a mask (all ones where x > 0); AND keeps x or 0.0.
#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
fn pos_avx2(a: &[f32]) -> (f32, u32) {
    use std::arch::x86_64::*;
    let (chunks, tail) = a.as_chunks::<8>();
    let zero = _mm256_setzero_ps();
    let (mut s, mut c) = (zero, _mm256_setzero_si256());
    for x in chunks {
        // SAFETY: x is [f32; 8]; loadu needs no alignment.
        let v = unsafe { _mm256_loadu_ps(x.as_ptr()) };
        let m = _mm256_cmp_ps::<_CMP_GT_OQ>(v, zero); // lane = 0xFFFF_FFFF where x > 0, else 0
        s = _mm256_add_ps(s, _mm256_and_ps(v, m)); // x where true, +0.0 where false
        c = _mm256_sub_epi32(c, _mm256_castps_si256(m)); // all ones is -1, so subtracting counts
    }
    let (mut sl, mut cl) = ([0.0_f32; 8], [0_u32; 8]);
    // SAFETY: both arrays hold exactly 8 lanes; storeu needs no alignment.
    unsafe {
        _mm256_storeu_ps(sl.as_mut_ptr(), s);
        _mm256_storeu_si256(cl.as_mut_ptr().cast(), c);
    }
    let (mut s, mut c) = (0.0, 0);
    for j in 0..8 {
        s += sl[j];
        c += cl[j];
    }
    let (ts, tc) = pos_branchy(tail);
    (s + ts, c + tc)
}
/// Branch-free lanes: `v > zero` is a @Vector(8, bool) mask; @select keeps x or 0.0 per lane.
fn posMask(a: []const f32) Pos {
    const zero: V = @splat(0);
    const U = @Vector(8, u32);
    var s: V = zero;
    var c: U = @splat(0);
    var i: usize = 0;
    while (i + 8 <= a.len) : (i += 8) {
        const v: V = a[i..][0..8].*;
        const m = v > zero;
        s += @select(f32, m, v, zero);
        c += @select(u32, m, @as(U, @splat(1)), @as(U, @splat(0)));
    }
    const sl: [8]f32 = s;
    var r: Pos = .{ .sum = 0, .count = @reduce(.Add, c) };
    for (sl) |l| r.sum += l;
    const t = posBranchy(a[i..]);
    return .{ .sum = r.sum + t.sum, .count = r.count + t.count };
}
// Branch-free lanes: lanes_gt gives all-ones where x > 0; select keeps x or 0.0 per lane.
pos_mask :: proc(a: []f32) -> (r: Pos) {
	U :: #simd[8]u32
	zero: V
	s: V
	c: U
	i := 0
	#no_bounds_check for ; i + 8 <= len(a); i += 8 {
		v := intrinsics.unaligned_load((^V)(&a[i]))
		m := simd.lanes_gt(v, zero) // #simd[8]u32: 0xFFFF_FFFF or 0
		s += simd.select(m, v, zero)
		c += m & U(1)
	}
	for l in simd.to_array(s) {
		r.sum += l
	}
	r.count = simd.reduce_add_ordered(c)
	t := pos_branchy(a[i:])
	return {r.sum + t.sum, r.count + t.count}
}

Rust and Odin compiled the branchy loop as written: a compare, a conditional jump and an add. With random signs, about half of those jumps mispredict, and the loop runs at about 4.6 ns per element in Rust. The 8-lane mask version runs at 0.15 ns (Rust) and 0.34 ns (Odin): about 30× for Rust. Zig is the honest exception. Because Zig compiled for this Ice Lake with AVX-512, LLVM turned the if into a scalar compare that writes an AVX-512 mask register (vucomiss, seta, kmovd) and a masked add. There is no branch left to mispredict, so Zig's scalar loop already runs at 0.40 ns, and its explicit mask version at 0.10 ns. The lesson is not that Zig predicts better; it is that “branchy” source does not guarantee branchy machine code, so look at the assembly before you explain a number.

Threads: split the arrays, not the objects

SIMD is width inside one core. Threads are width across cores. DOD's contribution to threading is simple and very effective: if the state is a set of flat arrays and the update is the same for every element, then splitting the arrays into contiguous chunks and giving one chunk to each thread needs no locks, no atomics and no shared writes. Each thread streams its own cache lines. The only coordination is “start” and “wait for all”.

Our kernel is the SoA particle step from Chapter 4, shrunk to two dimensions: x += vx * dt; y += vy * dt over four columns. All three languages split the same way: they round the chunk length up to a multiple of 32 floats (128 bytes) and start every column on a 128-byte boundary, so that no two threads ever write into the same 128-byte pair of cache lines. Rounding the length alone is not enough, since ordinary allocations are only 4- or 16-byte aligned and the boundaries would then fall inside a pair. Rust allocates each column with 31 floats of slack and starts at the first aligned element, Zig uses gpa.alignedAlloc(f32, .fromByteUnits(std.atomic.cache_line), n) (128 on x86-64), and Odin uses make_soa_aligned(#soa[]Particle, n, 128). The next section explains why 128 and not 64.

/// Split the SoA columns into `threads` disjoint chunks (whole multiples of 32 floats = 128 B; the columns
/// are 128-byte aligned, so no two threads write the same cache-line pair), and let each thread run `passes` steps over its chunk.
fn step_parallel(x: &mut [f32], y: &mut [f32], vx: &[f32], vy: &[f32], threads: usize, passes: usize) {
    let chunk = x.len().div_ceil(threads).next_multiple_of(32);
    thread::scope(|s| {
        let cols = x.chunks_mut(chunk).zip(y.chunks_mut(chunk)).zip(vx.chunks(chunk)).zip(vy.chunks(chunk));
        for (((x, y), vx), vy) in cols {
            s.spawn(move || {
                for _ in 0..passes {
                    step(x, y, vx, vy);
                }
            });
        }
    });
}
/// Split the columns into `threads` disjoint chunks (whole multiples of 32 floats = 128 B; the columns are
/// 128-byte aligned, so no two threads write the same cache-line pair), one std.Thread each, then join them all.
fn stepParallel(s: Soa, threads: usize, passes: usize) void {
    const chunk = std.mem.alignForward(usize, std.math.divCeil(usize, s.x.len, threads) catch unreachable, 32);
    var pool: [8]std.Thread = undefined;
    var spawned: usize = 0;
    var lo: usize = 0;
    while (lo < s.x.len) : (lo += chunk) {
        const hi = @min(lo + chunk, s.x.len);
        const part: Soa = .{ .x = s.x[lo..hi], .y = s.y[lo..hi], .vx = s.vx[lo..hi], .vy = s.vy[lo..hi] };
        pool[spawned] = std.Thread.spawn(.{}, worker, .{ part, passes }) catch @panic("spawn failed");
        spawned += 1;
    }
    for (pool[0..spawned]) |t| t.join();
}
// One particle step over a chunk: x += vx·dt, y += vy·dt. Columns hoisted into locals first.
worker :: proc(c: Chunk) {
	n := len(c.p)
	xs, ys, vxs, vys := c.p.x[:n], c.p.y[:n], c.p.vx[:n], c.p.vy[:n]
	for _ in 0 ..< c.passes {
		#no_bounds_check for i in 0 ..< n {
			xs[i] += vxs[i] * DT
			ys[i] += vys[i] * DT
		}
	}
}

// Split the #soa slice into `threads` disjoint chunks (whole multiples of 32 elements, so every column
// chunk is a multiple of 128 B; make_particles aligns each column to 128 B, so no two threads write the
// same cache-line pair).
step_parallel :: proc(p: #soa[]Particle, threads, passes: int) {
	chunk := ((len(p) + threads - 1) / threads + 31) &~ 31
	pool: [8]^thread.Thread
	k := 0
	for lo := 0; lo < len(p); lo += chunk {
		hi := min(lo + chunk, len(p))
		pool[k] = thread.create_and_start_with_poly_data(Chunk{p[lo:hi], passes}, worker)
		k += 1
	}
	thread.join_multiple(..pool[:k])
	for t in pool[:k] {
		thread.destroy(t)
	}
}
  • Rust: std::thread::scope (stable since 1.63)[8] lets threads borrow local data, and chunks_mut hands each an &mut to a disjoint piece: the borrow checker proves the pieces don't overlap. (In production, rayon's par_chunks_mut adds work stealing.)
  • Zig: std.Thread.spawn with a function and an argument tuple, then join. Nothing checks that the chunks are disjoint; it's the code's job.
  • Odin: thread.create_and_start_with_poly_data passes one Chunk (slicing an #soa slice slices every column at once) to a typed procedure; join_multiple and destroy finish up[9]. The worker hoists the column slices into locals, which matters in Odin (Chapter 4 explains why).

Zig 0.16 removed std.Thread.Pool, Mutex, WaitGroup and friends in favour of the std.Io interface[10]. io.async expresses asynchrony, not parallelism: an implementation may run the function inline, so a benchmark that must use two cores uses std.Thread.spawn, which still means one OS thread.

Every run checks that the thread count does not change the result: the particles are stepped three times with 1, 2 and 4 threads, and the checksum of the output bits is the same (446be9f861039fff) in all nine runs, three languages × three thread counts.

False sharing: when threads fight over a line they don't share

Coherence works in whole cache lines. When a core writes to a line, every other core's copy of that line must be invalidated first; when another core then writes to the same line, ownership moves back. That is correct and necessary when two threads write the same variable. It is pure waste when they write different variables that happen to share a line: per-thread counters in one array, a queue's head and tail pointers declared next to each other, a struct of per-worker stats. Nothing is logically shared, and the line bounces anyway. Drepper measured this on a four-socket Pentium 4 in 2007: threads incrementing their own variables on one shared line took 390%, 734% and 1,147% longer with 2, 3 and 4 threads than with the variables on separate lines[11].

In the figure, with 16 alternating writes and the counters in the same line, how many invalidations will the model count?

15. The first write is a cold miss from memory; each of the other 15 finds the line Modified in the other core, takes it, and invalidates the other copy. With 128-byte padding the count is 0: each core takes its line once and then only hits.

Why 128 bytes: the adjacent-line prefetcher

Cache lines on x86 are 64 bytes, so padding each counter to 64 bytes should be enough, and on many machines it is. But since Sandy Bridge, Intel's L2 spatial prefetcher “strives to complete every cache line fetched to the L2 cache with the pair line that completes it to a 128-byte aligned chunk”[12]. When core 0 misses on line 0, it may also fetch line 1, and if core 1 owns line 1, that is coherence traffic for a line core 0 never asked for. That is why crossbeam's CachePadded uses #[repr(align(128))] on x86-64[13] and why Zig's std.atomic.cache_line is 128 on x86-64 and aarch64, with a comment citing the same prefetcher[14].

The benchmark gives each of two threads its own AtomicU64 (relaxed fetch_add, 16 M times each) in four placements: one thread alone (the baseline), both counters in one 64-byte line, one counter per 64-byte line, and one per 128 bytes. The three languages spell the padding three ways:

/// Two counters in one 64-byte line (the array is aligned so it cannot straddle two lines).
#[repr(align(64))]
struct Packed([AtomicU64; 2]);

/// One counter per 64-byte line: adjacent lines still form one 128-byte pair for the spatial prefetcher.
#[repr(align(64))]
struct Pad64(AtomicU64);

/// One counter per 128-byte block, as crossbeam's CachePadded does on x86-64.
#[repr(align(128))]
struct Pad128(AtomicU64);

const _: () = assert!(size_of::<Packed>() == 64 && size_of::<Pad64>() == 64 && size_of::<Pad128>() == 128);

/// Each of the two threads increments its own counter `iters` times. Returns the total.
fn two_threads(c0: &AtomicU64, c1: &AtomicU64, iters: u64) -> u64 {
    thread::scope(|s| {
        s.spawn(|| hammer(c0, iters));
        s.spawn(|| hammer(c1, iters));
    });
    c0.load(Ordering::Relaxed) + c1.load(Ordering::Relaxed)
}
/// Two counters in one 64-byte line (aligned so the pair cannot straddle two lines).
const Packed = struct { c: [2]Counter align(64) };
/// One counter per 64-byte line: adjacent lines still form one 128-byte pair for the spatial prefetcher.
const Pad64 = struct { c: Counter align(64) };
/// One counter per std.atomic.cache_line (128 on x86-64: Zig already accounts for the pair prefetch).
const Pad128 = struct { c: Counter align(std.atomic.cache_line) };

comptime {
    std.debug.assert(@sizeOf(Packed) == 64 and @sizeOf(Pad64) == 64);
    std.debug.assert(std.atomic.cache_line == 128 and @sizeOf(Pad128) == 128);
}

/// Each of the two threads increments its own counter `iters` times. Returns the total.
fn twoThreads(t: Two) u64 {
    const t0 = std.Thread.spawn(.{}, hammer, .{ t.c0, t.iters }) catch @panic("spawn failed");
    const t1 = std.Thread.spawn(.{}, hammer, .{ t.c1, t.iters }) catch @panic("spawn failed");
    t0.join();
    t1.join();
    return t.c0.load(.monotonic) + t.c1.load(.monotonic);
}
// Two counters in one 64-byte line (aligned so the pair cannot straddle two lines).
Packed :: struct #align (64) {
	c: [2]u64,
}
// One counter per 64-byte line: adjacent lines still form one 128-byte pair for the spatial prefetcher.
Pad64 :: struct #align (64) {
	c: u64,
}
// One counter per 128-byte block, as crossbeam and Zig's std.atomic.cache_line do on x86-64.
Pad128 :: struct #align (128) {
	c: u64,
}
#assert(size_of(Packed) == 64 && size_of(Pad64) == 64 && size_of(Pad128) == 128)

// Each of the two threads increments its own counter `iters` times. Returns the total.
two_threads :: proc(t: Two) -> u64 {
	t0 := thread.create_and_start_with_poly_data(Job{t.c0, t.iters}, hammer)
	t1 := thread.create_and_start_with_poly_data(Job{t.c1, t.iters}, hammer)
	thread.join_multiple(t0, t1)
	thread.destroy(t0)
	thread.destroy(t1)
	return intrinsics.atomic_load_explicit(t.c0, .Relaxed) + intrinsics.atomic_load_explicit(t.c1, .Relaxed)
}

Rust puts the alignment on a wrapper type with #[repr(align(128))], Zig on the field with align(std.atomic.cache_line) (so the constant follows the target), and Odin on the struct with struct #align (128). All three pin the sizes at compile time, the habit from Chapter 3. The charted runs are pinned to CPUs 0 and 2 (the taskset file in the chapter's code directory), which on this orb are two different physical cores (more on that below).

In Rust the same-line case runs at 29 ns per increment against 6.4 ns for a thread alone: about 4.3× slower, for counters that never interact. Two threads with padded counters finish in the same wall time as one thread doing half the total work, which is perfect scaling. We could not measure a difference between 64- and 128-byte padding on this machine. That matches the one public measurement we found: a 2026 benchmark reproduced the prefetcher effect at 64-byte spacing on a Skylake Xeon (AWS c5d, up to about 1.1× with much higher variance) but found “practically no difference” on an Ice Lake Xeon (AWS c6i)[15]. So 128 is the pessimistic choice: it costs 64 extra bytes per padded slot and protects you on the CPUs where the pair prefetch does bite.

Pad things that different threads write: per-thread counters, queue ends, per-worker accumulators. Don't pad every element of a big array: 128 bytes per u64 is a 16× memory cost and throws away the density this book has been fighting for. For per-element data, use the previous section's pattern: each thread owns a contiguous chunk, so only the chunk boundaries could share a line, and 128-byte-aligned columns split into 128-byte multiples remove even that. Read-mostly data needs no padding at all: many cores can hold the same line in Shared state at once.

Scaling: two cores, four threads

This orb has 4 vCPUs, but they are 2 physical cores with 2 hyperthreads each. lscpu -e says CPUs 0 and 1 are core 0, CPUs 2 and 3 are core 1. Two hyperthreads on one core share its execution units, its L1 and its L2. They help when one thread stalls (on a cache miss, a mispredict) and the other can use the idle units, and they help little when both are busy with the same kind of work.

The charted runs are pinned to taskset -c 0,2: one hyperthread on each core, so “two threads” means two real cores. Under that pinning, a 4-thread run oversubscribes two CPUs, which shows what more threads than cores buys you: little or nothing. (std::thread::available_parallelism respects the affinity mask and reports 2 under this taskset; Zig's getCpuCount says 2 as well.)

Two threads give about 1.9× in Rust and more in Zig, 3.2×. A superlinear speedup often means the working set changed level: 1 MiB of columns sits near the edge of one core's 1.25 MiB L2, and half of it fits in each of two L2s comfortably. That is a hypothesis we did not test, and it does not explain why Rust and Odin, with the same working set, gain less; Zig's single-thread time is also the slowest of the three. The DRAM-sized run (8 M particles, 128 MiB, one pass) gives 1.8× (Odin) to 2.0× (Zig) with two cores. One core alone could not saturate memory here, so the second core's extra outstanding misses still help.

Whether the hyperthreads help as well depends on how much of each core one thread leaves idle; an unpinned run cannot tell you, because the OS may put the “2 threads” case on two siblings of one core. The robust conclusions are the pinned ones: two physical cores give close to 2× on a loop with no shared writes, and threads beyond your CPUs give little or nothing.

Caveats

  • Algorithm and layout first. SIMD multiplies whatever the algorithm leaves; it does not fix an O(n²) (Chapter 12 has a path tracer where a BVH beat SIMD by orders of magnitude[16]). And the vector loads in this chapter all read contiguous runs of one field; on AoS data the same code needs gathers or shuffles and most of the gain disappears[17].
  • Memory-bound loops gain little. The DRAM controls show it twice: SIMD and threads both run into bandwidth. Two cores helped us because one core could not saturate memory; on a big server with many cores the curve flattens much earlier.
  • Wide vectors can lower the clock. On some Intel generations heavy 512-bit (and, on older ones, 256-bit) code reduces the core's frequency, which can make AVX-512 a net loss in mixed workloads. We did not measure frequency here (no counters), which is one more reason the book's explicit code stays at AVX2.

Break the dependency chain so lanes and cores can work side by side, put the work in contiguous columns so one load fills a register and one chunk belongs to one thread, keep threads' writes at least 128 bytes apart, and stop when the loop is waiting for memory.

Exercises

The naive dot product runs at about 1.2 ns per element at L1 size and about 1.4 ns at DRAM size. Why is the DRAM version barely slower, when DRAM is a hundred times further away than L1?

Because the naive loop is limited by the add chain, about four cycles per element, not by memory. Four cycles per 8 bytes is slower than the roughly 10 GB/s one core got from DRAM in this chapter's dot product, so memory keeps up. Only once the chain is broken does the memory side become the limit, and then the DRAM version is several times slower than the L1 version.

With eight accumulators, why might four vector accumulators (32 partial sums) still be faster than one vector of eight?

One vector of eight is still one chain: each vaddps waits ~4 cycles for the previous one, so you get 8 elements per 4 cycles. Four independent vectors keep four adds in flight, 32 elements per 4 cycles, which reaches the two-loads-per-cycle limit. The rule of thumb: accumulators ≈ latency × throughput (4 cycles × 2 adds/cycle = 8 vector registers would be the maximum useful; 4 is enough when loads limit you).

Integer sums vectorize without help. Why is u32 wrapping addition allowed to be reordered when f32 addition is not?

Wrapping integer addition is associative and commutative: any order gives the same bits modulo 2³². Floating-point addition rounds after every operation, and the rounding depends on the magnitudes involved, so different orders give different bits (the table in this chapter shows six different answers to one dot product).

A thread pool has 8 workers, each with a struct Stats { jobs: u64, ns: u64 }, stored in [8]Stats. How many bytes do all eight occupy, how many 128-byte pairs do they span, and what is the smallest fix?

16 bytes each, 128 bytes total: all eight workers' stats fit in one 128-byte pair (two 64-byte lines, four workers per line), so every update contends with three or seven other workers. Align Stats to 128 (#[repr(align(128))], align(std.atomic.cache_line), #align (128)) for 1 KiB total, or keep the counts in each worker's local variables and write them once at the end.

The 4-thread runs under taskset -c 0,2 are barely faster than the 2-thread runs, if at all. Under taskset -c 0,1, what would you expect for 1 vs 2 threads, and why?

CPUs 0 and 1 are hyperthreads of the same core. Two threads there share one core's execution units, L1 and L2. For a compute-bound loop that already keeps the units busy, expect well under 2×; for a loop that stalls a lot, more. For false sharing, the two threads share one L1, so you might expect the “same line” penalty to vanish. Do not count on it: two lock-prefixed read-modify-writes to one line still serialize each other, even inside one core. Run the taskset -c 0,1 line from the try box above and measure before you assume siblings are immune.

Rewrite the “sum of positives” to compute a clamped sum, adding min(x, 1.0) for positive x. Which extra vector operation do you need, and is there still a branch?

A lane-wise minimum: _mm256_min_ps in Rust's std::arch, @min(v, one) on vectors in Zig, simd.min in Odin. Apply it before the select. There is still no branch: the mask selects between min(x, 1) and 0.
