    Troubleshooting MJWarp

    Something is wrong: an exception, a pause, a crash, or worse, numbers that look fine and are not. Each entry gives the symptom you see, the cause, the fix, and the chapter section that owns the topic. Everything was collected from the pitfall and warning boxes of the 30 chapters and the Colab setup, and checked against mujoco-warp 4.0.1 (source tree 8f5b9f1).

    Three habits that prevent most entries

    Check d.overflow after every run with contacts. Call mjw.forward after writing state. Write into arrays (fill_, assign, kernels) instead of replacing them, and set integer options before the first step and before any capture.

    1Install, GPU and Colab setup8

    Problems that show up in the first two cells of a notebook. Every course notebook starts with !nvidia-smi and the standard setup cell (driver check, pinned install, imports, ON_GPU, GRAPH_COND); Ch 1 §5 explains it line by line.

    "No NVIDIA GPU visible", or ON_GPU is False

    Setup
    Cause
    The Colab runtime has no GPU (or no nvidia-smi). Warp then picks its CPU device: everything still runs, only far slower, and nothing raises.
    Fix
    Runtime > Change runtime type > GPU, then run the first cells again. Check in code with wp.get_cuda_device_count() > 0, which is how every course script sets ON_GPU and picks its budget (NWORLD = 4096 if ON_GPU else 8). On CPU all examples still work with the small budgets: that is how the course is verified.
    import warp as wp
wp.init()
print(wp.get_device(), "| CUDA devices:", wp.get_cuda_device_count())

    Owner: Ch 1 §5 · also Ch 4 §1

    "WARNING: Warp sees no GPU" although nvidia-smi shows one

    SetupGPU only
    Cause
    Warp could not load the CUDA driver for its build. warp-lang==1.19.0 from PyPI is built with CUDA 13 and needs an R580 or newer driver. The usual cause is a CUDA 13 Warp on an older driver, for example after installing warp-lang by hand. (The CUDA Version in the nvidia-smi header is the newest CUDA the driver supports, not what is installed.)
    Fix
    Reinstall with the setup cell: it reads the driver major from nvidia-smi --query-gpu=driver_version,name and installs NVIDIA's +cu12 release wheel of the same Warp version when the driver is older than 580. Then Runtime > Restart session: an imported Warp cannot be swapped inside a running Python process.
    WARP = ("warp-lang==1.19.0" if major >= 580 else
        "https://github.com/NVIDIA/warp/releases/download/v1.19.0/"
        "warp_lang-1.19.0+cu12-py3-none-manylinux_2_28_x86_64.whl")

    Owner: Ch 1 §5

    Warp CUDA warning: Could not find or load the NVIDIA CUDA driver on a CPU machine

    Setup
    Cause
    Warp prints this to stderr at import when there is no NVIDIA driver at all.
    Fix
    Nothing to fix on a CPU-only box: it is expected, and it is not part of any example's expected output. On a GPU runtime it means the driver did not load; see the previous entry.

    Owner: Ch 1 §5 · also Ch 4 §1

    PackageNotFoundError for md.version("mujoco"), or a broken import mujoco

    RaisesSetup
    Cause
    The distribution is called mujoco-core; the import name is still mujoco. Installing the mujoco distribution on top puts a second copy of the same package into site-packages.
    Fix
    Ask for md.version("mujoco-core"). Never pip install mujoco next to it. If it happened, uninstall both and rerun the setup cell.

    Owner: Ch 1 §5

    ImportError: mujoco.viewer requires 'glfw' to be installed.

    Raises
    Cause
    mujoco-warp was installed without the [viewer] extra. viewer.py imports mujoco.viewer at the top, and the extra is what pulls mujoco-core[rendering] (glfw, PyOpenGL) and pillow.
    Fix
    pip install "mujoco-warp[viewer]==4.0.1" "mujoco-core[rendering]==4.0.1", as the setup cell does. --viewer viser needs the extra too (plus mjviser>=0.0.13).

    JAX is CPU-only or broken after pip install jax on Colab

    Setup
    Cause
    Colab ships a matched jax + jaxlib + CUDA plugin; installing jax on top can replace one of them.
    Fix
    Use the preinstalled JAX. If you imported JAX before setting its environment variables, restart the runtime.

    Owner: Ch 28 §4

    Hundreds of Module ... load lines on the first step

    Setup
    Cause
    Warp 1.19 logs at INFO by default: one line per kernel module it compiles or loads.
    Fix
    Set the log level right after import warp, as every course script does.
    import warp as wp
wp.config.log_level = wp.LOG_WARNING
import mujoco_warp as mjw

    Owner: Ch 1 §5 · also Ch 4 §8

    error: expected member name or ';' when a kernel compiles

    Raises
    Cause
    Warp copies kernel parameter names into the generated C++ argument struct. A parameter named case, default, new, class, ... is a C++ keyword.
    Fix
    Rename the parameter.

    2Slow, pausing or recompiling7

    Speed problems. Rule of the course: CPU numbers are for checking that a script works; rank settings with your own GPU numbers from the notebook.

    The first mjw.step takes a long time; later calls are fast

    Slow
    Cause
    JIT compilation: Warp compiles each kernel module the first time it is needed and stores the binary in the kernel cache (wp.config.kernel_cache_dir). A new Colab runtime starts with an empty cache, so the first step compiles again.
    Fix
    Expected. Time a warm-up call separately and never include it in a benchmark. To force a cold start for a measurement, point wp.config.kernel_cache_dir somewhere new before wp.init() (what ex6_jit_timing.py --cold does).

    Owner: Ch 1 §5 · also Ch 4 §8, Ch 25 §1

    A pause of seconds after changing an option, then fast again

    Slow
    Cause
    Some options are compile-time constants of kernels: they go into a kernel factory (@cache_kernel) or through wp.static. A new value builds a new kernel on first use. Measured in Ch 24: ls_iterations and warn_overflow load new modules; switching solver, broadphase, the integrator or some disableflags bits can too, when they lead to kernels not loaded yet.
    Fix
    Set integer options once, before the first step and before any capture. Array options (timestep, gravity, tolerance, ...) never recompile: write them with fill_ / assign. Full list: the knob board.

    Owner: Ch 24 §4 · also Ch 7 §7, Ch 9 §10, Ch 20 §8, Ch 13 §1

    A training loop is much slower than mjwarp-testspeed

    SlowGPU only
    Cause
    Host reads. On a GPU, .numpy() waits for every queued kernel and then copies; get_data_into does about 140 such copies for one world. One call per step can cost more than the physics.
    Fix
    Keep data on the device: read batched arrays only for logging, or use them from a kernel or from PyTorch (zero-copy). Use get_data_into only to look at a world. Also compare like with like: testspeed applies keyframe ctrl plus noise; rerun it with --noise_std 0 and the same nworld and sizes.

    Owner: Ch 4 §2 · also Ch 5 §6, Ch 28 §1, Ch 25 §4

    Mean solver iterations is small, but the batch is still slow

    SlowGPU only
    Cause
    With capture_while the solver loop runs until its slowest world is done: one stuck world at 100 iterations makes every world pay for 100 iterations.
    Fix
    Look at d.solver_niter.numpy().max(), not the mean. Lower m.opt.iterations or find the stuck world.

    Owner: Ch 20 §10 · also Ch 24 §5

    Out of memory at large nv and nworld with the Newton solver

    RaisesGPU only
    Cause
    Newton allocates its Hessian as (nworld, nv_pad, nv_pad) float32 per solve, plus a second buffer of the same size when nv > 48 on the incremental path. At nv 120 that is 128 KB per world: 512 MB for 4096 worlds.
    Fix
    Use fewer worlds, or the CG solver (m.opt.solver = mjw.SolverType.CG before the first step and before capture), which has no H at all.

    Owner: Ch 20 §6 · also Ch 20 §10

    ValueError: testspeed available for gpu only

    Raises
    Cause
    testspeed._main checks the device before loading the model.
    Fix
    Run mjwarp-testspeed on a GPU. On CPU, time a hand-made loop instead (as Ch 25's examples do), and treat the number as a CPU number.

    Owner: Ch 25 §4

    Setting A beats B on CPU, but not on the GPU

    Slow
    Cause
    On CPU, Warp runs kernel threads one after another and every launch costs Python time, so rankings can flip.
    Fix
    Use CPU runs to check correctness only; rank settings with GPU numbers at the nworld you will train with, with graphs on in both runs.

    Owner: Ch 25 §1 · also Ch 25 §8

    3Errors from put_model: unsupported features7

    put_model checks every feature your MjModel uses against MJWarp's own enums and raises before anything is copied to the device. The full searchable list is the "supported?" explorer on API at a glance.

    NotImplementedError: mjSOL_PGS is unsupported. or ['mjGAIN_PID'] not supported.

    Raises
    Cause
    A scalar option (integrator, cone, solver) or an enum-typed array value (actuator gain/bias/dyn/trn types, equality, geom, sensor and wrap types, sleep policies) that MJWarp does not implement. The two message formats: scalar options say X is unsupported., arrays list the offending values. Known gaps in 4.0.1: the PGS solver, PID actuators, SO3 transmission and bias, distance and flexvert equalities.
    Fix
    Change the model: solver="Newton" or "CG", another actuator type, etc. You can derive the whole list from the enums (Example 1.7).

    Owner: Ch 1 §7 · also Ch 5 §2

    NotImplementedError: Body plugins not supported. (also Actuator, Sensor)

    Raises
    Cause
    Only SDF geometry plugins exist on the Warp side.
    Fix
    Remove the plugin, or for SDF geoms register a Warp SDF (next category).

    Owner: Ch 1 §7 · also Ch 18 §8

    NotImplementedError: Flex-HField collision is not implemented. (also Flex-SDF, Rigid flexes)

    Raises
    Cause
    put_model rejects any model with a flex plus a heightfield geom, a flex plus an SDF geom, or a rigid flex (flexcomp rigid="true"), even if they could never touch and even with contype="0" conaffinity="0".
    Fix
    Keep soft bodies and terrain in separate models; soft bodies on terrain are not possible in 4.0.1. Other flex refusals: dof=quadratic, self-collision or passive contact of interpolated flexes, flex equalities with sleeping.

    Owner: Ch 23 §5 · also Ch 23 §8, Ch 18 §5

    ValueError: flex elasticity is no longer integrated implicitly under integrator='implicit' and 'implicitfast' ...

    Raises
    Cause
    check_discrete, called at the top of every _forward, refuses flex stiffness with the implicit integrators.
    Fix
    Use integrator="discrete", or Euler with a small timestep. (noslip is in turn not implemented for the discrete integrator.)

    Owner: Ch 13 §5 · also Ch 23 §7

    I need float64 / results must match C MuJoCo bit for bit

    Silent
    Cause
    Everything on the device is float32; there is no float64 mode. put_model also raises the solver tolerance to at least 1e-6.
    Fix
    Compare against C MuJoCo with tolerances (about 1e-6 per step for stable systems) and compare statistics for long or chaotic rollouts. See float32 vs C.

    Owner: Ch 1 §7 · also Ch 5 §7

    An SDF model loads, but nacon stays 0

    Silent
    Cause
    The Warp SDF functions (user_sdf / user_sdf_grad, or register_sdf_plugins(mjw)) were patched in after the first put_model, forward, step or collision of the process. Later has no effect.
    Fix
    Register at the top of a fresh process. In a notebook: %%writefile + !python file.py, or restart the runtime and patch in the first cell. The CLI tools register mujoco.sdf.* plugins automatically for XML models (not .mjb).

    Owner: Ch 18 §9 · also Ch 18 §8

    SDF contacts report about half the penetration depth

    Silent
    Cause
    On the SDF path the reported dist is max(A, B) at the final point, not the penetration depth: for a flat overlap of depth h the best value is -h/2.
    Fix
    Do not compare SDF dist with primitive or convex colliders, which report the full depth.

    Owner: Ch 18 §7

    4Contacts and buffer overflow14

    MJWarp allocates every buffer once, in make_data. When one runs out, the kernel drops the extra work, sets a bit in d.overflow and keeps going. Owner: Ch 9.

    Overflow decoder Computed in your browser

    Type an integer (for example 9, or 0x408), or toggle the bits. Bits come from types.py::OverflowType in the 4.0.1 wheel (12 bits, ALL = 4095).

    Boxes sink into or fall through the floor; towers collapse; no exception

    Silent
    Cause
    A buffer overflowed and contacts or constraint rows were dropped. Overflow is silent: the only signals are a wp.printf line from the device and the bits in d.overflow.
    Fix
    Check d.overflow after the run (the bits are sticky until reset_data), decode it with the widget below or with describe_overflow(d) from my_env.py, and size the buffers with the Ch 9 recipe.
    import mujoco_warp as mjw
bits = d.overflow.numpy()
for w in range(len(bits)):
    names = [b.name for b in mjw.OverflowType if bits[w] & b]
    if names:
        print(f"world {w}:", " | ".join(names))

    Owner: Ch 9 §6 · also Ch 9 §7, Ch 9 §8

    d.overflow is 0 after mjw.forward, but contacts are missing

    Silent
    Cause
    The NEFC, BROADPHASE and NARROWPHASE checks live in the _next_time kernel at the end of the integrator: step reports them, forward and collision do not. (Bits set inside collision, such as CCD, HFIELD and EPA_HORIZON, can appear after forward.)
    Fix
    After a bare forward or collision, compare the counters yourself: d.nacon.numpy()[0] against d.naconmax, d.ncollision.numpy()[0] against d.naconmax, d.nefc against d.njmax.

    Owner: Ch 9 §1 · also Ch 15 §2

    nconmax looked big enough per world, but one world still lost contacts

    Silent
    Cause
    nconmax only multiplies into the size of one shared pool (naconmax): "one world may have more than nconmax contacts". njmax is the opposite: no world may have more than njmax constraints. BROADPHASE and NARROWPHASE compare global counters, so they light in every world at once, even worlds with no contacts.
    Fix
    Size the pool from the total over all worlds at the worst moment (naconmax), and njmax from the worst single world.

    Owner: Ch 9 §5 · also Ch 9 §2, Ch 9 §7

    Overflow appeared after adding distance or collision sensors

    Silent
    Cause
    Collision sensors are written into the same contact pool and count against naconmax.
    Fix
    Add their slots to the contact budget and check d.overflow.

    Owner: Ch 14 §5

    NARROWPHASE is set in a cloth scene while nacon stays well below naconmax

    Silent
    Cause
    The flex candidate arrays are naconmax long and hold every hit before de-duplication.
    Fix
    Size flex scenes from the overflow bit, not from nacon: the Ch 23 checkpoint needed nconmax = 192 where the Ch 9 recipe gave 48.

    Owner: Ch 23 §5

    CCD overflow - please increase naccdmax beyond ...

    Silent
    Cause
    Convex collision scratch rows ran out. One CCD row can produce up to 4 contacts; every box-box pair in contact takes a row, and with MULTICCD so does every face/face pair of boxes, cylinders and meshes.
    Fix
    Count pairs that penetrate or take multi-contact, not contacts, and size per world with nccdmax (plus a safety factor) so it follows nworld.

    Owner: Ch 17 §7

    height field collision overflow ... please adjust resolution

    Silent
    Cause
    Too many heightfield prisms for one geom pair; the warning is printed once per pair.
    Fix
    Decrease the number of hfield rows and columns, or the size of the colliding geom.

    Owner: Ch 18 §4

    linesearch iterations limit reached - please increase ls_iterations beyond 20

    Silent
    Cause
    The Newton linesearch hit ls_iterations in some step and set the LS_ITERATIONS bit. It is a warning: the step completes. Device prints are flushed late, which is why the line appears after your own output.
    Fix
    Usually harmless. To silence only this print: m.opt.warn_overflow &= ~mjw.OverflowType.LS_ITERATIONS, once, before the first step (it recompiles). Raising ls_iterations also recompiles.

    Owner: Ch 5 §9 · also Ch 9 §10, Ch 20 §8

    My test compares nacon with mjd.ncon and fails

    Silent
    Cause
    Contact counts differ from MuJoCo C on heightfields (4 vs up to 6 or more) and on SDF pairs; box-box and convex multi-contact also generate their own sets.
    Fix
    Compare physical outcomes (rest heights, forces, trajectories within a tolerance), and size buffers from MJWarp's own counts.

    Owner: Ch 18 §3

    No contact on the first step for an object placed exactly on the floor

    Silent
    Cause
    A corner at distance 0 is not a contact (0 < 0 + 0 is false). Gravity closes the gap within one step.
    Fix
    Harmless in a simulation; when you call mjw.collision on a hand-placed pose, place the object 0.5 to 1 mm into its support.

    Owner: Ch 16 §5

    Editing m.geom_contype after put_model changes nothing

    Silent
    Cause
    No rigid broadphase or narrowphase kernel reads the bitmasks at run time: they were folded into nxn_pairid once.
    Fix
    Edit the mujoco.MjModel (or the MJCF) and call mjw.put_model again. Note that an explicit <pair> re-enables pairs that the masks and exclusions would drop.

    Owner: Ch 15 §3 · also Ch 15 §10

    A distance sensor between far-apart geoms reads its cutoff with SAP

    Silent
    Cause
    The sweep-and-prune broadphase only visits neighbouring pairs, so the sensor override never runs on a far pair.
    Fix
    Use the NXN broadphase for such scenes, or keep sensor pairs close.

    Owner: Ch 15 §6 · also Ch 15 §7

    Cylinders or meshes wobble or slowly spin on a surface

    Silent
    Cause
    MULTICCD was disabled for speed: those pairs then get one contact each.
    Fix
    Re-enable it, or measure the stability of the scene before trading it for throughput.

    Owner: Ch 17 §6

    NVMAX is set with sleeping on

    Silent
    Cause
    More DOFs were awake at once in some world than nvmax allows.
    Fix
    Size nvmax for the worst world at the worst moment (start-up, resets); measure the peak with d.nv_awake.

    5NaNs, blow-ups and crashes8

    MJWarp has no safety net of its own and does not bounds-check arrays in normal mode. While you develop a kernel, wp.config.mode = "debug" (set before the first launch) compiles bounds checks into every array access.

    One world shows NaN and stays NaN; the learner is poisoned

    Silent
    Cause
    C MuJoCo's mj_checkPos / mj_checkVel / mj_checkAcc reset a simulation that produced NaN or huge values. MJWarp has no equivalent and no auto-reset (the DisableBit comment lists AUTORESET as unsupported).
    Fix
    Add a non-finite guard to your done mask and reset those worlds on the device (nonfinite_reset(m, d, done) in my_env.py), then mjw.reset_data(m, d, reset=done).
    mjw.step(m, d)
wp.launch(done_kernel, ...)          # landed / timeout
nonfinite_reset(m, d, done)          # NaN guard: only ever sets done[w] = True
mjw.reset_data(m, d, reset=done)
wp.launch(randomize_velocity, ...)   # after reset_data, before forward
mjw.forward(m, d)                    # fresh observations

    Owner: Ch 8 §10 · also Ch 1 §7

    A stiff spring or contact explodes, or ignores a tiny timeconst

    Silent
    Cause
    Explicit integration of a spring that is too stiff for the step size blows up. MuJoCo protects contacts: timeconst is clamped to at least 2 * timestep unless REFSAFE is disabled or the integrator is discrete.
    Fix
    Use a smaller timestep, or a softer solref (larger timeconst). For stiff joint damping, implicitfast treats damping implicitly at about Euler's cost.

    Owner: Ch 3 §3 · also Ch 3 §2, Ch 2 §4, Ch 13 §9

    Crash or corrupted memory after get_state

    Crash
    Cause
    get_state does not check the buffer size: an undersized buffer is written out of bounds (CPU: process crash; GPU: silent corruption).
    Fix
    Always allocate the buffer from mj_stateSize and assert the shape (the snapshot / restore helpers in my_env.py do).
    buf = wp.zeros((d.nworld, mujoco.mj_stateSize(mjm, sig)), dtype=float)
assert buf.shape == (d.nworld, mujoco.mj_stateSize(mjm, sig))

    Owner: Ch 8 §4 · also Ch 29 §6

    Segfault (exit 139) in a custom contact kernel

    Crash
    Cause
    d.contact.flex, elem and vert have shape (0,) when m.nflex == 0; writing them is an out-of-bounds write.
    Fix
    Never write those fields without a flex. Develop with wp.config.mode = "debug".

    Owner: Ch 9 §2 · also Ch 26 §6

    Segfault on the first step with SLEEP enabled and island="disable"

    Crash
    Cause
    In 4.0.1 the compacted solver buffers are allocated only when sleep is enabled (false when islands are disabled) or nvmax is given, but the solver tests only the SLEEP bit.
    Fix
    Drop the SLEEP flag when you disable islands, or pass nvmax to make_data.

    Owner: Ch 21 §4

    Garbage or a crash after set_length_range with many worlds

    Crash
    Cause
    It launches over (nworld, nu) and writes actuator_lengthrange[worldid, ...] without the round-robin wrap, so an unbatched output is written past its end.
    Fix
    Batch actuator_lengthrange to nworld first (Example 10.12).

    Owner: Ch 10 §8

    A tiled kernel hangs on the GPU but runs on CPU

    GPU onlyCrash
    Cause
    Tile operations are collectives: if some lanes return early or skip a tile_* call inside a divergent branch, the block deadlocks. On CPU there is one lane, so it runs.
    Fix
    Call tile functions unconditionally; put per-lane work in ordinary strided loops with a uniform trip count.

    Owner: Ch 26 §8

    rays(..., rc=rc) returns wrong hits in worlds > 0 or crashes

    Crash
    Cause
    With a flex in the model, the BVH stride per world is bvh_ngeom + bvh_nflexgeom, but rays uses bvh_ngeom (4.0.1 and still at 8f5b9f1).
    Fix
    Use rc=None (brute force) for scenes with flexes; rendering is not affected.

    6Wrong numbers without an error33

    The hardest bugs: everything runs, and the result is wrong. Most of them come from four habits: writing state without running forward, replacing arrays instead of writing into them, trusting CPU aliasing, and Python-level flags decided at put_model time.

    MJWarp and C MuJoCo trajectories differ

    Silent
    Cause
    MJWarp computes in float32, C in float64. For stable systems the difference stays around 1e-6 per step (Example 5.6: 7e-7 in qpos after 60 steps). Chaotic systems (a tumbling robot, a pile of objects, a long humanoid rollout) amplify any difference exponentially: after a few seconds neither run "is right".
    Fix
    Compare short horizons with tolerances, and statistics (energy, success rates, distributions over many worlds) for long ones.

    Owner: Ch 5 §7 · also Ch 22 §5

    d.time == 1.0 never becomes true, or an interval sensor fires one step late

    Silent
    Cause
    d.time is float32 and gets timestep added once per step: after 11 steps of 0.01 it reads 0.109999985; after a million steps the clock is off by 135 s.
    Fix
    Count steps with an integer, or compare with a tolerance of half a timestep; reset the clock with reset_data for long episodes; avoid sensor periods that are exact multiples of dt on the edge.

    Owner: Ch 5 §7 · also Ch 14 §6

    I wrote qpos, but xpos, contacts or sensors did not change

    Silent
    Cause
    Derived quantities are computed by the pipeline, not by the write.
    Fix
    Call mjw.forward(m, d) after writing state and before reading derived quantities (or rendering).

    Owner: Ch 2 §9 · also Ch 27 §4

    qacc is wrong by a lot after calling stages by hand

    Silent
    Cause
    fwd_position(factorize=False) + fwd_acceleration() solves with the factor qLD of an old qpos: no exception, no NaN.
    Fix
    Exactly one factorization per new qpos: fwd_position() + fwd_acceleration(), or fwd_position(factorize=False) + fwd_acceleration(factorize=True). After anything that changes d.M, call factor_m before solve_m.

    Owner: Ch 11 §9 · also Ch 7 §3

    RuntimeError: ... argument 'opt_timestep' expects an array ... but passed value has type float

    Raises
    Cause
    m.opt.timestep = 0.005 replaced the Warp array with a Python float. An existing graph silently keeps reading the old array.
    Fix
    Write into the array.
    m.opt.timestep.fill_(0.005)        # or m.opt.timestep.assign([0.005])

    Owner: Ch 5 §3 · also Ch 24 §4

    A change to a Data or Model field has no effect

    Silent
    Cause
    The field was replaced with a new array (d.qpos = wp.array(...)) instead of written. Kernels and captured graphs hold the old pointer; a replaced Model array also loses its _is_batched tag.
    Fix
    After make_data, write with assign, wp.copy, fill_, zero_ or a kernel. Replace Model arrays (to batch them) only before capture, keeping dtype and trailing shape.

    Owner: Ch 6 §5 · also Ch 6 §9, Ch 10 §2, Ch 29 §8

    assign accepted a wrongly shaped source

    Silent
    Cause
    wp.copy is a flat byte copy: it refuses a larger source but silently accepts a smaller one and never compares shapes. An (nworld - 1, nv) source leaves the last world untouched.
    Fix
    Assert the source shape yourself before assign.

    Owner: Ch 6 §4

    Stored arrays all show the last step (CPU), or a subtraction gives 0

    Silent
    Cause
    On Warp's CPU device .numpy() returns a zero-copy view of device memory; on a GPU it returns a fresh copy. Code that relies on either behaviour is wrong on the other device.
    Fix
    Call .copy() on every host array you keep across steps.
    zs.append(d.qpos.numpy()[:, 2].copy())

    Owner: Ch 6 §10 · also Ch 12 §9, Ch 4 §2

    Per-world density, viscosity or wind is ignored

    Silent
    Cause
    put_model decides once: m.has_fluid = bool(wind.any() or density > 0 or viscosity > 0) from the XML. With all three zero the fluid pass never runs.
    Fix
    Put a non-zero density, viscosity or wind in the XML of any model you randomize them on. (The inertia-box fluid model has no buoyancy term.)

    Owner: Ch 10 §3 · also Ch 6 §13

    Per-world conveyor speeds (geom_surfacevel) do nothing

    Silent
    Cause
    m.flg_surfacevel is a Python bool copied from the MjModel; the surface-velocity code is skipped when it is False.
    Fix
    Give at least one geom a nonzero surfacevel in the MJCF, or set m.flg_surfacevel = True after put_model.

    Owner: Ch 16 §9

    Randomizing one geom's friction has no effect

    Silent
    Cause
    Contact friction is the element-wise maximum of the two geoms' frictions (unless one has a higher priority). A floor at 1.0 dominates a box randomized below it.
    Fix
    Randomize both geoms of the pair, or use priority / explicit pairs.

    Owner: Ch 10 §3 · also Ch 10 §10

    Bigger randomized geoms keep the XML mass; subtree masses are identical across worlds

    Silent
    Cause
    MJWarp never recomputes body_mass / body_inertia from sizes, and set_const writes one shared row into an unbatched output.
    Fix
    Scale mass by s³ and inertia by s⁵ yourself, batch every derived output (body_subtreemass, ...) to nworld, then call set_const.

    Owner: Ch 10 §7 · also Ch 10 §5, Ch 30 §4

    There is no m.opt.impratio to randomize

    Raises
    Cause
    MJWarp stores m.opt.impratio_invsqrt = 1/sqrt(impratio), batched per world.
    Fix
    Write impratio_invsqrt.

    Owner: Ch 19 §8

    Hinge spring forces are off (e.g. by about 2 N)

    Silent
    Cause
    MJCF reads hinge springref, ref and range in degrees unless <compiler angle="radian"/>.
    Fix
    Set angle="radian" or give degrees.

    Owner: Ch 12 §2

    Policy actions drive the wrong actuators on a MuJoCo 4 model

    Silent
    Cause
    ctrl[i] drives actuator i only when every actuator has ctrlnum = 1.
    Fix
    Find an actuator's slots with actuator_ctrladr; size action spaces from m.nu, not m.nactuator.

    Owner: Ch 12 §8

    cacc, cfrc_int or cfrc_ext look wrong or stale

    Silent
    Cause
    They hold post-solve values only when m.opt.run_rne_postconstraint is set (default False) or a sensor needs it; otherwise cfrc_ext keeps whatever was in it.
    Fix
    Set m.opt.run_rne_postconstraint = True before you read them.

    Owner: Ch 11 §4 · also Ch 12 §5

    A force applied with xfrc_applied acts as a torque

    Silent
    Cause
    xfrc_applied is (force, torque) at the body's centre of mass, while the c* spatial vectors are (rotation, translation).
    Fix
    Put the force in slots 0-2 of xfrc_applied.

    Owner: Ch 11 §3

    Orientations are rotated about the wrong axis

    Silent
    Cause
    MuJoCo quaternions are (w, x, y, z); SciPy's as_quat() and Warp's built-ins (wp.quat_rotate, wp.transform, ...) use (x, y, z, w).
    Fix
    np.roll(q_xyzw, 1) from SciPy (or scalar_first=True); use MJWarp's math helpers or reorder with wp.quat(q[1], q[2], q[3], q[0]) before a Warp built-in. See the math toolkit.

    Owner: Ch 2 §3 · also Ch 4 §6

    Free-body angular velocity looks rotated

    Silent
    Cause
    qvel[0:3] of a free joint is world-frame linear velocity, qvel[3:6] is angular velocity in the body frame.
    Fix
    Rotate with xmat to get world-frame angular velocity.

    Owner: Ch 3 §4 · also Ch 13 §2

    Mocap targets jump back after a reset

    Silent
    Cause
    reset_data sets mocap_pos / mocap_quat back to the model (or keyframe) values.
    Fix
    Run your target kernel again after every reset, before the next step.

    Owner: Ch 8 §5

    expects an array with dtype=int32 from reset_data_keyframe

    Raises
    Cause
    The keyframe array must be int32 (wp.array(np.array([...])) gives int64 on Linux); only the array form treats an out-of-range id as "skip".
    Fix
    wp.array(ids, dtype=int).

    Owner: Ch 8 §2

    The control callback runs four times per step / sees odd states

    Silent
    Cause
    Under RK4 the callback runs once per stage; stages 2-4 see intermediate qpos/qvel while sensordata still holds stage-1 values. step1/step2 integrate with Euler when the model uses RK4.
    Fix
    Keep callbacks cheap, side-effect-free functions of the state; with RK4 and a controller, set ctrl before mjw.step.

    Owner: Ch 8 §7 · also Ch 13 §4

    Nothing moves with njmax=0 (4.0.1)

    Silent
    Cause
    With njmax == 0 the 4.0.1 solver returns early without filling d.efc.Ma, which the Euler damping solve (and IMPLICITFAST, IMPLICIT) uses.
    Fix
    Never pass njmax=0 to make_data with these integrators.

    Owner: Ch 13 §3

    A long actuator or sensor delay acts like a shorter one

    Silent
    Cause
    The delay buffer holds nsample samples; reads before the oldest sample return the oldest value. read_sensor also subtracts the delay for you.
    Fix
    Size nsample from the largest delay (incl. randomized ones); pass the time at which you want the delayed reading.

    Owner: Ch 14 §8

    A rangefinder on a world-body camera reads -1

    Silent
    Cause
    Rays exclude the body that carries the site or camera: body 0 excludes every static geom, the floor included.
    Fix
    Mount the sensor on a separate static body.

    Owner: Ch 14 §5

    Observations and sensors disagree by one step

    Silent
    Cause
    Sensors are computed inside forward at the start of mjw.step, so after a step they describe the state before the integrator moved it.
    Fix
    Pack observations after a forward, or from sensors only.

    Owner: Ch 26 §2

    A force callback sees unclamped ctrl

    Silent
    Cause
    The actuator kernel clamps ctrl into a local variable; d.ctrl is not modified (and with delays the kernel used the delayed ctrl).
    Fix
    Clamp with m.actuator_ctrlrange in your kernel.

    Owner: Ch 26 §4 · also Ch 8 §8

    Reproducibility tests pass on CPU and fail on the GPU

    GPU onlySilent
    Cause
    Float atomics sum in arbitrary order on a GPU, so low bits change; contact order also changes. CPU runs are deterministic either way.
    Fix
    Run reproducibility tests on the GPU; select contacts by contact.worldid and compare buffers in canonical order; m.opt.deterministic helps only partly in 4.0.1 (only its ATOMICS bit has an effect; the CONTACTS and CONSTRAINT sorts are empty stubs), so for bitwise replays use the replay technique and measure the cost.

    Owner: Ch 22 §1 · also Ch 22 §2, Ch 22 §3, Ch 22 §6

    Rigid contacts carry stale flex ids

    Silent
    Cause
    In 4.0.1 rigid colliders never reset flex/elem/vert of a reused slot.
    Fix
    A side is a flex exactly when contact.geom is -1 on that side.

    A cloth falls away from its pins

    Silent
    Cause
    For a dim=2 flex, elastic2d defaults to "none": young and thickness alone give no forces.
    Fix
    Set elastic2d="stretch", "bend" or "both".

    Owner: Ch 23 §1

    Gradients grow every iteration

    Silent
    Cause
    tape.zero() was forgotten, or not captured inside the graph before the backward.
    Fix
    Zero the tape every iteration (inside the graph when you capture).

    Owner: Ch 29 §2

    A tensor kept from MJWarp changes by itself; JAX results depend on earlier calls

    Silent
    Cause
    wp.to_torch views alias live memory. A JAX op that closes over d is not pure: time, warmstart, ctrl and contacts persist between calls.
    Fix
    Clone what you keep; pass hidden state in and out explicitly.

    Owner: Ch 28 §1 · also Ch 28 §4

    The agent learns to end episodes immediately

    Silent

    Fix
    Keep per-step rewards non-negative in states you want, or add an explicit failure penalty.

    7CUDA graph capture and replay8

    A CUDA graph records launches once and replays them; conditional nodes loop on device. Owner: Ch 24. The three verdicts for any change: live (array, read at replay), recapture (Python value baked into the recording), recompile + recapture (a kernel constant).

    Capture fails, or hangs, around .numpy() / print(arr)

    RaisesGPU only
    Cause
    A device-to-host copy needs the device to finish, which is impossible while the stream is being recorded.
    Fix
    No .numpy(), .item() or prints of arrays inside wp.ScopedCapture(). Read results after wp.capture_launch; wp.printf inside kernels is fine.

    Owner: Ch 24 §2

    Capture fails on an old driver, with a CUDA version < 12.4 detected warning

    RaisesGPU only
    Cause
    Conditional nodes (capture_while in the solver) need CUDA 12.4+ in both toolkit and driver. put_model only warns and still sets graph_conditional = True.
    Fix
    Set the flag before capturing (it is itself a baked knob); the setup cell's GRAPH_COND tells you which case you are in. Consider lowering m.opt.iterations, because the fallback unrolls the iterations.
    if not wp.is_conditional_graph_supported():
    m.opt.graph_conditional = False      # before wp.ScopedCapture()

    Owner: Ch 24 §6 · also Ch 1 §5

    Changing m.opt.iterations, integrator, solver, flags or callbacks has no effect on replay

    Silent
    Cause
    Integer and bool options and callbacks are read by Python while recording; the graph replays what was recorded.
    Fix
    Recapture after any change to an integer option, a flag or a callback. Array options are live.

    Owner: Ch 24 §4 · also Ch 13 §1, Ch 7 §7, Ch 26 §3

    A randomized field is ignored after capture

    Silent
    Cause
    A graph stores the pointers of the arrays it read: a replaced array is never seen.
    Fix
    Replace arrays before capture; afterwards only write into them.

    Owner: Ch 10 §2 · also Ch 6 §5, Ch 29 §8

    A counter, print or Python if inside a callback runs only once

    Silent
    Cause
    Callbacks run on the host during capture; only their kernel launches are recorded.
    Fix
    Keep all decisions inside kernels.

    Owner: Ch 8 §9 · also Ch 26 §3

    Results of a captured helper are never updated

    Silent
    Cause
    The helper allocated its output during capture; the replay writes into memory Python never sees again. Inside a conditional node body you cannot allocate at all.
    Fix
    Allocate outputs before capturing and pass them in.

    Owner: Ch 24 §8 · also Ch 24 §2

    Mass randomization with set_const inside a graph

    GPU only
    Cause
    set_const clones arrays and relaunches over every world; capturing it on a GPU is unverified in this course.
    Fix
    Keep mass DR eager, at rollout boundaries; in-place fields (friction, damping, gains, gravity) can be re-drawn inside the graph.

    Owner: Ch 10 §11 · also Ch 30 §9

    RuntimeError: Device cpu is not a CUDA device

    Raises
    Cause
    Something called a CUDA-only API on CPU: mjwarp-record (wp.get_stream() in cli.unroll) or an EventTracer scope (wp.Event(enable_timing=True)).
    Fix
    Run the CLI on a GPU, or the same loop by hand on CPU; pass enabled=ON_GPU to the tracer.

    8Rendering, viewer and recording10

    Two render paths: copy one world to the host and use mujoco.Renderer (OpenGL), or ray-trace every world on the device with the batch renderer. Ch 5 §8 compares them; Ch 27 owns the batch renderer.

    ImportError when constructing mujoco.Renderer

    RaisesSetup
    Cause
    No PyOpenGL, or MUJOCO_GL=egl without an EGL library. The backend must be chosen before import mujoco; if mujoco was imported with another backend, the choice is fixed until a restart.
    Fix
    In rendering notebooks the setup cell sets MUJOCO_GL=egl first. Catch Exception and fall back to the MJWarp batch renderer (Examples 2.12, 5.9).
    import os
os.environ.setdefault("MUJOCO_GL", "egl")   # before "import mujoco"
import mujoco

    Owner: Ch 2 §12 · also Ch 5 §8

    mjwarp-viewer does not open on Colab

    Setup
    Cause
    The native viewer (mujoco.viewer.launch_passive) needs a display; Colab has none.
    Fix
    On Colab, record instead: mjwarp-record (GIF/WebP) or the batch renderer + mediapy. --viewer viser runs in a browser, but on Colab it would need a tunnel (unverified). Locally with a display the native viewer works; on CPU it prints Running Warp unoptimized on CPU.

    mjwarp-record fails on CPU

    Raises

    Fix
    Run it on a GPU; on CPU, run the same loop by hand (Example 5.11).

    Owner: Ch 5 §9

    mjwarp-record ... --video humanoid.mp4 stops with an unknown flag

    Raises
    Cause

    Fix
    --output humanoid.gif (or .webp).

    Owner: Ch 5 §9

    ValueError: Segmentation channel requested for recording, but segmentation rendering is disabled.

    Raises
    Cause
    --channel segmentation needs the render context to render segmentation, and --render_seg defaults to false. Depth works without a flag because --render_depth defaults to true. Both channels need --render_mode warp (otherwise: ... channel recording is only supported under the 'warp' rendering mode.).
    Fix
    Pass --render_seg true together with --render_mode warp.
    mjwarp-record model.xml --output seg.gif --render_mode warp --channel segmentation --render_seg true

    Owner: Ch 5 §9 · also Ch 27 §11

    Batch-rendered images are 1x1, garbled, transposed or stale

    Silent
    Cause
    cam_res is (width, height) but images come out (nworld, height, width); the get_* kernels trust your output shape. Without cam_res and render_rgb the camera's MJCF attributes decide. The BVH must be refit before every render, after the poses are computed.
    Fix
    Every frame: step/forward → (write hand-set cameras) → refit_bvh → render → get_rgb(rc, camera_index, rgb_out) with an (nworld, H, W) output. Check rc.rgb_adr.numpy()[cam] >= 0. The model needs at least one camera.

    A camera position I set is ignored

    Silent
    Cause
    camlight recomputes cam_xpos / cam_xmat in every forward/step.
    Fix
    Write hand-set cameras after step/forward and before refit_bvh / render, every frame.

    Owner: Ch 27 §7

    A lidar does not see collision-only geoms

    Silent
    Cause
    With rc=, only geoms in the BVH can be hit, and the BVH holds only enabled_geom_groups (default [0, 1, 2]), separate from the ray geomgroup mask.
    Fix
    Add the group to enabled_geom_groups, or use rc=None.
