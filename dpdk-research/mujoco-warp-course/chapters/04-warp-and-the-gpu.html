    NVIDIA Warp and How a GPU Runs Your Kernel

    MJWarp is MuJoCo written as a few hundred small Warp kernels. Before you can read it, debug it or extend it, you need Warp itself: arrays that live on a device, kernels that run once per thread, and a mental picture of what the GPU does with those threads. This chapter builds that picture from the ground up and ends by reading a real MJWarp kernel line by line.

    Beginner About 2.5 h (tiles and factories are optional)· Prerequisites: Ch 1, Ch 2

    • Write @wp.kernels and @wp.funcs, and launch them in 1-D and 2-D.
    • Explain warps, blocks, grids, SMs, divergence, coalescing, shared memory and occupancy.
    • Understand JIT compilation and caching, wp.static, atomics and correct timing.
    • Avoid the wp.quat storage pitfall, and read forward.py::_next_velocity.

    1Devices: where your data lives

    Warp is a Python library from NVIDIA. You write ordinary-looking, typed Python functions; Warp translates them to C++ or CUDA, compiles them, and runs them on a device. There are two kinds of device: "cpu" (always present) and one "cuda:N" per NVIDIA GPU. The Python program itself always runs on the CPU; we call that side the host.

    The key idea of GPU programming is that the host and the GPU have separate memories. An array created on "cuda:0" lives in GPU memory; Python only holds a handle to it. Kernels run where the data is, and moving data between the two sides crosses a comparatively slow bus. Everything in MJWarp is designed so that the data stays on the GPU while you step: mjw.Data is a bag of device arrays, and mjw.step only queues kernels that read and write them.

    Three calls cover devices:

    Pitfall: Warp silently falls back to the CPU

    If Warp sees no GPU (wrong Colab runtime, missing driver), the default device is cpu and everything still runs, just slowly. On this box Warp prints Warp CUDA warning: Could not find or load the NVIDIA CUDA driver to stderr. That is why every script in the course has the budget block ON_GPU = wp.get_device().is_cuda and the notebook's setup cell prints the device.

    2Arrays: wp.array, dtypes and shapes

    A wp.array is a typed block of memory on one device, with up to four dimensions. Three facts describe it: its dtype (what one element is), its shape (how many elements along each axis) and its device. In Warp, float means 32-bit float and int means 32-bit int. MJWarp is float32 throughout, while C MuJoCo is float64, which is why the course compares the two with tolerances near 1e-5.

    The dtype can be a small vector or matrix. wp.vec3 is three floats, wp.quat four, wp.mat33 nine, and wp.spatial_vector six (MuJoCo's rotation:translation pairs). The Warp shape counts elements, so wp.zeros(4, dtype=wp.vec3) has shape (4,), but its NumPy copy has shape (4, 3): the vector components become a trailing NumPy axis. This is exactly how MJWarp's Data is declared in types.py: xpos: array("nworld", "nbody", wp.vec3) has Warp shape (nworld, nbody) and NumPy shape (nworld, nbody, 3).

    Pitfall: .numpy() is a synchronization point

    On a GPU, .numpy() first waits until every queued kernel has finished, then copies. One call per step in a training loop can cost more than the physics. Keep data on the device and read it back only for logging or plotting. (Example 4.1 also shows the CPU surprise: there, .numpy() is a view, so writing into it changes the Warp array. Code that relies on either behavior is a bug on the other device.)

    Note: shapes in MJWarp

    The real shape of a Data field is set by make_data; the symbolic shape in types.py ("nworld", "nq", "*") is metadata written by the types.array(...) helper. Batched layouts, the "*" Model axis and worldid % shape[0] are the subject of Ch 6.

    3Kernels and threads

    A kernel is a Python function decorated with @wp.kernel. It is not called directly. Instead you launch it with wp.launch(kernel, dim=..., inputs=[...], outputs=[...]), and Warp runs the body once for every index in dim. Each run is a thread, and inside the body wp.tid() tells the thread which index it is. A launch over one million elements starts one million threads; there is no loop in your code.

    Kernel rules follow from the fact that the body is compiled to C++/CUDA:

    • Every parameter has a type annotation: float, int, wp.vec3, wp.array[float], wp.array2d[wp.vec3], and so on. (MJWarp writes the bracket form wp.array[float]; the older wp.array(dtype=float) is equivalent.)
    • A kernel returns nothing. Results are written into output arrays. inputs and outputs are concatenated in order to fill the parameters; the split is a convention for readers and for differentiation.
    • Only a typed subset of Python works inside: arithmetic, if, for i in range(n), while, Warp built-ins and @wp.funcs. No lists, dicts, NumPy or prints of Python objects (wp.printf exists for debugging).
    • A local that is reassigned in a loop must be typed at its first assignment, e.g. total = float(0.0).

    The last line matters for MJWarp: launch sizes come from the model (m.nv, m.nu, m.nsensor, ...), and many models have zero of something. The repository's CONTRIBUTING.md tells contributors not to wrap launches in if n > 0: when the size is already the launch dimension: "Launching with dimension 0 is a safe no-op in Warp."

    Two-dimensional launches

    Pass a tuple as dim and wp.tid() returns one index per dimension. MJWarp's most common launch is dim=(d.nworld, m.nv) with worldid, dofid = wp.tid(): one thread per (world, DOF) pair. Threads are numbered with the last dimension varying fastest, the same row-major order as the arrays, so thread (w, j) and thread (w, j+1) are neighbours. Section 4.5 shows why that matters.

    Pitfall: parameter names become C++ names

    Warp copies kernel parameter names into the generated C++ argument struct. While writing Example 4.6 we named a kernel parameter case, and the CPU build failed with error: expected member name or ';' at wp::int32 case;. Avoid C++ keywords (case, default, new, class, ...) as parameter names.

    4How a GPU runs your kernel

    A CPU core is built to run one stream of instructions as fast as possible: deep pipelines, branch prediction, big caches. A GPU makes the opposite trade. It has many small, simple cores and hides slow memory not with caches but with sheer numbers of threads: while some threads wait for data, others compute. Understanding five ideas is enough to reason about almost every performance decision in MJWarp: the hardware units, the thread hierarchy, scheduling in waves, divergence and coalescing.

    4.1 The hardware: SMs, lanes, registers, shared memory

    An NVIDIA GPU is a collection of streaming multiprocessors (SMs). Each SM has execution lanes, a large register file (the fastest storage, private to each thread), a block of on-chip shared memory (shared by the threads of one block), and warp schedulers that pick which group of threads issues its next instruction. All SMs share an L2 cache and the large, slow global memory where every wp.array lives. Small GPUs have a few dozen SMs, data-center GPUs more than a hundred.

    4.2 Threads, warps, blocks and grids

    Your launch's threads are grouped at three levels. Hardware groups 32 consecutive threads into a warp (the word clash with "Warp the library" is a coincidence). Warp the library groups threads into blocks of block_dim threads (default 256, i.e. 8 warps); a block runs on one SM and its threads can share memory and synchronize. All blocks of one launch form the grid. wp.tid() hides all of this: it is the thread's global index, decoded into your dim tuple.

    4.3 Scheduling in waves, and occupancy

    The GPU does not start all blocks at once. Each SM can hold only so many threads, blocks and registers at a time. The block scheduler fills every SM up to its limit; whenever a block finishes, the next one takes its place. When the grid is much larger than what fits, the blocks run in successive waves. Occupancy is the fraction of an SM's warp slots that are in use: high occupancy means more warps to switch to while others wait for memory. Two consequences matter for MJWarp:

    • Small launches waste the GPU. With 8 worlds and nv = 27 you launch 216 threads: one block, one SM busy, the rest idle. That is why MJWarp shines at thousands of worlds, and why the course's GPU budget is NWORLD = 4096.
    • The last wave can be ragged. If the grid is 1.1 waves, the second wave keeps only a tenth of the GPU busy. MJWarp sizes some launches from the hardware: collision_convex.py::_ccd_grid_size and solver.py::_jtdaj_groups_per_world ask wp.get_suggested_block_size how many threads fill the device and launch "a few device waves" instead of one mostly idle thread per buffer slot (Ch 17, Ch 20).

    4.4 Divergence: when lanes disagree

    The 32 lanes of a warp share one instruction stream. If they reach an if and some lanes want the then side while others want the else side, the warp cannot do both at once. It runs the then side with the other lanes masked off, then the else side with the first group masked off, then the lanes reconverge. This is divergence: the cost of a divergent branch is the sum of both sides, not the maximum. If all 32 lanes agree, the untaken side is skipped entirely, so branches are only expensive when neighbours disagree.

    MJWarp limits divergence at the design level. The convex narrowphase launches one kernel per pair of geom types, so every thread of a launch runs the same collision routine (collision_convex.py, Ch 17). The primitive narrowphase is a single kernel, collision_primitive.py::_primitive_narrowphase, whose if type1 == ... and type2 == ... chain is built with wp.static and contains only the pair types present in the model, so lanes can still diverge, but only between pairs that actually exist (Ch 16). Compile-time flags become wp.static branches that are removed from the code (section 7).

    4.5 Coalescing: neighbours should read neighbours

    Global memory is not read one float at a time. The hardware fetches aligned segments (32-byte sectors, grouped into 128-byte lines). When the 32 lanes of a warp load 32 consecutive floats, those 128 bytes arrive as one line: the access is coalesced. When each lane reads an address a whole row apart, the warp needs 32 separate sectors and uses 4 bytes of each. Same instructions, up to 8x the bytes moved (32 separate sectors instead of 4).

    This is why the order of the launch dimensions must match the order of the array dimensions. MJWarp stores state as (nworld, n) row-major arrays and launches dim=(d.nworld, n) with worldid, i = wp.tid(): the fastest-varying thread index walks the contiguous axis. Flip either one and every warp becomes strided. (One-thread-per-world kernels that read a short row, like the reward kernels of Ch 26 §2, are strided by the row length; for small rows the caches absorb most of it.)

    4.6 Shared memory, registers and occupancy

    Two resources decide how many warps an SM can keep resident, and therefore its occupancy:

    • Registers. Each thread's locals live in registers. If a kernel needs many (long functions, big unrolled loops, many vec3/mat33 temporaries), fewer warps fit. This is one reason MJWarp splits the pipeline into many small kernels instead of one huge one.
    • Shared memory. A block that reserves a large tile in shared memory leaves room for fewer blocks on the same SM. MJWarp's tiled kernels (Cholesky factorization in smooth.py, solver reductions in solver.py) pick their block_dim per kernel family through the experimental types.BlockDim settings stored as m.block_dim.

    Occupancy is not a goal in itself; a kernel limited by memory bandwidth needs enough warps in flight to keep the memory system busy, and beyond that more warps do not help. Ch 25 shows how to measure instead of guessing.

    4.7 What changes on Warp's CPU device

    Warp's CPU backend compiles the same kernel to native code and runs a launch as a plain loop over all thread indices, in index order (Example 4.3 recorded it). There are no lanes, so no divergence; there is no shared memory, so tiles use ordinary memory; and a launch returns only when the loop is done, so timing needs no synchronization (Example 4.10, section 10). Blocks collapse too: Warp's config says that, unless wp.config.enable_cpu_blocks (experimental) is set, "CPU launch block dimensions greater than one resolve to one". MJWarp's code is written to stay correct when wp.block_dim() is 1:

    5Device functions: @wp.func

    A kernel is an entry point: it is launched from Python and returns nothing. A @wp.func is a helper that runs on the device and is called from kernels or other funcs. It takes typed arguments, may return a value (or a tuple), and is usually inlined by the compiler, so calling it usually costs nothing. You cannot launch a func. Its parameters can be values or wp.arrays, which the func may index and write into, even with atomics: MJWarp's collision_core.py::write_contact takes the contact arrays and does wp.atomic_add(nacon_out, 0, 1) itself.

    MJWarp's _src/math.py is almost entirely funcs (30 @wp.func definitions in the 4.0.1 wheel): quaternion products, rotations, frame transforms. Because they follow MuJoCo's conventions, the course reuses them rather than re-deriving the math. They are internal (_src), so they carry the private badge.

    6The wp.quat storage pitfall

    Recall from Ch 2

    MuJoCo quats are (w,x,y,z); Ch 2 §3 and its quaternion card.

    wp.quat is just four floats. Warp's own quaternion built-ins (wp.quat_rotate, wp.quat_identity, wp.transform, ...) interpret them as (x, y, z, w), with the scalar last. MJWarp stores MuJoCo's (w, x, y, z) in the same four slots: d.xquat, m.body_quat and the quaternion part of a free joint's qpos all have w in slot 0. Nothing in the type system notices the difference. Handing an MJWarp quaternion to a Warp built-in silently rotates about the wrong axis.

    Pitfall: never pass an MJWarp quaternion to a Warp built-in

    Use MJWarp's helpers (math.rot_vec_quat, math.quat_to_mat, math.mul_quat), or reorder explicitly: wp.quat(q[1], q[2], q[3], q[0]). The repository's CONTRIBUTING.md states the rule: "All public APIs, Model, and Data fields follow the MuJoCo convention (w, x, y, z). Explicitly convert or document when passing to native Warp functions (wp.transform)." The wrong answer in Example 4.5 is not random: the MuJoCo-ordered [0.7071, 0, 0, 0.7071] read as (x, y, z, w) is a 90 degree turn about x, which leaves (1, 0, 0) where it was.

    7Compile-time specialization: wp.static

    Ordinary ifs in a kernel are decided per thread at run time. wp.static(expr) is evaluated once, in Python, while Warp generates the code. Inside if wp.static(flag): the untaken side is simply not emitted, and for _ in range(wp.static(n)): has a constant trip count the compiler can unroll. The expression may read Python variables that are in scope when the kernel is defined, typically the arguments of a function that builds the kernel: a kernel factory.

    MJWarp uses this everywhere option flags would otherwise create branches: sleep on/off, the integrator, the cone type, determinism. Each combination becomes its own small, branch-free kernel. The flip side is that changing such a flag means a different kernel, which means a compile the first time and, under a CUDA graph, a recapture (Ch 24).

    The module name ends in the module hash. Both specializations have the same Python source, but the hash also covers the resolved wp.static values, so they hash differently: two modules and two compiles. Calling the factory again with the same flag produced the same kernel object (Warp 1.19 recognized the identical unique module).

    Going deeper: factories, module="unique", enable_backward=False

    module="unique" gives a kernel its own Warp module instead of sharing the module of the Python file it is defined in. Factories need it: every specialization is a separate kernel, and sharing one module would mean recompiling all of them whenever one is added. The module name then encodes the factory, as in the make_clip__locals__clip_... names above.

    enable_backward=False skips generating adjoint (reverse-mode gradient) code, which roughly halves the generated code and the compile time. MJWarp sets it module-wide at the top of most files, e.g. forward.py and smooth.py call wp.set_module_options({"enable_backward": False}) and collision_core.py also passes "default_grid_stride": False. Gradients through MJWarp therefore need explicit adjoint rules (Ch 29).

    Caching factories. MJWarp wraps its factories in warp_util.cache_kernel, a dictionary whose key is a hash of each positional argument (lists are hashed as tuples, and any argument with a .size attribute, such as an array or a NumPy value, is reduced to that size) plus the function's module and name. Two different arrays of equal size therefore map to the same cached kernel, so only pass values that really define the specialization. The same Python kernel object is returned every time (the source comment says it exists "to avoid crashes in graph_conditional code"). Writing your own factories with it is the subject of Ch 26 §7, which owns cache_kernel.

    8JIT compilation and the kernel cache

    Nothing is compiled when you write @wp.kernel. On the first launch on a device, Warp takes the whole module the kernel belongs to (by default, every kernel and func in the same Python file), generates C++ source (for the CPU) or CUDA C++ (for a GPU), compiles it, and loads the binary. This is just-in-time (JIT) compilation. The module is identified by a hash of its kernels' Python source, argument types, referenced constants and functions, the resolved wp.static values and the module options. Code generation itself runs only on a cache miss. The result is stored in the kernel cache (wp.config.kernel_cache_dir; ~/.cache/warp/1.19.0 on Linux, including Colab). The next process that needs the same hash loads the binary instead of compiling it.

    Warp reports each module load at INFO level, and INFO is Warp 1.19's default. A first mjw.step loads dozens of modules, so an unconfigured script prints dozens of lines. This is the one place the course shows that output; everywhere else the import block sets wp.config.log_level = wp.LOG_WARNING right after import warp (wp.config.quiet does not exist in 1.19). Example 4.12 catches the lines with wp.set_logger so it can count them.

    Tip: notebooks and the __main__ module

    In a notebook every kernel you define lives in the module __main__. Defining a new kernel in a later cell changes that module's hash, so the next launch recompiles all notebook kernels together. It is harmless but explains the occasional slow cell; module="unique" on a kernel isolates it.

    9Atomics, and why float sums depend on order

    Threads run concurrently, so two threads that do total[0] = total[0] + x at the same time can both read the old value and one update is lost. An atomic operation such as wp.atomic_add(total, 0, x) performs the read-add-write as one indivisible step and returns the old value. MJWarp uses atomics to reserve slots in shared buffers: in collision_core.py::write_contact each new contact does cid = wp.atomic_add(nacon_out, 0, 1) to claim the next free contact index (Ch 9).

    Atomics remove lost updates, but not ordering. Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) because each addition rounds. On a GPU the order in which threads reach the accumulator changes from run to run, so a float sum built by atomics can change in its low bits between two identical runs. Integer atomics (counting) are exact; float atomics are not reproducible bit for bit.

    Two lessons hide in this output. First, a long serial float32 sum (the CPU device's atomic loop) accumulates rounding error: about 4.7 here, while NumPy's pairwise float32 sum is off by only 0.014. Second, the 8-value case is deliberately extreme (1e8 swallows small numbers in float32), but it is the same effect that makes the last digits of a GPU contact-force sum flicker between runs.

    Teaser: determinism

    Float atomics sum in an arbitrary order, so the low bits of a sum can change between runs. MJWarp has an opt.deterministic mode (types DeterminismType: CONTACTS, CONSTRAINT, ATOMICS) that trades some speed for bitwise-reproducible runs. The full treatment is Ch 22.

    10Timing GPU code correctly

    On a GPU, wp.launch does not run the kernel; it appends it to a stream, a queue that the GPU drains in order, and returns at once. Python races ahead while the GPU works. A timer that stops right after the launch measures how long it took to queue, not to run. To time device work, make the host wait: wp.synchronize() blocks until every queued kernel has finished, and wp.ScopedTimer(name, synchronize=True) does that for you on entry and exit. Also warm up once first, or you time the JIT compile.

    Tip: the course's timing recipe

    Warm up once (JIT), call wp.synchronize() before starting and before stopping the clock, repeat and keep the best or the median, and report throughput (world-steps per second). Without a CUDA graph, timing mjw.step for a small model mostly measures Python launch overhead; Ch 24 removes it.

    11Going deeper: a tiles preview

    Everything so far used independent threads. Some work, such as summing a row or factorizing a small matrix, is faster when the threads of a block cooperate through shared memory. Warp exposes that with tiles. This section is optional; Ch 26 §8 owns the topic.

    Going deeper: wp.launch_tiled, wp.tile_load, wp.tile_sum, wp.tile_store

    wp.launch_tiled(kernel, dim=[nworld], block_dim=32, ...) starts block_dim threads for each logical index, here one block per world. Inside, wp.tid() is the logical index (the world), and tile operations are collective: every thread of the block calls them. wp.tile_load(data[worldid], shape=(64,)) loads one world's row into a tile, the threads split the elements between them; wp.tile_sum reduces it in a tree; wp.tile_store writes the 1-element result. Tile shapes must be compile-time constants, which is why MJWarp's tiled kernels (Cholesky in smooth.py, solver reductions in solver.py) are factories keyed on sizes.

    In short: a tiled launch gives each logical index a block of threads that share memory (Ch 26 §8).

    13Check yourself

    Quiz

    a = wp.zeros((8, 5), dtype=wp.vec3). What are a.shape and a.numpy().shape?

    Warp counts elements; NumPy appends the vector dims. Same as d.xpos: Warp (nworld, nbody), NumPy (nworld, nbody, 3).

    A kernel is launched with dim=(nworld, nv) and starts with worldid, dofid = wp.tid(). Which index differs between two consecutive threads (same warp)?

    The last launch dimension varies fastest, so neighbouring threads touch neighbouring elements of a (nworld, nv) array: coalesced.

    Why is calling d.qpos.numpy() once per step in a GPU training loop a bad idea?

    It is a synchronization point plus a transfer over the bus. Keep data on the device; read it back only to log or plot.

    What is a warp (the hardware one)?

    32 lanes share an instruction stream; this is the unit of divergence and of coalescing.

    Half the lanes of a warp take the if side (4 cycles) and half the else side (4 cycles). Roughly how long does the warp spend in the branch?

    Divergent branches cost the sum of both sides. If all lanes agree, the untaken side is skipped.

    Why does MJWarp turn option flags into if wp.static(flag): branches inside kernel factories?

    The untaken side is not emitted: no divergence, fewer registers. Cost: one module per specialization.

    On a GPU you time wp.launch(k, ...) by reading the clock right after it returns. What did you measure?

    Launches are asynchronous. Use wp.synchronize() or wp.ScopedTimer(..., synchronize=True).

    q = d.xquat.numpy()[0, 1] gives [0.7071, 0, 0, 0.7071]. What rotation is it, and can you pass the wp.quat directly to wp.quat_rotate?

    MJWarp stores (w, x, y, z) in wp.quat slots; Warp built-ins read (x, y, z, w).

    A float32 total built with wp.atomic_add by a million threads differs in its last digits between two identical GPU runs. Why?

    Each addition rounds; a different order rounds differently. Ch 22 shows MJWarp's deterministic mode.

    On Warp's CPU device (default config), what is wp.block_dim() inside a kernel launched with wp.launch_tiled(..., block_dim=32)?

    CPU block dimensions resolve to one thread; MJWarp's tiled code is written so that lane 0 then covers everything.

    @wp.kernel
def kinetic_energy(mass: wp.array[float], vel: wp.array2d[wp.vec3], ke_out: wp.array[float]):
    worldid = wp.tid()
    total = float(0.0)
    for i in range(vel.shape[1]):
        v = vel[worldid, i]
        total += 0.5 * mass[i] * wp.dot(v, v)
    ke_out[worldid] = total

    15Summary

    Key takeaways

    • A wp.array has a dtype, a shape and a device. Vector dtypes add trailing NumPy dims: (nworld, nbody) of vec3 is (nworld, nbody, 3) in NumPy.
    • .numpy() on a GPU array synchronizes and copies; keep simulation data on the device.
    • A kernel runs once per index of dim; wp.tid() returns the index, last dimension fastest. dim=0 is a no-op.
    • 32 lanes form a warp and run in lockstep; branches where lanes disagree cost both sides; neighbouring lanes should read neighbouring addresses. MJWarp's (nworld, n) arrays with dim=(nworld, n) launches are built for exactly that.
    • Blocks run on SMs in waves; small launches leave most of a GPU idle. The CPU device runs threads in a loop, with block size 1: correct, not fast.
    • @wp.funcs are inlined helpers; MJWarp's math.py funcs use (w, x, y, z) quaternions, Warp's built-ins (x, y, z, w).
    • wp.static specializes code at generation time; every specialization is a module, compiled once and cached on disk by hash. The course sets wp.config.log_level = wp.LOG_WARNING to silence the load log.
    • Float atomics depend on arrival order; time device code with warm-up and wp.synchronize().

    Next, Ch 5 puts these pieces to work: put_model, make_data, step, and how to look at the result.

    Stuck? See Troubleshooting (slow first call, Warp silently on CPU, module-load log spam) or the course map.
