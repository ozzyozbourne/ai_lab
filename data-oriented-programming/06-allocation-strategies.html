Chapter 6

Allocation Strategies

A game frame builds 65,536 little strings, a debug label for every entity, say, prints a few, and throws them all away 16 milliseconds later. Written the obvious way, that frame calls malloc 65,537 times and free 65,537 times, every frame, forever. Each of those calls is cheap, and together they still decide where every string lands in memory and how much bookkeeping surrounds it. This chapter is about replacing that per-object bookkeeping with something that matches how the data actually lives: allocate by lifetime, not by object.

The previous chapters changed the shape of data. This one changes where the bytes come from. The ideas are old (arenas, pools, stacks, regions), and each of our languages takes them seriously in its own way. Zig makes you pass an allocator to every function that allocates. Odin passes one implicitly in a context and gives every program a per-frame scratch arena. Rust 1.100 has just stabilised the Allocator trait, and its borrow checker can prove that nobody uses frame memory after the frame has been reset.

What malloc actually costs

A general-purpose allocator has a hard job: requests of any size, in any order, from any thread, and any block may be freed at any time, alone. To serve that it keeps metadata: a header next to each block (glibc stores the chunk size in the 8 bytes before the pointer it returns), size classes that round requests up, per-class free lists, per-thread caches, and a way to merge free neighbours. Modern allocators serve the common case from a thread-local cache in a few dozen instructions, but the costs add up in four places:

  1. Instructions per call. Both malloc and free are function calls that look up a size class, pop or push a list, and sometimes take a slow path (refill the cache, ask the OS for pages, merge holes). At Google, across the whole fleet, allocation and deallocation took 4.3% of all CPU cycles, and 3.6–10.1% in the five applications that spend the most there[1].
  2. Bytes per object. A 40-byte request becomes a 48-byte chunk (8 B header, rounded to 16), and a 1-byte request becomes 32. Small objects pay the most, proportionally.
  3. Placement. The allocator puts your object wherever a hole of the right class happens to be. In a long-running program, objects created together end up scattered across pages, so a loop over them touches more cache lines and more TLB entries than it needs to. Google's hugepage-aware TCMalloc rework (Temeraire) did not make malloc itself faster; it changed placement, and the fleet saw 6% fewer TLB-miss stalls and 26% less memory wasted to fragmentation[2]. One service spent more time inside the allocator and still served 3.4% more requests per second.
  4. Freeing. Every object you allocated alone must be freed alone: a walk over a whole data structure at teardown, and a bug (leak, double free, use after free) each time you get it wrong.

The fix is not a faster malloc. It is to notice that most objects do not need what malloc offers: an individual lifetime.

Think in lifetimes, not objects

Ginger Bill (Odin's creator) starts his allocator series with three questions: how big is the allocation, how long does it live, and how is it used[3]. Then he makes a rough table of his own programs: size and lifetime both known, 95%; size unknown but lifetime known, ~4%; size known but lifetime unknown, ~1%; both unknown, under 1%. It is a guess from experience, not a measurement, but anyone who has written a game, a compiler or a server will recognise it. You usually know exactly when a whole group of objects dies:

  • Permanent: configuration, asset tables, the interned string table. Dies at exit.
  • Transient, with a cycle-based lifetime: everything belonging to one level, one HTTP request, one file being compiled. Dies at the end of the cycle.
  • Scratch: a formatted log line, a temporary array inside one function, the strings of one frame. Dies in moments.

Bill calls these the generations of lifetimes; Ryan Fleury makes the same argument in Untangling Lifetimes and concludes that a program needs only a handful of lifetimes, each served by its own arena[7]. Once you sort your objects that way, freeing stops being a per-object problem. You free a phase.

Three levels of six frames, four temporaries per frame, plus a few level and program objects. How many free calls does a per-object allocator make by the end, and how many arena resets replace them?

The figure counts 87 objects (3 program + 12 level + 72 frame), so 87 individual frees. The arenas need 18 frame resets, 3 level resets and 1 program reset: 22. The ratio grows with objects per frame. The real benchmark below has 65,536 per frame, so one reset replaces 65,537 frees.

The arena (bump allocator)

An arena, also called a linear, bump or region allocator, is a block of memory and an offset. To allocate n bytes with alignment a, round the offset up to a multiple of a, hand out the bytes from there, and add n. To free one object, do nothing. To free everything, set the offset back to zero[4]. That is the whole algorithm.

The win is more than the few instructions saved. Objects allocated together sit together, in allocation order, which is usually the order you will read them in, so a loop over the frame's strings streams through consecutive cache lines, and the hardware prefetcher sees a straight line. Nothing is wasted on headers. Freeing a million objects costs one store. And because the arena never reuses memory in the middle of a phase, a whole class of bugs (double free, freeing the wrong pointer, leaking one object) cannot happen inside it.

After the first eight allocations, which side touches more cache lines, and by roughly how much?

The heap, by almost 2× in this model: the arena packs the frame's 240 bytes of payload into 4 cache lines, while the heap turns them into 384 bytes of chunks (headers and rounding) dropped into holes across 2 KiB, touching 7 lines, after searching 9 holes. With an empty, fresh heap the gap would be smaller; it is the aged heap, with its long-lived residents, that scatters new objects.

Here is the arena in Rust, as an implementation of the Allocator trait that Rust 1.100 has just stabilised. The bytes live in a heap-allocated Box<[Cell<u8>]>; the Cell lets it hand out writable memory through a shared reference. The trait is implemented for &Bump, not Bump, so every container holds a borrow and the arena cannot be moved, reset or dropped while a block is alive. (Moving the owning value would move its Box, which Stacked Borrows, one of the candidate aliasing models Miri checks, treats as a fresh unique pointer; a doc test checks that Vec<u8, Bump> is rejected.) The trait is unsafe to implement because the compiler cannot check its promises, so a SAFETY comment states them. Apart from the unsafe fn deallocate signature the trait requires, every method body is safe code.

pub struct Bump {
    buf: Box<[Cell<u8>]>,
    used: Cell<usize>,
}

// SAFETY:
// * The allocator is `&Bump`, not `Bump`. Every block lies inside `buf`, and a container holding a
//   `&Bump` keeps the arena borrowed, so the arena cannot be dropped, moved or `reset` (which takes
//   `&mut self`) while a block is alive. Copying or moving the `&Bump` itself never touches `buf`.
//   We deliberately give the owning `Bump` no `Allocator` impl: moving it by value would move the
//   `Box`, and under Stacked Borrows that move retags the `Box` and invalidates pointers into it.
// * Blocks never overlap: `used` only moves forward between resets, and each block starts at or
//   after the end of the previous one.
// * `base + capacity` cannot overflow the address space, because `buf` is a real allocation.
// * Nothing here can panic (all arithmetic is checked), so no method unwinds.
// * The arena never reads or writes the bytes it has handed out.
unsafe impl Allocator for &Bump {
    fn allocate(&self, layout: Layout) -> Result<NonNull<[u8]>, AllocError> {
        // `Cell<u8>` has the same layout as `u8`, and writing through a pointer derived from a
        // shared reference is allowed because the bytes are inside `UnsafeCell`s.
        let base = self.buf.as_ptr().cast_mut().cast::<u8>();
        let start = (base.addr() + self.used.get())
            .checked_next_multiple_of(layout.align())
            .ok_or(AllocError)?
            - base.addr();
        let end = start.checked_add(layout.size()).ok_or(AllocError)?;
        if end > self.buf.len() {
            return Err(AllocError);
        }
        self.used.set(end);
        let ptr = NonNull::new(base.wrapping_add(start)).ok_or(AllocError)?;
        Ok(NonNull::slice_from_raw_parts(ptr, layout.size()))
    }

    unsafe fn deallocate(&self, _ptr: NonNull<u8>, _layout: Layout) {
        // Individual frees do nothing. `reset` frees the whole frame at once.
    }
}
fn framesArena(f: Frame) u64 {
    var acc: u64 = 0;
    for (0..TICKS) |t| {
        acc +%= tick(f.arena.allocator(), t, f.count, false) catch @panic("out of memory");
        _ = f.arena.reset(.retain_capacity); // keep the block, drop its contents
    }
    return acc;
}
frames_arena :: proc(f: ^Frame) -> u64 {
	context.allocator = mem.arena_allocator(f.arena) // every make/append below now bumps
	acc: u64
	for t in 0 ..< u64(TICKS) {
		acc += tick(t, f.count, false)
		free_all(context.allocator) // offset = 0
	}
	return acc
}

The Rust version is about thirty lines because it is the allocator itself. The Zig and Odin versions only use an arena, because both standard libraries already have one. That difference is the first lesson in how each language thinks about allocation, and we will come back to it.

The same code, any allocator

The interesting part is what does not change. The per-frame work below is written once, and the caller chooses where its memory comes from. In Rust the allocator is a type parameter: Vec<u8, A> with A = Global is the ordinary heap vector, and with A = &Bump it is a vector inside the frame arena. In Zig it is a runtime Allocator value (a pointer plus a vtable) passed to every call that allocates. In Odin it is nothing at all in the signature: make and non_zero_make read context.allocator, which the caller set.

/// One frame: build `count` short-lived messages (8..=71 bytes), use them, drop them.
/// The same code runs on the global heap (`Global`) and on a frame arena (`&Bump`).
fn tick<A: Allocator + Copy>(alloc: A, t: u64, count: usize) -> u64 {
    let mut msgs: Vec<Vec<u8, A>, A> = Vec::with_capacity_in(count, alloc);
    for i in 0..count as u64 {
        let h = mix(t, i);
        let len = 8 + (h >> 58) as usize;
        let mut m = Vec::with_capacity_in(len, alloc);
        m.extend((0..len).map(|j| (h as u8).wrapping_add(j as u8)));
        msgs.push(m);
    }
    let mut sum = 0u64;
    for m in &msgs {
        let bytes: u64 = m.iter().map(|&b| u64::from(b)).sum();
        sum = sum.wrapping_add(bytes ^ ((m.len() as u64) << 32));
    }
    sum
    // `msgs` drops here: count + 1 calls to `free` on Global, nothing at all on &Bump.
}
/// One frame: build `count` short-lived messages (8..=71 bytes), use them, drop them.
/// The same code runs on any allocator. With an arena there is nothing to free one by one.
fn tick(alloc: Allocator, t: u64, count: usize, comptime free_each: bool) Allocator.Error!u64 {
    var msgs: std.ArrayList([]u8) = try .initCapacity(alloc, count);
    defer if (free_each) msgs.deinit(alloc);
    for (0..count) |i| {
        const h = mix(t, i);
        const m = try alloc.alloc(u8, 8 + @as(usize, @intCast(h >> 58)));
        for (m, 0..) |*b, j| b.* = @as(u8, @truncate(h)) +% @as(u8, @truncate(j));
        msgs.appendAssumeCapacity(m);
    }
    var sum: u64 = 0;
    for (msgs.items) |m| {
        var bytes: u64 = 0;
        for (m) |b| bytes += b;
        sum +%= bytes ^ (@as(u64, m.len) << 32);
    }
    if (free_each) for (msgs.items) |m| alloc.free(m);
    return sum;
}
// One frame: build `count` short-lived messages (8..=71 bytes), use them, drop them.
// Everything comes from context.allocator, so the caller decides where the frame lives.
tick :: proc(t: u64, count: int, free_each: bool) -> u64 {
	msgs := make([dynamic][]u8, 0, count)
	for i in 0 ..< count {
		h := mix(t, u64(i))
		m := non_zero_make([]u8, 8 + int(h >> 58))
		for &b, j in m {
			b = u8(h) + u8(j)
		}
		append(&msgs, m)
	}
	sum: u64
	for m in msgs {
		bytes: u64
		for b in m {
			bytes += u64(b)
		}
		sum += bytes ~ (u64(len(m)) << 32)
	}
	if free_each {
		for m in msgs {
			delete(m)
		}
		delete(msgs)
	}
	return sum
}

Notice the asymmetry in freeing. Rust frees through Drop either way, but Bump::deallocate is an empty function, so after inlining the 65,537 drops on the arena path compile to nothing. Zig and Odin take a free_each flag: on the heap path somebody has to call free/delete on each message, and on the arena path the whole point is that nobody does. In Zig, ArenaAllocator.free is a no-op unless the block is the most recent one, so calling it would be correct but pointless; skipping it is the idiom.

The Allocator trait, Global, Vec::new_in, Vec::with_capacity_in and Box::new_in are stable as of 1.100.0 (they had been nightly-only since 2016). Only Vec and Box take an allocator parameter on stable so far: String, HashMap and the other collections do not yet, and Rc/Arc with allocators are still behind the allocator_ext feature[14]. That is why the Rust program builds its strings as Vec<u8, A> rather than String.

The borrow checker forbids reset while anything is alive

An arena's one real danger is the red bar in the lifetimes figure: a pointer that outlives its phase. In Zig and Odin, nothing stops you from keeping a slice into the frame arena after reset/free_all; the next frame silently overwrites it. Rust can rule it out, and the design falls out naturally. Every Vec<_, &Bump> holds a shared borrow of the arena, and reset takes &mut self. You cannot hold both, so the compiler rejects any program that resets the arena while something allocated from it is still reachable:

    /// Frees everything at once by moving the bump pointer back to the start.
    ///
    /// It takes `&mut self`, so it can only be called when no `&Bump` borrow is alive, which means
    /// no `Vec<_, &Bump>` or `Box<_, &Bump>` still points into the buffer:
    ///
    /// ```compile_fail,E0502
    /// use ch06_allocation_strategies::Bump;
    /// let mut frame = Bump::with_capacity(1024);
    /// let names: Vec<u8, &Bump> = Vec::with_capacity_in(16, &frame);
    /// frame.reset(); // error[E0502]: cannot borrow `frame` as mutable because it is also borrowed as immutable
    /// println!("{}", names.len());
    /// ```
    pub fn reset(&mut self) {
        *self.used.get_mut() = 0;
    }

The frame loop that does compile shows the other side: inside the loop body, tick borrows &*frame, returns a plain u64, and its vectors are dropped before the call returns. By the time frame.reset() runs, no borrow is left.

fn frames_arena(frame: &mut Bump, count: usize) -> u64 {
    let mut acc = 0u64;
    for t in 0..TICKS as u64 {
        acc = acc.wrapping_add(tick(&*frame, t, count));
        frame.reset(); // compiles only because nothing from this frame is still alive
    }
    acc
}

There is a price. Because every arena vector borrows the arena, storing one in a struct needs a lifetime parameter, and long-lived code has to thread 'frame through its types, as rustc does with its 'tcx arenas. Zig and Odin trade that friction for discipline and tooling: Odin's Tracking_Allocator and Zig's SafeAllocator catch leaks and double frees in the heap at run time, but neither catches a stale slice into an arena that was reset. In debug builds, poison the arena on reset (fill it with 0xAA) so stale reads produce obvious garbage instead of last frame's plausible data.

The borrow check covers the arena value. If you hand out raw pointers (Vec::as_ptr, Box::into_raw) and dereference them in unsafe code after a reset, Rust cannot help. That is one more reason the book's Rust code keeps unsafe to the impl blocks.

Frame, temporary and stack allocators

A frame arena is just an arena with a schedule: allocated once, reset at the top or bottom of every frame, tick or request. A scratch or temporary allocator is the same thing at a smaller scale, often shared by everything in a thread. And a stack allocator is an arena that can also give back its most recent allocations: either with a small header per allocation, so you can pop them one at a time in LIFO order, or with a saved offset, a "savepoint" you roll back to[5].

Odin builds the scratch arena into the language runtime. Every thread has a context.temp_allocator, a growing arena whose first block is 4 MiB by default (DEFAULT_TEMP_ALLOCATOR_BACKING_SIZE), and the overview says it plainly: it is "for temporary and short lived allocations, which are to be freed once per cycle/frame/etc."[15] Library procedures like fmt.tprintf use it on purpose. You call free_all(context.temp_allocator) once per frame. For a savepoint inside a frame, the runtime gives you runtime.DEFAULT_TEMP_ALLOCATOR_TEMP_GUARD(), a @(deferred_out) procedure that records the temp arena's position and rolls it back when the enclosing scope ends: a stack allocator in one line. The program's rss_bytes uses it, so reading /proc/self/statm never leaves anything behind in the temp arena:

frames_temp :: proc(f: ^Frame) -> u64 {
	context.allocator = context.temp_allocator
	acc: u64
	for t in 0 ..< u64(TICKS) {
		acc += tick(t, f.count, false)
		free_all(context.temp_allocator)
	}
	return acc
}

rss_bytes :: proc() -> int {
	runtime.DEFAULT_TEMP_ALLOCATOR_TEMP_GUARD() // rewinds the temp arena when this proc returns
	data, err := os.read_entire_file("/proc/self/statm", context.temp_allocator)
	if err != nil {
		return 0
	}
	fields := strings.fields(string(data), context.temp_allocator)
	pages, _ := strconv.parse_int(fields[1] if len(fields) > 1 else "0")
	return pages * 4096
}
fn framesFixed(f: Frame) u64 {
    var acc: u64 = 0;
    for (0..TICKS) |t| {
        acc +%= tick(f.fba.allocator(), t, f.count, false) catch @panic("out of memory");
        f.fba.reset(); // end_index = 0
    }
    return acc;
}

Zig spells the same ideas as separate types. FixedBufferAllocator is an arena over a buffer you own. ArenaAllocator grows by asking its child allocator for blocks, and reset(.retain_capacity) keeps one block big enough for the last frame, so after the first frame it stops calling its child at all. BufferFirstAllocator tries a stack buffer first and falls back to a real allocator. Odin also ships mem.Stack, mem.Small_Stack and mem.Scratch if you want them explicitly.

0.16 made std.heap.ArenaAllocator thread-safe and lock-free (allocation is an atomic add on the block's end index) and introduced "Juicy Main", pub fn main(init: std.process.Init)[13]. 0.17 renamed StackFallbackAllocator to BufferFirstAllocator (the buffer is now an argument, and std.heap.stackFallback is gone) and replaced DebugAllocator with std.heap.SafeAllocator[12]. Code from 2024 that writes std.heap.GeneralPurposeAllocator(.{}){} no longer compiles.

Who chooses the allocator?

All three languages agree that the caller should be able to choose where a library's memory comes from. They disagree about how visible that choice should be.

Zig: an allocator argument on every call

Zig has no global allocator. A function that allocates takes an std.mem.Allocator, and the standard containers are "unmanaged" since 0.15: they do not even store one, so you write list.append(gpa, x) and list.deinit(gpa). You can see from a function's signature whether it can allocate, and a test can pass std.testing.allocator, which fails the test on a leak. main receives the program's allocators in std.process.Init (Chapter 2): init.gpa is SafeAllocator in -O debug/-O safe and smp_allocator in -O fast without libc, and init.arena is a process-lifetime arena. The fixed-buffer frame's buffer comes from init.arena, so nobody ever frees it by hand:

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const gpa = init.gpa; // smp_allocator in -O fast, SafeAllocator (leak-checking) in -O debug/safe
    var buf: [4096]u8 = undefined;
    var fw = Io.File.stdout().writer(io, &buf);
    const out = &fw.interface;
    // …
    var arena: std.heap.ArenaAllocator = .init(gpa);
    defer arena.deinit();
    // Worst case per tick: one slice header and MAX_MSG bytes per message (TigerStyle: size it once).
    // It lives as long as the program, so it comes from init.arena and is never freed by hand.
    const fixed = try init.arena.allocator().alloc(u8, per_tick * (@sizeOf([]u8) + MAX_MSG) + 64);
    var fba: std.heap.FixedBufferAllocator = .init(fixed);
    const frame: Frame = .{ .gpa = gpa, .arena = &arena, .fba = &fba, .count = per_tick };

Odin: an implicit context

Odin passes a hidden context to every procedure with the default calling convention. It carries context.allocator (by default the libc heap via runtime.heap_allocator) and context.temp_allocator. Assigning context.allocator inside a scope redirects every allocation in every procedure called from that scope, including library code that was never written with arenas in mind. That is how frames_arena turns tick into arena code without touching it. The same mechanism installs debugging: in a -debug build, the program wraps the heap in a Tracking_Allocator that prints every leak with its source location at exit (it prints nothing for this program).

	when ODIN_DEBUG {
		// Debug builds: wrap the heap in a tracking allocator and report leaks at exit.
		track: mem.Tracking_Allocator
		mem.tracking_allocator_init(&track, context.allocator)
		context.allocator = mem.tracking_allocator(&track)
		defer {
			for _, entry in track.allocation_map {
				fmt.eprintf("%v leaked %v bytes\n", entry.location, entry.size)
			}
			mem.tracking_allocator_destroy(&track)
		}
	}

Implicit is not invisible. context.allocator is still set when you call a procedure that stores what it allocates somewhere long-lived (a cache, a global map). If that procedure runs while context.allocator is your frame arena, its data dies at the next free_all. Set the context in the smallest scope that needs it, as frames_arena does, and pass allocators explicitly to anything that keeps memory. The new core:os made its allocator parameters required for this reason: "Requiring an explicit allocator makes it very clear who and what is allocating where"[16].

Rust: a type parameter with a default

Rust's collections were always parameterised by an allocator internally; 1.100 makes the parameter public. Vec<T> is Vec<T, Global>, so existing code is unchanged, and Vec<T, &Bump> is a different type. Being a type has consequences in both directions. The compiler knows statically which allocator each vector uses, so it inlines the bump and deletes the no-op frees (the benchmark below shows what that buys). But a function that takes &Vec<u8> will not accept a Vec<u8, &Bump>; generic code has to say A: Allocator, as tick does. Taking slices (&[u8]) at API boundaries avoids most of that.

Pools: same size, individual lifetimes

Arenas need a shared lifetime. Some objects really do live and die one by one: projectiles, network connections, particles with random lifetimes, nodes in a tree you edit. If they are all the same size, a pool serves them in O(1) without any of a general allocator's search: split a buffer into equal chunks and thread a free list through the free chunks themselves, so each free chunk stores the index or address of the next one[6]. Allocate = pop the head. Free = push it back. No headers, no size classes, no fragmentation (every hole fits every request), and all objects stay inside one buffer, which keeps them dense in cache and TLB. Chapter 5's generational pool is this pool with a generation check added.

    fn pop_free(&self) -> Option<u32> {
        let i = self.free_head.get();
        let link = self.link(i)?; // NIL is out of range, so an empty pool returns None here
        let next = u32::from_le_bytes([link[0].get(), link[1].get(), link[2].get(), link[3].get()]);
        self.free_head.set(next);
        Some(i)
    }

unsafe impl Allocator for &Pool {
    fn allocate(&self, layout: Layout) -> Result<NonNull<[u8]>, AllocError> {
        if layout.size() > self.chunk || layout.align() > self.align {
            return Err(AllocError);
        }
        let i = self.pop_free().ok_or(AllocError)?;
        let base = self.buf.as_ptr().cast_mut().cast::<u8>();
        let ptr = NonNull::new(base.wrapping_add(self.first + i as usize * self.chunk)).ok_or(AllocError)?;
        Ok(NonNull::slice_from_raw_parts(ptr, layout.size()))
    }

    unsafe fn deallocate(&self, ptr: NonNull<u8>, _layout: Layout) {
        let offset = ptr.as_ptr().addr().wrapping_sub(self.buf.as_ptr().addr() + self.first);
        self.push_free((offset / self.chunk) as u32);
    }
}

pool_allocator_proc :: proc(
	data: rawptr,
	mode: mem.Allocator_Mode,
	size, alignment: int,
	old_memory: rawptr,
	old_size: int,
	loc := #caller_location,
) -> (
	[]byte,
	mem.Allocator_Error,
) {
	p := (^Pool)(data)
	switch mode {
	case .Alloc, .Alloc_Non_Zeroed:
		if size > p.chunk || alignment > p.align {
			return nil, .Invalid_Argument
		}
		c := p.free_head
		if c == nil {
			return nil, .Out_Of_Memory
		}
		p.free_head = c.next
		bytes := ([^]byte)(c)[:size]
		if mode == .Alloc {
			mem.zero_slice(bytes)
		}
		return bytes, nil
	case .Free:
		if old_memory != nil {
			c := (^Free_Chunk)(old_memory)
			c.next = p.free_head
			p.free_head = c
		}
	case .Free_All:
		pool_free_all(p)
	case .Resize, .Resize_Non_Zeroed, .Query_Info:
		return nil, .Mode_Not_Implemented
	case .Query_Features:
		if set := (^mem.Allocator_Mode_Set)(old_memory); set != nil {
			set^ = {.Alloc, .Alloc_Non_Zeroed, .Free, .Free_All, .Query_Features}
		}
	}
	return nil, nil
}

Odin's core:container/pool is a typed object pool, not an Allocator, and core:mem has no fixed-size pool allocator, so the Odin program writes one as an allocator procedure: a single proc that switches on the requested mode (.Alloc, .Free, .Free_All, …), which is why any Odin allocator can slot into context.allocator. Rust's version keeps the free list as u32 indices in the first four bytes of each free chunk (safe byte reads through Cell). Zig's MemoryPool uses an intrusive linked list and hands out pointers aligned for a list node (8 bytes), so returning a *Projectile (alignment 4) needs an @alignCast; the compiler refused the first version without it.

The pool benchmark simulates 64 ticks; each tick spawns a batch of 24-byte projectiles with a time-to-live of 1 to 16 ticks, moves every live projectile, and despawns those whose time is up. Lifetimes overlap and end in random order, so an arena cannot serve them, and the comparison is pool versus one heap allocation per projectile. The same simulate function runs on both:

/// Spawn `spawn` projectiles per tick, move them, despawn each when its ttl runs out.
/// Every projectile is its own allocation with its own lifetime.
fn simulate<A: Allocator + Copy>(alloc: A, spawn: usize) -> u64 {
    let mut live: Vec<Box<Projectile, A>> = Vec::new();
    let mut sum = 0u64;
    for t in 0..POOL_TICKS as u64 {
        for i in 0..spawn as u64 {
            let h = mix(t + 1000, i);
            let p = Projectile {
                x: (h & 0xFFFF) as i32,
                y: ((h >> 16) & 0xFFFF) as i32,
                vx: ((h >> 32) & 15) as i32 - 8,
                vy: ((h >> 36) & 15) as i32 - 8,
                ttl: 1 + ((h >> 40) % MAX_TTL) as u32,
                id: (t * spawn as u64 + i) as u32,
            };
            live.push(Box::new_in(p, alloc));
        }
        let mut k = 0;
        while k < live.len() {
            let p = &mut live[k];
            p.x += p.vx;
            p.y += p.vy;
            p.ttl -= 1;
            if p.ttl == 0 {
                sum = sum.wrapping_add(score(p));
                live.swap_remove(k); // drops the Box: `free`, or a push onto the pool's free list
            } else {
                k += 1;
            }
        }
    }
    live.iter().fold(sum, |s, p| s.wrapping_add(score(p)))
}

fn simulate(src: anytype, gpa: Allocator, spawn: usize) !u64 {

    var sum: u64 = 0;

        for (0..spawn) |i| {

            const p = try src.create();

                .x = @intCast(h & 0xFFFF),
                .y = @intCast((h >> 16) & 0xFFFF),

                .vy = @as(i32, @intCast((h >> 36) & 15)) - 8,
                .ttl = 1 + @as(u32, @intCast((h >> 40) % MAX_TTL)),

        }

            p.x += p.vx;
            p.y += p.vy;

                src.destroy(p); // gpa.free, or a push onto the pool's free list
                _ = live.swapRemove(k);
            } else k += 1;
        }
    }
    for (live.items) |p| {
        sum +%= score(p);
        src.destroy(p);
    }
    return sum;

A cautionary tale: Ghostty's largest memory leak

Custom allocators move bookkeeping into your code, where it can go wrong. The Ghostty terminal (written in Zig) takes standard-size scrollback pages from a memory pool and mmaps rare oversized ones directly; on free, a standard-size page went back to the pool and anything else was munmaped. A hot-path optimisation reused the oldest page as the newest and "resized" it to standard size in its metadata only. When that page was freed, its metadata said "standard", so the big mapping went to the pool and was never unmapped[8]. The bug lived since at least 1.0 and surfaced when a popular CLI tool filled scrollback with multi-codepoint graphemes; one user reported 37 GB after ten days. The lessons: a pool must know for certain which blocks it owns, "size says where it came from" is a fragile ownership test, and leak checkers in CI (Ghostty runs leak-detecting Zig allocators and Valgrind) only catch the conditions the tests produce.

Pitfall: growing arrays in an arena

An arena can only extend an allocation in place if it is the most recent one. A dynamic array that grows by doubling asks to resize; if something else was allocated after it, the arena must allocate a new, bigger block and copy, and the old block stays behind, dead but not reclaimable until the reset. Karl Zylinski, writing about Odin, calls it "a graveyard of old blocks in a trail behind the currently used block"[11]. Two arrays growing in turns is the worst case, because each always blocks the other:

With doubling, the dead copies add up to about the live size, hence 2×; Zig's ArrayList grows by roughly 1.5× plus a constant, which leaves more, smaller corpses. The fixes, in order of preference: know the size and reserve it once (the Odin program then sets each array's allocator to mem.panic_allocator(), so an accidental regrow crashes loudly instead of leaking); keep growing arrays on the general heap or in their own arena; or use a virtual-memory arena, which can grow its last allocation in place, which brings us to the next trick.

Reserve, then commit

On a 64-bit machine, address space is nearly free and physical memory is not. The operating system lets you separate the two: reserve a huge contiguous range of virtual addresses (it costs a kernel bookkeeping entry, no RAM), then commit pages as you reach them. On Linux, an anonymous mmap already behaves this way, because the kernel backs a page with RAM only when it is first touched; Windows makes the two steps explicit with VirtualAlloc(MEM_RESERVE) and MEM_COMMIT. Fleury's advice is to "reserve a massive upper-bound of contiguous virtual address space, then commit physical pages as needed"[7].

An arena built that way never moves and never chains blocks: it is one contiguous range that can grow to its reservation, its last allocation can always grow in place (so the graveyard above disappears for the top-most array), and pointers into it stay valid. Page granularity also lets you give memory back without moving anything: Ghostty later compresses idle scrollback pages and returns them to the OS with madvise while their addresses stay reserved[18]. Each program reserves 1 GiB, writes one byte in each 4 KiB page of the first 16 MiB, and reads its resident set size from /proc/self/statm:

Zig gives you std.posix.mmap, and a FixedBufferAllocator over the mapping is a good reserved arena. Rust's standard library has no reserve/commit API; a huge vec![0u8; N] gets the same effect only because glibc serves it from fresh mmap zero pages, an implementation detail rather than a guarantee. Static allocation: the TigerStyle extreme

If you can put every allocation into a known phase, you can take the last step: allocate everything at startup and never again. TigerBeetle, a financial database written in Zig, makes this a rule in its TigerStyle guide: "All memory must be statically allocated at startup. No memory may be dynamically allocated (or freed and reallocated) after initialization."[9] At startup it computes a worst-case count for every kind of object from its configuration (connections, messages in flight, batch sizes), allocates exactly that, and then wraps its allocator in a state machine (init → static → deinit) that asserts if anyone allocates after initialisation. Its architecture document calls static allocation "a forcing function to ensure that everything has a limit"[10].

The benefits are not mainly speed. A program that cannot allocate after startup cannot run out of memory halfway through a request, has a footprint you can read off its configuration, and cannot use heap memory after freeing it. The cost is that you must know your limits and reject work beyond them. Phil Eaton notes that Zig's fixed-capacity container methods (initCapacity plus *AssumeCapacity) make this practical[17]. This chapter's programs take a small step that way: frame buffers and the pool are sized once from the worst case, so neither asks for memory inside the timed loop.

Measuring it

The frame benchmark runs 16 ticks. Each tick builds 65,536 messages of 8 to 71 bytes (a mixing function of tick and index chooses the length and the bytes, identically in all three languages), sums their bytes, and discards them. "Heap per object" allocates each message and the per-tick list from the general-purpose heap and frees them all; "frame arena" allocates the same from an arena reset once per tick. Every variant prints a checksum, and the checksums match to the last bit across variants and languages (0x0277eab53a846fae at full size).

A worked example with real numbers

Payload length is 8 plus a uniform value in 0–63, so 39.5 bytes on average. In the Zig and Odin arenas each message also needs a 16-byte slice (pointer + length) in the tick's list: 39.5 + 16 = 55.5 bytes per message, within 0.03% of the high-water mark the programs print (3,636,193 bytes for 65,536 messages). Rust's list holds Vec<u8, &Bump> values, which are 32 bytes (pointer, capacity, length and the &Bump), so its arena reaches 71.5 bytes per message. On a glibc heap, the same 39.5-byte average payload becomes a chunk of header + payload rounded up to 16: about 56 bytes per message before the list. So per tick the heap version makes 65,537 calls to malloc, 65,537 to free, and spreads about 3.7 MB of chunks over whatever holes it finds; the arena version makes zero calls to either, writes 2.6 MB of payload in one contiguous run, and resets with one store. The working set (3.6 MB) is bigger than L2 (1.25 MiB) but within the usable L3 that Chapter 2 measured, so most of the gap is probably allocator instructions and frees rather than cache misses; without performance counters we cannot prove it.

Three things in that chart need explaining, and none of them is "Zig is slow".

  • The heap baselines differ. Rust's Global and Odin's default context.allocator both call glibc's malloc/free. Zig in -O fast without libc uses smp_allocator, a simpler per-thread free-list design, and on this single-threaded workload it is noticeably faster than glibc. The arena has less to beat.
  • The arenas differ. Rust's &Bump is a type parameter, so allocate is inlined into tick and the empty deallocate vanishes. Zig's Allocator is a runtime interface: every alloc is an indirect call through a vtable, and ArenaAllocator's fast path is an atomic add because it is thread-safe since 0.16. FixedBufferAllocator skips the atomics and came out ahead of ArenaAllocator here. Odin's allocator is also a procedure pointer, called per allocation.
  • Odin's temp allocator is slightly behind its mem.Arena. One visible difference in the runtime source: free_all on the temp arena zeroes the used part of its block, while mem.Arena's free_all only sets offset = 0. We have not profiled it, so treat that as a plausible reason, not a finding.

In Rust and Odin the pool's margin is smaller than the arena's, and that is the honest result. (In Zig the two margins are about the same, because its smp_allocator heap left the arena little to beat.) Every projectile still gets created and destroyed one at a time, the simulation does real work per tick, and glibc's thread cache is already very good at recycling same-size 32-byte chunks; it is itself a pool for that size class. What the pool adds is a guarantee rather than a big speed-up: all projectiles live inside one buffer, there are no headers, and no allocation can fail or fragment inside the loop.

When not to

  • Long-lived arenas accumulate garbage. An arena that is never reset is a leak with good locality. If objects in one "phase" actually die at very different times (a server whose request arena lives as long as a slow client), you pay for the slowest one.
  • Escaping pointers. Anything that outlives its arena is a use-after-free. Rust catches it at compile time for values that borrow the arena; in Zig and Odin, keep arenas phase-scoped, poison memory on reset in debug builds, and copy what must survive into a longer-lived arena before the reset.
  • Drop and destructors. In Rust, a Vec<T, &Bump> still runs each T's destructor; only the memory is free. If T owns heap memory of its own (a String), that memory is still freed one by one. Arena-friendly data is plain data.
  • The heap is good. Modern allocators are fast, and for objects with genuinely unpredictable lifetimes they are the right tool. Measure before replacing one; our pool result shows how small the margin can be.
  • Custom allocators are code you maintain. Ghostty's leak lived for years in a pool that worked for the common case. Keep the ownership rules simple, and test the rare path.

Group objects by when they die, give each lifetime its own arena (or a pool when objects of one size die one by one), and freeing a million objects becomes a single reset that the hardware, the allocator and in Rust even the borrow checker can reason about.

Exercises

A bump arena holds a 1-byte bool, then a u64, then a u16, starting at offset 0. What is the offset after each allocation, and how many bytes are padding?

The bool goes at 0 (offset 1). The u64 needs 8-byte alignment, so the pointer rounds up to 8 and ends at 16 (7 bytes of padding). The u16 goes at 16 and ends at 18. Total 18 bytes, 7 of them padding. Allocating in decreasing alignment order (u64, u16, bool) gives 11 bytes and no padding, the same lesson as Chapter 3, now applied to an allocator.

Why does Bump::reset take &mut self while allocate takes &self? What would go wrong if reset took &self?

Collections hold a shared reference to the allocator (Vec<T, &Bump>), so allocation must work through &self. If reset also took &self, you could call it while vectors still point into the buffer, and the next allocations would overwrite their contents: a use-after-free in safe code, which would make the unsafe impl unsound. Requiring &mut self lets the borrow checker prove no borrow is alive, and the trait's documentation explicitly allows mutation through &mut access to invalidate blocks.

In Odin, a procedure called during a frame does cache[key] = strings.clone(name), while context.allocator is the frame arena. What happens, and what are two fixes?

The clone lives in the frame arena, the map entry outlives the frame, and after free_all the next frame overwrites the bytes: the cache now holds garbage strings. Fixes: pass an explicit long-lived allocator to strings.clone(name, cache_allocator), or narrow the scope where context.allocator is the frame arena so the caching code runs outside it. (Interning into a permanent arena is a third.)

The frame benchmark's working set is about 3.6 MB per tick. If each tick builds only 4,096 messages (about 230 KB, inside L2), which effects push the arena's advantage up, which push it down, and how would you find out which wins?

Up: the arena's writes get cheaper because everything stays in L2, while the heap path still pays its allocator instructions per message. Down: glibc's thread cache also does better on a small, hot heap, recycling the same few chunks from cache. Which wins depends on the machine and the allocator. On this orb a quick Rust run (256 ticks × 4,096 messages) gave a smaller ratio than the full-size run, so the second effect won. The way to find out is to change the count and measure both sizes.

Ghostty's pool decided ownership from a page's size field. Design an ownership test that cannot drift out of sync with the real allocation.

Decide from the memory itself, not from mutable metadata: for example, check whether the page's address lies inside the pool's own reserved range (one comparison when the pool reserves one contiguous region), or store an immutable "origin" tag set when the page is created and never changed by resizes. Either way, also keep the true mapping length next to the pointer so munmap always gets the right size. Hashimoto's actual fix was simpler: never reuse non-standard pages at all.

TigerBeetle allocates everything at startup. Name one thing this program would have to bound, and how, to follow TigerStyle completely.

The number of live projectiles: it is already bounded by spawns per tick × maximum ttl (the pool is sized to exactly that), but the live list still grows on the heap. Allocate it once with that capacity and use appendAssumeCapacity (Zig), Vec::with_capacity plus an assertion (Rust), or a pre-sized [dynamic] with mem.panic_allocator() (Odin). Then reject spawns beyond the limit instead of growing.
