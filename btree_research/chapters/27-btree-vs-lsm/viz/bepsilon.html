A B-tree applies every change to a leaf at once. An LSM-tree collects changes and merges them later. A B-epsilon tree sits in between: each internal node keeps a small buffer of pending changes and pushes them one level down in batches. This page shows a single such node. It is a textbook model, written in JavaScript only; none of the guide's code bases contains one.

What to look for

  • A put is a message. It is appended to the buffer of the node, which is in RAM. No leaf is read or written.
  • Flush in batches. When the buffer is full, the child with the most waiting messages gets all of them at once: one leaf read, one leaf write, one write of the node, however many messages move. The card on the right shows what a B+tree would have paid for the same keys: one read and one write per key.
  • Reads stay cheap. A get looks at the buffer first (the node had to be read anyway to find the child), and the newest message for the key wins. Only then does it read the leaf. Nothing has to be searched in several runs, as in an LSM-tree.
  • Deletes are messages too. A delete message does the job of an LSM tombstone, but it only lives until the next flush of its child.
  • The epsilon knob. A node has a fixed size. The more of it is buffer, the bigger the batches and the fewer pivots fit, so the tree gets taller. All pivots and no buffer is a B-tree; change the buffer size above and compare the I/O per message. With a buffer of 2 a batch is often a single message, and the extra node write makes it worse than a B+tree.
