    Part VI · Chapter 29

    Gradients, Sampling-Based Optimization and Parallel System Identification

    Many problems in robotics are optimization problems: find the controls that swing a pole up, or find the friction that makes the simulator match a video. This chapter shows three ways to attack them with MJWarp. Gradients through wp.Tape work for your own kernels. diff.py is the registry that would let MJWarp functions join a tape; in 4.0.1 it has no rules. The method that works today is to use the worlds themselves: finite differences, the cross-entropy method, and parallel system identification, each running thousands of candidates in one batched rollout.

    Expert About 2.5 h· Prerequisites: Ch 10, Ch 24, Ch 26 (Ch 28 recommended)

    • What diff.py does in 4.0.1: every public function is wrapped, no adjoint rule is registered, so every MJWarp call inside a tape raises.
    • How to use register_adjoint (array_args, in/out/model/render fields, supported) and the AdjointRule contract on your own functions.
    • Finite-difference derivatives with one world per perturbation, and how to pick epsilon in float32.
    • CEM as the iterative extension of Ch 8's random-shooting MPC, with correct State snapshots.
    • The non-RL capstone: fit mass, damping and friction to recorded data, with one world per candidate.

    Before you start: recap

    • A state snapshot is mjw.get_state into a (nworld, mj_stateSize) array; use State.PHYSICS (+ WARMSTART for bitwise replays) (Ch 8 §4).

    • Your own kernels read d.qpos etc. with one thread per world and write per-world rewards or losses (Ch 26).

    1Derivatives in one picture

    Most of this chapter is about one question: if I change an input a little, how much does the output change? For a rollout, the inputs can be a control sequence, an initial state or a model parameter. The output is usually one number: a cost, a reward, a fitting error. The answer is the derivative, or, with many inputs, the gradient.

    A program is a chain of small operations. The chain rule says the derivative of the whole chain is the product of the derivatives of the links. There are two orders in which to multiply them.

    • Forward mode picks one direction of change of the inputs, a tangent \dot x, and pushes it forward with the values: every intermediate v gets its own \dot v. One pass gives the derivative of every output along that one input direction.
    • Reverse mode runs the program forward, keeps a record, then walks the record backward. It starts from one output and a cotangent \bar y = 1 and pulls it back: every intermediate gets \bar v = \partial y / \partial v. One backward pass gives the derivative of that one output with respect to every input.
    y = x_1 x_2 + \sin x_1
    \text{forward (one tangent): } \dot y = x_2 \dot x_1 + x_1 \dot x_2 + \cos(x_1)\,\dot x_1
    \text{reverse (one cotangent): } \bar x_1 = \bar y\,(x_2 + \cos x_1), \quad \bar x_2 = \bar y\,x_1

    Count the passes. With n inputs and m outputs, forward mode needs n passes to get the full Jacobian, reverse mode needs m backward passes (each costs a small constant times the forward, plus the memory for the record). A loss has m = 1, so reverse mode is the cheap one when there are many inputs: that is why deep learning uses it. Finite differences need no derivative code at all, but cost one or two extra forward runs per input. On a GPU those extra runs are just more worlds in the same batch, which changes the picture.     2wp.Tape on a two-line kernel

    Warp implements reverse mode with a tape. When Warp compiles a kernel with enable_backward=True (the default), it also generates an adjoint kernel: for every statement, the local reverse-mode rule, in reverse order. Inside with wp.Tape(): each wp.launch is recorded together with its arrays. Arrays created with requires_grad=True carry a second array of the same shape, .grad, that holds the cotangent.

    1. Run the forward under the tape.
    2. Seed the cotangent of the output: y.grad.fill_(1.0) means "differentiate L = \sum_i y_i". For a scalar loss array use loss.grad.fill_(1.0).
    3. tape.backward() launches the recorded adjoints from last to first.
    4. Read x.grad. Call tape.zero() before the next backward.

    Two lines of the output deserve a second look, because the same rules govern the MJWarp adjoint registry in §4.

    • The backward consumes the output cotangent. After tape.backward(), y.grad is 0. The kernel overwrote y, so the old contents of y had no influence on the loss, and their cotangent is 0. The adjoint leaves exactly that value behind, because an earlier launch that wrote y would receive it next.
    • Input gradients accumulate. Re-seeding and calling backward() again gives x.grad = 4x: adjoints add (+=) into input gradients. This is what makes fan-out correct (an array read by two kernels collects both contributions), and it is why you must call tape.zero() between iterations of an optimizer.

    Pitfall: stale gradients

    Forgetting tape.zero() in a training loop gives gradients that grow every iteration. In a captured graph (Ch 24) capture tape.zero() inside the graph, before the backward, as diff_test.py::test_graph_capture does, or replays accumulate.

    Where reverse mode gets expensive

    The tape keeps every recorded launch and its arrays alive until you drop it. A rollout of T steps that overwrites d.qpos in place cannot be replayed backward unless each step's inputs are kept (checkpointed) somewhere: memory grows with T. Finite differences across worlds need no record at all.

    3Why MJWarp functions cannot join a tape in 4.0.1

    Recall from Ch 4

    Almost every MJWarp module (all the pipeline modules: forward.py, smooth.py, solver.py, the collision files, ...) calls wp.set_module_options({"enable_backward": False}) at import, so no adjoint code is generated: compile time and binary size drop (Ch 4 §7). set_const.py and sort.py are exceptions: their kernels keep Warp's default. That changes nothing for the tape, because they run only inside wrapped API functions that have no rule.

    Without adjoints, a tape that recorded mjw.step would silently produce wrong gradients: Warp would skip the missing adjoints during the backward pass. mujoco_warp/_src/diff.py exists to make that failure loud. Its module docstring says it directly: "MuJoCo Warp kernels are compiled with enable_backward=False, so recording API functions on a wp.Tape would produce wrong gradients (Warp skips their adjoints)."

    The mechanism has three parts.

    1. The last line of mujoco_warp/__init__.py is _differentiable(locals()). diff.differentiable walks the namespace and replaces every public function (inspect.isfunction(obj) and a name without a leading underscore) by diff._wrap(fn). Classes and enums are left alone. That is 72 functions in 4.0.1: the pipeline (step, forward, kinematics, ...), but also put_model, make_data, put_data, get_state, set_state, ray, render, set_const.
    2. _wrap stores RULES[name] = None and the parameter names in _PARAMS[name], and returns a functools.wraps wrapper (so mjw.step.__wrapped__ is the original function and docstrings are kept).
    3. The wrapper checks the active tape. No tape (or the internal _ScratchTape): it calls the function directly, with no other cost. A real tape and RULES[name] is None: it raises NotImplementedError(f"Differentiation of '{name}' is not supported.") before touching the arguments, so nothing is recorded.

    Nothing in the 4.0.1 package calls register_adjoint; rules appear only in diff_test.py, which registers them on test functions and restores the registry afterwards. So the answer to "which mjw calls can run inside a wp.Tape?" is: none of them.

    Version note: status in 4.0.1

    The README at commit 8f5b9f1 says: "Differentiability via Warp is not yet available. See #500 for progress." diff.py is the scaffolding for that work: the registry, the validation and the recording logic are complete and tested, but no MJWarp function has a rule yet. Expect rules to appear function by function in later versions; check sorted(k for k, v in diff.RULES.items() if v is not None) after upgrading.

    Practical consequence

    Keep every MJWarp call outside any active tape, including setup (put_data, forward) and helpers such as get_state. If you use a tape for your own kernels (a loss, a policy written in Warp), close it before you step the simulator. For derivatives through the physics, use the world-parallel methods of §5-§7.

    4register_adjoint and the AdjointRule contract

    The registry is open. diff.register_adjoint attaches an adjoint rule to any function that went through _wrap: an MJWarp function by name, or your own function after you wrap it. That is how you build differentiable pieces that follow the MJWarp calling convention fn(m, d, ...) and compose with plain Warp kernels on one tape.

    def register_adjoint(
  fn: Callable | str,
  backward: Callable[..., None] | None = None,
  *,
  in_fields: Sequence[str] = (),
  out_fields: Sequence[str] | None = None,      # defaults to in_fields
  model_fields: Sequence[str] = (),
  render_fields: Sequence[str] = (),
  array_args: Sequence[str] = (),
  supported: Callable[..., Sequence[str] | str | None] | None = None,
) -> Callable:

    Model fields, render fields and the decorator form

    Two field lists behave differently from in_fields and out_fields. model_fields names fields of the Model argument that may receive gradients, but the wrapper only tracks them: it does not turn on requires_grad for them, so you set it yourself on the parameters you want to differentiate. render_fields are fields of the first RenderContext argument; they are promoted like in_fields and out_fields. The test suite registers a rule for mjw.mul_m in the decorator form: calling register_adjoint without a backward returns a decorator, and decorating your backward installs it as a custom rule (diff_test.py, condensed):

    m.body_mass.requires_grad = True   # model_fields are tracked, not promoted

@diff.register_adjoint(mjw.mul_m, array_args=("res", "vec"), model_fields=("body_mass",))
def mul_m_bwd(m, d, res, vec, skip=None, M=None):
  # M is symmetric, so vec.grad += M @ res.grad; res is overwritten, so consume res.grad
  m_res_grad = wp.zeros(vec.shape, dtype=float)
  mjw.mul_m(m, d, m_res_grad, res.grad)
  wp.launch(_axpy_kernel, dim=vec.shape, inputs=[1.0, m_res_grad], outputs=[vec.grad])
  res.grad.zero_()

    The backward is called with the forward arguments, so its signature mirrors mul_m(m, d, res, vec, skip=None, M=None). _axpy_kernel is a small test helper (y += a * x).

    The contract a backward must keep

    The AdjointRule docstring is precise, and Example 29.1 showed why each clause exists:

    • Accumulate (+=) into the input gradients, like a kernel adjoint.
    • Consume the output gradients: afterwards each must equal the cotangent of the array's pre-call contents. Zero where the forward overwrote it; when the field is updated in place, clone the incoming gradient first. The earlier call that wrote the array receives it next.
    • Do not change requires_grad; keep scratch cotangents in your own allocations, not in Data gradients; recompute intermediates from the inputs instead of reading outputs that later calls may overwrite.
    • List every field with gradients that the forward reads or overwrites. Kernel launches and copies between arrays with gradients are detected; zero_(), fill_(), assign() and copies involving an array without gradients are not.

    Notice x.requires_grad: False before the taped call and True after. The wrapper promoted the listed array arguments (non-empty float arrays) for you, and only then ran the forward. Without a tape the same wrapper is a plain function call.

    What the wrapper checks, in order

    Under a tape, _wrap's inner wrapper validates the call in a fixed order, and every refusal happens before anything is recorded on your tape. Step through it:

    Going deeper: what a rule for an MJWarp function would take

    You may register a rule on an MJWarp function yourself: diff.register_adjoint("mul_m", my_bwd, array_args=("res", "vec"), ...). diff_test.py::test_finite_difference_jacobian does exactly that for mjw.mul_m: the mass matrix is symmetric, so the backward of res = M vec is another mul_m call, vec.grad += M res.grad, followed by res.grad.zero_(). The rule works because its backward never needs a Warp adjoint: it reuses the forward function on the cotangent.

    For step there is no such shortcut. A correct backward would need the adjoint of collision detection (discontinuous when contacts appear), of the constraint solver (an iterative optimization whose derivative is defined through its optimality conditions), and of the integrator, with the intermediate state of every step kept or recomputed. That is the work tracked by issue #500. Until it lands, the derivatives of rollouts come from the worlds themselves.

    5Finite differences across worlds

    A central difference estimates a derivative from two evaluations:

    \frac{\partial f}{\partial u_j} \approx \frac{f(u + h e_j) - f(u - h e_j)}{2h}

    For a rollout f = final state after T steps and u = a control sequence with k knots, the full Jacobian needs 2k perturbed rollouts plus the nominal. In MJWarp they are simply 2k+1 worlds: world 0 is the nominal, world 2j+1 adds +h to knot j, world 2j+2 subtracts it. One set_knot kernel gives each world its own control, and one batched rollout computes every column.

    Choosing epsilon in float32

    The step h trades two errors. The Taylor remainder of a central difference is \tfrac{h^2}{6} f''': big h is biased. Round-off in each evaluation is about \varepsilon\,|f|, and dividing by 2h amplifies it: small h is noisy. The total

    E(h) \approx C\,h^2 + \frac{\varepsilon_{\text{eff}}}{h}, \qquad h^\star = \left(\frac{\varepsilon_{\text{eff}}}{2C}\right)^{1/3}

    has a minimum. With float64 (\varepsilon \approx 2.2\times10^{-16}) the optimum is around 10^{-5} to 10^{-6}; with MJWarp's float32 (\varepsilon \approx 1.19\times10^{-7}) it moves up by more than two decades. And a rollout of 50 steps accumulates round-off from every step, so the effective noise \varepsilon_{\text{eff}} is several times machine epsilon. Example 29.5 measures it against a float64 C MuJoCo reference.

    Rules of thumb for FD across worlds

    • Start with h \approx 10^{-2} times the input's scale in float32, then check two neighbours (h/3, 3h): if the Jacobian changes in the third digit, you are on the noisy side.
    • Perturbations must not cross a clip: a control at its ctrlrange limit has a zero one-sided derivative. Example 29.5 keeps every knot inside [-1, 1].
    • Contacts make f non-smooth: a contact that appears in only one of the two perturbed worlds gives a large, meaningless difference. Use a bigger h, or smooth the quantity (Exercise 29.1 interpolates a crossing time instead of counting steps).
    • All worlds must start bitwise identical, warmstart included. On a GPU, float atomics can change low bits between worlds (Ch 22 §1): that adds noise and pushes h^\star up.

    6Sampling-based optimization: the cross-entropy method

    Recall from Ch 8

    Random-shooting MPC: snapshot the state, give each world a random action sequence, roll all of them out, keep the best world's first action (Ch 8 §11). Use State.PHYSICS (+ WARMSTART for bitwise replays); PHYSICS has no TIME bit, so add it if d.time matters (the State docstring in types.py lists TIME under PHYSICS, but the actual value, mujoco.mjtState.mjSTATE_PHYSICS = 16414, excludes the TIME bit; FULLPHYSICS includes it) (Ch 8 §4).

    Random shooting samples from a fixed distribution and throws away everything it learned. The cross-entropy method (CEM) keeps a distribution over plans, a Gaussian with mean \mu and standard deviation \sigma per knot, and moves it toward what worked:

    1. Sample N plans u^{(i)} \sim \mathcal N(\mu, \sigma^2), clip to the control range.
    2. Restore the start snapshot in every world and roll out all N plans at once; a kernel adds the reward of each step to ret[worldid].
    3. Keep the K best plans, the elites.
    4. Refit \mu, \sigma to the elites (\sigma floored so it does not collapse too early). Repeat.

    It needs no gradient, it handles contacts and discontinuities, and its expensive part, step 2, is exactly the batched rollout MJWarp is built for. Two small tricks make it robust: world 0 replays the current mean (a free check that the mean is improving) and world 1 replays the best plan found so far (elitism), so the best return can never go down.

    Read the log as an optimizer trace. The best return climbs in steps (-69, -25, -22, then positive) while the mean \sigma shrinks from 0.8 to 0.17: the distribution narrows around plans that swing the pole over the top. The line "replays ... reproduced its return exactly: True" is the snapshot doing its job: the same plan from the same restored State.PHYSICS | TIME gives a bitwise equal return, so comparisons between iterations are fair. The final best plan brings the pole within 0.031 rad of upright 1.6 s in (angle sampled every 0.2 s); an open-loop plan cannot hold it there, which is why Ch 8 re-plans every control interval (MPC) and why Ch 30 learns a feedback policy.

    Pitfall: which state bits to snapshot

    For CARTPOLE (no contacts, no delays) State.PHYSICS | TIME restores everything the rollout depends on. With contacts add WARMSTART: the solver starts from qacc_warmstart, and a stale warmstart changes the result in the last bits. Models with actuator/sensor delays or plastic springs are covered because PHYSICS includes HISTORY and PLASTIC. And always allocate the buffer as (nworld, mj_stateSize(mjm, sig)): get_state does not check the size.

    7Capstone: parallel system identification

    System identification is the inverse of simulation. You have a recording from the real system (joint encoders, a motion-capture trajectory) and a model with unknown parameters; you want the parameters that make the model reproduce the recording. It is the step that makes a simulator trustworthy before you train in it, and it is the non-RL capstone of this course: everything from Parts II and VI meets here.

    Three design choices carry the example.

    • Batched Model fields, and the derived ones too. put_model(mjm, batch_sizes=...) gives dof_damping, body_mass and body_inertia one row per world, and also the derived fields this model's dynamics need (body_subtreemass, body_invweight0, dof_invweight0, actuator_acc0), exactly the Ch 10 recipe. set_const also writes camera and light fields that track the subtree COM (cam_poscom0, light_poscom0 and others); batch those too before rendering per-world candidates. Inertia is scaled with the mass, because inertia is a sum of m r^2.
    • set_const eagerly, outside any graph. It runs after every mass write, before the rollout. For this contact-free pendulum the loss is the same with or without it (we checked), because the dynamics read body_mass and body_inertia directly; but body_subtreemass feeds smooth.py and the subtree sensors, and the invweights set constraint regularization, so a model with contacts or limits would silently use the old values.
    • A full-covariance CEM, as cheap insurance. The recording pins the damping down sharply but the mass only weakly, with a mild positive coupling (a heavier lower link with a little more damping looks similar): in the landscape stepper below, the low-loss band is nearly vertical. Refitting a 2x2 covariance to the elites lets the Gaussian tilt if the valley is tilted; the printed correlation peaks at +0.69 in rounds 2-3 and ends at +0.41. On this problem it is not needed: the same run with one \sigma per parameter (diagonal covariance, CPU, same seed) recovers damping 0.1501 and mass 1.6033, against 0.1501 and 1.6034 with the full covariance. It costs nothing, and it matters when two parameters really trade off against each other.

    The best loss settles at 4.1\times10^{-6}\ \mathrm{rad}^2, which is the sensor-noise variance 0.002^2 = 4\times10^{-6}: the fitted model explains the recording down to its noise, and its rms error equals that of the true parameters. That is the stopping criterion to look for in real identification work; a fit far below the noise floor means you are fitting the noise.

    With contacts: friction from a sliding box

    Friction is the parameter people most often get wrong, and it is the easiest to batch: geom_friction is a "*" field and feeds no derived constant, so there is no set_const call. The contact kernels combine the two geoms with an element-wise max (collision_core.py::contact_material_params), so Example 29.8 writes the candidate into both the slope and the box. A 1-D problem does not need CEM: each round scores an evenly spaced grid, keeps the best, and zooms in around it.

    Real data is harder

    Here the "real" system is C MuJoCo in float64, so the model class is right and only float32 versus float64 and the injected noise separate them. Real recordings add unmodelled effects (backlash, cable forces, motor dynamics) and the loss floor rises above the sensor noise. Widen the prior box, identify a few parameters at a time, check identifiability with a landscape like the one in the stepper above, and validate on a recording you did not fit.

    On a GPU the rollout inside evaluate is the part worth capturing as a CUDA graph (Ch 24): the T launches of set_torque, mjw.step and add_loss are device work on arrays that keep their addresses. reset_data_keyframe is less clean: it allocates a mask array on every call, and with an int key also a key array, so capturing it relies on Warp's mempool allocation during capture (Ch 24 §2, Allocations). The simple choice is to call it eagerly before each replay and capture only the step loop. This course has not measured that capture on a GPU. The .assign() calls write into the same arrays, so a graph captured once can be replayed every round. Ch 30 applies the same split to domain randomization inside an RL environment.

    Do not replace arrays a graph uses

    Writing m.dof_damping = wp.array(...) instead of m.dof_damping.assign(...) gives the Model a new array at a new address; a captured graph keeps reading the old one (Ch 6 §5, replace vs assign; Ch 24).

    _has_adjoint checks each recorded launch for enable_backward; MJWarp modules set it to False (Example 29.4, part 4).

    In Example 29.5 the float32 Jacobian error is smallest around h = 1e-2 to 3e-2 and grows for h = 1e-5. Why?

    E(h) \approx C h^2 + \varepsilon_{\text{eff}}/h with \varepsilon_{\text{eff}} a few times float32 epsilon; its minimum is near (\varepsilon_{\text{eff}}/2C)^{1/3}.

    For CEM on a scene with contacts, which signature makes a replayed plan bitwise reproducible?

    The solver starts from qacc_warmstart; restoring it is what turns "close" into "bitwise equal" (Ch 8 §4).

    For parallel identification of a link mass you batch body_mass. What else does the course recipe require?

    Ch 10's rule: set_const writes body_subtreemass, the invweights and actuator_acc0 (plus camera and light fields such as cam_poscom0), so the outputs the dynamics read need one row per world as well.

    Exercise 29.1: FD gradient of a landing time

    Auto-checked

    Drop BALL_DROP from H \pm h (H = 1 m, h = 0.05 m) in two worlds of one batch. Find the time at which the ball centre first reaches z = R = 0.1 m (interpolate linearly between steps, so the answer is smooth in H), and form the central difference. Free fall gives t = \sqrt{2(H - R)/g}, so dt/dH = 1/\sqrt{2g(H-R)}.

    H, EPS, R, G = 1.0, 0.05, 0.1, 9.81
dtdh = ...       # your FD estimate from a 2-world rollout
analytic = 1.0 / np.sqrt(2 * G * (H - R))
assert abs(dtdh - analytic) / analytic < 0.03
    Show solution

    One rollout with nworld=2. Note the .copy(): on the CPU device d.qpos.numpy() is a view of the Warp array, so without it z_prev would change under you at the next step. Output on CPU: FD dt/dh = 0.2381 s/m, analytic = 0.2380 s/m.

    import mujoco
import numpy as np
import warp as wp
wp.config.log_level = wp.LOG_WARNING
import mujoco_warp as mjw

BALL_DROP = """
<mujoco model="ball_drop">
  <option timestep="0.002"/>
  <worldbody>
    <light pos="0 0 3" dir="0 0 -1"/>
    <geom name="floor" type="plane" size="5 5 .1" rgba=".8 .8 .8 1"/>
    <body name="ball" pos="0 0 1">
      <freejoint/>
      <geom name="ball" type="sphere" size=".1" mass="1" rgba="1 .3 .3 1"/>
    </body>
  </worldbody>
</mujoco>
"""
H, EPS, R, G = 1.0, 0.05, 0.1, 9.81


def landing_times(heights):
    """Time at which the ball centre first reaches z = R, linearly interpolated between steps."""
    mjm = mujoco.MjModel.from_xml_string(BALL_DROP)
    m = mjw.put_model(mjm)
    d = mjw.make_data(mjm, nworld=len(heights), nconmax=4, njmax=16)
    q = np.tile(mjm.qpos0, (len(heights), 1))
    q[:, 2] = heights
    d.qpos.assign(q)
    dt = mjm.opt.timestep
    t_land = np.full(len(heights), np.nan)
    z_prev = np.array(heights, dtype=float)
    for i in range(1, 400):
        mjw.step(m, d)
        z = d.qpos.numpy()[:, 2].copy()   # copy: on CPU .numpy() is a view
        hit = np.isnan(t_land) & (z <= R)
        t_land[hit] = (i - 1) * dt + dt * (z_prev[hit] - R) / (z_prev[hit] - z[hit])
        z_prev = z
        if not np.isnan(t_land).any():
            break
    return t_land


t = landing_times([H - EPS, H + EPS])
dtdh = (t[1] - t[0]) / (2 * EPS)
analytic = 1.0 / np.sqrt(2 * G * (H - R))
print(f"FD dt/dh = {dtdh:.4f} s/m, analytic = {analytic:.4f} s/m")
assert abs(dtdh - analytic) / analytic < 0.03
print("ok")

    Exercise 29.2: a custom adjoint for y = 2x + 1

    Auto-checked

    Write affine(m, d, x, y) with a kernel compiled with enable_backward=False, its backward affine_bwd(m, d, x, y), wrap it with diff._wrap, register it with array_args=("x", "y"), run it under wp.Tape on x = [0, 1, -3], seed y.grad = 1 and call tape.backward().

    assert np.allclose(y.numpy(), [1.0, 3.0, -5.0])
assert np.allclose(x.grad.numpy(), 2.0)
assert np.allclose(y.grad.numpy(), 0.0)   # the rule consumed the output cotangent
    Show solution

    The constant +1 has no derivative; the backward adds 2 * y.grad and zeroes y.grad. Output on CPU: y = [ 1. 3. -5.] x.grad = [2. 2. 2.], then ok.

    import mujoco
import numpy as np
import warp as wp
wp.config.log_level = wp.LOG_WARNING
import mujoco_warp as mjw
from mujoco_warp._src import diff


@wp.kernel(enable_backward=False)
def affine_kernel(x: wp.array[float], y_out: wp.array[float]):
    i = wp.tid()
    y_out[i] = 2.0 * x[i] + 1.0


@wp.kernel(enable_backward=False)
def affine_bwd_kernel(y_grad: wp.array[float], x_grad_out: wp.array[float]):
    i = wp.tid()
    x_grad_out[i] += 2.0 * y_grad[i]


def affine(m, d, x, y):
    wp.launch(affine_kernel, dim=x.shape[0], inputs=[x], outputs=[y])


def affine_bwd(m, d, x, y):
    wp.launch(affine_bwd_kernel, dim=x.shape[0], inputs=[y.grad], outputs=[x.grad])
    y.grad.zero_()


w = diff._wrap(affine)
diff.register_adjoint(affine, affine_bwd, array_args=("x", "y"))
mjm = mujoco.MjModel.from_xml_string("<mujoco><worldbody/></mujoco>")
m, d = mjw.put_model(mjm), mjw.make_data(mjm)
x = wp.array([0.0, 1.0, -3.0], dtype=float)
y = wp.zeros(3, dtype=float)
with wp.Tape() as tape:
    w(m, d, x, y)
y.grad.fill_(1.0)
tape.backward()
print("y =", y.numpy(), "x.grad =", x.grad.numpy())
assert np.allclose(y.numpy(), [1.0, 3.0, -5.0])
assert np.allclose(x.grad.numpy(), 2.0)
assert np.allclose(y.grad.numpy(), 0.0)
print("ok")
diff.RULES.pop("affine", None)    # leave the global registry as 4.0.1 ships it
diff._PARAMS.pop("affine", None)

    11Summary

    Key takeaways

    • Forward mode pushes one tangent and gives all outputs along one input direction; reverse mode pulls one cotangent and gives one output's gradient with respect to all inputs.
    • wp.Tape: forward under the tape, seed .grad, backward(), read input .grad, zero(). Adjoints accumulate into inputs and consume overwritten outputs.
    • In 4.0.1 every public mjw function is wrapped by diff._wrap and diff.RULES holds no rule, so any MJWarp call inside an active tape raises NotImplementedError. Keep setup and simulation outside the tape.
    • register_adjoint declares array_args and Data/Model/RenderContext fields, an optional supported hook and a backward; the wrapper validates, promotes, runs the forward on a scratch tape, rejects undeclared field access, and records. Native rules cannot work for MJWarp kernels (enable_backward=False).
    • Derivatives through the physics come from the worlds: 2k+1 worlds give a central-difference Jacobian in one rollout. In float32, h around 1e-2 of the input scale is a good start; check its neighbours.
    • CEM = random shooting that learns: sample, roll out all at once, keep elites, refit. Snapshot with State.PHYSICS (+ TIME, + WARMSTART with contacts).
    • Parallel system identification: one world per candidate in batched Model fields, set_const eagerly after mass writes, loss on the device, full covariance for correlated parameters; stop at the noise floor.

    Stuck? See Troubleshooting or the course map. The Part VI review quiz is at the end of Ch 30.
