Chapter 1

The Data Is the Problem

“Picture this: Toward the end of the development cycle, your game crawls, but you don’t see any obvious hotspots in the profiler. The culprit? Random memory access patterns and constant cache misses.” Noel Llopis opened the 2009 article that named data-oriented design with that scene[1]. Fourteen years later Casey Muratori took the textbook example of “clean” polymorphic code, a class hierarchy of shapes with a virtual Area(), and made it ten times faster by changing how the shapes were stored[6]. This chapter is about why that works. It covers where the idea came from, what it is and is not, and the same shapes benchmark rebuilt in Rust, Zig and Odin and measured on a real machine.

The short version: your program runs on a CPU that is very fast at arithmetic, slow to fetch memory it has not seen recently, and good at guessing branches only when they follow a pattern. Most programs do the same thing to many items, so the way those items sit in memory decides how much of the machine you actually use. Data-oriented design (DOD) is the habit of designing that layout first: work out what data you have, how much of it, and how it will be read, then write the code that transforms it. The rest of this book is techniques for doing that well, in three languages that make it easier than C++ did.

What data-oriented design is

Llopis gave the definition that stuck: “Data-oriented design shifts the perspective of programming from objects to the data itself: The type of the data, how it is laid out in memory, and how it will be read and processed”[1]. Programming, he wrote, “by definition, is about transforming data”. A program takes input data and produces output data, so it makes sense to start from the data rather than from the code that happens to touch it.

Mike Acton put the same idea as the first principle of his CppCon 2014 keynote: “The purpose of all programs, and all parts of those programs, is to transform data from one form to another.” He followed it with “If you don’t understand the data you don’t understand the problem” and “If you don’t understand the hardware, you can’t reason about the cost of solving the problem”[3]. Richard Fabian’s book gives the most careful version: “data-oriented design is the practice of designing software by developing transformations for well-formed data where the criteria for well-formed is guided by the target hardware and the patterns and types of transforms that need to operate on it”[4].

Three ideas run through all three definitions, and through every chapter after this one:

  1. Where there is one, there are many. Llopis asked how many places in your last program had only one of something: “One enemy? One vehicle? One pathfinding node? One bullet? One particle? Never!”[1] Code written for one object at a time pays its overheads once per object. Code written for the whole batch pays them once.
  2. The data is not the problem domain. That is Fabian’s first principle[4]. The way you talk about a game (a monster has a position, health and an inventory) does not have to be the way you store it. Store it the way it is read.
  3. The hardware is the platform. A cache line, a branch predictor and a SIMD register have costs you can estimate on paper. Acton’s blunt phrasing: “Software does not run in a magic fairy aether powered by the fevered dreams of CS PhDs”[3].

DOD is not “only about cache misses”. Fabian calls that “a common misconception” and says the approach “is about all aspects of the data”[4]: how much of it there is, how often it changes, which parts are read together, and what you can avoid storing at all. Caches are just where the cost shows up first, which is why this chapter starts with them.

A short history, 2009 to 2023

None of the ideas are new. Acton said so himself: DOD is “certainly not new ideas”, it is “more of a reminder of first principles” and “a response to the culture of C++”[3]. Fred Brooks wrote in 1975, “Show me your tables, and I won’t usually need your flowcharts; they’ll be obvious” (quoted in Teodorescu’s ACCU retrospective[11]). Database people and HPC people had laid data out by access pattern for decades. What changed around 2009 was the hardware: memory latency, measured in CPU cycles, had grown so large that object-at-a-time code left most of the chip idle. Fabian: “The time was right in 2009. The hardware was ripe for a change in how to develop”[4].

Llopis, 2009: the name

Llopis’s column in the September 2009 Game Developer blamed “object-oriented programming (OOP) and the culture that surrounds it” for games that were slow without an obvious hotspot and hard to parallelize[1]. His fix was to organize the program around its “ideal data format”, usually “large blocks of contiguous, homogeneous data that we can process sequentially”.

Albrecht, 2009: the numbers

Tony Albrecht, then at Sony’s European R&D group, gave the movement its first widely shared measurements. His slides start with a chart from Hennessy and Patterson: “1980: RAM latency ~ 1 cycle”, “2009: RAM latency ~ 400+ cycles. What can you do in 400 cycles?”[2] His test was a scene tree of 11,111 nodes updated on a PS3. The profile showed 50,421 branch mispredictions at 23 cycles each, about 0.36 ms, and 36,345 L2 cache misses at 400 cycles each, about 4.54 ms: the misses cost more than ten times as much. He then changed the data and left the maths alone. Moving the same objects together in memory took the update from 19.6 ms to 12.9 ms with no code change, and flattening them into arrays took it to 4.8 ms; software prefetch then got it to 3.3 ms (Chapter 2 charts all four steps).

In 2017 Albrecht repeated the exercise on a modern x86 machine with 55,000 objects: layout alone took the update from 17.5 ms to 9.5 ms, “No functional code changes”, and SIMD then took it to 6.2 ms[10]. His conclusion is a good motto for this book: “Measuring performance is not enough. You need to know why something is slow.”

Acton, 2014: the three lies and a 10× napkin

Mike Acton’s keynote at CppCon 2014 is the talk most people mean when they say “DOD”. He was the engine director at Insomniac Games, and he told a room of C++ programmers that their culture rested on three lies: “Software is a platform” (“Obvious, hardware is the platform”), “Code designed around model of the world” (which hides data and couples unrelated things), and “Code is more important than data”[3].

His rule of thumb from the same talk became the slogan of the whole movement: “Where there is one, there are many. Try looking on the time axis.” The second sentence matters. Even a value you have exactly one of, like a flag on the player, has many instances over time, one per frame. Then he did arithmetic, which is the part worth copying.

The worked example: UpdateFoo

Acton showed a member function, GameObject::UpdateFoo(float f), that reads a two-float velocity, takes its length, and adds it into a float member m_Foo. In the compiled code the velocity sat at byte offset 8 of the object and m_Foo at offset 184, in a different cache line. He estimated a cache miss at “~200” cycles and the maths (multiply, add, square root) at about 40[3].

Then he moved the data the loop needs into its own arrays: a 12-byte FooUpdateIn {float m_Velocity[2]; float m_Foo;} and a 4-byte FooUpdateOut {float m_Foo;}, processed by a free function UpdateFoos(in, count, out, f). For 32 items that is 384 bytes of input (6 lines) and 128 bytes of output (2 lines), and the hardware prefetcher can stream the next line while the current one is processed.

Before reading on: with those numbers, roughly how much faster is the array version than the object version?

The object version pays two waited-for misses plus the work: 2 × 200 + 40 = 440 cycles per item. The array version touches 8 lines for 32 items. If prefetching overlaps memory with work, time is the larger of 32 × 40 = 1,280 cycles of maths and 8 × 200 = 1,600 cycles of line fetches, so 1,600 / 32 = 50 cycles per item. That is 8.8×, which Acton rounded to 10×. Play with the sliders below and watch which bound wins.

Acton’s slides do the same sum. In the object version about 400 of the 440 cycles are waiting: “Time spent waiting for L2 vs. actual work ~10:1”. Each 64-byte line delivered 8 or 4 useful bytes: “Waste 56 bytes / 64 bytes”, “Waste 60 bytes / 64 bytes”, “90% waste!” In the array version each input line carries 5.33 items, about 213 cycles of work, roughly the cost of one miss, so the memory cost hides behind the work. His conclusion: “Using cache line to capacity* = 10x speedup”, with the footnote “* Used. Still not necessarily as efficiently as possible.”

The point is not the exact 10×. It is that you can get a useful estimate before writing any code, by counting bytes and lines. The slide that follows reads: “Ignoring inconvenient facts is not engineering; It’s dogma.”[3]

Fabian, 2018: tables

Richard Fabian’s Data-Oriented Design is the book-length treatment, free to read online[4]. Its distinctive move is to borrow from databases: normalize your data into tables, and let a row’s presence in a table be its state. An entity is not “a monster with an isHurt flag”. It is a row that appears in the hurt table while it is hurt. He calls this existence-based processing, and Chapters 7 and 9 build on it. He also concedes that objects work well for driver layers and APIs with large, stable handles.

Kelley, 2021: making the many smaller

Andrew Kelley’s Handmade Seattle talk is the bridge to this book’s languages[5]. He rewrote the Zig compiler’s core data structures and reduced the method to one sentence. In a third-party transcript of the talk it reads: “Identify where you have a lot of the same thing in memory and make the size of each thing smaller.” The results he reported for the compiler: tokens went from 64 bytes to 5, AST nodes from 120 bytes to 15.6 on average (22% faster parsing), and instructions of ZIR, Zig’s untyped intermediate form, from 54 bytes to 20.3 (a further 39% less wall-clock time). Chapters 3, 4, 5 and 11 are this talk, worked through in three languages.

Muratori, 2023: the shapes

Casey Muratori’s video and article took the example that “clean code” books use to teach polymorphism and measured it[6]. A class with a virtual Area() and four subclasses (square, rectangle, triangle, circle), summed through an array of pointers, ran at about 35 cycles per shape. One flat shape_union {type, width, height} and a switch gave 24 cycles. Then he noticed that every area is a coefficient × width × height, replaced the switch with a four-entry table lookup, and got 3.0–3.5 cycles, “fully 10x faster or more”. A second per-shape property (corner count) pushed the table version to about 15× faster, and a lightly optimized AVX version to 20–25×.

His most quoted lines are “It’s three or four years of hardware evolution erased because somebody said to use polymorphism instead of switch statements”, and “Our job is to write programs that run well on the hardware that we are given”. His own caveats matter just as much; they come up below.

What DOD is not

This book’s folder is called data-oriented-programming, because that is what it was commissioned as. But that phrase already names something else, and the clash causes real confusion, so here it is sorted out.

Yehonathan Sharvit’s Data-Oriented Programming (Manning, 2022) is a good book about a different goal. Its four principles are “Separating code (behavior) from data”, “Representing data with generic data structures”, “Treating data as immutable” and “Separating data schema from data representation”[8]. The first overlaps with DOD. The second and third pull the other way: a map of boxed values is the opposite of a packed array. Brian Goetz’s “Data Oriented Programming in Java” means records, sealed types and pattern matching[9]: the tagged-union style of version 2 below, a fine way to model data that says nothing about layout.

Data-driven design is different again. Llopis was explicit: “data-oriented design does not imply that something is data-driven … That is an orthogonal concept”[1]. A data-driven game reads its rules from files, and it can still store everything in a tree of objects. Finally, DOD is not the same thing as an entity-component system (ECS). An ECS is one architecture that often uses DOD layouts, and Chapter 9 looks at it critically.

The shapes benchmark, in three languages

Now the code. Every program in this book is written three times, in Rust 1.100, Zig 0.17.1 and Odin dev-2026-11, as honest equivalents: the same algorithm, the same data and the same sizes, each written the way that language would naturally write it. Where the languages differ, the difference is the lesson.

The job is Muratori’s, with one change: instead of summing the areas, each version writes the area of every shape into an output array. That is a transform in Acton’s sense, and it avoids a trap: a floating-point sum is a chain of dependent additions that would cap the fast versions at one add per shape (Chapter 8 deals with it). All three programs generate the same shapes from the same seeded SplitMix64 generator, so they compute bit-identical areas. Every version prints a checksum: the wrapping sum of the areas’ bit patterns, which does not depend on order. At 220 shapes it is 0x000424fc68e6dec1 in all six runs of all three languages.

Version 1: dynamic dispatch

The “clean” version: each shape is its own type with its own area, the collection holds type-erased handles, and the call site does not know what it is calling. The three languages spell this very differently.

// ---- 1. dynamic dispatch: a trait object per shape ----
trait Shape {
    fn area(&self) -> f32;
}
impl Shape for Square {
    fn area(&self) -> f32 {
        self.side * self.side
    }
}
impl Shape for Rectangle {
    fn area(&self) -> f32 {
        self.width * self.height
    }
}
impl Shape for Triangle {
    fn area(&self) -> f32 {
        0.5 * self.base * self.height
    }
}
impl Shape for Circle {
    fn area(&self) -> f32 {
        PI * self.radius * self.radius
    }
}

/// Each element is a 16-byte fat pointer (data pointer + vtable pointer) to its own heap allocation.
fn areas_dyn(shapes: &[Box<dyn Shape>], out: &mut [f32]) {
    for (o, s) in out.iter_mut().zip(shapes) {
        *o = s.area(); // load vtable pointer, load fn pointer, indirect call
    }
}
const Shape = struct {
    ptr: *anyopaque,
    vtable: *const VTable,

    const VTable = struct {
        area: *const fn (ptr: *anyopaque) f32,
        destroy: *const fn (ptr: *anyopaque, gpa: Allocator) void,
    };

    fn area(s: Shape) f32 {
        return s.vtable.area(s.ptr); // load fn pointer from the vtable, indirect call
    }

    /// Heap-allocates `value` and returns a Shape whose vtable is generated at compile time for T.
    fn create(gpa: Allocator, value: anytype) !Shape {
        const T = @TypeOf(value);
        const gen = struct {
            fn areaOf(ptr: *anyopaque) f32 {
                const self: *T = @ptrCast(@alignCast(ptr));
                return self.area();
            }
            fn destroyIt(ptr: *anyopaque, a: Allocator) void {
                const self: *T = @ptrCast(@alignCast(ptr));
                a.destroy(self);
            }
            const vtable: VTable = .{ .area = areaOf, .destroy = destroyIt };
        };
        const p = try gpa.create(T);
        p.* = value;
        return .{ .ptr = p, .vtable = &gen.vtable };
    }
};

fn areasDyn(shapes: []const Shape, out: []f32) void {
    for (shapes, out) |s, *o| o.* = s.area();
}
square_area :: proc "contextless" (s: Square) -> f32 {return s.side * s.side}
rectangle_area :: proc "contextless" (r: Rectangle) -> f32 {return r.width * r.height}
triangle_area :: proc "contextless" (t: Triangle) -> f32 {return 0.5 * t.base * t.height}
circle_area :: proc "contextless" (c: Circle) -> f32 {return math.PI * c.radius * c.radius}

// An explicit overload set: `area(x)` picks the procedure by the argument's type at compile time.
area :: proc {
	square_area,
	rectangle_area,
	triangle_area,
	circle_area,
}

// ---- 1. dynamic dispatch: a type-erased pointer plus a pointer to a table of procedure pointers ----
Shape_VTable :: struct {
	area: proc "contextless" (data: rawptr) -> f32,
}

Shape :: struct {
	data:   rawptr,
	vtable: ^Shape_VTable,
}

// One vtable per type. Each entry casts the rawptr back to its concrete type.
square_vtable := Shape_VTable {
	area = proc "contextless" (data: rawptr) -> f32 {return area((^Square)(data)^)},
}
rectangle_vtable := Shape_VTable {
	area = proc "contextless" (data: rawptr) -> f32 {return area((^Rectangle)(data)^)},
}
triangle_vtable := Shape_VTable {
	area = proc "contextless" (data: rawptr) -> f32 {return area((^Triangle)(data)^)},
}
circle_vtable := Shape_VTable {
	area = proc "contextless" (data: rawptr) -> f32 {return area((^Circle)(data)^)},
}

areas_dyn :: proc "contextless" (shapes: []Shape, out: []f32) {
	for s, i in shapes {
		out[i] = s.vtable.area(s.data) // load proc pointer from the vtable, indirect call
	}
}

Rust has this built in. Box<dyn Shape> is a fat pointer: 8 bytes pointing to the heap object and 8 bytes pointing to a compiler-generated vtable for that concrete type (drop glue, size, alignment, then the trait’s methods; the exact layout is unspecified). Each Box::new is a separate heap allocation. Zig has no traits, and its standard library uses this hand-built pattern for its own interfaces: std.mem.Allocator is ptr: *anyopaque, vtable: *const VTable. Here create builds one vtable per concrete type at compile time. Odin has no methods. Procedures are values, so a vtable is just a struct of procedure fields, and Shape mirrors Zig’s {data, vtable}. The "contextless" calling convention drops the implicit context pointer, so the call carries only the data pointer, as in the other two.

Look at what one iteration costs. The loop loads a 16-byte handle and follows the data pointer to the heap object. It loads a function pointer out of the vtable and makes an indirect call, a jump to an address held in a register. The CPU cannot wait to learn that address before it fetches the next instructions, so it predicts the target from history. If the shapes come in random order, the history is useless.

Version 2: a switch over a tagged union

Muratori’s first step was to put every shape in one fixed-size value with a type tag and switch on the tag. All three languages have tagged unions (sum types) built in, so the idiomatic version reuses the very same structs and the very same area functions. Only the dispatch changes.

enum ShapeEnum {
    Square(Square),
    Rectangle(Rectangle),
    Triangle(Triangle),
    Circle(Circle),
}

/// Same structs, same `area` methods; only the dispatch changed. The compiler sees every case and inlines it.
fn areas_match(shapes: &[ShapeEnum], out: &mut [f32]) {
    for (o, s) in out.iter_mut().zip(shapes) {
        *o = match s {
            ShapeEnum::Square(q) => q.area(),
            ShapeEnum::Rectangle(r) => r.area(),
            ShapeEnum::Triangle(t) => t.area(),
            ShapeEnum::Circle(c) => c.area(),
        };
    }
}
const ShapeUnion = union(enum) {
    square: Square,
    rectangle: Rectangle,
    triangle: Triangle,
    circle: Circle,

    /// `inline else` stamps out one prong per variant, each calling that variant's own `area`.
    fn area(s: ShapeUnion) f32 {
        return switch (s) {
            inline else => |v| v.area(),
        };
    }
};

fn areasSwitch(shapes: []const ShapeUnion, out: []f32) void {
    for (shapes, out) |s, *o| o.* = s.area();
}
Shape_Union :: union #no_nil {
	Square,
	Rectangle,
	Triangle,
	Circle,
}

areas_switch :: proc "contextless" (shapes: []Shape_Union, out: []f32) {
	for s, i in shapes {
		switch v in s {
		case Square:
			out[i] = area(v)
		case Rectangle:
			out[i] = area(v)
		case Triangle:
			out[i] = area(v)
		case Circle:
			out[i] = area(v)
		}
	}
}

Each element is now 12 bytes in all three languages (the programs print it): a tag padded to 4 bytes plus the largest payload, two f32s. They live in one contiguous array, with no pointers and no heap objects. Rust’s match calls each area statically. Zig’s inline else stamps out one prong per variant. Odin’s switch v in s binds v to the payload, and #no_nil removes the union’s “empty” state. All three compilers reject a switch that misses a case (Odin unless you write #partial switch), so adding a fifth shape points you at every place that must handle it.

The CPU still has to choose a code path per shape, so there is still a data-dependent jump to predict. Muratori was clear that a switch is not “less polymorphic” than a vtable. They are “two different implementations of the same thing”[6].

Version 3: the coefficient table

Once the four cases sit next to each other, the pattern is plain to see. Every area is c × w × h. Store a kind and two dimensions (squares and circles store theirs twice), look up c, and the branch disappears:

#[repr(u8)]
enum Kind {
    Square,
    Rectangle,
    Triangle,
    Circle,
}

/// Squares and circles store their one dimension twice (height = width), as in Muratori's version.
#[derive(Clone, Copy)]
struct FlatShape {
    kind: Kind,
    width: f32,
    height: f32,
}

const COEF: [f32; 4] = [1.0, 1.0, 0.5, PI];

fn areas_table(shapes: &[FlatShape], out: &mut [f32]) {
    for (o, s) in out.iter_mut().zip(shapes) {
        *o = COEF[s.kind as usize] * s.width * s.height; // no branch: one load from a 16-byte table
    }
}
const Kind = enum(u8) { square, rectangle, triangle, circle };

/// Squares and circles store their one dimension twice (height = width), as in Muratori's version.
const FlatShape = struct { kind: Kind, width: f32, height: f32 };

const coef = [4]f32{ 1.0, 1.0, 0.5, pi };

fn areasTable(shapes: []const FlatShape, out: []f32) void {
    for (shapes, out) |s, *o| o.* = coef[@backingInt(s.kind)] * s.width * s.height;
}
Kind :: enum u8 {
	Square,
	Rectangle,
	Triangle,
	Circle,
}

// Squares and circles store their one dimension twice (height = width), as in Muratori's version.
Flat_Shape :: struct {
	kind:          Kind,
	width, height: f32,
}

// An enumerated array: indexed by Kind directly, no casts.
COEF := [Kind]f32 {
	.Square    = 1.0,
	.Rectangle = 1.0,
	.Triangle  = 0.5,
	.Circle    = math.PI,
}

areas_table :: proc "contextless" (shapes: []Flat_Shape, out: []f32) {
	for s, i in shapes {
		out[i] = COEF[s.kind] * s.width * s.height // no branch: one load from a 16-byte table
	}
}

This is the step that gives the 10×. The loop body is now a load, a table lookup and two multiplies, with no jump that depends on the data. It was not a clever compiler that made it possible. The programmer saw that the four types were not really four behaviours but one formula with four constants. Muratori’s argument is that code organized by operation (all the area cases side by side) makes such patterns visible, while code organized by type (each class in its own file) hides them. To index by an enum, Rust converts it with as usize, Zig uses @backingInt, and Odin has enumerated arrays, [Kind]f32, indexed by the enum directly.

@intFromEnum and @enumFromInt still compile but are deprecated in favour of @backingInt and @fromBackingInt[13], which this book uses throughout.

Version 4 (preview): one array per kind

Muratori stopped at the table. In a follow-up he wrote that “Data Oriented Design” proponents objected that he had not shown a “segregated array case, which would have been faster than any of the cases I showed”, and answered, “I do not disagree with them at all”[7]. Here it is. If the kind of a shape never changes, do not store it. Store which array the shape is in. Squares need one f32, rectangles and triangles two, and circles one, so the average is 6 bytes per shape instead of 12. Each loop runs one formula with constants the compiler can see.

struct ShapesByKind {
    squares: Vec<f32>,         // side
    rectangles: Vec<[f32; 2]>, // width, height
    triangles: Vec<[f32; 2]>,  // base, height
    circles: Vec<f32>,         // radius
}

/// Four tight loops with no dispatch. `out` is filled kind by kind, so its order differs from the other versions.
fn areas_by_kind(s: &ShapesByKind, out: &mut [f32]) {
    let (o_sq, rest) = out.split_at_mut(s.squares.len());
    let (o_re, rest) = rest.split_at_mut(s.rectangles.len());
    let (o_tr, o_ci) = rest.split_at_mut(s.triangles.len());
    for (o, &side) in o_sq.iter_mut().zip(&s.squares) {
        *o = side * side;
    }
    for (o, &[w, h]) in o_re.iter_mut().zip(&s.rectangles) {
        *o = w * h;
    }
    for (o, &[b, h]) in o_tr.iter_mut().zip(&s.triangles) {
        *o = 0.5 * b * h;
    }
    for (o, &r) in o_ci.iter_mut().zip(&s.circles) {
        *o = PI * r * r;
    }
}
const ShapesByKind = struct {
    squares: std.ArrayList(f32) = .empty, // side
    rectangles: std.ArrayList([2]f32) = .empty, // width, height
    triangles: std.ArrayList([2]f32) = .empty, // base, height
    circles: std.ArrayList(f32) = .empty, // radius

    fn deinit(self: *ShapesByKind, gpa: Allocator) void {
        self.squares.deinit(gpa);
        self.rectangles.deinit(gpa);
        self.triangles.deinit(gpa);
        self.circles.deinit(gpa);
    }
};

/// Four tight loops with no dispatch. `out` is filled kind by kind, so its order differs from the other versions.
fn areasByKind(s: *const ShapesByKind, out: []f32) void {
    var i: usize = 0;
    for (s.squares.items, out[i..][0..s.squares.items.len]) |side, *o| o.* = side * side;
    i += s.squares.items.len;
    for (s.rectangles.items, out[i..][0..s.rectangles.items.len]) |r, *o| o.* = r[0] * r[1];
    i += s.rectangles.items.len;
    for (s.triangles.items, out[i..][0..s.triangles.items.len]) |t, *o| o.* = 0.5 * t[0] * t[1];
    i += s.triangles.items.len;
    for (s.circles.items, out[i..][0..s.circles.items.len]) |r, *o| o.* = pi * r * r;
}
Shapes_By_Kind :: struct {
	squares:    [dynamic]f32, // side
	rectangles: [dynamic][2]f32, // width, height
	triangles:  [dynamic][2]f32, // base, height
	circles:    [dynamic]f32, // radius
}

// Four tight loops with no dispatch. `out` is filled kind by kind, so its order differs from the other versions.
// Copy the slice headers into locals first: read through `s` inside the loops, LLVM must assume a store to
// `o[i]` might change `s.squares` itself, reloads it every iteration, and does not vectorize (much slower).
areas_by_kind :: proc(s: ^Shapes_By_Kind, out: []f32) {
	squares, rectangles, triangles, circles := s.squares[:], s.rectangles[:], s.triangles[:], s.circles[:]
	o := out
	for side, i in squares {
		o[i] = side * side
	}
	o = o[len(squares):]
	for r, i in rectangles {
		o[i] = r[0] * r[1]
	}
	o = o[len(rectangles):]
	for t, i in triangles {
		o[i] = 0.5 * t[0] * t[1]
	}
	o = o[len(triangles):]
	for r, i in circles {
		o[i] = math.PI * r * r
	}
}

This is Fabian’s “one table per enum value” and Muratori’s “n different arrays”. Chapter 7 develops it properly, including what happens when items change kind and must move between arrays. It is only a preview here because it changes the shape of the API: the output comes out grouped by kind. That is one reason the checksum must not depend on order.

The first line of the Odin procedure copies the four slices into locals. Without it the compiler had to assume that each store to the output might change the slice behind the pointer s, so it re-read it on every iteration, did not vectorize, and ran much more slowly (Chapter 4 explains the pitfall). The Zig loops compile to plain one-at-a-time arithmetic, because Zig 0.17.1 switches off LLVM’s loop vectorizer[12] (the details are in Chapter 4).

What the CPU does per shape

Before the measurements, a model. the figure below walks the same twelve shapes through each version. It shows the memory each one touches, drawn to scale (one pixel of width per byte, in every row), and the branch predictor’s guesses. The predictor here is the simplest useful one: it guesses that the next shape is the same kind as the last. Real predictors keep long histories; Chapter 7 looks at them.

In the vtable mode with random kinds, roughly how many of the 12 shapes will mispredict? And how many in “sorted by kind”?

About 3/4 of them, so around 9 of 12: with four equally likely kinds, the next shape matches the last only one time in four, and no history helps when there is no pattern. This particular draw gives 10, counting the first call, which has nothing to go on. Sorted, it is only the four kind changes, however many shapes there are. At 16 cycles each, the mispredicts alone add about 12 cycles to every random shape and almost nothing to sorted ones. The table and per-kind modes have no data-dependent branch, so they have nothing to mispredict.

The cycle numbers in the figure come from a deliberately crude model: a base cost per shape when every branch is predicted, plus the mispredict penalty for each wrong guess. Agner Fog puts the penalty at “approximately 15 - 25 clock cycles, depending on the processor”, and notes that “the rules for prediction and misprediction of virtual function calls is the same as for switch statements”[14]. That last remark predicts our first measured surprise.

Measured on this machine

Here are the six runs, in all three languages, at 220 (about a million) shapes, pinned to one core. Two of them are controls. They run versions 1 and 2 again on the same shapes after a stable sort by kind, with the heap objects allocated in sorted order. That separates the cost of the dispatch mechanism from the cost of unpredictable dispatch.

Four things stand out.

The table version is about 6× faster than dynamic dispatch in Rust, and 13× and 11× in Zig and Odin, whose table loops are faster than Rust’s. That is Muratori’s result, reproduced in three languages on a different CPU. The per-kind arrays go further, about 20× faster than dynamic dispatch in Rust (23× in Zig, 21× in Odin). They read half the bytes of the table version, and Rust and Odin vectorize those plain loops (Zig does not, as noted above). At a million shapes the per-kind loop mostly waits for memory, so the three languages end up close. At --quick size, where everything fits in L2, the vectorized Rust and Odin loops are clearly faster than Zig’s scalar one.

The switch is hardly faster than the vtable, about 1.1× in Rust, 1.2× in Zig and 1.0× in Odin, not Muratori’s 1.5×. In Rust they cost 9.7 ns and 8.8 ns per shape (Zig and Odin are in the same range), about two dozen cycles at this chip’s 2.6 GHz nominal clock. We cannot read the real clock without performance counters, so treat any cycle figure as a range. Agner Fog’s remark explains why the two are so close: an indirect call and a switch’s jump are predicted the same way, and on random kinds both are wrong most of the time.

Sorting fixes the switch, and only partly fixes dynamic dispatch. With the same shapes sorted by kind, the tagged union gets about 5× faster in Rust, where it lands close to the table. Sorted dynamic dispatch improves too, but stays 2.5× slower than the sorted switch in Rust, 2.6× in Odin and 1.8× in Zig (the allocator explains Zig, below). With prediction out of the way, what remains is memory. A million handles is 16 MB, and the heap objects behind them add another 32 MB, against 12 MB for the tagged array. That no longer fits in L2, or in the roughly 6–8 MiB of L3 this virtual machine actually gets (Chapter 2 measures it), so it streams from memory, and the prefetcher hides only part of that cost. That is Acton’s arithmetic again.

The allocator shows up in the numbers. The programs print the median distance between consecutive heap objects. Rust’s Box and Odin’s new_clone both went to glibc malloc here, and each 4- or 8-byte object sat 32 bytes from the previous one. Zig’s init.gpa in -O fast is std.heap.smp_allocator, which packs them 8 bytes apart, and Zig’s sorted dynamic dispatch is correspondingly faster. None of this is visible in the source code. It is a property of where the data ended up.

Three compilers, three default targets

By default Rust compiles for baseline x86-64 (SSE2), Zig for the machine it runs on (here an Ice Lake server with AVX-512), and Odin for x86-64-v2 (SSE4.2, no AVX), so when a Zig loop beats a Rust loop, check this before you conclude anything about the language. Chapter 8 measures what the wider vectors are worth.

Muratori’s caveats, and ours

A demonstration this clean invites overreach, so here are its limits, starting with the ones its author gave. In his reply to a reporter, Muratori said the video’s goal was “to quickly demonstrate the magnitude of the performance cost for each programming style choice”, not to explain why. That explanation comes later in his course[7]. He chose not to show separate arrays because he “was trying to demonstrate the performance difference between methods that handle data types whose type needs to be dynamic”. For a full analysis he “would have used real-world examples like graph traversal, where types cannot be easily segregated into separate arrays without a lot of extra work.”

Our own caveats:

  • It is a microbenchmark. The loop does nothing but dispatch. In a real program, each call does more work, and the dispatch overhead is a smaller share of it. The win from version 3 came from noticing a formula. Most real types will not collapse into one line.
  • The heap is pristine. We allocate the boxes in a fresh process, in order, so they sit nearly sequentially in memory. That is the best case for dynamic dispatch. A long-running program with a fragmented heap scatters them, and every handle becomes the pointer chase of Chapter 2.
  • Random kind order is a choice. It is a realistic one for a scene full of mixed objects, and it is what makes the branch unpredictable. With sorted kinds the switch is cheap (the control runs show how cheap).
  • The machine is a shared virtual machine with no performance counters, so we report noisy wall-clock medians, not cycles (Chapter 12).

None of this makes the result go away. It tells you where the cost lives. You pay for dispatch when it is unpredictable, and you pay for memory when it is scattered or padded. Both are properties of the data, and you can fix both before you write the loop.

Your program is a transformation of many items of data on real hardware, so design the layout of that data (how big each item is, what is next to what, and what the CPU has to guess) before you design the code that touches it.

Exercises

Using the bytes-per-shape table, how many 64-byte lines does each version pull through the cache for 220 shapes (ignore the output array)? Which versions fit in this machine’s 1.25 MiB L2?

Dynamic dispatch with glibc: 16 MiB of handles + 32 MiB of heap = 48 MiB = 786,432 lines. With Zig’s allocator: 24 MiB = 393,216 lines. Tagged union or table: 12 MiB = 196,608 lines. Per-kind: 6 MiB = 98,304 lines. None fit in L2. Chapter 2’s sweep found that this virtual machine gets roughly 6–8 MiB of usable L3 (the chip has 54 MiB, shared with the host’s other tenants), so only the per-kind arrays can stay in L3; the rest stream from memory. At --quick size (4,096 shapes) everything fits in L2 (the largest is 192 KiB), which is why the quick-run ratios differ from the full-size ones.

A predictor remembers the last two kinds and guesses the next from that pair. Does it beat 3/4 mispredicts on uniformly random kinds? On kinds that repeat in a fixed cycle (square, circle, triangle, rectangle, square, …)?

Random: no. Each kind is independent of the history, so any guess is right one time in four, whatever the predictor remembers. Cycle: yes, after a few shapes to learn it, it is never wrong, because the history now determines the next kind. History only helps when the data has a pattern; sorting by kind gives it one.

Muratori’s second experiment weights each area by 1 / (1 + corners). What has to change in each of the four versions?

Version 1 needs a second virtual method (corner_count), so a second indirect call per shape. Version 2 needs a second match or switch, or a bigger one. In version 3 only the constants change: COEF becomes {1/5, 1/5, 0.5/4, π} (a circle has 0 corners), and the loop stays the same. That is why its advantage grew to about 15× in his test. In version 4 each loop gets a different constant, and the code shape is unchanged.

In the figure above, set misses to 300 cycles and keep 40 cycles of work. What speedup does the model give, and how much work per item would make the array version compute-bound?

Objects: 2 × 300 + 40 = 640 cycles per item. Arrays (32 items, 8 lines): max(32 × 40, 8 × 300) = 2,400 cycles = 75 per item, so about 8.5×. It becomes compute-bound when 32 × work ≥ 8 × 300, so work ≥ 75 cycles per item. Acton’s per-line version of the same argument (5.33 items × work ≥ one miss) ignores the output lines and gives 56.

Suppose a long-running program had freed and reallocated shapes for an hour, so the boxes are scattered across the heap in random order. Which versions get slower, and does sorting the handle array by kind still help?

Only dynamic dispatch, because it is the only version that follows pointers. Each handle now points to an unrelated line, often a miss, and the hardware cannot prefetch it because the address is only known once the handle has been loaded. Sorting the handles by kind fixes branch prediction but not the memory order, so you pay the pointer chase of Chapter 2 on every shape. The array versions do not care how the heap looks.

std.mem.Allocator in Zig uses exactly the {ptr, vtable} pattern that lost so badly here. Is that a mistake?

No. An allocator call is not the inner loop of anything you care about. A program makes far fewer allocator calls than it touches items, and an indirect call that goes to the same target every time is well predicted. Dynamic dispatch costs a lot when it is per item, in a hot loop, over unpredictable types. At a boundary called rarely (an allocator, an I/O backend, a plugin), it buys flexibility for almost nothing. Fabian makes the same concession for driver layers and APIs. “Where there is one, there are many” is the test: how many calls are there, really?
