A B-tree that stores byte strings can only compare byte strings. This page shows how a row of typed values is turned into bytes whose plain memcmp order is the order you asked for, and what goes wrong when any single step of the encoding is left out. It accompanies chapter 11 of the guide; the code it mirrors is in zig/src/keycodec.zig and rust/src/keycodec.rs.

1. Sort by bytes, get the order of the values

Eight rows with the key (name ASC, score DESC NULLS LAST, id ASC), in the order the chapter's program receives them. Press play: an insertion sort orders them by comparing key bytes only. Then switch one of the four fixes off and watch the same sort put rows in the wrong place. You can add rows of your own; in a name, \x00 (backslash, x, two hex digits) enters one arbitrary byte.

2. One value becomes one key column

Pick a type, type a value, and step through what the encoder does to it and why. The code panel highlights the line that performs each step. For f64 you can also type inf, nan, -nan, or raw bits as hex such as 0xfff000000000beef (a NaN with a payload).

3. Why varints are not keys

Records store lengths and small integers as varints because they are short. Type two numbers and compare the byte order of each encoding with the numeric order.
