Chapter 3

Size, Alignment and Padding

Take a 16-byte struct and add one bool. In information-theory terms you added one bit, but the struct is now 24 bytes. Andrew Kelley puts it this way: “We paid the cost of 64 bits just to add one to the struct.”[2] This chapter explains where those bytes go, which of the three languages moves your fields around and which leaves them alone, and how to win the bytes back. It ends with a measurement showing when bytes turn into time.

Chapter 2 showed that the machine moves memory in 64-byte cache lines and that a trip to DRAM costs about a hundred times more than an L1 hit. Once you know that, the size of an element is not a bookkeeping detail. It sets how many elements arrive per line, how many lines a loop pulls in, and so whether a working set fits in a cache level or spills out of it. The unit of thought in this chapter is bytes per element. Every struct in it has a size_of you can predict on paper, and three compilers that check you.

The rules, in three lines

On x86-64 and AArch64 every primitive type has a natural alignment equal to its size: u8 and bool are 1, u16 is 2, u32 and f32 are 4, and u64, f64 and pointers are 8. A value of alignment a must start at an address that is a multiple of a. A struct obeys three rules:

  1. Each field starts at the next offset that is a multiple of its alignment. The skipped bytes are padding.
  2. The struct's alignment is the largest alignment of its fields.
  3. The struct's size is rounded up to a multiple of its alignment. The bytes added at the end are tail padding. They exist so that element i + 1 of an array is aligned too, because arrays have no gaps between elements.

That is the whole algorithm. Eric Raymond's “The Lost Art of Structure Packing” works through the same rules for C at length[10]. Kelley's talk on data-oriented design walks an audience through it as a quiz[1][2], and it is worth doing the same quiz yourself before you look at a tool.

In C order, what are the size and alignment of struct { a: u32, b: bool }, of struct { a: u32, b: u64, c: u32 }, and of the same three fields written as u32, u32, u64?

8 B with alignment 4 (4 + 1, then 3 bytes of tail padding). 24 B with alignment 8: a at 0, 4 bytes of padding, b at 8, c at 16, then 4 bytes of tail padding. Written as u32, u32, u64 it is 16 B with no padding at all. All three programs print exactly these numbers. Add a bool to the 16-byte version and it is 24 B again.

Why the hardware wants it

Alignment exists because loads and stores work on aligned chunks. A naturally aligned value of up to 8 bytes can never straddle a 64-byte cache line, so the load touches one line and one bank. A misaligned value can cross a line boundary and then needs two line accesses. AMD's Zen 5 optimization guide says a misaligned load that spans a 64-byte boundary “suffers, at minimum, a one cycle penalty”[17], and crossing a 4 KiB page boundary is worse. Some architectures fault on misaligned accesses altogether, and atomics must be naturally aligned everywhere. So compilers pad by default, and when you ask for no padding they emit byte-wise or unaligned loads instead.

Padding costs you because the cache does not know which bytes are padding. A line arrives whole. Padding takes up cache capacity, memory bandwidth, page-table reach and disk space, exactly like real data. the figure below shows the arithmetic for the monster struct that runs through this chapter.

Who decides the field order

The three rules are fixed. What varies is whose order they apply to. If the compiler may lay fields out in any order, it can sort them so that padding nearly disappears. If it must follow the order you wrote, the padding is your responsibility. Here the three languages differ, and the differences matter when you read other people's numbers: Kelley's quiz is about C order, and it gives different answers for a plain Zig struct.

Rust. The Reference says that for the default representation “the ordering does not have to be the same as the order in which the fields are specified in the declaration of the type”, and that the layout may change between compilations[3]. In practice rustc sorts fields to keep padding small, which is why the Rust performance book tells you that you “do not have to worry about field ordering”[4]. #[repr(C)] switches to the C algorithm in declaration order, and that is what you need for FFI, for memory-mapped files, or whenever you want to control the order yourself.

Zig. A plain struct has no guaranteed layout. The language reference says that if well-defined layout is not needed, struct “is a better choice because it places fewer restrictions on the compiler”[7], and Zig 0.17.1 does reorder. extern struct matches the C ABI of the target. packed struct is something else again: a struct made of bits, covered in its own section below.

Odin. The documentation lists struct directives (#packed, #align, #raw_union, #min_field_align, #max_field_align)[8] but does not state the default ordering in so many words. So we measured it. The offset_of probes in layout.odin below put Mixed's fields at 0, 8, 16 and 20, exactly in declaration order, with 24 B total. The struct-level #asserts make the build fail if that ever changes. Odin keeps the order you write, the same as C and as Rust's repr(C).

Rust and Zig pick exactly the same order: the 8-byte field first, then the 4-byte one, then the bytes. That is what “sort by alignment, largest first” gives you, and sorting by hand in Odin gives the same offsets. Neither Rust nor Zig promises that algorithm. If an offset matters, ask the compiler with offset_of! or @offsetOf. Do not derive it from the declaration.

In the figure above, the Monster preset starts at 32 B in C order. Can any ordering get below 24 B?

No. The data is 8 + 4 + 4 + 1 + 1 = 18 bytes and the alignment is 8, so the size must be a multiple of 8 that is at least 18, which is 24. Sorting reaches that bound. The only ways below it are to change the fields themselves (narrower types, an index instead of a pointer, moving the bools out) or to change the alignment. That is the rest of the chapter.

Packed is not free. repr(packed) and #packed drop padding by giving every field alignment 1. The compiler then has to assume any field may be misaligned. Rust makes taking a reference to a packed field a compile error, because references must be aligned: copy the field out by value, or use &raw const s.field with read_unaligned. Odin allows &p.b on a #packed struct, but the pointer you get may be misaligned, and passing it to code that expects an aligned ^u64 (atomics, SIMD loads) is a bug. Use packed layouts for wire formats and file headers, and sort fields everywhere else. Sorting gets you within a few bytes of packed for free.

#field_align(N) is deprecated in favour of #min_field_align(N), and there is now also #max_field_align(N), which caps every field's alignment like C's #pragma pack. The parser also wants parentheses: #align(64) without them gets the warning “#align requires parentheses around the expression”[9].

Kelley's monster: 24 → 16 → 12 bytes

The middle of Kelley's talk is one struct shrunk in stages. A monster has a pointer to its animation, two 32-bit integers (hit points and a coordinate) and an alive flag. On a 64-bit CPU that is 8 + 4 + 4 + 1 = 17 bytes of data and 24 bytes of struct, “24 bytes on 64-bit CPUs”, and 2.4 KB for 100 of them[2]. Reordering does not help, because the fields are already sorted. The padding comes from the single byte at the end, which forces 7 bytes of tail padding.

Kelley removes the bool first. Instead of a flag in every monster, he keeps two arrays, one of live monsters and one of dead ones. The bit is still there, “it's which array is it in”, but it no longer costs memory, and the size falls to 16 B[2]. Then he replaces the 8-byte pointer with a 32-bit index into an animation array. That halves the field and also drops the struct's alignment from 8 to 4, so the size falls to 12 B: “Instead of taking up 2.4 kilobytes for 100 monsters, we're taking up 1.2”[2]. Out-of-band booleans, and the existence-based processing they lead to, are the subject of Chapter 7. Indices instead of pointers are Chapter 5. Here we only count the bytes.

struct Animation {
    frames: Vec<u32>,
}

/// A pointer, two u32s and a bool: 8 + 4 + 4 + 1 = 17 bytes of data, 24 bytes of struct.
struct Monster<'a> {
    anim: &'a Animation,
    hp: u32,
    y: u32,
    alive: bool,
}

/// `alive` moved out of band (one array of live monsters, one of dead ones): 16 bytes.
struct MonsterOob<'a> {
    anim: &'a Animation,
    hp: u32,
    y: u32,
}

/// The pointer replaced by a u32 index into an animation table: 12 bytes, alignment 4.
struct MonsterIdx {
    anim: u32,
    hp: u32,
    y: u32,
}

const _: () = assert!(size_of::<Monster>() == 24);
const _: () = assert!(size_of::<MonsterOob>() == 16);
const _: () = assert!(size_of::<MonsterIdx>() == 12);
const Animation = struct { frames: []const u32 };

const Monster = struct { anim: *const Animation, hp: u32, y: u32, alive: bool };
/// `alive` moved out of band (one list of live monsters, one of dead ones): 16 bytes.
const MonsterOob = struct { anim: *const Animation, hp: u32, y: u32 };
/// The pointer replaced by a u32 index into an animation table: 12 bytes, alignment 4.
const MonsterIdx = struct { anim: u32, hp: u32, y: u32 };

In all three languages the sizes are checked when the program compiles. Change a field and the build stops. The section on compile-time asserts below comes back to that. The struct-padding grids show the three stages side by side.

Enums as one byte

An enum with five variants needs three bits, and every language stores it in at least a byte. How many bytes beyond that depends on the language. Rust picks the smallest integer that fits the discriminants, so a five-variant fieldless enum is 1 byte unless you ask for something else with #[repr(u32)]. Zig infers the tag type: enum { bee, human, snake, wolf, ghost } has tag type u3 and occupies 1 byte. You can pin it with enum(u8), which also makes it usable in extern and packed structs.

Odin is different: “By default, int is used as the backing type for an enumeration”[8], so a plain enum {Bee, Human} is 8 bytes with alignment 8, and the program prints exactly that. Put that enum in a struct next to a u32 and the struct is 16 B, where enum u8 would give 8 B.

Odin enums default to 8 bytes. Write Kind :: enum u8 { ... } for any enum that is stored in bulk. An enum that is only passed around in procedure arguments can stay int-backed, but one per entity in a ten-million-element array is 70 MB of zeros.

Niches: making Option free

“Maybe a value” needs one more state than the value has. If the type already has bit patterns that are never valid, the compiler can use one of them for none and the optional costs no extra bytes. Rust calls such an invalid bit pattern a niche, and uses niches aggressively. A &T or Box<T> is never null, so Option<&T> is 8 bytes. A bool only uses 0 and 1, so Option<bool> is 1 byte. A five-variant enum leaves 251 byte values unused, so Option<Kind> is 1 byte. A plain u32 has no invalid pattern, so Option<u32> needs a separate tag and, after padding, takes 8 bytes. NonZeroU32 rules out 0, which gives the niche back: Option<NonZeroU32> is 4 bytes. The standard library documents this as a guaranteed representation for Option of the NonZero types, references, Box and a few more[12].

This matters most for indices. A parent link stored as Option<u32> doubles the field. A newtype around NonZeroU32 (store index + 1, or reserve 0 for a sentinel node) keeps it at 4 bytes. The Rust compiler does the same with its own index types: its newtype_index! macro reserves the values above 0xFFFF_FF00, so that Option of an index stays 4 bytes.

#[derive(Clone, Copy)]
enum Kind {
    Bee,
    Human,
    Snake,
    Wolf,
    Ghost,
}

/// A typed index whose zero bit pattern is forbidden, so `Option<AnimId>` can use 0 for `None`.
#[derive(Clone, Copy)]
struct AnimId(NonZeroU32);

const _: () = assert!(size_of::<Kind>() == 1);
const _: () = assert!(size_of::<Option<Kind>>() == 1); // spare discriminant values
const _: () = assert!(size_of::<Option<u32>>() == 8); // no spare bit pattern: tag + padding
const _: () = assert!(size_of::<Option<AnimId>>() == 4); // 0 is the niche
const _: () = assert!(size_of::<Option<&u64>>() == 8); // null is the niche
const Kind = enum { bee, human, snake, wolf, ghost }; // tag type u3, stored in 1 byte
/// Zig has no NonZero types. The idiom is a non-exhaustive enum with a named sentinel.
const AnimId = enum(u32) { none = std.math.maxInt(u32), _ };

comptime {
    std.debug.assert(@sizeOf(Kind) == 1);
    std.debug.assert(@sizeOf(?Kind) == 2); // no niche: a separate "has value" byte
    std.debug.assert(@sizeOf(?u32) == 8); // tag + padding
    std.debug.assert(@sizeOf(AnimId) == 4); // the sentinel costs nothing
    std.debug.assert(@sizeOf(?AnimId) == 8); // but `?` does not know about it
    std.debug.assert(@sizeOf(?*const u64) == 8); // optional pointers use address 0
}
Kind :: enum u8 {
	Bee,
	Human,
	Snake,
	Wolf,
	Ghost,
}
Kind_Default :: enum {
	Bee,
	Human,
} // backing type defaults to int: 8 bytes
// Odin has no NonZero types; a distinct integer with a reserved value is the usual typed index.
Anim_Id :: distinct u32
ANIM_NONE :: Anim_Id(max(u32))

#assert(size_of(Kind) == 1 && size_of(Kind_Default) == 8)
#assert(size_of(Maybe(Kind)) == 2) // a union tag byte; no niche from unused enum values
#assert(size_of(Maybe(u32)) == 8) // tag + padding
#assert(size_of(Maybe(Anim_Id)) == 8) // the reserved value is a convention, not a niche
#assert(size_of(Maybe(^u64)) == 8) // a single-pointer union uses nil: no tag

Zig guarantees exactly one niche: “An optional pointer is guaranteed to be the same size as a pointer. The null of the optional is guaranteed to be address 0”[7]. Other optionals get a separate flag. In 0.17.1 ?Kind is 2 bytes even though the enum's u3 tag has three unused values, and ?u31 is 8 bytes even though a whole bit is free. There is no NonZero type either. The Zig idiom for an optional index is a non-exhaustive enum with a named sentinel, enum(u32) { none = std.math.maxInt(u32), _ }, which stays 4 bytes and gives each index its own type (Alex Kladov calls the pattern a “happy accident of language design”[16]). You compare against .none by hand. Wrap it in ? and you are back to 8 bytes.

Odin's Maybe(T) is a union with one variant. A union whose only variant is a pointer uses nil as its empty state, so Maybe(^u64) is 8 bytes. Everything else carries a tag: Maybe(u32) is 8 bytes, and so is Maybe(Anim_Id) for a distinct u32. The idiom matches Zig's: a distinct u32 plus a reserved constant such as ANIM_NONE :: Anim_Id(max(u32)). The Odin overview also notes that multiple return values (-> (int, bool)) usually replace Maybe in APIs[8]. That is fine for a return value, but a struct field still needs a sentinel.

Smaller types: narrow integers, f16, quantization, bit packing

Reordering and niches remove padding. The next step is to make the fields themselves smaller. The Rust performance book's advice applies to all three languages: indices “are often reasonable to store as u32, u16, or even u8, and then coerce to usize at use points”[4]. A hit-point count below 1000 fits a u16, and a tile coordinate on a 4096-wide map fits 12 bits.

Quantization does the same for floats. A position inside a 1 km cell stored as three f32s takes 12 bytes. Store each axis as a u16 fraction of the cell and it takes 6 bytes, with a step of 1000 m / 65535 ≈ 1.5 cm, so the worst-case rounding error is half that. All three programs quantize 123.456 m to 8091 and decode it to 123.4607 m, an error of 4.7 mm. meshoptimizer's documentation describes the same trade for vertex data, for example “it's common to quantize normals using 3 8-bit integers”[19]. Quantize what you store. Do the arithmetic in full precision and convert at the edges.

Half floats are the built-in version of the same trade. Zig and Odin both have a native f16 (2 bytes, 11 significant bits). It holds 123.456 as 123.4375, an error of 1.85 cm at that magnitude, and the error grows with the magnitude. Quantization spreads its precision evenly over a known range instead. In Rust 1.100, f16 is still unstable (feature f16, tracking issue #116909[15]). On stable, store the raw u16 bits or quantize.

Bit packing goes below the byte. Zig's packed struct(u32) { kind: u4, layer: u4, index: u24 } is a u32 whose fields are bit ranges “arranged from least to most significant”[7], and Zig's arbitrary-width integers (u4, u24) make the widths part of the type. Odin's bit_field u32 { kind: u8 | 4, ... } does the same, with a “well defined layout (Least-Significant-Bit)” that the docs contrast with C bit-fields, which “are undefined and are not portable”[8]. Rust has no bit-fields, so you write the shifts and masks yourself in a newtype. All three encode (3, 7, 123456) as the same word, 0x01e24073.

/// World position as three f32: 12 bytes.
struct PosF32 {
    x: f32,
    y: f32,
    z: f32,
}

/// The same position quantized to u16 steps inside a 1 km cell (1000 m / 65535 ≈ 1.5 cm): 6 bytes.
struct PosU16 {
    x: u16,
    y: u16,
    z: u16,
}

const CELL_M: f32 = 1000.0;

fn quantize(v: f32) -> u16 {
    ((v / CELL_M).clamp(0.0, 1.0) * u16::MAX as f32).round() as u16
}

fn dequantize(q: u16) -> f32 {
    q as f32 / u16::MAX as f32 * CELL_M
}

/// Rust has no bit-fields: pack kind (4 bits), layer (4 bits) and index (24 bits) into a u32 by hand.
#[derive(Clone, Copy)]
struct PackedRef(u32);

impl PackedRef {
    fn new(kind: u32, layer: u32, index: u32) -> Self {
        assert!(kind < 16 && layer < 16 && index < (1 << 24));
        PackedRef(kind | layer << 4 | index << 8)
    }
    fn kind(self) -> u32 {
        self.0 & 0xF
    }
    fn layer(self) -> u32 {
        (self.0 >> 4) & 0xF
    }
    fn index(self) -> u32 {
        self.0 >> 8
    }
}
const PosF32 = struct { x: f32, y: f32, z: f32 }; // 12 bytes
const PosU16 = struct { x: u16, y: u16, z: u16 }; // 6 bytes: 1 km cell / 65535 ≈ 1.5 cm steps
const PosF16 = struct { x: f16, y: f16, z: f16 }; // 6 bytes, but only ~3 significant digits

/// Fields are laid out from the least significant bit: kind = bits 0..3, layer = 4..7, index = 8..31.
const PackedRef = packed struct(u32) { kind: u4, layer: u4, index: u24 };

comptime {
    std.debug.assert(@sizeOf(PackedRef) == 4);
}
Pos_F32 :: struct {
	x, y, z: f32,
} // 12 bytes
Pos_U16 :: struct {
	x, y, z: u16,
} // 6 bytes: 1 km cell / 65535 ≈ 1.5 cm steps
Pos_F16 :: struct {
	x, y, z: f16,
} // 6 bytes, but only ~3 significant digits

// Least-significant bit first: kind = bits 0..3, layer = 4..7, index = 8..31.
Packed_Ref :: bit_field u32 {
	kind:  u8  | 4,
	layer: u8  | 4,
	index: u32 | 24,
}

#assert(size_of(Packed_Ref) == 4)

Zig's packed struct is not C's packed. It is an integer. The four-field Mixed as a packed struct is a 112-bit integer, and u112 has the size and alignment of a u128 on x86-64, so it comes out at 16 bytes with alignment 16, not the 14 bytes that repr(C, packed) and #packed give. Use packed struct for flags and bit-level encodings with an explicit backing type such as packed struct(u32). For “no padding between byte-sized fields”, sort the fields of a plain struct, or use SoA (Chapter 4).

To read the backing integer of a packed struct (or of an enum), use @backingInt(p), and @fromBackingInt for the reverse. (Chapter 1 has the matching enum renames.)

Bit sets of booleans (Odin's bit_set[Flag; u8], Zig's std.bit_set, a u8 of flags in Rust) are the other common packing. They pay off most when the flags move out of the struct altogether, which is the out-of-band idea again, so they are covered in Chapter 7.

Pin sizes at compile time

Size is a property you design for, so it should be checked like one. A colleague adds a bool to a hot struct and it grows from 16 to 24 bytes without any visible change. A size assert turns that into a compile error. Each language has a one-line form, and the chapter's programs use all three:

/// 8 + 4 + 4 + 1 = 17 bytes of fields, padded to 24 (align 8).
#[derive(Clone, Copy)]
struct Fat {
    anim: usize, // stands in for a pointer: same size and alignment
    hp: u32,
    y: u32,
    alive: bool,
}

/// 4 + 4 + 4 + 1 = 13 bytes of fields, padded to 16 (align 4).
#[derive(Clone, Copy)]
struct Index {
    anim: u32,
    hp: u32,
    y: u32,
    alive: bool,
}

/// 4 + 4 + 2 + 1 = 11 bytes of fields, padded to 12 (align 4).
#[derive(Clone, Copy)]
struct Small {
    anim: u32,
    hp: u32,
    y: u16,
    alive: bool,
}

const _: () = assert!(size_of::<Fat>() == 24);
const _: () = assert!(size_of::<Index>() == 16);
const _: () = assert!(size_of::<Small>() == 12);

Rust evaluates the const _: () = assert!(...) item during compilation. Since 1.80 size_of is in the prelude, so it needs no import. Zig runs the comptime block in the compiler. Odin's #assert is a compile-time directive. Both compilers use this on themselves. rustc's AST has a list of static_assert_size!(Expr, 64)-style guards[14], and Zig's Air.zig asserts @sizeOf(Data) == 8 for its instruction payload[13]. The Rust performance book suggests putting the assert behind #[cfg(target_arch = "x86_64")], “because type sizes can vary on different platforms”[4]. A struct with a pointer is 24 B on x86-64 and 16 B on a 32-bit target.

See a compiler's view of every type. These need tools this orb does not have (nightly Rust, pahole with debug info), so no output is shown here. Run them on your own machine:

# C, Zig or Odin binaries with DWARF debug info: holes and padding per struct (Linux, package "dwarves")

The Linux networking developers used pahole exactly this way: Eric Dumazet's tcp_sock work found and removed holes, and kernel slides show pahole --reorganize on task_struct reporting “saved 80 bytes and 1 cacheline”[20][18]. Rust's -Zprint-type-sizes is nightly-only. On stable, size_of, align_of and offset_of! (stable since 1.77) give you the same numbers one type at a time[4].

Thresholds: 64 bytes and 128 bytes

Shrinking a type does not pay off evenly. Some sizes are cliffs. Nicholas Nethercote's long series on speeding up rustc gives two of them with numbers.

64 bytes: one cache line. In July 2026 he shrank rustc's AST expression node from 72 to 64 bytes, “small enough to fit in a cache line”. Expressions are the most common AST node, and the change “reduced wall-time on a small number of AST-heavy benchmarks, some by more than 10%”, while “cache miss rates on those same benchmarks fell by as much as 29%”[5]. At 72 bytes, most nodes straddle two lines. At 64, each node in a line-aligned array is exactly one line.

128 bytes: inline copy or memcpy. “Rust types that are larger than 128 bytes are copied with memcpy rather than inline code”[4]. Above that size, every move of a value becomes a function call. In the same July 2026 post, a hot vector element was 136 bytes. Nethercote avoided two-thirds of the moves and “shrank the type down to 104 bytes so that memcpy wasn't used for the remaining moves”, and wall time on the two worst crates fell by 40%[5]. We did not check whether rustc or LLVM sets that threshold, so treat it as a property of rustc, not a law of hardware; we did not check Zig's or Odin's either.

The same series is honest about the other side. In 2022 he shrank Attribute from 152 to 32 bytes for a 5.13% drop in peak memory, and explicitly credited the Zig compiler's work[11]. Size wins are real, but how big they are depends on how hot the type is and which threshold you cross.

Measuring padding waste

Do padding bytes cost time, or only memory? The benchmark answers that for one loop. It builds N monsters, for N from 10 thousand to 10 million, in three layouts that hold the same values:

  • 24 B fat: a pointer-sized anim handle, hp: u32, y: u32, alive: bool, which is Kelley's starting struct;
  • 16 B index: the handle as a u32 index (alignment drops to 4);
  • 12 B small: the index, and y narrowed to u16.

The values come from a stateless splitmix64 hash of the index, so all three languages build identical monsters. The pass reads every field and sums the live ones. Each program stops with an error if the layouts' checksums differ; at 10 M monsters all nine runs printed 264,734,445,134. The sum is written without a branch, multiplying by alive, because a quarter of the monsters are dead at random and a branch would measure mispredictions instead of bytes. That effect gets its own chapter. Timing uses the harness from Chapter 2. This benchmark keeps alive inside the struct so that the work stays identical across layouts. Its 24 → 16 → 12 path therefore differs from Kelley's in the middle step, but the sizes are the same.

/// The per-monster work: read every field, sum the live ones.
/// Branch-free on purpose: `alive` is random, and a branch would measure mispredictions (Chapter 7).
trait Score {
    fn score(&self) -> u64;
}

impl Score for Fat {
    fn score(&self) -> u64 {
        (self.anim as u64 + self.hp as u64 + self.y as u64) * self.alive as u64
    }
}

impl Score for Index {
    fn score(&self) -> u64 {
        (self.anim as u64 + self.hp as u64 + self.y as u64) * self.alive as u64
    }
}

impl Score for Small {
    fn score(&self) -> u64 {
        (self.anim as u64 + self.hp as u64 + self.y as u64) * self.alive as u64
    }
}

fn total<M: Score>(ms: &[M]) -> u64 {
    ms.iter().map(M::score).sum()
}
/// The per-monster work: read every field, sum the live ones. One function per element type.
fn totalOf(comptime M: type) fn ([]const M) u64 {
    return struct {
        fn total(ms: []const M) u64 {
            var s: u64 = 0;
            for (ms) |m| {
                // Branch-free on purpose: `alive` is random, and a branch would measure mispredictions (Chapter 7).
                s += (@as(u64, m.anim) + m.hp + m.y) * @intFromBool(m.alive);
            }
            return s;
        }
    }.total;
}
// The per-monster work: read every field, sum the live ones. One instantiation per element type.
// Branch-free on purpose: `alive` is random, and a branch would measure mispredictions (Chapter 7).
total :: proc(ms: []$M) -> u64 {
	s: u64
	for m in ms {
		s += (u64(m.anim) + u64(m.hp) + u64(m.y)) * u64(m.alive)
	}
	return s
}

The three versions differ where the languages do. Rust uses a small trait and one generic total. Zig returns one concrete function per layout from a comptime function (totalOf(M)), because the harness takes a comptime f. Odin's parametric total :: proc(ms: []$M) has to be pinned to a concrete instantiation before it can be passed as a procedure value.

At 10 M monsters the arrays are 240 MB, 160 MB and 120 MB, far beyond any cache on this orb. If the loop is limited by memory bandwidth, how should the 24 B and 12 B times compare? And what about at 10 thousand monsters (240 KB, inside L2)?

At 10 M the time should follow the bytes, so the 24 B layout should take up to twice as long. On this orb it is about 1.75× slower in Rust, about 1.7× in Zig and about 1.7× in Odin. At 10 thousand, everything is in cache, and the gap shrinks to about 1.3× (Rust). What is left there comes from the code the compiler generates for each layout, not from memory.

Worked example: from bytes to milliseconds

Take the Rust numbers at 10 M monsters, the ones charted above. The fat layout took 2.9 ns per monster, so 29 ms per pass over 240 MB. The small layout took 1.6 ns per monster, so 16 ms over 120 MB. Both read their bytes at a similar rate, so the loop is bandwidth-bound and time ≈ bytes ÷ bandwidth. Halving the bytes would ideally halve the time. We got 1.75× instead of 2× because the smaller layout reads its bytes slightly more slowly than the fat one. The 16 B layout falls in between, at 2.1 ns per monster.

Kelley's point, in milliseconds: at this size, on this machine, each padding byte costs about the same as a data byte, about one twenty-fourth of the fat layout's per-monster time per pass. A 60 Hz frame is 16.7 ms. The small layout's pass alone takes about a frame, and the fat layout's pass takes about 1.75× as long, far more than a frame. A game that really walks ten million monsters every frame must shrink them further, or touch fewer.

What happens in cache

The left side of the figure above is just as instructive. When the array fits in L2, all three layouts run several times faster per monster, and the differences between them are not proportional to bytes. In Zig, the 16 B layout is as slow as the 24 B one in cache, and only the 12 B layout is faster. In Rust and Odin, the 16 B and 12 B layouts are close together. These are differences in the code the compiler generates for each layout (how it loads the fields, and whether and how it vectorizes), and they can change with a compiler version. In cache, size buys you capacity: the 12 B array stays in a cache level that the 24 B array has already left, and that is why the fat line in the figure above steps up a size earlier than the others.

Machine: see Chapter 2. The runs were pinned with taskset -c 2; the L3 is shared with other tenants, which blurs where the L3-to-DRAM step happens. Read the shapes and ratios, not the absolute nanoseconds.

When not to shrink

  • Layouts that are part of a contract. FFI structs, file formats, network packets and memory-mapped data need a fixed order (repr(C), extern struct, Odin's default). Do not “optimize” them by reordering.
  • Deliberate grouping. Fields that different threads write should be on separate cache lines (Chapter 8). Hot fields are sometimes kept together on the first line on purpose. A reordering compiler does not know about either, so annotate with repr(C) or an alignment and assert the offsets.
  • Packed and misaligned data costs extra instructions on every access, may cross cache lines, and breaks atomics.
  • Narrow types have edges. A u16 hit-point count silently wraps in release builds unless you check. Quantized positions lose precision, and repeated physics updates in 16-bit fixed point drift. Keep full precision for the arithmetic.
  • Cold types. Shrinking a struct that is touched once per frame, or of which there are twenty, buys nothing: Nethercote abandoned a 16-byte token type because the speedup was negligible[6] (Chapter 12 tells the story). Shrink the types that a profiler, a heap profiler or a count of elements says are hot.
  • Beyond sorting, the remaining padding sits between differently sized fields of the same element. The structural fix for that is to stop storing them together at all: struct-of-arrays, the subject of the next chapter.

Every element pays for its padding in cache lines and bandwidth. So know your sizes (and pin them with a compile-time assert), let the compiler sort fields or sort them yourself in Odin and repr(C), and then shrink the fields themselves: one-byte enums, niches, indices, narrow and quantized types, and bits.

Exercises

What are the sizes of struct { a: u8, b: u32, c: u16, d: u8 } in C order and with reordering? Check your answer in the figure above.

C order: a at 0, 3 bytes of padding, b at 4, c at 8, d at 10, then 1 byte of tail padding, so 12 B. Sorted (u32, u16, u8, u8): 8 B with no padding. rustc agrees: 12 for repr(C) and 8 for the default layout.

A tree of 10 million nodes stores a parent link per node. How much memory does Option<NonZeroU32> save compared with Option<u32>, and what is the equivalent in Zig and Odin?

4 bytes per node, so 40 MB (80 MB versus 40 MB for the field alone, and possibly more if the extra 4 bytes add padding to the node). In Zig, use enum(u32) { none = std.math.maxInt(u32), _ } rather than ?u32. In Odin, use a distinct u32 with a reserved constant rather than Maybe(u32). Both stay at 4 bytes, but you check for the sentinel by hand.

Why is Option<Option<NonZeroU32>> 8 bytes, while Option<Option<bool>> is 1 byte?

NonZeroU32 has exactly one invalid bit pattern (0), and the inner Option uses it, so the outer one needs a tag. A bool leaves 254 byte values unused, enough for both levels of None. rustc 1.100 prints 8 and 1.

In Zig, what are @sizeOf and @alignOf of packed struct { a: u8, b: u16, c: u1 }? And if c becomes a u48?

A packed struct is its backing integer. The first is a u25, which x86-64 stores like a u32: 4 bytes, aligned to 4. The second is a u72, which LLVM stores like a u128: 16 bytes, aligned to 16, for 9 bytes of fields. Zig 0.17.1 prints 4/4 and 16/16.

In Odin, what are the size and alignment of struct { a: u8, kind: Kind, b: u8 } when Kind :: enum u16 { A, B }? And with the default Kind :: enum { A, B }, in this order and with kind first?

With enum u16: a at 0, 1 byte of padding, kind at 2, b at 4, then 1 byte of tail padding: 6 B, alignment 2. The default enum is int-backed (8 bytes, alignment 8): a at 0, 7 bytes of padding, kind at 8, b at 16, tail padding to 24 B. Putting kind first gives 8 + 1 + 1 = 10, rounded up to 16 B. Odin prints 6/2, 24/8 and 16.

You quantize positions in a 1 km cell to u16. What is the worst-case error, and how many bits would you need for 1 mm?

The step is 1000 m / 65535 ≈ 15.3 mm, and rounding to the nearest step gives at most half of that, ≈ 7.6 mm. The program's 4.7 mm is within that bound. For 1 mm worst-case error you need a step of at most 2 mm, so 1000 / 0.002 = 500,000 steps, which needs 19 bits. A 64-bit word could pack three 19-bit axes (57 bits) with a packed struct(u64) or bit_field u64.

Run code/ch03-size-alignment-padding with N = 300000 and N = 3000000. At which N does the 24 B layout leave L2 (1.25 MiB on this orb), and at which does it leave L3? Does the chart show it there?

The 24 B layout exceeds 1.25 MiB at about 55 thousand monsters and 54 MiB at about 2.4 million. The 12 B layout reaches the same points at twice those counts. In the run charted above, the big step for the fat layout is at 1 M monsters (24 MB), before the nominal L3 size. The L3 is shared with other tenants and the prefetcher hides the L2 step for a sequential scan, so the measured steps are blurrier and earlier than the nominal sizes. That is why this book plots measurements instead of drawing cache sizes.
