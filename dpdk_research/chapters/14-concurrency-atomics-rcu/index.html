Chapter 14

Concurrency: Atomics, Memory Ordering, Locks and RCU

Before we put a shared hash table or routing table between cores (ch17, ch18), we need the rules for sharing memory at all. After this chapter you can pick the right DPDK 26.11 atomic and memory order, tell a CPU barrier from a device barrier, choose a lock (or no lock), update shared data with RCU so that readers never wait, and lay out per-lcore data so that cores do not fight over cache lines. Every claim is checked by a program you run on this machine.

1Three things that go wrong when cores share memory

Up to now each lcore mostly had its own queue, its own mempool cache and its own counters. As soon as two lcores touch the same variable, three separate problems appear. They are easy to mix up, so we name them first.

  1. Atomicity: is the operation indivisible? counter++ is a load, an add and a store. If two cores do it at the same time, both can load 41 and both store 42: one update is lost. A 64-byte config copied with memcpy is many stores; a reader in the middle sees half old, half new (a torn read).
  2. Visibility: will the other core ever see my store, and when? The compiler may keep a variable in a register and never reload it. The CPU keeps recent stores in a private store buffer for a while.
  3. Ordering: if I write data and then flag, does another core that sees the new flag also see the new data? Not necessarily: both the compiler and the CPU may reorder memory accesses, as long as the reordering is invisible to the current thread.

The C11 standard calls two accesses to the same location from different threads, at least one a write and at least one not atomic, a data race, and a program with a data race has undefined behaviour. The fix is to make every shared access either atomic (and say what ordering it needs), or protected by a lock, or not shared at all. DPDK gives you tools for all three; the third (no sharing) is usually the fastest, and we end the chapter with it.

volatile is not the answer

volatile forces the compiler to emit every load and store, which fixes the "kept in a register" part of visibility. It does not make counter++ atomic (it is still load, add, store), it does not stop the CPU from reordering, and it does not order the volatile access against ordinary ones. Some old DPDK code used volatile fields plus rte_smp_*mb() barriers. In 26.11 the barriers are gone, and the right replacement is an atomic with an explicit memory order.

2The 26.11 atomics API

DPDK 26.11 has one atomics API: thin macros in lib/eal/include/rte_stdatomic.h that follow C11 <stdatomic.h> names. The old rte_atomic16/32/64_t types and functions, deprecated since 21.05, were removed in this release, together with the rte_smp_mb/rmb/wmb barriers (release notes, doc/guides/rel_notes/release_26_11.rst).

The memory order says what the operation guarantees beyond atomicity:

  • rte_memory_order_relaxed: atomic, no ordering. Right for statistics counters and for a flag whose only meaning is itself.
  • rte_memory_order_release (stores): every load and store before it in program order becomes visible no later than this store. The "publish" side.
  • rte_memory_order_acquire (loads): no load or store after it may happen before it. The "subscribe" side. An acquire load that reads the value of a release store synchronizes with it: everything the writer did before the release is visible to the reader after the acquire.
  • rte_memory_order_acq_rel: both, for read-modify-writes (a ring head CAS, a refcount decrement).
  • rte_memory_order_seq_cst: acq_rel plus one global order of all seq_cst operations. The only one that forbids store-buffering (section 3). The most expensive.

You have already used this pairing: an rte_ring producer writes the objects, then stores prod.tail with release; the consumer loads prod.tail with acquire before reading the objects (lib/ring/rte_ring_c11_pvt.h, ch5). A spinlock is acquire on lock and release on unlock.

3Memory ordering: x86-TSO, Arm and the compiler

Why would a CPU reorder at all? A store has to wait until the core owns the cache line (it may need to fetch it from another core, which takes hundreds of cycles). Rather than stall, the core puts the store in a store buffer and keeps executing. Later loads are served from the cache straight away, even though older stores are still waiting. To the current thread this is invisible: if it loads an address it stored to, the load is served from its own store buffer (store-to-load forwarding). To other cores it is visible: they see the stores late.

Architectures differ in what they allow:

  • x86-64 is TSO (total store order, Intel SDM vol. 3, 8.2.2, quoted in lib/eal/x86/include/rte_atomic.h): loads are not reordered with loads, stores are not reordered with stores, stores are not reordered with older loads. Only a store followed by a load to a different address can appear reordered. Consequence: on x86 an acquire load and a release store are ordinary mov instructions; they only stop the compiler.
  • Arm (AArch64) is weakly ordered: any pair of accesses to different addresses may be observed out of order unless something orders them. Release stores compile to stlr, acquire loads to ldar, fences to dmb.
  • The compiler may reorder, merge or delete accesses to non-atomic variables on any architecture, as long as one thread cannot tell. Relaxed atomics may also be reordered with each other by the C11 rules.

Litmus tests

A litmus test is a tiny two-thread program and a question about its outcome. Two classics:

MP: message passing
/* T0 */            /* T1 */
data = 1;           r1 = flag;
flag = 1;           r2 = data;
/* Can T1 see r1 == 1 && r2 == 0? */

"I saw the flag but not the data." This is the ring, the config publish, every hand-off.

SB: store buffering (Dekker)
/* T0 */            /* T1 */
x = 1;              y = 1;
r1 = y;             r2 = x;
/* Can we get r1 == 0 && r2 == 0? */

"Both loads beat both stores." This breaks Dekker/Peterson mutual exclusion and any "set my flag, then check yours" protocol.

Choose a test, an ordering and an architecture, then step through the worst-case interleaving. On x86 the verdict comes with the number litmus.c measured on this VM; on Arm it is what the architecture model allows, clearly marked as not measured here.

MP: 0 forbidden outcomes in a million, even with relaxed atomics, because x86 never reorders store-store or load-load. That is not proof that relaxed is correct: the same code is allowed to fail on Arm and the compiler is allowed to reorder it. SB: the "impossible" (0, 0) shows up about 15% of the time with relaxed, and just as often with release/acquire. Only the seq_cst fence brings it to zero. Barrier costs: release/acquire fences and rte_io_wmb() cost nothing on x86 (they emit no instruction); a seq_cst fence costs about 18 cycles, rte_mb() (mfence) about 32.

Why DPDK's seq_cst fence is not mfence

rte_atomic_thread_fence(rte_memory_order_seq_cst) on x86 emits lock addl $0,-128(%rsp): a locked add to a dummy stack slot. Any locked instruction drains the store buffer, and this one is cheaper than mfence (18 vs 32 cycles above). mfence also orders non-temporal stores and device memory, which CPU-to-CPU code does not need (lib/eal/x86/include/rte_atomic.h).

Read the x86 writer_plain: the store of the constant 1 (movl $0x1,..., the flag) comes before the division finishes and before msg is stored. A reader on another core can see plain_ready == 1 and an old msg, on x86, with no CPU reordering at all. writer_release on x86 is the same instructions in the right order: release cost nothing but stopped the compiler. On AArch64 the release store becomes stlr. reader_plain on x86 loads the flag once and then spins forever on jmp ce (a jump to itself); clang for Arm deleted the loop entirely. Both are legal, because a plain variable that no one in this thread writes "cannot change".

The full listing in expected_output.txt also shows writer_barrier (rte_compiler_barrier(): correct order, no instruction; enough for MP on x86 but not on Arm, where the two str can still become visible out of order) and writer_relaxed (here gcc happened to keep the order; the C11 model does not promise it).

"It works on x86" is not a proof

Relaxed atomics for a hand-off pass every test on x86, and then fail on an Arm server, sometimes once a day. If one thread publishes data for another, use a release store and an acquire load (or a lock) even though x86 generates the same code. It documents the intent and it is correct everywhere.

4CPU-to-CPU vs CPU-to-device ordering

Everything so far ordered memory accesses between CPUs, through coherent caches. A NIC is a different observer. A driver writes descriptors in ordinary memory, which the NIC reads by DMA, then writes a doorbell: a register in the device's PCI BAR, mapped as uncached I/O memory. If the doorbell write overtakes the descriptor writes, the NIC fetches stale descriptors.

Waiting politely: rte_pause and rte_wait_until_equal

Every spin loop in this chapter calls rte_pause() (x86 pause: tells the core it is spinning, saves power, frees resources for the hyper-thread sibling and avoids a pipeline flush when the value changes). rte_wait_until_equal_16/32/64(addr, expected, memorder) in lib/eal/include/generic/rte_pause.h packages the loop "spin with pause until *addr == expected" with relaxed or acquire ordering; on Arm with RTE_ARM_USE_WFE it sleeps in wfe until the line changes. The generic ticketlock is built from it: rte_wait_until_equal_16(&tl->s.current, me, rte_memory_order_acquire).

5The lock zoo

All DPDK locks are busy-waiting locks: a waiter spins on its lcore instead of sleeping in the kernel. That is right for a pinned lcore that has nothing else to do, and wrong for a thread that shares its CPU (a spinning waiter can burn the time slice the lock holder needs). They live in lib/eal/include/.

Two rows are often confused. seqcount vs seqlock: the read side is identical (rte_seqlock_read_begin() just calls rte_seqcount_read_begin()); the difference is only that the seqlock's writers take a spinlock. With one control thread updating a config, a seqcount is enough. rwlock vs pflock: under a steady stream of readers the rwlock lets a waiting writer in first (writer preference), and readers queue behind; the pflock alternates phases, so a waiting writer gets in after the current readers, and readers that arrive meanwhile get in after that one writer.

Uncontended (1 thread), every lock costs 20 to 60 cycles: one or two atomic instructions. The ticketlock is cheapest because unlock is a plain release store. With 2 or 3 threads the cost jumps 30 to 100 times: the cache line holding the lock (and the counter) must move between cores on every hand-off. The spinlock is not fair (37/37/26%), the ticket, MCS and phase-fair locks give exactly a third each, and fairness costs: strict FIFO means the lock always moves to another core, never staying with the core that just released it.

Three results deserve a comment:

  • MCS is the slowest here. MCS wins when many waiters would all hammer one line; with three vCPUs that advantage is small, and each acquisition does more atomic operations plus a hand-off write to a line owned by another core. On a 64-core socket the picture reverses (exercise 3).
  • Read locks do not scale for tiny sections. rte_rwlock_read_lock with 3 readers costs 711 cycles, not 35: every reader writes the lock word (reader count +4), so the line still ping-pongs. A read lock helps only when the read section is long. For short reads of shared data, use RCU (section 9) or a seqlock (section 6): readers write nothing shared.
  • pthread_mutex looks fast with 3 threads (221 cycles). It sleeps waiters in the kernel (futex) and the thread that releases the lock usually takes it again many times before a sleeper wakes up, so the line stays put. Throughput is good; the latency for the sleeper is a system call and a wake-up (microseconds), which is why it is not used on a data-plane lcore.
Lock-holder preemption

Every busy-waiting lock assumes the holder is running. If its thread is descheduled (an overloaded VM, two lcores mapped to one CPU with --lcores, a control thread spinning on a data-plane core), every waiter spins for the whole time slice. Fair locks are worse: the next ticket holder may itself be descheduled, and the lock sits idle. Pin lcores, do not oversubscribe, and never take a data-plane lock from a thread that can sleep.

6Seqlocks: readers retry instead of waiting

The data plane reads a 64-byte config millions of times per second; the control plane changes it a few times per second. A lock makes every reader pay. A seqlock makes the writer pay a little and readers pay only when they actually overlapped a write.

code/seqlock_cfg.cC
                case SEQLOCK:
                        do {
                                sn = rte_seqlock_read_begin(&lock.sl);
                                memcpy(&copy, &config, sizeof(copy));
                                if (!rte_seqlock_read_retry(&lock.sl, sn))
                                        break;
                        case SEQLOCK:
                                rte_seqlock_write_lock(&lock.sl);       /* sn becomes odd */
                                write_fields(++v);
                                rte_seqlock_write_unlock(&lock.sl);     /* sn even again */
                                break;

The first excerpt is the reader, the second the writer (between them, write_fields() stores version into all eight fields with small pauses, so a write takes about a microsecond). The protected data may be read with plain loads, as rte_seqlock.h's own example does; the copy may be garbage, but it is never used unless the sequence number proves it is not.

Pointers inside seqlocked data

A seqlock copy is safe only if the data is self-contained. If the config held a pointer and the writer freed what it pointed to, a reader could dereference it between read_begin and read_retry: a use-after-free that the retry detects too late. For pointers to dynamically allocated objects, use RCU.

The fix is to compare and replace two words at once: the pointer and a counter that every successful push or pop increments. x86-64 has cmpxchg16b; DPDK exposes it as rte_atomic128_cmp_exchange() on a 16-byte-aligned rte_int128_t, and lib/stack/rte_stack_lf_c11.h uses it for the stack head {top, cnt}, with release on push (the new element's next must be visible before the head) and relaxed or acquire on pop. cas128.c replays the ABA history on one lcore with both kinds of CAS:

code/cas128.cC
        /* ---- 2. {pointer, counter} CAS ---- */
        A.next = &B;
        struct head h = { &A, 0 };
        struct head old = h;                    /* T1 reads {A, 0} */
        struct head nh  = { old.top->next, old.cnt + 1 };       /* wants {B, 1} */

The 64-bit CAS accepts the recycled A and installs B, which is no longer on the stack: corruption. The 128-bit CAS sees counter 3 instead of 0, fails, and gives T1 the current head to retry with. A 64-bit counter cannot wrap around during the nanoseconds a thread spends between its read and its CAS.

9RCU: readers that never wait

Locks, seqlocks and CAS loops all make readers do something shared. The data plane mostly reads shared tables (routes, ACL rules, configs), and they change rarely. RCU (read-copy-update) makes reading free: readers follow a pointer and use what they find, with no lock and no shared write. The writer never modifies an object readers can see. It builds a new copy, swaps the pointer atomically, and frees the old copy only when no reader can still hold it.

DPDK's lib/rcu implements QSBR (quiescent-state-based reclamation). A quiescent state is a point where a reader holds no references to shared data. For a poll-mode lcore there is a natural one: the top of its while (1) loop. Each reader announces it there; the writer waits until every registered, online reader has announced one after the swap. That wait is the grace period.

  • rte_rcu_qsbr_get_memsize(max_threads), rte_rcu_qsbr_init(v, max_threads): create the QSBR variable (one cache-aligned counter per thread id plus a bitmap of registered ids).
  • Reader, once: rte_rcu_qsbr_thread_register(v, id), then rte_rcu_qsbr_thread_online(v, id) before the first dereference.
  • Reader, every loop: rte_rcu_qsbr_quiescent(v, id): an acquire load of the global token and, if it changed, a release store of it into my counter. Usually just one load.
  • Reader, before blocking (sleep, syscall, long wait): rte_rcu_qsbr_thread_offline(v, id); the writer then ignores it. _online again before touching shared data. At exit: _offline and rte_rcu_qsbr_thread_unregister().
  • Writer: t = rte_rcu_qsbr_start(v) (bump the token, release) and rte_rcu_qsbr_check(v, t, wait) (has every online reader reached t?), or both in one call: rte_rcu_qsbr_synchronize(v, my_id). A writer that is not itself a reader passes RTE_QSBR_THRID_INVALID.

The two classic RCU bugs

A reader that blocks (sleeps, waits on a socket, spins on something slow) while online stretches every grace period to its blocking time, and the writer, or the memory waiting to be freed, piles up. A reader that forgets rte_rcu_qsbr_thread_online() (or goes offline while still holding a pointer) is not waited for, and its pointer can be freed under it.

The defer queue: do not wait, free later

rte_rcu_qsbr_synchronize() blocks the writer for a grace period per update. With the defer queue the writer enqueues the old object together with a new token and returns; the queue frees entries whose grace period is over, automatically inside later enqueues or explicitly with rte_rcu_qsbr_dq_reclaim().

10Per-lcore data: the fastest sharing is none

Statistics are the most common shared data, and they do not need to be shared at all: give each lcore its own counter, let only that lcore write it, and let a stats reader (telemetry, ch13) sum them occasionally. There are three ways to give each lcore its own copy.

  • An array indexed by rte_lcore_id(). Simple and readable by anyone. Each element must be cache-aligned, or neighbouring lcores share a line (false sharing, below). RTE_CACHE_GUARD (lib/eal/include/rte_common.h) adds RTE_CACHE_GUARD_LINES (1 here) empty lines after it, against the adjacent-line prefetcher. Cost: RTE_MAX_LCORE (128 in this build) × 128 B even if you use four lcores.
  • Thread-local storage: RTE_DEFINE_PER_LCORE(type, name) and RTE_PER_LCORE(name) (lib/eal/include/rte_per_lcore.h) are __thread variables. Cheap, but other threads cannot reach them, so a stats reader cannot sum them.
  • Lcore variables (24.11+, lib/eal/include/rte_lcore_var.h, experimental: build with -DALLOW_EXPERIMENTAL_API). static RTE_LCORE_VAR_HANDLE(struct foo, h); declares a typed handle; RTE_LCORE_VAR_ALLOC(h) allocates one zeroed instance per lcore id; RTE_LCORE_VAR(h) is a pointer to the calling lcore's instance; RTE_LCORE_VAR_LCORE(id, h) to any lcore's; RTE_LCORE_VAR_FOREACH(id, ptr, h) iterates over all. There is no RTE_LCORE_VAR_VALUE. Instances are never freed.

False sharing and the MESI ping-pong

Caches keep copies coherent per 64-byte cache line, using a protocol of the MESI family: a line in a core's cache is Modified (only copy, dirty), Exclusive (only copy, clean), Shared (read-only, others may have it) or Invalid. To write, a core needs the line in M or E, so it invalidates every other copy. If two cores write two different counters that happen to sit in the same line, the line moves back and forth on every write, although no data is shared: false sharing.

{
        uint64_t sum = 0;
        unsigned int i;

        switch (l) {

One shared atomic counter costs 165 cycles per increment with three writers: every increment drags the line across. A locked fetch_add on a private counter in a packed array is even worse (236 cycles): false sharing, with no shared data at all. Padding or an lcore variable brings the same locked add to 12.8 cycles, the uncontended cost of a locked instruction. The plain load+store increment costs about 0.7 cycles in every layout on this CPU, even packed, even with a reader polling: the store buffer (and store-to-load forwarding) absorbs repeated stores to one address, so the line does not have to move on every increment. Do not rely on that: it depends on the microarchitecture and on the loop doing nothing else; a locked operation, or real work between increments, exposes the false sharing again. The rule stays: one writer per counter, no lock prefix, counters on their own lines (or in lcore variables), and correctness is the same in all ten rows (total = 15,000,000).

Common pitfalls

  • error: unknown type name 'rte_atomic32_t' or implicit declaration of rte_smp_wmb: code written for DPDK <= 25.x. Port with the migration table (section 2); decide for each barrier whether the reader is a CPU or a device.
  • Hand-off with relaxed atomics "works": on x86 the hardware hides it (MP: 0 in a million). It fails on Arm or after the compiler moves a store. Publish with release, consume with acquire.
  • Release/acquire to implement "set my flag, check yours": SB still happens (176,609 times in a million above). Needs seq_cst fences or seq_cst operations.
  • A plain flag in a spin loop: the compiler hoists the load and the loop never ends (reader_plain: jmp to itself). Use an atomic load (acquire if it guards data).
  • rte_smp_wmb() before a doorbell replaced by rte_atomic_thread_fence(release): correct on x86 by accident, wrong on Arm. A device is the reader: rte_io_wmb() or rte_write32().
  • seq_cst everywhere "to be safe": every seq_cst store is an xchg (18 cycles here vs 0.4). Use it only where SB-style ordering is needed.
  • A spinlock taken by a thread that can be preempted (or two lcores on one CPU): waiters spin for whole time slices. Keep locks off non-pinned threads; prefer RCU or rings for control/data-plane hand-offs.
  • rwlock for tiny read sections: readers still write the lock word; 711 cycles with 3 readers here. Use RCU or a seqlock.
  • seqcount with two writers: the sequence number gets corrupted and readers accept torn data. Two writers need rte_seqlock_t.
  • Pointers inside seqlocked data: retry detects the race too late for a freed pointer. Use RCU for pointers.
  • RCU reader blocks while online: grace periods grow to the blocking time (50 µs reader: 49.45 µs grace periods). Call rte_rcu_qsbr_thread_offline() around blocking calls.
  • RCU reader never went online, or reports a quiescent state while still holding a pointer: use-after-free.
  • Freeing right after unlinking from a lock-free table: the "broken" mode. Free after a grace period (synchronize or defer queue).
  • Per-lcore counters in a packed array, or per-lcore structs without __rte_cache_aligned: false sharing (236 vs 12.8 cycles for a locked add). Align and guard, or use lcore variables (and do not pad those).
  • Atomic RMW on a counter only one lcore writes: 12.8 cycles instead of 0.7. A relaxed load + store is enough.
  • RTE_LCORE_VAR from an unregistered non-EAL thread: rte_lcore_id() is LCORE_ID_ANY and the pointer is invalid. Register the thread or use RTE_LCORE_VAR_LCORE().
  • Compiling rte_lcore_var.h users without -DALLOW_EXPERIMENTAL_API: errors about the experimental rte_lcore_var_alloc.

Exercises

Exercise 1 easy Port old atomics and a doorbell to 26.11

This pre-26.11 code no longer compiles. Port it, deciding for each barrier whether the reader is another CPU or a device:

static rte_atomic32_t pkts;
rte_atomic32_inc(&pkts);
ring->slot[i] = m;  rte_smp_wmb();  ring->tail = i + 1;        /* to another lcore */
txd->addr = iova;  txd->len = len;  rte_smp_wmb();  *db = tail; /* to the NIC */
Hint

A counter: RTE_ATOMIC(uint32_t) and a relaxed fetch_add. The ring tail publishes data to a CPU: make the tail store a release store (and the consumer's load acquire). The doorbell publishes to a device: rte_write32(tail, db).

Solution

code/solutions/port_26_11.c runs a producer/consumer over the ported hand-off (1,000,000 items, checked sum) and rings a fake doorbell. Its output is at the end of expected_output.txt.

Exercise 2 medium Defer queue vs synchronize

Make rcu_swap use the RCU defer queue instead of rte_rcu_qsbr_synchronize(), and compare the writer's per-update latency (median, p99, max). How big must the pool be, and why?

Hint

Freed configs now wait in the queue, so the pool needs room for them: size it and the dq at the same number. The free callback gets a pointer to the bytes you enqueued (here a struct cfg *). If the pool runs dry, call rte_rcu_qsbr_dq_reclaim().

Solution

code/solutions/rcu_dq.c. Measured here: synchronize median 0.69 µs, p99 1.23 µs; defer queue median 0.43 µs, p99 8.74 µs. The median drops because the writer no longer waits; the p99 rises because every 32nd enqueue does a batch of reclamation. With slow readers the difference is much larger (try adding the 50 µs reader from rcu_swap's slow mode).

Exercise 3 medium Why is MCS slower here?

In locks_bench, the MCS lock is slower than the spinlock with 2 and 3 threads. Explain why, and why MCS still scales better on a machine with 64 cores contending.

Hint

Count atomic operations and remote cache-line transfers per hand-off for each lock, as a function of the number of waiters n. Then look at what happens to the spinlock's line when n waiters all re-read it after every release.

Exercise 4 stretch Break a non-thread-safe API

Pick a DPDK API that is documented as not thread-safe (for example an SP/SC rte_ring used from two producers, or rte_eth_tx_burst on one net_null queue from two lcores) and write a test that shows the damage (lost or duplicated objects, wrong counters). Then fix it with the cheapest correct tool from this chapter.

Summary
  • Shared memory has three separate problems: atomicity, visibility and ordering. volatile solves none of them completely.
  • 26.11 has only C11-style atomics: RTE_ATOMIC(T) and rte_atomic_*_explicit(..., rte_memory_order_*). rte_atomicNN_* and rte_smp_*mb are gone.
  • x86-TSO only reorders a store with a later load (SB: about 15% here; MP: 0). Arm reorders much more (model only here). The compiler reorders plain accesses anywhere (objdump shows the flag stored first).
  • Publish with release, consume with acquire. Use seq_cst fences only for store-then-load protocols. Order CPU writes against a device with rte_io_wmb() / rte_write32().
  • Locks cost 20 to 60 cycles alone and thousands under contention; fairness (ticket, MCS, pflock) has a price. Seqlocks let readers retry instead of block; seqcount is the single-writer variant. clang -Wthread-safety finds lock bugs at compile time.
  • The ABA problem is fixed with a 128-bit CAS of {pointer, counter} (rte_atomic128_cmp_exchange).
  • RCU QSBR makes readers free: swap a pointer, wait for a grace period (0.66 µs here, but as long as the slowest online reader's loop), then free; or hand the old object to a defer queue.
  • The cheapest sharing is none: per-lcore counters on their own cache lines, preferably in lcore variables, written by one lcore and summed by a reader.
