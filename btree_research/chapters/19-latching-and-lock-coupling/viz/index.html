Two threads use one B+tree. What may the second thread do while the first is in the middle of an operation? That depends on what the first one has locked. This page runs the same two operations under four protocols: one mutex for the whole tree, one reader-writer lock for the whole tree, a latch per node with latch coupling, and optimistic descent with version counters. Text and code: chapter README.

1. One operation frozen, the other one runs

These are the experiments of section 3 and 4 of zig build run / cargo run. Thread T1 starts and is stopped in the middle, still holding its locks; then thread T2 runs. A badge on a node names the thread and the mode: S shared (several readers), X exclusive (one writer); a dashed badge ending in ? is a thread waiting for that latch. Change the protocol and watch the same experiment end differently. Press Space to play, → to step, or tick Predict to be asked first.

2. Your turn: you are the scheduler

Pick an operation for each thread and press Start. Each press of a Step button lets that thread take exactly one step, so you choose the interleaving. A thread that needs a latch held by the other one cannot step until it is released. Things to try with latch coupling: put 26 against get 17 (stop the writer after it has latched #6); two puts into different leaves; then the same under the reader-writer lock. With the optimistic protocol, let a reader note a version, run a writer through the same leaf, and watch the reader start again.

The model grants a shared latch whenever no writer holds the node. Real reader-writer locks often make new readers queue behind a waiting writer so that writers are not starved; the order of who gets in is then different, the set of latches each protocol needs is the same.

3. Does the picture match the code?

The JavaScript model behind this page is a port of the chapter's Zig and Rust code. It rebuilds the canonical tree under each protocol, repeats every frozen-operation experiment, the replaced-root experiment and the full-node-table experiment, and compares the text with expected_output.txt (sections 1, 3, 4 and 5). The optimistic protocol is not in the programs and so has no such check.
