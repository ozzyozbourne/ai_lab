Chapter 09

Testing Without Hardware: Buses, devargs, Virtual PMDs and testpmd

You do not need a DPDK-capable NIC to build, test and debug a DPDK application. After this chapter you can name, create and find devices with devargs, pick the right software PMD for a test, push traffic in from the Linux kernel, and drive dpdk-testpmd as both a lab bench and a debugger.

1Why you can test DPDK without a NIC

In ch8 you wrote a forwarding loop against the ethdev API: rte_eth_rx_burst() in, rte_eth_tx_burst() out. That loop never asks what is behind the port. A poll mode driver (PMD) sits behind every port, and DPDK ships PMDs whose "hardware" is just software: a function that invents packets, an rte_ring, a pcap file, a Linux tap interface, a kernel socket. Your application cannot tell the difference, so you can develop, unit-test, reproduce bugs and run CI on any Linux box, including this 4-vCPU VM whose only NIC (eth0) must never be touched.

The price is realism. A software PMD has its own costs (system calls, copies, a kernel in the path) and its own limits (no hardware offloads, no real RSS, no descriptor rings). Knowing those costs is what separates a useful test from a misleading benchmark, so this chapter measures them.

2The device model: buses, devices, drivers and classes

Before a port exists, DPDK has to find something to drive. The EAL splits that job into four kinds of objects, all declared in lib/eal/include/rte_bus.h, rte_dev.h and rte_class.h:

  • A bus (struct rte_bus) knows how to scan for devices and probe them. The PCI bus reads /sys/bus/pci/devices; the vdev bus has nothing to scan and creates a device only for each --vdev you give it.
  • A device (struct rte_device) is one thing found on a bus: a PCI function 0000:02:00.0 or a virtual device net_null0. It has a name, a NUMA node, and the devargs it was created with.
  • A driver (struct rte_driver) registers itself on one bus at program start (a constructor, see RTE_PMD_REGISTER_VDEV below). When the bus finds a device the driver accepts, it calls the driver's probe().
  • A class (struct rte_class) is the kind of object a driver creates: eth for ethdev ports. Probe creates the class object (a port id, a cryptodev id) that your application uses. In 26.11 only the eth class registers an rte_class; the class layer is what lets you filter ports by MAC address.

The bus list matters on real hardware (ch23 has the full table: PCI, auxiliary for mlx5 sub-functions, vmbus for Hyper-V, platform devices matched from the device tree in 26.11, cdx, uacce, fslmc/dpaa for NXP). On this VM we pass --no-pci, so the PCI bus is registered but does not scan, and every device comes from the vdev bus.

3devargs: how you name and configure a device

A devargs string identifies a device and carries arguments for it. You meet devargs in three EAL options and in the hotplug API (doc/guides/prog_guide/devargs.rst):

There are two syntaxes. The simplified syntax, which you will use 95% of the time, is [bus:]device_name[,key=value,...]: an optional bus prefix, the device name, then driver arguments. The generic (multi-layer) syntax names each layer explicitly: bus=<bus>,<bus args>/class=<class>,<class args>/driver=<drv>,<driver args>. It exists to match devices (for example "every ice port, pass it representor=[0-3]") rather than to name one.

rte_devargs_parse(struct rte_devargs *da, const char *dev) (in rte_devargs.h) does this split for you. It fills da->bus (the rte_bus that recognised the name), da->name, da->args (an alias of drv_str), and for the generic syntax bus_str / cls_str. It allocates da->data, so call rte_devargs_reset(&da) afterwards. If no bus prefix is given, each bus is asked in turn whether it recognises the name; when none does, it returns -EFAULT, which rte_strerror() prints as "Bad address".

/* Part C: rte_devargs_parse() splits a device string into its layers. */
static void
demo_devargs_parse(void)
{
	static const char *const strs[] = {
		"net_null0,size=128",
		"vdev:net_ring0",
		"net_pcap0,rx_pcap=in.pcap,tx_pcap=out.pcap",
		"bus=vdev,name=net_null0/class=eth/driver=net_null,size=64",
		"nosuchbus:foo0",
	};
	unsigned int i;

	printf("\nPart C: rte_devargs_parse()\n");
	for (i = 0; i < RTE_DIM(strs); i++) {
		struct rte_devargs da;
		int ret;

		memset(&da, 0, sizeof(da));
		ret = rte_devargs_parse(&da, strs[i]);
		printf("  \"%s\"\n", strs[i]);
		if (ret < 0) {
			printf("    -> error %d (%s)\n", ret, rte_strerror(-ret));
			continue;
		}
		printf("    -> bus=%s name=\"%s\" args=\"%s\"\n",
		       da.bus ? rte_bus_name(da.bus) : "(none)", da.name,
		       da.args ? da.args : "");
		if (da.bus_str || da.cls_str)
			printf("       bus_str=\"%s\" cls_str=\"%s\"\n",
			       da.bus_str ? da.bus_str : "", da.cls_str ? da.cls_str : "");
		rte_devargs_reset(&da);   /* frees da.data / layer strings */
	}
}

4Finding devices: the device and ethdev iterators

Once devices exist you often want "every device on the vdev bus" or "the port whose MAC is X". Two iterators take a devargs string as a filter:

  • RTE_DEV_FOREACH(dev, filter, &it) (rte_dev.h) yields struct rte_device * of any class. It is built on rte_dev_iterator_init() / rte_dev_iterator_next() and needs at least a bus= or a class= layer. Use the accessors rte_dev_name(), rte_dev_bus() + rte_bus_name(), rte_dev_driver() + rte_driver_name(), rte_dev_numa_node(), rte_dev_devargs(), rte_dev_is_probed(): the structs themselves are opaque to applications.
  • RTE_ETH_FOREACH_MATCHING_DEV(port, filter, &it) (rte_ethdev.h) yields ethdev port ids. It is built on rte_eth_iterator_init() / rte_eth_iterator_next(). If you break out of the loop early, call rte_eth_iterator_cleanup(&it); finishing the loop cleans up for you.
code/devargs_iter.cC
static void
list_devices(const char *filter)
{
	struct rte_dev_iterator it;
	struct rte_device *dev;
	unsigned int n = 0;
	/* rte_dev_iterator_init() splits a multi-layer string ("bus=../class=..")
	 * IN PLACE (it writes '\0' over each '/') and the iterator keeps
	 * pointers into it. So pass a writable buffer that outlives the loop:
	 * a string literal with a '/' would crash with SIGSEGV. */
	char buf[128];

	snprintf(buf, sizeof(buf), "%s", filter);
	printf("\nRTE_DEV_FOREACH(dev, \"%s\")\n", filter);
	RTE_DEV_FOREACH(dev, buf, &it) {
		const struct rte_devargs *da = rte_dev_devargs(dev);
		const struct rte_driver *drv = rte_dev_driver(dev);

		printf("   %-14s bus=%-5s driver=%-12s numa=%d probed=%d args=\"%s\"\n",
		       rte_dev_name(dev), rte_bus_name(rte_dev_bus(dev)),
		       drv ? rte_driver_name(drv) : "-", rte_dev_numa_node(dev),
		       rte_dev_is_probed(dev), (da && da->args) ? da->args : "");
		n++;
	}
	printf("   -> %u device%s\n", n, n == 1 ? "" : "s");
}

/* Part 2: the ethdev iterator yields port ids. If the loop is left early
 * with break, rte_eth_iterator_cleanup() must be called; running to the
 * end cleans up automatically. */
static void
match_ports(const char *filter)
{
	struct rte_dev_iterator it;
	uint16_t port;
	char buf[256];
	int len = 0;

	/* rte_eth_iterator_init() rejects some strings; check it first so we
	 * can print the reason instead of silently matching nothing. */
	int ret = rte_eth_iterator_init(&it, filter);
	if (ret < 0) {
		printf("   %-46s -> error %d (%s)\n", filter, ret, rte_strerror(-ret));
		return;
	}
	rte_eth_iterator_cleanup(&it);

	buf[0] = '\0';
	RTE_ETH_FOREACH_MATCHING_DEV(port, filter, &it) {
		char name[RTE_ETH_NAME_MAX_LEN];

		if (rte_eth_dev_get_name_by_port(port, name, sizeof(name)) != 0)
			snprintf(name, sizeof(name), "?");
		len += snprintf(buf + len, sizeof(buf) - len, " %u(%s)", port, name);
		if (len >= (int)sizeof(buf))
			break;   /* not reached here; shows where cleanup would go */
	}
	printf("   %-46s ->%s\n", filter, buf[0] ? buf : " (no port)");
}

Pitfall: three ways these iterators crash in 26.11

We found these while writing the chapter; each is reproducible with the code here.

  1. The generic iterator writes into your string. For a filter with a / ("bus=vdev/class=eth"), rte_dev_iterator_init() sets devargs.data to your pointer and rte_devargs_layers_parse() overwrites each / with '\0'. A string literal lives in read-only memory: SIGSEGV. list_devices() copies the filter into a stack buffer first (line 44).
  2. The ethdev iterator needs a driver part. Any filter that starts with bus= or class= but is not class=eth,... and has no driver= layer ("bus=vdev", "bus=pci", "bus=vdev/class=eth", and plain "class=eth" without the comma) leaves devargs.args NULL, and rte_eth_iterator_init() calls strlen() on it (lib/ethdev/rte_ethdev.c). The --crash run below dies with exit status 139.
  3. Generic filters with a driver layer match nothing for vdevs: the bus part is rebuilt as name= with an empty name. Use class=eth,mac=... or the device name instead.

5kvargs: parsing key=value arguments like a driver

After the device name, everything in a devargs string is key=value,key=value. Drivers parse it with the small kvargs library (lib/kvargs/rte_kvargs.h), and your own application can use it for sub-options too. The API is five calls:

CallWhat it does
rte_kvargs_parse(args, valid_keys)Copies and splits the string into at most RTE_KVARGS_MAX (32) pairs. valid_keys is a NULL-terminated array; any other key makes it return NULL. Pass NULL to accept every key. Commas inside [...] do not split (queues=[0,2-3]).
rte_kvargs_process(kv, key, handler, opaque)Calls handler(key, value, opaque) for each pair with that key (or all pairs if key is NULL). A handler returning < 0 stops it with an error. Returns -1 for a key that has no value.
rte_kvargs_process_opt(...)Same, but also calls the handler for value-less keys, with value == NULL (flags such as mode).
rte_kvargs_count(kv, key), rte_kvargs_get(kv, key)How many pairs have this key; the first value for it.
rte_kvargs_free(kv)Frees everything (NULL is fine).
code/kvargs_demo.c (the driver pattern)C
/* The keys our imaginary driver understands. The array MUST end in NULL. */
static const char *const valid_keys[] = { "rate", "burst", "mode", "queues", NULL };

/* Where the handlers store what they parsed. */
struct my_cfg {
	unsigned long rate;
	unsigned long burst;
	char mode[16];
	unsigned int calls;     /* how many times a handler ran */
};

/* arg_handler_t: called once per matching key=value pair.
 * Return >= 0 for success, < 0 to make rte_kvargs_process() fail. */
static int
parse_ulong(const char *key, const char *value, void *opaque)
{
	unsigned long *out = opaque;
	char *end;

	if (value == NULL) {            /* only happens with _process_opt() */
		printf("    handler(%s): no value\n", key);
		return -1;
	}
	errno = 0;
	*out = strtoul(value, &end, 0);
	if (errno != 0 || *end != '\0') {
		printf("    handler(%s): '%s' is not a number\n", key, value);
		return -1;
	}
	printf("    handler(%s) <- \"%s\" -> %lu\n", key, value, *out);
	return 0;
}

static void
demo_string(const char *s)
{
	struct rte_kvargs *kv;
	struct my_cfg cfg = { .rate = 0, .burst = 0, .mode = "none" };
	int ret;

	printf("\n  input \"%s\"\n", s);
	kv = rte_kvargs_parse(s, valid_keys);
	if (kv == NULL) {
		printf("    rte_kvargs_parse(valid_keys) -> NULL (unknown key or bad syntax)\n");
		/* Without a key list every key is accepted. */
		kv = rte_kvargs_parse(s, NULL);
		if (kv == NULL) {
			printf("    rte_kvargs_parse(NULL)       -> NULL too: syntax error\n");
			return;
		}
		printf("    rte_kvargs_parse(NULL)       -> %u pairs (no key check)\n",
		       rte_kvargs_count(kv, NULL));
		rte_kvargs_process_opt(kv, NULL, print_pair, NULL);
		rte_kvargs_free(kv);
		return;
	}

	printf("    %u pairs; count(rate)=%u count(burst)=%u count(mode)=%u\n",
	       rte_kvargs_count(kv, NULL), rte_kvargs_count(kv, "rate"),
	       rte_kvargs_count(kv, "burst"), rte_kvargs_count(kv, "mode"));
	rte_kvargs_process_opt(kv, NULL, print_pair, NULL);

	/* The usual driver pattern: one process() call per key. A key that
	 * is absent simply does not call the handler (ret 0). */
	ret = rte_kvargs_process(kv, "rate", parse_ulong, &cfg.rate);
	if (ret == 0)
		ret = rte_kvargs_process(kv, "burst", parse_ulong, &cfg.burst);
	if (ret == 0) {
		ret = rte_kvargs_process(kv, "mode", parse_mode, &cfg);
		if (ret < 0) {
			printf("    rte_kvargs_process(mode) = %d (key without value)"
			       " -> retry with rte_kvargs_process_opt\n", ret);
			ret = rte_kvargs_process_opt(kv, "mode", parse_mode, &cfg);
		}
	}
	if (rte_kvargs_get(kv, "queues") != NULL)
		printf("    rte_kvargs_get(queues) = \"%s\" (list kept whole)\n",
		       rte_kvargs_get(kv, "queues"));
	printf("    => ret=%d rate=%lu burst=%lu mode=%s (mode handler ran %u time%s)\n",
	       ret, cfg.rate, cfg.burst, cfg.mode, cfg.calls, cfg.calls == 1 ? "" : "s");
	rte_kvargs_free(kv);
}

Five behaviours to remember: an unknown key fails the whole parse (with a key list); a repeated key calls the handler twice, so the last one wins unless you collect them; a bare key needs _process_opt; 0x40 parses because the handler uses strtoul(..., 0); and validating the value is the handler's job (burst=lots).

A PMD publishes its keys with RTE_PMD_REGISTER_PARAM_STRING(), which is only documentation (it is what dpdk-pmdinfo.py prints). The real check is the key list it passes to rte_kvargs_parse(). For net_null (drivers/net/null/rte_eth_null.c) that is size, copy and no-rx, which is why part B of the demo re-parses the stored devargs->args with exactly those keys. ch23 writes a PMD that does this itself.

net_null and net_ring: the CPU-only baselines

net_null is the default "port" of this course because it never runs out of packets. Its RX function allocates a burst from your mempool and sets each length to size (default 64); its TX function counts bytes and frees. With copy=1 it also copies a dummy packet in and out. net_ring moves pointers through an rte_ring: a lone net_ring port receives what it sent, so it needs --tx-first to have anything in flight, and it does not count bytes (testpmd shows Rx-bps: 0).

Found while measuring: net_null copy=1 leaks every transmitted mbuf

In 26.11 eth_null_copy_tx() copies each packet into a dummy buffer and returns, but never calls rte_pktmbuf_free() (compare eth_null_tx(), which does). Under io forwarding the 8192-mbuf pool is gone after about 8000 packets and RX stops, because eth_null_copy_rx() silently returns 0 when allocation fails (no rx_nombuf either). Recipe 9 in section 10 captures it. For copy-cost measurements use rxonly, where testpmd frees the mbufs; that is how the ladder measures it.

net_pcap: files in, files out

One queue per stream argument: rx_pcap=in.pcap reads a file, tx_pcap=out.pcap writes one (with nanosecond timestamps, magic 0xa1b23c4d), rx_iface=eth1 reads a live interface. With no TX stream, TX drops; with no RX stream, RX returns nothing. infinite_rx=1 loads the file into mbufs once and replays them forever, a cheap traffic source (57 Mpps here). eof=1 reports link down at end of file. Section 9 replays a file through testpmd.

net_tap and net_tun: a real kernel interface

net_tap opens /dev/net/tun and creates a netdev you can see with ip link; frames written by DPDK arrive in the kernel as if received on that interface, and frames the kernel sends to it appear on DPDK's RX queue. Each packet is one readv() or writev() system call plus a copy. The interface is deleted when the port closes. tap also supports a subset of rte_flow through TC rules, but no RETA, and rte_flow isolate/create fail here (ch20). net_tun is the L3 variant (no Ethernet header).

net_af_packet: a socket on an existing interface

net_af_packet does not create an interface; it opens an AF_PACKET socket on one you name (iface=ch09a) and maps the kernel's PACKET_MMAP RX and TX rings. RX copies frames out of the ring into mbufs; TX copies into the ring and calls send() to kick the kernel. Two options matter in labs: ignore_outgoing=1 (new in 26.11) stops the socket from seeing its own transmitted frames, which otherwise come straight back on a veth; and qpairs=N,fanout_mode=hash spreads flows across N queues with the kernel's flow hash, the only real multi-queue steering available on this machine (ch15).

net_af_xdp: UMEM and four rings

AF_XDP is the kernel's fast path to user space. The PMD allocates a UMEM, a region of frames shared with the kernel, and four single-producer/single-consumer rings that carry frame addresses, not data:

  • fill ring (user to kernel): empty frames the kernel may receive into.
  • RX ring (kernel to user): descriptors of received frames.
  • TX ring (user to kernel): frames to transmit.
  • completion ring (kernel to user): transmitted frames that can be reused.

An XDP program attached to the interface's queue (start_queue, queue_count) redirects each packet into the socket with bpf_redirect_map(). On drivers with zero-copy support the NIC DMAs straight into UMEM; on a veth the kernel copies (copy mode), which is why af_xdp is only a little faster than af_packet here. Only traffic that lands on the bound queue reaches the socket.

History: KNI and its replacements

The Kernel NIC Interface was an out-of-tree kernel module (rte_kni.ko) that created vEthX netdevs for the "exception path" (send packets the app does not handle to the kernel). It broke with every kernel release and was a security worry, was deprecated in 22.11 and removed in 23.11. Its replacements are the PMDs in this section: net_tap (simplest), virtio_user with vhost-net (fastest, needs /dev/vhost-net, absent on this VM), af_xdp and af_packet. Old tutorials that mention rte_kni_* will not build.

What the ladder teaches:

  • ring > null rxonly > null io > null copy=1: moving a pointer is cheaper than allocating an mbuf, allocating is cheaper than allocating and freeing, and a 64-byte memcpy each way costs about 30% here.
  • pcap infinite_rx is a fast source because the file is pre-loaded; reading a real file would be much slower.
  • memif and vhost-user drop by an order of magnitude: one copy per direction, a second process on other vCPUs, and only 32 packets in flight. Their wide whiskers come from the other jobs on this VM.
  • tap, af_xdp, af_packet sit at 2-3 Mpps: every packet crosses the kernel. On a veth, af_xdp runs in copy mode and gains little over af_packet; with a zero-copy NIC driver the gap is large.

Some NICs (mlx5) stay on their kernel driver and use a bifurcated model instead of vfio-pci. ch23 covers VFIO, IOMMU groups and no-IOMMU mode; ch29 covers production system setup.

Common pitfalls

  • testpmd exits at once with "Creation of mbuf pool for socket 0 failed: Cannot allocate memory": the default pool does not fit in --no-huge -m 256. Pass --total-num-mbufs=8192.
  • testpmd in a script stops immediately: no -i, no --stats-period, stdin at EOF. Use --stats-period N + timeout -s INT, or pipe commands into -i.
  • A pcap replay or vhost test shows 0 packets: testpmd's start-up flush drained the RX queue. Add --no-flush-rx.
  • The app starts but has no port: a mistyped devargs key fails the probe silently from the app's point of view ("EAL: Failed to probe device"). Check rte_eth_dev_count_avail() and read the EAL log.
  • SIGSEGV in rte_eth_iterator_init() or rte_dev_iterator_init(): an ethdev filter without a driver part (bus=vdev, bare class=eth), or a string literal with a / passed to RTE_DEV_FOREACH. Use class=eth,..., device names, and writable buffers.
  • rte_vdev_init() returns -1 and rte_strerror() says "Operation not permitted": it returns a bare -1 for "no driver" and "probe failed". The log line has the real reason.
  • net_ring forwards nothing: nothing generates packets. Use --tx-first.
  • A veth ping-pong shows each packet twice, or rates double: af_packet sees its own transmitted frames. Use ignore_outgoing=1.
  • Counters that do not add up after clear port xstats: cleared while forwarding (racy on net_null RX), or packets drained by the start-up flush. Clear while stopped.
  • libxdp warnings scare a reviewer: "No bpffs found ... Falling back to loading single prog" is benign for a single socket. Mount bpffs only if you need multiple XDP programs per interface.
  • Leftover ch09* interfaces or /run/dpdk/ch09-* after a crash: put cleanup in a trap ... EXIT.

Summary
  • A bus finds devices, a driver of that bus probes them, and probe creates a class object (an ethdev port). The vdev bus creates devices only because you name them; drivers match by name prefix.
  • devargs name and configure devices: [bus:]name[,k=v...] or the layered bus=/class=/driver= form. rte_devargs_parse() splits them; drivers parse the arguments with kvargs and a valid-key list.
  • RTE_DEV_FOREACH and RTE_ETH_FOREACH_MATCHING_DEV filter devices with devargs strings. In 26.11, use class=eth,... or device names with the ethdev iterator, and writable buffers with the generic one.
  • rte_vdev_init(), rte_dev_probe(), rte_vdev_uninit() and rte_dev_remove() create and destroy devices at run time; a failed probe at init does not fail rte_eal_init().
  • Software PMDs trade realism for convenience: ring and null are CPU baselines (100-300 Mpps here), pcap replays files, tap/af_packet/af_xdp go through the kernel (2-3 Mpps here). Read software numbers as overhead comparisons, never as NIC performance.
  • testpmd: always --total-num-mbufs; background runs need --stats-period or a fed -i; --no-flush-rx for pcap and vhost; and its info, descriptor, verbose, burst-stats and xstats commands make it the first debugger to reach for.
