Chapter 5

Indices, Handles and Generations

Chapter 4 laid fields out for the loops that read them. This chapter does the same for the links between records. On a 64-bit machine every pointer costs eight bytes, and it points at one address that the allocator chose. Replace it with a 32-bit index into an array you own and the link shrinks by half. The data can then move, grow, go to disk and come back, and the borrow checker stops objecting. There is a cost: an index can outlive the thing it refers to. This chapter fixes that with generations, builds the same generational pool (a slot map) in Rust, Zig and Odin, and measures a million-node tree stored both ways.

A pointer is eight bytes of trust

Picture a binary search tree in the textbook style. Each node holds a key and two child pointers, and each node is its own heap allocation. In Rust that is Option<Box<Node>>, in Zig ?*Node, in Odin ^Node. The code is short and the picture in your head is clean. The machine sees something else. A 4-byte key is followed by 4 bytes of padding, because the pointers after it need 8-byte alignment. Then come 16 bytes of addresses. Of a 24-byte node, a sixth is payload and a sixth is padding. Two thirds are links, and each link is wide enough to address 16 exabytes when the tree holds a million nodes.

Andrew Kelley put this in one line in his Handmade Seattle talk on how the Zig compiler was rebuilt: a struct with four pointers is 32 bytes on a 64-bit target, the same struct with four u32 indices is 16 bytes, and its alignment drops from 8 to 4[1]. Smaller alignment matters as much as the size. A 4-aligned struct can follow a u32 or a u8 with less padding, and sits more tightly in arrays and in other structs. Noel Llopis made the same argument in 2008, in a column on how to manage relationships between game objects[2].

A tree node is {key: u32, left, right}. With 8-byte pointers it is 24 bytes. With u32 indices, how big is it, and how much memory does a million-node tree save once you count what malloc adds per allocation?

12 bytes, align 4, no padding. On this orb glibc hands out a 32-byte chunk for every 24-byte request (an 8-byte header plus the payload, rounded to 16), so a million pointer nodes occupy about 32 MB. The index tree is one 12 MB array. Most of the saving comes from malloc, not from the pointers, and it shows up in the measurements below.

Pointers become indices

The change is easy to state. Keep every node of one kind in one growable array, and store a link as the position of the target in that array. Here is the same node in all three languages, once with pointers and once with typed 32-bit indices. Each file asserts the sizes at compile time, so the claims in this section are checked every time the code builds:

The three pointer versions are 24 bytes for different reasons. Odin keeps fields in declaration order, so the padding sits after key where you wrote it. Rust and Zig may reorder fields, but nothing helps here: one 4-byte field next to two 8-byte fields always rounds up to 24. In Rust, Option<Box<PNode>> is still 8 bytes because a Box is never null, so None takes the null value. Zig's ?*PNode does the same, and so does Odin's nilable ^PNode.

What does the change buy? Five things, and they are worth keeping apart because they matter in different programs.

  1. Size. Links drop from 8 bytes to 4 and alignment from 8 to 4. The 24-byte node becomes 12. A 64-byte cache line now holds five nodes instead of two, and a 4 KiB page holds 341 instead of 170. Narrowing rarely costs anything measurable: on x86-64 and AArch64, 32-bit integer instructions are generally no slower than 64-bit ones, and the extra work is an occasional zero-extension or the +1 of a NonZero index (below).
  2. One allocation instead of n. The pointer tree calls malloc once per node and free once per node at teardown. The index tree grows one array by doubling, so about 20 reallocations for a million nodes, and one free.
  3. Relocatable. An index is a position, not an address. When the array reallocates, every index is still right, while every pointer into the old block is now dangling. You can also move nodes on purpose: sort them, compact them, or lay them out in the order you will walk them. The benchmark below does exactly that.
  4. Serializable. The array plus its indices means the same thing in a file, in another process or on a GPU. You write the bytes and read them back with no parsing, and only a small relocation step that points the top-level structures at the loaded arrays. Richard Feldman's Roc rewrite does this, a technique he says he learned from the Zig compiler[3]. Chapter 11 measures it.
  5. Borrow-checker friendly. A u32 borrows nothing. Rust code that would need Rc<RefCell<Node>> for parent links or cycles can hold plain integers instead, and mutate through &mut to the array. This is the heart of Catherine West's 2018 keynote, which we come back to below.

The figure counts two different things, and keeping them apart is the point. Bytes depend only on the node layout and the allocator: 32 per pointer node (with glibc) against 12 per index node, so 2.67× at any size. Lines touched also depend on where the nodes landed. On a fresh heap, consecutive malloc calls often return consecutive chunks, so the pointer tree is less scattered than the textbook says. On a heap that has been through a lot of malloc and free traffic, every node can land on a different line. The array cannot scatter. That is a property of the data structure, not luck with the allocator.

Worked example: a million nodes on this orb

The "heap span" is the distance from the lowest to the highest node address divided by the node count. It is only a lower bound on what the allocator used, but it lines up with each allocator's rules. glibc rounds a 24-byte request up to a 32-byte chunk. Odin's heap_allocator asks the C heap for alignment - 1 + size_of(rawptr) + size bytes (39 here) so it can align the block itself and store the original pointer just in front of it. That turns each 24-byte node into a 48-byte chunk (base/runtime/heap_allocator.odin). The array's figure is its capacity: Rust's Vec and Odin's [dynamic] happened to land on exactly 220, and Zig's ArrayList grows by a different factor and overshot by 22%. Even so, the index tree is 2.5 to 4× smaller, depending on the language and allocator.

Typed indices: an integer that knows what it points at

A raw u32 loses something a pointer had: its type. *Monster cannot be passed where *Item is expected, but nothing stops you from indexing the item array with a monster index. The fix is a distinct integer type for each array, which costs nothing at run time. All three languages can do this, and each does it differently.

/// A node index that cannot be mixed up with any other integer. It stores index + 1 in a
/// NonZeroU32, so Option<NodeId> is 4 bytes with 0 meaning None.
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
struct NodeId(NonZeroU32);

impl NodeId {
    fn new(index: usize) -> Self {
        let raw = u32::try_from(index + 1).expect("more than 2^32 - 1 nodes");
        NodeId(NonZeroU32::new(raw).expect("index + 1 is never 0"))
    }
    fn index(self) -> usize {
        self.0.get() as usize - 1
    }
}
/// A non-exhaustive enum: a u32 that is its own type, so a NodeId cannot be passed where a
/// plain integer (or some other enum(u32) id) is expected. `none` is the null value.
const NodeId = enum(u32) {
    none = std.math.maxInt(u32),
    _,

    fn from(i: usize) NodeId {
        return @fromBackingInt(@intCast(i));
    }
    fn index(id: NodeId) usize {
        return @backingInt(id);
    }
};
// `distinct` makes a new type with u32's representation: a Node_Id will not silently
// convert to or from u32 or any other distinct id; you must write Node_Id(i) or u32(id).
Node_Id :: distinct u32
NO_NODE :: Node_Id(max(u32))
  • Rust: a newtype over NonZeroU32. struct NodeId(NonZeroU32) is its own type, and because 0 can never occur, Option<NodeId> uses 0 for None and stays 4 bytes (a plain Option<u32> is 8). The price is storing index + 1. rustc's own newtype_index! macro does the opposite: it caps indices at 0xFFFF_FF00 and puts the niche at the top[4].
  • Zig: a non-exhaustive enum. enum(u32) { none = maxInt(u32), _ } is a u32 with one named value and every other bit pattern allowed. It is a new type, so it does not coerce to or from integers. Alex Kladov calls this "a happy accident of language design"[5], and the Zig compiler uses it everywhere (Ast.Node.Index, InternPool.Index).
  • Odin: distinct u32. One keyword makes a new nominal type with u32's representation. You can still index an array with it directly (t.nodes[id]), but mixing it with a plain u32 or another distinct id needs an explicit conversion. Like Zig, the code uses max(u32) as "none".

Rust: #[derive(Clone, Copy, PartialEq)] on a generic handle adds bounds you do not want. #[derive(Copy)] struct Handle<T> only implements Copy when T: Copy, so Handle<String> would not be Copy. Write the four impls by hand, as pool.rs does. And do not name the field gen: it is a reserved keyword in edition 2024.

Indices let you move the data

Here is the payoff of "relocatable" in a few lines. Because the links are positions, the program can copy the tree into a new array in pre-order (a node, then its left subtree, then its right subtree) and renumber the links on the way. After that, walking the tree mostly reads the array front to back. A pointer tree cannot do this without allocating every node again and rewriting every pointer.

/// Indices are positions, not addresses, so we can move every node and fix the links:
/// copy the tree in pre-order (a node, then its left subtree, then its right subtree).
fn relayout_preorder(&self) -> Tree {
    let mut out = Tree { nodes: Vec::with_capacity(self.nodes.len()), root: None };
    out.root = self.copy_preorder(self.root, &mut out.nodes);
    out
}

fn copy_preorder(&self, node: Option<NodeId>, out: &mut Vec<INode>) -> Option<NodeId> {
    let n = &self.nodes[node?.index()];
    let me = out.len();
    out.push(INode { key: n.key, left: None, right: None });
    out[me].left = self.copy_preorder(n.left, out);
    out[me].right = self.copy_preorder(n.right, out);
    Some(NodeId::new(me))
}
/// Indices are positions, not addresses, so we can move every node and fix the links:
/// copy the tree in pre-order (a node, then its left subtree, then its right subtree).
fn relayoutPreorder(t: *const Tree, gpa: Allocator) !Tree {
    var out: Tree = .{};
    try out.nodes.ensureTotalCapacityPrecise(gpa, t.nodes.items.len);
    out.root = t.copyPreorder(t.root, &out);
    return out;
}

fn copyPreorder(t: *const Tree, node: NodeId, out: *Tree) NodeId {
    if (node == .none) return .none;
    const n = t.nodes.items[node.index()];
    const me = out.nodes.items.len;
    out.nodes.appendAssumeCapacity(.{ .key = n.key });
    const l = t.copyPreorder(n.left, out);
    const r = t.copyPreorder(n.right, out);
    out.nodes.items[me].left = l;
    out.nodes.items[me].right = r;
    return .from(me);
}
// Indices are positions, not addresses, so we can move every node and fix the links:
// copy the tree in pre-order (a node, then its left subtree, then its right subtree).
tree_relayout_preorder :: proc(t: ^Tree) -> (out: Tree) {
	out.nodes = make([dynamic]INode, 0, len(t.nodes))
	out.root = copy_preorder(t, t.root, &out)
	return
}

copy_preorder :: proc(t: ^Tree, id: Node_Id, out: ^Tree) -> Node_Id {
	if id == NO_NODE {
		return NO_NODE
	}
	n := t.nodes[id]
	me := Node_Id(len(out.nodes))
	append(&out.nodes, INode{n.key, NO_NODE, NO_NODE})
	l := copy_preorder(t, n.left, out)
	r := copy_preorder(t, n.right, out)
	out.nodes[me].left, out.nodes[me].right = l, r
	return me
}

The Rust version uses ? on an Option to stop at a missing child. Zig and Odin compare against their "none" value. Zig calls ensureTotalCapacityPrecise once and then appendAssumeCapacity, so the copy can never fail halfway. The Rust and Odin versions reserve capacity and then push.

The dangling index, and generations

An index fixes size and placement. It does not fix lifetime. Say a monster stores target: u32 = 17. Slot 17 is freed when its occupant dies, and the next spawn reuses it. The monster now attacks a stranger. Nothing crashes and no sanitizer complains, because the index still points at valid memory. This is a stale-index bug (a single-threaded cousin of the ABA problem), and it is arguably worse than a dangling pointer, which at least has a chance of crashing.

The standard fix is to make the reference a pair: an index and a generation. Every slot keeps a counter. Freeing a slot increments it. A handle is valid only if its generation equals the slot's current one, so after a slot is reused, every old handle to it fails the comparison. Niklas Frykholm (who later wrote as Niklas Gray) described the version used in the Bitsquid engine (later Autodesk Stingray) in 2014[6]:

Three details in the design show how much thought fits in one integer. First, the whole id had to fit in 30 bits, because it is passed to Lua as a light userdata pointer and two bits tag it. Frykholm adds that on a 64-bit-only engine he would use more bits. Second, the generation table on the C++ side is a separate Array<unsigned char>: one byte per slot, so checking alive() reads a dense byte array that "will fit more in the cache". Third, 8 bits wrap after 256 reuses, which is not many. So freed indices go into a queue and are reused only when the queue holds more than MINIMUM_FREE_INDICES = 1024 of them. An id can only come back after "256 * 1024 entities" have been created and destroyed[6].

Andre Weissflog's "Handles are the better pointers" (2018) sets out rules in the same spirit: one system owns all items of a type in arrays, outsiders get only handles, and a handle becomes a pointer only briefly, never to be stored[7]. His later update adds per-slot generation counters, "bumped when a handle is released", and gives the honest answer to wrap-around: "Once the generation counter would 'overflow', disable that array slot, so that no new handles are returned for this slot." The pool in this chapter does exactly that.

Before you press Play: after remove orc and remove imp, which slot does the next insert get, 0 or 2?

Slot 2. The free list is a stack: removing imp pushed slot 2 on top of slot 0, so bat pops 2 and rat then gets 0. Bitsquid deliberately uses a FIFO queue with a 1024-entry minimum instead, so that any one slot is reused as rarely as possible and its 8-bit generation takes longer to wrap.

A generational pool in three languages

The pool is about a hundred lines in each language. A handle is 8 bytes, a 32-bit index plus a 32-bit generation, so wrap-around needs four billion reuses of one slot. Slots live in one growable array. Each slot holds either a value or a link to the next free slot, and the generation sits outside that union, because it has to survive the slot being free. That is the layout from Gray's later Our Machinery bulk-data post[8], which says to store the generation "outside the union".

pub struct Handle<T> {
    index: u32,
    generation: NonZeroU32,
    _marker: PhantomData<fn() -> T>, // typed, but owns no T: Send + Sync + Copy for any T
}

struct Slot<T> {
    generation: NonZeroU32,
    state: State<T>,
}

enum State<T> {
    Occupied(T),
    Free { next_free: Option<u32> },
    Retired, // generation counter exhausted: never handed out again
}

pub struct Pool<T> {
    slots: Vec<Slot<T>>,
    free_head: Option<u32>, // the free list lives *inside* `slots`
    len: usize,
}
/// Declared inside the generic, so Pool(Monster).Handle and Pool(Item).Handle are
/// different types: a typed handle for free. The zero handle is never valid
/// because generations start at 1.
pub const Handle = packed struct(u64) {
    index: u32,
    generation: u32,
    pub const none: Handle = .{ .index = 0, .generation = 0 };
};

const end = std.math.maxInt(u32); // end of the free list

/// The generation sits outside the union so it survives the slot being freed.
const Slot = struct {
    generation: u32,
    state: union(enum) {
        occupied: T,
        free: u32, // index of the next free slot, or `end`
        retired, // generation counter exhausted: never handed out again
    },
};

free_head: u32 = end, // the free list lives *inside* `slots`
len: u32 = 0,

	index: u32,
	gen:   u32, // starts at 1, so the zero value Handle{} is never valid
}

FREE_END :: max(u32) // end of the free list

Slot :: struct($T: typeid) {
	item:      T,
	gen:       u32, // survives the slot being freed and reused
	next_free: u32, // link in the free list while the slot is free
	live:      bool,
}

Pool :: struct($T: typeid) {
	slots:     [dynamic]Slot(T),
	free_head: u32, // the free list lives *inside* `slots`
	len:       int,
}

Each language makes the handle typed in its own way, and each has a reason.

  • Rust uses PhantomData<fn() -> T>. The handle mentions T for type checking but owns no T, so it is Copy, Send and Sync whatever T is. The slot is an enum State next to a NonZeroU32 generation, which keeps Option<Handle> at 8 bytes.
  • Zig declares Handle inside the function that returns the pool type. Every instantiation makes a new struct, so Pool(Monster).Handle and Pool(Item).Handle do not mix, and no phantom parameter is needed. It is a packed struct(u64), so a handle is exactly one 64-bit word that compares in one instruction. The slot state is a tagged union(enum), so reading slot.state.free on an occupied slot traps in -O debug and -O safe builds.
  • Odin gives Handle a type parameter it never uses in a field: Handle :: struct($T: typeid). Handle(Monster) and Handle(Item) are still different types. Odin has no generic union of "a T or a link" that reads as naturally, so the Odin slot keeps both a next_free field and a live flag. That costs a few bytes per slot. Gray notes that SoA/SIMD code is forced into the same layout, where "we have to use a proper struct field"[8].

Insert pops the free list or appends. Remove checks the handle, increments the generation, and pushes the slot. When a generation would overflow, the slot is retired instead, following Weissflog's rule:

pub fn insert(&mut self, value: T) -> Handle<T> {
    self.len += 1;
    if let Some(index) = self.free_head {
        let slot = &mut self.slots[index as usize];
        let State::Free { next_free } = slot.state else { unreachable!("free list points at a used slot") };
        self.free_head = next_free; // pop the free list
        slot.state = State::Occupied(value);
        return Handle { index, generation: slot.generation, _marker: PhantomData };
    }
    let index = u32::try_from(self.slots.len()).expect("pool full");
    let generation = NonZeroU32::MIN; // 1: a zeroed handle is never valid
    self.slots.push(Slot { generation, state: State::Occupied(value) });
    Handle { index, generation, _marker: PhantomData }
}

pub fn remove(&mut self, h: Handle<T>) -> Option<T> {
    let slot = self.slots.get_mut(h.index as usize)?;
    if slot.generation != h.generation || !matches!(slot.state, State::Occupied(_)) {
        return None; // stale or double remove
    }
    // Bump the generation so every outstanding copy of `h` stops matching.
    let state = match slot.generation.checked_add(1) {
        Some(g) => {
            slot.generation = g;
            let s = State::Free { next_free: self.free_head };
            self.free_head = Some(h.index); // push onto the free list
            s
        }
        None => State::Retired, // wrapping would make old handles valid again
    };
    self.len -= 1;
    match std::mem::replace(&mut slot.state, state) {
        State::Occupied(v) => Some(v),
        _ => unreachable!(),
    }
}
pub fn insert(self: *Self, gpa: Allocator, value: T) Allocator.Error!Handle {
    if (self.free_head != end) {
        const index = self.free_head;
        const slot = &self.slots.items[index];
        self.free_head = slot.state.free; // pop; safety-checked: must be a free slot
        slot.state = .{ .occupied = value };
        self.len += 1;
        return .{ .index = index, .generation = slot.generation };
    }
    const index: u32 = @intCast(self.slots.items.len);
    try self.slots.append(gpa, .{ .generation = 1, .state = .{ .occupied = value } });
    self.len += 1;
    return .{ .index = index, .generation = 1 };
}

pub fn remove(self: *Self, h: Handle) ?T {
    const slot = self.slotFor(h) orelse return null; // stale or double remove
    const value = slot.state.occupied;
    if (std.math.add(u32, slot.generation, 1)) |g| {
        slot.generation = g; // every outstanding copy of `h` stops matching
        slot.state = .{ .free = self.free_head };
        self.free_head = h.index; // push onto the free list
    } else |_| {
        slot.state = .retired; // wrapping would make old handles valid again
    }
    self.len -= 1;
    return value;
}
pool_insert :: proc(p: ^Pool($T), item: T) -> Handle(T) {
	p.len += 1
	if p.free_head != FREE_END {
		index := p.free_head
		s := &p.slots[index]
		p.free_head = s.next_free // pop the free list
		s.item, s.live = item, true
		return {index, s.gen}
	}
	append(&p.slots, Slot(T){item = item, gen = 1, next_free = FREE_END, live = true})
	return {u32(len(p.slots) - 1), 1}
}

// The pointer is valid only until the next insert: `slots` may reallocate. Keep the handle.
pool_get :: proc(p: ^Pool($T), h: Handle(T)) -> (^T, bool) #optional_ok {
	if int(h.index) >= len(p.slots) {
		return nil, false
	}
	s := &p.slots[h.index]
	if !s.live || s.gen != h.gen {
		return nil, false // stale handle, or never issued
	}
	return &s.item, true
}

pool_remove :: proc(p: ^Pool($T), h: Handle(T)) -> (item: T, ok: bool) {
	if _, live := pool_get(p, h); !live {
		return // stale or double remove
	}
	s := &p.slots[h.index]
	item, ok = s.item, true
	s.live = false
	s.item = {}
	p.len -= 1
	if s.gen == max(u32) {
		return // retired: wrapping to 0 would make old handles valid again
	}
	s.gen += 1 // every outstanding copy of `h` stops matching
	s.next_free = p.free_head
	p.free_head = h.index // push onto the free list
	return
}

Lookup is a bounds check, one generation compare and a liveness check, all on the same slot and usually in the same cache line:

pub fn get(&self, h: Handle<T>) -> Option<&T> {
    match self.slots.get(h.index as usize)? {
        Slot { generation, state: State::Occupied(v) } if *generation == h.generation => Some(v),
        _ => None,
    }
}
/// The pointer is valid only until the next insert: `slots` may reallocate.
/// Keep the handle, not the pointer.
pub fn get(self: *Self, h: Handle) ?*T {
    const slot = self.slotFor(h) orelse return null;
    return &slot.state.occupied;
}

fn slotFor(self: *Self, h: Handle) ?*Slot {
    if (h.index >= self.slots.items.len) return null;
    const slot = &self.slots.items[h.index];
    if (slot.generation != h.generation or slot.state != .occupied) return null;
    return slot;
}

A handle is stable. The pointer you get from it is not. Zig's get returns ?*T and Odin's returns ^T into the slot array. The next insert may reallocate that array and leave the pointer dangling. Rust turns this mistake into a compile error: get returns &T borrowed from the pool, and insert needs &mut self, so the borrow checker rejects holding one across the other. In Zig and Odin it is a convention: resolve, use, drop, exactly as Weissflog says[7].

Tests for stale handles

Each language's tests check the same behaviour. A removed handle does not resolve, a second remove is rejected, a reused slot gets generation + 1 and the old handle still fails, the free list is LIFO and lives inside the array, and a handle taken before 10,000 more inserts (and many reallocations) still finds its value. Here is the central test in Zig:

test "stale handle is detected after reuse" {
    const gpa = testing.allocator;
    var p: Pool([]const u8) = .empty;
    defer p.deinit(gpa);
    const a = try p.insert(gpa, "orc");
    const b = try p.insert(gpa, "elf");
    try testing.expectEqualStrings("orc", p.remove(a).?);
    try testing.expect(p.get(a) == null); // removed handle must not resolve
    try testing.expect(p.remove(a) == null); // double remove must be rejected
    const c = try p.insert(gpa, "goblin"); // reuses a's slot
    try testing.expectEqual(a.index, c.index);
    try testing.expectEqual(a.generation + 1, c.generation);
    try testing.expect(p.get(a) == null); // stale handle must not see the new occupant
    try testing.expectEqualStrings("goblin", p.get(c).?.*);
    try testing.expectEqualStrings("elf", p.get(b).?.*);
    try testing.expect(p.get(.none) == null);
    try testing.expectEqual(2, p.len);
}

Odin ships one: core:container/handle_map

Since the 2026 Q1 release Odin has a generational map in its core library[9]. Read the source in core/container/handle_map/ before you use it, because its design differs from the pool above in four ways:

  • The item stores its own handle. Dynamic_Handle_Map($T, $Handle_Type) has a where clause requiring a field named handle of the handle type in T, and the map writes idx and gen into it. There is no separate slot struct: the generation lives in your item.
  • You choose the handle size. Handle16 (u8 + u8), Handle32 (u16 + u16) or Handle64 (u32 + u32). The two halves must have the same unsigned type. Handle32 holds at most 65,534 items.
  • Index 0 is a sentinel. The first add writes a zero-valued item at index 0, so idx == 0 means "no handle" and the zero value of any handle is invalid. Removing an item sets its handle.idx to 0, and that is how iteration skips holes. A fixed Static_Handle_Map(N, T, H) therefore holds N − 1 items.
  • Pointers are stable. The dynamic map stores items in xar.Array(T, 4), an exponential array that adds new blocks instead of moving old ones, so get's ^T survives later adds. The free slots go into a separate unused_items array (the static map links them through a parallel [N]u32). On reuse the generation becomes prev_gen + 1 with no retirement, so a Handle16's 8-bit generation can wrap after 256 reuses of one slot.
// The same story with core:container/handle_map. The item must carry its own handle.
Entity :: struct {
	handle: hm.Handle64, // {idx: u32, gen: u32}
	hp:     int,
}

handle_map_demo :: proc() {
	ents: hm.Dynamic_Handle_Map(Entity, hm.Handle64)
	hm.dynamic_init(&ents, context.allocator)
	defer hm.dynamic_destroy(&ents)
	orc := hm.add(&ents, Entity{hp = 10})
	elf := hm.add(&ents, Entity{hp = 20})
	hm.remove(&ents, orc)
	goblin := hm.add(&ents, Entity{hp = 30}) // reuses orc's slot with gen + 1
	fmt.printfln("handle_map: orc=%v goblin=%v valid(orc)=%v valid(goblin)=%v len=%d", orc, goblin, hm.is_valid(&ents, orc), hm.is_valid(&ents, goblin), hm.len(ents))
	if e, ok := hm.get(&ents, elf); ok {
		e.hp -= 5
	}
	assert(!hm.is_valid(&ents, orc) && goblin.idx == orc.idx && goblin.gen == orc.gen + 1)
	assert(orc.idx == 1) // index 0 is a reserved "no handle" sentinel
}

The program prints orc=Handle64{idx = 1, gen = 1} goblin=Handle64{idx = 1, gen = 2} valid(orc)=false valid(goblin)=true len=2. It is the same story as the hand-rolled pool, shifted up by one slot because of the sentinel. Neither Rust nor Zig ships a generational container in its standard library. In Rust the usual choice is the slotmap crate (this book uses std only), and Zig code tends to hand-roll the pool, as above.

Catherine West's argument: indices are how Rust wants you to write games

Catherine West's closing keynote at RustConf 2018, "Using Rust for Game Development", starts from a question Rust newcomers keep asking: how do you structure a game "without needing Rc<RefCell> and Arc<Mutex> everywhere?"[10] Her answer starts with the object-oriented design people bring from C++. A World owns a HashMap<EntityId, Rc<Entity>>, and entity.update(&mut world) must borrow the entity mutably and then borrow it again through the world. That does not compile. Wrapping everything in RefCell makes it compile, and then the same re-entrancy becomes a run-time panic instead of a compile error.

The way out she shows is data-oriented. Entities become indices, components live in Vecs, and systems are plain functions that take &mut GameState. "You can do a LOT with indexes into Vecs. This is way easier than self borrowing or Rc<RefCell>," she writes. Then she adds generations, with a GenerationalIndexAllocator that hands out (index, generation) pairs, kept separate from GenerationalIndexArray<T> storage, so one allocator can key many component arrays. Her summary: "Rust highly rewards data-oriented design with simple, understandable ownership semantics."[10] The generational-arena crate says it was "Inspired by Catherine West's closing keynote at RustConf 2018"[12]; slotmap had already been released ("slotmap beat me to releasing a crate for it", West wrote).

One Rust problem remains: you sometimes need two &mut into the same array at once. The goblin hits the elf, and both lose hit points. pool.get_mut(a) followed by pool.get_mut(b) fails the borrow check, because the first &mut borrows the whole pool. slice::get_disjoint_mut solves exactly this. It takes an array of indices, checks that they are in bounds and pairwise distinct, and returns that many &mut, or an error. There is no unsafe and no RefCell:

/// Two `&mut` at once from two distinct live handles: no RefCell, no unsafe.
/// `get_disjoint_mut` (stable since 1.86) returns Err if the indices overlap.
pub fn get2_mut(&mut self, a: Handle<T>, b: Handle<T>) -> Option<[&mut T; 2]> {
    let [sa, sb] = self.slots.get_disjoint_mut([a.index as usize, b.index as usize]).ok()?;
    match (sa, sb) {
        (Slot { generation: ga, state: State::Occupied(va) }, Slot { generation: gb, state: State::Occupied(vb) })
            if *ga == a.generation && *gb == b.generation =>
        {
            Some([va, vb])
        }
        _ => None,
    }
}

get_disjoint_mut (for slices and for HashMap) was stabilised in Rust 1.86 (feature names get_many_mut for slices, map_many_mut for HashMap), and it is what you should use on 1.100. Before 1.86 you wrote split_at_mut gymnastics or reached for unsafe. It returns Err for an index out of bounds or for overlapping indices, so get2_mut(elf, elf) returns None, and a unit test checks that.

Zig and Odin have no such problem: pool.get(a) and pool.get(b) just return two pointers, and if a == b they alias. Rust makes you name the aliasing case; the other two let you forget it.

Deleting: swap-and-pop, holes, or tombstones

Our pool leaves a hole when it frees a slot. That is one of three choices, and Gray's bulk-data post lays them out clearly[8].

  • Shift everything down (Vec::remove, orderedRemove, ordered_remove). The array stays packed and in order, but deleting is O(n). Gray: "The first option is terrible".
  • Swap-and-pop (Vec::swap_remove, Zig swapRemove, Odin unordered_remove). The last element moves into the hole, in O(1), and the array stays packed. Iteration never skips anything. The catch: elements move, so an element's index is no longer a permanent name. You then need an ID → index indirection table, which is itself "an std::vector with holes", and every external lookup pays one extra dependent load.
  • Holes with an in-array free list, like our pool. Indices are permanent, so the index is the id, and there is no indirection. Free slots link to each other through their own unused memory, so the free list costs no extra space. Iteration has to skip holes, which is only expensive when there are many, and holes only appear after the count has gone down. Gray's verdict: "unless you need to optimize for fast iteration, you are probably better of[f] using the 'array with holes' approach."

A fourth option is a hybrid: keep the array packed for iteration, but on delete write a tombstone instead of moving anything, and compact later. EnTT does this when a component type asks for pointer stability. Michele Caini's "ECS back and forth" series shows the trade: references stay valid, and in return every iteration checks for tombstones [11].

Put swap-and-pop together with an id → index table and you have a sparse set: a sparse array indexed by id points into a dense array, and the dense array remembers which id is in each position. That is the storage under EnTT and many other ECS libraries, and it is where Chapter 9 picks up. The difference from this chapter is the direction of the promise. A pool promises stable positions, and a sparse set promises dense iteration.

Measuring it

The benchmark (code/ch05-indices-handles/) builds the same million-node BST four ways, from the same keys, and checks three times that the trees agree. The sum of insertion depths must match between the pointer tree and the index tree (same shape). Then three in-order walks fold the keys into one order-sensitive hash, and all three must produce the same 0xb465fe24fa4194d4 in all three languages. The three layouts are:

  • pointer nodes: one allocation per node, in insertion order;
  • u32 indices: one array, nodes in insertion order, so the same order as the pointer nodes;
  • u32 indices, DFS order: the same array after the pre-order relayout above.

Each walk is a plain recursive in-order traversal, a few dozen levels deep. What differs is where each node's bytes are and how many of them there are.

fn ptr_walk(node: &Option<Box<PNode>>, mut h: u64) -> u64 {
    if let Some(n) = node {
        h = ptr_walk(&n.left, h);
        h = h.wrapping_mul(31).wrapping_add(n.key as u64);
        h = ptr_walk(&n.right, h);
    }
    h
}
// …
fn walk(&self, node: Option<NodeId>, mut h: u64) -> u64 {
    if let Some(id) = node {
        let n = &self.nodes[id.index()];
        h = self.walk(n.left, h);
        h = h.wrapping_mul(31).wrapping_add(n.key as u64);
        h = self.walk(n.right, h);
    }
    h
}
fn ptrWalk(node: ?*const PNode, h0: u64) u64 {
    const n = node orelse return h0;
    var h = ptrWalk(n.left, h0);
    h = h *% 31 +% n.key;
    return ptrWalk(n.right, h);
}
// …
fn walk(t: *const Tree, node: NodeId, h0: u64) u64 {
    if (node == .none) return h0;
    const n = t.nodes.items[node.index()];
    var h = t.walk(n.left, h0);
    h = h *% 31 +% n.key;
    return t.walk(n.right, h);
}
ptr_walk :: proc(n: ^PNode, h0: u64) -> u64 {
	if n == nil {
		return h0
	}
	h := ptr_walk(n.left, h0)
	h = h * 31 + u64(n.key)
	return ptr_walk(n.right, h)
}
// …
tree_walk :: proc(t: ^Tree, id: Node_Id, h0: u64) -> u64 {
	if id == NO_NODE {
		return h0
	}
	n := t.nodes[id]
	h := tree_walk(t, n.left, h0)
	h = h * 31 + u64(n.key)
	return tree_walk(t, n.right, h)
}

Read the chart in two steps. Pointers → indices, same order: the walk is about 1.8× faster in Rust, about 1.6× in Zig and about 2.1× in Odin. The access pattern is the same random hop for both, so the gain comes only from size: 12 MiB of nodes instead of 32–48 MiB means more of the tree stays in the 1.25 MiB L2 and the roughly 6–8 MiB of usable L3, and fewer 4 KiB pages per hop for the TLB. The gap is modest because both trees are well past L2. Insertion order → DFS order: the same index tree walks about 2.8× faster in Rust after the relayout. The pointer version is about 5.1× behind it. Most of the win comes from layout, and the layout was only possible because the links are indices.

Build plus teardown is about 3.6× cheaper with indices in Rust, about 2.3× in Zig and about 4.3× in Odin. Both versions do the same descent from the root for every key, which is already a cache-missing walk, so the allocator's share is what you see here. Freeing a pointer tree means visiting every node again, and the index tree frees one block. Zig's smp_allocator is the cheapest per-node allocator of the three, and Odin's calloc-plus-alignment path, which turns each node into a 48-byte chunk, is the most expensive. Chapter 6 covers allocators. For now the lesson is simply to make fewer allocations.

What the generation check costs

A handle lookup does more than array[i]: a bounds check, a compare and a liveness test. The last part of the benchmark does 220 random lookups both ways over the same 220 u64 values, once into a plain array and once through pool handles, with the same random order and the same checksum.

The pool is about 3.8× slower in Rust here. Do not read that as "generations are expensive". Each lookup is an independent random access, the loop has plenty of memory-level parallelism, and what grew is the bytes per element: the value, the generation, the state tag or flag, and padding to 8. A value 8 bytes wide is close to the worst case for overhead. With a 64-byte component the slot would add about 25% instead of 200%. If lookups dominate, do what Bitsquid did: move the generations into their own dense array (one byte per slot there), so the check reads a small hot array and the values stay in theirs. When you iterate rather than look up, skip handles altogether and walk the array.

Caveats, and when to keep the pointer

  • An index needs its array. A pointer can be followed on its own. An index means nothing without knowing which array it belongs to. Code that passes references across many unrelated containers, or into a library, may be clearer with pointers. Typed indices help, but they do not carry the base address.
  • 232 is a limit. Four billion elements is plenty for a compiler or a game, but not for every database. Choose the index width on purpose and check for overflow. Rust's u32::try_from(...).expect always checks. Zig's @intCast checks in -O debug and -O safe but not in -O fast. Odin's u32(x) truncates silently, so the Odin program would need an explicit assert to handle more than 232 nodes.
  • Indices hide bugs a pointer would expose. A stale pointer may crash. A stale index reads valid, wrong data. Use plain indices only when lifetimes are simple (build once, free all at once, as with the tree and with ASTs), and use generations when things come and go.
  • Generations wrap. 8 bits wrap after 256 reuses of a slot, 16 bits after 65,536. Use 32 bits, retire exhausted slots (Weissflog), or delay reuse (Bitsquid).
  • The pointer you resolve is temporary. Growing the array moves the slots. Use storage that never moves (a large virtual-memory reservation, fixed-size blocks, Odin's xar) if you need stable addresses as well as handles. Gray's conclusion leans that way: holes, permanent pointers, and one big VM reservation or 16 KiB blocks[8].
  • Most of the speed is layout. The 1.6× to 2.1× from smaller nodes is real, but the larger gain came from walking the nodes in memory order. Indices made that possible; they did not do it on their own.

Store links as typed 32-bit indices into arrays you own, add a generation when slots are reused, and then use the freedom indices give you to put the data in the order you read it.

Exercises

A Zig node is struct { a: *Node, b: *Node, c: *Node, tag: u8 }. What are its size and alignment, and what are they with enum(u32) indices? How many fit in a 64-byte line in each case?

With pointers: 24 B of pointers plus 1 B of tag, rounded up to the 8-byte alignment, so 32 B with align 8, and two per line. With indices: 12 B plus 1 B, rounded up to align 4, so 16 B, and four per line. The tag's padding shrinks from 7 bytes to 3 because the alignment dropped as well as the link size.

How big is Option<Option<NodeId>>? Would the answer change if NodeId used the representation of rustc's newtype_index! instead of NonZeroU32?

8 bytes. NonZeroU32 has exactly one spare bit pattern, 0, and the inner Option uses it for None; the outer one has no niche left, so it needs a separate tag, padded to 4-byte alignment. A newtype_index! type reserves every value above 0xFFFF_FF00, about 255 spare patterns, so each nested Option takes the next one and the whole thing stays 4 bytes.

In the pool figure, after the story ends, which handle would a pool without generations return for the third deref orc, and why is that worse than a crash?

It would return the rat now in slot 0. The program keeps running with wrong data, and the bug shows up far from its cause: a monster attacks the wrong target, or a save file references the wrong item.

Bitsquid's ids have 8 generation bits and wait for 1024 free indices before reusing one. How many entities must be created and destroyed before one id can repeat? What changes if the free list is a LIFO stack as in this chapter's pool?

256 × 1024 = 262,144 creations (Frykholm's own number[6]). With a LIFO stack and no minimum, one entity created and destroyed in a loop reuses the same slot every time, so its generation wraps after 256 iterations. That is why 8-bit generations need a delay and 32-bit generations can use a stack.

Change Pool to keep generations in a separate Vec<u32> (or []u32, [dynamic]u32) next to the values. Which benchmark should improve, and which operation becomes two cache misses instead of one?

A loop that only checks is_valid reads a dense 4-byte array and gets faster. A full get that also reads the value now touches two arrays, generation then value, so it can miss twice. In Rust, storing values without an Option/enum per slot needs MaybeUninit and therefore unsafe, which this book avoids forbid outside std::arch, so keep the enum or store Option<T>.

You need to delete particles fast and iterate them every frame, and gameplay code holds references to a few of them. Which deletion strategy, and which extra structure?

Swap-and-pop for dense iteration, plus an id → index table (a pool of indices with generations) for the few external references. When a particle moves into a hole, update its entry in the table. Together that is a sparse set, which is Chapter 9's subject.

Run the benchmark with N = 4096 (--quick). Why do pointers and indices walk at nearly the same speed there, and sometimes the pointer tree wins?

4096 nodes take roughly 100 to 200 KiB as pointer nodes and 48 KiB as an array. Both fit in L2 (1.25 MiB), so neither walk misses much. Then instruction details dominate: the index walk computes base + 12·i and in Rust also subtracts the +1. At these sizes the layout difference has no cache effect to show.
