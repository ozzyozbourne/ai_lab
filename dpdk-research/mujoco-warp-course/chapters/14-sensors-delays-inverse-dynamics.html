    Part III · Chapter 14

    Sensors, Delays and Inverse Dynamics

    A robot never sees qpos. It sees an IMU, joint encoders, a laser, a touch pad, and all of them a little late. This chapter shows where MJWarp computes each of its 48 sensor types, how to slice d.sensordata for thousands of worlds, how cutoffs, sampling intervals and delays change what you read, and how mjw.inverse runs the equations of motion backwards to give you the torques of a whole trajectory in one launch.

    Advanced About 110 min· Prerequisites: Ch 12, Ch 13 (also uses Ch 7 and Ch 11)

    You will learn

    • Which sensors sensor_pos, sensor_vel and sensor_acc compute, and how to read sensordata by address in every world.
    • The full catalogue from SensorType: IMU, magnetometer, rangefinder data specs (RayDataField), collision and contact sensors (ConDataField), tactile, energy, clock.
    • What cutoff, interval and delay do, and how the history ring buffer in history.py works, slot by slot.
    • How to compute inverse dynamics, check the qfrc_inverse identity, and get exact trajectory torques with one world per time sample (the Part III project).

    Before you start: recap

    • forward runs position, velocity, actuation, acceleration and the constraint solver, in that order; step = forward + integrator (Ch 7 §2).
    • The equation of motion is M\ddot q + c = \tau + J^\top f; qfrc_bias is c, the RNE gives it, and the gravity trick sets the world body's acceleration to -g (Ch 11).
    • Passive forces (springs, joint damping) land in qfrc_passive, actuators in qfrc_actuator; rne_postconstraint recomputes body accelerations and forces with the constraint forces (Ch 12).
    • MuJoCo's Euler is semi-implicit and integrates joint damping implicitly unless eulerdamp is disabled; under RK4, sensors come from the start of the step (Ch 13 §3, §4).
    • Batched model fields are read as x[worldid % x.shape[0]], so a length-nworld array gives every world its own value (Ch 10 §2).
    • step1 / step2 split a step so a policy can read sensors and write ctrl in between (Ch 8 §7).

    1Three sensor stages and one array

    A sensor is a measurement you declare in the MJCF <sensor> block. The compiler gives each one a type (joint position, accelerometer, rangefinder, ...), a size called its dim (1 for a joint angle, 3 for an acceleration vector, 4 for a quaternion), and an address: the column where its values start in one flat array. MJWarp keeps that array for all worlds at once:

    FieldShapeMeaning
    d.sensordata(nworld, nsensordata)every sensor's values, one row per world
    mjm.sensor_adr(nsensor,)first column of each sensor (same in every world)
    mjm.sensor_dim(nsensor,)number of columns of each sensor
    mjm.sensor_needstage(nsensor,)the earliest pipeline stage whose results the sensor needs: POS, VEL or ACC

    A sensor is only as fresh as the quantities it reads. A joint angle needs nothing but qpos, so it can be computed right after the position stage. A gyro needs the body velocity, so it must wait for the velocity stage. A touch sensor sums contact forces, and those exist only after the constraint solver. So forward.py::_forward calls three sensor functions, each at the first moment it can:

    fwd_position(m, d, factorize=False)
if not skip_sensor:
  d.sensordata.zero_()          # every world, every column
  sensor.sensor_pos(m, d)
_energy_pos(m, d)

fwd_velocity(m, d)
if not skip_sensor:
  sensor.sensor_vel(m, d)
_energy_vel(m, d)

...                             # control callback, fwd_actuation, fwd_acceleration
solver.solve(m, d)
if m.opt.run_rne_postconstraint or (
  not skip_sensor and not (m.opt.disableflags & DisableBit.SENSOR) and m.sensor_rne_postconstraint
):
  smooth.rne_postconstraint(m, d)
if not skip_sensor:
  sensor.sensor_acc(m, d, skip_rne_postconstraint=True)

    Figure 1 shows the same order as a timeline. The three blue taps are the moments when sensor values are written. Hover or tap a part to read what happens there.

    Four consequences follow directly from this code, and they explain most "my sensor reads the wrong value" surprises:

    1. Sensors describe the state before integration. mjw.step calls forward and only then the integrator. After a step, d.qpos is at time t+h but d.sensordata still describes time t. Call mjw.forward(m, d) if you need sensors of the current state (Examples 14.2, 14.3 do this).
    2. The whole array is zeroed first. d.sensordata.zero_() runs for every world before sensor_pos. A sensor that writes nothing (a touch pad with no contact, a contact sensor with no match) reads exactly 0.
    3. The SENSOR disable flag empties the array. Each of sensor_pos, sensor_vel and sensor_acc starts with if m.opt.disableflags & DisableBit.SENSOR: return. The zeroing above still happens, so with <flag sensor="disable"/> every column is 0, and rne_postconstraint is skipped too (unless you set opt.run_rne_postconstraint). Use it to measure what sensors cost, with one catch in 4.0.1: if the model also enables the energy flag and has e_potential / e_kinetic sensors, d.energy stays at 0, because _energy_pos leaves energy to sensors that now return early (§7).
    4. step1 / step2 split the taps. step1 zeroes all of sensordata, then runs sensor_pos and sensor_vel and the control callback; step2 runs actuation, the solver and sensor_acc. A policy that runs between them can read every pos- and vel-stage sensor of the current state, but every acc-stage column (touch, contact, accelerometer, force, torque, actuatorfrc, ...) reads 0 until step2's sensor_acc fills it. Do not feed those columns to a policy that runs between the two calls.

    Source

    mujoco_warp/_src/forward.py · _forward, step1, step2; mujoco_warp/_src/sensor.py · sensor_pos, sensor_vel, sensor_acc. All three are also exported as mjw.sensor_pos, mjw.sensor_vel, mjw.sensor_acc, so a custom pipeline can call them itself.

    Going deeper: user sensors and the sensor callback

    A <user> sensor has a declared dim and needstage and no built-in formula. At the end of each stage function MJWarp runs if m.callback.sensor: m.callback.sensor(m, d, Stage.POS) (or Stage.VEL, Stage.ACC), with Stage from mujoco_warp._src.types private API. Your callback launches its own kernel that writes the user sensor's columns. The callback catalogue is owned by Ch 26; control callbacks were introduced in Ch 8 §9.

    2The sensor catalogue

    MJWarp supports a sensor type exactly when it appears in the enum mujoco_warp._src.types.SensorType private API. io.py::put_model checks every mjm.sensor_type against that enum and raises NotImplementedError for anything else, and a separate check raises "Sensor plugins not supported.". Example 14.1 builds one model with one sensor of every supported type, runs forward once, and prints the catalogue: name, type, stage, address, dim, and which launch list put_model sorted it into.

    How put_model sorts sensors into launches

    A GPU kernel is fastest when every thread does similar work, so put_model does not launch one kernel per sensor. It builds index lists from mjm.sensor_needstage and mjm.sensor_type, and each stage function launches one kernel per list, over (nworld, len(list)) threads:

And RANGEFINDER, TACTILE and USER sit in the generic lists too (sensor_pos_adr, sensor_vel_adr, sensor_acc_adr), as the table says, but _sensor_pos, _sensor_vel and _sensor_acc have no branch for these types: their thread writes nothing, and ray.rays, _sensor_tactile or the user callback fills the columns.

    3Acceleration-stage sensors: an IMU on a box

    An IMU combines three sensors you will use in almost every robot model. Each one is a short wp.func in sensor.py, and each returns its vector in the site frame: multiply a world vector by R^\top, where R is site_xmat.

    SensorStageFormula (site frame)Function
    gyrovelR^\top \omega_gyro
    magnetometerposR^\top B, B = opt.magnetic_magnetometer
    accelerometeraccR^\top(a - g) plus a velocity correction_accelerometer

    The accelerometer is the interesting one. A real accelerometer cannot feel gravity directly: in free fall it reads 0, and lying still on a table it reads +9.81 upward, because the table pushes it up. That quantity is called specific force, a - g. MJWarp gets it for free from the gravity trick of the RNE (Ch 11): the world body is given the acceleration -g, so every body's cacc already contains the -g offset. _accelerometer shifts cacc from the subtree centre of mass to the site, rotates it into the site frame and adds the term \omega_{\text{site}} \times v_{\text{site}} that converts the spatial acceleration into the classical acceleration of a point:

    dif = site_xpos_in[worldid, objid] - subtree_com_in[worldid, body_rootid[bodyid]]
ang = rotT @ cvel_top
lin = rotT @ (cvel_bottom - wp.cross(dif, cvel_top))
acc = rotT @ (cacc_bottom - wp.cross(dif, cacc_top))
correction = wp.cross(ang, lin)
return acc + correction

    Why is it an acc sensor that needs rne_postconstraint? A box resting on the floor has zero acceleration only because the contact force cancels gravity. The plain RNE in fwd_velocity knows nothing about contact forces; rne_postconstraint recomputes cacc and cfrc_int after the solver, with qfrc_constraint included. That is why put_model sets m.sensor_rne_postconstraint when the model has an accelerometer, force, torque, framelinacc or frameangacc sensor, and why those sensors cost an extra pass.

    Recall from Ch 2

    MuJoCo quats are (w,x,y,z); Ch 2 §3. Example 14.2 rotates the box with [cos 45°, sin 45°, 0, 0]: 90° about x.

    Read the three worlds: the resting box reads (0, 0, 9.81); on its side, the site's y-axis points up, so the reading moves to y; in free fall it reads 0 while the gyro shows the spin (2, 0, 5) rad/s. The spin is the body-frame angular velocity we set in qvel[3:6]; the box is a cube, so its inertia is the same about every axis and a torque-free spin stays constant. The magnetometer equals R^\top B to the last bit.

    4Reading sensordata by address

    Because addresses are the same in every world, a sensor is a column slice of the 2-D array: d.sensordata[:, adr:adr + dim] gives that sensor in every world at once. Looking addresses up by name each time is error-prone, so the running project module gets a helper. It reads the compiled MjModel, not the device model, because names live only on the host:

    # examples/14-sensors-delays-inverse-dynamics/my_env_step14.py (new in Ch 14)
def sensor_slices(mjm):
    """Return {sensor name: (adr, dim)} so d.sensordata[:, adr:adr + dim] is that sensor.

    Unnamed sensors get the key "sensor<i>". The addresses come from the compiled MjModel
    (mjm.sensor_adr, mjm.sensor_dim) and are the same in every world.
    """
    out = {}
    for i in range(mjm.nsensor):
        name = mujoco.mj_id2name(mjm, mujoco.mjtObj.mjOBJ_SENSOR, i) or f"sensor{i}"
        out[name] = (int(mjm.sensor_adr[i]), int(mjm.sensor_dim[i]))
    return out

    Later chapters use it to build observation kernels: Ch 26 packs these slices on the device without a round trip, and Ch 30 builds the RL environments on top. Example 14.3 runs the double pendulum PENDULUM with a different shoulder torque per world and prints every slice.

    Tip: stay on the device

    d.sensordata.numpy() copies the whole (nworld, nsensordata) array to the host. That is fine for a printout, but inside a training loop read the slice in a Warp kernel (Ch 26) or view it zero-copy as a torch tensor (Ch 28). A wp.array slice like d.sensordata[:, 2:5] is not contiguous, which is one more reason to gather in a kernel.

    5Sensors built on rays and collisions

    Four sensor families reuse machinery from other parts of the engine. They are the ones whose output layout you choose in the MJCF, and the ones that need buffer room.

    Rangefinders and the RayDataField mask

    A <rangefinder> casts a ray and reports what it hits. Attached to a site, it casts one ray from the site origin along the site's z-axis. Attached to a camera, it casts one ray per pixel of the camera's resolution. The data="..." attribute picks the outputs per ray, and the compiler stores the choice as a bitmask in mjm.sensor_intprm[i, 0], one bit per mjw.RayDataField member:

    bitRayDataFieldvaluesmeaning (from _sensor_rangefinder)
    0DIST1distance to the first hit, -1 when nothing is hit
    1DIR3unit ray direction (zeros on a miss)
    2ORIGIN3ray origin
    3POINT3hit point = origin + dist · dir (zeros on a miss)
    4NORMAL3surface normal at the hit
    5DEPTH1for cameras: distance along the optical axis (-dist · dir · cam_z); for sites: equal to dist; -1 on a miss

    The kernel computes a per-ray stride (the sum of the chosen sizes) and writes the requested fields in that bit order, each clamped by cutoff if one is set. So the sensor dim is \text{nrays} \times \text{stride}. Build a spec and watch the layout:

    Rangefinder data-spec builder Computed from the rules above

    Example 14.4 checks the rule on a real model: a site rangefinder with data="dist point normal" (mask 0b011001, dim 7) on a probe that moves to a different pose in each world, over a floor and a raised block, plus a 4x3 camera rangefinder with data="dist" (dim 12).

    Pitfall: rays ignore the sensor's own body

    put_model stores, for every ray, the body that carries the site or camera (m.sensor_rangefinder_bodyid), and sensor_pos passes it to ray.rays as the body to exclude. A camera declared directly in <worldbody> belongs to body 0, so its rays skip every static world geom, the floor included, and read -1. That is why Example 14.4 mounts its camera on a static body mast.

    Rays are a black box here

    The ray caster itself (mjw.ray, mjw.rays, geom-group filters, the BVH, lidar) is owned by Ch 27. The comment in sensor_pos says # TODO(team): use BVH for high-resolution camera rangefinders: in 4.0.1 a camera rangefinder tests every ray against the geoms directly, so keep its resolution small.

    Collision sensors: distance, normal, fromto

    <distance>, <normal> and <fromto> (types GEOMDIST, GEOMNORMAL, GEOMFROMTO) measure the closest approach of two geoms or two bodies. They do not have their own geometry code. put_model marks their geom pairs in the second column of m.nxn_pairid (nxn_pairid[pair][1] is the collision-sensor id, -1 otherwise), so the broadphase keeps those pairs even when contype/conaffinity would filter them. The narrowphase writes their results into the normal contact pool with the ContactType.SENSOR bit. In sensor_pos, _sensor_collision (one thread per contact slot) copies distance, position and normal of SENSOR contacts into a scratch array, and _sensor_pos picks the smallest distance per sensor:

    • the search starts at dist = sensor_cutoff, so pairs farther apart than cutoff read exactly cutoff, and normal/fromto read zeros;
    • a negative distance means penetration;
    • fromto is never clamped by cutoff (_write_scalar / _write_vector skip GEOMFROMTO).

    The normal flips between step 0 and step 300. That is not a bug: the reported vector points along the segment from geom 1 to geom 2. While the ball is above the floor, the ball's closest point is above the floor's, so the segment points down; once the ball sinks 0.4 mm into the floor, its closest point is below the floor's and the segment points up. MuJoCo C gives the same vectors.

    Pitfall: collision sensors use contact slots

    SENSOR contacts are written into the same pool as real contacts and count against naconmax. A scene sized exactly for its physical contacts can overflow once you add distance sensors (overflow decoding: Ch 9 §7). Example 14.5 passes nconmax=8 and checks d.overflow.

    Touch and contact sensors

    Both are acc sensors because they read efc.force, the result of the solver. <touch site="..."/> is a scalar: the sum of normal forces of the site body's contacts whose force ray passes through the site volume (so the site should enclose the contact patch). <contact> is the general tool. It matches contacts by geom, body, subtree or site on each side, keeps up to num of them (sorted or reduced by reduce="mindist|maxforce|netforce"), and writes, for each slot, the fields chosen by data="..." as a mjw.ConDataField bitmask in sensor_intprm[i, 0] (the reduce mode is in sensor_intprm[i, 1]):

    ConDataFieldvaluesmeaning
    FOUND1number of matching contacts (repeated in every slot)
    FORCE, TORQUE3 + 3contact force and torque in the contact frame (normal component first)
    DIST1penetration distance
    POS, NORMAL, TANGENT3 + 3 + 3contact point and frame axes, signed so they point away from the matched object
    LINVEL, ANGVEL3 + 3relative velocity in the contact frame (put_model rejects them for models with flexes)

    Matching first collects candidate contacts per sensor into a scratch array of size m.opt.contact_sensor_maxmatch (default 64; set it with a custom <numeric name="contact_sensor_maxmatch" data="..."/>, read in io.py). If a sensor matches more, the extras are dropped and, with warn_overflow, a warning tells you to increase it.

    Four box-corner contacts share the weight equally (2.4525 N each for 1 kg), touch and the contact-sensor sum both equal m g in every world, and the normal is (0, 0, -1): pointing away from the matched body box, into the floor.

    Going deeper: tactile sensors

    <tactile geom="..." mesh="..."/> turns every vertex of a mesh into a taxel. It is a vel sensor with dim = 3 × nvert: for each taxel, the penetration depth into the touching geom (from that geom's SDF) and two tangential slip speeds. sensor_vel launches _mark_tactile_contacts (one thread per contact, marks which geoms touch the pad's weld body), _collect_tactile_contacts_kernel and then _sensor_tactile over the taxels. The shipped model test_data/collision_sdf/tactile.xml is a full example. In Example 14.1 the pad is a builtin sphere mesh with 12 vertices, so its dim is 36.

    6Cutoff and interval sampling

    Real sensors saturate and real sensors sample at their own rate. MJWarp models both per sensor.

    Cutoff (cutoff="c", stored in m.sensor_cutoff) clamps the written value. sensor.py::_write_scalar and _write_vector look at the sensor's datatype: REAL values are clamped to [-c, c], POSITIVE values (touch, for example) to \min(v, c). A cutoff of 0 means no clamping. Rangefinder fields are clamped one by one with _clamp_real; GEOMFROMTO is exempt, and for distance sensors cutoff is also the search radius (§5).

    Interval (interval="period phase", stored in m.sensor_interval) makes a sensor update only once per period and hold its value in between, like a 33 Hz camera inside a 100 Hz simulation. The held value lives in the sensor's history buffer (§8), so the sensor needs nsample > 0; the delay machinery skips sensors without a buffer. history.py uses the buffer's first slot, the user slot, to store the time of the last sample, time_prev:

    # history.py::_insert_sensor_history_stage   (after the sensor was computed fresh)
if period > 0.0:
  time_prev = history_out[worldid, buf_offset]  # user slot stores time_prev
  if time_prev + period <= t:
    history_out[worldid, buf_offset] = time_prev + period
    _history_insert_vector(worldid, buf_offset, nsample, dim, t, sensordata_in, sensor_adr[sid], history_out)

# history.py::_apply_sensor_delay_kernel     (runs first: decides what sensordata shows)
if delay > 0.0:
  _history_read_vector(sensor_adr[sid], history_in, worldid, buf_offset, nsample, dim, t - delay, interp, sensordata_out)
elif period > 0.0:
  time_prev = history_in[worldid, buf_offset]  # user slot
  if time_prev + period > t:                   # not a sample time: show the held value
    _history_read_vector(sensor_adr[sid], history_in, worldid, buf_offset, nsample, dim, t, interp, sensordata_out)

    Note the comment in the source: "Revisit always-compute decision for computationally expensive sensors with interval/period (e.g., raytracers)". In 4.0.1 an interval sensor is still computed every step and then overwritten by the held value, so an interval does not save compute. At reset (reset_history), time_prev is set to phase, or to -period when phase is 0, so the first sample happens at t = 0.

    Pitfall: float32 time moves an interval sample by one step

    d.time is a float32 array in MJWarp; MuJoCo C uses double. After six steps of 0.01 s MJWarp's time is 0.059999995, while time_prev + period is 0.06 in float32 (0.059999999). The test time_prev + period <= t is False, so MJWarp takes that sample one step later (at 0.07 s) than C (at 0.06 s): the only difference in Example 14.7. If exact sample times matter, choose periods that are not multiples of dt on the edge, or add a small phase.

    7Energy, and which moment sensors describe

    d.energy has shape (nworld,) of wp.vec2: [E_\text{pot}, E_\text{kin}] per world. It is filled only when the model enables it, <option><flag energy="enable"/></option> (mjw.EnableBit.ENERGY). sensor.py::energy_pos adds gravitational potential energy and the potential energy of joint, tendon and flex springs; energy_vel computes \tfrac12 \dot q^\top M \dot q. Both are exported (mjw.energy_pos, mjw.energy_vel). Example 14.3 printed them: about 20 J of potential energy (the pendulum's zero is the world origin, 1.5 m below the hinge) and a small kinetic energy.

    The energy code below is quoted from the 4.0.1 wheel, the version the course pins; the dev tree at commit 8f5b9f1 changed it, and the version note after the RK4 callout shows how.

    # forward.py (4.0.1 wheel)
def _energy_pos(m: Model, d: Data):
  if m.opt.enableflags & EnableBit.ENERGY:
    if m.sensor_e_potential == 0:  # not computed by sensor
      sensor.energy_pos(m, d)
  else:
    d.energy.zero_()

    The e_potential and e_kinetic sensors are a second route: sensor_pos calls energy_pos and energy_vel itself when the model has them (kinetic energy only needs qvel and the mass matrix, both ready after the position stage), then copies the values into sensordata. Reading the code above, with the flag off _energy_pos then zeroes d.energy again, so the sensors are the way to get energy without enabling the flag. The reverse case is a trap in 4.0.1: with the energy flag on, <flag sensor="disable"/> and energy sensors in the model, sensor_pos returns before computing energy and _energy_pos skips it because the sensors exist, so d.energy stays [0, 0] while C MuJoCo still fills it.

    Checked on CPU

    A quick check on the CPU box (a one-hinge model with <e_potential/> and <e_kinetic/>, energy flag off, qvel = 1, one mjw.forward): sensordata = [9.81, 0.04425] and d.energy = [0, 0]. MuJoCo C reports the same sensor values but also fills mjd.energy = [9.81, 0.04425]. So in MJWarp read energy from the sensors, or enable the flag.

    Recall from Ch 13

    Under RK4, rungekutta4 runs three more _forward(m, d, skip_sensor=True) calls at perturbed states, so sensordata keeps the values of the step's first forward (time t), while d.energy is recomputed in each stage and ends up describing the last one (Ch 13 §4, Example 13.6). In 4.0.1 that holds only for models without energy sensors: with e_potential / e_kinetic sensors, _energy_pos leaves the work to sensor_pos, which the stages skip, so d.energy also keeps its time-t value.

    Version note: energy at 8f5b9f1

    The dev tree at commit 8f5b9f1 adds a skip_sensor argument and computes energy itself whenever the sensors will not:

    # forward.py at 8f5b9f1
def _energy_pos(m: Model, d: Data, skip_sensor: bool = False):
  if m.opt.enableflags & EnableBit.ENERGY:
    if m.sensor_e_potential == 0 or (m.opt.disableflags & DisableBit.SENSOR) or skip_sensor:  # not computed by sensor
      sensor.energy_pos(m, d)
  else:
    d.energy.zero_()

    _energy_vel changes the same way. There, RK4 stages always recompute d.energy, and the sensor-disabled case fills it too.

    8Delays: history ring buffers

    Motors respond late (communication, filtering) and sensors report late (processing). A policy trained without delays often fails on hardware that has them, so MuJoCo 4 and MJWarp model delays in the engine. Two attributes turn them on:

    <motor joint="slide" delay="0.03" nsample="5"/>          <!-- ctrl acts 0.03 s late -->
<jointpos joint="slide" delay="0.02" nsample="4"/>       <!-- reading is 0.02 s old -->

    nsample is the number of past samples kept; delay must fit inside them (nsample · dt must be at least the delay). Each delayed actuator and sensor gets a history buffer: a ring buffer of (time, value) pairs inside one flat Data array.

    FieldShapeMeaning
    d.history(nworld, nhistory)all buffers of one world, back to back
    m.actuator_history, m.sensor_history(*, n) vec2i(nsample, interp); interp 0 = zero-order hold, 1 = linear, 2 = cubic (Catmull-Rom)
    m.actuator_historyadr, m.sensor_historyadr(*, n)where each buffer starts in a d.history row
    m.actuator_delay, m.sensor_delay(*, n)delay in seconds, batched: one per world if you like (Ch 10)

    * = 1 or nworld (a batchable Model field, Ch 10); n = nu for the actuator fields, nsensor for the sensor fields.

    Pitfall: a delay longer than the buffer saturates silently

    The compiler does not check nsample · dt ≥ delay. If the delay is longer, the read at t - \text{delay} falls before the oldest sample, and _history_read_scalar/_history_read_vector return the oldest value (# extrapolate before oldest in history.py). The effective delay is then capped at about nsample steps: with nsample="5" and dt = 0.01, a delay of 0.06 or 0.08 acts exactly like 0.05 (MJWarp and C agree). Size nsample from the largest delay you plan to use, including per-world randomised delays.

    One buffer is 2 + n + n \cdot \text{dim} floats: [user, cursor, times[n], values[n × dim]]. For the motor above, 2 + 5 + 5 = 12 (nhistory: 12 in Example 14.8). The cursor is the physical index of the newest sample. Code never indexes slots directly; it asks for logical index i (0 = oldest, n-1 = newest) and converts:

    @wp.func
def _history_physical_index(cursor: int, n: int, logical: int) -> int:
  """Convert logical index (0=oldest, n-1=newest) to physical index."""
  return (cursor + 1 + logical) % n

    Two moments of each step touch the buffer:

    1. Read in fwd_actuation: history.read_ctrl_delayed launches _read_ctrl_delayed_kernel over (nworld, nactuator). Each thread queries its buffer at t - \text{delay}: a circular binary search (_history_find_index) finds the bracketing samples and the value is held or interpolated. The actuator uses that ctrl; d.ctrl itself is untouched.
    2. Insert in _advance, just before time moves on: history.insert_ctrl_history writes the current ctrl with timestamp t. A time newer than the newest sample advances the cursor and overwrites the oldest slot.

    Step through it with the real buffer of Example 14.8 (delay 0.03 s, dt 0.01 s, nsample 5, ctrl = 1 from step 0):

    One actuator's ring buffer over six steps

    history.py::_history_find_index / _history_read_scalar / _history_insert_scalarReal buffer from ex8

    The result [0, 0, 0, 1, 1, 1] matches MuJoCo C exactly. The reset buffer explains the zeros: reset_history fills the times with -n \cdot dt, \dots, -dt and the values with 0, as if ctrl had been 0 forever. (For an SO3 actuator with a quaternion ctrl the reset values are the identity quaternion instead.)

    Sensor delays

    Sensors use the same buffers in a different order. In each stage function, history.apply_sensor_delay(m, d, m.sensor_stage_*_adr) runs right after the fresh values are computed. It copies the fresh sensordata aside, overwrites the delayed sensors with the buffer read at t - \text{delay}, then inserts the saved fresh values with timestamp t. Its docstring says this matches MuJoCo C, where the delayed read happens in mj_sensorPos before the insert in mj_advance. The order matches, the place does not: in MJWarp the insert runs inside the stage function, so every call that reaches sensor_pos, sensor_vel or sensor_acc (each forward, each extra forward after a step, each inverse) writes the buffer at the current d.time. A second call at the same time overwrites that sample (the insert finds an exact time match), so an extra forward on an unchanged state is harmless, but a call on a different state at the same time replaces the stored value.

    The delayed reading is exactly 2 steps behind in every world. The read_sensor queries show the interpolation modes: at 0.065 s the delayed sensor looks up 0.045 s, between the 0.04 and 0.05 samples. ZOH returns the older one, 0.04 (times the world's speed); linear returns 0.045.

    Pitfall: read_sensor subtracts the delay for you

    _read_sensor_kernel computes t = time_in[worldid] - delay. Pass the time at which you want to know what the delayed sensor reports, not the time of the measurement you want. To read the fresh value measured at time \tau, pass \tau + \text{delay}.

    9Inverse dynamics

    Forward dynamics answers "given the forces, how does the system accelerate?". Inverse dynamics answers the opposite: "given the state and the acceleration I want, which generalized force produces it?". Rearranging the equation of motion (Ch 11) with every force on the left:

    \underbrace{\tau_\text{applied} + \tau_\text{actuator} + J^\top f_\text{ext}}_{\text{qfrc\_inverse}} \;=\; M\ddot q + c(q,\dot q) - \tau_\text{passive} - \tau_\text{constraint}

    That right-hand side is exactly what inverse.py::_qfrc_inverse computes, one thread per (world, dof):

    qfrc_inverse = qfrc_bias_in[worldid, dofid]
qfrc_inverse += Ma[worldid, dofid]               # M @ qacc, from support.mul_m
qfrc_inverse -= qfrc_passive_in[worldid, dofid]
qfrc_inverse -= qfrc_constraint_in[worldid, dofid]

    Here is the whole public function. It is short enough to read line by line:

    def inverse(m: Model, d: Data):
  """Inverse dynamics."""
  forward.check_discrete(m)
  forward.fwd_position(m, d)
  sensor.sensor_pos(m, d)
  forward.fwd_velocity(m, d)
  sensor.sensor_vel(m, d)

  is_discrete = m.opt.integrator == IntegratorType.DISCRETE
  invdiscrete = (m.opt.enableflags & EnableBit.INVDISCRETE) or is_discrete
  if invdiscrete:
    # save discrete-time qacc and compute continuous-time qacc
    qacc_discrete = wp.clone(d.qacc)
    discrete_acc(m, d, d.qacc)

  if is_discrete:
    derivative.eff_actuation(m, d)
    constraint.regularize_constraint(m, d)

  inv_constraint(m, d)
  smooth.rne(m, d)
  smooth.tendon_bias(m, d, d.qfrc_bias)
  sensor.sensor_acc(m, d)
  ...                    # discrete: eff_mul_m + _qfrc_inverse_discrete; else: mul_m + _qfrc_inverse
  if invdiscrete:
    # restore discrete-time qacc
    wp.copy(d.qacc, qacc_discrete)

    What to notice:

    • It computes sensors too, all three stages, at the given acceleration. So inverse is also how you evaluate an accelerometer or force sensor for an acceleration you prescribe. Unlike _forward it does not call d.sensordata.zero_() first.
    • Pitfall: it writes the delay buffers. On a model with delayed or interval sensors, the sensor stages inside inverse run apply_sensor_delay (§8): they insert the values at the given state into d.history with timestamp d.time, and sensordata returns the delayed values, not the fresh ones. With "worlds as time samples" each world's buffer then holds one arbitrary sample. Run inverse on a separate Data, or call mjw.reset_history(m, d) afterwards (it resets every world's buffers to the initial state).
    • No actuation, no solver iterations. ctrl and qfrc_applied are not read. inv_constraint creates a small InverseContext and calls solver.init_context, which evaluates J\ddot q - a_\text{ref} and the constraint forces it implies in one pass.
    • No @event_scope. forward and step are decorated, inverse is not, so an EventTracer (Ch 7, Ch 25) shows only its inner stages, not an inverse entry.
    • The 4.0.1 wheel vs the dev tree. At commit 8f5b9f1 the dev tree calls fwd_velocity(m, d, skip_com_vel=...) here; the 4.0.1 wheel calls plain fwd_velocity(m, d). Same result, the dev tree skips work.

    Version note

    EnableBit in 4.0.1 lists ENERGY, INVDISCRETE and SLEEP; its comment says # unsupported: OVERRIDE, FWDINV, ISLAND, DIAGEXACT. So C MuJoCo's automatic forward/inverse comparison (fwdinv) is not available: you run both calls yourself, as in Example 14.10.

    The qfrc_inverse identity

    If you run forward and then inverse on the same state, inverse sees forward's qacc and must return the forces that forward used: qfrc_applied + qfrc_actuator (plus J^\top xfrc_applied, zero here). That is a strong test of a model and of the engine, and Example 14.10 runs it on the PLAYGROUND scene with contacts in every world.

    The identity holds to 9\cdot10^{-4} while constraint forces reach 183. That residual is not float32 noise alone: forward stops its iterative solver at a tolerance, so its efc.force is slightly off the exact optimum, and inverse evaluates the forces exactly for the qacc it is given. The comparison with mj_inverse is 1.6\cdot10^{-4} relative to the constraint force: MJWarp's float32 pipeline vs C's double.

    INVDISCRETE: inverting what the integrator actually does

    The plain formula is a continuous-time statement. But your simulation is discrete, and the integrators of Ch 13 do not apply qacc as-is. MuJoCo's Euler, for example, treats joint damping implicitly: the velocity update is (M + hD)\,\Delta\dot q = h\,M\ddot q. With mjw.EnableBit.INVDISCRETE set in m.opt.enableflags, inverse first converts the qacc you give it, read as "the acceleration the integrator should realise", into the continuous acceleration that produces it. That is inverse.py::discrete_acc:

    integratorwhat discrete_acc does
    EULER\ddot q_c = M^{-1}(M + h\,D)\,\ddot q with D the damping derivative (_qfrc_eulerdamp); a plain copy if EULERDAMP or DAMPER is disabled
    IMPLICITmultiply by M - h\,\partial f/\partial \dot q (scratch implicit_qlu), then solve with M
    IMPLICITFASTmultiply by the symmetric derivative matrix from deriv_smooth_vel, then solve with M
    DISCRETEnothing: qacc already is the discrete step map, INVDISCRETE is implied (Ch 23)
    RK4NotImplementedError("discrete inverse dynamics is not supported by RK4 integrator")

    After the forces are computed, the original qacc is restored. m.opt.enableflags is a plain Python int read on the host when inverse is called, so you can flip it between calls (Example 14.12 does) without recompiling.

    One world per time sample

    Inverse dynamics has no time dependence: every sample of a trajectory is an independent problem. That makes it a perfect fit for the batched layout. Put sample k of the trajectory in world k, and one mjw.inverse call returns the torques of the whole trajectory.

    The derivatives you feed in matter. Example 14.11 tries two ways for a sine trajectory of the double pendulum. Method A uses the exact derivatives of the sines. Method B uses finite differences that match the semi-implicit Euler update of Ch 13, \dot q_{k+1} = \dot q_k + h\,\ddot q_k, q_{k+1} = q_k + h\,\dot q_{k+1}:

    \dot q_k = \frac{q_k - q_{k-1}}{h}, \qquad \ddot q_k = \frac{\dot q_{k+1} - \dot q_k}{h}

    Then both torque tables are replayed open loop: a tiny kernel copies row k of the table into qfrc_applied before step k, two worlds at once.

    Look at the numbers before the lesson. The two torque tables differ by only O(h): at most 0.004 N m from sample 1 on. The 0.320 N m line is sample k = 0 alone, where qd_b[0] is copied from qd_a[0], so qdd_b[0] contains the jump from the analytic to the finite-difference velocity. Tables this close still replay very differently (RMS error 3.8\cdot10^{-3} against 1.4\cdot10^{-7} rad), because an open-loop replay adds up every small torque error.

    The lesson: inverse dynamics is exact for the accelerations you give it. If those are the continuous derivatives, the torques are right for the continuous system, and the discrete simulation drifts by the integrator's error. If they are consistent with the integrator, the replay is exact. The pendulum has no joint damping, so method B alone is enough; the next section adds damping, where INVDISCRETE becomes necessary.

    Open-loop replay is the baseline. On hardware you would add feedback (a PD term around the reference) and the delays of §8. Trajectory optimisation and system identification on top of many parallel worlds are the topic of Ch 29.

    11Check yourself

    Quiz

    In which stage function is a <touch> sensor computed?

    Touch sums normal forces from efc.force, which exists only after the constraint solver, so _sensor_touch runs in sensor_acc.

    After mjw.step(m, d) with the Euler integrator, which time does d.sensordata describe?

    step = forward (which computes sensors) + integrator. Call mjw.forward for sensors of the new state.

    A jointvel sensor has cutoff="0.05" and the joint moves at 0.08. What does it read?

    REAL datatype: wp.clamp(value, -cutoff, cutoff) in _write_scalar (Example 14.7).

    What is the dim of <rangefinder camera="eye" data="dist normal"/> on a 8x6 camera?

    48 rays × stride (1 dist + 3 normal) = 192.

    A motor has delay="0.03" nsample="5" and dt=0.01. You set ctrl=1 before step 0. At which step does actuator_force first become 1?

    At step 3, t - 0.03 = 0 hits the sample inserted at t = 0: [0, 0, 0, 1, 1, 1] (Example 14.8).

    Which physical slot holds logical index 0 (the oldest sample) when cursor = 2 and n = 5?

    (cursor + 1 + logical) % n = (2 + 1 + 0) % 5 = 3.

    You call mjw.inverse right after mjw.forward. What should qfrc_inverse equal?

    Inverse recovers the external generalized force that forward used (Example 14.10).

    Why does Example 14.12 turn on EnableBit.INVDISCRETE?

    discrete_acc converts the discrete qacc with (M + hD); the replay error falls from 3e-2 to 3e-7 rad.

    Part III review (Ch 11-14)

    What goes wrong if you solve with a qLD that was factored for an older qpos?

    factor_m writes qLD; solving with an old qLD gives wrong qacc (Ch 11 §9).

    Which array holds joint spring and damping forces?

    Passive forces (springs, damping, gravcomp, fluid) are summed in qfrc_passive (Ch 12).

    What does IMPLICITFAST drop compared with IMPLICIT?

    implicitfast keeps a symmetric matrix and factors with Cholesky; implicit uses the full derivative and an LU (Ch 13).

    Which sensors make forward run rne_postconstraint?

    They read cacc or cfrc_int, which must include constraint forces (m.sensor_rne_postconstraint, §2-§3).

    Under RK4, where do the sensor values after a step come from?

    Stages call _forward(m, d, skip_sensor=True); only d.energy is recomputed per stage (Ch 13 §4). In 4.0.1 that is true only for models without energy sensors; at 8f5b9f1 _energy_pos/_energy_vel take skip_sensor and always recompute.

    You want torques for a 1000-sample trajectory. What is the batched way?

    "Worlds as time samples" (Examples 14.11, 14.12).

    13Summary

    Key takeaways

    • forward zeroes d.sensordata, then writes sensors at three taps: sensor_pos after the position stage, sensor_vel after the velocity stage, sensor_acc after the solver (and rne_postconstraint when an accelerometer, force, torque or frame-acceleration sensor needs it).
    • After mjw.step, sensors describe the state at the start of the step. The SENSOR disable flag leaves every column at 0.
    • Sensor i is d.sensordata[:, sensor_adr[i] : sensor_adr[i] + sensor_dim[i]] in every world; my_env.sensor_slices(mjm) builds the name map.
    • SensorType covers all 48 MuJoCo sensors except plugins. Rangefinder outputs are a RayDataField mask (dim = rays × stride), contact outputs a ConDataField mask (dim = num × fields); collision sensors use SENSOR contacts in the shared pool.
    • cutoff clamps; interval samples and holds (and in 4.0.1 still computes every step); float32 time can shift a sample by one step.
    • Delays use per-(world, object) ring buffers in d.history: read at t - \text{delay} with a circular binary search, insert at t; physical = (cursor + 1 + logical) % n.
    • mjw.inverse returns M\ddot q + c - \tau_\text{passive} - \tau_\text{constraint}; after forward it equals qfrc_applied + qfrc_actuator. INVDISCRETE inverts the integrator's actual update; one world per time sample gives a whole trajectory's torques in one call.

    Stuck? See Troubleshooting or the course map.
