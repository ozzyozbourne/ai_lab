    Determinism and Reproducibility

    Run the same MJWarp simulation twice on a GPU and the last bits of the numbers can change. A chaotic system then grows those bits into visible differences. This chapter shows exactly where the noise comes from, what m.opt.deterministic really does in mujoco-warp 4.0.1 (less than its name suggests), and how to build runs and tests that are reproducible bit for bit.

    Expert About 75 min· Prerequisites: Ch 19, Ch 20 (Ch 21 recommended)

    You will learn

    • The three sources of run-to-run noise on a GPU: contact slot order, constraint row order and float atomics, and why chaos amplifies low bits.
    • What each DeterminismType bit does in 4.0.1: only ATOMICS changes kernels; the CONTACTS and CONSTRAINT sorts are stubs.
    • When bitwise-identical runs are guaranteed (no contacts, at most one limit or equality row per world), and how the replay test from determinism_test.py handles contact scenes.
    • Why a reproducible restart needs State.PHYSICS | State.WARMSTART, and what determinism costs.
    • How to decide, case by case, whether you need bitwise reproducibility at all.

    Before you start: recap

    • Float atomics sum in arbitrary order, so low bits can change; Ch 4 §9. An integer wp.atomic_add on a counter hands each thread a unique slot, in no fixed order on a GPU.
    • All worlds share one flat contact pool: d.contact.* has naconmax slots and every contact stores its worldid (Ch 9 §2).
    • make_constraint turns contacts, limits and equalities into efc rows; each kernel reserves its rows with wp.atomic_add(nefc_out, worldid, k) (Ch 19 §6).
    • The Newton and CG solvers start from d.qacc_warmstart and stop after a tolerance or an iteration limit (Ch 20).
    • Use State.PHYSICS (+ WARMSTART for bitwise replays); Ch 8 §4.
    • The double pendulum is chaotic: a float32-vs-float64 difference of 1e-7 grows until the motions are unrelated (Ch 5 §7, Example 5.7).

    1Three sources of run-to-run noise

    A simulation is bitwise reproducible when two runs from the same start produce the same bit patterns, not just numbers that agree to six digits. On a CPU that is what you get by default. On a GPU it is not, and the reason is always the same: many threads update one shared place, and the GPU does not promise an order. MJWarp has three such places.

    The first two sources do not change any single number. A contact is the same contact whether it sits in slot 3 or slot 17. But every later stage that loops over contacts or rows and adds things up now adds them in a different order, and that turns the reordering into source 3: different float sums. Everything comes back to one fact about floating point.

    Recall from Ch 4

    Float atomics sum in arbitrary order, so low bits can change; Ch 4 §9. Example 4.9 summed eight float32 numbers in all 40320 orders and got many distinct results. This chapter adds the fix (records sorted before the sum) and its cost.

    Float addition is not associative

    In float32, (a + b) + c and a + (b + c) can differ in the last bit, because every addition rounds its result to 24 significant bits. The rounding error depends on the operands, so a different order rounds differently. A GPU kernel that runs wp.atomic_add(total, 0, x[i]) from a million threads performs the additions in whatever order the hardware serves the threads, and that order can change from launch to launch. Play with it below: each run adds the same twelve float32 values, but the threads arrive in a random order. The arithmetic is real float32 (JavaScript Math.fround).

    Example 22.1 does the same thing with Warp itself. It builds two kernel factories the way MJWarp builds its deterministic kernels: a deterministic argument that, when true, sets the Warp module option "deterministic" to wp.DeterministicMode.RUN_TO_RUN. Kernel A is a float sum; kernel B reserves slots with slot = wp.atomic_add(counter, 0, 1), the contact-slot pattern.

    Read the CPU output carefully. Both Warp modes print True on the CPU, and that is not because the option worked: Warp's CPU device runs the threads of a launch one after another, in index order, so there is nothing to fix. Warp's own source says so: the deterministic code generation is wrapped in #ifdef __CUDA_ARCH__ "so that CPU compilation falls through to normal atomic calls (CPU execution is already sequential/deterministic)" (warp/_src/deterministic.py). The slot owners come out as [0, 1, 2, ...] for the same reason. Part 2 of the example emulates a GPU in NumPy: 200 random arrival orders of 4096 values give 29 different float32 sums, up to 29 ulp apart. Sorting the records by thread id before the sum gives exactly one result.

    Pitfall: a CPU test proves nothing about GPU determinism

    Every reproducibility check in this chapter passes on CPU, with or without determinism. Run reproducibility tests on the GPU you care about. The notebook prints your GPU's numbers next to each CPU line.

    Which atomics are harmless?

    An integer atomic_add whose return value is ignored is exact: integer addition is associative, so the final count never depends on order. Integer and float atomic_min/atomic_max are order-independent too. The island code uses this on purpose: island.py::_dsu_union hooks the higher root to the lower root with atomic_cas, so the final island labels do not depend on which union ran first, and _island_map_dofs ("Map DOFs in ascending global order for deterministic solver inputs") computes each DOF's rank from the tree layout instead of a racy counter. The trouble starts when the return value of an integer counter is used as an address (sources 1 and 2), or when floats are added (source 3).

    2Contact slots and constraint rows: order without meaning

    In Ch 9 you met the contact pool. Here is the line that decides where a contact goes, from collision_core.py::write_contact:

    cid = wp.atomic_add(nacon_out, 0, 1)  # kernel_analyzer: ignore[atomic]
if cid < naconmax_in:
    contact_dist_out[cid] = dist_in
    contact_pos_out[cid] = pos_in
    ...
    contact_worldid_out[cid] = worldid_in

    The comment kernel_analyzer: ignore[atomic] tells MJWarp's kernel analyzer (a lint tool in the repository's contrib/kernel_analyzer) that this atomic is intentionally not wrapped in a deterministic factory. The same pattern reserves constraint rows in constraint.py, for example efcid = wp.atomic_add(nefc_out, worldid, nrow), and candidate pairs in the broadphase (collision_driver.py, atomic_add(ncollision_out, 0, 1)).

    The data is the same set of contacts in either run; only the permutation differs. So the right way to compare two contact buffers is to bring both into a canonical order first: sort by world, then by geom pair, then by position (a box resting on a box makes four contacts with the same geom pair). Figure 3 shows a real contact pool from Example 22.2 (2 worlds of box_stack(5), CPU) next to the same contacts in a shuffled order, the kind of order a GPU produces.

    The constraint rows inherit the problem. Each contact becomes a block of rows (4 for a pyramidal condim-3 contact). Inside one world the blocks can appear in either order, which changes the row index of every contact and the order of every sum over rows (for example J^T f in the solver). The efc strips below (A.3) show world 0 of two runs with the same five contacts.

    Pitfall: CPU order looks meaningful

    On the CPU, world 0's box-box contacts sit in slots 0-15 and its plane contacts in 128-131, in the same order every run. Code that assumes "slot k of run A is slot k of run B" or "world w's contacts are contiguous" passes on CPU and breaks on GPU. Always select contacts by contact.worldid, and compare buffers in a canonical order.

    3m.opt.deterministic: what each bit does in 4.0.1

    MJWarp's answer to the three sources is a bitmask option, m.opt.deterministic, with one bit per source. Its type is mjw.DeterminismType (types.py):

    BitValueDocstring in types.pyWhat 4.0.1 actually does
    NONE0non-deterministic executionthe default (put_model sets it)
    CONTACTS1stable contact ordering via geometric radix sortcalls collision_driver._sort_contacts, whose body is pass (# TODO(team): Implementation contact sorting.)
    CONSTRAINT2canonical constraint row orderingcalls constraint._sort_constraints, also pass
    ATOMICS4invariant floating-point atomic reductionsreal: 77 kernel factories compile in Warp's RUN_TO_RUN mode
    ALL7all determinism featuressame effect as ATOMICS

    The setter

    Option.deterministic is a Python property. Its setter maps True/False/None (and NumPy bools) to ALL/NONE, converts the value with operator.index, masks a negative complement such as ~DeterminismType.CONTACTS to the three valid bits, and raises ValueError for anything else. The value is stored as a plain int, so m.opt.deterministic &= ~DeterminismType.ATOMICS works.

    # mujoco_warp/_src/types.py, class Option (4.0.1)
@deterministic.setter
def deterministic(self, value: bool | int | None):
  if value is None or isinstance(value, (bool, np.bool_)):
    value = DeterminismType.ALL if value else DeterminismType.NONE
  value = operator.index(value)
  if value < 0:
    # complements, e.g. ~DeterminismType.CONTACTS is negative on Python 3.10
    value &= int(DeterminismType.ALL)
  if value & ~int(DeterminismType.ALL):
    raise ValueError(f"deterministic must be a DeterminismType bitmask, got {value}")
  self._deterministic = value

    Two details are worth remembering. A string like "ATOMICS" is rejected by the setter (TypeError), but io.override_model, the parser behind mjwarp-testspeed -o, accepts names, digits, "true"/"false" and |-joined names. And in override_model, "~CONTACTS" clears bits from the current value: from NONE it gives 0, from ALL it gives 6 (the test determinism_test.py::test_override_model pins this: "negation starts from the current value").

    How ATOMICS works: kernel factories and RUN_TO_RUN

    Every MJWarp kernel that contains a float atomic is built by a kernel factory: a function decorated with @cache_kernel whose last argument is deterministic: bool = False. Here is a real one (smooth.py):

    @cache_kernel
def _tendon_armature(nv: int, deterministic: bool = False):
  module_options = {"enable_backward": False}
  if deterministic:
    module_options["deterministic"] = wp.DeterministicMode.RUN_TO_RUN
    module_options["deterministic_max_records"] = nv

  @wp.kernel(module="unique", module_options=module_options)
  def kernel(...):
    ...

# and its caller, smooth.py::tendon_armature
det_atomics = bool(m.opt.deterministic & DeterminismType.ATOMICS)
... _tendon_armature(m.nv if det_atomics else 0, det_atomics) ...

    Three things happen here. First, module="unique" gives each variant its own Warp module, so the deterministic and the default kernel can coexist; cache_kernel keys its cache on the arguments, so flipping the option between steps simply picks the other cached variant (the test test_mode_toggle checks exactly that). Second, the Warp module option "deterministic" switches Warp's code generator to its deterministic lowering. Third, deterministic_max_records bounds how many records one thread may emit; it is needed when an atomic sits in a loop whose length static analysis cannot prove (here up to nv). The factory passes 0 on the default path, so the default kernel is not recompiled with a different size argument (_assert_default_path_keys tests this).

    What does Warp's deterministic lowering do? For a float atomic_add whose return value is unused, it replaces the atomic with a scatter of records (destination, thread id, value) into a temporary buffer, then sorts the records by (destination, thread id) and reduces them in that fixed order (warp/_src/deterministic.py, "scatter-sort-reduce"). A counter atomic whose return value is used, slot = wp.atomic_add(counter, i, 1), gets a second lowering, a two-pass launch: phase 0 records every reservation with all side effects suppressed, a deterministic sort and scan assign the offsets, and phase 1 runs the kernel again with those slots. MJWarp's slot and row counters (write_contact, the efc row kernels) do not get either lowering, because none of their kernels is built in a deterministic module (their atomics carry kernel_analyzer: ignore[atomic]). The float case, step by step:

    RUN_TO_RUN: scatter, sort, reduce

    warp/_src/deterministic.py · scatter-sort-reduceIllustrative values

tid = wp.tid()

    Going deeper: where the 77 factories live, and how the tests find them

    determinism_test.py::_det_factories walks every non-test module of mujoco_warp._src and collects functions that are wrapped by cache_kernel (they have __wrapped__) and have a deterministic parameter. In the 4.0.1 wheel that finds 77 factories: derivative 21, passive 15, smooth 15, solver 12, sensor 7, forward 2, sleep 2, bvh 1, constraint 1, support 1. _record_launches patches wp.launch and wp.launch_tiled and reads kernel.module.options["deterministic"], so the test can assert that with ATOMICS every factory kernel, and only those, runs in RUN_TO_RUN. test_factory_coverage checks that the scene cases exercise every factory, and test_factory_signatures that each one ends with deterministic=False. In the repository, the kernel analyzer (contrib/kernel_analyzer, not part of the wheel) enforces the rule at review time with two issues: MissingDeterministicFactory ("contains atomic operations but is not enclosed in a kernel factory with a 'deterministic' argument") and MissingDeterministicMaxRecords ("contains atomic operations in a dynamic loop and must set 'deterministic_max_records'").

    Rendering has its own switch: mjw.create_render_context(mjm, ..., deterministic=...) builds the flex BVH with bvh.accumulate_flex_vertex_normals(deterministic), and bvh.refit_flex_bvh (called from refit_bvh when the model has flexes) uses m.opt.deterministic & ATOMICS for the same kernel during refits (Ch 27).

    Warp also offers wp.DeterministicMode.GPU_TO_GPU, a stronger mode for reproducibility across GPU models. MJWarp only ever requests RUN_TO_RUN: "bit-exact repeated results on the same GPU architecture" (warp/config.py). Do not expect bitwise equality between, say, a T4 and an A100.

    4Bitwise reproducibility where it is possible: contact-free models

    Read the matrix again: in 4.0.1, ATOMICS fixes only the third row. So bitwise reproducibility is guaranteed only when the first two rows do not apply: no contacts, and no constraint rows whose order is racy. Turning contacts off removes the first row but not the second. Joint limits, friction loss and equality constraints also create efc rows, and every one of those kernels (_limit_slide_hinge, _limit_ball, _limit_tendon, _friction_dof, _equality_connect, _equality_joint, _equality_weld, ...) reserves its rows with the same wp.atomic_add(nefc_out, worldid, k) as the contact rows. None of them is a deterministic factory, so ATOMICS does not cover them. The safe statement is therefore: no contacts and at most one active limit, friction-loss or equality row per world. With more rows, a GPU can hand them out in a different order from run to run.

    determinism_test.py does find bitwise equality for its contact-free "tree" scenes (tendons, actuators, sensors, fluid, gravity compensation, an equality and limits) with ATOMICS and no replay. That is an observation on 2 worlds and 3 steps, not a guarantee from the code: with so few threads the row race rarely shows. (The dev tree's DeterminismType.CONSTRAINT path, called at constraint.py:6446 at 8f5b9f1, sorts the rows and closes this gap; the 4.0.1 wheel does not have it.) Example 22.4 runs one model of each kind: the double pendulum, which has no rows at all, and the shipped humanoid with contacts disabled, which falls into its joint limits and so has several racy limit rows per world.

    What to expect on a GPU. The pendulum's ATOMICS line must read bitwise equal: True: it has no efc rows, so float atomics are its only noise source. The humanoid's ATOMICS line will often read True as well, as in the library's tests, but nothing guarantees it: its limit rows are reserved in racy order, and one swapped pair of rows is enough to change the low bits of the solve. The NONE lines may or may not show a difference: a race needs two threads to hit the same address, and whether they do depends on the model (the humanoid has many tendon-free branches, the pendulum has two DOFs). The page does not quote a GPU result because this course is verified on CPU; your notebook prints yours. The line "NONE vs ATOMICS" compares two different summation orders, so on a GPU it can show a small nonzero difference even when both modes are individually reproducible.

    Tip: make the worlds different

    A reproducibility test where all worlds are identical can hide bugs that mix up worlds. Like determinism_test.py::_perturb (which gives world 1 different qvel and ctrl), Example 22.4 gives every world its own start velocity and control, and checks "worlds distinct".

    Note: the humanoid needed ls_iterations = 50

    With contacts off and random controls, the humanoid falls into its joint limits, and the shipped ls_iterations = 20 trips the LS_ITERATIONS overflow warning (Ch 20). Raising it is a static option, so it compiles new solver kernels once.

    5Contact scenes and the chaos amplifier

    Now the bad news. In a contact scene on a GPU, the contact and row order stay racy whatever you set, so the solver sums in a different order and the low bits change. Would that matter? A difference of one ulp (about 6e-8 for a coordinate near 0.5 m) sounds harmless. It is not, because many simulations are chaotic.

    Recall from Ch 5

    The double pendulum run in float32 (MJWarp) and float64 (C MuJoCo) matched to 1e-7 at first and then drifted until the motions were unrelated; a C run nudged by 1e-9 rad did the same (Ch 5 §7, Example 5.7). It is the system, not a bug.

    Example 22.5 has two parts. Part 1 runs a toppling box_stack(5) twice per mode and prints the difference and whether the raw contact order changed, without asserting anything. Part 2 measures the amplifier: run B starts exactly 1 ulp away in the top box's height, the size of the noise a reordered float32 sum leaves behind.

    Part 2 is the striking one. For ten steps the difference stays at one ulp. Then, within the next forty steps, it jumps by more than five orders of magnitude to almost 2 cm, and after one second some worlds differ by 70 cm: the boxes fell differently. Figure 6 plots every world, and a second dataset from Example 22.6 (next section) where the perturbation is the real thing, a shuffled contact order.

    Why the jumps? Smooth dynamics amplify a perturbation gradually (exponentially, at a rate set by the largest Lyapunov exponent). Contacts add discontinuities: whether a corner touches the floor at step 12 or step 13 is a yes/no decision, and a 1-ulp difference in height can flip it. After the flip the two runs have different active constraint sets, and the difference is suddenly the size of a contact impulse times a timestep. World 1 to 3 stay near 1e-3: their stacks settle and dissipation damps the difference. Worlds with a strong push topple, and their differences saturate at the size of the scene.

    Consequence for RL and for tests

    Two GPU runs of a contact-rich policy rollout can diverge macroscopically after a second of simulated time even with ALL set. Statistics over many worlds (mean return, success rate) are reproducible to sampling noise; individual trajectories are not. Write tests that compare statistics or short horizons with tolerances, or use the replay technique of the next section.

    6Testing reproducibility: the replay technique

    How do MJWarp's own tests check that ATOMICS works in contact scenes, if contact order is racy? They take the racy stages out of the comparison. determinism_test.py::_Replay wraps collision_driver.collision and constraint.make_constraint:

    • Run A (recording): after each call to either stage, snapshot every array of Data.
    • Run B (replay): before the stage, assert that its inputs (the whole Data) are bitwise equal to run A's; after the stage, assert that every float output holds the same bit patterns up to order (sorted bit patterns, _bits); then overwrite B's outputs with A's exact recording.
    • Everything downstream (solver, sensors, integrator) now sees identical inputs, so it can be compared bit for bit with _bitwise_diff.

    The docstring states the reason plainly: "CONTACTS and CONSTRAINT are not implemented yet, so collision and make_constraint emit rows in a racy order."

    Example 22.6 is a compact version of _Replay. Because a CPU run never reorders anything, it adds an injector that emulates the GPU: after every collision call it permutes the live contact slots at random. That is legal, since a contact is a self-contained record with its own worldid and make_constraint only runs after collision. Now the CPU shows the GPU problem, and the fix.

    Run B is the GPU's situation reproduced on a CPU: the same contacts in a different slot order make the trajectory first differ at step 2 (by about 6e-11), reach 2e-9 by step 10, and by step 30 the difference is 4 mm. Run C injects the same shuffle, but the replay wrapper checks the shuffled output against the tape ("same float bit patterns up to order": passed 120 times) and restores the recorded order, so the run is bitwise equal to A.

    Memory: the tape lives in host RAM

    The wrapper keeps a host copy of every Data array before and after each collision and make_constraint call: 2 stages x 2 snapshots per step, so the tape needs about (size of Data) x 4 x NSTEP bytes. For box_stack(5) with nconmax=32, njmax=128, Data is about 0.04 MB per world. That is why the GPU budget is only NWORLD=64, NSTEP=30 (about 0.3 GB): 1024 worlds for 100 steps would need about 16 GB and crash a Colab runtime. The example prints its tape size on the first line. For bigger runs, snapshot only the arrays the two stages write.

    Source

    mujoco_warp/_src/determinism_test.py · _Replay (record/check/restore), _bits (sorted bit patterns), _bitwise_diff, _snapshot/_restore/_flatten (every array reachable from Data, Model and a render context), _PHYSICS_FIELDS (fields invariant to row order), _check_scene (NONE vs ATOMICS within a tolerance, then two ATOMICS repeats bitwise).

    What the test compares between NONE and ATOMICS

    _check_scene compares a NONE run with an ATOMICS run only with assert_allclose(rtol=tol, atol=tol) (tol 1e-3, 1e-2 for stiff passive flex contacts, "stiff passive contacts amplify differences in summation order"), on _PHYSICS_FIELDS: qpos, qvel, qacc, the qfrc_* family, actuator and tendon quantities, subtree and com quantities, energy and flex vertex positions. Contact sensors are excluded because their values depend on contact order. Only ATOMICS against ATOMICS is compared bitwise.

    A reusable bitwise comparator

    Debugging a reproducibility failure starts with one question: where did the runs first differ? Example 22.7 is a helper you can drop into your own tests. It compares bit patterns, so it catches -0.0 vs 0.0 (which == calls equal) and treats identical NaNs as equal (== flags every NaN as different), and reports the first field, world and element, with both values in hex.

    The two hex values differ in their last byte (ce vs e8): 26 ulp after 50 steps, from a 1e-6 nudge. World 5, nudged by a single ulp, is listed too. The other six worlds are untouched, as they must be: a difference that leaks across worlds would be a bug.

    7Bitwise restarts: snapshots need the warmstart

    Recall from Ch 8

    Use State.PHYSICS (+ WARMSTART for bitwise replays); Ch 8 §4. mjw.get_state(m, d, buf, sig) copies the parts named by sig into a (nworld, mj_stateSize(mjm, sig)) array and does not check its size.

    Reproducibility is not only about two runs from the start. Often you want to restart from the middle: checkpoint an RL environment, branch rollouts from one state (Ch 29), or rerun the last 100 steps before a blow-up. The question is what a "state" must contain for the rerun to be bitwise identical. The answer includes something that is not physics at all: d.qacc_warmstart, the solver's starting guess. Newton and CG stop at a tolerance, so where they start decides which of many "converged enough" answers they return, in the low bits.

    A 0.45 mm difference after 100 steps, on a CPU where everything else is deterministic, from leaving out the warmstart. set_state writes only the parts named in the signature; without WARMSTART, qacc_warmstart keeps the value from the end of the reference run, so the first replayed solve starts from the wrong guess. On a GPU the complete snapshot is necessary but not sufficient: with contacts, the order noise of §5 comes on top, so PHYSICS | WARMSTART gives a bitwise restart only for models without contacts and with at most one active limit, friction-loss or equality row per world, with ATOMICS (or with a replay).

    Tip: time is separate

    State.PHYSICS does not include TIME (Ch 8, Example 8.4). Add State.TIME if your controller reads d.time, or use State.INTEGRATION (all 15 bits) for a full checkpoint.

    8What determinism costs, and determinism in your own kernels

    RUN_TO_RUN is not free on a GPU: each deterministic atomic site writes records to a temporary buffer, and Warp sorts and reduces them after the kernel. How much that costs depends on how many atomics a step executes, which depends on the model. Example 22.9 times NONE, ATOMICS and ALL and counts how many launches of one step run in RUN_TO_RUN.

    On the CPU the three modes run at the same speed within noise, because the deterministic path is compiled out. The launch counts are the more useful information, with two caveats: they are for one sampled step, and the solver loop runs until every world has converged, so its launches (and the RUN_TO_RUN ones among them) grow with solver_niter, which the example prints next to the counts. On box_stack(5) under ATOMICS a step with one solver iteration makes 96 launches (91 wp.launch + 5 wp.launch_tiled), and a later step with two solver iterations makes 106 (99 + 7). Some launch paths also branch on wp.get_device().is_cuda, so these are CPU counts. Within that sampled step the number of launches is the same in every mode (the record sort and reduction are Warp-internal work around a deterministic kernel, not MJWarp launches), with 16-17 of about 90 kernels running deterministically. Measure the GPU cost on your own scene: run the example in the notebook, or mjwarp-testspeed with -o "opt.deterministic=ATOMICS" (the override parser maps the string to DeterminismType). The tuning checklist of Ch 25 has a row for it: determinism off unless you need it.

    Determinism in your own kernels

    Custom kernels (Ch 26) follow the same rules. If your kernel adds floats into a shared location, either avoid the atomic (give each thread its own output and reduce in a fixed order, for example one thread per world looping over its elements), or build the kernel through a factory with a deterministic argument and set the Warp module options exactly like MJWarp does, sizing deterministic_max_records when the atomic sits in a loop. Integer counters whose return value becomes an address (slot = wp.atomic_add(counter, i, 1)) are not racy by nature: in a RUN_TO_RUN module Warp lowers them to its two-pass scheme and hands out the slots deterministically, at the cost of running the kernel twice. The alternative is to leave the kernel as it is and sort its output before you compare it. MJWarp's own slot and row counters stay racy because their kernels are not built in deterministic modules. Ch 26 §8 returns to this with your own observation and reward kernels.

    10Check yourself

    Quiz: determinism in 4.0.1

    Which DeterminismType bit changes the kernels that run in mujoco-warp 4.0.1?

    Only ATOMICS: 77 kernel factories are compiled with the Warp module option deterministic = RUN_TO_RUN. ALL has the same effect.

    After m.opt.deterministic = True, what does m.opt.deterministic hold?

    True/False/None map to ALL/NONE, and the value is stored as an int, so bit arithmetic like &= ~DeterminismType.ATOMICS works.

    Why are two GPU runs of a box stack not bitwise equal even with ALL?

    The CONTACTS and CONSTRAINT sorts are stubs in 4.0.1, so the order of contacts and rows still follows thread timing, and chaos amplifies the resulting low-bit differences (Example 22.6, run B).

    What does State.WARMSTART add to a snapshot, and why does it matter?

    In Example 22.8 a QPOS|QVEL restore was 0.45 mm off after 100 steps on CPU; PHYSICS|WARMSTART was exact.

    Example 22.1 prints "bitwise equal: True" on the CPU for NOT_GUARANTEED. Why?

    Warp even compiles the deterministic lowering only for CUDA (#ifdef __CUDA_ARCH__). A CPU reproducibility test says nothing about a GPU.

    The model has deterministic = NONE. You call override_model(m, {"opt.deterministic": "~CONTACTS"}). What is the result?

    In override_model, "~NAME" starts from the current value (Example 22.3). The setter with the int ~DeterminismType.CONTACTS gives 6 instead.

    In the replay test, how are the float outputs of collision in run B checked?

    _bits sorts each array's bit patterns, so a permutation compares equal while any changed value fails.

    Which of these atomics is order-independent on a GPU?

    The final count of an integer counter is exact in any order; the returned values are not.

    Part V review (Ch 19-22)

    Which constraint solvers does MJWarp 4.0.1 support?

    types.SolverType has CG and NEWTON with the comment "unsupported: PGS".

    How many efc rows does one condim-3 contact produce with the default pyramidal cone?

    A pyramidal cone uses 2(condim-1) rows: 4 for condim 3 (Ch 9, Ch 19).

    What happens when a world needs more rows than njmax?

    OverflowType.NEFC: "nefc > njmax". Size njmax from a rollout (Ch 9).

    Newton and CG start each solve from which vector?

    That is why WARMSTART belongs in a reproducible snapshot (§7).

    Islands are built with a disjoint-set union. Why do the island labels not depend on thread order?

    An order-independent rule (min root wins) instead of "first come, first served" (Ch 21).

    What must be enabled for bodies to fall asleep in MJWarp?

    <flag sleep="enable"/> sets EnableBit.SLEEP; sleep_tolerance sets the velocity threshold (Ch 21).

    def first_difference(d1, d2, fields=("qpos", "qvel", "qacc")):
    """(field, world) of the first bitwise difference, or None."""
    for name in fields:
        a, b = getattr(d1, name).numpy(), getattr(d2, name).numpy()
        ua = a.reshape(a.shape[0], -1).view(f"u{a.itemsize}")
        ub = b.reshape(b.shape[0], -1).view(f"u{b.itemsize}")
        bad = np.flatnonzero((ua != ub).any(axis=1))
        if bad.size:
            return name, int(bad[0])
    return None

    def replay_is_exact(sig, nstep=30):
    """Snapshot with `sig`, run nstep (reference), restore, rerun; True if qpos is bitwise equal."""
    size = mujoco.mj_stateSize(mjm, int(sig))
    buf = wp.zeros((d.nworld, size), dtype=float)

        mjw.step(m, d)

    12Summary

    Key takeaways

    • GPU runs differ because of three sources: contact slots from atomic_add(nacon_out, 0, 1), efc rows from atomic_add(nefc_out, worldid, k), and float atomics. The first two only reorder, but reordering changes later float sums.
    • Chaos amplifies one ulp to centimetres: in a toppling box stack a 1-ulp nudge stayed at 6e-8 for ten steps and reached 1.8 cm by step 50 (Example 22.5).
    • m.opt.deterministic is a DeterminismType bitmask stored as an int; True means ALL (7). In 4.0.1 only ATOMICS does something: 77 kernel factories compile with Warp's RUN_TO_RUN (scatter, sort, reduce). CONTACTS and CONSTRAINT call pass stubs; sort.py exists only in the dev tree.
    • Models with no contacts and at most one active limit, friction-loss or equality row per world are bitwise reproducible with ATOMICS on the same GPU model. More rows than that are reserved through the same racy atomic_add(nefc_out, ...) as contact rows, so bitwise equality there (as in determinism_test.py, 2 worlds x 3 steps) is an observation, not a guarantee. Contact scenes are not reproducible; test them with the replay technique (record collision and make_constraint, check up to order, restore) or in canonical order.
    • A bitwise restart needs State.PHYSICS | State.WARMSTART: without the warmstart a CPU replay was 0.45 mm off after 100 steps.
    • Determinism costs record buffers and sorts on a GPU; measure it on your scene (Example 22.9, mjwarp-testspeed -o "opt.deterministic=ATOMICS") and turn it on only for debugging, exact reproduction and regression tests.
    • Every check passes on CPU, where Warp runs threads in order. Test reproducibility on the GPU you care about.
