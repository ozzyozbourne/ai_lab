Two threads use one B+tree. What may the second thread do while the first is in the middle of an operation? That depends on what the first one has locked. This page runs the same two operations under four protocols: one mutex for the whole tree, one reader-writer lock for the whole tree, a latch per node with latch coupling, and optimistic descent with version counters. Text and code: chapter README.

1. One operation frozen, the other one runs

These are the experiments of sections 3, 4 and 7 of zig build run / cargo run. Thread T1 starts and is stopped in the middle, still holding its locks; then thread T2 runs. The last experiment in the list has four threads: it shows a convoy, a thread that waits for one that is itself only waiting. A badge on a node names the thread and the mode: S shared (several readers), X exclusive (one writer); a dashed badge ending in ? is a thread waiting for that latch. Change the protocol and watch the same experiment end differently. Press Space to play, → to step, or tick Predict to be asked first.

2. Your turn: you are the scheduler

Pick an operation for each thread and press Start. Each press of a Step button lets that thread take exactly one step, so you choose the interleaving. A thread that needs a latch held by the other one cannot step until it is released. Things to try with latch coupling: put 26 against get 17 (stop the writer after it has latched #6); two puts into different leaves; then the same under the reader-writer lock. With the optimistic protocol, let a reader note a version, run a writer through the same leaf, and watch the reader start again.

The wrong answer that coupling prevents. The last protocol in the list, no coupling (broken), is latch coupling with the reader's two steps swapped: it releases the parent first and latches the child afterwards. Choose it, set T1 to get 30 and T2 to put 26, and press Start. Step T1 until it has released #6 and holds nothing. Then step T2 to the end: leaf #3 splits and 30 moves to the new leaf #8. Now finish T1. It reports that 30 is not in the tree.

The sandbox tree lives in a node table of 24 nodes, like the fixed table of the programs. After enough splits a put ends with OutOfNodes and changes nothing; Reset tree starts over.

The model grants a shared latch whenever no writer holds the node. Real reader-writer locks often make new readers queue behind a waiting writer so that writers are not starved; the order of who gets in is then different, the set of latches each protocol needs is the same. In the convoy experiment above that makes things worse: once T4 waits for the root, a fifth thread that only wants to read would queue behind it as well.

3. Does the picture match the code?

The JavaScript model behind this page is a port of the chapter's Zig and Rust code. It rebuilds the canonical tree under each protocol, repeats every frozen-operation experiment, the replaced-root experiment, the full-node-table experiment and the four-thread convoy, and compares the text with expected_output.txt (sections 1, 3, 4, 5 and 7). The optimistic protocol is not in the programs and so has no such check.
