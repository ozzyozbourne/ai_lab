# Data-Oriented Design in Rust, Zig and Odin

An interactive HTML book about **data-oriented design (DOD)** in the performance sense: arrange data for the
loops that read it and the hardware that runs them. Every idea comes with a live figure, code in Rust, Zig and
Odin that compiles and runs, and benchmarks measured on a real machine.
(Chapter 1 separates this from Sharvit's "Data-Oriented Programming", which is about generic immutable data.
The folder name keeps the original wording.)

## Opening the book

- **Locally:** double-click `index.html`. Everything is plain HTML, CSS and classic scripts, so it works over `file://`.
  Fonts and syntax highlighting are vendored in `assets/vendor/`. Only the decorative 3D picture on the cover loads
  Three.js 0.187.0 from jsDelivr. Offline, it collapses to a caption.
- **GitHub Pages:** serve the repository (or this folder) as a static site. No build step.
- `components.html` is a QA fixture and the reference for chapter authors. It shows every component and shared figure.
  The book itself does not link to it.

## Layout

```
index.html                 cover, generated table of contents, how to read / run
01-…html … 12-…html        chapters (flat, next to index.html; they load assets/...)
references.html            all sources
components.html            QA fixture + "API for chapter authors"
assets/book.css            design system (tokens, layout, components, print, mobile)
assets/book.js             core runtime: BookQ, manifest/navigation, code tabs, viz registry, player, charts, bench data
assets/viz/*.js            shared figures (aos-soa, struct-padding, latency-ladder, cache-sim, pointer-chase,
                           bench-bars, bench-line, bench-dist); chapter figures are assets/viz/chNN-*.js
assets/data/bench.js       generated by code/bench_all.sh (plus per-chapter bench-chNN.js)
assets/vendor/             Prism 1.30.0 (+rust, zig, odin, bash), Inter + JetBrains Mono woff2 (see its README)
code/                      runnable examples (see below)
tools/smoke.sh             headless check of every page at 1280 px and 375 px
```

## Toolchains

| Language | Version | Notes |
|---|---|---|
| Rust | 1.100.0, edition 2024 | std only; one Cargo workspace `code/Cargo.toml` (`members = ["ch*/rust"]`) |
| Zig | 0.17.1 | single file per chapter: `zig run -O fast main.zig` (0.17 renamed `ReleaseFast` to `fast`) |
| Odin | dev-2026-11 | package dir per chapter: `odin run odin -o:speed -vet -strict-style` |

## Running the code

```sh
cd code
./run_all.sh               # cargo clippy -D warnings, odin check, then every chapter in --quick mode; pass/fail table
./run_all.sh ch03 ch04     # only these chapters
./bench_all.sh             # serial full-size runs pinned with taskset -c 2; writes results/ and assets/data/bench*.js
```

Each program takes an optional size `N` and `--quick` (small sizes), for example
`cargo run --release -q -p chNN_slug -- --quick` from `code/`, `zig run -O fast main.zig -- 1000000` from
`chNN-slug/zig/`, or `odin run odin -o:speed -vet -strict-style -- --quick` from `chNN-slug/`.

Programs print human-readable lines plus machine lines in this format:
`BENCH {"id":"chNN-x","label":"…","lang":"rust","n":…,"ns":median,"samples":[…]}`. The shared harness
(median of 7 runs after a warm-up, keep-alive, argument parsing, `emit_bench`) is in `code/harness/`. Each chapter
copies it verbatim between `// ---- harness ----` markers. To try the harness on its own:

```sh
cd code/harness
rustc --edition 2024 -O harness.rs -o /tmp/h && /tmp/h --quick
zig run -O fast harness.zig -- --quick
odin run odin -o:speed -vet -strict-style -- --quick
```

`bench_all.sh` records the machine in `code/results/machine.txt` (lscpu, topology, THP, compiler versions, date).
A chapter whose benchmark uses threads puts a `taskset` file (for example `0,2`) in its `code/chNN-*/` directory.
`bench_all.sh` rewrites every `assets/data/bench-chNN.js` from `code/results/`. Every field of a BENCH line except
`id` is kept (for example `value` and `unit`). An id or a language that a page used before but this pass did not
produce (because a run failed or a chapter was skipped) is carried over from the old file, flagged in its `note`,
and reported as a WARNING. Benchmark numbers from a shared cloud VM are noisy. Read them as ratios and shapes, not absolute truths.
