    What Is MuJoCo Warp?

    MuJoCo Warp (MJWarp) is the MuJoCo physics simulator rewritten as GPU kernels, so one Python call can advance thousands of independent simulations at once. This chapter explains what that sentence means, sets up a working Colab runtime, runs your first simulation in 1 and then 1024 worlds, and tells you plainly what MJWarp does not do yet.

    Beginner About 60 min· Prerequisites: none (Python and a little NumPy)

    You will learn

    • What a physics simulator does: state in, state out, and where MuJoCo fits.
    • Why GPUs help: many independent worlds advanced by one kernel launch.
    • What NVIDIA Warp is, and what MJWarp is (MuJoCo as Warp kernels, part of the Newton project).
    • How to set up Colab correctly: the [viewer] extra, the driver check, a GPU that Warp really sees.
    • How to run the same ball drop in C MuJoCo, in 1 MJWarp world and in 1024 worlds.
    • Which features are not supported yet (PGS, NaN checks and auto-reset, float64, PID, some plugins) and where the full list lives.

    1Physics simulation in one picture

    A physics simulator is a function that takes the state of a system at time t and returns the state a short moment h later. Call it again with that result, and again, and you get a movie of the system moving. Everything else (contacts, joints, motors, friction) is detail inside that one function.

    In MuJoCo the state of one simulation is mostly four things:

    • qpos: where everything is. For a free-flying ball that is 7 numbers: its centre x, y, z and an orientation quaternion.
    • qvel: how fast everything moves. A free ball has 6: three linear and three angular velocities.
    • act: internal states of actuators that have memory (muscles, filters). Often empty.
    • time: the simulated clock.

    Two more things go into each step but are not state: the controls ctrl (what your controller or policy commands) and the model (the constant description: masses, sizes, gravity, the timestep h).

    Simulators differ in what happens inside step: how bodies are described, how contacts are found, how forces that keep things from overlapping are computed. MuJoCo (Multi-Joint dynamics with Contact) is a simulator built for robotics and biomechanics: it is fast, accurate for jointed bodies, and treats contacts as soft constraints solved by a convex optimisation. It is the reference that MJWarp follows number by number.

    Why "state" matters for the rest of the course

    Everything in MJWarp is organised around this split. The model is uploaded once and reused; the state is what you read, write, reset and randomise. Keeping the two apart is also what lets MJWarp hold thousands of states next to a single model.

    2MuJoCo in five minutes

    You describe a scene in MJCF, MuJoCo's XML format. The MuJoCo compiler reads it and produces two objects:

    • MjModel: the compiled constants. Sizes such as nq (number of position coordinates) and nv (number of degrees of freedom), every body's mass and inertia, every geom's shape, and the options such as opt.timestep.
    • MjData: the state of one simulation (qpos, qvel, act, time, ctrl) plus everything computed from it while stepping: body positions xpos, the contact list, forces.

    Classic MuJoCo is a C library with Python bindings. It runs on the CPU, uses 64-bit floats (float64) everywhere, and one MjData is one world. To simulate 1000 worlds you create 1000 MjData objects and step them one after another (or spread them over a few CPU threads).

    Here is the model used throughout this chapter, BALL_DROP: a floor plane and a 0.1 m ball on a free joint, 1 m above the floor, simulated with a 2 ms timestep.

    <body name="ball" pos="0 0 1">

    3Why GPUs: throughput, not latency

    A CPU has a handful of big, fast cores. Each one finishes a single task quickly; this is good latency. A GPU has thousands of small, slower lanes that all run the same instructions on different data; this is good throughput: a lot of work finished per second, even though each piece takes longer.

    Robot learning, controller tuning and system identification all want throughput. They need millions of simulated steps across many variations of a scene, and the worlds do not depend on each other. Problems like that are called embarrassingly parallel: you can hand world 0 to lane 0, world 1 to lane 1, and so on, with no coordination. In MJWarp each such independent simulation is called a world, and the number of them is nworld.

    Two consequences are worth remembering from day one:

    • One world on a GPU is not faster than on a CPU. A single MJWarp world is usually slower than C MuJoCo. The win only appears when you simulate many worlds at once.
    • Overheads matter. Starting work on the GPU (a kernel launch) has a fixed cost. MJWarp hides it by doing every world in the same launch, and, later in the course, by recording all launches of a step into a CUDA graph (Ch 7, Ch 24).

    Numbers in this course

    This course is verified on a CPU box, and CPU numbers are always labelled as such. It never quotes GPU speeds: the notebooks print your numbers on your Colab GPU.

    4Warp and MJWarp in one paragraph each

    NVIDIA Warp. Warp is a Python library from NVIDIA for writing high-performance simulation code. You write a function in ordinary Python syntax with a @wp.kernel decorator; Warp JIT-compiles it to CUDA for NVIDIA GPUs or to C++ for the CPU, and wp.launch(kernel, dim=N, ...) runs it once per index 0..N-1, in parallel. Data lives in wp.arrays on a device ("cuda:0" or "cpu"). A kernel looks like this:

    @wp.kernel
def add_gravity(qvel: wp.array2d(dtype=float), g: float, h: float):
    worldid = wp.tid()                 # which world this thread handles
    qvel[worldid, 2] -= g * h          # each thread touches only its own world

wp.launch(add_gravity, dim=nworld, inputs=[d.qvel, 9.81, 0.002])   # nworld threads at once

    A sketch to show the shape of Warp code, not part of MJWarp. Ch 4 teaches kernels, and Ch 26 shows how to write your own next to MJWarp.

    MuJoCo Warp. MJWarp is MuJoCo's simulation pipeline re-implemented as a few hundred Warp kernels. In the README's words, it is "a GPU-accelerated version of the MuJoCo physics simulator, designed for NVIDIA hardware", and it is "maintained by Google DeepMind and NVIDIA as part of the Newton project" (the source files carry the copyright line "The Newton Developers"). You still write MJCF and compile it with ordinary MuJoCo; then you copy the result to the device and step it there:

    • mjw.put_model(mjm) copies the MjModel to the device as an mjw.Model (Warp arrays, float32).
    • mjw.make_data(mjm, nworld=N) allocates an mjw.Data holding N worlds at once. Every state array gets nworld as its first dimension: d.qpos has shape (nworld, nq).
    • mjw.step(m, d) advances every world by one timestep.

    What one mjw.step does

    mjw.step is ordinary Python. It calls the same stages as MuJoCo's mj_step, and each stage issues Warp kernel launches that cover all worlds at once. The stepper below walks through the real call order in forward.py (simplified: optional branches for sleeping and the discrete integrator are left out). You do not need to remember the stages now; Ch 7 is the full tour.

    Inside one mjw.step call

    forward.py::step, _forward
    def step(m, d):
  forward(m, d)  # -> _forward
    fwd_position(m, d)
    sensor_pos; _energy_pos
    fwd_velocity(m, d)
    sensor_vel; _energy_vel
    m.callback.control(m, d)
    fwd_actuation(m, d)
    fwd_acceleration(m, d)
    solver.solve(m, d)
    sensor_acc(m, d)
  euler(m, d)  # default integrator

    Where MJWarp sits in the ecosystem

    MJWarp is a library, not a training framework. Several projects build on it. You will not need any of them in this course, but it helps to know where they fit.

    Step 1 of the cell (choosing MUJOCO_GL before mujoco is imported) only matters in rendering notebooks; this chapter's notebook leaves it unset.

    1. Check the driver before installing. nvidia-smi prints the driver version, for example 580.82.07, NVIDIA L4. The cell keeps the part before the first dot as major. It first asks shutil.which("nvidia-smi") whether the tool exists at all: on a CPU runtime it does not, and calling it anyway would crash the cell with FileNotFoundError. Then smi stays empty, the cell prints "No NVIDIA GPU visible" and major is 0. It does all this before importing Warp, so the right Warp build is installed the first time and no runtime restart is needed.
    2. Pick the Warp build. warp-lang 1.19.0 from PyPI is built against CUDA 13 and needs an R580 or newer driver. On an older driver the cell installs NVIDIA's +cu12 release wheel of the same version instead.
    3. Install pinned versions. mujoco-warp only asks for warp-lang>=1.15 and mujoco-core>=4.0.0, so without pins you would get whatever is newest. The course pins the versions it was verified with.
    4. The [viewer] extra. In the 4.0.1 wheel it adds mujoco-core[rendering] (which pulls glfw and pyopengl) and pillow. You need those for mujoco.Renderer, mjwarp-viewer and mjwarp-record (Ch 5). Plain mujoco-warp pulls mujoco-core without its [rendering] extra (plus warp-lang, numpy, absl-py and etils); [viewer] adds mujoco-core[rendering] and pillow on top.
    5. Quiet the JIT log. Warp 1.19 logs at INFO by default and prints one "Module ... load" line per kernel module, hundreds on the first mjw.step. wp.config.log_level = wp.LOG_WARNING, set right after import warp, keeps the output readable. Every script in the course does the same.
    6. Confirm that Warp sees the GPU. If it does not, Warp silently uses its CPU device: everything still works, only far slower, and there is no error. wp.get_cuda_device_count() > 0 is the check; ON_GPU then picks big or small budgets in every example.
    7. Conditional graphs. wp.is_conditional_graph_supported() tells later chapters whether device-side loops inside CUDA graphs are available (Ch 24). You can ignore it for now.

    Pitfall: the package names

    The distribution is mujoco-core, the import name is mujoco. So md.version("mujoco-core") works and md.version("mujoco") raises PackageNotFoundError (Example 1.1 shows it). Never pip install mujoco on top: both distributions provide the mujoco package.

    Pitfall: the first call is slow

    Warp compiles kernels the first time they are needed and stores the binaries in a kernel cache. The first mjw.step in a fresh Colab runtime therefore takes a long time, and later calls are fast. Colab's cache disappears with the runtime. Example 1.6 measures this.

    Driver troubleshooting

    Reading the nvidia-smi line. The query in the setup cell prints driver_version, name, for example 580.82.07, NVIDIA L4. Only the number before the first dot matters here: 580 or more means the PyPI warp-lang==1.19.0 (CUDA 13) works. The plain !nvidia-smi table also shows a "CUDA Version" in its header: that is the newest CUDA the driver supports, not what is installed.

    "No NVIDIA GPU visible". The runtime has no GPU (or no nvidia-smi; the cell checks for it first instead of crashing). Change the runtime type to GPU and run the cells again. Everything still works on CPU with the small budgets, which is how this course is verified.

    "WARNING: Warp sees no GPU" although nvidia-smi shows one. Warp could not load the CUDA driver for its build. The usual cause is a CUDA 13 Warp on a driver older than 580, for example after installing warp-lang by hand. Reinstall with the setup cell (it picks the +cu12 wheel), then Runtime > Restart session, because an imported Warp cannot be swapped in a running Python process. On this CPU box Warp prints Warp CUDA warning: Could not find or load the NVIDIA CUDA driver to stderr at import; that is expected here.

    The kernel cache. wp.config.kernel_cache_dir is where compiled kernels go; Example 1.6 prints it (on this box /root/.cache/warp/1.19.0). Deleting it, or a new Colab runtime, means the next first step compiles again. You can point it elsewhere by setting wp.config.kernel_cache_dir before wp.init(), which is what ex6_jit_timing.py --cold does.

    CUDA older than 12.4. put_model calls warp_util.check_toolkit_driver(), which only warns that conditional graph nodes are unavailable and that Model.opt.graph_conditional should be set to False. That matters from Ch 24 on.

    6Hello world: one ball, then 1024

    Time to run code. The examples below are the files in examples/01-what-is-mujoco-warp/ and the cells of the notebook. Each block shows the real output of a run on this course's CPU box.

    Check the environment

    The smallest possible model makes a good install test, and it is the trick the official tutorial uses: if an empty <mujoco/> survives put_model, MuJoCo, Warp and MJWarp agree with each other.

    Look at the last three lines. On the host, mjm.opt.timestep is a Python float (float64). On the device, m.opt.timestep is a Warp array of float32 with shape (1,). That leading dimension is a batch dimension: later you can give each world its own timestep, gravity or friction by making it longer (Ch 10).

    The ball in C MuJoCo

    Read the numbers like a physicist. Free fall gives z = 1 - \tfrac12 g t^2: at t = 0.4 s that is 1 - 0.5 \cdot 9.81 \cdot 0.16 = 0.215, close to the printed 0.211 (the small gap is the discrete timestep). The ball's surface touches the floor when its centre reaches z = 0.1, at t = \sqrt{2 \cdot 0.9 / 9.81} \approx 0.43 s. After that one contact exists (ncon=1) and the ball rests at 0.09963 m: slightly below 0.1. MuJoCo contacts are soft, so a tiny penetration is normal (Ch 2 explains solref).

    The same ball in MJWarp

    Four changes turn the C loop into an MJWarp loop: put_model instead of using mjm directly, make_data(mjm, nworld=1) instead of MjData, mjw.step(m, d) instead of mj_step, and d.qpos.numpy()[0, 2] (world 0, coordinate 2) to read the height. The script runs both side by side and compares them. It also passes nconmax=4, njmax=16, which size the per-world contact and constraint buffers, and reads d.overflow, which reports whether they were too small; Ch 9 covers both.

    Why the results differ at all: float32

    C MuJoCo computes in 64-bit floats, MJWarp in 32-bit floats (d.qpos.dtype is float32). float32 keeps about 7 significant digits, so differences of about 10^{-6} to 10^{-7} are expected and harmless. MJWarp has no float64 mode. If you compare against C MuJoCo, compare with a tolerance, never with ==.

    Now 1024 worlds

    Going from one world to many is a single argument: nworld. The only new idea is how to give each world its own start. d.qpos is a (nworld, nq) array on the device, so you build a NumPy array of the same shape and write it in place with d.qpos.assign(...). Column 2 of a free joint's qpos is the height.

    Three things to notice. The same file runs 8 worlds on a CPU and 1024 on a GPU: the budget block at the top (ON_GPU = wp.get_device().is_cuda) is in every script of the course. nconmax=4, njmax=16 size the contact and constraint buffers per world; the last line checks that nothing overflowed (Ch 9 is all about this). And after 0.5 s the worlds disagree: low balls already rest (one at 0.0967, still bouncing into the soft floor), the highest one is still falling at 0.638 m.

    The hero animation at the top of this page comes from the next example: 256 double pendulums, which is nworld=256 even on the CPU, recorded every 5th step.

    The spread of the shoulder angle grows from 0.1 rad to 0.85 rad in three seconds. Nothing is wrong: the double pendulum amplifies tiny differences, and each world follows its own physics. Because chaos amplifies any difference, a GPU run may end at visibly different angles from this CPU run after a few seconds, even though each step agrees to float32 rounding. Ch 22 (determinism) comes back to this.

    Why was the first step slow?

    Habit: warm up before you time

    Whenever you measure speed, call mjw.step once first (to compile), call wp.synchronize() before reading the clock (GPU work runs asynchronously), and report world-steps per second. Ch 25 turns this into a proper benchmarking method.

    Source

    The launch count is measured by temporarily wrapping wp.launch and wp.launch_tiled around one mjw.step. The calls come from mujoco_warp/_src/forward.py (step, _forward, fwd_position, ...) and the modules it calls (smooth.py, collision_driver.py, constraint.py, solver.py).

    7What MJWarp does not do (yet)

    MJWarp follows MuJoCo closely, but not every feature is there. Most of the gaps will never bother a beginner; a few will. In plain language:

    • The PGS solver. Only the CG and Newton solvers exist. A model with solver="PGS" is rejected (Example 1.8).
    • NaN checks and auto-reset. C MuJoCo checks for exploding values (mj_checkPos, mj_checkVel, mj_checkAcc) and can reset automatically. MJWarp does neither (the DisableBit enum notes "unsupported: MIDPHASE, AUTORESET"): a world that blows up just keeps producing NaNs. Ch 8 writes a small reset kernel for this.
    • float64. Everything on the device is float32.
    • PID actuators and SO3 ball-joint actuators. MuJoCo 4 has PID gain and dynamics types and an SO3 transmission; the 4.0.1 wheel rejects them.
    • Plugins. Body, actuator and sensor plugins are rejected. SDF geometry plugins work once their Warp SDF functions are registered (Ch 18).
    • Some flex (soft body) combinations, for example a flex together with a heightfield, or quadratic interpolation. Flex is labelled experimental (Ch 23).
    • Gradients are experimental. The README says differentiability via Warp "is not yet available" (Ch 29 shows what does work).

    How is this known? Not from documentation alone: put_model checks the model. For each feature type it compares the values used in your MjModel with the members of MJWarp's own enums, and raises NotImplementedError for anything missing. The MJWarp enums in types.py even carry comments such as # unsupported: PGS. So the list of unsupported features can be read off the code.

    Going deeper: derive the list from the enums (Example 1.7)

    put_model (in _src/io.py) runs three kinds of check. Array fields such as actuator_dyntype, eq_type or tree_sleep_policy are tested with np.isin(field, MJWarpEnum); scalar options (opt.integrator, opt.cone, opt.solver) with field not in set(MJWarpEnum); and the flag words opt.disableflags, opt.enableflags by masking out every bit the MJWarp flag enum does not have. So diffing MuJoCo's mjt* enums against MJWarp's enums by value gives the enum-based part of what put_model rejects. It also checks geom, sensor and wrap types, which this script skips, and raises separately for plugins and some flex/solver combinations.

    The private-API badge is there because SleepPolicy and EqType are not exported from mujoco_warp; the script imports them from mujoco_warp._src.types, a name that may change. Two details show why deriving from code beats reading comments: EqType's comment says only "unsupported: DISTANCE", yet the diff also finds FLEXVERT; and BiasType has no SO3 member although GainType does. Sentinels such as mjNENABLE and mjTRN_UNDEFINED are skipped because they are counts and markers, not features.

    When you hit NotImplementedError

    Read the message: it names the MuJoCo enum value (mjSOL_PGS, ['mjGAIN_PID'], ...). Change that one setting in the MJCF (here: solver="Newton", the default) and try again. Errors from put_model are cheap: no kernel has been compiled yet.

    9Check yourself

    Quiz

    Where do the ball's current position and velocity live?

    State (qpos, qvel, act, time) and everything derived from it is in Data. Model is constant.

    Example 1.4 shows a maximum difference of about 1.6e-6 m between MJWarp and C MuJoCo. Why?

    float32 keeps about 7 significant digits, so differences around 1e-6 are rounding. Compare with a tolerance.

    What does nworld in mjw.make_data(mjm, nworld=1024) mean?

    Every per-world state array (qpos, qvel, ctrl, time, ...) gets nworld as its first dimension, e.g. d.qpos is (1024, nq). Contacts are the exception: they are pooled across all worlds in flat (naconmax, ...) arrays (Ch 6, Ch 9).

    Why does the course install mujoco-warp[viewer] instead of plain mujoco-warp?

    Plain mujoco-warp pulls mujoco-core without its [rendering] extra (plus warp-lang, numpy, absl-py, etils); [viewer] adds mujoco-core[rendering] and pillow.

    On the course's CPU box, the first mjw.step took about 25 s and the second 5 ms. What happened?

    Compiled kernels go to wp.config.kernel_cache_dir. With a warm cache the first call only loads them.

    You load a model with <option solver="PGS"/>. What happens?

    put_model compares opt.solver with mjw.SolverType, which has only CG and NEWTON.

    When is a single MJWarp world on a GPU faster than C MuJoCo on a CPU?

    One world leaves almost every GPU lane idle and still pays launch overheads. Batching worlds is the whole point.

    md.version("mujoco") raises PackageNotFoundError although import mujoco works. Why?

    Use md.version("mujoco-core") or mujoco.__version__, and never also pip install mujoco.

    A world in MJWarp blows up and its qpos becomes NaN. What does MJWarp do?

    AUTORESET is in the "unsupported" comment of DisableBit. Ch 8 writes a non-finite reset kernel.

    11Summary

    Key takeaways

    • A simulator maps state at t (qpos, qvel, act, time) plus controls and a constant model to the state at t + h.
    • MuJoCo compiles MJCF into an MjModel (constants) and keeps state in an MjData (one world, float64, CPU).
    • GPUs win on throughput: many independent worlds in one launch. One world alone is not faster.
    • Warp turns Python-written kernels into CUDA or CPU code; MJWarp is MuJoCo's pipeline as Warp kernels, maintained by Google DeepMind and NVIDIA within Newton.
    • The four calls: put_model, make_data(nworld=N), step, read arrays shaped (nworld, ...). One mjw.step is about 95 launches for the ball.
    • Setup: check the driver first, install pinned mujoco-warp[viewer]==4.0.1, set the Warp log level, confirm wp.get_cuda_device_count() > 0. The first step compiles kernels.
    • Not supported in 4.0.1: PGS, NaN checks and auto-reset, float64, PID and SO3 actuators, body/actuator/sensor plugins, some flex combinations; gradients are experimental. put_model tells you with NotImplementedError.

    Next, Ch 2 teaches the MuJoCo you need to write your own models: MJCF, joints and coordinates, geoms and soft contacts, actuators, sensors and MjSpec.
