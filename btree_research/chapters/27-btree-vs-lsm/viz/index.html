One stream of operations goes into a B+tree and into an LSM-tree. Both live on the same kind of block device, which does nothing but count: blocks read, blocks written, blocks in use. Watch who pays, and when.

What to look for

  • Writes. Every put into the B+tree reads the path and rewrites at least one whole leaf block. The LSM-tree puts the key into the memtable and touches no block at all, until the memtable is full. Then one flush writes all its keys together.
  • The bill arrives later. Press Chapter trace and step to put 3 and put 14: level 0 is full, and a compaction reads and rewrites every block of level 0 and level 1 in one operation. The bars on the right show the totals; the spike is in the single step.
  • Reads. A get on the B+tree costs one block per level, hit or miss. The LSM-tree asks the memtable, then each run from newest to oldest. A run is a small static tree: a run whose key range covers the key costs one block per index level plus one data block (2 or 3 blocks here), even if the key is not in it. Tick Predict to guess the cost of each get.
  • Deletes and overwrites. delete 15 writes a tombstone (struck through) without looking for the key. The old value and the tombstone both stay on the device until a compaction meets them.
  • The three amplifications. The last line of each card (amp) gives the chapter's ratios for the operations completed so far: write = entry slots written per put or delete (a block has 3 slots), read = blocks read per get, space = blocks in use divided by the blocks the live keys would fill if packed. A dash means there is nothing to divide by yet.
  • Growth factor. A larger growth factor makes each level hold more before it is merged down: fewer levels to search, more rewriting per level. To see it, press 12 random writes a dozen times with growth 2, then again with growth 4, and compare the levels. In so short a run the amplification lines can go either way; section 6 of the programs' output shows the trade over 12000 operations.
  • What the counters leave out. Nothing is cached: both structures pay for every block they look at, index blocks included, on every operation. There is no write-ahead log either, so the two do not promise the same thing: a B+tree put is on the device when it returns, while an LSM put sits in the memtable, in RAM only, until the next flush. A log that made every LSM put durable at once would add about one block write per put. There is no bloom filter either: with one per run, most of the probes that find nothing here would cost no block. The README puts numbers on all three.
