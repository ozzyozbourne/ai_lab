# tsp-sim — an educational simulator of a Groq-style Tensor Streaming Processor

A cycle-level simulator of one chip in the style of Groq's TSP / LPU, and a toy
compiler that schedules a small compute graph onto it with exact cycle timing.

It shows the idea the real chip is built on: the hardware has no caches, no
arbiters and no stalls. Data moves on *streams*, one position per clock cycle.
Each functional unit fires instructions from its own queue on cycles the
compiler chose in advance. If the compiler is one cycle off, the operand is not
there.

**This is not a model of the real chip's performance.** The organisation
follows the published papers; the cycle latencies do not, because Groq has
never published them. See [What is sourced and what is assumed](#what-is-sourced-and-what-is-assumed).

## Run it

Requires Python ≥ 3.11, NumPy and pytest. Nothing else.

```bash
python run_milestones.py
```

This compiles the three milestone models, runs each twice, validates the
schedule, compares the results with two NumPy references, and writes to `out/`:

| File | Content |
|---|---|
| `out/m1_timeline.html`, `m2_timeline.html`, `m3_timeline.html` | interactive timeline: every instruction queue and every stream lane, cycle by cycle (self-contained; open in a browser) |
| `out/*.program.txt` | the compiled program: one listing per instruction queue, with issue cycles |
| `out/summary.json` | cycle counts, digests and check results |
| `out/*.trace.json` | the full trace (not committed; regenerated by the command above) |

```bash
python run_milestones.py --paper-m1
```

Also runs M1 with a 320×320 matrix on the paper-scale chip preset.

```bash
python -m pytest -q
```

Runs the 309 tests (about 10 seconds).

## The milestones

| | Model | Cycles (toy chip) | Instructions |
|---|---|---|---|
| M1 | `y = relu(W·x + b)`, int8 weights, int32 result | 49 | 34 |
| M2 | two-layer MLP with requantisation, tiled over several MXM planes | 100 | 209 |
| M3 | one transformer decode step (single head, fixed length 8, fp16 weights) | 402 | 655 |
| M1 at 320×320 on the paper-scale preset | | 103 | 352 |

Cycle counts follow from the assumed latencies and would change with them. The
test `test_perturbed_latencies_still_correct` reruns every model with different
latencies: the results stay bit-identical and only the cycle counts move.

M3 is simplified: no layer normalisation, one attention head, no argmax, the
host does the embedding lookup, and the host (not the chip) appends the new key
and value to the cache for the next step. The exact definition is in
`plan.md` section 6.

## How it works

**The chip** (`tsp/hw`). A row of slices: `MXM | SXM | MEM… | VXM | MEM… | SXM | MXM`.
There are 32 streams flowing East and 32 flowing West, each one byte per lane.
An instruction issued at cycle `t` samples its operands at `t + d_skew` and its
result appears on a stream at its own position at `t + d_skew + d_func`. A
consumer `δ` positions downstream sees it exactly `δ` cycles later. A value
keeps moving until something overwrites it or it leaves the chip. Memory is the
only place a value can wait.

**The compiler** (`tsp/compiler`) runs seven passes:

1. *Tiling* — cut tensors into lane-width vectors and matrix products into unit operations.
2. *Unit assignment* — which MXM plane or SXM does each operation.
3. *Chain formation* — group operations into read → compute → write chains whose internal results flow directly from unit to unit.
4. *Timetable* — the offset of every instruction relative to its chain, from latencies and distances alone.
5. *Placement* — which memory slice, bank and address holds each stored vector.
6. *Conflict resolution* — list scheduling against reservation tables for queue slots, memory ports, MXM planes and stream cells. A conflict is resolved by trying another ALU, another parking slice, another stream, and finally a later start cycle.
7. *Emission* — one program per instruction queue, padded with `NOP`s.

No pass reads tensor values, so the schedule depends only on shapes.

**The checks** (`tsp/validate.py`, `tsp/reference.py`). The validator uses only
the program and the trace, and re-derives stream contents without the
simulator's code. It checks that every operand arrived on the exact cycle its
consumer sampled it, that no live value was overwritten, that no unit or memory
port was double-booked, and that the trace matches the program. Results are
compared with a bit-exact reference and with an independent plain-NumPy one.

## What is sourced and what is assumed

Every parameter is listed in the ledger in `research/dossier.md` section 7 with
its status and its source or reasoning. `tsp/config.py` carries the ledger ID
next to each constant, and a test fails if a constant has none. In short:

**Sourced** from the ISCA 2020 and ISCA 2022 Groq papers, which were read in full:

- the slice types and their West-to-East order; 16 lanes per superlane, 20 superlanes, 320-byte vectors;
- 32 streams per direction, one byte per lane, wider types on aligned stream groups;
- one hop per cycle; values flow until overwritten or off the edge; a slice picks its result direction;
- the form of the timing rule (`T = N + d_func + δ`) and the existence of `d_skew`;
- 88 memory slices with two banks each, one read and one write per cycle on different banks;
- four MXM planes, weights installed from 16 streams per cycle, int8 → int32 and fp16 → fp32 with one rounding step;
- 16 vector ALUs per lane and the operation names used here;
- no arbitration and no caches: conflicts are the compiler's job.

**Assumed**, because no source gives it:

- **every latency in cycles** (memory read 2, vector arithmetic 1, exp/rsqrt 3, matrix-vector product 3, switch 1, all `d_skew` 0);
- one stream-register position per slice (the paper's figure suggests one per four memory slices, so our paper-scale chip is about twice as "long" in hops);
- the whole **toy preset** (32 lanes, 16 memory slices per side, 64 words per bank);
- how instruction queues map to MXM and SXM units; that a queue issues one instruction per cycle (two for memory);
- the exact meaning of `requant`, the casts, and zero-fill on shift;
- how the two MXM planes of a hemisphere pair up for fp16;
- **the scheduling algorithm**. Nothing published describes Groq's; ours is built from the static-scheduling literature (dossier section 5).

**Not modelled:** the 20-tile diagonal wavefront (we simulate one superlane and
report `cycles + tiles − 1` for the last), `Ifetch`, `Sync`/`Notify`, `Repeat`,
gather/scatter, transpose/rotate, error correction, power, and anything
multi-chip. The ISCA 2022 multi-chip design is summarised in the dossier but not
simulated.

**Sources that could not be read:** the Hot Chips 2026 slides (HTTP 401; only
press coverage), Groq's "Inside the LPU" post, the full text of Rau's 1994
modulo-scheduling paper, and several paywalled analyses. The NVIDIA Groq 3 LPX
blog was read, but it gives no clock, lane counts or latencies for the newer
chip, so the simulator follows the 2020 paper. Details are in dossier section 1
and section 8.

## Known limits

- Bit-identical traces are guaranteed across runs and across processes on one machine. For M1 and M2 (integers only) golden digests are committed. M3 uses `exp` from the C library, which may differ in the last bit between platforms, so its digest is only compared across processes.
- A weight matrix must fit in the memory slices of one hemisphere; the compiler reports an error otherwise instead of spilling to the other side.
- Each MXM plane is used in scheduling order, so some operations start later than their ideal cycle. The compile report (`Program.report`) shows ideal and actual start cycles per chain.
- A graph cannot mix int8 and fp16 matrix products.
