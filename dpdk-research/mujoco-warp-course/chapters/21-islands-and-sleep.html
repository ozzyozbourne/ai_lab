    Islands and Sleeping

    A warehouse full of boxes that have stopped moving still costs a full physics step per box, unless the simulator notices that nothing is happening. MJWarp does this in two layers: it groups the bodies that push on each other into islands, and it lets an island that has been still for long enough fall asleep, so its contacts, constraint rows and DOFs drop out of the step until something wakes it. This chapter takes both apart, kernel by kernel, and shows every rule the 4.0.1 wheel enforces.

    Expert About 75 min· Prerequisites: Ch 20 (Newton solver), Ch 9 (contacts and overflow)

    You will learn

    • How a tree falls asleep: the tree_asleep countdown, sleep_tolerance, sleep cycles, and every way a tree wakes up.
    • Every sleep requirement put_model and make_data enforce in 4.0.1, and how to start a scene asleep without sleep="init".
    • How the compacted solve gathers only awake DOFs into nvmax_pad buffers, how to size nvmax, and why NVMAX overflow only fires with sleep on.
    • How collision runs in two passes with sleep, and when sleep makes a scene cheaper (and when it does not).

    Before you start: recap

    • Each world has its own constraint rows (efc): contacts, equalities, joint limits and friction, filled by make_constraint up to njmax per world (Ch 9 §5).
    • The Newton solver minimizes a convex cost over qacc; each iteration factors a dense Hessian of size nv (Ch 20).
    • Overflow is reported through bits in d.overflow, one int per world, decoded with mjw.OverflowType (Ch 9 §7).
    • The pipeline order is kinematics → collision → make_constraint → smooth forces → solve → integrate (Ch 7 §2).
    • A CUDA graph records launches once and replays them; conditional nodes loop on device; Ch 7 §10.

    1Islands: who is coupled to whom

    Start with the unit MJWarp reasons about. A kinematic tree is a body that hangs directly off the world body, together with all of its children. A free box is a tree with one body and 6 DOFs; a robot arm bolted to the floor is one tree with many bodies. MuJoCo numbers the trees 0 .. ntree-1, and every DOF knows its tree (m.dof_treeid), as does every body (m.body_treeid; static bodies get -1).

    Two trees are coupled when one constraint row touches DOFs of both: a contact between two boxes, a weld between two bodies, a tendon running over two arms. A contact between a box and the static floor involves only one tree: it does not couple anything, but it does make that tree constrained. An island is a maximal group of trees connected through constraint rows. Trees in different islands cannot exert any force on each other during the step, which is what makes it safe to freeze one island while another keeps moving.

    Where islands live in Data

    The output of island discovery is per world: d.nisland (shape (nworld,)) and d.tree_island (shape (nworld, ntree), the island id of each tree or -1). After a sleep-enabled solve, island.compute_island_mapping also fills the per-DOF and per-row views (d.dof_island, d.efc.island, d.island_nv, d.island_nefc, d.map_dof2idof, ...). make_data always allocates tree_island, nisland and efc.island, with or without sleep, so you can call island discovery on any Data.

    Who calls it? forward.py::fwd_position runs island.island(m, d) right after make_constraint, but only under if sleep_enabled, where sleep_enabled = SLEEP and not DisableBit.ISLAND. Without sleep the arrays keep whatever was in them (zeros and -1 from make_data). The public mjw.island(m, d) runs discovery on demand, on whatever efc rows the last forward produced.

    Read the two halves side by side. With sleep enabled, forward already filled the islands: five islands, and box 3 (in the air, no rows) is -1. With sleep disabled, forward left nisland = 0, yet the same 80 rows exist; one call to mjw.island produces the same partition, and it matches C MuJoCo, which always computes islands in mj_forward.

    2Finding islands on a GPU: a lock-free disjoint-set union

    On a CPU you would find islands with a graph search or a sequential disjoint-set union (DSU, also called union-find). Each tree starts as its own set, represented by a parent array where parent[t] = t means "t is a root". Find walks parent pointers up to the root; union makes one root the parent of the other. After processing every edge, two trees are in the same island exactly when they have the same root.

    MJWarp has to do this for thousands of worlds and thousands of rows at once, with many threads updating the same parent array concurrently. island.py::direct_dsu uses three ideas that make the parallel version safe without locks:

    1. Always hook the higher root under the lower root. Parent pointers only ever point to a smaller tree id, so no thread can create a cycle, and the final root of every island is its smallest tree.
    2. Link with compare-and-swap. wp.atomic_cas(parent, worldid, high_root, high_root, low_root) writes only if parent[high_root] is still high_root, that is, if it is still a root. If another thread got there first, the CAS fails and the loop recomputes both roots and tries again.
    3. Shorten paths with atomic_min. While walking up, _dsu_find lowers parent[current] to its grandparent when the grandparent is smaller. Because the pointers only decrease, a stale read never breaks anything: it only makes a path a bit longer.

    Island discovery, one row at a time

    How the launch is shaped

    The interesting kernel is _island_dsu. It is launched with wp.launch_tiled over (nworld, nchunk) with block_dim = BlockDim.island_dsu = 32: each block owns one chunk of one world's active rows ([0, min(njmax, nefc))), and its 32 lanes stride through the chunk. direct_dsu picks nchunk so that a small batch with many rows is still split into enough blocks, while a big batch keeps one block per world. It aims for about 2048 blocks: nchunk = min(ceil(2048 / nworld), ceil(njmax / 256)) and chunk_size = ceil(njmax / nchunk), so a world never gets more than one chunk per 256 rows of njmax (with njmax = 300 and a small batch that is 2 chunks of 150 rows). For each row the lane decides which trees it touches:

    Row type (efc.type)Trees taken from
    contact (frictionless, pyramidal, elliptic)the bodies of contact.geom[efc.id]; flex contacts use the bodies of both sides
    equality CONNECT / WELDeq_obj1id, eq_obj2id (via site_bodyid for site-based ones)
    other equalities, tendons, anything elsegeneric path: every DOF with a non-zero Jacobian entry in the row (CSR columns when sparse)
    FRICTION_DOF, LIMIT_JOINTthe tree of that DOF / joint (one tree: activates only)

    Two details keep the work small. A pyramidal contact with condim 3 has four rows that all touch the same trees; _is_repeated_fixed_support_efc skips a row whose type and id equal the previous row's. And with sleep on, a sleeping tree is dropped from the union (tree_awake == 0 → treated as -1), so islands only ever contain awake trees.

    3Where sleep lives in one step

    Sleeping is off by default. You turn it on in MJCF with <option><flag sleep="enable"/></option> (which sets EnableBit.SLEEP), or after loading with mjm.opt.enableflags |= mujoco.mjtEnableBit.mjENBL_SLEEP before put_model. Once on, it touches almost every stage of the pipeline. Figure 2 is the map; the next sections fill it in.

    Note the order: the decision to sleep happens at the very end of a step (sleep.sleep in _advance), and the wake checks happen at the start and in the middle of the next forward. A tree that falls asleep in step k is skipped from step k+1 on.

    4The sleep requirements in 4.0.1

    Sleep in MJWarp is built on the Newton solver and on compacted dense buffers, so it comes with rules. put_model rejects what cannot work; make_data decides whether to allocate the compacted workspace. All of these are from the 4.0.1 wheel:

    What does auto compile to? MuJoCo's compiler resolves each tree's policy into mjm.tree_sleep_policy: a passive box gets mjSLEEP_AUTO_ALLOWED; an actuated tree gets mjSLEEP_AUTO_NEVER, and sleep._tree_can_sleep returns False for it, so a robot never falls asleep. Example 21.6 prints all of it.

    Pitfall: SLEEP plus island="disable" crashes without nvmax

    In 4.0.1, make_data allocates the compacted buffers (d.cM, d.cJ, ...) only when sleep_enabled or nvmax is not None, and sleep_enabled is false when islands are disabled. But solver.solve tests only the SLEEP bit, so it still takes the compacted path and reads the empty (0, 0, 0) arrays. On the CPU device a single mjw.step on such a Data ends the process with a segmentation fault (exit code 139, checked while writing this chapter); on a GPU it is an out-of-bounds read. Either drop the SLEEP flag when you disable islands, or pass nvmax=mjm.nv as Example 21.6 (d) does. Do not pass a smaller nvmax here: the compact solve still runs, with every tree awake (nothing ever sleeps), so any nvmax < nv sets NVMAX on every step and the DOFs past nvmax get qacc = 0.

    The checklist is also a small function in the notebook (cell after Example 21.6), so you can run it on your own models before put_model:

print(ok, notes)        # e.g. False ['put_model raises ValueError: sleeping requires the Newton solver']

    5Falling asleep: countdowns and sleep cycles

    The whole sleep state of a world is one integer per tree, d.tree_asleep (shape (nworld, ntree)). Its sign tells you the state:

    The three kernels of sleep.sleep

    sleep.py::sleep runs at the end of every step and launches three kernels (plus _wake_non_metric_flex between the first two for flex models with a non-discrete integrator; see Ch 23). It also allocates island_can_sleep with wp.ones on every call, an allocation that matters if you capture the step in a graph:

    1. _sweep_awake_trees (one thread per world and tree). For every awake tree it calls _tree_can_sleep. A tree can sleep when its policy is not AUTO_NEVER, every body of the tree has xfrc_applied == 0, every DOF has qfrc_applied == 0, and every DOF satisfies |\ell_i\, \dot q_i| < \text{sleep\_tolerance}, where \ell_i is m.dof_length (a length scale that turns an angular velocity into a speed, so one tolerance works for both). If it can, the counter goes up by one (but never past -1); if not, it is reset to -11. opt.sleep_tolerance defaults to 1e-3 and can be batched per world.
    2. _check_island_can_sleep. An island may sleep only if all its trees are at -1. Any tree still below -1 vetoes its island with atomic_min(island_can_sleep, 0).
    3. _build_cycles (one thread per world). For each island that can sleep, it links the island's trees in ascending order into a circle (tree_asleep[prev] = next, last → first) and writes exactly zero into their qvel and qacc. A tree with no island (tree_island == -1, no constraint rows) that reached -1 becomes a self-cycle, tree_asleep[t] = t.

    From -11 it takes ten still steps to reach -1: that is mjMINAWAKE = 10. The island rule matters: a box resting on a box that is still wobbling stays awake until both are still, because putting only one of them to sleep would freeze a contact the other is still pushing on.

    Example 21.2 drops six tilted boxes from different heights and records the countdowns of world 0.

    Three things to read off. Every box is alone on the floor, so each one is its own island and becomes a self-cycle (tree_asleep[t] = t). nefc shrinks as boxes fall asleep: a sleeping box touching only static geometry produces no contact at all, because the broadphase skips asleep-static pairs (section 9). And once everything sleeps, qvel is exactly zero, not merely small: _build_cycles writes 0.0.

    6Waking up

    A sleeping tree costs almost nothing, but it must wake the moment anything could move it. MJWarp checks four kinds of triggers, at the points shown in Figure 2. All of them end in the same function, sleep.py::_wake_tree(ntree, worldid, treeid, wakeval, tree_asleep), which follows the cycle from treeid and writes wakeval into every tree of it. Waking one tree of a cycle wakes them all.

    Two subtle points. The user-change check uses zero tolerance: a sleeping tree has exactly zero velocity, so any value you write into its qvel wakes it. And wake_collision hands the woken tree the countdown value of the tree that touched it, not -11; the pair then counts down together, so they can fall asleep again in the same step.

    Part A pushes the bottom box of the stack in world 0 only: both stack boxes wake (one cycle), the loose boxes stay asleep, and world 1 is untouched (sleep state is per world). Part B writes a velocity into box 2 of world 1: it wakes at once, slides 0.1 m, hits box 3, and wake_collision wakes box 3 when the contact appears.

    Tip: reset needs no special care

    mjw.reset_data resets tree_asleep along with the rest of the state, and writing new qpos/qvel into a sleeping world is a "user change" that sleep.wake picks up at the next forward (non-zero velocity). One exception: writing only qpos with zero qvel into a sleeping tree does not wake it. Write the state, then set tree_asleep to -11 for the trees you moved (or reset the world).

    7Starting asleep without sleep="init"

    In C MuJoCo you can mark a body sleep="init" so a scene starts asleep: a warehouse that is quiet until a robot arrives. The 4.0.1 wheel rejects that policy (section 4), so the CLI uses a host-side trick. In _src/cli.py, the --init_asleep flag does, right before put_data:

    if INIT_ASLEEP.value:
  mjd.tree_asleep[:] = np.arange(mjm.ntree, dtype=np.int32)

    Every tree becomes a cycle of itself: asleep. Why does this survive put_data? Because io.py::put_data copies mjd.tree_asleep before it calls mujoco.mj_kinematics (which would reset it: "Capture sleep state before mj_kinematics, which resets tree_asleep as a side effect"), tiles it over all worlds and derives tree_awake from it.

    After one step nothing is awake, no contact exists (nacon 0), and the solver has no rows. The push wakes only box 4 of world 0, which immediately gets its floor contact back (16 rows in world 0, none in world 1). Use self-cycles only: a box stack started this way would have each box asleep alone, which is fine, because a contact with an awake neighbour wakes it.

    Note

    Starting asleep is also how the CLI benchmarks the sleep path: mjwarp-testspeed --init_asleep --nvmax=... (Ch 25). The flag only matters with a model that has sleep enabled.

    8The compacted solve and nvmax

    So far, sleeping removes contacts and rows. The second saving is in the linear algebra. The Newton solver factors a dense matrix of size nv per world (Ch 20). With sleep on, MJWarp builds that matrix only over the awake DOFs:

    1. island.update_active_dofs (launched from fwd_acceleration and again from solver.solve). The kernel built by _compact_dofs_builder runs one thread per world, walks the trees in order and, for every tree with tree_awake == 1, appends its DOFs to a compact index: dof_cdof[dof] = c and cdof_dof[c] = dof. The count is d.ncdof.
    2. Gather. There are two gathers. For the smooth acceleration, solver.smooth_solve_compact (called from fwd_acceleration on the sleep path) runs for every model, sparse or dense: _init_compact_inertia fills the dense buffer d.cM ((nworld, nvmax_pad, nvmax_pad)) with the identity, _gather_M_sparse copies the awake rows and columns of M into it, and _cholesky_factorize_solve_blocked factors it. The identity tail keeps the factorization well posed. For the constraint solve, solver._compact_gather always copies the awake DOF vectors (cqfrc_smooth, cqacc_warmstart, ...), and only for dense-Jacobian models (if not m.is_sparse) it also copies M into cM and the awake columns of the constraint Jacobian into d.cJ (_gather_J_dense). Sparse models (with the default jacobian="auto", io.py::is_sparse picks sparse when nv > 32, e.g. the 36-DOF six-box scene and Example 21.5's 96-DOF scene) skip that second copy: make_data allocates cM whenever sleep is on (or nvmax is given) but cJ only for dense models, and the compact constraint kernels read the full sparse M and J through dof_cdof/cdof_dof.
    3. Solve. solver.solve_compact shallow-replaces m and d with dataclasses.replace so that nv = nvmax_pad and the arrays are the compact ones, then runs the stock dense Newton solver on them. smooth_solve_compact does the same for the unconstrained acceleration with a blocked Cholesky.
    4. Scatter. _compact_scatter writes qacc and qfrc_constraint back to full DOF space; every DOF without a compact slot gets exactly 0. Then it recomputes efc.Ma = M qacc in full space for the integrator.

    The capacity of that compact space is nvmax, a make_data/put_data argument that defaults to nv. The buffers are nvmax_pad wide, where io.py::_nvmax_pad reserves one augmented column and rounds up to the dense tile size (TILE_SIZE_JTDAJ_DENSE = 16):

    p = 16 \left\lfloor \frac{\max(n, 1) + 16}{16} \right\rfloor

    with n = nvmax and p = nvmax_pad: 12 → 16, 16 → 32 (the augmented column needs a new tile), 36 → 48.

    If a world has more awake DOFs than nvmax, _compact_dofs maps only the first nvmax of them (in tree order), sets ncdof = nvmax, prints a warning (unless warn_overflow masks it) and ORs OverflowType.NVMAX into d.overflow. The DOFs that did not fit get zero acceleration. That is the only place in the wheel that sets the NVMAX bit, and it only runs on the sleep path: with SLEEP off (the flag itself, not just island), a too-small nvmax is simply ignored.

    Look closely at part 1. All six boxes start awake (36 DOFs) but only 12 fit. Boxes 2-5 get no slot, so their acceleration is exactly zero: they no longer respond to gravity or contact, _tree_can_sleep sees zero velocity, and they fall asleep after ten steps (tree_asleep 2..5). By step 20 only boxes 0 and 1 are awake, and they fit. All six boxes start resting on the floor, so the frozen ones look almost the same as correct ones: the simulation looks calm and plausible, and it is wrong, and the overflow bit is the only signal. In part 2 all six are still counting down (-2). Part 3 shows the sleep-off case: same nvmax, no bit, because the compacted path never ran.

    Pitfall: nvmax must cover the worst world, at the worst moment

    nvmax is one number for all worlds and the buffers are allocated once. Size it for the largest number of DOFs that can be awake at the same time in any world: at startup (everything starts awake unless you use the section 7 pattern), after a reset, and when a robot walks through the clutter. Check d.overflow for NVMAX the same way you check NARROWPHASE and CONSTRAINT bits (Ch 9). d.nv_awake gives you the awake DOF count per world to measure the peak.

    Going deeper: graph conditionals inside solve_compact

    The Newton loop normally runs inside wp.capture_while and stops when every world has converged (Ch 20). solve_compact keeps that only on CUDA: it sets graph_conditional = m.opt.graph_conditional and wp.get_device().is_cuda on the replaced options, so on Warp's CPU device the compacted loop runs all opt.iterations. That is why Example 21.5 makes the sleep path look slow on a CPU.

    The compact kernels also read the full-coordinate sparse M and J through the compaction maps on the incremental Newton path (sctx.compact_m_full, sctx.compact_d_full), instead of always multiplying gathered dense blocks.

    9Collision with sleep: two passes

    Collision detection has to solve a chicken-and-egg problem. To skip sleeping bodies it needs to know who is asleep; but a contact found this step may wake a sleeping body, and that body's other contacts must then be found too. fwd_position solves it with two passes:

    In order, fwd_position does this when sleep is on:

    1. Pass 1: collision(m, d). The broadphase skips asleep-asleep and asleep-static pairs and keeps asleep-awake pairs, the ones that may wake someone.
    2. sleep.wake_collision wakes the cycle of every sleeping tree that touches an awake tree or an awake mocap body.
    3. awake_prev = wp.clone(d.body_awake) snapshots the state pass 1 used, then sleep.update_sleep recomputes tree_awake, body_awake and the awake index lists.
    4. Pass 2: collision(m, d, awake_prev). ncollision is zeroed, nacon is kept, and the broadphase appends only pairs that involve a body that was asleep in awake_prev and is awake now. With graph_conditional, nxn_broadphase wraps only its broadphase launch in wp.capture_if(cond), where _any_awake_changed sets cond if any body changed state; the narrowphase still launches and finds 0 pairs when nothing woke.

    SAP cannot use capture_if: its sort and scan helpers allocate scratch memory internally, which a graph conditional body does not allow. So with the SAP broadphase pass 2 always launches and relies on the per-pair filter alone to drop the old pairs.

    Recall from Ch 7

    A CUDA graph records launches once and replays them; conditional nodes loop on device; Ch 7 §10. capture_if is the one-shot version of capture_while: the body runs or not depending on a device int, without a host round trip. Ch 24 owns graphs.

    Version note

    The dev tree at 8f5b9f1 moves this logic into forward.py: sleep.wake, wake_tendon, wake_collision and wake_equality take a woke flag, and update_sleep plus the second collision pass run inside wp.capture_if(woke, ...). In 4.0.1 the only capture_if on this path is the one in nxn_broadphase.

    10When sleep helps, and when it does not

    Sleep pays when a large fraction of the scene is at rest most of the time: bins of parts, warehouse shelves, piles of debris after a fall, a manipulation table where the robot touches one object at a time. It does nothing for a scene where everything moves all the time (a walking humanoid, a cartpole), and the bookkeeping (wake checks, island discovery, gather/scatter) then is pure overhead. Actuated trees default to AUTO_NEVER anyway.

    What exactly gets cheaper? Count the work that disappears for an asleep world:

    • Collision. Asleep-static and asleep-asleep pairs are dropped in the broadphase, so no narrowphase runs for them and nacon falls to 0 (Example 21.7).
    • Constraint rows. No contacts means no rows: nefc = 0, and the per-row kernels exit early for that world.
    • The solve. With fewer awake DOFs, the dense compact problem is smaller. But the launch dimensions are fixed by nvmax_pad, not by the actual awake count. The large saving comes from choosing an nvmax well below nv, which is only safe when you know how many DOFs can be awake at once.

    Example 21.5 times a 4 x 4 grid of resting boxes in three states.

    On the CPU dev box the sleep path is slower, and the reason is instructive. The compacted Newton loop runs all opt.iterations on CPU (no graph conditional), at the full nvmax_pad = 112 width (nvmax defaults to nv = 96), whether 0 or 16 boxes are awake. The work counts are what carries over: 512 contacts across the 8 worlds (64 per world) and 256 rows in world 0 drop to zero once asleep. On a GPU, measure it yourself with the notebook; the speed-up depends on how large the collision and constraint share of your step is and on how small you can make nvmax.

    Note: one batch, many worlds

    All worlds share the same launches. Sleep state is per world, so one busy world does not wake the others, but the fixed-size parts of the step (the nvmax_pad-wide solve, the per-tree kernels) are paid for every world. Think of sleep as removing per-world contact and row work, and of nvmax as the knob that shrinks the solve for everyone.

    11Check yourself

    Quiz

    You call mjw.forward on a model without the sleep flag. What is in d.tree_island?

    fwd_position calls island.island only under if sleep_enabled. The public mjw.island works on any Data (Example 21.1).

    A model has <flag sleep="enable" island="disable"/> and the Euler integrator. What happens?

    Disabling islands disables sleep. In 4.0.1 make_data then skips the compact buffers, but solver.solve still takes the compact path: pass nvmax or drop the SLEEP flag.

    Which SleepPolicy values does 4.0.1 accept?

    types.py::SleepPolicy: "unsupported: NEVER, ALLOWED, INIT". Only the compiler-chosen AUTO values pass put_model.

    With sleep disabled you pass nvmax=6 for a model with nv = 36. Why is no NVMAX bit ever set?

    update_active_dofs is called from fwd_acceleration and solver.solve only when SLEEP is on. Without sleep the full-size solver runs and nvmax is unused (Example 21.4, part 3).

    A tree has tree_asleep = -4 and its island partner is at -1. Both stay perfectly still. When do they fall asleep?

    -4 → -3 → -2 → -1 takes three sweeps; in the third, _check_island_can_sleep finds every tree at -1 and _build_cycles links both.

    World 0 has tree_asleep = [2, 3, 1, 0, 4]. You write a velocity into tree 1. Which trees wake?

    Follow the pointers from 1: 1 → 3 → 0 → 2 → 1. That is one cycle of four trees; tree 4 points to itself.

    In _dsu_union, why is the higher root always hooked under the lower root?

    Monotone pointers make the CAS-based union safe without locks, and _label_roots can number islands in MuJoCo's order (ascending smallest tree).

    Where does sleep save the most work?

    Most parts rest most of the time: their contacts with the bin and with each other vanish, and nvmax can be sized for the few parts that move.

    An awake box (countdown -5) lands on a sleeping box. What value does wake_collision write into the sleeping box's cycle?

    _wake_collision_kernel passes wakeval = tree_asleep[awake tree], so the pair counts down together.

    13Summary

    Key takeaways

    • An island is a group of kinematic trees connected by constraint rows; tree_island holds the id per tree, -1 for trees with no rows.
    • island.py finds islands with a lock-free DSU: hook the higher root under the lower with atomic_cas, shorten paths with atomic_min, then compress, label in ascending order and propagate.
    • forward runs island discovery only with sleep enabled; mjw.island(m, d) runs it on demand.
    • tree_asleep: -11 .. -1 is an awake countdown, ≥ 0 is the next tree in a sleep cycle. Ten still steps (mjMINAWAKE) and a whole island at -1 make a cycle; qvel and qacc become exactly 0.
    • User changes, contacts with awake trees, active equalities and tendons wake a tree, and waking one tree wakes its cycle.
    • 4.0.1 requires Newton, the default island flag, sleep="auto" bodies and no flex equality; start asleep by writing tree_asleep = arange(ntree) before put_data.
    • The awake DOFs are solved in nvmax_pad-wide compact buffers. Size nvmax for the worst moment and check the NVMAX bit, which exists only on the sleep path.
    • Sleep pays for mostly resting clutter, not for always-moving robots; measure it on the GPU.

    Stuck? See Troubleshooting or the course map.
