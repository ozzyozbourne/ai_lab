    Part II · Chapter 08

    Resets, State, Mocap and Control Loops

    A simulator you can only step forward is a toy. Real work needs more: end an episode in some worlds while the rest keep running, save a state and come back to it, move a target in every world, switch a constraint on and off, and run your own controller inside the step. This chapter shows how MJWarp does each of these for thousands of worlds at once, without ever leaving the GPU.

    Intermediate About 90 min· Prerequisites: Ch 7 (and through it Ch 6)

    You will learn

    • Reset all worlds or only some (reset_data(reset=mask)), or reset each world to its own keyframe (-1 = leave it alone).
    • Why a reset does not recompute kinematics, and when you must call forward.
    • Snapshot and restore any part of the state with get_state / set_state and the mjw.State bits, and why a bitwise replay also needs WARMSTART.
    • Drive one mocap target per world and switch equality constraints per world with d.eq_active.
    • Put a controller in the loop with step1 / step2 or m.callback.control; how ctrlrange clamps on read.
    • Build a device-side auto-reset with a done kernel and a NaN guard, and use worlds as parallel rollouts for sampling-based MPC.

    Before you start: recap

    • Every Data array has the world index first: d.qpos is (nworld, nq), d.mocap_pos is (nworld, nmocap) of vec3 (Ch 6 §1).
    • Write inputs in place with .assign(...) or a kernel; replacing the array object (d.ctrl = wp.array(...)) breaks captured graphs (Ch 6 §5, replace vs assign).
    • mjw.step = forward (position, velocity, actuation, acceleration, solve, with sensor taps) + integrate. The breadcrumb below is that pipeline (Ch 7 §1).
    • On a GPU each .numpy() is a device-to-host copy and a sync; keep them out of the hot loop (Ch 4 §2).
    • A keyframe, a mocap body and an equality constraint are MJCF features (Ch 2 §5 and §6).

    1reset_data: start over, in all worlds or just some

    In C MuJoCo you reset one simulation with mj_resetData. MJWarp has the same idea, but a batched simulator needs one more thing: you rarely want to reset every world. In reinforcement learning, world 17 may have fallen over while world 18 is in the middle of a good episode. So mjw.reset_data(m, d, reset=None) takes an optional per-world mask.

    • reset=None: every world is reset.
    • reset=mask: a wp.array of shape (nworld,), dtype bool or any integer type. World w is reset when mask[w] is True / nonzero. Any other shape or dtype raises ValueError. An integer mask is first cast to a fresh bool array; a bool mask is used as is.

    The whole loop below is one picture of what this chapter builds: step all worlds, look at them on the device, decide which ones are done, reset only those, let your controller write the next inputs, step again. No step of this loop copies data to the host.

    What a reset writes

    reset_data launches a handful of small kernels (all in io.py), each of which starts with the same two lines: worldid = wp.tid() and, when a mask was given, if not reset_in[worldid]: return. A world outside the mask is not touched at all. For a world inside the mask, three things happen:

    Two details are worth noticing. First, qacc_warmstart is zeroed. The constraint solver starts each step from this guess (§4), so a reset world's first solve starts cold, just as a fresh make_data does. Second, ctrl is zeroed too: if your policy writes ctrl before the step, write it after the reset.

    Worlds 0 and 2 went back to t = 0 and the start height; worlds 1 and 3 did not notice anything. After five more steps the reset worlds are exactly five steps "younger". The stepper below replays this run frame by frame, using the numbers the script recorded with --dump-json.

    Tip: a bool mask is the graph-friendly one

    With a bool mask, reset_data uses your array directly. With an integer mask it allocates a new bool array and casts into it on every call, and with reset=None it allocates wp.ones(nworld). Allocation inside a captured CUDA graph is a thing to avoid (Ch 24), so in a hot loop keep a preallocated wp.array(dtype=bool) that your done kernel writes.

    Going deeper: the kernels behind one call

    In the 4.0.1 wheel, one reset_data call launches, in order: reset_xfrc_applied (dim=(nworld, nbody, 6)), reset_M (dim=(nworld, M.shape[1])), reset_mocap (dim=(nworld, nbody): a thread per body checks body_mocapid >= 0), reset_contact (dim=naconmax: one thread per contact slot, skips slots past nacon and slots of unmasked worlds), reset_sleep and reset_nworld (dim=nworld, the per-world loops over nq, nv, nu, ...). Then history.reset_history if the model has delays (nhistory > 0), reset_plastic if it has plasticity, and sleep.update_sleep if sleep is enabled. All kernels are defined inside the function with module="unique"; Warp caches them after the first call, but the Python-side definition still runs on every call, which is one reason to capture the reset in a CUDA graph on the GPU (Ch 24, Ch 26).

    2reset_data_keyframe: a different start per world

    A keyframe stores a full starting state: time, qpos, qvel, act, ctrl, the mocap poses and the plastic references. mjw.reset_data_keyframe(m, d, key) first calls reset_data with a mask and then copies the keyframe in. The key argument comes in two forms:

    keyMeaningOut of range
    a Python intevery world goes to that keyframeValueError("key (1) must be in [0, 1).")
    a wp.array of int32 (dtype=int), shape (nworld,)world w goes to keyframe key[w]that world is left untouched (not reset at all). -1 is the usual "skip" value.

    The array form is how you start different worlds from different poses (for example, a library of start states for a curriculum), and how you skip worlds without building a separate bool mask. Inside, a kernel valid_key_mask turns the ids into mask[w] = key >= 0 and key < nkey, and that mask drives both the plain reset and the keyframe copy (reset_keyframe_data).

    Pitfall: the int form cannot skip

    Only the array form treats an out-of-range id as "skip". A plain int out of range raises. And the array must have an int32 dtype (Warp's int): a float array raises ValueError("key array must be of integer type, ..."), and an int64 array, which is what wp.array(np.array([0, -1, ...])) gives on Linux, passes that check but fails at launch: RuntimeError: Error launching kernel '...valid_key_mask', argument 'key_in' expects an array with dtype=int32. Build it with wp.array(..., dtype=int). (The reset mask of reset_data is less strict: it accepts any integer dtype.)

    3Stale derived data: call forward after a reset

    MuJoCo separates the state (what you need to continue a simulation: qpos, qvel, act, time, ...) from the quantities the pipeline computes from it (body poses, contacts, forces, sensors). A reset writes the state. It does not run the pipeline. So right after reset_data, d.xpos still holds the body positions of the old episode, and d.sensordata holds zeros (the reset zeroed it). If you read observations at this point, you read garbage.

    The fix is one call: mjw.forward(m, d) runs the whole pipeline (position, velocity, actuation, acceleration, solve, sensors) without integrating, so time does not move.

    Look at the first line again: even during normal stepping, xpos (0.0990) is not quite qpos (0.1001). That is not a bug. mjw.step computes xpos in the position stage, then integrates qpos. After a step, the derived quantities describe the state at the start of that step, one timestep behind qpos. The timeline makes both effects visible.

    Do you always need forward?

    No. If the next thing you do is mjw.step, the step's own position stage recomputes everything first, so a reset followed directly by a step is correct. You need forward when you read derived quantities before the next step: observations for a policy, sensor values, a rendered frame, contact counts.

    4Snapshots: get_state, set_state and State signatures

    A reset takes you back to the start. Often you want to go back to some moment: try an action, look at the result, undo it. That needs a snapshot. MJWarp copies MuJoCo's design: a state signature sig is an integer whose bits name the components you want, and two functions move those components between Data and a plain float array:

    sig = int(mjw.State.PHYSICS | mjw.State.WARMSTART)
buf = wp.zeros((d.nworld, mujoco.mj_stateSize(mjm, sig)), dtype=float)   # one row per world
mjw.get_state(m, d, buf, sig)            # Data -> buf
mjw.set_state(m, d, buf, sig)            # buf -> Data
mjw.set_state(m, d, buf, sig, active)    # only where the bool mask active[w] is True

    Each world's row is the concatenation of the selected components in bit order, not in the order you wrote them. One thread per world walks the 15 bits from low to high and appends each selected component (support.py::get_state). mujoco.mj_stateSize(mjm, sig) from C MuJoCo gives the row length, so the layout is identical to C MuJoCo's mj_getState.

    Four composites cover the usual needs. Their values come straight from mujoco.mjtState:

    • PHYSICS = QPOS | QVEL | ACT | HISTORY | PLASTIC = 16414: everything the dynamics integrate. It includes the delay buffers and the plastic references, so models with delays or plasticity restore correctly.
    • FULLPHYSICS = TIME | PHYSICS | PLUGIN = 24607.
    • USER = CTRL | QFRC_APPLIED | XFRC_APPLIED | EQ_ACTIVE | MOCAP_POS | MOCAP_QUAT | USERDATA = 8128: the inputs you set.
    • INTEGRATION = FULLPHYSICS | USER | WARMSTART = 32767: all 15 bits.

    Docstring vs value: PHYSICS has no TIME bit

    The types.py::State docstring says "PHYSICS: TIME | QPOS | QVEL | ACT | HISTORY | PLASTIC", but the enum member is mujoco.mjtState.mjSTATE_PHYSICS, which is 16414 and does not contain TIME (Example 8.4 prints includes TIME? False). After restoring a PHYSICS snapshot, d.time keeps whatever it was. Add State.TIME when your controller, reward or a time-dependent input reads d.time.

    Why QPOS | QVEL is "almost" a snapshot

    Take a scene with resting contacts, snapshot qpos and qvel, run 30 steps, restore, run the same 30 steps again. You would expect the same numbers. You get numbers that differ in the 8th digit. The missing piece is the solver's warmstart: every step, the constraint solver (Ch 20) starts iterating from d.qacc_warmstart, the acceleration of the previous step, and stops at a tolerance. Start from a different guess and it stops at a slightly different answer. After the restore, qacc_warmstart still holds the value from the end of the reference run, so the first replayed solve starts from a different guess. Add State.WARMSTART and the replay is bitwise identical (on CPU, and on GPU when the run is deterministic, Ch 22).

    For two free boxes, nq = 14 and nv = 12, so QPOS | QVEL is 26 floats. PHYSICS is also 26 because this model has no actuators, delays or plasticity. WARMSTART adds nv = 12, TIME adds 1. "time replayed exactly" is only True when TIME is in the signature.

    Pitfall: get_state does not check the buffer size

    The kernel writes state_out[worldid, adr + j] for every selected component, whatever the shape of your array. An undersized buffer is written out of bounds: on CPU that can crash the process, on GPU it silently corrupts other memory. Always allocate with wp.zeros((d.nworld, mujoco.mj_stateSize(mjm, sig)), dtype=float) and assert the shape. The snapshot / restore helpers this chapter adds to my_env.py do exactly that. A sig with bits at or above 1 << NSTATE raises ValueError.

    5Mocap bodies: one target per world

    A mocap body is a body that the physics does not move: you do. It is declared with mocap="true", must be a child of the world body and has no joints. Its pose is input data: d.mocap_pos with shape (nworld, nmocap) of vec3 and d.mocap_quat of quat. Mocap bodies are the standard way to drive a target, a hand, a moving platform or a "ghost" that a real body is welded to. In a batch, every world gets its own target.

    This chapter owns the shared model MOCAP_TARGET (plan model M10): a mocap body target with a non-colliding geom, and a free box welded to it. Compiled with mujoco 4.0.1 it has nmocap = 1, neq = 1, nq = 7, nv = 6.

    <geom name="floor" type="plane" size="5 5 .1"/>

    The lag grows linearly with the target's speed: distance / speed is 0.0398 s in every world. That is the steady-state lag of a critically damped spring-damper following a ramp, about twice the weld's time constant solref[0] = 0.02. The shape printed as (8, 1) because Warp reports vector arrays by their element count; each element is a vec3.

    Pitfall: mocap is input, so a reset overwrites it

    reset_data sets mocap_pos/mocap_quat back to the body's pos/quat from the model, and reset_data_keyframe to the keyframe's mpos/mquat. Your target kernel must run again after every reset, before the next step. Snapshots include mocap only with MOCAP_POS | MOCAP_QUAT (part of USER, not of PHYSICS).

    6Switching equality constraints per world

    Each equality constraint (connect, weld, joint, tendon, flex) has an on/off switch per world: d.eq_active, a bool array of shape (nworld, neq). make_data and reset_data fill it from m.eq_active0 (the MJCF active attribute, default true). Every equality kernel in constraint.py begins with

    if not eq_active_in[worldid, eqid]:
    return            # no rows for this constraint in this world

    So switching a constraint off does not weaken it: it removes its rows from that world's constraint problem for the next step. That gives you grasping and releasing (weld a gripper to an object, then switch it off), attaching and detaching parts, and scripted events, each world on its own schedule. You write it like any other input: d.eq_active.assign(...) from the host, or a kernel on the device (Exercise 8.2).

    After one step the picture is clean: 6 equality rows (ne) where the weld is on, none where it is off. After 100 steps the odd worlds have more rows, not fewer: their box lies on the floor with 4 contacts, and each pyramidal contact with condim = 3 adds 4 rows (Ch 9 explains the count). Use d.ne to see equality rows alone. The efc strip below shows the real row layout of four worlds after 100 steps.

    Where does the box go when you switch the weld on?

    A weld holds the relative pose stored in the model (eq_data; for MJCF welds without relpose it is taken from the model's initial configuration). For MOCAP_TARGET that pose is "box at the target". Switching the weld on while the box is 5 cm away therefore pulls it onto the target within a few time constants. Exercise 8.2 does exactly this.

    Source: sleep and equality

    In the 4.0.1 wheel, forward.py::fwd_position calls sleep.wake_equality(m, d) only when sleep is enabled and m.neq > 0: a sleeping body tied by an active equality to an awake one is woken up. Without sleep (the default) it is not called. Ch 21 covers sleep.

    7Control in the loop: step1, your policy, step2

    A feedback controller reads the current state (or the sensors) and computes the input for this step. With a plain mjw.step loop you can only read what the previous step left behind: the sensor values in d.sensordata after a step were computed at the start of that step, before the integrator moved the state (§3). MJWarp splits the step in two, like C MuJoCo's mj_step1 and mj_step2, so your code can run in the gap with fresh data:

    Three lessons sit in this output. A PD controller has a steady-state error under gravity: the spring kp · e must hold the gravity torque, so e ≈ τ_g / kp; the measured mean error is close to that estimate (the second link swings freely, so the error oscillates around it). Fresh sensors make a small but real difference (6.7e-4 rad here, more for fast or stiff controllers). And RK4 does not survive the split.

    Pitfall: step1 / step2 with RK4

    step2 integrates with implicit / implicitfast or discrete when the model uses them, and with Euler in every other case, including RK4. If you need RK4 and a controller, use m.callback.control (§9) or set ctrl before mjw.step. Know what the callback sees then: rungekutta4 calls _forward(m, d, skip_sensor=True) three more times per step, so the callback runs 4 times per mjw.step. In stages 2 to 4, d.qpos / d.qvel hold that stage's intermediate state, not the state at the start of the step, while d.sensordata still holds the stage-1 values (sensors are skipped). A sensor-reading controller like Example 8.9's mixes perturbed state with stale sensors, and any Python-side counter or stateful controller term (an integrator, a filter) advances 4x per step.

    8ctrlrange clamps on read; d.ctrl is never changed

    An actuator with ctrllimited and ctrlrange="-5 5" never applies more than 5. But the clamp happens inside the actuation kernel, on a local copy:

    # util_misc.py::clamp_ctrl, called from forward.py::_actuator_force
# (one thread per (world, actuator))
u = ctrl_in[worldid, adr]
if actuator_ctrllimited[adr] and not dsbl_clampctrl:
    ctrlrange = actuator_ctrlrange[worldid % actuator_ctrlrange.shape[0], adr]
    u = wp.clamp(u, ctrlrange[0], ctrlrange[1])
return u

# the call site in _actuator_force
ctrl = 0.0
if ctrlnum > 0:
    ctrl = util_misc.clamp_ctrl(actuator_ctrllimited, actuator_ctrlrange, ctrl_in, worldid, uadr, dsbl_clampctrl)

    So d.ctrl keeps whatever you wrote. This matters when you log actions, compute an action cost from d.ctrl, or compare against a policy's output: you see the raw value, not the applied one. The applied value shows up in d.actuator_force, the force in actuator space (gain · ctrl + bias, after the clamp). The gear is not part of it: the transmission applies it afterwards, so it shows up only in d.qfrc_actuator. Note also that actuator_ctrlrange is indexed with worldid % shape[0]: it can be a batched field, different per world (Ch 10). Setting DisableBit.CLAMPCTRL turns the clamp off; the flag is passed to the kernel as an ordinary argument, so changing it does not recompile.

    Delays change where ctrl comes from

    If the model has actuator delays (nhistory > 0), fwd_actuation first reads a delayed copy of the controls from the history buffer (history.read_ctrl_delayed) and clamps that. Ch 14 covers delays; State.HISTORY (inside PHYSICS) is what keeps them correct across snapshots.

    9Callbacks: code that runs inside the step

    step1 / step2 works, but it means your loop is three calls, and a mjw.step you capture in a CUDA graph (Ch 24) or call from a library (a viewer, mjwarp-testspeed) has no gap for you. The alternative is a callback: a plain Python function fn(m, d) stored on the model. MJWarp calls it at a fixed point in the pipeline, every time that point is reached. put_model creates an empty types.Callback() with seven slots:

    A callback is Python, and a graph remembers only kernels

    The callback runs on the host each time the pipeline reaches its socket. All it should do is launch kernels. When you capture mjw.step in a CUDA graph (Ch 24), the callback runs once, during capture; the graph records its kernel launches and replays them every time. Python side effects (the calls counter above, a print, reading .numpy(), choosing a kernel with an if on a device value) happen only at capture time. Keep all decisions inside the kernels.

    10Device-side auto-reset and a NaN guard

    Put §1-§3 together and you get the core of every batched RL environment: after each step, decide on the device which worlds are done, reset those, and continue. Nothing in this loop needs the host, so it runs without host round-trips and can be captured in a CUDA graph together with the step (Ch 24, Ch 26).

    It is not free, though. reset_done ends with mjw.forward(m, d) on every world on every iteration, also when no world is done. forward is the whole pipeline except the integrator (position, velocity, actuation, acceleration and the constraint solve), so the loop costs about one extra forward pass per step. It is unconditional on purpose: an if done.any() would need a host read and would break graph capture. A cheaper variant needs a conditional graph node around the forward (Ch 24), or reads the observations after the next step instead. Time both on your own GPU before you decide; this page has no GPU numbers for it.

    One more ingredient is needed because MJWarp, unlike C MuJoCo, has no NaN checks. C MuJoCo's mj_checkPos / mj_checkVel / mj_checkAcc reset a simulation that produced a NaN or a huge value and raise a warning. MJWarp has no equivalent and no auto-reset (the DisableBit comment lists AUTORESET as unsupported). A world that blows up keeps its NaNs forever, and an RL learner that reads them can be poisoned. So the done mask also gets a non-finite guard: a kernel that sets done[w] when any qpos or qvel entry is NaN or infinite.

    Three rules for done kernels

    • Preallocate. done, counters and random-number state are allocated once, before the loop (and before any graph capture).
    • OR, don't overwrite, when combining reasons. The guard kernel only ever sets done[w] = True, so it cannot cancel a reason set by an earlier kernel.
    • Randomize after reset_data, before forward. reset_data zeroes qvel and ctrl; any per-episode randomization (initial velocity, target, mass via Ch 10) must run after it, and before forward: randomizing after forward leaves every velocity-dependent quantity (cvel, velocity sensors, qfrc_bias) stale when you read the observation. reset_done(m, d, done, randomize) calls your randomize(m, d, done) in that slot. Seed with something that changes per episode (here worldid and the episode counter), or every episode of a world repeats the same throw.

    11Worlds as parallel rollouts: sampling-based MPC

    So far every world was a separate experiment. Here is a different use of the same batch: all worlds are copies of one system, and each copy tries a different future. Model predictive control (MPC) with random shooting works like this:

    1. Snapshot the current state (all worlds are identical, so any row would do).
    2. Sample one random action sequence per world: KNOTS = 10 values, each held for HOLD = 5 steps, a 0.5 s horizon.
    3. Roll out all worlds for the horizon while a kernel adds up an "upright" reward per world.
    4. Choose the world with the best score (a one-thread argmax kernel, still on the device).
    5. Restore the snapshot in every world, apply the best sequence's first action for one knot, and repeat from 1.

    Because every world gets the same first action after the restore, the worlds stay bitwise identical as long as no constraint is active: the batch is both the real system and the planner's scratch space. The TIME | PHYSICS restore leaves each world's qacc_warmstart from its own rollout, so once the slider limit or a contact becomes active the worlds can drift apart; add WARMSTART to keep them identical then. How the wall time of one planning iteration compares with one rollout on a GPU is for you to measure: time the loop in the notebook on your own GPU (call wp.synchronize() before reading the clock). The snapshot uses TIME | PHYSICS: PHYSICS carries the delay and plasticity state for models that have them, and TIME is added so that d.time does not jump forward by a horizon on every iteration. The cartpole has a joint limit but no contacts; add WARMSTART if your rollouts must reproduce bitwise.

    With only 64 random samples per iteration the planner brings the pole from 0.4 rad to about 0.01 rad in one second; with no force it falls over and swings around (4.7 rad).

    Look at the cart line of the output, though: after one second the cart is already 0.98 m from the centre of a rail that ends at ±1.8 m. The reward penalises the cart position only weakly (0.05 * x * x), and a 0.5 s horizon is too short to see the end of the rail coming, so this planner lets the cart drift. Run it for 40 iterations instead of 20 and the cart reaches the slider limit after about 1.8 s. From then on the limit constraint is active, and the TIME | PHYSICS snapshot (no WARMSTART) can let the worlds drift apart, as described above; in a CPU run with sampling seed 11 instead of 7 the pole was then lost. The interactive demo in the notebook fixes the cost: a 1 s horizon and a reward that also penalises the cart position and velocity (0.2 * x * x + 0.05 * xdot * xdot) keep the cart within about 1.1 m (CPU run from 0.4 rad, 64 samples, seed 11, 2 s). Always print the state variables your reward does not care much about.

    Step through the real planning iterations below: the faint coloured lines are 15 of the 64 sampled futures, the thick accent-coloured line is the winner, and the solid line in the text colour, ending in a dot, is what actually happened.

    Where this goes next

    Random shooting throws away everything it learned at each iteration. The cross-entropy method (CEM) keeps the best samples, fits a distribution to them and samples again; Ch 29 extends this example to CEM with the same State.PHYSICS snapshots, and uses gradients through the simulator as another way to choose actions.

    12Check yourself

    Quiz

    After mjw.reset_data(m, d, reset=mask), which of these is not reset in a masked world?

    xpos is derived by the position stage. It keeps the old episode's values until forward or step runs.

    reset_data_keyframe(m, d, wp.array([0, -1, 2, 0], dtype=int)) on a model with nkey = 2. What happens to world 2?

    Key 2 is outside [0, nkey), so valid_key_mask gives False and the world is skipped, exactly like -1.

    You restore a QPOS | QVEL snapshot in a scene with resting contacts and replay the same steps. Why can the result differ in the last digits?

    The iterative solver stops at a tolerance, so its answer depends on its starting guess. Add State.WARMSTART for a bitwise replay.

    What is bool(mjw.State.PHYSICS & mjw.State.TIME) in mujoco-warp 4.0.1?

    PHYSICS = QPOS | QVEL | ACT | HISTORY | PLASTIC; FULLPHYSICS adds TIME (and PLUGIN).

    How does a mocap body differ from a free body?

    _kinematics_branch copies mocap_pos_in[worldid, mocapid] into xpos. Forces act on bodies attached to it (here through the weld), never on it.

    You set d.eq_active[w, k] = False. What changes in world w at the next step?

    Each equality kernel returns early when eq_active_in[worldid, eqid] is False, so ne drops by that constraint's rows.

    A model uses integrator="RK4". You run step1, a policy kernel, step2. How is the step integrated?

    Use m.callback.control with mjw.step if you need RK4 and a controller. It then runs 4 times per step: stages 2 to 4 see the stage's intermediate qpos / qvel (not the step's start state) and stage-1 sensordata, so counters and stateful controller terms advance 4x per step.

    An actuator has ctrlrange="-1 1". You write ctrl = 3 and step. What do you read back?

    The clamp works on a local copy in the kernel: raw input stays in d.ctrl, the applied value shows in actuator_force (for a motor, gain 1, no bias). The gear is applied by the transmission, so it appears only in qfrc_actuator.

    Your m.callback.control increments a Python counter. You capture mjw.step in a CUDA graph and launch it 1000 times. What is the counter?

    A graph records kernel launches. Callbacks must put all their logic inside kernels.

    14Summary

    Key takeaways

    • reset_data(m, d, reset=mask) resets only the worlds where the bool / int mask of shape (nworld,) is set: qpos ← qpos0, mocap ← body pose, eq_active ← eq_active0, and time, qvel, ctrl, act, warmstart, applied forces, sensordata zeroed.
    • reset_data_keyframe takes an int (all worlds, must be valid) or a per-world int array (out-of-range ids such as -1 skip the world).
    • Resets write state, not derived data: call mjw.forward before reading xpos, sensors or contacts.
    • get_state / set_state pack the mjw.State bits in bit order into a (nworld, mj_stateSize) array. Use PHYSICS (+TIME if anything reads d.time) for MPC (PHYSICS has no TIME bit), add WARMSTART for bitwise replays, INTEGRATION for everything. The buffer size is not checked: allocate with mj_stateSize.
    • d.mocap_pos / d.mocap_quat are per-world inputs read by kinematics; d.eq_active switches equality rows on and off per world.
    • step1 / policy / step2 gives the controller fresh sensors (RK4 falls back to Euler); m.callback.control puts it inside step and inside a captured graph (under RK4 it runs 4 times per step, 3 of them with stale sensors).
    • ctrlrange clamps inside _actuator_force; d.ctrl keeps the raw value.
    • Auto-reset = done kernel + NaN guard + masked reset + randomize + forward, all on the device. Worlds can also be identical copies that try different futures: random-shooting MPC.

    Stuck? See Troubleshooting (NaN blow-ups, undersized state arrays) or the course map. Next: Ch 9 sizes the contact and constraint buffers these scenes have been using.
