Chapter 9

Tooling, Production, RAG and Online Evaluation

GitHub runs more than 4,000 offline tests on every Copilot model candidate, most of them in CI, and then switches a group of its own employees to the new model before anyone else sees it[1]. Even with all that, its headline online metric turned out to be the wrong one: optimising the suggestion acceptance rate “could lead to incorrectly favoring a high volume of simple and short suggestions”, so the team now also optimises accepted-and-retained characters[2]. That one story holds the two halves of this chapter. The first half is tooling, and its punchline is that every eval tool you will meet is the same loop (dataset → solver → scorer → log → metric) with a different spelling. The second half is production, where the loop runs on live traffic that has no labels, and the hard questions are which number to trust, how sure to be, and what to do when it moves.

9.1Map of the territory

There are now hundreds of open-source eval projects, and new ones appear every month. The good news is that they sort into six layers by the question they answer, and most real stacks use one tool from two or three layers[3]. The lower layers are model-centric: they answer “how capable is model or agent X?” on a fixed public benchmark. The upper layers are product-centric: they answer “did my change to my application regress?” on my own data. Anthropic’s agent-evals guide draws the same line between the evaluation harness (runs tasks, records, grades, aggregates) and the agent harness or scaffold (lets the model act), and stresses that when you evaluate an agent you evaluate the two together[3].

9.2Anatomy of a harness

The fastest way to understand any eval tool is to write a small one yourself. Every tool in Table 9.1 has the same parts (Chapter 1.2 introduced the vocabulary):

  • a dataset of samples, each with an input and a target (Inspect Sample, lm-eval “doc”, Harbor task directory, verifiers TaskData);
  • a solver that turns a sample into a transcript (Inspect solver, Braintrust task, LangSmith target, Weave Model.predict);
  • a scorer that turns a transcript into a score (scorer, grader, evaluator, metric, reward: all synonyms);
  • a runner that schedules many solver calls concurrently, repeats them for several epochs, and writes a log;
  • an aggregate with an error bar.

The listing below is the core of mini_harness.py, an Inspect-shaped harness in about 150 lines. Three design choices matter more than they look. First, concurrency is capped by an asyncio.Semaphore, because real providers rate-limit you. Second, the mock model draws its randomness from a generator seeded by (seed, sample id, epoch), so the result does not depend on which coroutine happens to finish first; with a shared generator, changing max_concurrency would change your score. Third, scores pass through value_to_float, which copies Inspect’s conversion of "C"/"I"/"P"/"N" to 1/0/0.5/0, including its behaviour of mapping an unknown string to 0.0[22].

class MockModel:
    """Seeded stand-in for an LLM. Per-category skill; per-(sample, epoch) RNG so that the
    output does not depend on the order in which concurrent coroutines happen to run."""

    SKILL = {"add": 0.95, "sub": 0.80, "mul": 0.60, "div": 0.40}

    def __init__(self, seed: int = 0, latency_s: float = 0.002):
        self.seed, self.latency_s = seed, latency_s

    async def generate(self, sample: Sample, epoch: int) -> str:
        rng = random.Random(f"{self.seed}:{sample.id}:{epoch}")
        await asyncio.sleep(self.latency_s * rng.random())          # pretend network latency
        if rng.random() < self.SKILL[sample.metadata["category"]]:
            return f"Let me compute. ANSWER: {sample.target}"
        return f"Let me compute. ANSWER: {int(sample.target) + rng.choice([-2, -1, 1, 10])}"


def generate(model: MockModel) -> Solver:       # the simplest solver: call the model once
    async def solve(state: TaskState) -> TaskState:
        state.messages.append({"role": "user", "content": state.sample.input})
        state.completion = await model.generate(state.sample, state.epoch)
        state.messages.append({"role": "assistant", "content": state.completion})
        return state
    return solve


def match_answer() -> Scorer:                   # like Inspect's pattern()/answer() scorers
    async def score(state: TaskState, target: str) -> Score:
        m = re.search(r"ANSWER:\s*(-?\d+)", state.completion)
        if not m:
            return Score("I", "", "invalid_response_format")
        return Score("C" if m.group(1) == target else "I", m.group(1))
    return score


def pass_fail_scorer() -> Scorer:               # a home-made scorer that returns "pass"/"fail"
    async def score(state: TaskState, target: str) -> Score:
        ok = (await match_answer()(state, target)).value == "C"
        return Score("pass" if ok else "fail")
    return score


def value_to_float(v: str | float) -> float:
    """Inspect-style conversion: C/I/P/N -> 1/0/0.5/0. Unknown strings become 0.0 silently."""
    if isinstance(v, (int, float)):
        return float(v)
    return {"C": 1.0, "I": 0.0, "P": 0.5, "N": 0.0}.get(v, 0.0)


async def run_task(task: Task, max_concurrency: int = 8, log_path: pathlib.Path | None = None):
    sem = asyncio.Semaphore(max_concurrency)
    in_flight = peak = 0

    async def one(sample: Sample, epoch: int) -> dict:
        nonlocal in_flight, peak
        async with sem:                                             # cap concurrent model calls
            in_flight += 1
            peak = max(peak, in_flight)
            state = await task.solver(TaskState(sample, epoch))
            sc = await task.scorer(state, sample.target)
            in_flight -= 1
        return {"task": task.name, "id": sample.id, "epoch": epoch,
                "category": sample.metadata["category"], "messages": state.messages,
                "score": asdict(sc), "value": value_to_float(sc.value)}

    jobs = [one(s, e) for e in range(task.epochs) for s in task.dataset]
    records = await asyncio.gather(*jobs)                           # results come back in job order
    if log_path:
        log_path.parent.mkdir(exist_ok=True)
        with log_path.open("w") as f:
            for r in records:
                f.write(json.dumps(r) + "\n")
    return records, peak


def accuracy_and_stderr(records: list[dict]) -> tuple[float, float, float]:
    """Mean over all (sample, epoch) rows; naive SE treats rows as independent, the
    clustered SE treats epochs of the same sample as one cluster (Chapter 5)."""
    v = [r["value"] for r in records]
    n, mean = len(v), sum(v) / len(v)
    sd = math.sqrt(sum((x - mean) ** 2 for x in v) / (n - 1))
    naive = sd / math.sqrt(n)
    clusters: dict[str, float] = {}
    for r in records:
        clusters[r["id"]] = clusters.get(r["id"], 0.0) + (r["value"] - mean)
    g = len(clusters)
    clustered = math.sqrt(g / (g - 1) * sum(c * c for c in clusters.values())) / n
    return mean, naive, clustered

Read the output from the bottom. The log is one JSON line per (sample, epoch), with the full message list: this is what inspect view, lm-eval’s --log_samples and every tracing product show you, and it is the thing you read during error analysis. The accuracy is 0.708 over 120 rows, but the rows are not independent: the three epochs of one sample share its difficulty. Treating each sample as a cluster raises the standard error from 0.042 to 0.049 (Chapter 5.3 derives the clustered SE). Finally, the same model scored by a scorer that returns "pass"/"fail" gets 0.000, with no error and no warning. That is the silent-coercion trap, and it is real: Inspect maps unknown string values to 0.0 unless you supply your own value_to_float[22].

Whenever a new scorer reports a suspiciously low number, check the score values in the log before you debug the model. A custom scorer should return the framework’s own constants (CORRECT/INCORRECT) or floats, and your harness should fail loudly on an unknown value. The assert_runner.py program in 9.6 raises on an unknown assertion type for the same reason.

If you can explain each line of run_task, you can read the source of any harness. When a tool’s numbers surprise you, ask the five questions this loop suggests: which samples, which solver (prompt, scaffold, sampling parameters), which scorer (and its extraction), how many epochs and how they are reduced, and which aggregate and error bar.

9.3Benchmark harnesses: lm-eval, lighteval, HELM, OLMES, simple-evals

Benchmark harnesses exist because the same benchmark name does not give the same number. Three years of maintaining lm-evaluation-harness led its authors to codify the “folk knowledge” of evaluation: results are sensitive to setup details that papers rarely report, so you should share code, prompts and per-sample outputs[23]. OLMES documented the sources of irreproducibility one by one (prompt format, the choice of in-context examples, probability normalisation, and cloze versus multiple-choice formulation) and proposed a standard for each[24]. A harness is how you pin all of them down.

lm-evaluation-harness

lm-eval[25] is the de facto open harness for few-shot and zero-shot evaluation of base and instruct models. A model backend implements three request types: loglikelihood (log-probability of a continuation, used for multiple-choice “cloze” scoring), loglikelihood_rolling (perplexity) and generate_until (free text, stopped at until strings). API chat models usually cannot return prompt log-probabilities, so they can only run generate_until tasks, which is one reason MMLU numbers differ between harnesses (Chapter 2.4). Tasks are YAML. The full file also defines a second pipeline, flexible-extract, with regex (-?[$0-9.,]{2,})|(-?[0-9]+) and group_select: -1 (take the last match). Both scores are reported.

Notice that the metric is not just “exact match”. It is a filter pipeline (extract, then select) followed by a normaliser (delete commas, dollar signs, everything up to ####, and a trailing full stop, then lower-case) followed by string equality. Change any stage and the number changes. filter_ablation.py re-implements both pipelines and runs them on the same 20 generations:

def normalise(s: str) -> str:
    for pat in IGNORE:
        s = re.sub(pat, "", s)
    return s.lower().strip()


def strict_extract(gen: str) -> str:
    m = STRICT.findall(gen)
    return m[0] if m else INVALID                                  # take_first


def flexible_extract(gen: str) -> str:
    matches = FLEXIBLE.findall(gen)
    if not matches:
        return INVALID
    m = matches[-1]                                                # group_select: -1
    return next((g for g in m if g), INVALID) if isinstance(m, tuple) else m


def exact_match(pred: str, target_text: str) -> int:
    return int(normalise(pred) == normalise(target_text))

HELM (pip install crfm-helm) introduced multi-metric evaluation: seven metrics (accuracy, calibration, robustness, fairness, bias, toxicity, efficiency) over 16 core scenarios plus 26 targeted ones, 42 scenarios across 30 models in the original paper[26][27]. Its workflow is helm-run --run-entries mmlu:subject=philosophy,model=openai/gpt2 --suite my-suite --max-eval-instances 10, then helm-summarize and helm-server to browse. HELM’s efficiency metric is an early example of cost-aware reporting. OLMES is a written standard with a reference implementation in allenai/olmes[24]. simple-evals argued for the opposite default from the classic harnesses: the “zero-shot, chain-of-thought setting, with simple instructions”, calling few-shot and role-play prompts “carryovers from evaluating base models”[15]. It is deprecated, but it is still the most readable implementation of MMLU, GPQA and SimpleQA graders you will find.

An “MMLU score” from lm-eval (log-likelihood over answer letters; zero-shot unless you pass --num_fewshot 5; subjects micro-averaged, weighted by size[95]), from simple-evals (zero-shot CoT, generated letter) and from a vendor report are three different measurements. Always report the harness and version, task version (metadata.version in the YAML), prompt, few-shot count, chat template on/off (and any system instruction), filter, sampling parameters, and whether subtasks are micro- or macro-averaged (Chapter 2.10).

9.4Inspect in depth

Inspect (inspect_ai), from the UK AI Security Institute, is the general framework in layer B and the one this book’s mini harness imitates[28]. An eval is a Task(dataset, solver, scorer). Datasets come from Hugging Face, CSV or JSON and become Sample(input, target, id, metadata). A solver is an async function over a TaskState; solvers compose (system prompt, chain of thought, generate, self-critique), and agents such as react() are solvers too. Scorers include includes, match, pattern, answer, exact, f1, choice, math, model_graded_qa and model_graded_fact[22]. The hello-world task from the docs:

A custom scorer is an async function returning a Score; the decorator declares which metrics aggregate it:

@scorer(metrics=[accuracy(), stderr()])
def close_enough(rel_tol: float = 0.01):
    async def score(state: TaskState, target: Target) -> Score:
        numbers = re.findall(r"-?\d+(?:\.\d+)?", state.output.completion)
        if not numbers:
            return Score(value=INCORRECT, explanation="No number found in output.")
        answer = numbers[-1]
        expected = float(target.text)
        correct = abs(float(answer) - expected) <= rel_tol * abs(expected)
        return Score(value=CORRECT if correct else INCORRECT,
                     answer=answer, explanation=state.output.completion)
    return score

Epochs and reducers. epochs=Epochs(5, ["mean", "pass_at_5"]) runs each sample five times and reduces per sample before aggregating; on the command line, --epochs 5 --epochs-reducer pass_k_3. The built-in reducers include mean, mode, at_least_{n}, pass_at_{k} (the unbiased estimator of Chapter 2.5) and pass_k_{k} (pass^k, all k trials succeed; Chapter 5.9)[22]. Statistics. Metrics include accuracy(), mean(), stderr(cluster="category"), bootstrap_stderr(), ci(), ci_wilson() (recommended over ci() for 0/1 scores) and grouped(accuracy(), "category") for per-slice results. The clustered standard error is the one to use whenever samples share a passage, a repository or a template.

Use it to unit-test scorers in CI with no API key: if a scorer gives the default mock output anything but zero, it is broken. Logs. CORRECT, INCORRECT, PARTIAL and NOANSWER are the strings "C", "I", "P", "N", mapped by value_to_float() to 1.0, 0.0, 0.5 and 0.0. Any other string ("pass", "yes") becomes 0.0 unless you pass a converter[22]. The mini_harness.py run above shows the effect: 0.708 becomes 0.000. Inspect’s answer() and pattern() scorers do flag unparseable outputs with reason="invalid_response_format"; count those separately from wrong answers.

9.5Agent and environment harnesses

Agent harnesses run an agent inside a container or simulated world and then check the outcome state (Chapter 6.3). That makes them slow and stateful, and it gives them failure modes of their own: broken tasks, leaky verifiers, stale caches and infrastructure noise. The Agentic Benchmark Checklist found that SWE-bench Verified has insufficient tests on some tasks and that TAU-bench counted empty responses as successes, with mis-estimation of up to 100% in relative terms[30]. The defence is the same in every harness: run a gold or Oracle solution (must score 1), run a null agent (must score 0), and keep the verifier out of the agent’s reach.

SWE-bench

A SWE-bench instance is a real GitHub issue; a prediction is a JSONL row with instance_id, model_name_or_path and model_patch (a unified diff). The harness builds a Docker image per instance, applies the patch, and runs the instance’s FAIL_TO_PASS and PASS_TO_PASS tests; the instance is resolved when all of them pass[31]. SWE-bench Verified is “a subset of 500 problems that real software engineers have confirmed are solvable”. The current CLI[32]:

swebench eval verified --gold                          # sanity check: reference patches must resolve
swebench eval verified -p preds.jsonl --run-id r1 -j 8 # writes logs/evaluation/r1/results.json
swebench report r1 -d verified                         # re-grade existing logs without containers
swebench infer verified -m gpt-5 -o preds              # generate predictions with mini-SWE-agent

The README carries a warning that deserves its own program: results are cached by run_id and instance_id only, so a different patch submitted under the same run id is not re-evaluated[32]. swebench_cache_trap.py builds a toy harness with three instances whose “tests” are Python assertions and caches exactly that way:

class Harness:
    def __init__(self, key_mode: str = "run_id"):
        self.cache: dict[tuple[str, ...], bool] = {}
        self.key_mode, self.container_runs = key_mode, 0

    def key(self, run_id: str, inst: Instance, patch: str) -> tuple[str, ...]:
        if self.key_mode == "run_id":                        # what the README warns about
            return (run_id, inst.instance_id)
        return (inst.instance_id, hashlib.sha256(patch.encode()).hexdigest()[:12])   # content-addressed

    def evaluate(self, preds: list[dict], run_id: str) -> dict[str, bool]:
        out = {}
        for p in preds:
            inst = next(i for i in INSTANCES if i.instance_id == p["instance_id"])
            k = self.key(run_id, inst, p["model_patch"])
            if k not in self.cache:
                self.container_runs += 1
                self.cache[k] = run_tests(inst, p["model_patch"])
            out[inst.instance_id] = self.cache[k]
        return out

τ²-bench and BFCL

τ-bench simulates customer-service conversations: a domain is a policy document, tools over a database, tasks, and an LLM user simulator; success means the final database state equals the goal state and required outputs were given[33]. It introduced pass^k, computed in the original repository as the mean over tasks of comb(c, k) / comb(num_trials, k). τ²-bench adds “dual control” (the user can act on the world too) and a telecom domain[34]; the current repository, “τ-bench 2.0”, covers airline, retail and telecom in six languages, with text and full-duplex voice (text-v1 is 900 tasks = 6 languages × 3 domains × 50)[35]. τ-bench 2.0 English scores are not comparable with 1.x: retail and telecom each use 50 reviewed task replacements, prompts gained a language clause and an entity-order rule, the user simulator has a persona block, communication checks use an LLM judge instead of substring matching, and the voice simulator defaults to gpt-5.5 (was gpt-4.1). The leaderboard shows 1.x and 2.0 on separate tabs, and the v1.0.1 release reproduces 1.x numbers; the repository also lists banking_knowledge (a retrieval-style domain) and intake domains. Always report the benchmark release with the domain[35]. With 50 tasks per domain, intervals are wide: run several trials and report them (Chapter 6.6). BFCL checks function calls by abstract-syntax-tree matching (function name, required parameters, each value in an allowed set), and later versions add multi-turn state checks and agentic web-search and memory categories; the CLI is bfcl generate then bfcl evaluate[36][37].

Harbor and Terminal-Bench

Harbor is “a framework from the creators of Terminal-Bench for evaluating and optimizing agents and language models”: it runs arbitrary agents (Claude Code, OpenHands, Codex CLI) on thousands of containers in parallel and is the official harness for Terminal-Bench 2.0[11]. The Terminal-Bench paper reports 89 hard terminal tasks in Harbor format, with frontier agents below 65%[12]. Harbor’s most useful idea is its plain-file task contract:

my-task/
├── instruction.md          # prompt; "Don't leak the tests"
├── task.toml               # [task] name/version/keywords; [agent] timeout_sec; [verifier] timeout_sec; [environment] cpus/memory_mb/network_mode
├── environment/Dockerfile  # install what the task requires, NOT the solution
├── solution/solve.sh       # Oracle agent runs it to prove solvability
└── tests/test.sh           # writes /logs/verifier/reward.txt (0/1) or reward.json

The verifier writes a single number to /logs/verifier/reward.txt, or several to reward.json (for example {"accuracy": 0.95, "runtime_sec": 1.2}). The Oracle agent runs solution/solve.sh to prove the task is solvable. [verifier] environment_mode = "separate" runs the tests in a different environment from the agent, so the agent cannot read or edit them, and Reward Kit (harbor-rewardkit) supports multi-criterion and judge grading. A run is harbor run --dataset terminal-bench@2.0 --agent claude-code --model ... --n-concurrent 4.

harbor_runner.py plays the harness without Docker: it writes the task directory to a temporary folder, gives each trial a fresh workspace, runs an “agent” (a shell script) with the timeout from task.toml, then copies in a clean set of tests and runs the verifier. It tries four agents against a strict verifier (diff against the expected file), a lazy one (file exists), and a configuration where the tests are visible to the agent:

def run_trial(task: pathlib.Path, agent: str, verifier: str, tests_visible: bool) -> str:
    cfg = read_toml(task / "task.toml")
    with tempfile.TemporaryDirectory() as ws_str:               # fresh workspace per trial
        ws = pathlib.Path(ws_str)
        app, logs, tests = ws / "app", ws / "logs" / "verifier", ws / "tests"
        app.mkdir()
        logs.mkdir(parents=True)
        shutil.copy(task / "environment" / "input.txt", app / "input.txt")
        env = {**os.environ, "APP_DIR": str(app), "LOGS_DIR": str(logs), "TESTS_DIR": str(tests)}
        if tests_visible:                                       # the leak: tests baked into the image
            shutil.copytree(task / "tests", tests)
        script = (task / "solution" / "solve.sh").read_text() if AGENTS[agent] is None else AGENTS[agent]
        try:
            subprocess.run(["bash", "-c", script], cwd=app, env=env, check=False,
                           timeout=cfg["agent"]["timeout_sec"], capture_output=True)
        except subprocess.TimeoutExpired:
            pass                                                # timeout: verify whatever is there
        shutil.rmtree(tests, ignore_errors=True)                # verifier gets a clean copy of tests
        shutil.copytree(task / "tests", tests)
        subprocess.run(["bash", str(tests / verifier)], env=env, check=False,
                       timeout=cfg["verifier"]["timeout_sec"], capture_output=True)
        reward = logs / "reward.txt"
        if not reward.exists():                                 # a missing reward is an infra error, not 0
            return "ERROR"
        return reward.read_text().strip()

verifiers: an eval that is also an RL environment

Prime Intellect’s verifiers (“our library for RL environments + evals”) expresses the same contract in Python. Its v1 API has an immutable TaskData row, a Task with lifecycle hooks (setup, finalize, validate) and @vf.reward / @vf.metric methods, and a Taskset whose load() returns tasks[13]:

import verifiers.v1 as vf

class AdditionData(vf.TaskData):
    answer: int

class AdditionTask(vf.Task[AdditionData]):
    @vf.reward
    async def exact_match(self, trace: vf.Trace) -> float:
        return float(trace.last_reply == str(self.data.answer))

class AdditionConfig(vf.TasksetConfig):
    num_tasks: int = 100

class AdditionTaskset(vf.Taskset[AdditionTask, AdditionConfig]):
    def load(self) -> list[AdditionTask]:
        return [AdditionTask(AdditionData(prompt=f"What is {i} + {i}?", answer=2 * i),
                             self.config.task)
                for i in range(self.config.num_tasks)]

Container tasks can grade in an isolated sandbox (ScoringConfig(mode="isolated")), the same idea as Harbor’s separate verifier, and vf-validate <taskset> runs the gold solutions with no model call, the same idea as --gold and the Oracle. Chapter 7.3 treats verifiers as an RL environment in depth (Chapter 7.3).

Harbor and verifiers make the agent harness explicit (--agent claude-code; a harness id in verifiers), and for good reason: comparing two models under two different scaffolds measures the scaffolds. Container CPU and memory limits, timeouts, network policy (network_mode) and API flakiness also move agent scores, so record them in the task config and report them with results (Chapter 6.9).

9.6App-level testing libraries

Layer D is where most product teams start, and Hamel Husain’s advice for it is blunt: begin with unit-test-style assertions (“Level 1”), add model and human evaluation (“Level 2”), and reserve A/B tests (“Level 3”) for significant changes, because “the cost of Level 3 > Level 2 > Level 1. This dictates the cadence.”[38] He also warns: “Don’t buy fancy LLM tools. Use what you have first.” The libraries below are worth adopting when they save you plumbing, not because they come with metrics.

    t, v, out = a["type"], a.get("value"), r.output
    if t == "equals":
        return out == v, t
    if t == "contains":
        return v in out, f"{t} {v!r}"
    if t == "icontains":
        return v.lower() in out.lower(), f"{t} {v!r}"
    if t == "not-contains":
        return v not in out, f"{t} {v!r}"
    if t == "not-icontains":
        return v.lower() not in out.lower(), f"{t} {v!r}"
    if t == "regex":
        return re.search(v, out) is not None, f"{t} {v}"
    if t == "is-json":
        try:
            json.loads(out)
            return True, t
        except json.JSONDecodeError:
            return False, t
    if t == "python":                       # promptfoo exposes `output` and `context`
        try:
            return bool(eval(v, {"json": json, "re": re}, {"output": out, "context": vars_})), f"python {v}"
        except Exception as e:              # an exception is a failure, not a crash
            return False, f"python raised {type(e).__name__}"
    if t == "cost":
        return r.cost <= a["threshold"], f"cost {r.cost:.5f} <= {a['threshold']}"
    if t == "latency":
        return r.latency_ms <= a["threshold"], f"latency {r.latency_ms:.0f}ms <= {a['threshold']}"
    raise ValueError(f"unknown assertion type {t}")   # fail loudly: never coerce an unknown type

9.9Regression testing in CI

Production evaluation is a stack of layers, each catching failures the others miss; Anthropic borrows the Swiss Cheese Model from safety engineering to say that “no single evaluation layer catches every issue”[3] (Chapter 1.9). The first layer runs on every change: a regression suite. Anthropic distinguishes it from a capability suite: a regression eval asks “does the agent still handle all the tasks it used to?” and should pass at “nearly 100%”, while a capability eval starts with a low pass rate and is hill-climbed. When a capability eval saturates (“an eval at 100% tracks regressions but provides no signal for improvement”), it graduates into the regression suite[3].

The naive CI gate compares one run of the candidate with one run of the baseline and fails if the pass rate dropped. It cries wolf, because LLM outputs vary between runs even with “deterministic” settings (temperature 0, fixed seed)[52] (see Chapter 5.10). The fix is the paired comparison of Chapter 5.5: run both arms on the same items, several times each, compute the per-item difference di = c̄i − b̄i (mean over repeats), and bootstrap the mean difference over items[53]. Then decide with a non-inferiority margin m:

PASS if L ≥ −m;   FAIL if U < 0 (and L < −m);   otherwise INCONCLUSIVE → add repeats (9.1) where [L, U] is the 95% paired bootstrap interval for mean(d), and m is the largest regression you are willing to ship (5 points below).

prompt_regression_ci.py runs a 200-item JSONL suite (data/regression_set.jsonl) through a mock model and three assertions (valid JSON, cites a [doc-N] source, under the length limit), with a response cache keyed by (model, prompt version, item, repeat). It then simulates 1,000 CI runs for each true change:

def paired_gate(base: np.ndarray, cand: np.ndarray, margin: float, rng, B: int = 2000):
    d = cand.mean(axis=1) - base.mean(axis=1)                        # per-item paired difference
    idx = rng.integers(0, len(d), size=(B, len(d)))
    boots = d[idx].mean(axis=1)
    lo, hi = np.quantile(boots, [0.025, 0.975])
    if lo >= -margin:
        verdict = "PASS"                                             # any regression is < margin
    elif hi < 0:
        verdict = "FAIL"                                             # regression is clear
    else:
        verdict = "INCONCLUSIVE"                                     # CI too wide: get more data
    return d.mean(), lo, hi, verdict


def two_stage(p_b: np.ndarray, p_c: np.ndarray, rng, margin: float = 0.05) -> str:
    b = (rng.random((len(p_b), 3)) < p_b[:, None]).astype(float)
    c = (rng.random((len(p_c), 3)) < p_c[:, None]).astype(float)
    v = paired_gate(b, c, margin, rng, B=400)[3]
    if v != "INCONCLUSIVE":
        return v
    b = np.hstack([b, rng.random((len(p_b), 7)) < p_b[:, None]])    # escalate: 7 more repeats
    c = np.hstack([c, rng.random((len(p_c), 7)) < p_c[:, None]])
    v = paired_gate(b, c, margin, rng, B=400)[3]
    return "REVIEW" if v == "INCONCLUSIVE" else v

9.10Evaluating retrieval

A retrieval-augmented generation (RAG) system is two systems in a trench coat: a retriever that picks context and a generator that writes from it. Evaluate them separately, or you will not know which one to fix. Barnett et al.’s experience report from three RAG deployments lists seven failure points: FP1 missing content (the answer is not in the corpus), FP2 missed the top-ranked documents, FP3 retrieved but not in the context after consolidation, FP4 not extracted, FP5 wrong format, FP6 incorrect specificity and FP7 incomplete. The first three are retrieval-side failures and the last four generation-side, and the report’s first key takeaway is that “validation of a RAG system is only feasible during operation”[54]. The retriever half has fifty years of information-retrieval metrics behind it. For a query with ranked results r1…rK, graded relevance reli (0 = not relevant) and relevant set R:

P@k = |relevant in top k|k,   R@k = |relevant in top k||R|,   RR = 1rank of first relevant,   AP = 1|R| Σk P@k · 1[rk relevant] (9.2) hit@k is 1 if any relevant document is in the top k. MRR and MAP are the means of RR and AP over queries.
DCG@k = Σi=1..k g(reli)log2(i + 1),   nDCG@k = DCG@kIDCG@k,   g(rel) = rel (linear) or 2rel − 1 (exponential) (9.3) IDCG@k is the DCG of the ideal ordering of all judged documents. The exponential gain rewards highly relevant documents more strongly.

Worked example (reproduced by retrieval_metrics.py). Relevant documents d2 (rel 3), d5 (rel 2), d9 (rel 1); the system returns [d1, d2, d3, d5, d7]. P@5 = 2/5 = 0.40; R@5 = 2/3 = 0.667; hit@1 = 0, hit@5 = 1; RR = 1/2 = 0.5; AP = (1/2 + 2/4)/3 = 0.333 (d9 was never retrieved, so it contributes 0 but still counts in |R|). Linear gain: DCG@5 = 3/log23 + 2/log25 = 1.893 + 0.861 = 2.754; IDCG@5 = 3/1 + 2/log23 + 1/log24 = 4.762; nDCG@5 = 0.578. Exponential gain: DCG = 7/1.585 + 3/2.322 = 5.709; IDCG = 7 + 3/1.585 + 1/2 = 9.393; nDCG@5 = 0.608. Same ranking, two numbers: always state the gain function and k. BEIR reports nDCG@10[55].

def average_precision(ranked: list[str], qrels: Qrels) -> float:
    """AP = (1/|R|) * sum_k P@k * 1[doc k relevant]; relevant docs never retrieved add 0."""
    n_rel = sum(r > 0 for r in qrels.values())
    hits, total = 0, 0.0
    for i, d in enumerate(ranked, 1):
        if qrels.get(d, 0) > 0:
            hits += 1
            total += hits / i
    return total / n_rel if n_rel else 0.0


def dcg(gains: list[float]) -> float:
    return sum(g / math.log2(i + 1) for i, g in enumerate(gains, 1))


def ndcg_at_k(ranked: list[str], qrels: Qrels, k: int, gain: str = "linear") -> float:
    g = (lambda r: float(r)) if gain == "linear" else (lambda r: 2.0 ** r - 1)
    actual = [g(qrels.get(d, 0)) for d in ranked[:k]]
    ideal = sorted((g(r) for r in qrels.values()), reverse=True)[:k]
    return dcg(actual) / dcg(ideal) if ideal else 0.0


def ragas_context_precision(verdicts: list[int]) -> float:

    for i, v in enumerate(verdicts):
        cumsum += v
        if v:

The ragas_context_precision function copies the logic of RAGAS’s context precision, which is AP with one change: it divides by the number of relevant items retrieved (plus 10−10), not by |R|[16]. On verdicts [0, 1, 0, 1, 0] it gives (1/2 + 2/4)/2 = 0.50 where AP gives 0.333. It therefore measures ranking quality among what was retrieved and does not penalise missing documents; that is context recall’s job (9.11).

def _calculate_average_precision(self, verdict_list: t.List[int]) -> float:
    cumsum = 0
    numerator = 0.0
    for i, v in enumerate(verdict_list):
        cumsum += v
        if v:
            numerator += cumsum / (i + 1)
    denominator = cumsum + 1e-10
    score = numerator / denominator
    return score

The real method takes a list of Verification objects (v = 1 if ver.verdict else 0), starts from score = np.nan and logs a warning when the judge’s response cannot be parsed. Note that all-zero verdicts give 0/1e-10 = 0.0, not NaN: “nothing relevant was retrieved” and “the judge failed” are different results.

Where the labels come from

Every metric above needs relevance judgments (“qrels”), and in production you rarely have them. The classic answer is TREC-style pooling: humans judge the union of the top results from several systems. Its known flaw is incomplete judgments: an unjudged document is scored as non-relevant, which penalises a new retriever that finds documents nobody judged. In the script, the novel retriever scores 0.660 with unjudged = 0, and 0.943 once its two new documents are judged (the old system scores 0.423 under the full judgments). Dropping unjudged documents (“condensed lists”) is a common workaround, but it overshoots here (1.000). The modern answer is an LLM assessor. Thomas et al. at Bing built a relevance-labelling prompt that agrees with first-party searcher preference data and used it for large-scale labelling[56]; UMBRELA is an open-source reproduction of that assessor[57], used in the TREC 2024 RAG Track, which also scores answers against “nuggets” of required information with the AutoNuggetizer framework[58]. pytrec_eval gives you trec_eval’s exact definitions in Python[59] if you need numbers comparable to published IR results; for zero-shot retrieval across domains, BEIR is the standard benchmark[55].

Before you trust LLM relevance labels, label 100–200 query–document pairs yourself and measure agreement (Cohen’s κ, or precision and recall of the “relevant” label), exactly as for any judge (Chapter 4.3). Then use the LLM to fill the holes left by pooling.

Retrieval decisions in practice

  • Shortlist, then re-rank on your data. MTEB[111] and its multilingual successor MMTEB[112] are the usual way to shortlist embedding models, but leaderboard rank does not transfer reliably to a specific domain (BEIR made the same point for zero-shot retrieval[55]). Re-run the shortlist on your own qrels.
  • Match the granularity. Qrels are often at document level while RAG retrieves chunks. Map chunks to their parent documents, or label at passage level, and re-run retrieval evals after any change to chunk size or overlap, since it changes P@k and recall@k.
  • Pick the metric the generator feels. The generator sees a set, not a ranking, so the primary retrieval metric for RAG is usually recall@k (or context recall) at the k actually passed to the generator. Rank-sensitive nDCG matters more when context is truncated or ordered (see Lost in the Middle in 9.11).
  • Compare retrievers paired. Run both on the same queries and use a paired per-query bootstrap or randomisation test (Chapter 5.5), not two separate intervals.
  • Compare rankers online by interleaving. Team-draft interleaving merges the rankings of two retrievers into one list shown to each user, the two systems alternately “drafting” their next-best item[116]. A click (or, in RAG, the chunk the generator cites or the user opens) is credited to the system that contributed that item, and the system with more credit across sessions wins. Large-scale studies on Yahoo! and Bing search found that interleaving agrees with offline metrics and is far more sensitive than A/B tests on absolute click metrics[117]; it is often cited as needing about two orders of magnitude less traffic. Caveat: it measures relative preference between two rankers, not absolute quality, so it suits retriever swaps better than end-to-end generation changes (use an A/B test, 9.15, for those).

9.11Evaluating generation in RAG

The generator half needs different metrics, because the question is no longer “did we fetch the right documents?” but “did the answer use them, and only them?” RAGAS introduced the now-standard reference-free set, computed with LLM prompts “without having to rely on ground truth human annotations”[41]:

  • Faithfulness (groundedness): split the answer into atomic statements S, ask an NLI model or LLM whether the retrieved context supports each, and report |supported| / |S|. Five claims with four supported gives 0.80.
  • Answer relevance: generate n questions from the answer and average their embedding cosine similarity to the real question. It penalises incomplete and padded answers, not wrong ones.
  • Context precision / relevance: the share (or rank-weighted share) of retrieved chunks that are relevant (9.10).
  • Context recall: the share of claims in a reference answer that the retrieved context supports. It needs a reference.

The faithfulness score itself is three lines in RAGAS, and the interesting line is the one for zero statements:

def _compute_score(self, answers: NLIStatementOutput):
    # check the verdicts and compute the score
    faithful_statements = sum(
        1 if answer.verdict else 0 for answer in answers.statements
    )
    num_statements = len(answers.statements)
    if num_statements:
        score = faithful_statements / num_statements
    else:
        logger.warning("No statements were generated from the answer.")
        score = np.nan
    return score

A refusal (“I don’t know”) yields no statements and therefore NaN, and a nanmean silently drops it. A system that abstains on every hard question then looks more faithful than one that tries. Report the abstention rate as its own metric.

Beyond RAGAS, three designs are worth knowing. ARES fine-tunes lightweight judges on synthetic data for context relevance, answer faithfulness and answer relevance, then uses prediction-powered inference with “only a few hundred human annotations” to produce statistically valid estimates[61]; 9.13 builds that correction. RAGChecker works at claim level in both directions: precision, recall and F1 of response claims against ground-truth claims, retriever diagnostics (claim recall, context precision) and generator diagnostics (context utilisation, noise sensitivity, hallucination, self-knowledge, faithfulness), with meta-evaluation showing better correlation with human judgments than other metrics[62]. Nugget evaluation, as in TREC 2024, checks whether an answer contains each atomic unit of required information[58]. For a map of the benchmark landscape, see the RAG evaluation survey[63]; for task-stratified benchmarks, CRUD-RAG organises tasks by create, read, update and delete scenarios[64] and FinanceBench poses open-book questions over SEC filings[65].

Citation quality. When answers cite sources, check two more things. Citation recall: is each statement fully supported by the passages it cites (NLI entailment of the statement by the concatenated cited passages)? Citation precision: is each citation needed, so that it supports some part of the statement and removing it would not leave support intact? These are the metrics of ALCE[110]. An answer can be perfectly faithful to the retrieved context while citing the wrong document, so faithfulness over the whole context does not replace a citation check, and the “cites a [doc-N]” assertion in 9.9 checks only that a citation is present. toy_rag.py shows the gap below.

Two findings should shape your test cases. Position matters: models use information best when it sits at the beginning or end of the context and worst in the middle[66], so test with the key passage at several positions and prefer rank-aware retrieval metrics. Targeted abilities: RGB tests noise robustness, negative rejection (refusing when no document answers), information integration across documents and counterfactual robustness[67]; each is a slice worth having in your own suite.

A second checker also requires the claim’s numbers to appear in that sentence.

def generate(question: str, ctx: list[str], rate: float, rng: random.Random) -> tuple[list[str], int]:
    """Extractive answer: the 2 context sentences sharing most tokens with the question, plus maybe
    one fabricated sentence. Returns (answer sentences, number of fabricated sentences)."""
    q = set(tokens(question))
    ranked = sorted(ctx, key=lambda s: -len(q & set(tokens(s))))
    if not ranked or not q & set(tokens(ranked[0])):
        return [], 0                                                   # refusal: "I don't know."
    answer = ranked[:2]
    if rng.random() < rate:
        subject = re.match(r"(The Zorbel \w+|\w+)", answer[0]).group(1)
        if rng.random() < 0.5:
            answer.append(f"{subject} is waterproof to {rng.randint(5, 90)} metres.")  # invented fact
        else:
            src = next((s for s in answer if re.search(r"\b\d+\b", s)), answer[0])
            nums = list(re.finditer(r"\b\d+\b", src))
            if nums:                                                   # change the last number
                m = nums[-1]
                answer.append(src[:m.start()] + str(int(m.group()) + 13) + src[m.end():])  # number swap
            else:
                answer.append(f"{subject} is waterproof to {rng.randint(5, 90)} metres.")
        return answer, 1
    return answer, 0


def supported(claim: str, ctx: list[str], check_numbers: bool) -> bool:
    c = tokens(claim)
    for s in ctx:
        st = set(tokens(s))
        if sum(t in st for t in c) / len(c) >= 0.8:
            if not check_numbers or set(re.findall(r"\d+", claim)) <= set(re.findall(r"\d+", s)):
                return True
    return False

Agentic and multi-turn RAG

In 2025–2026 retrieval is often a tool call inside an agent trajectory (a deep-research agent issuing a dozen searches, a support agent querying a knowledge base between account actions), not a single retrieve-then-generate step. Two ideas carry over from the rest of this section, and one is new.

Fix the corpus so the retriever can be scored separately. Live web search makes agent scores irreproducible and mixes retriever quality with agent skill. BrowseComp-Plus replaces the web with a fixed, curated corpus that has human-verified evidence documents and mined hard negatives, so the same agent can be run with different retrievers[114]. GPT-5 scores 55.9% with BM25 and 70.1% with Qwen3-Embedding-8B, while making fewer search calls: swapping the retriever alone moves the agent score by about 14 points. An agent leaderboard that does not hold the retriever fixed is comparing two things at once.

Grade the end state, not just the answer. τ-Knowledge adds a τ-Banking domain (the banking_knowledge domain in the tau2-bench repository; see 9.5) with about 700 interlinked knowledge documents plus tool-mediated account updates, graded on verifiable, policy-compliant state changes[115]. The authors note that most existing benchmarks evaluate retrieval or tool use independently. Frontier models reach only about 25.5% pass^1, and reliability falls further over repeated trials (Chapter 5.9 covers pass^k).

Add per-step retrieval metrics. For each trajectory log: recall of gold evidence per search call and cumulatively over the trajectory; the number of search calls (a cost and efficiency metric, like tokens); and whether the final answer cites or uses the retrieved evidence, which is the faithfulness and citation scoring above applied to the union of all retrieved chunks. Grade the outcome and the trajectory as in Chapter 6 (6.3, 6.10).

When there is no context to check against, you can still ask whether the model is consistent. SelfCheckGPT samples several responses and measures their agreement[72]. Semantic entropy refines this: sample M answers, cluster them by meaning (two answers share a cluster if each entails the other), and compute the entropy of the cluster distribution[73]:

SE = −Σc p(c) ln p(c) (9.4) where p(c) is the share (or summed probability) of sampled answers in meaning cluster c. High SE suggests a confabulation.

Worked example (reproduced by semantic_entropy.py). Ten samples fall into clusters of size 7, 2 and 1: SE = −(0.7 ln 0.7 + 0.2 ln 0.2 + 0.1 ln 0.1) = 0.250 + 0.322 + 0.230 = 0.802 nats. One cluster of ten gives 0; ten singletons give ln 10 = 2.303.

def meaning(ans: str) -> str:
    """Stand-in for bidirectional entailment: two answers share a cluster iff they map to one meaning."""
    key = ans.lower().rstrip(".")
    return CANON.get(key, CANON.get(key.replace("it is ", ""), key))


def entropy(counts: list[int]) -> float:
    n = sum(counts)
    return 0.0 - sum(c / n * math.log(c / n) for c in counts if c)


def semantic_entropy(samples: list[str]) -> float:
    return entropy(list(Counter(meaning(s) for s in samples).values()))


def lexical_entropy(samples: list[str]) -> float:
    return entropy(list(Counter(samples).values()))


def auroc(scores: list[float], labels: list[int]) -> float:
    """P(score of a positive > score of a negative), ties count 1/2."""
    pos = [s for s, y in zip(scores, labels) if y]
    neg = [s for s, y in zip(scores, labels) if not y]
    wins = sum((p > q) + 0.5 * (p == q) for p in pos for q in neg)
    return wins / (len(pos) * len(neg))

9.13Online evaluation on live traffic

Online evaluation runs evaluators on production traces, where there is no gold label. The design has five parts:

  1. Sample traces, stratified by risk. You cannot judge everything, and uniform sampling wastes the budget on easy traffic. Sample heavily from high-stakes intents, new features, long conversations and traces with negative signals (thumbs down, re-asks, guardrail hits), and keep a uniform slice so you can still estimate population rates (weight strata back by their sampling rates).
  2. Run judges asynchronously. Cheap deterministic checks and small NLI checkers can run inline (9.16); LLM judges run off the request path, on the sampled stream, so they add no user-facing latency. Langfuse, for example, runs LLM-as-judge evaluators on “live production traces”[46].
  3. Calibrate against humans. A judge that has not been checked against human labels is a guess (Chapter 4.8); judges inherit the failure modes of the models they grade[78]. Measure the judge’s true-positive and false-positive rates on a human-labelled sample, not raw agreement[38].
  4. Correct the estimate. Use the labelled sample to remove the judge’s bias with prediction-powered inference (below).
  5. Route to annotation queues. Send disagreements, low-confidence verdicts and a random slice to human reviewers; their labels feed both the calibration set and the eval set (9.18).

Prediction-powered inference (PPI) combines N judge-only items with n items that have both a human label Y and a judge score f[79] (Chapter 4.11 derives it; Chapter 5.14 treats it as statistics):

θ̂PP = 1N Σunlabelled f(X̃i) − 1n Σlabelled (f(Xj) − Yj),    Var ≈ Var(f)N + Var(f − Y)n (9.5) The second sum (the “rectifier”) estimates the judge’s bias on a random labelled sample; the labelled items must be an i.i.d. sample of the same traffic.

Eq. 9.5 assumes a uniform random labelled sample. If you sample labelled traces by risk stratum (bullet 1), compute the rectifier per stratum and combine the strata with their traffic-share weights (stratified PPI); applying the single-pool formula to a risk-weighted sample over-corrects toward the risky strata.

Worked example (reproduced by ppi_online.py). The judge says 80.0% of N = 10,000 answers are faithful. On n = 300 human-labelled answers the judge says 82% and humans say 76%, so the rectifier is 0.06 and θ̂PP = 0.80 − 0.06 = 0.74. Reporting 0.80 would overstate quality by six points.

If you know the judge’s TPR and FPR, the Rogan–Gladen estimator θ = (pobs − FPR)/(TPR − FPR) also corrects the rate[102]: (0.807 − 0.40)/(0.95 − 0.40) = 0.740. It needs TPR and FPR estimated on labelled data, and it becomes unstable when TPR − FPR is small; PPI does the same job without estimating them separately.

For comparing two variants with PPI (a paired difference rather than one rate), see Chapter 4.

def ppi_mean_ci(y_lab: np.ndarray, f_lab: np.ndarray, f_unlab: np.ndarray) -> tuple[float, float]:
    rect = f_lab - y_lab
    est = f_unlab.mean() - rect.mean()
    se = np.sqrt(f_unlab.var(ddof=1) / len(f_unlab) + rect.var(ddof=1) / len(rect))
    return est, se


def rogan_gladen_ci(y_lab: np.ndarray, f_lab: np.ndarray, f_unlab: np.ndarray) -> tuple[float, float]:
    """theta = (p_obs - FPR) / (TPR - FPR), with TPR/FPR estimated on the labelled sample.
    Delta-method SE: Var(p)/J^2 + (theta^2 Var(TPR) + (1 - theta)^2 Var(FPR)) / J^2, J = TPR - FPR."""
    pos, neg = y_lab == 1, y_lab == 0
    tpr, fpr, p = f_lab[pos].mean(), f_lab[neg].mean(), f_unlab.mean()
    j = tpr - fpr
    theta = (p - fpr) / j
    var = (p * (1 - p) / len(f_unlab) + theta ** 2 * tpr * (1 - tpr) / pos.sum()
           + (1 - theta) ** 2 * fpr * (1 - fpr) / neg.sum()) / j ** 2
    return theta, np.sqrt(var)


def simulate(true_p: float, tpr: float, fpr: float, N: int, n: int, sims: int, rng) -> dict:
    out = {k: {"est": [], "cover": [], "width": []} for k in ("judge", "human", "ppi", "rg")}
    for _ in range(sims):
        y = rng.random(N + n) < true_p                      # unobserved truth for every item
        f = np.where(y, rng.random(N + n) < tpr, rng.random(N + n) < fpr).astype(float)
        y = y.astype(float)
        f_u, f_l, y_l = f[:N], f[N:], y[N:]                 # the labelled n are a random sample
        cands = {
            "judge": (f_u.mean(), f_u.std(ddof=1) / np.sqrt(N)),
            "human": (y_l.mean(), y_l.std(ddof=1) / np.sqrt(n)),
            "ppi": ppi_mean_ci(y_l, f_l, f_u),
            "rg": rogan_gladen_ci(y_l, f_l, f_u),
        }
        for k, (est, se) in cands.items():
            out[k]["est"].append(est)
            out[k]["cover"].append(abs(est - true_p) <= Z * se)
            out[k]["width"].append(2 * Z * se)
    return {k: {m: float(np.mean(v)) for m, v in d.items()} for k, d in out.items()}

Two warnings. PPI assumes the labelled items are a random sample of the same traffic; if humans only label flagged traces, the rectifier is biased (label a uniform slice for calibration, and use the flagged ones for error analysis). And the criteria themselves move. Shankar et al. found that “users need criteria to grade outputs, but grading outputs helps users define criteria”: criteria drift[78]. Their EvalGen interface aligns LLM-generated evaluators with human grades as those grades accumulate, and SPADE mines prompt edit history to synthesise runtime assertions[80]. Version your rubric and your judge prompt, and re-calibrate when either changes.

9.14User feedback signals

Users grade your system all day. Explicit feedback is thumbs, stars and free-text reports. Implicit feedback is behaviour: accepting a suggestion, keeping it, editing it, copying an answer, re-asking the question in other words, abandoning the session, coming back next week. Microsoft’s Experimentation Platform describes a funnel for LLM features (opportunities → prompts sent → responses returned → seen → accepted → retained), quality signals such as edit distance between successive prompts (reformulation) and between the response and the retained content, and retention metrics such as conversations per user and days active[81]. Both sources warn about explicit feedback: Anthropic calls thumbs-down data “sparse and self-selected”[3], and ExP says it suffers “from low sample size and selection bias”[81].

The Copilot story is the canonical lesson in choosing among these. Ziegler et al. found that acceptance rate was the best predictor of developers’ perceived productivity[82], so it became the metric. Optimising it then favoured short, easy suggestions, so the 2025 custom model was also optimised for accepted-and-retained characters, with reported gains of 20% in accepted-and-retained characters, 12% in acceptance rate, three times the throughput and 35% lower latency[2]. GitHub also notes a confound between metrics: “Higher latency might actually lead to a higher acceptance rate because users might see fewer suggestions total”[1]. That is Goodhart’s law with a production dashboard, and the remedy is to pair every volume metric with a quality or retention metric.

Selection bias has a precise form. If the probability of leaving feedback depends only on observed covariates (segment, platform, intent), the bias is correctable by inverse-propensity weighting: weight each feedback-giver by 1/P(feedback | covariates). If it depends on the satisfaction itself (unhappy users click more), no reweighting on covariates can fix it.

def ipw(seg, sat, gave) -> float:

    w = 1.0 / est_prop[seg[gave]]

9.15A/B testing LLM features

Offline evals and online judges tell you whether outputs are good. Only a randomised experiment tells you whether shipping the change caused users to do better, which is why Husain puts A/B testing at the top of his three levels[38] and GitHub runs production A/B tests as the last of its three evaluation layers[2]. The statistics come from the online controlled experiments literature. The ingredients:

  • One overall evaluation criterion (OEC), decided before the test: for Copilot, accepted-and-retained characters; for a support bot, resolution without escalation; for a chat product, retention.
  • Guardrail metrics that must not regress even if the OEC improves: p95 latency, cost per request, refusal rate, safety-filter rate, error and 429 rates. ExP’s framework lists exactly these families for LLM experiments: GPU utilisation and cost (tokens, 429s, truncations), Responsible AI (content-filter rates), latency (time to first token, tokens per second), the utility funnel, edit distance, thumbs and retention[81].
  • A sample size fixed in advance by a power calculation, and a randomisation unit (usually the user, not the request, so one person does not see both arms and so per-user metrics are independent).

Two checks before reading any result. (1) Sample ratio mismatch (SRM): test the observed arm counts against the planned split with a chi-square goodness-of-fit test, and treat p < 0.001 as a broken experiment, not a result (Fabijan et al. catalogue the causes at Microsoft scale[96]). Typical LLM causes are bot filtering that treats the arms differently, timeouts or crashes in one arm (a slower model drops more sessions before logging) and opt-in flows. With 50,500 vs 49,500 users at a planned 50/50, χ² = 2 × 500² / 50,000 = 10.0 and p ≈ 0.0016: not yet over the strict alarm line, but far below 0.01 and worth stopping to investigate. (2) Unit-of-analysis mismatch: when you randomise by user but measure per request or per suggestion (acceptance rate, thumbs per response, latency per request; Copilot’s OEC is exactly this shape), the metric is a ratio of per-user sums, R = ΣYi / ΣNi, and requests from the same user are correlated. The per-request binomial standard error is then too small. Use the delta method over users[97], or bootstrap users (Chapter 5.3’s clustered resampling, applied to the randomisation unit):

Var(R) ≈ 1n μN² (σY² − 2R σYN + R² σN²) n users per arm; μN the mean requests per user; σY², σN², σYN the variances and covariance of per-user accepted counts Yi and request counts Ni.

ab_test_sim.py runs 2,000 A/A tests with 2,000 users per arm, lognormal requests per user and a per-user acceptance propensity. The naive per-request standard error (0.0057) is half the delta-method one (0.0116), and a z-test built on it declares a difference in 32.6% of A/A tests; the delta-method test does so in 5.5%. The code for both checks is short:

def srm_check(counts, split) -> tuple[float, float]:
    counts = np.asarray(counts, dtype=float)
    expected = counts.sum() * np.asarray(split, dtype=float) / np.sum(split)
    chi2 = float(np.sum((counts - expected) ** 2 / expected))
    assert len(counts) == 2, "df = 1 closed form; use a chi-square table for more arms"
    return chi2, math.erfc(math.sqrt(chi2 / 2))

Worked example (reproduced by ab_test_sim.py). Thumbs-up rate p = 0.6, so σ² = 0.6 × 0.4 = 0.24. To detect δ = 2 points: n ≈ 16 × 0.24 / 0.0004 = 9,600 per arm (exact formula 9,419). Those are users who give feedback; if 5% do, you need 192,000 users per arm. This is the quantitative case for implicit signals measured on everyone.

CUPED reduces the variance by regressing out a pre-experiment covariate X (for example, the same user’s activity the week before): Ycv = Y − θ(X − E[X]) with θ = Cov(X, Y)/Var(X), which gives Var(Ycv) = Var(Y)(1 − ρ²)[83]. With ρ = 0.6 the variance falls by 36%, so you need 36% fewer users for the same power. Because X is measured before randomisation, the adjustment cannot be affected by the treatment; Lin and Crespo extend the idea to combine pre- and in-experiment data without post-treatment bias[84] (Chapter 5.4 covers variance reduction for offline evals).

def peeking_fpr(looks: int, per_look: int, sims: int, rng, z_crit: float = Z_A, p: float = 0.6) -> float:
    """A/A test: stop and declare a winner at the first look where |z| > z_crit."""
    a = rng.binomial(per_look, p, (sims, looks)).cumsum(axis=1)
    b = rng.binomial(per_look, p, (sims, looks)).cumsum(axis=1)
    n = per_look * np.arange(1, looks + 1)
    pa, pb = a / n, b / n
    pool = (pa + pb) / 2
    z = (pb - pa) / np.sqrt(2 * pool * (1 - pool) / n)
    return float(np.mean((np.abs(z) > z_crit).any(axis=1)))

Peeking is the most common way to break an A/B test. If you check a fixed-horizon z-test every day and stop the first time it says “significant”, the false-positive rate is no longer 5%. In our A/A simulation (no true effect) it rises to 8.3% with 2 looks and 24.9% with 20 daily looks (the offline analogue, and sequential stopping rules, are in Chapter 5). Either commit to a fixed horizon, or use a sequential design whose boundary accounts for the looks; by simulation, a constant boundary of |z| > 2.68 restores 5% over 20 looks. That is a Pocock-style boundary, one of the group-sequential designs built for a fixed number of planned looks. O’Brien–Fleming boundaries are instead very strict early and close to the fixed-horizon value at the final look, so little power is lost if the test runs to completion [98]: in the simulation, a boundary of c√(K/k) calibrated to 5% over 20 looks demands |z| > 9.61 on day 1 and only |z| > 2.15 on day 20 (against 2.68 throughout for Pocock), with a false-positive rate of 0.048 on fresh simulations. Lan–DeMets alpha-spending functions keep that error control when look times are not planned in advance[99]. For dashboards that people refresh daily, always-valid inference (mSPRT, always-valid p-values and confidence sequences) stays valid however often you look[100][101]; Johari, Pekelis and Walsh developed it for Optimizely’s Stats Engine. Rule of thumb: group-sequential for a few scheduled looks, always-valid for continuous monitoring, at the cost of wider intervals.

LLM features add their own traps. Novelty: a new assistant gets curious clicks in week one, so run long enough to see the steady state and plot the effect by day. Interference (a violation of SUTVA, the assumption that one unit’s outcome does not depend on another’s assignment): shared caches, shared rate limits and collaborative documents let one arm affect the other. Shadow deployments run the candidate on real requests without showing users its output; they measure latency, cost, error rates and judge scores safely, but ExP notes that they cannot measure user-response metrics[81]. Canaries ship to a small slice (GitHub switches “a number of Hubbers” to a candidate model first[1]) to catch disasters before a full test. Simulated users: AgentA/B runs LLM agents as simulated shoppers to pre-test web variants (an Amazon.com case study), positioned as a complement to, not a replacement for, real A/B tests[85].

9.17Cost and latency SLOs

Quality is not the only thing users experience. For a streaming LLM response, two latencies matter: time to first token (TTFT, how long until text appears) and time per output token (TPOT, also inter-token latency), which together give end-to-end latency ≈ TTFT + (output tokens − 1) × TPOT (the simulation below drops the −1, one token in 80–350). For reasoning models, hidden thinking tokens are generated before any visible text and are billed, so report time to first visible token alongside TTFT, and count reasoning tokens in cost per successful task. ExP lists TTFT at several percentiles, requests per second and tokens per second among its LLM experiment metrics, and counts truncated responses (finish_reason: "length") and 429 throttles as wasted utilisation[81]. A service-level objective (SLO) names a percentile, a threshold and a window, for example “p95 TTFT < 800 ms and 99% of requests complete in < 5 s over 28 days”; the error budget is 1 − target (here, 1% of requests), and the burn rate is the observed bad fraction divided by the budget (above 1× means the budget runs out before the window ends).

Cost needs the same care. The honest unit is cost per successful task: total spend divided by tasks that actually succeeded, so that throttled, truncated and failed responses count against the system that produced them.

def cost_per_success(model: str, n: int, p_success: float, p_429: float, p_trunc: float, rng):
    in_tok = rng.integers(800, 2500, n)
    out_tok = rng.integers(100, 700, n)
    throttled = rng.random(n) < p_429                              # 429: no tokens billed, retried later
    truncated = (~throttled) & (rng.random(n) < p_trunc)           # finish_reason == "length": billed, useless
    ok = (~throttled) & (~truncated) & (rng.random(n) < p_success)
    pin, pout = PRICE[model]
    cost = np.where(throttled, 0.0, in_tok * pin + out_tok * pout)
    return cost.sum() / n, cost.sum() / ok.sum(), ok.mean()

Prompt caching is a first-order cost driver for agents and RAG, where long system prompts, tool schemas and retrieved context repeat across calls. Providers bill cached input tokens at a steep discount; for example, Anthropic bills cache reads at 0.1× the base input price and 5-minute cache writes at 1.25×[118] (multipliers vary by model and provider, so check the current pricing page). Because editing or reordering the system-prompt prefix or tool list invalidates the cache, treat a drop in cache hit rate after a prompt, tool-schema or model change as a cost regression even when quality is unchanged.

9.18Drift detection and evolving eval sets

An eval set is a snapshot of what users asked when you built it. Three things drift away from it: the inputs (new topics, languages, lengths), the model (a provider updates the weights behind a fixed name), and the grader (a new judge version scores the same outputs differently). The model case is documented: Chen, Zaharia and Zou found GPT-4’s accuracy at classifying numbers as prime vs. composite fell from 84% in March 2023 to 51% in June 2023 behind the same API name[90]. The authors attribute this partly to GPT-4 following chain-of-thought prompts less reliably; GPT-3.5 moved the other way on the same task, and both models made more formatting mistakes in generated code (for example, markdown fences that make code not directly executable). Much of the drift was behaviour and format, which an extraction-sensitive eval reads as lost capability, so a canary eval should log format-compliance and extraction failures separately from accuracy (see the filter ablation in 9.3). Pin model snapshots where you can, and run a scheduled canary eval where you cannot. For inputs, the population stability index compares binned distributions (topic or intent clusters, length buckets):

PSI = Σi (ai − ei) ln aiei (9.8) ei and ai are the expected (eval-set) and actual (production) shares of bin i. Common heuristic thresholds: < 0.1 stable, 0.1–0.25 moderate, > 0.25 major (an industry convention, not a theorem).

Worked example (reproduced by drift_monitor.py). Expected topic shares [0.25, 0.25, 0.25, 0.25], actual [0.10, 0.20, 0.30, 0.40]: (−0.15)ln 0.4 + (−0.05)ln 0.8 + (0.05)ln 1.2 + (0.15)ln 1.6 = 0.137 + 0.011 + 0.009 + 0.071 = 0.228, “moderate”.

def psi(expected: np.ndarray, actual: np.ndarray, eps: float = 1e-6) -> float:
    e, a = np.clip(expected, eps, None), np.clip(actual, eps, None)
    return float(np.sum((a - e) * np.log(a / e)))


def ks_2samp(x: np.ndarray, y: np.ndarray) -> tuple[float, float]:
    xs, ys = np.sort(x), np.sort(y)
    grid = np.concatenate([xs, ys])
    d = float(np.max(np.abs(np.searchsorted(xs, grid, "right") / len(xs)
                            - np.searchsorted(ys, grid, "right") / len(ys))))
    ne = len(x) * len(y) / (len(x) + len(y))
    lam = (math.sqrt(ne) + 0.12 + 0.11 / math.sqrt(ne)) * d
    p = 2 * sum((-1) ** (j - 1) * math.exp(-2 * j * j * lam * lam) for j in range(1, 101))
    return d, min(1.0, max(0.0, p))


def cusum_down(x: np.ndarray, mu0: float, k: float, h: float) -> int | None:
    s = 0.0
    for t, v in enumerate(x):
        s = max(0.0, s + (mu0 - v) - k)
        if s > h:
            return t
    return None


def ewma_alarm(x: np.ndarray, mu0: float, sigma: float, lam: float = 0.2, L: float = 3.0) -> int | None:
    z = mu0
    limit = L * sigma * math.sqrt(lam / (2 - lam))
    for t, v in enumerate(x):
        z = lam * v + (1 - lam) * z
        if z < mu0 - limit:
            return t
    return None

The last line is about judge drift. A frozen anchor set of outputs with human labels, re-scored whenever the judge changes, separates “the system changed” from “the ruler changed”: here a judge upgrade moves the anchor-set pass rate by +7.5 points with no change to the system. Turning production failures into eval cases closes the loop. OpenAI’s guide says to “log everything” and to run continuous evaluation “to run evals on every change, monitor your app to identify new cases of nondeterminism, and grow the eval set over time”[21]; Vercel says any failing prompt “becomes a permanent part of the test set”[92]. In practice: every thumbs-down, guardrail hit, escalation and judge failure lands in a triage queue; a human writes the expected behaviour; near-duplicates are merged; and the case is added to the regression suite with a tag for its slice and its date, so you can check later whether old cases still represent traffic (Chapter 3.2).

Before launch.

  • Every trace is logged with inputs, retrieved context, outputs, tool calls, latency, tokens, cost, and model, prompt and judge versions.
  • An eval set built from real or realistic traffic, stratified by intent, with tail cases and a held-out slice (Chapter 3).
  • Assertion tests on hard constraints (format, citations, PII) at ~100% pass, run on every commit.
  • A regression suite gated by a paired comparison with a stated margin, repeats and a response cache; a separate capability suite that is reported, not gated.
  • RAG components measured separately: retrieval (recall@k, nDCG@k with stated gain), generation (faithfulness, answer relevance, abstention rate).
  • Every LLM judge validated against human labels (TPR, TNR or κ), version-pinned, with a frozen anchor set.
  • Harness sanity runs: gold/Oracle scores 1, null agent scores 0, infrastructure errors counted separately from failures.

After launch.

  • Inline guardrails evaluated as classifiers (precision, recall, false-block rate, p95 added latency).
  • Online judges on a risk-stratified sample plus a uniform slice; PPI-corrected rates with intervals on the dashboard.
  • Implicit signals (acceptance, retention, edits, re-asks) alongside explicit feedback, which is treated as a biased sample.
  • SLOs on p95/p99 TTFT and end-to-end latency, error and 429 rates, and cost per successful task, with burn-rate alerts.
  • A/B tests for significant changes, with an OEC, guardrail metrics, a pre-computed sample size and no peeking (or a sequential design built for it).
  • Every A/B result passes the sample-ratio-mismatch check first, and its variance is computed at the randomisation unit (delta method or cluster bootstrap over users), not per request.
  • Drift monitors on inputs (PSI, embeddings), model (scheduled canary eval) and judge (anchor set), and a weekly triage that turns failures into eval cases.

Solution

With our seed, an identical candidate now gets PASS 41.9%, FAIL 4.9% and REVIEW 53.2% (down from PASS 95.8%, FAIL 3.9% and REVIEW 0.3% at a 5-point margin; the naive column also moves, from 37.0% to 38.9%, because the change shifts the random-number stream): the 95% interval after 10 repeats is about ±0.024 wide, larger than the margin, so most runs cannot prove non-inferiority. The interval width scales as 1/√(items × repeats), so to halve it you need about four times the data: more items (best, because it also improves coverage), more repeats, or lower-variance items. This is the power calculation of Chapter 5.6 applied to a CI gate.

Suppose a pre-period covariate correlates with your OEC at ρ = 0.8 instead of 0.6. By how much does CUPED cut the variance, and how many users per arm does the 9,600-per-arm design of 9.15 need? Verify the variance ratio by calling cuped_demo with rho=0.8.

Solution

(This assumes the metric is continuous with a covariate that strong; binary thumbs-up rates rarely have one, which is another reason to prefer continuous implicit signals.)

  • Every eval tool is the same loop (dataset → solver → scorer → log → metric); learn one deeply (Inspect is a good choice) and read the others as dialects.
  • Extraction, filters and score conversion are part of the metric: strict vs flexible gsm8k differ by 30 points on identical generations, and an unknown score string can turn 0.708 into 0.000.
  • Agent harnesses need their own QA: gold or Oracle = 1, null agent = 0, separate verifier, content-addressed caches, and infrastructure errors counted apart.
  • Gate CI on paired, repeated comparisons with a non-inferiority margin; a single-run comparison blocked 37% of identical candidates in our simulation.
  • Evaluate RAG as retrieval plus generation; state k and the gain function; report abstentions instead of letting NaNs vanish; test numbers and positions explicitly.
  • Online judges must be calibrated and bias-corrected: a judge reading 0.80 with true 0.74 has a tight interval that never covers the truth, and PPI fixes it with a few hundred labels.
  • Thumbs data is sparse and self-selected; reweighting fixes only selection on observed covariates. Prefer implicit signals and random surveys.
  • A/B tests need an OEC, guardrail metrics, a pre-computed sample size and no peeking; watch p99, cost per successful task, and drift in inputs, model and judge.
