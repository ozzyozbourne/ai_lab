    Many Worlds: The Batched Data Layout

    MJWarp's whole point is to step thousands of simulations at once. This chapter is about how those worlds are laid out: which arrays have one row per world, which parameters can differ between worlds and how they are shared, where the bytes live, how to write inputs without breaking anything, and when the GPU actually beats C MuJoCo.

    Beginner About 2 h· Prerequisites: Ch 5 (and through it Ch 4)

    You will learn

    • Predict the shape of any Data field (nworld, ...) and any Model field (batched (B, ...) or structural).
    • Write per-world inputs in place with assign, wp.copy and fill_, and know why replacing an array is a trap.
    • Explain round-robin batching, field[worldid % B], and show it with per-world gravity.
    • Picture the pooled contact arrays tagged with worldid next to the per-world constraint arrays.
    • Turn a shape into byte addresses and see why nworld-first gives coalesced reads.
    • Know what .numpy() costs, batch your host reads, plot many worlds, and read a throughput curve.

    Before you start: recap

    • The four calls: mujoco.MjModel → mjw.put_model → mjw.make_data(mjm, nworld=...) → mjw.step(m, d) (Ch 5 §1).
    • On the device everything is float32; continuous m.opt fields are arrays of shape (1,), discrete ones are Python ints (Ch 5 §3).
    • A wp.array has a dtype, a shape and a device; vector dtypes such as wp.vec3 add trailing NumPy dimensions; on a GPU, .numpy() is a copy plus a sync (on Warp's CPU device it is a view of the same memory) (Ch 4 §2).
    • 32 lanes of a warp run in lockstep; branches serialize; contiguous reads coalesce (Ch 4 §4).
    • MuJoCo quaternions are (w, x, y, z) (Ch 2 §3).
    • qpos has nq entries (free joint 7, hinge 1) and qvel has nv (free 6, hinge 1) (Ch 2 §3).

    1The nworld-first rule

    A world is one complete, independent simulation. mjw.make_data(mjm, nworld=N) allocates the state of N of them at once, and every array in mjw.Data gets the same first dimension, nworld. Row w of d.qpos is the generalized position of world w, row w of d.xpos holds every body position of world w, and so on. That is the whole rule:

    d.<field>.shape == (nworld, <the MuJoCo size>, ...) e.g. d.qpos: (nworld, nq), d.xpos: (nworld, nbody)

    Classic MuJoCo has one MjData with qpos of shape (nq,). MJWarp keeps the same field names and simply stacks N of them. Kernels start with worldid = wp.tid() (or worldid, i = wp.tid() for a 2-D launch) and index qpos[worldid, i], so one launch updates all worlds.

    mjw.Model is different. It describes the scene, which is the same for every world, so most of it has no world dimension at all. But every batched field (one declared with a "*" spec: mostly numeric parameters such as masses, sizes, friction, gravity and timestep, plus a few integer selectors, §6) has a leading batch dimension B, which is 1 by default. A Model field of shape (1, nbody) is one row shared by every world. Make it (nworld, nbody) and each world gets its own row. Figure 1 shows the two layouts side by side; §6 explains the rule that maps worlds to rows.

    Example 6.1 walks over dataclasses.fields(d) and prints the shape of every array. The model is PLAYGROUND (a free ball, a free box and a hinged arm: nq = 15, nv = 13, nu = 1, nbody = 4 including the world body) with nworld = 4. Read the output as a table of rules: every row starts with 4.

    Three things stand out:

    • Empty is still a shape. act, mocap_pos and eq_active are (4, 0) because this model has no activations, mocap bodies or equality constraints. The script skips them, but they exist, so code that writes d.mocap_pos works for any model.
    • Per-world counters are arrays too. nefc, time, overflow and friends are (nworld,): each world has its own clock and its own constraint count.
    • Only two non-empty top-level arrays break the rule: nacon and ncollision are (1,). They count over all worlds, because contacts live in one shared pool (d.contact.pos is (naconmax,), §8). Constraint rows, in contrast, are per world: d.efc.force is (nworld, njmax).

    2Vector dtypes and their NumPy views

    Look again at xpos: its Warp shape is (4, 4) but .numpy() gives (4, 4, 3). Warp stores small fixed-size vectors and matrices as a single element, a vec3 is one element of 12 bytes. The NumPy view unpacks that element into a trailing dimension. Kernels see one element: p = xpos[worldid, bodyid] is a whole wp.vec3.

    Recall from Ch 2

    MuJoCo quats are (w,x,y,z); Ch 2 §3. MJWarp keeps that order in d.xquat; the only new thing here is that one quaternion is one 16-byte array element.

    MJWarp also defines its own small vector and matrix types in types.py (vec5, vec6, vec10, mat43, mat63, ...); for example each contact's five friction coefficients are one vec5 element of d.contact.friction. They behave the same way. d.energy is a vec2f per world (potential, kinetic), so its NumPy view is (nworld, 2).

    Tip

    The docstrings in types.py are written in NumPy shapes (xpos ... (nworld, nbody, 3)) while the declared spec uses Warp shapes plus a dtype (array("nworld", "nbody", wp.vec3)). Both are correct; they count different things. Example 6.9 prints them side by side.

    3From shape to bytes: linear memory

    Device memory is one long line of bytes. A Warp array is a pointer to the start of its block plus a shape, and the elements are stored row-major (C order): the last index changes fastest. For d.xpos, shape (nworld, nbody) of 12-byte vec3, the float with indices [w, b][k] sits at

    \text{off}(w, b, k) = \big((w\, n_\text{body} + b)\cdot 3 + k\big)\cdot 4

    bytes, which is what .strides says: (nbody · 12, 12) bytes per step along each axis. Whole worlds are laid end to end; inside a world, bodies are adjacent; inside a body, x, y, z are adjacent.

    Why does the order matter? Recall how a GPU reads memory.

    Recall from Ch 4

    32 lanes run in lockstep; branches serialize; contiguous reads coalesce; Ch 4 §4.

    Warp numbers the threads of a 2-D launch dim=(nworld, nbody) with the last dimension fastest (launch_coord in Warp's native/builtin.h): thread t gets (worldid, bodyid) = (t // nbody, t % nbody). That is the same order as the data. So 32 neighbouring threads, one warp, read 32 neighbouring vec3s: 384 contiguous bytes, a handful of memory transactions. Many MJWarp kernels are launched exactly like this, dim=(d.nworld, m.nbody) or (d.nworld, m.nv), with worldid, i = wp.tid() on the first line.

    Switch the overlay to dim=nworld, body 1: one thread per world reading the same body gives a strided pattern, one vec3 every nbody · 12 bytes. For small models the strides are short and still land in few segments; for a humanoid (17 bodies, 204 bytes per world) each thread hits a different 128-byte segment. This is one reason the pipeline prefers 2-D launches over a per-world loop.

    The trick in Example 6.2 is to write each float's own word index into d.xpos (it is an output array, so overwriting it before forward is harmless) and read it back through the NumPy view. A value of 95 at [7, 3, 2] proves that this float lives at byte 95 × 4 = 380.

    Going deeper: what if MJWarp were element-first?

    An (nbody, nworld) layout would make the per-world launch (dim=nworld, fixed body) perfectly coalesced and the 2-D launch strided. MJWarp chose nworld-first because it matches MuJoCo's own field layout (row w is exactly one MjData field), makes a world's state one contiguous block (cheap to copy one world out with get_data_into, or to slice d.qpos[w]), and keeps the common (nworld, n) launches coalesced. Kernels that need a different access pattern use tiles, shared memory or grid-stride loops (Ch 7 atlas, Ch 26).

    4Writing per-world inputs

    Inputs are the Data fields that you set and the pipeline reads: qpos, qvel, ctrl, act, qfrc_applied, xfrc_applied, mocap_pos, mocap_quat, eq_active, userdata. Because each has an nworld dimension, every world can get a different value. The recipe is always the same: build an (nworld, ...) array and copy it into the existing device array.

    Example 6.3 gives the arm hinge of PLAYGROUND a different angle in each world. The hinge is the last joint, so its qpos address is 14 (after two free joints of 7). After .assign we call mjw.forward, which runs kinematics for all worlds, and compute the arm tip from the body pose: tip = xpos + xmat @ (0.5, 0, 0).

    A rotation by q about +y maps the body x-axis to (\cos q, 0, -\sin q), so the tip height is 1 - 0.5 \sin q, matching to float32 precision (6e-8).

    Example 6.4 does the same for controls: d.ctrl is (nworld, nu), so we give world w a motor torque from −1 to 1 and step 100 times. The ball and box behave identically in every world; only the arm differs.

    The arm is a horizontal capsule with no damping, so gravity swings it down (positive angle) and the torque adds or removes energy; the strongest positive torque carries it over the top to 5.49 rad (past 3π/2, though short of a full turn, 2π ≈ 6.28). The spread of 4.3 rad is the point: one launch, eight different trajectories.

    Pitfall: assign and copy check bytes, not shapes

    For a NumPy or list source, array.assign(src) wraps it as wp.array(src, dtype=self.dtype, copy=False, device="cpu") and then calls wp.copy; for a Warp-array source it calls wp.copy(self, src) directly, with no dtype conversion (Warp's types.py, array.assign). wp.copy is a flat byte copy in memory order. It refuses a source that is larger than the destination but silently accepts a smaller one, and it does not compare shapes: an (nworld − 1, nv) source fills the first worlds and leaves the last world untouched; an (nworld, nv − 1) source would shift every row. Always build the full (nworld, ...) array (as np.tile(mjm.qpos0, (nworld, 1)) does) or assert src.shape == d.qpos.shape first.

    5Identity matters: replace vs assign

    There are two ways to put new numbers into d.qpos, and they look almost the same:

    d.qpos.assign(q)           # write INTO the existing array: same object, same device pointer
d.qpos = wp.array(q)       # REPLACE the attribute with a brand-new array somewhere else in memory

    For the next eager mjw.step both work, because step looks up d.qpos when it launches its kernels. The difference shows up for everything that grabbed the array before the replacement: a variable in your controller, a helper that cached d.qpos, a torch tensor that shares its memory (Ch 28) and, most importantly, a captured CUDA graph, which recorded the raw device pointer (Ch 24). They all keep reading and writing the old buffer, and nothing warns you.

    Line B is the quiet failure: old.fill_(0.0) was meant as a reset, it "worked" on the old buffer (old z is 0), and the simulation never saw it. Line C is the loud one: wp.array of a float64 NumPy array is a float64 Warp array, and the first kernel that reads it rejects it. From a NumPy source, assign would have converted to float32 for you, because it wraps the source with the destination's dtype.

    Rule of this course

    After make_data, never assign a new array to a Data field. Write into it with assign, wp.copy, fill_, zero_ or a kernel. The same holds for Model fields once you have captured a graph; before that, replacing a Model array is the simplest way to batch it (§6), as long as dtype and trailing shape match. Ch 24 shows the graph consequence and the recapture fix.

    6The Model batch dimension

    Every Model field is declared in types.py with array(dim_1, ..., dtype). The first dimension tells you whether it can vary per world:

    # mujoco_warp/_src/types.py (4.0.1 wheel)
class Option:
  timestep: array("*", float)
  gravity: array("*", wp.vec3)
  ...
class Model:
  body_mass: array("*", "nbody", float)     # "*" = any nonzero leading size B
  geom_type: array("ngeom", int)            # no "*": structural, shared by all worlds

    The docstring of array says it plainly: dim may also be "*", which means any nonzero size. put_model allocates every "*" field with B = 1 unless you pass batch_sizes. Kernels then read the row with a modulo, so any B works:

    # smooth.py::_cacc_world (gravity enters the recursive Newton-Euler pass here)
worldid = wp.tid()
cacc_out[worldid, 0] = wp.spatial_vector(wp.vec3(0.0), -gravity[worldid % gravity.shape[0]])

# forward.py::_next_time
time_out[worldid] = time_in[worldid] + opt_timestep[worldid % opt_timestep.shape[0]]

    The rule is the spec, not the dtype: a field can vary per world if and only if its spec starts with "*". Everything that defines the topology has no "*" and is shared: types (geom_type, jnt_type), the tree (body_parentid), addresses (jnt_qposadr, dof_bodyid), counts (m.nq is a plain Python int) and discrete options (m.opt.integrator, m.opt.solver, m.opt.iterations). All worlds share the same kinematic tree and the same kernels.

    A few integer and bool fields are batched, because they select data rather than define the tree: geom_dataid (which mesh or heightfield a geom uses), geom_matid, light_type, light_castshadow, light_active, mat_texid and actuator_historyadr are all array("*", ...) in types.py. Kernels read them round robin like any other batched field (bvh.py: geom_dataid[worldid % geom_dataid.shape[0], geom_id]). geom_dataid is how per-world meshes work: io_test.py's per_world_mesh helper compiles all mesh variants into the shared mesh tables, pads each body to the largest variant's geom count, and then sets a (nworld, ngeom) geom_dataid (with -1 to switch off an unused slot). To vary the tree itself (more bodies, other joints) you build different MJCF and run separate Models.

    In the 4.0.1 wheel, 133 Model arrays are batchable: 121 declared on Model and 12 on Option. (types.py has 157 "*" specs in total; the other 24 belong to RenderContext, Ch 27.) The other 324 Model arrays are structural. batch_sizes is the clean way to make a field per world: it allocates (B, ...) with every row a copy of the MJCF value, ready for in-place edits (Ch 10 builds domain randomization on it).

    Two ways to batch a Model field

    (1) mjw.put_model(mjm, batch_sizes={"body_mass": nworld}), then edit in place. (2) Replace the field: m.opt.gravity = wp.array(rows, dtype=wp.vec3) with any leading size B (Example 6.8; io_test.py::test_model_batched_fields does this for every batched field). Changing a field that other quantities are derived from (mass, inertia, sizes, qpos0) also needs mjw.set_const with matching batch sizes for the derived fields: that is Ch 10.

    7Round robin, not blocks

    With B rows and nworld worlds, world w reads row w % B. This is round-robin batching: rows are dealt to worlds like cards. With B = 2 the even worlds get row 0 and the odd worlds row 1; it is not "the first half gets row 0". (The tutorial notebook calls this distributing values "evenly" and assigns [gravity, -gravity] to "half of the worlds": true in count, but interleaved.)

    The stepper below walks one real kernel, smooth.py::_cacc_world, thread by thread with B = 3 and nworld = 8. Each thread computes its own row index; no thread ever looks at another world.

    One thread per world reads gravity[worldid % 3]

    smooth.py::_cacc_world
    @wp.kernel
def _cacc_world(
  gravity: wp.array[wp.vec3],
  cacc_out: wp.array2d[wp.spatial_vector],
):
  worldid = wp.tid()
  cacc_out[worldid, 0] = wp.spatial_vector(
    wp.vec3(0.0),
    -gravity[worldid % gravity.shape[0]])

    Five steps of 2 ms from rest give v_z = -5 \cdot 0.002 \cdot g = -0.0981 m/s for normal gravity. With [g, -g] the odd worlds fall up: interleaved, exactly as the modulo predicts. With B = nworld every world has its own row, which is the common case for domain randomization.

    Tip: want blocks? Build them yourself

    If you want worlds 0..3 to share one setting and 4..7 another, use B = nworld and fill the rows in blocks on the host (np.repeat(rows, nworld // B, axis=0)). The kernel always does w % B; only you decide what each row contains.

    8Pooled arrays: one list for all worlds

    Not every per-world quantity has a fixed size. The number of contacts changes every step and differs wildly between worlds (one world's tower falls, another's ball is in the air). Giving every world a worst-case block would waste memory, so MJWarp keeps contacts in one shared contact pool: d.contact.pos, d.contact.dist, d.contact.frame, ... have shape (naconmax,), a single counter d.nacon of shape (1,) counts the contacts found (the filled slots are min(nacon, naconmax)), and every contact carries a d.contact.worldid tag. A collision thread that finds a contact reserves the next free slot with an atomic add (collision_core.py::write_contact) and writes its world id next to the geometry.

    Two consequences to remember now (Ch 9 owns the details):

    • To find world w's contacts you filter: d.contact.worldid.numpy()[:min(nacon, d.naconmax)] == w. They are not contiguous and not sorted. get_data_into does this filtering for you when it copies one world back to an MjData (Ch 5).
    • nconmax is a per-world budget used to size the pool (naconmax = nconmax × nworld by default), not a per-world guarantee. njmax, in contrast, is a hard per-world limit because d.efc really has an nworld dimension.

    Source

    mujoco_warp/_src/types.py · Contact (every field array("naconmax", ...)) and Constraint (force: array("nworld", "njmax", float)); Data.nacon: array(1, int). collision_core.py · write_contact: cid = wp.atomic_add(nacon_out, 0, 1), then if cid < naconmax_in: ... contact_worldid_out[cid] = worldid_in.

    9Spec strings and mark_batched

    How does the library itself know which arrays are per world? Through the declared specs. The helper in types.py is tiny:

    def array(*args) -> wp.array:
  """A wrapper around wp.array that adds extra metadata to ease type introspection.

  Format is array(dim_1, dim_2, ..., dtype).  dim may be a constant int, or reference a size from
  Model or Data (e.g. "nq" or "nworld").  dim may also be "*", which means any nonzero size.
  """
  shape, dtype = args[:-1], args[-1]

  arr = wp.array(ndim=len(shape), dtype=dtype)
  arr.shape = shape

  return arr

    It returns an empty array whose .shape is overwritten with the names of the dimensions. That object becomes the dataclass field's type annotation, so dataclasses.fields(mjw.Data) tells you, for every field, ('nworld', 'nbody') and vec3f. It is metadata for introspection, not the runtime shape. Inside put_model, make_data and put_data, warp_util.mark_batched walks the dataclass and tags each real array whose spec starts with "*" or "nworld":

    # mujoco_warp/_src/warp_util.py
def mark_batched(obj):
  """Recursively set _is_batched = True on all batched warp arrays within obj."""
  ...
    spec_shape = getattr(f.type, "shape", ())
    if spec_shape and spec_shape[0] in ("*", "nworld"):
      val._is_batched = True

    Kernels never look at _is_batched; they use the modulo. Within the repository only the tests read the tag (io_test.py::test_is_batched_metadata checks that every "*"/"nworld" field is tagged; io_jax_test.py::test_put_model_nworld_array checks that geom_pos and opt.gravity are tagged and body_parentid is not), so think of it as a label for tools and interop layers that need to know which axis is the world axis.

    Pitfall: a replaced array loses its tag

    mark_batched runs once, inside put_model. When you replace m.opt.gravity with your own wp.array, the new array is untagged (Example 6.8 prints _is_batched tag: False). Simulation is unaffected; only code that relies on the tag is. Prefer batch_sizes plus in-place edits when you can.

    Example 6.9 also starts the course's running project: my_env.py gets its first helper, make_worlds(xml, nworld, ...), which returns (mjm, m, d) and asserts the nworld-first shape. Ch 8, 9, 10, 14, 24, 26 and 30 add to the same file.

    Version note

    The spec is metadata, and a few allocations differ from it on purpose. Constraint.J is declared ("nworld", 1, "njmax_nnz") (the sparse layout), but for a small model with the dense Jacobian make_data allocates (nworld, njmax_pad, nv_pad); Example 6.1 prints efc.J (4, 64, 16). Trust .shape at run time; use the spec to know which axis is which. The dev tree's types.py has 156 "*" specs vs 157 in the 4.0.1 wheel.

    Going deeper: the kernel analyzer enforces the modulo

    The repository (not the wheel) ships contrib/kernel_analyzer, a static checker for MJWarp kernels. One of its rules, MissingBatchModulo in ast_analyzer.py, flags a kernel that indexes a "*"-batched Model parameter without % shape[0]. That is how a 4.0.1 kernel stays correct for every B: the rule is mechanical, so a tool can check it. If you write your own kernels that read Model fields (Ch 26), follow the same pattern.

    10Host reads and plotting many worlds

    arr.numpy() looks innocent, but on a GPU it allocates host memory, copies device to host, and waits for every kernel queued so far. Python sits idle until the GPU has drained the queue, and the GPU sits idle while Python prepares the next step. Do it every step and you add one more round trip to every step.

    "One more", because an eager mjw.step on a GPU already waits for the device inside the solver. With the default m.opt.graph_conditional = True, solver._solve runs its iterations in wp.capture_while(nsolving, ...). When no CUDA graph is being captured, Warp runs that loop on the host: before each check it copies the 1-element counter nsolving to pinned host memory and synchronizes the stream. So an eager step synchronizes once per solver iteration plus once for the final check, at least once per step. Only a captured CUDA graph (Ch 24), where the loop becomes a device-side conditional node, lets the host enqueue step after step without waiting. The advice still holds: a .numpy() per step adds an allocation, a copy and one more full sync on top of that.

    Version note

    mujoco-warp 4.0.1, solver.py:4711: if m.opt.iterations != 0 and m.opt.graph_conditional: wp.capture_while(...), otherwise a Python for loop over m.opt.iterations. The eager host-side loop is in Warp 1.19's capture_while (warp.copy(condition_host, condition) then warp.synchronize_stream). On Warp's CPU device the condition is read straight from memory, with no copy.

    On Warp's CPU device there is no separate processor to wait for, and .numpy() does not even copy: array.to("cpu") is a no-op for an array that is already on the CPU, and the result is a NumPy view that aliases the Warp buffer (Warp's types.py, array.numpy()). So on the CPU the two loops cost the same, and the ratio above is within timing noise (1.0x to 1.05x across runs on this box). The example runs each variant once untimed and then keeps the best of 3 alternating runs, because the first timed loop after a fresh step is up to 2x slower whatever it does; without that, the first variant would look expensive for the wrong reason. On a GPU the gap is real: each read is a device-to-host copy plus a full sync, and how large it is depends on the GPU and nworld. Run the notebook cell on a Colab GPU to see the real gap; the timing numbers in this course are never GPU numbers unless your own notebook prints them.

    Pitfall: on CPU, .numpy() is a live view

    Because the CPU result aliases device memory, zs.append(d.qpos.numpy()[:, 2]) in a CPU loop stores 100 views of the same memory, and every entry shows the last step. That is why Example 6.10 appends .numpy()[:, 2].copy(). On a GPU the same line happens to work, because there .numpy() returns a fresh host copy; add .copy() anyway so the code is correct on both devices.

    Recall from Ch 5

    get_data_into is the expensive version of this: it performs dozens of device-to-host copies to fill one MjData. Use it to look at one world, never inside a training loop (Ch 5 §6).

    Record on the device, read once

    To plot trajectories you need values from many steps. The batched way is to keep a (nstep, nworld) buffer on the device and fill one row per step with a tiny kernel, then read it once. Example 6.11 does that for 64 bouncing balls and 256 double pendulums.

    The measured bounce comes about 20 ms after the free-fall prediction because MuJoCo contacts are soft: the ball first sinks into the floor while the contact force decelerates it, and only then does qvel z turn positive (Ch 2 §4 has the intuition).     11When is the GPU actually faster?

    Batching is what makes MJWarp fast, and Example 6.12 shows why with one number first: a single mjw.step of the tiny BALL_DROP scene is 95 kernel launches (counted by wrapping wp.launch for one call). Each launch has a fixed cost on the host and the device, whether it runs 1 thread or 100,000. So:

    • Expect one world on a GPU to be slower than C MuJoCo. C MuJoCo runs the whole step for one world in about 3 µs on one CPU core (Example 6.12 measures it); MJWarp pays ~95 launches of several µs each for the same work, plus, in eager mode, a host-device round trip at each solver loop check inside wp.capture_while (§10). This course has no GPU measurement of its own: the first row (nworld = 1) of Example 6.12 in your GPU notebook is the check.
    • Throughput grows with nworld while the device has idle lanes: the step time barely changes, so world-steps per second grow almost linearly (the launch-overhead regime).
    • Then the device is full (every SM busy, occupancy saturated: there are more worlds than lanes that can run at once): step time starts to grow with nworld and world-steps/s flattens. Where that happens depends on the GPU and the model.

    Even on the CPU device the shape is visible: the step time stays about flat (3 to 4 ms on this box) from 1 to 64 worlds, so world-steps/s grows about linearly with nworld: roughly 50× to 80× for 64× the worlds across runs, the spread being machine-load noise in a 3 ms step. (The example discards one timed pass and warms each nworld up for 30 steps first; otherwise the first timed loop in the process looks about 2× slower than it is.) The CPU device never catches C MuJoCo here: it has a handful of cores, not thousands of lanes. On your Colab GPU the curve keeps climbing for much longer. Paste your notebook's JSON below to plot your own numbers next to the CPU ones.

    Two forward links. The launch overhead and the solver's host round trips are exactly what CUDA graphs remove: one graph launch replays all 95 kernels, with the solver loop as a device-side conditional node (Ch 7 §10 teaser, Ch 24). And "device full" is where profiling and tuning (Ch 25) start to matter.

    12Check yourself

    Quiz

    A model has nbody = 5. With nworld = 1024, what are the Warp shape and the NumPy shape of d.xpos?

    One vec3 is one Warp element; the NumPy view unpacks it into a trailing axis of 3.

    m.opt.gravity has 3 rows and nworld = 8. Which worlds use row 1?

    1 % 3 = 4 % 3 = 7 % 3 = 1. Rows 0 and 1 serve three worlds each, row 2 only two.

    Why is m.geom_type shape (ngeom,) with no batch dimension?

    Its spec is array("ngeom", int): no "*". Only fields with a "*" spec can vary per world: mostly numeric parameters, plus a few integer selectors such as geom_dataid.

    Your env wrapper stored self.ctrl = d.ctrl. Later some code ran d.ctrl = wp.array(actions, dtype=float). What happens on the next step?

    Replacement changes identity. Write with wp.copy(d.ctrl, src) or d.ctrl.assign(...) instead (Example 6.6).

    What is the shape of d.contact.pos for nworld = 32 with the default nconmax = 48?

    Contacts live in one pool of naconmax slots; d.contact.worldid says whose contact each slot holds.

    With nbody = 4, at which byte offset is d.xpos[2, 1][2] (the z of body 1 in world 2)?

    ((2·4 + 1)·3 + 2)·4 = (27 + 2)·4 = 116 bytes.

    Why does d.qpos.numpy() inside the stepping loop slow a GPU run so much?

    An eager GPU step already syncs inside the solver (wp.capture_while checks its counter on the host); a .numpy() adds an allocation, a copy and one more full sync every step. Record on the device (a (nstep, nworld) buffer) and read once (Example 6.11).

    d.qvel.assign(np.ones((nworld - 1, nv))). What happens?

    wp.copy only refuses a source larger than the destination (Example 6.5).

    On a GPU, you should expect a single world of BALL_DROP to step slower in MJWarp than in C MuJoCo. Why?

    About 95 launches of several µs each, against about 3 µs for a whole C step; the first row of Example 6.12 in your GPU notebook confirms it. Eager stepping also syncs with the host at each solver loop check (§10). Throughput only wins with many worlds per launch (and fewer launches and no host round trips: CUDA graphs, Ch 24).

    Why the density matters

    put_model decides once whether the fluid model runs at all: m.has_fluid = bool(mjm.opt.wind.any() or mjm.opt.density > 0 or mjm.opt.viscosity > 0) (io.py), and passive.py calls _fluid only if m.has_fluid. Without density in the MJCF, has_fluid is False and your wind array is never read: the balls do not drift (verified on CPU). A batched array is live; a Python-level decision made at put_model time is not.

    Show one solution 
    @wp.kernel
def seed_qpos(seed: int, qpos0: wp.array2d(dtype=float), adr: int, lo: float, hi: float,
              qpos: wp.array2d(dtype=float)):
    worldid, i = wp.tid()
    qpos[worldid, i] = qpos0[worldid % qpos0.shape[0], i]      # round robin, like the library
    if i == adr:
        state = wp.rand_init(seed, worldid)                    # one stream per world
        qpos[worldid, i] = lo + (hi - lo) * wp.randf(state)

wp.launch(seed_qpos, dim=(d.nworld, mjm.nq), inputs=[42, m.qpos0, 0, -1.0, 1.0], outputs=[d.qpos])

    14Summary

    Key takeaways

    • Every Data array is (nworld, ...); only the pool counters nacon and ncollision are (1,), and the contact arrays are one (naconmax,) pool tagged with worldid. Constraint rows are per world.
    • Vector dtypes are one Warp element: xpos is Warp (nworld, nbody), NumPy (nworld, nbody, 3).
    • Memory is row-major: offset = ((w·nbody + b)·3 + k)·4. With dim=(nworld, n) launches, a warp reads contiguous bytes.
    • Model fields with a "*" spec have a batch dimension B (default 1) and are read as field[worldid % B]: round robin, not blocks. Structural fields and discrete options are shared.
    • Write inputs in place (assign, wp.copy, fill_, kernels). Replacing an array breaks every holder of the old one; assign checks bytes, not shapes.
    • On a GPU, .numpy() is an allocation, a copy and a sync, on top of the sync an eager step already does inside the solver; on Warp's CPU device it is a view of the live buffer (add .copy() to keep a snapshot). Record on the device, read once.
    • Expect one world on a GPU to be slower than C MuJoCo (≈95 launches of several µs each against ≈3 µs for a whole C step, plus solver-loop syncs when stepping eagerly; the first row of Example 6.12 in your GPU notebook checks it); throughput comes from many worlds per launch.
