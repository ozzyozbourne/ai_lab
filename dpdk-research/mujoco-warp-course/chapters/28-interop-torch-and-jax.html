    Part VI · Chapter 28

    Interop with PyTorch and JAX

    MJWarp keeps every world's state in Warp arrays on the GPU. A learning framework wants that state as torch tensors or JAX arrays, and wants to send actions back. This chapter shows how to do that without copying a single byte through the CPU: zero-copy torch views, writing actions into d.ctrl, wrapping mjw.step as a JAX operation with wp.jax_callable, and the traps on each road (dtypes, strides, streams, XLA memory, stale example scripts).

    Expert About 80 min· Prerequisites: Ch 24, Ch 26 (for the RL capstone, Ch 30, §1-§3 are enough)

    You will learn

    • How wp.to_torch and wp.from_torch share one buffer between Warp and PyTorch, and how to prove it with data pointers.
    • The caveats: float32 everywhere, vec3/quat arrays as trailing dims, strided slices, float64 tensors, uint32 buffers, and CUDA streams.
    • How to feed a torch policy's actions into d.ctrl without replacing the array.
    • How to wrap an MJWarp step as a JAX op (wp.jax_callable, graph_mode, output_dims), unroll it with lax.scan, and set the XLA variables before import jax.
    • What is stale in contrib/jax_unroll.py, the custom_vmap batching pattern, the MJX field contract, and where the ecosystem frameworks fit.

    Before you start: recap

    • A wp.array lives on one device and has a raw address, arr.ptr; arr.numpy() copies it to the host (Ch 4 §2).
    • Every Data field is world-first, (nworld, ...); xpos is a vec3 array, xquat a quat array (Ch 6 §2).
    • Write into existing arrays (assign, wp.copy, kernels); never rebind a Data field to a new array (Ch 6 §5).
    • A CUDA graph records launches once and replays them; conditional nodes loop on device (first met in Ch 7 §10; owner Ch 24).
    • Custom kernels read and write MJWarp's arrays directly, one thread per world (Ch 26).
    • pip warp-lang 1.19.0 is a CUDA 13 build and needs an R580+ driver (Ch 1 §5).

    1Zero-copy: one buffer, several views

    A GPU array is a block of device memory plus a little description: where it starts (a pointer), the element type, the shape and the strides (how many bytes to skip to reach the next element along each axis). Two libraries can look at the same block as long as they agree on that description. Nothing is copied; each library just builds its own object around the same pointer. This is called zero-copy sharing.

    There are standard ways to pass that description between libraries. DLPack is a small C struct (pointer, device, dtype, shape, strides) that PyTorch, JAX, NumPy and Warp all understand. NumPy's __array_interface__ and the GPU twin __cuda_array_interface__ are Python dictionaries with the same information. Warp implements all of them; which one a given call uses is a detail, the result is the same: a second view of one buffer.

    Warp provides the conversions as plain functions:

    CallGivesCopies?Notes (warp 1.19 source)
    wp.to_torch(a)torch.TensornoCUDA: torch.as_tensor(a, device=...) via __cuda_array_interface__; CPU: torch.as_tensor(numpy.asarray(a)); bfloat16: DLPack

    Pitfall: a view aliases live memory; clone what you keep

    Lifetime is not the problem: both directions keep a reference. wp.from_torch stores the tensor inside the Warp array (a._tensor = t), and wp.to_torch builds the tensor with torch.as_tensor on the array itself on CUDA (the source comment: "we must be sure to maintain a reference to the owning object to prevent memory allocs going out of scope") or on numpy.asarray(a) on CPU, so the tensor keeps the Warp array alive even after del d. The two real dangers are different:

    • Aliasing. The view always shows the current buffer. The wp.to_torch docstring: "Clone the tensor if PyTorch must retain those values after Warp may modify or zero the underlying array." A replay buffer that stores q itself, not q.clone(), stores the same memory N times.
    • Rebinding. If d.qpos is ever replaced by a new array (d.qpos = ..., or a fresh make_data), the old view does not follow: it keeps reading the old buffer, which is still allocated because the view holds it, and silently goes stale. Make the views again after you rebind a field (Figure 4).

    2Caveats: dtypes, shapes, contiguity and streams

    Zero-copy only works when both sides describe the memory the same way. Four things go wrong in practice.

    Dtypes and shapes

    MJWarp stores every float as float32. Composite Warp types become extra trailing tensor dimensions: a vec3 array of shape (nworld, nbody) is a torch tensor of shape (nworld, nbody, 3). Quaternions keep MuJoCo's (w, x, y, z) order (Warp's wp.quat type is (x, y, z, w) in its own math functions, but MJWarp only uses the storage; Ch 4 §6).

    Data fieldWarp dtype, shapetorch view
    d.qposfloat32, (nworld, nq)(nworld, nq) float32
    d.xposvec3f, (nworld, nbody)(nworld, nbody, 3)
    d.xquatquatf, (nworld, nbody)(nworld, nbody, 4), (w, x, y, z)
    d.xmatmat33f, (nworld, nbody)(nworld, nbody, 3, 3)
    d.cvelspatial_vectorf, (nworld, nbody)(nworld, nbody, 6), (rot, trans)
    packed RGB of the rendereruint32torch.uint32 (few ops; unpack first, Ch 27)

    Going the other way, wp.from_torch maps the tensor's dtype: torch.float64 becomes wp.float64, torch.int64 becomes wp.int64. That is not an error yet, and wp.copy into a float32 MJWarp field does not check the dtype either: it only compares the element size in bytes (type_size_in_bytes(src.dtype) != type_size_in_bytes(dest.dtype) in warp/_src/context.py::copy). So 8-byte float64 and int64 sources raise RuntimeError: Incompatible array data types, but a 4-byte int32 or uint32 source is copied bit for bit with no error. A policy that emits discrete torch.int32 actions writes [1, 2, 3, 4] into d.ctrl as the denormal floats 1e-45 3e-45 4e-45 6e-45 (Example 28.2, part 3). The rule: convert in torch first (.float() or .to(torch.float32)) before wp.from_torch. Many torch defaults are float32 already, but anything that went through NumPy (torch.from_numpy of a float64 array) is float64.

    Contiguity and strides

    A tensor is contiguous when its elements sit in memory in plain row-major order with no gaps. Slicing a column (acts[:, 1]) or transposing makes a strided view: same buffer, bigger jumps. For a scalar dtype, wp.from_torch keeps the strides and returns a strided Warp array; it is still zero-copy, and wp.copy handles it. For a vector or matrix dtype the trailing component dimensions must be contiguous, or wp.from_torch raises. The widget shows the four cases Example 28.2 tries.

    Streams

    A CUDA stream is a queue: kernels in one stream run in order, kernels in different streams may run at the same time. When torch reads wp.to_torch(d.qpos), its kernel must not start before MJWarp's last kernel that writes qpos has finished. The two docstrings in warp/_src/torch.py spell out the rules: streams made by warp.Stream(), including Warp's default stream, are blocking streams, which implicitly synchronize with the CUDA legacy default stream that torch uses by default; streams made with torch.cuda.Stream() are non-blocking. So:

    • Default torch stream + default Warp stream: ordered, nothing to do.
    • torch on its own torch.cuda.Stream(): run MJWarp on that same stream with wp.ScopedStream(wp.stream_from_torch(side)), or make one stream wait for the other (wp.wait_stream, torch.cuda.current_stream().wait_stream(...)). Keep a Python reference to every Warp array you use on that side stream (temporaries included) until after the wait_stream or a synchronize: the stream_from_torch docstring warns "ensure that Warp-owned resources are not garbage-collected while work on the non-blocking stream is still pending".
    • Host reads: .numpy() waits for the work; reading a torch CUDA tensor on the host (.item(), .cpu()) waits for torch's stream. On CPU there are no streams; wp.synchronize() is still a good habit before torch touches Warp memory.
    Going deeper: what from_torch checks

    From warp/_src/torch.py::from_torch: it converts torch strides (elements) into byte strides (s * ctypes.sizeof(dtype._type_)). For a dtype with a _shape_ (vectors, matrices) it requires the tensor's last dims to equal that shape and the innermost strides to be exactly one element and one row, then trims those dims from shape and strides. It computes a capacity from the tensor's untyped storage, so a view that starts in the middle of a storage still knows where the allocation ends. With requires_grad it also wraps (or allocates) a gradient buffer; that is what Ch 29's tape uses for plain Warp kernels.

    3Feeding actions in: copy into d.ctrl, never replace it

    A policy produces a tensor of actions, one row per world. There are two ways to hand it to MJWarp. One is right.

    Recall from Ch 6 and Ch 24

    Write into existing arrays; rebinding a field to a new array leaves every holder of the old address behind (Ch 6 §5). A CUDA graph records launches once and replays them; conditional nodes loop on device (Ch 7 §10). The recorded launches hold raw addresses, so a captured step keeps reading the old d.ctrl buffer (Ch 24).

    Example 28.3 closes the loop with a torch controller on CARTPOLE. Observations come out through zero-copy views made once (they follow d.qpos and d.qvel forever, since those are never replaced). The policy is a linear state feedback u = \mathrm{clip}(g_k\,K x, -1, 1) with gains K from an LQR design, scaled by g_k \in [0, 1] across worlds, so world 0 has no controller and world 7 the full one. Actions go in with wp.copy(d.ctrl, wp.from_torch(act.contiguous())). An equivalent zero-copy form is wp.to_torch(d.ctrl).copy_(act): torch writes straight into MJWarp's buffer.

    Tip: do the per-step work on the device

    Everything in the loop above stays on Warp's device: torch.cat of two views, a matmul, a clamp, one wp.copy. The only host reads are at the end. Ch 30 turns this pattern into the CartpoleEnv wrapper (torch backend), with the step graph-captured (Ch 24) and observations and rewards from kernels (Ch 26).

    4The JAX bridge: mjw.step as a JAX op

    JAX is different from torch in two ways that matter here. Its arrays are immutable: a function never changes its inputs, it returns new arrays. And JAX code is traced and compiled: jax.jit turns a Python function into one XLA program, and jax.lax.scan turns a loop into a single compiled loop. A live zero-copy view of MJWarp state fits neither idea. Example 28.4 shows why: the "immutable" jax.Array from wp.to_jax(d.qpos) changes when MJWarp steps.

    The bridge that works is wp.jax_callable. It turns a Python function whose arguments are annotated Warp arrays into a JAX operation: an XLA foreign function interface (FFI) call. XLA allocates the input and output buffers; when the compiled program reaches the call, Warp wraps those buffers as Warp arrays (no copy) and runs your function on them. Your function copies the inputs into MJWarp's own Data, steps, and copies the results into the outputs. From JAX's side it is a pure function (qpos, qvel) -> (qpos', qvel').

    Step 0: the environment, before import jax

    Three variables must be in os.environ before JAX starts its backend, because XLA reads them once. The only placement that is always early enough is before the first import jax, which is why the notebook sets them in a cell of their own.

    The bridge, piece by piece

    The pieces, as _src/jax_test.py writes them:

    • A closure over m and d. warp_step(qpos_in, qvel_in, qpos_out, qvel_out) does not take the model or data as arguments; it uses the ones in scope. Inputs come first, outputs last (a jax_callable rule), and every argument has a Warp array annotation (wp.array2d[wp.float32]).
    • num_outputs=2 and output_dims. XLA allocates outputs before it calls you, so their shapes are given up front: {"qpos_out": (NWORLD, nq), "qvel_out": (NWORLD, nv)}. This is why NWORLD is fixed for a compiled program. The call returns a list; unpack it (qpos, qvel = warp_step_fn(...)) or lax.scan complains that the carry changed from a tuple to a list.
    • graph_mode=wp.JaxCallableGraphMode.WARP. Warp, not XLA, captures the CUDA graph. The docstring says to use this mode "when the callable cannot be used as a subgraph, such as when it uses conditional graph nodes", which mjw.step does when m.opt.graph_conditional is true (the solver's capture_while).
    • An explicit m.opt.graph_conditional. jax_test.py runs both values. The course sets ON_GPU and wp.is_conditional_graph_supported(): conditional nodes need CUDA 12.4+ (Ch 24). The fallback branch in solver.py::_solve (a fixed Python loop of m.opt.iterations iterations) carries the comment "This branch is mostly for when JAX is used as it is currently not compatible with CUDA graph conditional": that is the situation where XLA captures (graph_mode=JAX). With WARP mode, Warp captures. jax_test.py runs both settings in WARP mode (GPU only, and its only check is that the call does not raise; not run in this course). If a capture fails on your setup, False is the safe choice.
    • A skip guard. The test skips unless jax.default_backend() == "gpu" and wp.get_device().is_cuda.

    Pitfall: the op is not really pure

    JAX believes warp_step_fn is a pure function of (qpos, qvel). It is not. Everything you do not copy in lives on in d between calls: d.time keeps counting, d.qacc_warmstart carries the last solver solution, d.act, d.ctrl, d.mocap_pos and the contact buffers keep whatever the previous call left. Two jitted functions that close over the same d share that hidden state. If you need it, pass it in and out explicitly, as the Apollo notebook does with ctrl and qacc_warmstart. And because d has one fixed nworld, every array that crosses the boundary has leading dimension NWORLD.

    The torch and JAX versions tell the same story: gain 0 lets the pole fall, gain 0.14 loses it too, gain 0.29 keeps it up but swinging (up to about 0.39 rad in Figure 5, a reward dip in Figure 7), and from gain 0.43 on the pole stays upright.     7Batching per-env code: the custom_vmap pattern

    JAX RL libraries (Brax, Playground's MJX environments) write the environment step for one environment and then call jax.vmap to run thousands. vmap normally works by pushing a batch dimension through every operation. A Warp op cannot be treated that way: it was built for one fixed NWORLD and fixed output_dims. wp.jax_callable does take a vmap_method argument (default "broadcast_all", also settable per call) that it passes to jax.ffi.ffi_call. Under jax.vmap the batched FFI call gets an extra leading axis, and Warp folds the batch dims into each array's first dim (collapse_batch_dims), so the Python function sees arrays with B times as many rows. A Warp function that closes over a fixed-size mjw.Data (nworld=1 or NWORLD) cannot accept that: the arrays it receives no longer have the shape of the Data it steps, which is why the Apollo pattern routes the batch to an op built for NWORLD worlds instead. The Apollo locomotion notebook (contrib/apptronik_apollo_locomotion.ipynb) solves this with jax.custom_batching.custom_vmap: you give the per-env function a vmap rule, and when vmap meets the function it calls the rule once with the whole batch. The rule calls the batched MJWarp op a single time.

    The Apollo rule, condensed (it works on mjx.Data structs; the full cell also lists which mjx.Data fields come back batched):

    @jax.custom_batching.custom_vmap
def step(d: mjx.Data):
  return d

@step.def_vmap
def step_vmap_rule(axis_size, in_batched, d: mjx.Data):
  if in_batched[0].ctrl:
    assert d.ctrl.shape[0] == axis_size
  else:
    d = d.replace(ctrl=jp.tile(d.ctrl, (axis_size, 1)))
  ...
  qpos, qvel, xpos, xmat, qacc_warmstart, subtree_com, cvel, site_xpos = jax_mjwarp_step(
    d.ctrl, d.qpos, d.qvel, d.qacc_warmstart
  )
  d = d.replace(qpos=qpos, qvel=qvel, ...)
  return d, out_batched

    Three details carry over to any use of the pattern. The Warp op is fixed to NWORLD, so the rule asserts or tiles to that size (the notebook also tiles a single policy action to NWORLD for its rollout). The op returns more than qpos/qvel: whatever the env's observation and reward code reads (xpos, site_xpos, cvel, ...) plus qacc_warmstart, so the solver's warmstart survives the functional round trip. And a small custom kernel (xquat_to_xmat) converts MJWarp's (w, x, y, z) body quaternions into the rotation matrices that mjx.Data.xmat expects. Example 28.8 is a minimal, runnable version on plain arrays that counts how often the Warp function runs.

    Eight Python-level calls of a 1-world op versus one call of the 8-world op, with identical results (max |loop - vmap|: 0.0). On a GPU the difference is the whole point of MJWarp: one launch sequence over 8192 worlds instead of 8192 tiny ones. The example keeps the eager loop to the first 8 envs even there: in WARP mode the graph-cache key is hash((device_ordinal, call_id, *ip, *op)) (warp/_src/jax/ffi.py), and every Python-level call of a jax_callable assigns a new call_id (self.call_id += 1 in __call__). So each eager call misses the cache even if XLA happens to reuse the same addresses, and captures a new CUDA graph of mjw.step; each eager call pays a full graph capture, so 8192 eager calls are impractical. A jitted function traces once, keeps one call_id and replays while the addresses match. Each eager call also adds one entry to the op's call_descriptors dict, which is never removed.

    8MJX impl="warp" and the field contract

    Hand-written jax_callable wrappers are the do-it-yourself route. The official JAX route is MJX, MuJoCo's JAX package, which the README names for JAX users: "you can use MJWarp via MJX and the legacy MJX environments in Playground's rss2025 directory". The MuJoCo documentation describes an MJX implementation switch, impl="warp", that runs a subset of the MJWarp API behind MJX's JAX interface. MJX is a separate package (mujoco-mjx) and its API is not part of this repository, so this course does not print MJX calls; check the MJX docs for the version you install.

    Version note

    The repo marks its own JAX bridges as temporary: _src/jax_test.py carries "TODO(team): JAX test is temporary, remove after we land MJX:Warp", and pyproject.toml says the same about the [cpu]/[cuda] JAX extras. Expect the hand-written bridge to be replaced by MJX's.

    What the repository does contain is the contract MJX relies on to wrap MJWarp's structs: _src/io_jax_test.py ("do not edit this file without consulting with the MuJoCo/MJX team").     Pitfall: _is_batched is metadata

    A batched Model field with leading dim 1 is read with worldid % 1 by the kernels (round-robin, Ch 6 §7). A JAX wrapper must not assume shape[0] == nworld for Model fields; only Data fields scale with nworld.

    10Check yourself

    Quiz

    You make q = wp.to_torch(d.qpos), then call mjw.step(m, d) 10 times. What does q contain?

    q.data_ptr() == d.qpos.ptr: it is the same memory, so it always shows the current state (after the Warp work has finished).

    A policy returns a torch.float64 action tensor. What does wp.copy(d.ctrl, wp.from_torch(act)) do?

    float64 is 8 bytes and the float32 field 4, and wp.copy compares element byte sizes, so it raises. Beware the 4-byte case: an int32 tensor would pass the size check and be copied bit for bit as garbage floats, with no error. Call act.float() first (Example 28.2, part 3).

    What does wp.from_torch(acts[:, 1]) return for a (nworld, 3) float32 tensor?

    Byte strides (12,); wp.copy into d.ctrl then works. A vec3 view with a strided inner dim would raise.

    When must you order the torch and Warp streams yourself?

    torch.cuda.Stream() streams are non-blocking; run MJWarp on the same stream with wp.ScopedStream(wp.stream_from_torch(side)) or wait between them.

    Why are the three XLA variables set before import jax?

    Before the import is the one placement that is always early enough; the notebook gives them a cell of their own.

    put_data(mjm, mjd, nworld=8192, nconmax=64 * 8192) in mujoco-warp 4.0.1 allocates how many contact slots?

    nconmax is per world; the total naconmax = nconmax x nworld = 64 x 8192 x 8192 = 4,294,967,296. Pass nconmax=64.

    With graph_mode=WARP, a print inside warp_step fires...

    FfiCallable.ffi_callback keys a graph cache by (device, call_id, buffer addresses) and replays on a hit (the stepper in §4). Inside one jitted program the call_id is fixed, so it replays while the addresses match; every eager Python call gets a new call_id and always captures.

    Why does the Apollo notebook wrap its step in jax.custom_batching.custom_vmap?

    Example 28.8: 8 calls of a 1-world op in a loop versus 1 call of the 8-world op under vmap.

    Two different jitted functions close over the same d and both call the Warp op. What do they share?

    Pass whatever state matters in and out explicitly (Apollo does it for ctrl and qacc_warmstart).

    Exercise 28.2: make_ctrl_writer(d)

    Auto-checked

    Write make_ctrl_writer(d). It returns a function write(actions) that copies a torch tensor of shape (nworld, nu) into d.ctrl without replacing it, accepting any float dtype. The asserts check the values and that d.ctrl is still the same object at the same address.

    def make_ctrl_writer(d):
    ...

before_obj, before_ptr = d.ctrl, d.ctrl.ptr
write = make_ctrl_writer(d)
write(torch.full((NWORLD, mjm.nu), 0.5, dtype=torch.float64, device=dev))
assert d.ctrl is before_obj and d.ctrl.ptr == before_ptr

    Show solution
    def make_ctrl_writer(d):
    target = d.ctrl                      # hold the array, not the attribute
    def write(actions):
        src = wp.from_torch(actions.to(torch.float32).contiguous())
        wp.copy(target, src)             # values move, the address stays
    return write

    .to(torch.float32) fixes the dtype trap from §2; .contiguous() is free when the tensor already is.

    Stretch: mjw.forward as a JAX op

    Stretch

    Wrap mjw.forward with wp.jax_callable so that it maps (qpos, qvel) to qacc (one output), and wrap mjw.step as in Example 28.5. On the double pendulum (Euler integrator, no damping) check that qvel + h * qacc from the forward op equals the qvel the step op returns. Then explain what the two ops share when they close over one d, and what jax.grad does to either.

    Show a solution sketch
    def warp_forward(qpos_in: wp.array2d[wp.float32], qvel_in: wp.array2d[wp.float32],
                 qacc_out: wp.array2d[wp.float32]):
    wp.copy(d.qpos, qpos_in); wp.copy(d.qvel, qvel_in)
    mjw.forward(m, d)
    wp.copy(qacc_out, d.qacc)

fwd = wp.jax_callable(warp_forward, num_outputs=1, graph_mode=mode,
                      output_dims={"qacc_out": (NWORLD, mjm.nv)})
(qacc,) = fwd(qpos, qvel)                  # a list of one array
qpos1, qvel1 = stp(qpos, qvel)
assert jp.allclose(qvel + mjm.opt.timestep * qacc, qvel1, atol=1e-5)

    On CPU (graph mode NONE) the largest difference is about 4e-7, float32 rounding. Both ops copy into and out of the same d: everything not copied in (d.time, d.qacc_warmstart, d.ctrl, contacts) is shared, and whatever one op leaves in d is what the other op's next call starts from, except the fields it copies in. Give each op its own Data when that matters. jax.grad raises for both (§5).

    12Summary

    Key takeaways

    • wp.to_torch(d.field) is a zero-copy view (same data_ptr); make views once and reuse them. .numpy() is a copy that goes stale.
    • MJWarp is float32; composite dtypes become trailing dims; quaternions stay (w, x, y, z).
    • wp.from_torch keeps strides for scalar dtypes, refuses strided inner dims for vector dtypes, and maps float64 to float64. wp.copy only checks element byte size: float64/int64 raise, int32/uint32 are reinterpreted bit for bit with no error. Convert with .float() first.
    • Default torch and Warp streams are ordered; a torch.cuda.Stream() needs wp.stream_from_torch or an explicit wait.
    • Actions go into d.ctrl (wp.copy or to_torch(d.ctrl).copy_); rebinding d.ctrl breaks graphs and views.
    • For JAX: set the XLA variables before import jax, wrap a closure with wp.jax_callable(..., graph_mode=WARP, output_dims=...), set graph_conditional explicitly, keep NWORLD fixed, unroll with lax.scan. On CPU, graph mode NONE works.
    • In WARP mode the Python body runs only on capture; graphs are cached per (call_id, buffer addresses), and every eager call has a new call_id. Hidden state in d survives between calls.
    • contrib/jax_unroll.py: wrong ../benchmark path, nconmax that is per world now, a kernel-cache wipe. custom_vmap turns per-env code into one batched call. MJX impl="warp" is the official JAX route.
