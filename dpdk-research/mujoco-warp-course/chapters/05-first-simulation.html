    Part I · Chapter 05

    Your First MJWarp Simulation (and How to See It)

    Four calls take a MuJoCo model onto the GPU, step thousands of copies of it at once, and bring one copy back so you can look at it. This chapter shows each call, what it does behind your back, how accurate the result is, and every way to turn your worlds into pictures and videos.

    Beginner About 75 min· Prerequisites: Ch 3, Ch 4

    You will learn

    • Use put_model, make_data, put_data, step, forward and get_data_into correctly.
    • Explain what put_model does: checks features, converts to float32 device arrays, adds warp-only options.
    • Know the side effects: put_data changes your host MjData; make_data leaves derived fields zero until forward.
    • Compare MJWarp with C MuJoCo and read float32 differences and chaotic divergence correctly.
    • Read and change m.opt, knowing which fields are arrays and which are Python ints.
    • See one world (frames, videos, tiles) and know what mjwarp-viewer and mjwarp-record can and cannot do.

    Before you start: recap

    • An MjModel holds constants; an MjData holds the changing state of one simulation (Ch 2 §1).
    • A rigid body has 6 DOF: position + orientation (quat), linear + angular velocity; a time step turns forces into the next state (Ch 3).
    • MuJoCo quats are (w,x,y,z); a free joint stores 7 qpos numbers but 6 qvel numbers (Ch 2 §3).
    • A Warp kernel is compiled (JIT) on its first launch and cached; wp.array.numpy() copies a device array to the host and waits for the device (Ch 4).
    • Float atomics sum in arbitrary order, so low bits can change; Ch 4 §9.

    1The four-call workflow

    You never write a special model format for MJWarp. You write ordinary MJCF, compile it with ordinary MuJoCo on the CPU, and then hand the result to MJWarp. Every MJWarp program has the same shape:

    1. Compile on the host. mjm = mujoco.MjModel.from_xml_string(xml). This is plain MuJoCo: float64, NumPy arrays, one model.
    2. Copy the model to the device. m = mjw.put_model(mjm) returns an mjw.Model: the same field names, but stored as Warp arrays on the GPU (or on the CPU device when there is no GPU).
    3. Allocate the state of many worlds. d = mjw.make_data(mjm, nworld=4096) starts every world from the model's default pose; d = mjw.put_data(mjm, mjd, nworld=4096) starts every world from an existing MjData.
    4. Step, then look. mjw.step(m, d) advances all worlds by one timestep in one call. mjw.get_data_into(mjd, mjm, d, world_id) copies one world back into a host MjData so classic MuJoCo tools (the renderer, the viewer, your own analysis) can use it.

    The picture below is the map for the whole chapter. Hover, tap or tab to each box to read what it holds. Notice that make_data and put_data take the host model mjm, not the device model m: they need the host model's sizes and, for put_data, run host MuJoCo functions on it.

    Here is the complete minimal program, which you will take apart piece by piece in this chapter. Its scene is a single ball above a floor:

    import mujoco
import numpy as np
import warp as wp
wp.config.log_level = wp.LOG_WARNING   # quiet the JIT log (Ch 4)
import mujoco_warp as mjw

XML = """
<mujoco>
  <worldbody>
    <geom type="plane" size="5 5 0.1"/>
    <body pos="0 0 1"><freejoint/><geom type="sphere" size="0.1"/></body>
  </worldbody>
</mujoco>"""
NWORLD, NSTEPS = 4096, 1000                          # on a CPU, try 8 and 100

mjm = mujoco.MjModel.from_xml_string(XML)            # 1. compile on the host
m = mjw.put_model(mjm)                                # 2. model to the device
d = mjw.make_data(mjm, nworld=NWORLD, nconmax=8, njmax=32)  # 3. state of all worlds
for _ in range(NSTEPS):
    mjw.step(m, d)                                    # 4. all worlds, one call per step
print("overflow:", "none" if not d.overflow.numpy().any() else d.overflow.numpy())
mjd = mujoco.MjData(mjm)
mjw.get_data_into(mjd, mjm, d, world_id=0)            #    look at world 0 on the host

    Why explicit nconmax and njmax?

    Contacts and constraint rows live in fixed-size buffers that are allocated once by make_data. If you leave the sizes out, make_data takes a guess from the model (_default_nconmax and _default_njmax in io.py): 48 contacts and 64 constraint rows per world for a small rigid scene without heightfields, flexes or SDF geoms. A constraint row, or efc row, is one scalar constraint the solver enforces, and a contact needs several. The guess knows nothing about how your scene will move, so this course sizes the buffers for each scene and checks d.overflow at the end. Here one sphere on a plane makes at most one contact, which needs 4 rows with the default pyramidal friction cone, so nconmax=8, njmax=32 leaves plenty of room. What the sizes mean and how to choose them is the subject of Ch 9.

    2put_model in one picture

    put_model is a customs gate between the CPU world of MuJoCo and the GPU world of MJWarp. It does three jobs, in this order:

    1. Inspect. Every feature the model uses is checked against what MJWarp implements. Unknown geom, sensor, actuator or equality types, the PGS solver, plugins and a few combinations are rejected with a NotImplementedError or ValueError before anything is copied. Some things only produce a warning (for example a friction coefficient so small that it "may cause NaN").
    2. Convert. Every array field that mjw.Model shares with MjModel is copied into a Warp array. Warp's float is 32-bit, so the float64 numbers of the host model become float32 on the device. Many fields get a leading batch dimension of size 1, which later lets you give each world its own value (Ch 10).
    3. Add. MJWarp needs things C MuJoCo does not: precomputed tree levels for parallel kinematics, launch sizes, feature flags like has_fluid that let kernels skip work, and a set of warp-only options such as the broadphase algorithm. The solver tolerance is also raised to at least 1e-6, because float32 cannot resolve float64's default of 1e-8.

    The stepper below walks through put_model in the order the 4.0.1 wheel runs it. Use it as a reading guide for mujoco_warp/_src/io.py: each frame names the line you would find there.

    Nothing here runs a kernel: put_model is pure host code plus device allocations, so it is fast and never triggers JIT compilation. The first kernel launch (the first step) is the slow one (Ch 4).

    3Option: arrays vs Python ints

    m.opt is an mjw.Option dataclass. It holds the same physics options as mjm.opt plus ten warp-only fields. The important split is not MuJoCo vs warp-only, though; it is array vs int:

    • Continuous options (timestep, gravity, wind, magnetic, density, viscosity, the tolerances, impratio_invsqrt) are Warp arrays of shape (1,). Kernels read them as opt_timestep[worldid % opt_timestep.shape[0]], so you can later replace them with an array of length nworld and give every world its own value (Ch 10). Write them in place with .fill_(v) or .assign([...]) (or wp.copy), never with a Python float. On a GPU .numpy() returns a host copy, so writing into it changes nothing on the device.
    • Discrete options (integrator, solver, iterations, ls_iterations, disableflags, broadphase, warn_overflow, ...) are plain Python ints or bools. The Python code reads them to decide which kernels to launch, and some are baked into the kernel source with wp.static. They are therefore the same for every world, and changing one after the first step can trigger a recompile (the knob board in Ch 24 lists which).

    Four things in that table deserve a second look. tolerance reads 1e-06 although the MJCF never set it: MuJoCo's default is 1e-8, and put_model clamped it (Example 5.2). Some MuJoCo option fields are missing (for example jacobian, impratio, disableactuator and the o_* override fields): put_model uses jacobian to decide m.is_sparse and turns impratio into impratio_invsqrt, so Option does not store them. And ls_parallel is a property that only raises: it was removed in 3.9.1, and the error message tells you so instead of failing silently. Finally, broadphase reads NXN because this small model has few geom pairs: put_model picks the broadphase from the filtered pair count (NXN below 250,000 pairs, otherwise a sweep-and-prune variant), so a large scene shows SAP_TILE or SAP_SEGMENTED here (Ch 15).

    Why 1e-6? float32 carries about 7 significant decimal digits: its machine epsilon is 2^{-23} \approx 1.19\times10^{-7}. A solver that stops when the improvement falls below 1e-8 asks for changes that float32 arithmetic cannot even represent, so it would run all iterations every step for nothing. The clamp keeps the stopping test meaningful.

    Pitfall: assigning a float to an array option

    m.opt.timestep = 0.005 replaces the Warp array with a Python float and kernels that expect an array break. Write into the array instead: m.opt.timestep.fill_(0.005) or m.opt.timestep.assign([0.005]). Replacing an array object with a new wp.array of the right type works, but has consequences for CUDA graphs; Ch 6 explains replace vs assign.

    Tip: change discrete options before the first step

    Set m.opt.iterations, m.opt.solver or m.opt.warn_overflow right after put_model. warn_overflow, for example, is read through wp.static in _next_time, so changing it later builds and compiles a new kernel.

    4make_data vs put_data

    Both functions return an mjw.Data with nworld worlds and take the same sizing keywords (nconmax, njmax, naconmax, nccdmax, naccdmax, njmax_nnz, nvmax). They differ in where the starting state comes from and in what they do to your host objects.

    Why does make_data seed geom_xpos at all? Because of static geoms: geoms attached to the world body (like the floor) never move, so the physics loop never recomputes their pose. The comment in io.py::make_data says this call "is the only place they are initialized". That is also why moving a static body after make_data needs care.

    Pitfall: put_data is not read-only

    If you keep a host MjData as a reference (say, to compare against later), put_data will have run kinematics on it. Usually harmless, but if you deliberately left derived fields stale, or you are checking "did my code compute xpos?", copy first: mjw.put_data(mjm, copy.copy(mjd), ...).

    Which one should I use?

    make_data for training and sweeps (start from the model's default pose, then randomize). put_data when a state exists on the host already: a settled scene, a keyframe you modified in Python, a state loaded from a log. Remember that put_data copies contacts too (Exercise 5.1).

    5step vs forward

    mjw.forward(m, d) computes every derived quantity of the current state: positions of bodies, contacts, constraint rows, forces, sensor values and the acceleration qacc. It does not change qpos, qvel or time. mjw.step(m, d) is forward followed by one integrator, which uses qacc to update qvel and qpos and then advances time. That is the same contract as C MuJoCo's mj_forward and mj_step.

    When do you call forward yourself? Whenever you have written qpos or qvel by hand and want to read something that depends on them before the next step: body positions for a reward, sensor values, a rendered frame. Example 5.3 showed the classic case: right after make_data, xpos is zero until forward runs. The same holds after reset_data (Ch 8). Two more facts from the source:

    • step and forward only enqueue kernel launches. Python returns before the GPU has finished; the first .numpy() or wp.synchronize() waits. Time your loops accordingly (Ch 4).
    • There is also step1/step2, which split a step around the point where you set ctrl; Ch 8 uses them for control loops.

    6Getting one world back: get_data_into

    mjw.get_data_into(result, mjm, d, world_id=0) fills an existing mujoco.MjData with the state of one world. It is the bridge to everything that speaks classic MuJoCo: mujoco.Renderer, the viewer, mj_* analysis functions. It is not a simple slice, for two reasons.

    Contacts are pooled. MJWarp does not give each world its own contact array. All worlds write their contacts into one shared pool of naconmax slots, and each contact records its worldid. A busy world can use more than its share; a quiet world uses none. So to rebuild one world's MjData.contact, get_data_into has to read the whole pool and keep the entries whose worldid matches (Ch 9 owns the pool and its sizing; here you only need the picture).

    Constraint rows can be out of order. C MuJoCo stores constraint rows as equality, friction, limit, then contact rows, with each contact's rows contiguous. On the GPU, rows are reserved by atomic counters, so contact rows may interleave. How many rows a contact takes depends on its condim (contact dimension: 1 is the normal force only, 3 adds friction in two tangent directions) and on the friction cone: with MuJoCo's default pyramidal cone a condim-3 contact uses 2 x (3 - 1) = 4 rows. get_data_into reorders them ("mujoco expects contiguous efc ordering for contacts; this ordering is not guaranteed with mujoco warp, we enforce order here").

    On the CPU device a .numpy() is little more than a memory copy, and still get_data_into is a couple of hundred times slower than reading one batched array. On a GPU every one of its copies is a separate transfer across PCIe (the bus between CPU and GPU) plus a synchronization that stalls the queue of launched kernels, and d.qpos.numpy()[world_id] copies all 4096 worlds to keep one. Run Example 5.5 on Colab to see your own numbers.

    Pitfall: get_data_into in a training loop

    It is meant for looking at a world: a video, a debug print, a comparison with C MuJoCo. In a loop that runs every step it destroys GPU throughput. Read the batched arrays you need (d.qpos.numpy(), or better, keep them on the device and use them from a kernel or from PyTorch, Ch 28).

    7Accuracy: float32, chaos, and the clock

    MJWarp computes in float32; C MuJoCo computes in float64. So how close are they? Example 5.6 runs eight identical worlds and C MuJoCo side by side for 60 steps of the PLAYGROUND scene (a ball and a box dropping on a floor, plus a swinging arm), then copies world 2 back.

    Positions agree to about 7e-7, which is a few float32 rounding steps at values near 1. Velocities differ more (3e-5) because contacts just started: the solver's stopping tolerance is now 1e-6, and contact forces are where small differences show first. The contact and constraint counts match exactly. All eight worlds are bit-identical to each other on this run (spread 0), because they started identical; on a GPU, atomic additions in arbitrary order can make identical worlds differ in their last bits (Ch 22).

    Recall from Ch 4

    Float atomics sum in arbitrary order, so low bits can change; Ch 4 §9. That is why identical GPU worlds can drift apart in their last digits while identical CPU worlds here stayed bit-identical.

    Chaos: when tiny differences stop being tiny

    For the falling ball, float32 and float64 stay around 1e-6 (about 1e-7 after 100 steps, about 1e-6 after 1000; Exercise 5.2) and do not grow exponentially: the motion is stable, small errors stay small. Some systems are chaotic: two starts that differ by \delta_0 separate roughly like \delta(t) \approx \delta_0\, e^{\lambda t} for some rate \lambda > 0, until the difference is as large as the motion itself. A double pendulum swinging with enough energy is the textbook example. Example 5.7 starts the double pendulum (model M2) from its horizontal keyframe in MJWarp and in C MuJoCo, plus a second C run nudged by 1e-9 rad.

    Read the chart from left to right. For the first second both curves sit at their starting level: ~1e-7 for float32 vs float64 (one rounding step) and 1e-9 for the nudged twin. Then both rise along straight lines, which on a log axis means exponential growth, with the same slope: the rate \lambda belongs to the pendulum, not to MJWarp. The float32 curve crosses 1e-2 about 3.7 s earlier only because it started about two decades higher. After about 11 s the two MJWarp and C pendulums are doing visibly different things (watch the replay), and after 15 s neither run "is right": a 1e-9 change in the start makes as much difference.

    Why the example switches to RK4

    M2 uses MuJoCo's default Euler integrator, which slowly removes energy from this undamped pendulum. With --euler the divergence grows the same way for about 7 s (MJWarp vs C passes 1e-2 at step 702), then the pendulum has lost enough energy to stop tumbling and the curve flattens; the 1e-9 twin never reaches 1e-2 within 20 s. RK4 keeps the energy, so the chaos lasts. Integrators are Ch 13's topic.

    What this means for you

    Do not expect MJWarp and C MuJoCo to produce the same trajectory for long horizons of a chaotic system (a robot tumbling, a pile of objects, a long humanoid rollout). Compare statistics instead: energy, success rates, distributions over many worlds. For short horizons and stable systems, per-step agreement around 1e-6 is expected, and that is what the auto-checked Exercise 5.2 tests.

    The clock is float32 too

    d.time is a float32 array, and the _next_time kernel adds timestep to it once per step. float32 cannot store 0.01 exactly (the nearest value is 0.009999999776...), and each addition rounds again. After 11 steps the clock reads 0.109999985.

    The last rows are the important ones. The spacing between neighbouring float32 numbers grows with their size: near 1000 it is about 6\times10^{-5}, near 8000 about 5\times10^{-4}, and above 8192 (where the million-step clock ends up) about 10^{-3}. Adding 0.01 to a clock that can only move in steps of about 0.001 rounds badly every time. Play with it below: type a number to see its two encodings, then drag the slider to add the timestep a million times.

    Tip: never test d.time == 1.0

    Count steps instead (an integer), or compare with a tolerance of half a timestep. For long episodes, reset the clock (reset_data sets time = 0, Ch 8). Most of the physics never reads time, but actuator and sensor delays (history buffers) and the clock sensor do: in models that use them, clock drift changes the result, one more reason to call reset_data on long episodes. Delays are Ch 14's topic.

    8Seeing it: two render paths

    There are two ways to turn MJWarp state into pixels, and they answer different questions.

    • Path 1: copy one world back and use MuJoCo's OpenGL renderer. get_data_into → mujoco.Renderer.update_scene(mjd) → render(). Full MuJoCo visuals and the free camera, but one world per frame, a host copy per frame, and an OpenGL context (on Colab: EGL, which the notebook's first cells set up). Use it to look at results.
    • Path 2: the MJWarp batch renderer. create_render_context once, then per frame refit_bvh → render → get_rgb. refit_bvh updates the BVH (a tree of bounding boxes that lets each ray skip most geoms) to the new poses. render ray-traces every camera of every world in one kernel launch on the device (a megakernel: one big kernel instead of many small ones), needs no OpenGL and no display, and also works on Warp's CPU device. Use it when you need many images: vision-based RL, datasets, tiles of many worlds. Ch 27 explains how it works.

    One frame

    Example 5.9 renders world 0 of PLAYGROUND after 0.5 s. It tries path 1 first and falls back to path 2 when mujoco.Renderer cannot be created. On this course's CPU verification box there is no OpenGL library, so the fallback is what produced the expected output and the images below; on Colab with the EGL cells you get a 320x240 OpenGL frame instead.

    Pitfalls of the batch renderer

    cam_res is (width, height) but output arrays are (nworld, height, width). The signature is get_rgb(rc, camera_index, rgb_out); some public docs show other keyword names. Without cam_res and render_rgb the camera's MJCF attributes decide, which can mean a 1x1 image. Run forward (or step) before rendering a state you wrote by hand, and refit_bvh before every render. The model must have at least one camera.

    A video and a tile of worlds

    A video is just a list of frames taken every render_every steps, where render_every = max(1, int(1 / (fps * timestep))) (the rule mjwarp-record uses; the max keeps it at least 1 when a timestep is longer than a frame). Because the batch renderer draws all worlds every time, you get a tiled view of many worlds for free: reshape the (nworld, H, W, 3) stack into a grid. Example 5.10 gives nine worlds nine different initial ball velocities and does both.

    The complete flag table of every CLI lives in API at a glance.

    Pitfall: the usage line in record.py is wrong

    The module docstring says mjwarp-record benchmarks/humanoid/humanoid.xml --video humanoid.mp4 --nworld 1. There is no --video flag (absl stops with an unknown-flag error) and .mp4 is not accepted. Use --output humanoid.gif (or .webp).

    Why it is GPU only

    record.py drives the rollout with cli.unroll, which runs the step once under wp.ScopedCapture() and then wraps every step in wp.ScopedStream(wp.get_stream()). On the CPU device the capture itself succeeds (there is no CUDA graph to record), but wp.get_stream() raises RuntimeError: Device cpu is not a CUDA device before the stream is ever entered. Example 5.11 therefore runs the CLI on a GPU and, on CPU, the same loop by hand.

    Two lines of that output come from inside a kernel: when the Newton linesearch (the search for a step length inside each solver iteration) hits ls_iterations in some step, the kernel sets the LS_ITERATIONS bit in d.overflow and calls wp.printf. Device prints are flushed later than Python's, which is why they appear last. It is a warning, not a crash: the step completes and the simulation goes on. Overflow bits and what to do about them are Ch 9's subject; here, notice that the course examples check d.overflow and print it.

    10Check yourself

    Quiz

    Which of these calls changes a host object you passed in?

    put_data runs mj_kinematics on your mjd (and mj_comPos ... mj_factorM when mjd.M is zero), so mjd.xpos changes (Example 5.4).

    Right after d = mjw.make_data(mjm, nworld=4), what is d.xpos.numpy()[0, 1] for a ball body that starts at z = 1?

    Derived fields stay zero until forward or step. Only a few poses (xquat, xmat, ximat, geom_xpos, geom_xmat) are seeded.

    What does mjw.forward(m, d) not update?

    forward is step without the integrator; time only moves in _next_time, at the end of the integrator.

    Why should you not call get_data_into inside an RL training loop?

    Each .numpy() waits for the device and copies a whole batched array; Example 5.5 measured ~200x the cost of one batched read even on CPU.

    You want a different timestep. Which line is correct right after put_model?

    timestep is a continuous option, a Warp array of shape (1,); write into it in place.

    You set mjm.opt.tolerance = 1e-10 before put_model. What does m.opt.tolerance.numpy() print?

    opt.tolerance = max(opt.tolerance, 1e-6), because float32 cannot resolve smaller improvements (Example 5.2).

    MJWarp and C MuJoCo diverge by 1 rad after 11 s on the double pendulum. What is the best conclusion?

    Both curves in Figure 6 grow with the same slope; only the starting error differs.

    On a CPU-only machine, which way of getting a GIF of your rollout works?

    That is the loop record.py runs in warp mode, without cli.unroll (Example 5.11).

    With the tile function of Example 5.10 and 3 columns, where does world 7 land?

    row = 7 // 3 = 2, column = 7 % 3 = 1 (both counted from 0). Try it in Figure 10.

    12Summary

    Key takeaways

    • Four calls: put_model(mjm) once, make_data(mjm, nworld) or put_data(mjm, mjd, nworld) once, step(m, d) in a loop, get_data_into(mjd, mjm, d, k) to look at world k.
    • put_model checks features (raising before allocating), converts to float32 device arrays, adds warp-only fields and options, and clamps tolerance to at least 1e-6.
    • In m.opt, continuous options are (1,) arrays (write in place, can become per-world); discrete options are Python ints, the same for all worlds, and may recompile when changed.
    • make_data leaves derived fields zero until forward; put_data copies an MjData and mutates it (kinematics on the host).
    • forward = everything but integration; time only advances in step, in float32 (0.109999985 after 11 steps of 0.01).
    • MJWarp matches C MuJoCo to ~1e-6 per step; chaotic systems amplify that like any other tiny difference, so compare statistics for long horizons.
    • get_data_into filters the pooled contacts, reorders efc rows and does ~140 host copies: for looking, never for training loops.
    • To see worlds: mujoco.Renderer on one copied world, or the batch renderer on all worlds at once (works on CPU too). mjwarp-record is GPU only and writes .gif/.webp via --output; mjwarp-viewer needs a display.

    Next, Ch 6 opens up the batched layout you have been using: why every array starts with nworld, how memory is laid out, and the difference between writing into an array and replacing it.
