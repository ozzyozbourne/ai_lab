    Part VI · Chapter 27

    Rays, Lidar and Batch Rendering for Thousands of Worlds

    A robot that learns from pixels or range scans needs observations from every parallel world, made on the GPU, without a trip through OpenGL. MJWarp has two tools for that: a ray caster (mjw.ray, mjw.rays) and a batch ray-tracing renderer (mjw.render). The renderer is accelerated by one bounding volume hierarchy that holds every geom of every world, and the ray caster uses the same hierarchy when you pass it a render context. This chapter takes both apart, line by line.

    Expert About 120 min· Prerequisites: Ch 15, Ch 24 (recommended: Ch 10)

    • The four-call render pipeline and every create_render_context option (4.0.1), as keyword arguments.

    • Decode the uint32 ARGB, depth and segmentation buffers; per-world visual randomization; Gaussian splats.
    • Camera modes (fixed, track, trackcom, targetbody) and the ordering rule for cameras you write by hand.

    Before you start: recap

    • There are two ways to see a simulation: copy one world into MjData and use MuJoCo's OpenGL renderer, or render every world on the device with the batch ray tracer (Ch 5 §8). This chapter is about the second.
    • An AABB is a cheap box around a shape; testing boxes first and shapes second is the idea behind every broadphase (Ch 15).
    • 32 lanes run in lockstep; branches serialize; contiguous reads coalesce (Ch 4 §4). Each kernel has a launch shape from the atlas (Ch 7).
    • A CUDA graph records launches once and replays them; conditional nodes loop on device (Ch 7 §10, Ch 24).
    • A Model field whose first axis is per-world is read at worldid % shape[0]; put_model(batch_sizes=...) makes room for per-world values (Ch 10 §2).
    • The rangefinder sensor calls rays as a black box (Ch 14). Here we open the box.

    1One ray, then many: mjw.ray and mjw.rays

    A ray is an origin \mathbf p and a direction \mathbf v; its points are \mathbf p + t\,\mathbf v for t \ge 0. Casting a ray means finding the smallest t at which it meets a geom. MJWarp returns three things per ray:

    • dist: that smallest t, or -1 when nothing is hit. It is a ray parameter: the primitive tests solve for t in units of |\mathbf v| (for example ray_sphere solves a t^2 + 2bt + c = 0 with a = \mathbf v\cdot\mathbf v). Pass unit directions: dist is then in metres. In the 4.0.1 wheel the rc=None mesh and heightfield tests also assume a unit vec (_orthogonal_basis(vec) is not normalized), so a non-unit vec can miss meshes there while the rc path still hits. The dev tree (8f5b9f1) normalizes first.
    • geomid: the geom that was hit, or -1.
    • normal: the surface normal at the hit, in world coordinates.

    The public API has two functions in mujoco_warp/_src/ray.py:

    mjw.ray(m, d, pnt, vec, geomgroup=None, flg_static=True, bodyexclude=-1, rc=None)
    # pnt, vec: wp.array2d[vec3] of shape (1, 1) or (nworld, 1)  -> returns (dist, geomid, normal), each (nworld, 1)

mjw.rays(m, d, pnt, vec, geomgroup, flg_static, bodyexclude, dist, geomid, normal, rc=None)
    # pnt, vec: (1, nray) or (nworld, nray); bodyexclude: wp.array[int] of shape (nray,)
    # dist, geomid, normal: preallocated outputs of shape (nworld, nray), written in place

    ray is a convenience wrapper: it checks the shapes, allocates three (nworld, 1) outputs, fills a one-element bodyexclude array and calls rays. Because it allocates on every call it is fine for a script, not for a training loop; there you preallocate and call rays. The first axis of pnt/vec may be 1: the kernels read pnt[worldid % pnt.shape[0], rayid], the same round-robin rule as batched Model fields. Rays read d.geom_xpos and d.geom_xmat, so run kinematics, forward or step first.

    What one ray costs without help: the tiled brute-force kernel

    Without a render context (rc=None) rays runs wp.launch_tiled(_ray, dim=(nworld, nray), block_dim=m.block_dim.ray) (64 by default). That is a tiled launch: every (world, ray) pair gets a block of 64 threads. Thread tid of the block tests geoms tid, tid + 64, tid + 128, ... (a stride loop), and after each pass the block reduces its 64 distances with wp.tile_argmin and keeps the running minimum. Misses count as MJ_MAXVAL, so they never win. The cost per ray is O(\text{ngeom}): fine for ten geoms, wasteful for a thousand.

    One ray, one block: stride over the geoms, reduce with tile_argmin

    ray.py::_rayIllustrative: 4 lanes (real 64)
    worldid, rayid, tid = wp.tid()
num_threads = wp.block_dim()
min_dist = MJ_MAXVAL; min_geomid = -1
for geomid in range(tid, upper, num_threads):
    dist = _ray_geom_mesh(..., geomid)
    if dist < 0: dist = MJ_MAXVAL   # miss
    tile_dist = wp.tile(dist)
    i = wp.tile_argmin(tile_dist)
    if tile_dist[i] < min_dist: keep it
dist_out[worldid, rayid] = min_dist or -1

    Inside the loop, _ray_geom_mesh first asks _ray_eliminate whether the geom may be hit at all (§2), then dispatches on the geom type to an analytic intersection. Each one maps the ray into the geom's local frame with _ray_map (R^\top(\mathbf p - \mathbf x), R^\top \mathbf v) and solves a small problem there:

Without rc, 4.0.1 assumes a unit vec: a non-unit one can miss (the dev tree normalizes first).

    A lidar: many rays per world

    A 2-D lidar is just nray rays in a fan. The clean GPU way is to keep everything on the device: a tiny kernel with launch shape (nworld, nray) reads the robot body's d.xpos and d.xmat and writes each world's ray origins and directions, then one rays call casts them all. bodyexclude is a per-ray array: here every ray ignores the robot's own body. Without it, every ray starts inside the robot's cylinder and reports the exit point at 0.15 m.

    The geomgroup argument has the type vec6, which lives in mujoco_warp._src.types and is not re-exported, hence the private-API badge. Passing None works only for ray, not for rays.

    Recall from Ch 14

    The rangefinder sensor is one ray per sensor. sensor.py builds the rays from the site frames and calls ray.rays(...) without a render context (the code carries TODO(team): use BVH for high-resolution camera rangefinders). Everything in this section applies to it.

    2What a ray may hit: _ray_eliminate

    Before any intersection math, ray.py::_ray_eliminate decides whether a geom is a candidate at all. It returns True (skip the geom) in this order:

    1. Body exclusion: the geom's body is the ray's bodyexclude.
    2. Invisible: no material and geom_rgba alpha is 0, or the material's mat_rgba alpha is 0.
    3. Static: flg_static=False and body_weldid[body] == 0, i.e. the geom is welded to the world (walls, floors, and any body with no joint between it and the world).
    4. Group mask: if geomgroup is all -1, nothing more is filtered. Otherwise the geom's group is clamped to 0..5 and the geom is skipped when geomgroup[group] == 0. Any non-zero value (1 or -1) includes the group.

    Pitfall: two different group filters

    The ray geomgroup mask and the render context's enabled_geom_groups are separate. When you pass rc= to rays, only geoms that are in the BVH can be hit, and the BVH holds only geoms whose group is in enabled_geom_groups (default [0, 1, 2]). A collision-only geom in group 3 is then invisible to the lidar even with geomgroup all -1. The brute-force path (rc=None) has no such limit.

    A second limit: in 4.0.1, rays(..., rc=rc) on a model with a flex (rc.bvh_nflexgeom > 0) returns wrong hits in worlds > 0, or reads past the end of enabled_geom_ids and can crash the process, because _ray_bvh uses the wrong per-world stride (§3). Use rc=None for scenes with flexes.

    3The scene BVH: one tree, every world

    A BVH (bounding volume hierarchy) is a tree of boxes. Leaves are boxes around primitives; each inner node's box encloses its children. A ray that misses a node's box cannot hit anything below it, so the traversal skips the whole subtree. With a reasonable tree a ray touches O(\log n) nodes instead of all n geoms.

    MJWarp builds one Warp BVH over the geoms of all worlds, in bvh.py::build_scene_bvh:

    1. _compute_bvh_bounds runs with dim=(nworld, bvh_ngeom) and writes one world-space AABB per enabled geom into flat arrays rc.lower, rc.upper at index worldid * (bvh_ngeom + bvh_nflexgeom) + local_id. Per-type helpers (_compute_sphere_bounds, _compute_box_bounds, _compute_capsule_bounds, _compute_plane_bounds, ...) do the work. A plane gets a flat box with half-extent 2·max(size_x, size_y) in the plane (1000 m if either size is <= 0), padded by 1 cm.
    2. The same kernel writes rc.group[i] = worldid. The groups are the worlds.
    3. wp.Bvh(rc.lower, rc.upper, groups=rc.group, constructor="sah") builds the tree with the surface area heuristic. Warp keeps each group in its own subtree.
    4. compute_bvh_group_roots (dim=nworld) stores wp.bvh_get_group_root(bvh_id, w) in rc.group_root[w]: the node where world w's subtree starts.

    A ray of world w then starts its traversal at group_root[w]: wp.bvh_query_ray(bvh_id, origin, dir, group_root[worldid]). It never visits another world's boxes, so worlds cannot see each other, and one build serves every world.

    Two levels: meshes, heightfields and flexes keep their own BVH

    The scene BVH holds one box per geom, not triangles. For a mesh the box comes from mesh_bounds_size (the largest absolute vertex coordinate per axis) rotated by the geom's pose. The triangles live in a second-level wp.Mesh built once per mesh by bvh.py::build_mesh_bvh (bvh_constructor="cubql", leaf size 2), in the mesh's own frame and shared by all worlds. When a ray enters a mesh geom's box, ray.py::ray_mesh_with_bvh transforms the ray into the mesh frame and traverses the triangle BVH. Heightfields work the same way (build_hfield_bvh), after _optimize_hfield_mesh greedily merges coplanar neighbouring cells into larger rectangles to cut the triangle count. 2-D and 3-D flexes get one box per flex in the scene BVH plus a per-flex triangle mesh with one group per world (§13).

    Version note

    The dev tree (commit 8f5b9f1) also re-frames meshes in build_mesh_bvh (_REFRAME_MIN_GAIN = 1.25: rotate the vertices back when that shrinks the summed triangle boxes by 25%). That code is not in the 4.0.1 wheel.

    Refit, not rebuild

    The context builds its BVH from a fresh mujoco.MjData after mj_forward: every world in the pose of qpos0, not your d. When geoms move, mjw.refit_bvh(m, d, rc) calls refit_scene_bvh, which re-runs _compute_bvh_bounds on the live d.geom_xpos, d.geom_xmat and m.geom_size and then rc.bvh.refit(): the tree's shape stays, only the boxes are recomputed bottom-up. It also refits flex meshes when m.nflex > 0. A refit is always correct; if objects travel far from where the tree was built, boxes overlap more and traversal gets slower, but never wrong. A rebuild means a new context.

    Traversal with a shrinking search distance

    With a context, rays launches ray.py::_ray_bvh with a plain dim=(nworld, nray): one thread per ray, no tiles. The thread asks Warp for the next box the ray enters, wp.bvh_query_next(query, bounds_nr, min_dist). The third argument is the farthest distance still of interest; it shrinks every time a closer geom is found, so boxes beyond the current best are skipped. The box index is turned back into a geom with enabled_geom_ids[bounds_nr - worldid * ngeom], and the geom is tested with the same filters and primitives as before.

    Pitfall: rays(rc=...) with a flex in the scene

    In 4.0.1 (and still at commit 8f5b9f1), rays passes ngeom = rc.bvh_ngeom, so _ray_bvh subtracts worldid * rc.bvh_ngeom. The boxes, however, are laid out with a stride of bvh_ngeom + bvh_nflexgeom per world (the render megakernel uses that stride correctly). With no flex the two agree. When the model has a flex (rc.bvh_nflexgeom > 0), rays(..., rc=rc) returns wrong hits in worlds > 0, or reads past the end of enabled_geom_ids and can crash the process. Use rc=None for scenes with flexes; rendering itself is not affected.

    Walking one world's subtree

    ray.py::_ray_bvhIllustrative 2-D scene
    worldid, rayid = wp.tid()
min_dist = MJ_MAXVAL
query = wp.bvh_query_ray(bvh_id, o, dir,
          group_root[worldid])
while wp.bvh_query_next(query, nr,
                        min_dist):
    gid = enabled_geom_ids[nr - w*ngeom]
    dist, n = _ray_geom_mesh_bvh(.., gid)
    if 0 <= dist < min_dist:
        min_dist = dist; min_geomid = gid
dist_out[w, ray] = min_dist or -1

    In this flex-free, primitive-only scene both paths agree on every ray. For mesh geoms they can differ when the ray starts inside the mesh, because the rc path culls back faces and the brute-force path does not; with a flex, use rc=None (pitfall above). On this CPU the BVH path is more than 10x faster with 192 geoms (a CPU number, not a GPU number); the gap grows with the geom count. Run the notebook on a GPU to see your own numbers. The model has no camera, so the context renders nothing (nrender 0); it is only used for its BVH. group_root holds node indices, which is why they look arbitrary.

    4The four-call render pipeline

    The batch renderer is a ray tracer: for every pixel of every active camera in every world it casts one ray (or n^2 with supersampling) into the scene BVH, finds the closest hit and shades it. It needs no OpenGL, no display and no EGL, and it runs on Warp's CPU device too (slowly). The whole API is four calls:

    render_util.py::create_render_context does a lot of one-time work, in this order:

    1. Makes a host MjData and runs mj_forward (the qpos0 pose used for the first BVH).
    2. Builds the splat BVH if splats are given (§13), then one triangle BVH per mesh and per used heightfield, and the flex BVHs.
    3. Finds a skybox texture and uploads textures as wp.Texture2D (only when use_textures or a skybox needs them).
    4. Resolves cam_active, cam_res and the three output flags per active camera; computes the output addresses (§8).
    5. znear = vis.map.znear * stat.extent, zfar = vis.map.zfar * stat.extent.
    6. Precomputes the camera-frame ray direction of every pixel (and every sub-sample) with _build_rays (§6).
    7. Records which geom types occur (geom_ray_types) and light facts (spot lights? default attenuation?) for the megakernel (§9).
    8. Allocates the output buffers, calls bvh.build_scene_bvh, and marks batched arrays (warp_util.mark_batched).

    Then the loop. render fills rc.seg_data with (-1, -1), builds the megakernel on the first call and caches it on rc._megakernel, and launches it.

    Why refit: the stale-BVH flipbook

    The renderer only finds geoms whose boxes the ray enters. Move a body and forget refit_bvh, and rays aimed at its new place enter no box. Rays aimed at the old box still test the geom, but at its new position, so they miss too. The body vanishes:

    Pitfall: the two orders that must hold every frame

    (1) step/forward before refit_bvh: the boxes are computed from d.geom_xpos. (2) refit_bvh before render. After writing qpos by hand, call mjw.forward (or mjw.kinematics followed by mjw.camlight) first, or both the poses and the boxes are stale. Changing m.geom_size per world also needs a refit: the box size comes from it.

    Pitfall: the repo's own contrib/render.py has a positional bug

    It calls mjw.create_render_context(mjm, nworld, (render_width, render_height), _RENDER_RGB.value, _RENDER_DEPTH.value, _RENDER_SEG.value, _USE_TEXTURES.value, _USE_SHADOWS.value, enabled_geom_groups=...). Counting from mjm, the 8th parameter is use_fast_math, not use_shadows. So --shadows toggles fast math and shadows stay off. Keyword arguments make this class of bug impossible.

    camera_index is not the MuJoCo camera id

    Everything in the context is indexed by the position in the active camera list. rc.cam_id_map[k] maps it back to the MuJoCo id. With cam_active=["side", "front"], get_rgb(rc, 0, ...) returns the side camera. A model without cameras gives nrender 0 and empty output buffers.

    6From pixel to ray: compute_ray

    A MuJoCo camera looks along its local -z axis, with +y up and +x to the right. The columns of d.cam_xmat[w, cam] are those three axes in world coordinates. render_util.py::compute_ray turns pixel (px, py) of a W x H image into a camera-frame direction. For a perspective camera without intrinsics:

    h = z_\text{near}\tan\tfrac{\text{fovy}}{2},\quad w = h\,\tfrac{W}{H},\quad u = \tfrac{p_x + 0.5}{W},\quad v = \tfrac{p_y + 0.5}{H}
    \mathbf d_\text{cam} = \operatorname{normalize}\big(-w + 2w\,u,\;\; h - 2h\,v,\;\; -z_\text{near}\big)

    So pixel row 0 is the top of the image, rays go through pixel centres (the +0.5), and z_\text{near} cancels after normalizing: it only fixes where the image plane is drawn. In the megakernel the world ray is origin = d.cam_xpos, dir = d.cam_xmat @ d_cam.

    • Intrinsics. If the camera has a sensor size (cam_sensorsize[1] != 0, MJCF sensorsize/focal/principal), the frustum edges come from fx, fy, cx, cy (cam_intrinsic), and the sensor is cropped to the image aspect ratio.
    • Orthographic (cam_projection == ProjectionType.ORTHOGRAPHIC): every direction is (0, 0, -1); instead each pixel gets an origin offset on a sensor that is fovy length units tall. The megakernel adds cam_xmat @ offset to the origin (only compiled in when some active camera is orthographic).
    • Precomputed rays. In 4.0.1, create_render_context always fills rc.ray with _build_rays, once per camera and sub-sample (dim=(W, H)), from the host mjm.cam_fovy etc., at rc.ray[offset + px + py*W]. Example 27.10 shows a 1024-entry buffer even with use_precomputed_rays=False. The flag decides whether the megakernel reads rc.ray (per-world FOV changes are then ignored, §12) or calls compute_ray per pixel with the per-world cam_fovy/cam_intrinsic. The newer source (commit 8f5b9f1) skips the buffer when the flag is False.

    znear, zfar and planar depth

    znear and zfar are vis.map.znear/zfar times stat.extent (Example 27.8 prints 0.0148 m and 73.87 m for its scene). The megakernel limits the search to zfar / cos(theta) along the ray, where \cos\theta = -d_{\text{cam},z}, and drops hits whose planar distance is beyond zfar. The depth it stores is planar (z-depth): the distance along the camera's optical axis, depth = dist * -d_cam.z (comment in the source: "Planar depth"). A flat wall facing the camera has one depth value everywhere, which is what most depth cameras and OpenGL depth buffers report.

    7Camera and light modes, and the ordering rule

    The renderer does not compute camera poses; it reads d.cam_xpos and d.cam_xmat. Those are written by smooth.py::camlight, which fwd_kinematics calls right after kinematics and com_pos, so it runs inside every forward and step. Its kernel _cam_local_to_global (launch dim=(nworld, ncam)) implements the MJCF mode attribute:

    cam_modePositionOrientation
    fixed (0)xpos[body] + rot(cam_pos): rigidly attached to its bodyxquat[body] * cam_quat
    track (1)xpos[body] + cam_pos0: follows the body origin, keeps its initial offsetcam_mat0: fixed in the world (does not spin with the body)
    trackcom (2)subtree_com[body] + cam_poscom0: follows the subtree centre of masscam_mat0 (fixed in the world)
    targetbody (3)like fixedlooks at xpos[cam_targetbodyid]: z = \text{normalize}(\text{cam} - \text{target}), x \perp z and world up
    targetbodycom (4)like fixedlooks at subtree_com[cam_targetbodyid]

    A target mode with no valid target falls back to fixed. Lights have the same five modes in _light_local_to_global (writing d.light_xpos, d.light_xdir); a targeted light points its direction at the target. The other light fields the renderer uses are Model fields: light_type (spot 0, directional 1, point otherwise), light_castshadow, light_active, light_cutoff (degrees), light_exponent, light_attenuation, and the ambient, diffuse and specular colours.

    The ordering rule for cameras you write by hand

    camlight recomputes d.cam_xpos/d.cam_xmat in every forward/step. A camera you set yourself (an orbit, a camera on a robot arm you control, a randomized viewpoint) must be written after step/forward and before refit_bvh/render, every frame. Written before step, it is overwritten (Example 27.14 prints the MJCF position again). The columns of cam_xmat are the camera's x, y, z axes; z points backwards (away from what the camera sees). contrib/render.py::_set_orbit_camera builds them exactly this way.

    8One thread per (world, ray): mapping and output buffers

    render.py::render launches the megakernel with dim=(d.nworld, rc.total_rays) and block_dim=m.block_dim.render (64). total_rays is the sum of W*H over the active cameras: all cameras' pixels are laid end to end in one flat range. This is layout 5 of the launch-shape atlas, the (world, ray) grid.

    The thread does not get its camera from the launch; it finds it. The kernel loops over the active cameras, subtracting each camera's pixel count until rayid falls inside one. With a handful of cameras that loop is a few integer compares.

    Thread (world 1, rayid 800) finds its pixel

    The three buffers

    Each world owns one row of each buffer. Within a row, the cameras that have that output are laid end to end; camera c starts at rgb_adr[c] (or depth_adr, seg_adr), and -1 means "this camera has no such output". Inside a camera the order is row-major, py * W + px.

    BufferShape, dtypeValue
    rc.rgb_data(nworld, sum of RGB pixels), uint320xAARRGGBB from pack_rgba_to_uint32; alpha is 255 for shaded pixels; a miss stores the packed background_color, including its alpha (255 by default).
    rc.depth_data(nworld, sum of depth pixels), float32planar depth in metres; 0 for a miss.
    rc.seg_data(nworld, max(sum of seg pixels, 1)), vec2i(objid, objtype): (geom, mjOBJ_GEOM=5), (flex, mjOBJ_FLEX=9), (-1, -1) background (re-filled at every render).

    Pitfalls when unpacking

    • cam_res is (width, height), but images come out as (nworld, height, width).
    • The get_* kernels trust the shape of your output array: they launch dim=(out.shape[0], H*W) with H, W taken from out. A wrong shape reads the wrong pixels without any error.
    • Calling get_rgb for a camera with render_rgb=False uses rgb_adr = -1 as the offset. Check rc.rgb_adr.numpy()[cam] >= 0 first (contrib/render.py::_rgb_frame does).
    • get_rgb(rc, camera_index, rgb_out) is the real signature; some docs show other keyword names. The unpack kernel's docstring says "ABGR", but the bits are 0xAARRGGBB (red in bits 16-23), as Example 27.6 shows.
    • get_depth(rc, cam, depth_scale, out) returns clamp(depth / depth_scale, 0, 1): good for a picture, lossy for metric work. Read rc.depth_data for metres.

    Version note

    In the dev tree, the rays of a camera are traversed in 8-row tiles for coherence (render_util.tile_pixel, TILE_ROWS) while results are still stored row-major, and RenderContext has any_rgb/any_seg. The 4.0.1 wheel traverses plain row-major order and has neither.

    9The specialised megakernel

    All of rendering is one kernel, generated per context by render.py::_build_megakernel(m, rc). A megakernel does the whole per-pixel pipeline (find camera, build ray, cast, shade, write) in one launch, so no intermediate image ever goes to memory. The price is code size: a kernel that handles every geom type, textures, shadows, splats and orthographic cameras uses many registers, and on a GPU registers limit how many threads run at once (occupancy). So the builder strips everything this context will never need, at compile time:

    • _make_cast_ray(rc.geom_ray_types, first_hit) builds a cast_ray with one if wp.static(int(GeomType.X) in geom_ray_types): branch per type. A scene of spheres and boxes compiles only those two intersection routines. A second variant with first_hit=True (any-hit, for shadow rays) returns as soon as anything is in range.
    • _make_compute_lighting(cast_ray_first_hit) and _make_sample_texture(geom_ray_types) are specialised the same way.
    • rc_static collects every scalar field of the context (bools, ints, floats, vec3), and the kernel tests them with wp.static(...): precomputed rays, orthographic cameras, zfar, vertex normals, backface culling, splats, skybox, supersampling, textures, specular, emission, ambient, headlight, per-light ambient, default attenuation, spot lights.
    • for light_index in range(wp.static(M_NLIGHT)) unrolls the light loop for the model's light count.
    • The kernel is declared @wp.kernel(module="unique", enable_backward=False, grid_stride=False, module_options={"fast_math": rc.use_fast_math}): its own module, no adjoint, no grid-stride loop.

    Building and compiling the kernel costs far more than launching it, so render keeps it on the context: if rc._megakernel is None: rc._megakernel = _build_megakernel(m, rc) (tested by render_test.py::test_megakernel_cached_across_renders). Consequences:

    • Make one context and reuse it. A new context means a new specialisation and, unless Warp's kernel cache already has that exact code, a compile (a few seconds on this CPU box).
    • Facts baked from the Model (number of lights, which geom types are enabled) are frozen in the kernel too. Per-world values (colours, sizes, light colours) stay live: they are kernel arguments.
    Going deeper: "Static parameters extracted for JAX FFI closure"

    The comment above rc_static explains why the context's scalars are captured in a Python dict instead of being read from rc inside the kernel: the generated kernel must be a closure over plain values so that the same render function can be wrapped by Warp's JAX FFI (wp.jax_callable, Ch 28). Arrays stay as kernel arguments; warp_util.mark_batched(rc) tags the context's per-world arrays for those wrappers.

    10Shading: Blinn-Phong, shadows, textures, skybox, supersampling

    After cast_ray returns the closest hit (ties within a relative tolerance go to the higher geom index, "like MuJoCo's GL depth test"), the megakernel shades it. The base colour is geom_rgba, or the material's mat_rgba when the geom has a material and its rgba is exactly the MuJoCo default (0.5, 0.5, 0.5, 1) (_geom_rgba), multiplied by the texture colour if there is one. Then:

    color = emission · base + base · (headlight.ambient, or 0.3 if the headlight is off and there are no lights) + Σ base · light.ambient (when use_ambient_lighting)
      + Σlights [ base · light.diffuse · max(0, n·L) + light.specular · mat_specular · max(0, n·H)shininess·128 ] · atten · visible
      + headlight: same diffuse + specular with L = -camera forward (the light shines along the camera's forward axis),  then clamp to [0, 1]
    • Lights (_make_compute_lighting): directional (L = -light_xdir), point and spot (L toward light_xpos). Attenuation 1/(a_0 + a_1 d + a_2 d^2) unless the model uses the default (1, 0, 0). A spot outside its cutoff contributes nothing; inside, it is scaled by \cos^{\text{exponent}}. H = \text{normalize}(L + V).
    • Defaults without a material: DEFAULT_MAT_SPECULAR = 0.5, shininess exponent 0.5 x MAX_SHININESS = 64, emission 0. No lights and no headlight: ambient fallback NO_LIGHT_AMBIENT_FALLBACK = 0.3.
    • Headlight (vis.headlight): an extra directional light along the camera's forward axis, never shadowed. Turn it off in MJCF with <visual><headlight active="0"/></visual>.
    • Shadows (use_shadows=True, per light castshadow): an any-hit ray from hit + 1e-4 n toward the light (up to the light, or 1e8 for directional lights). If anything is hit, visible = shadow_light_fraction (default 0.3), which scales that light's diffuse and specular.
    • Textures (use_textures): per geom type UV mapping (_texture_plane, _texture_sphere_ellipsoid, _texture_cylinder, _texture_capsule, _texture_box, _texture_hfield, _texture_mesh) into a linear-filtered wp.Texture2D; texrepeat and texuniform are honoured.
    • Skybox (render_skybox=True and a skybox texture): misses sample the cube map (sample_skybox) instead of background_color.
    • Backface culling (default on): a hit whose normal points along the ray (the camera is inside a geom) is dropped. Off: the normal is flipped and the inside is shaded two-sided.
    • Vertex normals: mesh normals are interpolated with the hit's barycentric coordinates; a vertex normal more than ~37° off the face (dot < 0.8, vertex_normal) falls back to the face normal, like mjr_uploadMesh.
    • Alpha: geoms whose effective rgba alpha is 0 are skipped (as in the ray API). Any other alpha is drawn fully opaque, with no blending (splats are the exception, see §13).

    No reflections, refraction, global illumination, fog or PBR: expect the look of simple OpenGL. For throughput, run Example 27.11 on your own GPU.

    Supersampling

    samples_per_pixel=n renders n^2 passes. At creation, _build_rays is called with an nW \times nH virtual image and the sub-pixel (sx, sy) of each pass, so the ray buffer holds total_rays * n * n directions; pass k reads them at ray_base = k * total_rays. Colours are summed in float into rc.aa_accum (not into the packed bytes, to avoid early rounding) and _aa_resolve divides by n^2 and packs. Depth and segmentation are written only by pass 0. It needs precomputed rays and at least one RGB camera (both are ValueErrors otherwise).

    11Depth and segmentation in practice

    Depth and segmentation come from the same closest hit as RGB and cost little extra. Segmentation is a pair per pixel because two kinds of objects can be hit: geoms report (geom_id, 5), flexes (flex_id, 9). A segmentation image is how you get instance masks for free, or check what a camera actually sees.

    12Visual domain randomization

    Recall from Ch 10

    A batched Model field has a leading per-world axis and is read at worldid % shape[0]; mjw.put_model(mjm, batch_sizes={"field": n}) allocates it (Ch 10 §2).

    The megakernel reads these Model fields with the worldid % shape[0] rule, so each can differ per world: geom_rgba, geom_matid, geom_size, geom_dataid, the material fields mat_rgba, mat_texid, mat_texrepeat, mat_texuniform, mat_specular, mat_shininess, mat_emission, every light field (light_type, light_active, light_castshadow, light_ambient/diffuse/specular, light_attenuation, light_cutoff, light_exponent), and cam_fovy, cam_intrinsic. Not per world: cam_projection, cam_sensorsize, geom_type. Three rules:

    1. Colours, materials and lights just work: write the batched array and render. Per-world textures: batch mat_texid and point worlds at different textures (render_test.py::test_render_per_world_mat_texid_batch_size).
    2. geom_size changes the boxes: refit_bvh after writing it.
    3. cam_fovy and cam_intrinsic need use_precomputed_rays=False, because precomputed rays were built once from the host model. The docstring says so: "When using domain randomization for camera intrinsics, set to False." Supersampling then is not available.

    Per-world skyboxes work by overwriting rc.skybox_tex_id and rc.skybox_face_width with length-nworld arrays (render_test.py::test_per_world_skybox_textures): they are read at worldid % shape[0] too. Per-world camera poses need no batching: d.cam_xpos/d.cam_xmat are already per world (mind the ordering rule of §7).

    13Flex surfaces and Gaussian splats

    Recall from Ch 23

    A flex is a deformable body made of vertices (ropes, cloth, soft solids); its vertex positions per world are d.flexvert_xpos (Ch 23).

    Flexes. A 1-D flex (rope) enters the scene BVH as one capsule per edge (flex_geom_edgeid >= 0), intersected with ray_capsule. A 2-D or 3-D flex gets one box in the scene BVH plus its own triangle mesh with one group per world (bvh.py::build_flex_bvh: _build_flex_2d_elements, _build_flex_2d_sides, _build_flex_3d_shells). refit_bvh calls refit_flex_bvh, which re-accumulates vertex normals (accumulate_flex_vertex_normals; at build time the context's deterministic flag picks the atomic-free variant, during refits the ATOMICS bit of m.opt.deterministic does, Ch 22), moves the surface points (a cloth is drawn as two faces offset by flex_radius; flex_render_smooth) and refits the mesh. Hits report (flex_id, mjOBJ_FLEX) in the seg buffer, as the cloth in Example 27.8 does.

    Gaussian splats. A Gaussian splat is a fuzzy 3-D ellipsoid: a centre, a rotation (w, x, y, z), a per-axis standard deviation, an RGB colour and an opacity. Scenes captured with 3D Gaussian Splatting (3DGS) are millions of them. MJWarp can draw them next to meshes, which is how you put a photo-real captured background behind a simulated robot.

    • Pass splat_position (n,3), splat_rotation (n,4), splat_scale (n,3), splat_rgba (n,4) together (a ValueError otherwise), plus optional splat_adr (group offsets, [0, n] by default) and splat_group_id (nworld,) (which group each world sees, 0 by default). Different worlds can see different captured scenes.
    • bvh.py::build_splat_bvh bounds each splat by the box of the ellipsoid where its response drops to SPLAT_MIN_RESPONSE / opacity (_compute_splat_bounds: radius \sqrt{-2\ln r} standard deviations), builds a grouped wp.Bvh, and stores the root of each world's group in rc.splat_group_root.
    • render.py::ray_splat maps the ray into the splat's scaled frame, takes the point of closest approach t = -\mathbf p\cdot\mathbf v / \mathbf v\cdot\mathbf v, and returns \alpha = \min(1, \text{opacity}\cdot e^{-|\boldsymbol\delta|^2/2}); splats with \alpha below 0.01 or 1/255 are skipped.
    • render.py::shade_splats composites front to back, at most _MAX_SPLAT_HITS = 32 sorted hits per BVH pass, and repeats passes until the transmittance falls below 0.005. The search stops at the geom hit distance, so solid geometry hides splats behind it. Splats are not lit: their colour is used as is.
    • Final pixel: splat_color + transmittance * (geom colour, background or skybox). Depth takes the splat distance where transmittance first drops below 0.005; seg ignores splats.
    • Edited rc.splat_* arrays? Call mjw.refit_splat_bvh(rc). refit_bvh does not touch splats.

    One ray through five splats

    render.py::shade_splatsIllustrative alphas
    T = 1.0; color = 0; depth = -1
while T > 0.005:
    hits = up to 32 nearest splats
    if no hits: break
    for i in hits (front to back):
        color += rgb[i] * alpha[i] * T
        T *= 1 - alpha[i]
        if depth < 0 and T < 0.005:
            depth = dist[i]
pixel = color + T * behind

    Walkthrough: contrib/render.py

    The repository ships a command-line renderer that is not installed by pip (the contrib/ folder is not in the wheel; clone the repo to use it). It is a compact reference for everything in this chapter:

    • _load_ply_splats(filename) reads a binary little-endian 3DGS .ply (--splat file.ply): positions x, y, z; rot_0..3 normalized; scale = exp(scale_*); opacity = sigmoid(opacity); colour clip(0.5 + SH_C0 * f_dc_*, 0, 1) with _SH_C0 = 0.28209479177387814.     • --orbit: _set_orbit_camera writes d.cam_xpos/d.cam_xmat for every frame, then render. It never steps, so camlight never overwrites the camera.
    • Remember its positional create_render_context call (§5): --shadows does not do what it says.

    14Videos, graph capture and performance

    Recall from Ch 24

    A CUDA graph records launches once and replays them with one call; Python overhead disappears. Warm up (JIT) before capturing, and on CUDA < 12.4 set m.opt.graph_conditional = False first (Ch 24).

    refit_bvh, render and the get_* unpacks are plain Warp launches (plus a fill_), so they can be captured like step (render_test.py::test_render_graph_capture checks that the captured render gives identical output). Two things must happen before capture: the step kernels must be compiled and the megakernel must exist on rc._megakernel, so call everything once eagerly. Example 27.11 captures a physics graph and a render graph and replays them per video frame.

    15Check yourself

    Quiz

    You create a context with cam_res=(64, 48) and 8 worlds. What shape must the array passed to get_rgb have?

    cam_res is (W, H); outputs are (nworld, H, W). The unpack kernel takes H and W from your array, so a transposed shape silently scrambles the image.

    The model has cameras front (id 0) and side (id 1). You pass cam_active=["side"]. Which call returns the side camera?

    camera_index is the position in the active list; rc.cam_id_map = [1] maps it back to the MuJoCo id.

    You write new qpos into every world and call mjw.forward, then mjw.render. Some objects are missing from the images. Why?

    Example 27.7: 16 sphere pixels, 0 after moving without refit, 18 after refit_bvh.

    A collision mesh in geom group 3 must be seen by a lidar that uses rays(..., rc=rc) with geomgroup all -1. The context used default options. Is it hit?

    Create the context with enabled_geom_groups=[0, 1, 2, 3], or cast without rc.

    A camera looks straight at a flat wall 3 m away. What does rc.depth_data hold for a pixel near the image corner?

    depth = dist * -d_cam.z. Example 27.8: corner ray 2.55 m long, depth 2.0 m.

    You batch cam_fovy per world but every world renders with the same field of view. What fixes it?

    Precomputed rays were built once from the host mjm.cam_fovy. Dynamic rays call compute_ray with cam_fovy[worldid % shape[0]]: Example 27.10 goes from [52, 52, 52] to [256, 52, 12] sphere pixels.

    You set d.cam_xpos / d.cam_xmat for an orbit camera, then call step, refit_bvh, render. The image shows the MJCF view. Why?

    The ordering rule. Example 27.14 prints the MJCF position after a write that came before step.

    mjw.ray with vec = (0, 0, -2) hits a floor 1 m below the origin. What is dist?

    The point is pnt + t * vec; with |vec| = 2 the floor is at t = 0.5. Use unit directions to get metres. This holds for planes and the other primitives; for meshes and heightfields the 4.0.1 rc=None path also needs a unit vec, or the ray can miss.

    Why does MJWarp generate a new megakernel per render context?

    Geom types, lights, flags and splats become compile-time facts. Changing them means a new context and a compile.

    With splat_adr=[0, 100, 300] and splat_group_id=[1, 0, 1], which splats does world 2 see?

    Group k is [splat_adr[k], splat_adr[k+1]); world 2 uses group splat_group_id[2] = 1.

    Someone runs python contrib/render.py scene.xml --shadows and sees no shadows. Why?

    Count from mjm: the 8th positional parameter is use_fast_math. Always use keyword arguments.

def min_range(m, d, robot, nray=NRAY, rc=None):
    """Smallest lidar range per world, rays in the horizontal plane at the robot origin."""
    ang = 2 * np.pi * np.arange(nray) / nray
    origin = d.xpos.numpy()[:, robot]
    pnt = wp.array(np.repeat(origin[:, None], nray, 1), dtype=wp.vec3)
    vec = wp.array(np.tile(np.stack([np.cos(ang), np.sin(ang), 0 * ang], 1), (d.nworld, 1, 1)),
                   dtype=wp.vec3)
    dist = wp.zeros((d.nworld, nray), dtype=float)
    gid = wp.zeros((d.nworld, nray), dtype=int)
    nrm = wp.zeros((d.nworld, nray), dtype=wp.vec3)
    mjw.rays(m, d, pnt, vec, vec6(-1, -1, -1, -1, -1, -1), True,
             wp.full(nray, robot, dtype=int), dist, gid, nrm, rc=rc)
    r = dist.numpy()
    return np.where(r < 0, np.inf, r).min(1)


def analytic(xy):
    wall = 1.95 - np.abs(xy).max(1)
    pillar = np.linalg.norm(xy - [1.0, 1.0], axis=1) - 0.2
    return np.minimum(wall, pillar)


mjm = mujoco.MjModel.from_xml_string(ROOM)
m = mjw.put_model(mjm)
d = mjw.make_data(mjm, nworld=NWORLD, nconmax=8, njmax=32)
q = np.tile(mjm.qpos0, (NWORLD, 1)); q[:, :2] = XY
d.qpos.assign(q.astype(np.float32))
mjw.kinematics(m, d)
robot = mujoco.mj_name2id(mjm, mujoco.mjtObj.mjOBJ_BODY, "robot")
got, want = min_range(m, d, robot), analytic(XY)
print("lidar :", got.round(4))
print("exact :", want.round(4))
assert np.allclose(got, want, atol=1e-3), (got, want)
rc = mjw.create_render_context(mjm, nworld=NWORLD)
mjw.refit_bvh(m, d, rc)
assert np.allclose(min_range(m, d, robot, rc=rc), got, atol=1e-6)
print("min_range matches the geometry in all", NWORLD, "worlds (with and without the BVH)")

    Show a solution

    Verified on CPU (12 frames, 32x32, frames change by ~5-11 grey levels on average between steps of the orbit).

    import mujoco
import numpy as np
import warp as wp
wp.config.log_level = wp.LOG_WARNING
import mujoco_warp as mjw

RENDER_SCENE = """
<mujoco model="render_scene">
  <option timestep="0.01666"/>
  <worldbody>
    <light name="top" pos="0 0 2" dir="0 0 -1" directional="true"/>
    <camera name="camera" pos="0 2 0" quat="0 0 1 1"/>
    <geom name="floor" type="plane" pos="0 0 -.5" size="2 2 .1" rgba=".9 .9 .9 1"/>
    <body name="box_and_sphere" euler="0 0 -30">
      <joint name="swing" type="hinge" axis="1 -1 0" pos="-.2 -.2 -.2"/>
      <geom name="red_box" type="box" size=".2 .2 .2" rgba="1 0 0 1"/>
      <geom name="green_sphere" pos="-.2 -.2 -.2" size=".1" rgba="0 1 0 1"/>
    </body>
  </worldbody>
</mujoco>
"""


def look_at(eye, target, up=(0.0, 0.0, 1.0)):
    """cam_xmat columns = camera x, y, z axes in world; the camera looks along -z."""
    fwd = np.asarray(target, float) - eye
    fwd /= np.linalg.norm(fwd)
    x = np.cross(fwd, up); x /= np.linalg.norm(x)
    y = np.cross(-fwd, x)
    return np.column_stack([x, y, -fwd])


NWORLD, W, H, NFRAME = 2, 32, 32, 12
mjm = mujoco.MjModel.from_xml_string(RENDER_SCENE)
m = mjw.put_model(mjm)
d = mjw.make_data(mjm, nworld=NWORLD)
rc = mjw.create_render_context(mjm, nworld=NWORLD, cam_res=(W, H), render_rgb=True,
                               render_depth=False, render_seg=False)
rgb = wp.zeros((NWORLD, H, W), dtype=wp.vec3)
frames = []
mjw.forward(m, d)
for f in range(NFRAME):
    mjw.step(m, d)                                     # 1. physics (camlight runs inside)
    a = 2 * np.pi * f / NFRAME                         # 2. THEN overwrite the camera
    eye = np.array([2 * np.sin(a), 2 * np.cos(a), 0.6])
    pos, mat = d.cam_xpos.numpy(), d.cam_xmat.numpy()
    pos[:, 0], mat[:, 0] = eye, look_at(eye, [0, 0, -0.2])
    d.cam_xpos.assign(pos)
    d.cam_xmat.assign(mat)
    mjw.refit_bvh(m, d, rc)                            # 3. refit + render read the new camera
    mjw.render(m, d, rc)
    mjw.get_rgb(rc, 0, rgb)
    frames.append((np.clip(rgb.numpy()[0], 0, 1) * 255).astype(np.uint8))
diffs = [np.abs(frames[i + 1].astype(int) - frames[i]).mean() for i in range(NFRAME - 1)]
print(len(frames), "orbit frames; mean change between frames:", np.round(diffs, 1))

    17Summary

    Key takeaways

    • mjw.ray (one ray per world, allocates) and mjw.rays (many rays, preallocated outputs) return dist (the ray parameter; -1 = miss), geomid and normal per (world, ray).
    • _ray_eliminate filters by bodyexclude, zero alpha, flg_static (welded to world) and the geomgroup mask (all -1 = off, 0 = exclude).
    • Without rc: a tiled kernel, 64 lanes per ray, tile_argmin over all geoms. With rc: one thread per ray walks its world's subtree of one grouped BVH from group_root[worldid].
    • The BVH is built at qpos0: always step/forward → refit_bvh → render. Without refit, moved objects vanish.
    • Pass every create_render_context option as a keyword. Groups 3+ are invisible by default; camera_index counts active cameras; cam_res is (W, H), images are (H, W).
    • One megakernel, dim=(nworld, total_rays), specialised with wp.static and cached on rc._megakernel; changing a flag means a new context.
    • Blinn-Phong with optional shadows (0.3 of the light by default), textures, skybox, culling, vertex normals and n^2 supersampling. Depth is planar; seg is (objid, objtype); RGB is packed 0xAARRGGBB.
    • Visual DR: batch the Model fields; per-world FOV needs use_precomputed_rays=False. Splats: per-world sets via splat_group_id, front-to-back compositing, refit_splat_bvh after edits.
    • Cameras come from camlight in every forward; hand-written cameras go after step, before refit_bvh / render, every frame. Refit and render can be captured in a CUDA graph.
