Chapter 7

Branches, Batches and Existence

A game has a million entities and half of them are dead. The update loop visits every one, loads its alive flag, and jumps over the dead ones. On this machine that loop takes about 5.5 ns per entity. Move the living entities into a table of their own, so that being in the table is being alive, and the same update takes about 0.36 ns, roughly 15× faster. Nothing about the arithmetic changed. What changed is that the loop stopped asking a question for every element, and stopped paying for the answer.

This chapter is about questions a loop asks: is this one alive, which kind is this, is this byte a letter. Each question is a branch, and each branch has a price that depends on how predictable the answers are. We will measure that price properly, in a benchmark built so the optimizer cannot hide it, and then look at three ways to stop paying it: answer the question once for a whole batch, make the answer part of where the data lives, or look the answer up instead of computing it.

Where there is one, there are many

Mike Acton's CppCon 2014 keynote put it as a rule of thumb: “Where there is one, there are many. Try looking on the time axis.”[1] Noel Llopis made the same point five years earlier[2]. A function that takes one particle is a lie about the program, which has a thousand and will re-do every piece of setup on each call: load the constants, check the mode, look up the vtable, ask the predictor to guess the same branch again.

Batching means writing the function for the collection instead. The per-call work is paid once per batch and the per-item work runs in a tight loop that the compiler can unroll, vectorize and schedule. Two real systems show how far this goes.

  • TigerBeetle, a financial database written in Zig, only accepts batches: “up to 8,190 transfers per query”. The cost of consensus and replication “is paid only once per batch”, and on the CPU side “executing a batch of transfers is just one tight CPU loop!”[3] Under light load the batches shrink on their own, trading throughput for latency. What small batches cost TigerBeetle's storage, and the fix that followed, is one of Chapter 12's case studies[4].
  • MonetDB/X100 (Boncz, Zukowski and Nes, CIDR 2005) is the database version. Instead of passing one tuple at a time between query operators, X100 passes “vectors” of about 1,000 values. The paper's Figure 10 runs TPC-H Query 1 at vector sizes from 1 to 4M. At size 1, “interpretation overhead also hits MonetDB/X100 strongly”; “with increasing vector size, the execution time quickly improves”; the best size “seems to be 1000, but all values between 128 and 8K actually work well”; and “performance starts to deteriorate when intermediate results do not fit in the cache anymore”. At 4M tuples per vector it behaves like the older column-at-a-time engine[6]. DuckDB, its descendant, fixes its vector size at 2,048 at compile time[7].

The X100 curve has a shape worth memorising, because every batch-size experiment has it. Too small and you pay the per-call overhead on every item. Big enough and that overhead vanishes into the noise. Too big and the batch no longer fits in cache, so every stage writes its intermediate results out to a slower level and the next stage reads them back. The figure below draws the first half of that argument.

A batch-size sweep

Our version of the X100 experiment is a three-stage pipeline: generate a value from an index, mix its bits, multiply by a constant, then sum. Each stage is called through a dynamic interface (a trait object in Rust, a function pointer in Zig, a procedure value in Odin), like an operator in a query interpreter. The pipeline pushes 4M items through in batches of size B, so per batch it makes three indirect calls and keeps two buffers of B × 8 bytes alive. The result is the same for every B, and the program asserts it.

/// Push `total` items through gen -> mix -> scale -> sum, `batch` at a time.
/// Per batch: three dynamic calls and a sum. Working set: two buffers of `batch` u64.
#[inline(never)]
fn run_pipeline(ops: &[&dyn Op], total: usize, batch: usize, a: &mut [u64], b: &mut [u64]) -> u64 {
    let mut sum = 0u64;
    let mut base = 0;
    while base < total {
        let len = batch.min(total - base);
        let (a, b) = (&mut a[..len], &mut b[..len]);
        ops[0].run(base as u64, &[], a);
        ops[1].run(base as u64, a, b);
        ops[2].run(base as u64, b, a);
        sum = a.iter().fold(sum, |s, &x| s.wrapping_add(x));
        base += len;
    }
    sum
}
const Stage = struct {
    k: u64,
    runFn: *const fn (k: u64, base: u64, inp: []const u64, out: []u64) void,
};

/// Push `total` items through gen -> mix -> scale -> sum, `batch` at a time.
/// Per batch: three indirect calls and a sum. Working set: two buffers of `batch` u64.
noinline fn runPipeline(c: PipeCtx) u64 {
    var sum: u64 = 0;
    var base: usize = 0;
    const s = c.stages;
    while (base < c.total) {
        const len = @min(c.batch, c.total - base);
        const a = c.a[0..len];
        const b = c.b[0..len];
        s[0].runFn(s[0].k, base, &.{}, a);
        s[1].runFn(s[1].k, base, a, b);
        s[2].runFn(s[2].k, base, b, a);
        for (a) |x| sum +%= x;
        base += len;
    }
    return sum;
}
Stage :: struct {
	k:   u64,
	run: proc(k, base: u64, inp, out: []u64),
}

// Push `total` items through gen -> mix -> scale -> sum, `batch` at a time.
// Per batch: three indirect calls and a sum. Working set: two buffers of `batch` u64.
run_pipeline :: #force_no_inline proc(c: Pipe_Ctx) -> u64 {
	sum: u64
	s := c.stages
	for base := 0; base < c.total; base += c.batch {
		n := min(c.batch, c.total - base)
		a, b := c.a[:n], c.b[:n]
		s[0].run(s[0].k, u64(base), nil, a)
		s[1].run(s[1].k, u64(base), a, b)
		s[2].run(s[2].k, u64(base), b, a)
		for x in a {
			sum += x
		}
	}
	return sum
}

Rust's &dyn Op is a fat pointer (data + vtable); Zig and Odin store a plain function pointer next to its parameter. All three compile to one indirect call per stage per batch (the Rust binary has exactly three call *0x18(%rax) in run_pipeline).

The working set is 16 bytes per item of batch size. Where should the per-item time start rising again on this machine (L1d 48 KiB, L2 1.25 MiB, and an L3 of 54 MiB shared with the host, of which Chapter 2 measured only a few MiB as usable)?

Not at L1. The stages stream through their buffers sequentially, so the prefetcher keeps L2 almost as good as L1 here: the curve stays flat from batch 64 (1 KiB) to 64K (1 MiB). It rises once the two buffers outgrow L2, at 256K items (4 MiB), which is already about all the L3 we get, and climbs further as they head for DRAM.

In Rust the flat region is several times cheaper than batch 1, and the right-hand end gives most of it back: batch 4M is several times slower than batch 1K. The language does not matter much. All three show the drop, the plateau and the rise, with Zig and Odin a little above Rust on the plateau, plausibly because Zig's plain loops are scalar (its loop vectorizer is off: see Chapter 4); we did not check the assembly. The lesson is DuckDB's: pick a batch that keeps everything one stage hands to the next in L1 or L2, and stop there.

What a branch costs, measured properly

Chapter 2 gave the price of a mispredicted branch: Agner Fog's “approximately 15 - 25 clock cycles, depending on the processor”, roughly the length of the pipeline[13]. A correctly predicted branch is nearly free, “typically 0 - 2 clock cycles”. So a branch costs whatever its mispredictions cost, and that depends entirely on the data.

The famous demonstration is Stack Overflow's most-voted question: a loop that adds up the elements >= 128 ran about six times faster once the array was sorted[14]. It often fails to reproduce, because modern compilers turn that loop into a conditional move or vector code. Our program includes it, so you can see it fail:

/// The famous sorted-array loop: sum the elements below `t`. No store depends on the
/// condition, so the optimizer is free to make it branchless (and vectorize it).
#[inline(never)]
fn sum_if(input: &[u32], t: u32) -> u64 {
    let mut s = 0u64;
    for &x in input {
        if x < t {
            s += x as u64;
        }
    }
    s
}
/// The famous sorted-array loop: sum the elements below `t`. No store depends on the
/// condition, so the optimizer is free to make it branchless.
noinline fn sumIf(input: []const u32, t: u32) u64 {
    var s: u64 = 0;
    for (input) |x| {
        if (x < t) s += x;
    }
    return s;
}
// The famous sorted-array loop: sum the elements below `t`. No store depends on the
// condition, so the optimizer is free to make it branchless.
sum_if :: #force_no_inline proc(input: []u32, t: u32) -> u64 {
	s: u64
	for x in input {
		if x < t {
			s += u64(x)
		}
	}
	return s
}

In all three languages the sorted and random versions take the same time, about 0.3 ns per element. The disassembly shows why: there is no branch left to predict. Rust and Zig emit cmp + cmovae (select zero or the value, then add), unrolled; Odin, which targets x86-64-v2 by default, goes further and vectorizes it with SSE4 pmaxud/pcmpeqd/pandn masks. The if in the source was never a jump in the binary.

A branch the optimizer cannot remove

To measure a real branch we need a loop where the condition controls a side effect that cannot be done speculatively. A filter does it: copy each element that passes into an output buffer, and advance the output cursor only when it passed. Stream compaction like this is everywhere (building a list of visible objects, a selection vector in a database, the alive list in the next section). The branchy version stores conditionally, so the compiler cannot convert it into arithmetic without inventing a store the program did not ask for. The branchless version always stores and advances the cursor by 0 or 1; if the element failed, the next store overwrites it. This needs an output buffer as long as the input, a cost the branchy version does not have.

/// Branchy: push `x` into the output only when it passes. The store itself is conditional,
/// so the compiler cannot turn this into a conditional move: it must keep the jump.
#[inline(never)]
fn filter_branchy(input: &[u32], t: u32, out: &mut [u32]) -> usize {
    let mut n = 0;
    for &x in input {
        if x < t {
            out[n] = x;
            n += 1;
        }
    }
    n
}

/// Branchless: always write, then advance the cursor by 0 or 1. `out` must be as long as
/// `input`. `select_unpredictable` asks for a conditional move instead of a jump.
#[inline(never)]
fn filter_branchless(input: &[u32], t: u32, out: &mut [u32]) -> usize {
    let mut n = 0;
    for &x in input {
        out[n] = x;
        n = std::hint::select_unpredictable(x < t, n + 1, n);
    }
    n
}
/// Branchy: push `x` into the output only when it passes. The store itself is conditional,
/// so the compiler cannot turn this into a conditional move: it must keep the jump.
noinline fn filterBranchy(input: []const u32, t: u32, out: []u32) usize {
    var n: usize = 0;
    for (input) |x| {
        if (x < t) {
            out[n] = x;
            n += 1;
        }
    }
    return n;
}

/// Branchless: always write, then advance the cursor by 0 or 1. `out` must be as long as
/// `input`. `@intFromBool` turns the comparison into a number: no jump to predict.
noinline fn filterBranchless(input: []const u32, t: u32, out: []u32) usize {
    var n: usize = 0;
    for (input) |x| {
        out[n] = x;
        n += @intFromBool(x < t);
    }
    return n;
}
// Branchy: push `x` into the output only when it passes. The store itself is conditional,
// so the compiler cannot turn this into a conditional move: it must keep the jump.
filter_branchy :: #force_no_inline proc(input: []u32, t: u32, out: []u32) -> int {
	n := 0
	for x in input {
		if x < t {
			out[n] = x
			n += 1
		}
	}
	return n
}

// Branchless: always write, then advance the cursor by 0 or 1. `out` must be as long as
// `input`. Converting the bool to an int gives a number, not a jump.
filter_branchless :: #force_no_inline proc(input: []u32, t: u32, out: []u32) -> int {
	n := 0
	for x in input {
		out[n] = x
		n += int(x < t)
	}
	return n
}

Zig's @intFromBool returns a u1 and Odin converts with int(x < t); Rust could write n += (x < t) as usize, and we use std::hint::select_unpredictable because it states the intent.

select_unpredictable(condition, true_val, false_val) is “functionally equivalent to if b { true_val } else { false_val }” but tells the optimizer the condition is hard to predict. The lowering “is not guaranteed (on any platform)” and “might decrease performance if condition is well-predictable”[15]. Here LLVM did something better than cmov: for n + 1 versus n it emitted cmp + adc $0x0, adding the carry flag straight into the cursor.

We run both filters over 64K values (256 KiB in, the same out: L2-resident, so memory is not the bottleneck) in three families of input:

  • random, keep p%: values uniform in 0..100, keep x < p, for p = 0, 10, …, 100. At 0% and 100% the branch always goes the same way; at 50% it is a coin flip.
  • sorted: the same values at 50%, sorted, so the branch flips once.
  • period k: a random pattern of k keep/drop decisions, repeated, keeping half. A predictor that remembers enough history learns short periods and loses long ones.

How the predictor guesses

Before the numbers, a model. The simplest predictor that works is a 2-bit saturating counter: four states, strongly not-taken to strongly taken. Predict “taken” in the upper two states; move one step towards whatever actually happened. Two states per direction means one surprise does not flip the prediction, which is what makes a loop branch (taken, taken, …, not taken once at the end) cheap. Real predictors are far better at patterns: TAGE-style designs keep several tables of such counters, indexed by longer and longer histories of recent branch outcomes. But no history helps with a coin flip. Algorithmica's measurements show the price on a Zen 2 core: about 14 cycles per element for a 50/50 branch, against a little over 4 once the data is sorted[11]. The figure below runs the counter.

Random values, keep 50%. What fraction of the branches will the 2-bit counter mispredict? And with “alternating” input (keep, drop, keep, drop…)?

About half on random input: any rule is right half the time against a fair coin. On alternating input the single counter swings between the two weak states, and depending on where it starts it can be wrong on every branch. Switch to “counter per history”, which picks a counter by the last two outcomes, and it learns the pattern after a few steps and stops missing. That is the period-k experiment in miniature.

The predictability sweep

Sketch both curves (time per element against the fraction kept, 0 to 100%) before you look. Where do they cross?

The branchy filter traces an upside-down U: cheap at the ends, worst at 50%, where every other element mispredicts. The branchless filter is flat, because it does the same work whatever the data. They cross very close to the ends. Branchy wins only when almost nothing is kept, because it then skips almost every store. At 100% kept it stores every element too, so it can at best tie: in our runs branchless was still ahead in Rust and Odin, and branchy slightly ahead in Zig. Already at 10% and 90% branchless wins in all three. That is far narrower than Algorithmica's rule of thumb that branchy code wins above ~75% predictability[12], because our branchless loop is so cheap.

The curves are as clean as benchmarks get. At 50% the branchy filter takes about 4 ns per element in Rust and 3.4 ns in Zig; the branchless filter is about 8× faster. Sort the input and the branchy filter falls to about 0.46 ns, slightly faster than branchless, because a predicted branch skips the store for the dropped half:

Worked example: reading the penalty off the curve

The sweep lets us estimate the mispredict penalty without performance counters, which this machine does not expose. In Rust at 50%, branchy costs 4.2 ns and branchless 0.52 ns per element. Both do roughly the same useful work, so the difference, about 3.5 ns, is mostly the mispredictions. Any predictor against a fair coin mispredicts about half the elements: 3.5 ns / 0.5 ≈ 7.0 ns per mispredict. If the core runs near its 2.6 GHz nominal clock, that is about 18 cycles. We cannot read the actual clock here, so take it as a range, but it sits inside Agner Fog's 15–25 cycles.

Now use the penalty to predict another point. Take the branchless cost, about 0.5 ns, as the base. At 10% kept, a perfect “always guess the common case” predictor misses 10% of the time: 0.5 + 0.10 × 7.0 ≈ 1.20 ns. For the 2-bit counter on independent random outcomes, the four states form a small Markov chain whose steady state gives a miss rate of p(1 − p) / (p2 + (1 − p)2): 11.0% at p = 0.1 (a million-step simulation agrees to three decimals), so 0.5 + 0.11 × 7.0 ≈ 1.27 ns. We measured 1.31 ns: a few percent above the 2-bit model and the oracle. That is what we should expect. Random outcomes carry no pattern for a big predictor's history to find, so it can do no better than guess the majority, and a 2-bit counter already gets within one point of that; the small excess is the kind of thing aliasing between branches in a real predictor adds. Sanity checks like this are how you know a benchmark is measuring what you think.

Patterns the predictor can learn

The period sweep is the best evidence that modern predictors are not 2-bit counters: a pattern of 2,048 random-looking decisions, repeated, is predicted almost perfectly. Then, between 2K and 8K, the history runs out and the branchy filter climbs back to its coin-flip cost. Zig's binary, whose branchy loop is unrolled four times, learns longer periods; we did not find out why. The practical point is the other one: you cannot rely on the predictor's history size, which changes between CPU generations.

The benchmark that measured nothing. Our first Zig version called the read-only sumIf 16 times on one slice and LLVM computed it once; the repetition loops below hide the input on every pass (Chapter 12 has the full story).

/// One timed run: `reps` passes of filter `f` over the same input.
fn repeated(comptime f: FilterFn) fn (FilterCtx) usize {
    return struct {
        fn run(c: FilterCtx) usize {
            var total: usize = 0;
            for (0..c.reps) |_| {
                std.mem.doNotOptimizeAway(c.input.ptr); // memory barrier: each pass really runs
                total += f(c.input, c.t, c.out);
            }
            return total;
        }
    }.run;
}

Existence-based processing

So far the branch was a property of the data that we could only work around. Richard Fabian's book takes a stronger position: most of these branches should not exist, because where the data is stored should answer the question. His chapter on existential processing has section headings that are instructions: “Don't use booleans”, “Don't use enums quite as much”[8].

Instead of an isHurt field checked by every update, keep a table that contains a row only for hurt entities, and regenerate health for every row in it. In Fabian's words, each such table has an “implicit boolean hidden in the row existing in the table”. The same works for enums: “Any enum can be emulated with a variety of tables. All you need is one table per enumerable value. Setting the enumeration is an insert into a table or a migration from one table to another.”[8] That is Chapter 1's version 4, the per-kind shape arrays, stated as a general rule; Muratori gives the same advice for his shapes: n kinds, n arrays, n loops, no dispatch[10]. Andrew Kelley applies it to the monster from Chapter 3: the bool is still there, “it's which array is it in”, and the struct shrinks from 24 to 16 bytes[9].

The benefits stack up: no branch to mispredict; no bytes loaded for dead entities; a homogeneous loop the compiler can unroll and vectorize; and visible work, since the length of the table is the to-do list.

The rest of this section uses the second of the chapter's three ways, place: four places to keep “alive”, then tables, bucketing by type, compaction and dirty lists. The third way, look it up, follows in its own section.

Four places to keep “alive”

Our benchmark updates a million entities (x += vx; y += vy) with a random half, then a random 90%, dead. It keeps the alive state in four places:

  1. A field and an if. Entity is four i32s and a bool: 17 bytes of data, 20 with padding.
  2. An out-of-band bool array. The bodies are 16 bytes and the flags live in a parallel []bool. Still a branch per entity, but the struct lost its padding.
  3. An out-of-band bit set. One bit per entity; the loop walks the set bits with “count trailing zeros”, so it never even looks at dead entities' bodies.
  4. Tables. An alive table and a dead table. Killing an entity moves its row from one to the other with swap-and-pop, and the update runs over the alive table with no condition at all.
/// Version 1: the flag is a field. 17 bytes of data, 20 with padding.
#[derive(Clone, Copy)]
struct Entity {
    x: i32,
    y: i32,
    vx: i32,
    vy: i32,
    alive: bool,
}

/// Versions 2-4: the same data without the flag. 16 bytes.

struct Body {
    x: i32,
    y: i32,
    vx: i32,
    vy: i32,
}

const _: () = assert!(size_of::<Entity>() == 20);

The size assertions pin the claim from Chapter 3: the one-byte flag costs four bytes per entity, because the struct's alignment is 4.

Bit sets in three standard libraries

When state must stay attached to the entity's index (other systems hold indices into this array, as in Chapter 5), you cannot move rows freely. Then the next best thing is to take the flag out of the struct and pack it: one bit per entity is 128 KiB for a million, against 1 MiB of bools or 4 MiB of padding. Rust's standard library has no bit-set type, so we write the loop on u64 words directly. Zig has std.bit_set, and Odin has core:container/bit_array for runtime sizes and the built-in bit_set type for small fixed ones.

/// Out-of-band bits: visit only the set bits, 64 entities per word.
#[inline(never)]
fn update_bitset(bodies: &mut [Body], alive: &[u64]) {
    for (w, &word) in alive.iter().enumerate() {
        let mut m = word;
        while m != 0 {
            let b = &mut bodies[w * 64 + m.trailing_zeros() as usize];
            b.x += b.vx;
            b.y += b.vy;
            m &= m - 1; // clear the lowest set bit
        }
    }
}
/// Out-of-band bits: the bit set's iterator visits only the set bits.
noinline fn updateBitset(c: BitsCtx) usize {
    var it = c.alive.iterator(.{});
    while (it.next()) |i| {
        const b = &c.bodies[i];
        b.x += b.vx;
        b.y += b.vy;
    }
    return c.bodies.len;
}
// Out-of-band bits: core:container/bit_array's iterator visits only the set bits.
update_bitset :: #force_no_inline proc(c: Bits_Ctx) -> u64 {
	bodies := c.bodies
	it := ba.make_iterator(c.alive)
	for i in ba.iterate_by_set(&it) {
		b := &bodies[i]
		b.x += b.vx
		b.y += b.vy
	}
	return u64(len(c.bodies))
}

All three iterators do the same thing underneath: Zig's next() is literally @ctz(bits_remain) followed by bits_remain &= bits_remain - 1, the two lines in our Rust loop. Zig's iterator inlines into a tight loop; Odin's iterate_by_set supports a bias and re-checks the word index on every call, and in our measurements it is about three times as slow as the other two.

std.bit_set.Static(n) (formerly StaticBitSet) and std.bit_set.Dynamic (formerly DynamicBitSetUnmanaged, now a deprecated alias). Dynamic is unmanaged: try .initEmpty(gpa, n) and deinit(gpa); static sets use the .empty and .full declaration literals[16].

A bit_set is no longer limited to 128 elements: it can be backed by an array, for example bit_set[Big; [4]u64][17]. For per-entity flags you still want a small bit_set[Flag; u8] in a column of its own.

Tables and swap-and-pop

The fourth version is existence proper. Killing an entity is a table migration: take its row out of alive, push it onto dead. Taking a row out of the middle of a dense array with swap-and-pop (move the last row into the hole, shrink by one) is O(1) and keeps the table dense, at the cost of order. Chapter 5 compared it with holes and tombstones; here it is the engine of state change.

impl Table {
    fn push(&mut self, id: u32, b: Body) {
        self.ids.push(id);
        self.bodies.push(b);
    }
    /// Swap-and-pop: the last row moves into the hole. O(1), and the table stays dense.
    fn swap_remove(&mut self, row: usize) -> (u32, Body) {
        (self.ids.swap_remove(row), self.bodies.swap_remove(row))
    }
}

/// Changing state is moving a row from one table to another.
fn kill_where(alive: &mut Table, dead: &mut Table, pred: impl Fn(u32) -> bool) {
    let mut row = 0;
    while row < alive.ids.len() {
        if pred(alive.ids[row]) {
            let (id, b) = alive.swap_remove(row);
            dead.push(id, b);
            // do not advance: the row now holds what was the last element
        } else {
            row += 1;
        }
    }
}

/// Existence: no flag, no branch. Every row in this table is alive.
#[inline(never)]
fn update_alive(alive: &mut [Body]) {
    for b in alive {
        b.x += b.vx;
        b.y += b.vy;
    }
}
/// A table per state: MultiArrayList keeps `id` and `body` in two columns.
const Row = struct { id: u32, body: Body };
const Table = std.MultiArrayList(Row);

/// Changing state is moving a row from one table to another.
fn killWhere(gpa: Allocator, alive: *Table, dead: *Table, dead_pct: u64) !void {
    var row: usize = 0;
    while (row < alive.len) {
        if (dies(alive.items(.id)[row], dead_pct)) {
            try dead.append(gpa, alive.get(row));
            alive.swapRemove(row); // the last row moves into the hole, in every column
            // do not advance: the row now holds what was the last element
        } else row += 1;
    }
}

/// Existence: no flag, no branch. Every row in this table is alive.
noinline fn updateAlive(alive: []Body) usize {
    for (alive) |*b| {
        b.x += b.vx;
        b.y += b.vy;
    }
    return alive.len;
}
// A table per state: #soa stores `id` and `body` as two columns.
Row :: struct {
	id:   u32,
	body: Body,
}

// Changing state is moving a row from one table to another.
kill_where :: proc(alive, dead: ^#soa[dynamic]Row, dead_pct: u64) {
	row := 0
	for row < len(alive) {
		if dies(alive[row].id, dead_pct) {
			append(dead, alive[row])
			unordered_remove(alive, row) // the last row moves into the hole, in every column
			// do not advance: the row now holds what was the last element
		} else {
			row += 1
		}
	}
}

// Existence: no flag, no branch. Every row in this table is alive.
update_alive :: #force_no_inline proc(alive: []Body) -> u64 {
	for &b in alive {
		b.x += b.vx
		b.y += b.vy
	}
	return u64(len(alive))
}

A table has two columns, the stable id and the body. Rust has no SoA container, so Table keeps two Vecs in step by hand; Zig's MultiArrayList.swapRemove moves the last row in every column at once; Odin's #soa[dynamic]Row does the same with unordered_remove, and soa_unzip splits out the bodies. In all three the update loop sees a plain []Body.

Half the entities alive, in random order. The opening of this chapter said the table version is roughly 14× faster. The flag version reads 20 MiB and the table version 8 MiB. How much of that do the bytes explain, and where does the rest come from?

Bytes explain only 2.5×; the rest is the coin-flip branch. A million unpredictable branches at roughly 18 cycles per miss, half of them missing, is several milliseconds by itself. The bool array, with smaller structs but the same branch, is only a little faster than the flag. The bit set has no data branch on the bodies and lands in between.

The rough budget for the 50% case: the flag loop takes about 5.5 ms for a million entities. The table loop moves its 8 MiB (read and written) in about 0.36 ms, about 22 GB/s for this workload. Reading 20 MiB at that rate would take about 1 ms, and half a million mispredicts at ~7 ns would take about 3.5 ms, which adds up to most of the flag loop's time.

All three languages land within about 10% of each other on the flag, bool-array and table versions. The table version in particular costs the same per entity in all three, because it is limited by memory, not by code. The exception is the bit set in Odin, for the iterator reason above.

When existence is the wrong tool. Moving rows costs a copy and a swap-remove per state change, and it reorders the table. If most entities change state every frame, the migrations can cost more than the branch you removed. Asking “what state is entity 42 in?” becomes a search across tables; Fabian concedes that “finding out the value of an enum in an entity is difficult”[8]. Keep an id → (table, row) index if that query is hot, and fix it up on every swap (that is a sparse set, Chapter 9). If order matters, as it does for draw order, use a bit set or sort a key array instead.

Sorting and bucketing by type

A mixed array processed with a switch per element has the same disease as the alive flag, multiplied by the number of kinds. Fabian's one-table-per-enum-value is the cure, and Chapter 1 measured it with per-kind shape arrays. If the data must arrive mixed, there are two cheaper half-measures. Sorting by kind makes the branch predictable but costs O(n log n) every time the data changes; greyblake's note is blunt, “sorting the input is not a fix: sorting costs much more than the filtering itself”[20]. Bucketing as the data is produced (append each new item to its kind's array) costs nothing extra and is what TigerBeetle does with its homogeneous batches: a batch is all accounts or all transfers, so the kind is decided once per batch.

Stream compaction and dirty lists

The branchless filter from the first half of the chapter is the general tool for building such tables: compact the survivors of a predicate into a dense output (a selection vector, in X100's terms[6]), and downstream loops run over it with no condition.

The same idea applied to change tracking is the dirty list. A dirty flag per row means every consumer scans every row to find the few that changed. A list of dirty row indices means the consumer visits exactly those rows. A bit per row makes marking idempotent, so a row changed ten times is listed once:

/// A dirty list: remember *which* rows changed, once each, instead of a dirty flag per row
/// that every consumer has to scan for.
struct DirtyList {
    seen: Vec<u64>, // one bit per row: already listed?
    rows: Vec<u32>,
}

impl DirtyList {
    fn new(n: usize) -> Self {
        DirtyList { seen: vec![0; n.div_ceil(64)], rows: Vec::new() }
    }
    fn mark(&mut self, row: u32) {
        let (w, bit) = (row as usize / 64, 1u64 << (row % 64));
        if self.seen[w] & bit == 0 {
            self.seen[w] |= bit;
            self.rows.push(row);
        }
    }
    /// Hand the dirty rows to `f`, then forget them. Cost: O(dirty), not O(rows).
    fn drain(&mut self, mut f: impl FnMut(u32)) {
        for &row in &self.rows {
            f(row);
            self.seen[row as usize / 64] &= !(1u64 << (row % 64));
        }
        self.rows.clear();
    }
}
/// A dirty list: remember *which* rows changed, once each, instead of a dirty flag per row
/// that every consumer has to scan for.
const DirtyList = struct {
    seen: std.bit_set.Dynamic, // one bit per row: already listed?
    rows: std.ArrayList(u32) = .empty,

    fn mark(d: *DirtyList, gpa: Allocator, row: u32) !void {
        if (!d.seen.isSet(row)) {
            d.seen.set(row);
            try d.rows.append(gpa, row);
        }
    }

    /// Hand the dirty rows to the caller, then forget them. Cost: O(dirty), not O(rows).
    /// The returned slice is valid until the next `mark`.
    fn drain(d: *DirtyList) []const u32 {
        for (d.rows.items) |row| d.seen.unset(row);
        defer d.rows.clearRetainingCapacity();
        return d.rows.items;
    }
};
// A dirty list: remember *which* rows changed, once each, instead of a dirty flag per row
// that every consumer has to scan for.
Dirty_List :: struct {
	seen: ba.Bit_Array, // one bit per row: already listed?
	rows: [dynamic]u32,
}

dirty_mark :: proc(d: ^Dirty_List, row: u32) {
	if !ba.get(&d.seen, row) {
		ba.set(&d.seen, row)
		append(&d.rows, row)
	}
}

// Hand the dirty rows to the caller, then forget them. Cost: O(dirty), not O(rows).
// The returned slice is valid until the next `dirty_mark`.
dirty_drain :: proc(d: ^Dirty_List) -> []u32 {
	for row in d.rows {
		ba.unset(&d.seen, row)
	}
	defer clear(&d.rows)
	return d.rows[:]
}

In quick mode the program marks 512 random rows out of 1,024 and drains 395 distinct ones; the cost of the drain is 395 visits, not 1,024. This is Acton's cache-line arithmetic from Chapter 1 turned around: instead of paying a cache line per entity to find out that nothing happened, you pay only for what did.

Lookup tables, and recompute versus store

The third way to stop asking a question is to have answered it in advance. Ghostty's profiling found that “30% of the time taken for every printed character was spent calculating codepoint width”. Hashimoto “precalculated the codepoint width for every single Unicode codepoint value” into a 3-stage lookup table, and even folded a branch into it: triple-width characters are clamped to double width in the table, “without an additional conditional at runtime”. ASCII throughput went up 2.8× in his benchmark, random UTF-8 about 5×, and cat of ASCII a further 2.5× in wall time[18]. Years later the same print path was batched too: a 2026 PR hands whole runs of codepoints to one call that “hoists the invariants”, and plain ASCII parsing went from 128 to 725 MB/s[5].

Our small version classifies bytes as identifier characters, [A-Za-z0-9_], either with comparisons or with a 256-entry table built at compile time. The table is 256 bytes, four cache lines, so it lives in L1.

/// Built at compile time: 1 for [A-Za-z0-9_], else 0.
const IDENT: [u8; 256] = {
    let mut t = [0u8; 256];
    let mut c = 0;
    while c < 256 {
        let b = c as u8;
        t[c] = (b.is_ascii_alphanumeric() || b == b'_') as u8;
        c += 1;
    }
    t
};

fn count_ident_lut(text: &[u8]) -> usize {
    text.iter().map(|&c| IDENT[c as usize] as usize).sum()
}
/// Built at compile time: 1 for [A-Za-z0-9_], else 0.
const IDENT: [256]u8 = blk: {
    var t: [256]u8 = undefined;
    for (&t, 0..) |*x, c| x.* = @intFromBool(std.ascii.isAlphanumeric(c) or c == '_');
    break :blk t;
};

noinline fn countIdentLut(text: []const u8) usize {
    var n: usize = 0;
    for (text) |c| n += IDENT[c];
    return n;
}
// A table written as a literal with index ranges: 1 for [A-Za-z0-9_], else 0.
@(rodata)
IDENT := [256]u8 {
	'a' ..= 'z' = 1,
	'A' ..= 'Z' = 1,
	'0' ..= '9' = 1,
	'_'         = 1,
}

count_ident_lut :: #force_no_inline proc(text: []u8) -> int {
	n := 0
	for c in text {
		n += int(IDENT[c])
	}
	return n
}

Rust builds the table in a const block with a while loop (no for in const fn yet), Zig with a comptime for, and Odin with an array literal that accepts ranges like 'a' ..= 'z' = 1.

The table wins in every language, by about 4× in Zig and more in Odin and Rust. The comparison versions are where the compilers' choices from the asm table show up: Zig's branchless scalar code is the fastest of the three at about 1.2 ns per byte; Odin's branches mispredict on random text and cost about 4.5 ns; and Rust's vectorized version lands in between at about 2.7 ns, more than twice Zig's scalar code. It unpacks bytes into wide lanes and repacks them, a reminder that “the compiler vectorized it” is not the same as “it got faster”. The table version sidesteps all of that: one load per byte, the same machine code everywhere.

The opposite trade is just as data-oriented. Carbon's toolchain stores no line and column with its tokens; they are recomputed from the token index when a diagnostic needs them[19]. Count how often each answer is needed and what it costs to keep in cache: a 256-byte table used for every byte belongs in L1, a per-token line number used once per error belongs nowhere.

A branch costs what its mispredictions cost, so either make the answer predictable, compute it without a jump, look it up, or, best of all, store the data so the question never needs asking: in batches that answer it once, and in tables whose membership is the answer.

Exercises

The branchless filter needs an output buffer as long as the input, even when it keeps 1%. Why, and how would you avoid allocating that much for a mostly-empty result?

It stores every element before deciding whether to keep it, so the store position must be valid even if everything is kept. Process the input in batches of, say, 1,024 into a small scratch buffer and copy the survivors out after each batch. That is batching again: the bound is per batch, not per input.

Using the 2-bit counter model, what misprediction rate do you expect on a random branch that is taken with probability p? Compare with the measured sweep at 10% and 30%.

Number the states 0 (strong not-taken) to 3 (strong taken), with q = 1 − p. In steady state each neighbouring pair balances, πk+1 = πk · p/q. The counter misses a taken branch in states 0–1 and a not-taken one in 2–3, which works out to pq / (p2 + q2): 11.0% at 10%, 36.2% at 30%, 50% at 50%. (Simulate it to check; 2pq, the chance two outcomes differ, is the 1-bit “same as last time” predictor, which misses 18% and 42%.) With ~7.0 ns per miss on a ~0.5 ns branchless base, the 2-bit model predicts about 1.27 ns and 3.0 ns. We measured 1.3 ns and 3.2 ns in Rust, a few percent worse: the real predictor behaves like a 2-bit counter here, because on random outcomes there is no history for it to exploit, and aliasing in a real predictor costs a little extra.

In the existence benchmark at 10% alive, the bool array is only 1.2× (Odin) to 1.5× (Rust) faster than the flag in the struct, although 90% of the entities it tests are dead. Why so little?

Both walk their arrays in index order, testing every entity, and the hardware prefetcher streams in body lines whether or not their entities are alive. With the branch now 90% predictable, memory is the main cost, and the gain is just the 20% smaller bodies plus a separate, dense flag array. Only the versions that skip the dead (bit set, table) stop touching their memory.

Write the Odin bit-set loop without core:container/bit_array, using a []u64 and intrinsics.count_trailing_zeros. What do you expect it to cost compared with the Rust version?

for word, w in alive { m := word; for m != 0 { i := w*64 + int(intrinsics.count_trailing_zeros(m)); b := &bodies[i]; b.x += b.vx; b.y += b.vy; m &= m - 1 } }, with bodies hoisted into a local. It should match Rust and Zig, since all three then compile to the same count-trailing-zeros / clear-lowest-bit loop (tzcnt/blsr on Zig's native target, rep bsf plus lea/and on Rust's and Odin's default targets, which lack BMI); the gap in the chart is library overhead, not language overhead.

Your game kills about 1% of entities per frame and spawns as many. Each update system reads the alive table once. Is moving rows between tables worth it, compared with a bit set?

Almost certainly. 1% migrations per frame cost about 0.01 × n row copies, while every system saves the dead entities' loads and the branch on every row, every frame. The bit set is the better choice when other code holds stable indices into the array (moving rows would invalidate them) or when most entities change state every frame.

The batch sweep's right-hand end is 64 MiB of buffers. Suggest a change to the pipeline that keeps the same total work but makes even a huge requested batch run at plateau speed.

Internally cap the batch: split any requested batch into chunks of about 1K–64K items and run all three stages on one chunk before moving to the next, so intermediates stay in L1/L2. This is exactly X100's and DuckDB's design: the user sees a table, the engine sees cache-sized vectors.
