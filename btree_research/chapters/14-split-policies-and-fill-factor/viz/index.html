A page is full and one more cell must go in. Somewhere between two of its cells the page has to be cut in two. This page lets you watch where four different policies make that cut, and what the choice does to an index after a few hundred inserts. It accompanies chapter 14 of the guide; the code that it mirrors is in zig/src/split.zig and rust/src/split.rs.

1. One split, step by step

Each box is a cell, as wide as the bytes it occupies; the number in bold is its key, #n is the row id that tells equal keys apart. Pick a page, say where it sits in the tree, pick a policy, and step through the decision. Tick Predict to be asked for the cut before it is shown.

2. The same inserts under two policies

Both rows receive exactly the same cells in the same order; only the split policy differs. Every gauge is one 4096-byte leaf page in key order, filled to the height of its content. A step is one insert that made a page split.

3. What the programs measured

The chapter's Zig and Rust programs run the four workloads with 20 000 inserts each and print this (it is part of expected_output.txt). “Separators with a row id” counts the cuts that fell inside a run of equal keys: the parent then has to store the row id as well as the key.
