Chapter 4

AoS, SoA and Hot/Cold Splitting

Our particle is 64 bytes. The loop that runs every frame reads 24 of them. The cache does not know or care which 24 you wanted: it moves whole 64-byte lines, so the loop pays for all 64. This chapter turns the array inside out so the hot loop moves only the bytes it uses. Then it shows the two cases where turning it inside out makes things worse.

Sixty-four bytes to use twenty-four

Here is the record the whole chapter uses, a plausible particle for a game or a visual-effects tool: a position and a velocity, which every frame needs, and ten fields that other systems read now and then (mass, age, lifetime, size, colour, id, flags, a random seed, the emitter and a render group). Sixteen four-byte fields make exactly 64 bytes, one cache line here, and aligning it to 64 puts every particle in exactly one line.

/// Sixteen 4-byte fields. The update reads 6 of them (24 B) and writes 3.
#[derive(Clone, Copy, Default)]
#[repr(align(64))] // one particle = exactly one cache line
struct Particle {
    px: f32, py: f32, pz: f32, // hot: read and written every frame
    vx: f32, vy: f32, vz: f32, // hot: read every frame
    mass: f32, age: f32, life: f32, size: f32, // cold from here on
    color: u32, id: u32, flags: u32, seed: u32, emitter: u32, group: u32,
}
const _: () = assert!(size_of::<Particle>() == 64);
/// Sixteen 4-byte fields. The update reads 6 of them (24 B) and writes 3.
const Particle = struct {
    px: f32, py: f32, pz: f32, // hot: read and written every frame
    vx: f32, vy: f32, vz: f32, // hot: read every frame
    mass: f32, age: f32, life: f32, size: f32, // cold from here on
    color: u32, id: u32, flags: u32, seed: u32, emitter: u32, group: u32,
};
comptime {
    std.debug.assert(@sizeOf(Particle) == 64);
}
// Sixteen 4-byte fields. The update reads 6 of them (24 B) and writes 3.
// Odin keeps declaration order; #align(64) makes one particle exactly one cache line.
Particle :: struct #align (64) {
    px, py, pz:              f32, // hot: read and written every frame
    vx, vy, vz:              f32, // hot: read every frame
    mass, age, life, size:   f32, // cold from here on
    color, id, flags, seed:  u32,
    emitter, group:          u32,
}
#assert(size_of(Particle) == 64)

Rust puts #[repr(align(64))] on the type and Odin puts #align(64) on the struct. Plain Zig structs have no type-level alignment attribute, so Zig asks for it where the array is allocated (gpa.alignedAlloc(Particle, .fromByteUnits(64), n)). All three check the 64-byte size at compile time (Chapter 3), and with sixteen four-byte fields no field order can add padding.

The update is the smallest loop that still counts as physics:

fn update(&mut self, dt: f32) {
    for p in &mut self.ps {
        p.px += p.vx * dt;
        p.py += p.vy * dt;
        p.pz += p.vz * dt;
    }
}
fn update(self: *Aos) void {
    for (self.ps) |*p| {
        p.px += p.vx * dt;
        p.py += p.vy * dt;
        p.pz += p.vz * dt;
    }
}
aos_update :: proc(l: Aos) -> u64 {
    for &p in l.ps {
        p.px += p.vx * DT
        p.py += p.vy * DT
        p.pz += p.vz * DT
    }
    return 0
}

Each iteration reads six floats (24 bytes) and writes three (12 bytes). The CPU cannot fetch 24 bytes from memory. The smallest unit it moves between DRAM, L3, L2 and L1 is a 64-byte cache line (Chapter 2). So the loop fetches the whole particle and uses three eighths of it.

Before reading on: if the 4,194,304 particles (256 MiB) do not fit in any cache, how many bytes does one pass of this loop move between the core and DRAM, and how many does it need?

It moves 256 MiB in (every line is read) and 256 MiB out: the loop wrote to every line, and a dirty line goes back to memory whole. That is 512 MiB. It needs 4,194,304 × 36 B = 144 MiB. About 72% of the traffic is bytes the loop never looks at.

Per particle, that is 128 bytes of memory traffic to do 36 bytes of work. Mike Acton's version of this argument, in his CppCon 2014 keynote, is the reason this book exists: when you read one field from a fat object in a loop, most of every cache line you pay for is waste, and the waste is the cost[1]. The rest of this chapter is four ways to stop paying for it, three languages' ways of writing them, and measurements that show where each one stops working.

Four ways to store the same particles

The same sixteen fields of the same N particles can be laid out in memory in four standard ways:

  • Array of structs (AoS). [N]Particle. A particle's fields sit next to each other. This is what every language gives you by default, and what "an array of objects" means.
  • Hot/cold split. Two parallel arrays with the same index: hot[N] holds what the frame loop touches (pos, vel: 24 B), and cold[N] holds everything else (40 B). It is still an array of structs, just two of them.
  • Struct of arrays (SoA). One array per field: px[N], py[N], …, group[N]. Particle i is the i-th element of sixteen arrays. A loop that reads px streams a dense array of floats.
  • Array of structs of arrays (AoSoA). Blocks of 8 particles. Inside a block each field is an [8]f32: {px[8], py[8], …, group[8]}, 512 bytes per block. It is SoA in small tiles, which keeps SoA's vector-friendly layout while keeping one particle's fields within one 512-byte block. ISPC calls this "hybrid SoA" and has a soa<8> qualifier for it[9].

Count the outlined lines in the figure above. AoS touches all 16 lines for 16 particles. The other three layouts each fetch 6 lines, 24 bytes per particle, exactly what the loop reads. For reads they tie. For writes they do not, because a line with one written byte goes back to memory whole: every hot/cold line holds some particle's pos, so all 6 are written back, while SoA writes back only its 3 pos columns and AoSoA the 2 lines per block that hold px, py and pz.

Bytes fetched, bytes used

The cost model behind all of this is short. In a loop over many records that do not fit in cache, the time is roughly bytes moved ÷ bandwidth. Bytes moved is the number of distinct cache lines that hold any byte the loop reads, times 64, plus 64 for every line it dirties. Bytes used is the sum of the field sizes the loop actually reads. Their ratio is the fraction of the bandwidth you are paying for that does useful work.

That model fits in a figure. The figure below uses the chapter's real 64-byte particle. Pick the fields the loop reads, and each layout computes which of its lines hold those fields. Switch to random records to see the opposite access pattern: one whole record at a random index, where no two accesses share a line.

In the figure, select only pos with random records. Which layout is cheapest, and by how much?

AoS, with exactly 1 line per record: pos sits at the start of the particle's own line. Hot/cold is close behind at 1.13 lines (one record in eight has its 12 bytes of pos straddling a line boundary). AoSoA needs 2 lines, because px, py and pz are three 32-byte arrays in the same block. SoA needs 3, one per column. With random access, the cost is the number of different places a record's fields live, not the number of bytes.

A worked example with real numbers

Take 4,194,304 particles (222). In AoS that is 256 MiB, far bigger than this machine's 1.25 MiB of L2 and the roughly 6–8 MiB of L3 this virtual machine could use in Chapter 2's sweep (Chapter 2). Per pass of the update:

If every loop runs at the same bandwidth, the model predicts AoS about 3.6 times slower than SoA, with AoSoA and hot/cold close behind SoA. Measured on this orb, Rust's AoS update is about 4.2× slower than its SoA update, Odin's is about 4.0×, and Zig's is about 2.6×. In Rust, the AoS loop took 7.1 ns per particle and the SoA loop 1.7 ns. AoS moves 128 bytes per particle (64 read, 64 written back) and SoA moves 36, so divide bytes by time and the two loops come out at roughly the same rate. Both loops run at about the same bandwidth. SoA is faster because it moves fewer bytes, which is the whole argument in one measurement. (That rate counts reads plus write-backs for this one loop. Chapter 2's read-only streams measure something else, and neither is "the" bandwidth of the machine.) At 60 frames per second, the AoS pass alone (30 ms) would not fit in a 16.7 ms frame. The SoA pass (7.1 ms) would.

The model is less good at the middle of the table. It says hot/cold and AoSoA should be within a third of SoA. Measured in Rust, hot/cold took about 1.9× SoA's time and AoSoA about 2.2×. We will come back to why after the code.

SoA in Rust: you write it yourself

Rust has no struct-of-arrays type in the language or in std. You write one Vec per field and keep them the same length yourself. Crates such as soa_derive[12] and soa-rs[13] generate this from a derive macro (soa-rs uses one allocation for all fields), but this book uses std only, so here it is by hand:

// ---- 3. SoA, hand-written: one Vec per field ----
#[derive(Default)]
struct Soa {
    px: Vec<f32>, py: Vec<f32>, pz: Vec<f32>,
    vx: Vec<f32>, vy: Vec<f32>, vz: Vec<f32>,
    mass: Vec<f32>, age: Vec<f32>, life: Vec<f32>, size: Vec<f32>,
    color: Vec<u32>, id: Vec<u32>, flags: Vec<u32>, seed: Vec<u32>, emitter: Vec<u32>, group: Vec<u32>,
}
impl Soa {
    fn push(&mut self, p: Particle) {
        self.px.push(p.px); self.py.push(p.py); self.pz.push(p.pz);
        self.vx.push(p.vx); self.vy.push(p.vy); self.vz.push(p.vz);
        self.mass.push(p.mass); self.age.push(p.age); self.life.push(p.life); self.size.push(p.size);
        self.color.push(p.color); self.id.push(p.id); self.flags.push(p.flags);
        self.seed.push(p.seed); self.emitter.push(p.emitter); self.group.push(p.group);
    }
}
impl Layout for Soa {
    const LABEL: &'static str = "SoA";
    const UPDATE_BYTES: usize = 24;
    fn build(n: usize) -> Self {
        let mut s = Soa::default();
        (0..n).for_each(|i| s.push(particle(i)));
        s
    }
    fn update(&mut self, dt: f32) {
        // No multi-slice `for` in Rust: zip the columns. Disjoint field borrows are fine.
        let pos = self.px.iter_mut().zip(&mut self.py).zip(&mut self.pz);
        let vel = self.vx.iter().zip(&self.vy).zip(&self.vz);
        for (((x, y), z), ((vx, vy), vz)) in pos.zip(vel) {
            *x += vx * dt;
            *y += vy * dt;
            *z += vz * dt;
        }
    }

Three things are worth noticing. First, self.px.iter_mut() and self.vx.iter() borrow different fields of the same struct, which the borrow checker allows. Second, Rust has no multi-slice for, so the update zips six iterators; it is ugly, but zipped slice iterators compile to plain indexed loops with no bounds checks. Third, and this is the big one, &mut means "no other reference can see this memory". Rust passes that to LLVM as noalias, so LLVM knows a store to px cannot change vx and can vectorize without a run-time overlap check. In the cache-resident run below, Rust's SoA update is the fastest plain loop of the three languages.

The cost of doing it by hand shows up as soon as you need a whole record. A get(i) that copies particle i out of sixteen Vecs does sixteen bounds checks, because the compiler cannot know the sixteen lengths are equal. In the "read every field" loop, that made SoA several times slower than AoS on a cache-resident run, before the fix below. The fix is to prove the lengths once, by re-slicing every column to ..n before the loop:

fn every(&self) -> u64 {
    // Row by row over 16 columns. Re-slicing every column to n proves the lengths once,
    // so the loop has no bounds checks (a plain self.get(i) loop pays 16 per record).
    let n = self.px.len();
    let f = [&self.px, &self.py, &self.pz, &self.vx, &self.vy, &self.vz, &self.mass, &self.age, &self.life, &self.size];
    let u = [&self.color, &self.id, &self.flags, &self.seed, &self.emitter, &self.group];
    let (f, u) = (f.map(|c| &c[..n]), u.map(|c| &c[..n]));
    let mut total = 0u64;
    for i in 0..n {
        let fs: u64 = f.iter().map(|c| c[i].to_bits() as u64).sum();
        let us: u64 = u.iter().map(|c| c[i] as u64).sum();
        total = total.wrapping_add(fs + us);
    }
    total
}

A hand-written SoA has invariants the type system does not know: every column has the same length, and every push, swap-remove and sort must touch all of them. Forget one column in swap_remove and the particles' fields quietly stop lining up. Keep every mutation in one impl block, and assert the lengths in debug builds.

SoA in Zig: std.MultiArrayList

Zig's standard library has SoA built in, as a comptime-generated container. Its doc comment states the case plainly: it "allows for memory savings if the struct or union has padding, and also improves cache usage if only some fields or just tags are needed for a computation"[3]. Andrew Kelley's talk on data-oriented design calls switching an ArrayList to a MultiArrayList "a five-character fix, same API", and in his monster example it takes 10,000 monsters from 160 KB to 91 KB, because the padding disappears[2].

list: std.MultiArrayList(Particle),
cols: std.MultiArrayList(Particle).Slice, // column pointers, computed once (valid until the list grows)

fn build(gpa: Allocator, n: usize) !Self {
    var list = try std.MultiArrayList(Particle).initCapacity(gpa, n); // exactly n: no rounding up
    for (0..n) |i| list.appendAssumeCapacity(particle(i));
    return .{ .list = list, .cols = list.slice() };
}
fn deinit(self: *Self, gpa: Allocator) void {
    self.list.deinit(gpa);
}
fn update(self: *Self) void {
    const s = self.cols;
    if (vectorized) {
        integrateVec(s.items(.px), s.items(.vx));
        integrateVec(s.items(.py), s.items(.vy));
        integrateVec(s.items(.pz), s.items(.vz));
    } else {
        for (s.items(.px), s.items(.py), s.items(.pz), s.items(.vx), s.items(.vy), s.items(.vz)) |*x, *y, *z, vx, vy, vz| {
            x.* += vx * dt;
            y.* += vy * dt;
            z.* += vz * dt;
        }
    }
}

The idioms to learn: build it with .empty or initCapacity and pass the allocator to every call that allocates; call slice() once, outside the loop, to compute the column pointers; s.items(.px) is then a plain []f32. The multi-object for walks six columns in lockstep and checks their lengths match in safe builds. list.get(i) and list.set(i, p) convert between one Particle and the columns. A MultiArrayList of a tagged union stores tags and data columns, the layout of the Zig compiler's own AST and of Chapter 11.

Under the hood it is one allocation. The columns sit back to back, sorted by field alignment (descending), so there is no padding between them; fields with equal alignment keep their declaration order. The program prints where the columns start for a 4,096-particle list: px at +0, vx at +49,152 (3 × 16 KiB) and seed at +212,992 (13 × 16 KiB). Remember those multiples of 16 KiB; they come back in the aliasing section.

Zig 0.17.1 does not auto-vectorize loops. It builds its LLVM pipeline with LoopVectorization = false (src/zig_llvm.cpp, line 288), as a workaround for an LLVM miscompilation of a vectorized loop (llvm-project issue #186922) that broke the Zig compiler's own bootstrap[4]. In practice:

  • Loops stay scalar. The multi-object for above compiles to scalar vmulss and vaddss, one float at a time, even though Zig targets this machine's own CPU (which has AVX-512) and the columns cannot overlap.
  • Straight-line code still vectorizes. The SLP vectorizer, which packs independent operations within a block of code, still runs. Zig's AoSoA update loops over a fixed [8]f32; LLVM unrolls that into straight-line code and SLP packs it into 8-wide AVX (vmulps ymm).
  • For SIMD, write the vectors yourself with @Vector:
/// p += v * dt, eight lanes at a time, then a scalar tail.
fn integrateVec(p: []f32, v: []const f32) void {
    const V = @Vector(lanes, f32);
    const dtv: V = @splat(dt);
    var i: usize = 0;
    while (i + lanes <= p.len) : (i += lanes) {
        const pv: V = p[i..][0..lanes].*;
        const vv: V = v[i..][0..lanes].*;
        p[i..][0..lanes].* = pv + vv * dtv;
    }
    for (p[i..], v[i..]) |*x, u| x.* += u * dt;
}

The program measures both versions, as SoA and SoA @Vector; the charts below show that the difference is larger in cache than in DRAM. The setting is a workaround, not a design choice, so check src/zig_llvm.cpp again when you upgrade Zig.

ensureTotalCapacity(gpa, n) may round the capacity up (it grows by a formula), and slice() places the columns by capacity, not length. If you need the exact layout, as this benchmark does, use initCapacity(gpa, n) or setCapacity. A Slice is only valid until the list grows, just like a pointer into an ArrayList.

SoA in Odin: #soa

Odin puts the layout in the type system. #soa[]Particle is a slice of particles stored as columns, and you index it exactly as you would index []Particle. The overview's own example comment says "Same syntax as AOS and treat as if it was an array"[5]:

soa_build :: proc(l: ^Soa, n: int) {
    l.ps = make(#soa[]Particle, n)
    for i in 0 ..< n {
        l.ps[i] = particle(i) // same syntax as AoS
    }
    return
}
soa_update :: proc(l: Soa) -> u64 {
    for &p in l.ps {     // p is an SOA proxy: p.px reads column px at this index
        p.px += p.vx * DT
        p.py += p.vy * DT
        p.pz += p.vz * DT
    }
    return 0
}
soa_get :: proc(l: Soa, i: int) -> Particle {return l.ps[i]} // gathers 16 columns
soa_every :: proc(l: Soa) -> (s: u64) {
    for p in l.ps {
        s += field_sum(p)
    }
    return
}
soa_free :: proc(l: Soa) {delete(l.ps)}

Compare soa_update with aos_update earlier: the loop body is identical, character for character. Switching layout is one keyword in the declaration. for &p in ps gives you a SoA proxy for row i, so p.px reads column px; l.ps[i] = particle(i) scatters one struct across sixteen columns; l.ps[i] gathers it back. You can also take a column as a plain slice: l.ps.px[:len(l.ps)] is a []f32.

There are three kinds. #soa[N]T is a fixed array, a struct of [N] arrays with no allocation. #soa[]T is a slice: one pointer per field plus a length, so size_of(#soa[]Particle) is 136 bytes (the program prints it). #soa[dynamic]T adds capacity and an allocator. As in Zig, make_soa_aligned in base/runtime/core_builtin_soa.odin makes one allocation and lays the columns back to back, here in declaration order[7].

The general make, append, delete, pop, unordered_remove and ordered_remove procedure groups include the #soa versions, so you no longer need to spell append_soa or delete_soa (they still exist). #soa[dynamic; N]T is rejected; use #soa[N]T with your own length.

Two Odin #soa surprises. for p in ps gives you a read-only copy; writing p.px += … is a compile error that tells you to write for &p in ps. And &ps[i] is not a ^Particle: it is what Odin calls an SOA pointer (container plus index), because there is no Particle in memory to point at. A procedure that takes ^Particle cannot accept it; pass the index or the column slices instead.

Odin: hoist slices out of a pointer before a hot loop. If a loop reads s.xs[i] through s: ^T and stores through another slice, LLVM must assume the store might overwrite the slice header behind s, so it reloads the header every iteration and does not vectorize. That is why Chapter 1's first Odin per-kind loop was much slower than Rust's. Copy the slices into locals first (xs := s.xs); this chapter's procedures take their layouts by value, which has the same effect.

Odin makes switching cheap, but it does not tell you when to switch: its own forum calls #soa "a somewhat niche feature … [not] something you should be using by default"[6].

Hot/cold splitting

Full SoA is the extreme. Most of its benefit in this benchmark comes from one cut: the fields the frame loop reads go into one struct, everything else into another, in two parallel arrays with the same index. That is hot/cold splitting, which predates the data-oriented vocabulary: Chilimbi, Davidson and Larus called it structure splitting in 1999 and had a compiler do it from profile data[10]. You keep a struct, a debugger that shows a whole hot record, and code that looks like AoS code.

// ---- 2. hot/cold split: two parallel Vecs, same index ----
#[derive(Clone, Copy, Default)]
struct Hot {
    px: f32, py: f32, pz: f32,
    vx: f32, vy: f32, vz: f32,
}
#[derive(Clone, Copy, Default)]
struct Cold {
    mass: f32, age: f32, life: f32, size: f32,
    color: u32, id: u32, flags: u32, seed: u32, emitter: u32, group: u32,
}
const _: () = assert!(size_of::<Hot>() == 24 && size_of::<Cold>() == 40);

struct HotCold {
    hot: Vec<Hot>,
    cold: Vec<Cold>,
}
// ---- 2. hot/cold split: a MultiArrayList with two columns, each an AoS ----
const Hot = struct { px: f32, py: f32, pz: f32, vx: f32, vy: f32, vz: f32 };
const Cold = struct {
    mass: f32, age: f32, life: f32, size: f32,
    color: u32, id: u32, flags: u32, seed: u32, emitter: u32, group: u32,
};
comptime {
    std.debug.assert(@sizeOf(Hot) == 24 and @sizeOf(Cold) == 40);
}

const HotCold = struct {
    pub const label = "hot/cold";
    pub const update_bytes = 24;
    list: std.MultiArrayList(struct { hot: Hot, cold: Cold }),
// ---- 2. hot/cold split: two plain slices, zipped into one #soa view with soa_zip ----
Hot :: struct {
    px, py, pz, vx, vy, vz: f32,
}
Cold :: struct {
    mass, age, life, size:                   f32,
    color, id, flags, seed, emitter, group: u32,
}
#assert(size_of(Hot) == 24 && size_of(Cold) == 40)

Hot_Cold :: struct {
    hc: #soa[]struct {
        hot:  Hot,
        cold: Cold,
    },
}

hot_cold_build :: proc(l: ^Hot_Cold, n: int) {
    hot := make([]Hot, n)
    cold := make([]Cold, n)
    for i in 0 ..< n {
        p := particle(i)
        hot[i] = {p.px, p.py, p.pz, p.vx, p.vy, p.vz}
        cold[i] = {p.mass, p.age, p.life, p.size, p.color, p.id, p.flags, p.seed, p.emitter, p.group}
    }
    l.hc = soa_zip(hot = hot, cold = cold) // no copy: a #soa slice over the two existing arrays
    return
}

hot_cold_free :: proc(l: Hot_Cold) {
    hot, cold := soa_unzip(l.hc) // back to the two plain slices
    delete(hot)
    delete(cold)
}

Rust uses two Vecs built with unzip(). Zig uses a MultiArrayList whose element has two struct fields: two columns, each an array of structs, in one allocation. Odin glues two ordinary slices into one #soa view with soa_zip, which copies nothing; soa_unzip takes it apart again to free it.

In the measurements, hot/cold takes Rust's AoS update at 4M particles from 7.1 ns per particle to 3.3 ns, and the other two languages behave alike: most of SoA's win for the smallest change to the code. The rest of the gap is probably vectorization. Filling eight float lanes from interleaved 24-byte Hot structs takes shuffles, and in cache the hot/cold loop stayed well behind the vectorized SoA and AoSoA loops in every language. That fits scalar code; we did not read every compiler's assembly to confirm it.

"Cold" has to be cold on every path that runs often. If the frame loop also reads age to retire dead particles, age is hot, and leaving it in cold[i] adds a second stream and a second cache line per particle. Decide the split from what the loops read, not from what the fields mean.

AoSoA: blocks of eight

AoSoA keeps SoA's best property for SIMD (eight consecutive px values are one 32-byte vector load) and undoes its worst property for random access (sixteen arrays that may be hundreds of megabytes apart). Every field of particle i lives in block i / 8, at lane i % 8, within 512 bytes.

// ---- 4. AoSoA: blocks of 8 particles, SoA inside each block ----
#[derive(Clone, Copy, Default)]
#[repr(align(64))]
struct Block {
    px: [f32; LANES], py: [f32; LANES], pz: [f32; LANES],
    vx: [f32; LANES], vy: [f32; LANES], vz: [f32; LANES],
    mass: [f32; LANES], age: [f32; LANES], life: [f32; LANES], size: [f32; LANES],
    color: [u32; LANES], id: [u32; LANES], flags: [u32; LANES],
    seed: [u32; LANES], emitter: [u32; LANES], group: [u32; LANES],
}
const _: () = assert!(size_of::<Block>() == 16 * 4 * LANES);

// AoSoA update: a lane loop over each block's fixed [f32; 8] arrays.
fn update(&mut self, dt: f32) {
    for b in &mut self.blocks {
        for j in 0..LANES {
            b.px[j] += b.vx[j] * dt;
            b.py[j] += b.vy[j] * dt;
            b.pz[j] += b.vz[j] * dt;
        }
    }
}
// ---- 4. AoSoA: blocks of 8 particles, SoA inside each block ----
const Block = struct {
    px: [lanes]f32, py: [lanes]f32, pz: [lanes]f32,
    vx: [lanes]f32, vy: [lanes]f32, vz: [lanes]f32,
    mass: [lanes]f32, age: [lanes]f32, life: [lanes]f32, size: [lanes]f32,
    color: [lanes]u32, id: [lanes]u32, flags: [lanes]u32,
    // …
fn update(self: *Aosoa) void {
    for (self.blocks) |*b| {
        for (&b.px, &b.py, &b.pz, b.vx, b.vy, b.vz) |*x, *y, *z, vx, vy, vz| {
            x.* += vx * dt;
            y.* += vy * dt;
            z.* += vz * dt;
        }
    }
}
// ---- 4. AoSoA: a slice of fixed #soa[8]Particle blocks ----
// #soa[8]Particle is a struct of sixteen [8]f32/[8]u32 arrays: exactly one AoSoA block.
Block :: #soa[LANES]Particle
#assert(size_of(Block) == 16 * 4 * LANES)

aosoa_update :: proc(l: Aosoa) -> u64 {
    for &b in l.blocks {
        b.px += b.vx * DT // array programming: eight lanes per statement
        b.py += b.vy * DT
        b.pz += b.vz * DT
    }
    return 0
}

Odin wins the elegance contest outright. A fixed #soa[8]Particle is an AoSoA block, a struct of sixteen [8] arrays, and array programming turns b.px += b.vx * DT into an eight-lane update. It compiled to packed SSE, four lanes at a time, because Odin's default x86-64-v2 target, like Rust's x86-64 baseline, has no AVX. Zig gets 8-wide AVX from a multi-object for over the block's arrays (through the SLP vectorizer), and Rust writes the lane loop out. AoSoA costs i / 8 and i % 8 on every random access, plus a tail block when N is not a multiple of 8, which this benchmark avoids.

Now the surprise from the worked example: in the DRAM-sized runs, AoSoA's update was slower than hot/cold in Rust and Odin and about equal in Zig, although the model says it moves 17% fewer bytes than hot/cold. Each 512-byte block holds the six hot fields in its first 3 lines, then 5 lines the update skips. The hardware prefetchers that make sequential reads fast fetch ahead in a stream, and a pattern of "3 lines, skip 5" is likely to pull some skipped lines in anyway. Without performance counters we cannot confirm that, but the measured time fits AoSoA moving clearly more than its modelled 40 bytes per particle. Niklas Gray, who built data-oriented engines at Bitsquid and Our Machinery, guessed at the same cost when he recommended this layout: "There might also be some cost associated with the skipping, even if we were processing full cache lines, not 100 % sure"[8].

What the measurements say

The program runs every layout at three sizes: 16,384 particles (1 MiB of AoS, fits in L2), 1,048,576 (64 MiB) and 4,194,304 (256 MiB). Each measurement is the median of seven runs after a warm-up, on one pinned core. Every layout must produce the same checksums (bit patterns of all positions after eight updates; of all sixteen fields for the other two experiments), and they match bit for bit across layouts and languages: the inputs come from the same integer hash[11], and dt is a power of two, so v * dt is exact and a fused multiply-add cannot change the result.

Run it (quick mode takes seconds; full size takes about a minute per language):

cd code && ./run_all.sh ch04
cargo run --release -q -p ch04_aos_soa_hot_cold            # full size, from code/
cd ch04-aos-soa-hot-cold/zig && zig run -O fast main.zig
cd ch04-aos-soa-hot-cold && odin run odin -o:speed -vet -strict-style
At 4M particles, which is faster: the Zig SoA update with explicit @Vector, or the plain scalar one?

The vector version, but only by about 1.2× (1.9 ns against 2.3 ns per particle), because the loop mostly waits on memory, not arithmetic. Gray's line applies: "if we're completely memory-bound, SIMD can't make us run faster"[8]. At 16K particles, where the data sits in L2, the gap was about 1.6×.

The two charts are the same code at two sizes, and they tell different stories. When the data is in DRAM, layout is most of the story and SIMD adds little. When the data fits in cache, layout matters only because it enables SIMD. With 16,384 particles Rust's AoS loop takes about 2.2× as long as its vectorized SoA loop, and Odin's AoS about 2.5× as long as its AoSoA. Gray's article makes the same point as arithmetic: a ×10 from better cache use and a ×8 from 8-wide SIMD do not multiply to ×80. You get the bandwidth win when you are memory-bound and the SIMD win when you are not, and the two rarely stack[8].

When AoS wins

Gray ends his careful AoS-vs-SoA analysis like this: "My take on AoS vs SoA is that in most cases, the performance improvements are not worth the extra hassle of writing code in this more cumbersome way. I would use a regular AoS as the 'default' storage format for systems and only switch to SoA for systems that need the speed of SIMD calculations, such as culling and particles"[8]. He also suggests a middle path: keep the data in AoS and copy it into a temporary SoA buffer for one heavy algorithm. The benchmark has two controls that show when he is right.

Control 1: touch every field

SoA's advantage is entirely "don't fetch what you don't read". If the loop reads every field, there is nothing to skip. The every experiment sums all sixteen fields of every particle (think of a save, a network snapshot, or a checksum). AoS now uses 100% of every line it fetches, and so does SoA. The model in the bytes figure above says all four layouts tie at 64 bytes per particle.

AoS narrows the gap. In Rust it shrinks from the update's ratio to about 2.0×, in Odin to about 1.5×, and in Zig SoA is now slower: AoS takes about 0.7× of SoA's time. Why is SoA still up to twice as fast in Rust when the bytes are equal? Probably not bytes but streams: SoA reads sixteen arrays at once, each needing its own prefetch stream and its own TLB entries, while AoS reads one. And in Zig, where MultiArrayList places the sixteen columns at exact multiples of 4 KiB, the next section's problem also applies.

Control 2: random whole records

The second control is the access pattern SoA is worst at: look up a particle by index, read the whole record, move on to an unrelated index. Think of "the particle the player clicked on", or a join from another table. AoS fetches one line per record. SoA fetches sixteen, one from each column, and none of them helps the next lookup.

SoA is about 6× slower than AoS in Rust, about 11× in Zig and about 6× in Odin. It is not 16×, because the CPU can have several cache misses in flight at once (memory-level parallelism, Chapter 2): the sixteen loads of one SoA record are independent, so they overlap. The random lookup is the one place where the AoSoA tiles earn their awkward indexing. A record's sixteen 4-byte fields sit in eight adjacent lines of one 512-byte block, so random reads cost about 1.6× AoS's time in Rust, about 1.9× in Odin and about 3.6× in Zig, instead of 6× or more. Hot/cold costs two or three lines per record (2.75 on average): it takes about 1.2× AoS's time in Rust and about 1.2× in Odin, but about 1.8× in Zig, whose AoS lookup is the fastest of the three.

So the honest summary is not "SoA is faster". It is: SoA is faster for loops that read a few fields of many records, much less ahead (or behind) for loops that read all fields, and much slower for code that reads whole records at random. Most programs have all three kinds of access. The layout should follow whichever one dominates the time.

Page-aligned columns fight over cache sets

There is one more way SoA can hurt, and it is about addresses rather than bytes. A cache is not one big bag of lines. Each address can only go into one set, picked by a few address bits, and each set holds a fixed number of lines (the ways). On this orb the L1 data cache is 48 KiB, 12-way, with 64 sets of 64-byte lines (from /sys/devices/system/cpu/cpu0/cache/index0/). The set index is address bits 6 to 11:

Now look at where SoA columns start. MultiArrayList and #soa put the columns back to back, each capacity × 4 bytes long. With a power-of-two capacity, every column starts a multiple of 4 KiB after the first, so px[i] … group[i] all map to the same L1 set. (L1 is indexed by bits inside the 4 KiB page, so this is guaranteed; whether they also collide in L2 depends on which physical pages the kernel handed out.) A loop that reads all sixteen columns row by row needs sixteen lines in one 12-way set, so lines get evicted while the loop still needs them. Hand-written Rust SoA is no safer: each large Vec is its own mmap, and the program prints that px, vx and size all start at offset 16 within their pages.

Gray describes the same trap with VM-allocated SoA arrays: "all of the 10 fields of a particle's struct will map to the same cache block. If our cache is 8-way set associative this means that all the fields of the particle can't be in the cache at the same time. Oops!"[8] His fix is AoSoA in groups of 8. The cheaper fix, when you control the allocation, is to stagger the columns. The benchmark's alias experiment does exactly that: one buffer, sixteen u32 columns, read row by row, once with column k at k × n and once at k × (n + 16), which shifts each column by one more cache line. Same data, same loop, same checksum:

fn sum_columns(cols: &[&[u32]; COLS]) -> u64 {
    let n = cols[0].len();
    let cols = cols.map(|c| &c[..n]); // equal lengths: no bounds checks in the loop
    let mut total = 0u64;
    for i in 0..n {
        total = total.wrapping_add(cols.iter().map(|c| c[i] as u64).sum::<u64>());
    }
    total
}

/// Column k starts at k * stride elements. stride = n (n a power of two): every column start is a
/// multiple of 4 KiB from the first, so element i of all 16 columns maps to the same L1 set.
fn columns(buf: &[u32], n: usize, stride: usize) -> [&[u32]; COLS] {
    std::array::from_fn(|k| &buf[k * stride..k * stride + n])
}
fn sumColumns(cols: *const [cols_n][]const u32) u64 {
    var total: u64 = 0;
    for (0..cols[0].len) |i| {
        var s: u64 = 0;
        inline for (cols) |c| s += c[i];
        total +%= s;
    }
    return total;
}
sum_columns :: proc(cols: ^[COLS][]u32) -> (total: u64) {
    n := len(cols[0])
    for i in 0 ..< n {
        s: u64
        #unroll for k in 0 ..< COLS {
            s += u64(cols[k][i])
        }
        total += s
    }
    return
}

The staggered columns win by about 1.3× in Rust, about 1.2× in Zig and about 1.2× in Odin, and by 1.1× to 1.3× at every size we ran: modest next to the 4× from layout, and without counters we cannot say how much is L1 conflict misses and how much L2 or prefetcher behaviour. (Odin is slower overall, probably because -o:speed keeps bounds checks on the sixteen column reads; we did not check the assembly.) It is the kind of effect that makes a benchmark jump when N changes from 1,000,000 to 1,048,576. If an SoA loop reads many columns at once, keep the count well below the associativity (hot/cold, or AoSoA) or pad the allocation. Odin's runtime source gives the same advice in a comment on its SoA allocation code: with a power-of-two capacity of 1,024 or more, same-size fields map to one L1 set, so pad the capacity[7].

Caveats

  • No hardware counters here. The explanations for AoSoA's skipping cost and the aliasing effect fit the data, but we could not confirm them with perf. On your machine, compare the layouts with perf stat -e cycles,L1-dcache-load-misses,LLC-load-misses.
  • One CPU. Apple's M-series uses 128-byte lines (Chapter 2), which makes AoS waste worse for small hot sets, and other prefetchers will treat the AoSoA skip pattern differently.
  • The update is the friendliest case for SoA: three multiply-adds per particle and no branches. Real systems mix loops that want different layouts, and you pay for each conversion between them.

Lay data out for the loops that dominate the time: SoA or hot/cold when a hot loop reads a few fields of many records, AoS when code reads whole records or every field, AoSoA when you need both SIMD and locality, and in every case measure, because a layout that halves the bytes can lose to prefetchers, bounds checks, a disabled vectorizer or four kilobytes of bad luck.

Exercises

A loop reads pos and age of the chapter's particle and writes age. How many bytes per particle does each layout move (reads plus write-backs), in a long sequential loop?

Used: 16 B (12 + 4). AoS: 64 read + 64 written back = 128 B. Hot/cold as defined (age is cold): 24 B hot + 40 B cold read, and 40 B written back because age is cold, so 104 B. SoA: 16 B read + 4 B written back = 20 B. AoSoA: px/py, pz/vx and age/mass share lines, so 3 of 8 lines per block, 24 B read plus 8 B written back (only the age line is dirty) = 32 B. Hot/cold is only as good as the split; moving age into Hot fixes it. Check it in the bytes figure (the figure's write toggle only covers pos).

Why does the random-record control get worse for SoA as N grows, while AoS stays at about one line per record?

At 16K particles everything is in L2, so SoA's sixteen loads per record are L2 hits plus the gather overhead. At 4M particles each of the sixteen columns is 16 MiB, so each load is a likely L3 or DRAM miss and also a TLB miss with 4 KiB pages (16 columns × 16 MiB is far beyond the second-level TLB's reach). AoS needs one line and one page per record. Memory-level parallelism hides part of the sixteen misses, which is why the measured factor is about 6× in Rust, about 6× in Odin and about 11× in Zig, not 16×.

Zig's MultiArrayList sorts columns by alignment. Give a struct where that sorting changes the column order, and say whether it matters for the aliasing problem.

For example struct { a: u8, b: u64, c: u32 }: the columns go b (align 8), c (4), a (1). It removes padding between columns but does not help aliasing: with a power-of-two capacity every column's size (8n, 4n, n bytes) is still a multiple of 4 KiB once n ≥ 4,096, so every column start still lines up modulo 4 KiB.

Write the Odin hot/cold update without soa_zip, using only #soa. What changes in memory?

Declare hc: #soa[]struct { hot: Hot, cold: Cold } and allocate it with make; the loop is the same. In memory there is now one allocation, the hot column followed by the cold column (like Zig's), instead of two allocations glued by a view. soa_zip is for arrays that already exist, for example ones that come from different systems.

The update's model says AoS moves 3.56× the bytes of SoA, yet the measured ratio in Rust is about 4.2×. Give two reasons the measured ratio can exceed the byte ratio.

(1) The two loops need not reach the same bandwidth: if the scalar AoS loop reaches slightly less of it than the vectorized SoA loop, the time ratio exceeds the byte ratio. (2) AoS dirties every line it reads, and a mix of reads and write-backs can cost more than its byte count suggests. Without counters both stay hypotheses; perf stat would let you compare bytes per cycle.

Gray suggests keeping data as AoS and converting to a temporary SoA for one algorithm. For the update loop at 4M particles, would that pay off?

No. Converting reads all of AoS (256 MiB) and writes a pos/vel copy (96 MiB); the update then reads and writes the copy, and copying pos back rewrites the AoS lines (another 256 MiB in and out). That is more than the plain AoS update's 512 MiB. The trick pays when the algorithm makes many passes over the data, or does enough arithmetic per byte that SIMD matters.
