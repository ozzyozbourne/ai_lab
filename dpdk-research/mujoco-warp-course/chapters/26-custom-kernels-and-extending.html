    Part VI · Chapter 26

    Writing Custom Kernels and Extending MJWarp

    So far you have used MJWarp as a black box: put data in, call mjw.step, read results out. This chapter opens the box from the outside. You will write your own Warp kernels that read and write mjw.Model and mjw.Data directly on the device, plug them into the pipeline through the seven callbacks, feed the solver contacts that you computed yourself, specialize kernels with factories and tiles, and test and lint them exactly the way the MJWarp developers do.

    Expert About 100 min· Prerequisites: Ch 4, Ch 24 (Ch 8, Ch 9 and Ch 22 recommended)

    You will learn

    • Write kernels that follow MJWarp's own conventions: # Model: / # Data in: / # In: / # Out: groups, _in/_out suffixes, worldid % shape[0], typed locals, no defaults.
    • Build observation, reward and done kernels and capture them with mjw.step and the auto-reset in one graph.
    • Use the full callback catalogue (control, passive, act_dyn/act_gain/act_bias, sensor with Stage, contactfilter) and their exact contracts.
    • Feed external contacts to the solver with opt.run_collision_detection=False, and know how it differs from DisableBit.CONTACT.
    • Specialize kernels with wp.static factories and cache_kernel, reduce per world with tiles, keep env state in d.userdata.
    • Reuse MJWarp wp.funcs, keep kernels deterministic, test against MuJoCo C and run the kernel analyzer.
    Open in Colab Download notebook

    In Colab: Runtime > Change runtime type > GPU, then run the first cell. Every example also runs on Warp's CPU device with small budgets; that is how the outputs below were recorded (mujoco-warp 4.0.1, warp-lang 1.19.0, CPU). Nothing on this page is a GPU performance number.

    Before you start: recap

    • A kernel runs once per thread index; wp.tid() gives the index, and MJWarp's simplest kernel forward.py::_next_velocity already shows the parameter conventions (Ch 4 §12).
    • A value used through wp.static is a compile-time constant: a new value compiles a new kernel (Ch 4 §7).
    • m.callback.control(m, d) runs inside _forward after the velocity sensors and before actuation; a done kernel plus reset_data(m, d, reset=mask) resets worlds on the device (Ch 8 §9, §10).
    • Contacts of all worlds share one pool of naconmax slots; d.nacon[0] counts the used ones and contact.worldid says whose a slot is (Ch 9 §2).
    • A CUDA graph records launches once and replays them; it remembers array addresses, so allocate before capture and assign, never replace (Ch 24 §3). my_env.capture_step(m, d, nsub, post) records steps plus your kernels (§8).
    • Float atomics sum in arbitrary order, so low bits can change; Ch 4 §9 (Ch 22 §1 has the full treatment).

    1The anatomy of an MJWarp kernel

    Recall from Ch 4

    forward.py::_next_velocity is MJWarp's simplest kernel: worldid, dofid = wp.tid(), a timestep read with opt_timestep[worldid % opt_timestep.shape[0]], and one write per thread into qvel_out; Ch 4 §12.

    An MJWarp kernel is an ordinary Warp kernel with a strict house style. The style is not decoration: it encodes three facts that every kernel touching mjw.Model or mjw.Data must respect.

    1. Everything is batched over worlds. Data fields have shape (nworld, ...), so thread worldid reads row worldid. Model fields whose first dimension is "*" in types.py have either one row (shared) or nworld rows (per-world domain randomization, Ch 10), so they are read with worldid % field.shape[0].
    2. Kernels only see arrays and plain values. You cannot pass m or d to a kernel; you unpack the fields you need and pass them one by one in the launch. The parameter names say where each one came from: Model fields keep their name, Data fields get _in or _out.
    3. Reads and writes are explicit. A parameter that a kernel writes ends in _out and sits at the end. Everything else is read-only. This is what makes it safe to capture kernels into a graph and to reason about which stage owns which field.

    Figure 1 is the reward kernel you will add to my_env.py in Example 26.1, annotated with the rules. Hover, tap or tab through the numbered badges.

    The rules come from two places in the repository. CONTRIBUTING.md states them in prose ("_in for inputs, _out for outputs, matching Model/Data field order"; hoist global reads into locals before loops; precompute reciprocals; do not guard a launch with if n > 0 when n is already the launch dimension, because launching with dimension 0 is a safe no-op; parenthesize bitwise expressions; quaternions are (w, x, y, z); no .numpy() inside a simulation step). The kernel analyzer in contrib/kernel_analyzer turns them into machine checks. The table maps each rule to the analyzer's issue class (from ast_analyzer.py at commit 8f5b9f1).

    Tip: name things after the fields

    The analyzer recognizes a parameter as a Model or Data field purely by its name (minus _in/_out). If you call your buffer reward_out, it is "other"; if you call a parameter qpos_in, it must have exactly the type of Data.qpos. Contact and constraint fields are prefixed: contact_dist_out is d.contact.dist, efc_force_in is d.efc.force.

    2RL-style kernels: reward, observation and done, in one graph

    A reinforcement-learning environment needs four things per step and per world: a physics step, an observation vector, a reward number and a done flag (plus a reset for the worlds that are done). On a GPU with thousands of worlds, the only fast way to do this is to compute all four on the device, in kernels with one thread per world, and to capture them together with mjw.step into one CUDA graph. Python then issues one wp.capture_launch per control step and never touches the data.

    Three rules make such kernels graph-safe:

    • Preallocate every output (reward, total, obs, done) before capture. Temporaries inside the captured function are fine: mjw.step itself allocates some during capture (on CUDA this needs the mempool, which Warp enables at init where the device supports it; on CPU it always works). But arrays that Python reads, resets or passes in must exist before capture, because the graph keeps writing the memory it captured: a new array created eagerly, or an attribute replaced after capture, is never seen by the graph.
    • Change inputs by contents, not by object: d.ctrl.assign(...), .zero_(), wp.copy, or a kernel. Never d.ctrl = wp.array(...).
    • No host reads inside: .numpy() forces a device-to-host sync and cannot be captured on CUDA. Read results after the loop, or in a separate diagnostic pass.

    Example 26.1: a reward kernel and an accumulator in the step graph

    The double pendulum (shared model M2) gets a different constant shoulder torque in every world. The reward is the negative distance from the tip site to a target point plus a small control cost, times the timestep, and accumulate sums it into an episode return. Both kernels are recorded after mjw.step by my_env.capture_step(m, d, nsub=1, post=post) from Ch 24.

    Read the output carefully. After capture, total is still zero: capturing records the launches, it does not run them. After 200 replays every world has its own return, and the last reward matches a NumPy recomputation from d.site_xpos to float32 rounding. Figure 2 replays the same rollout from the script's --dump-json output: every panel is one world (one thread of the reward kernel), the dashed arrow is the distance the kernel measures, and the bar under each panel is the value the thread drops into reward[worldid].

    Example 26.2: an observation kernel and a counter in d.userdata

    An observation kernel packs selected state into a dense (nworld, nobs) buffer that a policy network can read without copies (Ch 28 shares it with PyTorch). The layout is decided once on the host: my_env.obs_columns(mjm, ["v1", "tip_pos"]) uses sensor_slices from Ch 14 to turn sensor names into d.sensordata column indices and uploads them as an int array. The kernel then launches with dim=(nworld, nobs), one thread per entry, and each thread decides from its index k whether it copies from qpos, qvel or the sensor columns. The same example also keeps two numbers per world in d.userdata, MuJoCo's free per-world scratch space (§9 covers it fully).

    The kernel and the NumPy concatenation agree exactly (it is a copy, so the difference is 0.0, not just small). The observation of world 0 reads [qpos (2) | qvel (2) | v1 (1) | tip_pos (3)]; v1 is the jointvel sensor of the same joint, so it is qvel[0] taken at the start of the step (-0.3776 vs -0.3712 now; see the pitfall below). It is redundant and one step stale, which is why the example leaves q1 out. In your own environments, choose either the raw state or the sensor, not both.

    Pitfall: the observation buffer is stale until you pack it

    pack_obs reads d.qpos, d.qvel and d.sensordata as they are now. Sensors are computed inside forward, which runs at the start of mjw.step, so after a step they describe the state before the integrator moved it, while qpos and qvel are already the new state. If you need both consistent, pack after a forward (the reset path does one), or build the observation from sensors only.

    Example 26.3: step, done, reset and re-randomize in one graph

    This is the full environment loop of Ch 30 in miniature. The cart-pole (shared model M5, plus <size nuserdata="1"/>) has no controller yet, only a constant push per world, so the pole falls. After every mjw.step the graph runs four more things: count_userdata (steps in this episode), done_kernel (fell, left the rail or timed out), my_env.reset_done (Ch 8: reset_data(m, d, reset=done) then forward) and randomize_pole (a fresh angle from a counter-based random stream for the worlds that were reset), then apply_push writes the push back into d.ctrl. That last launch is needed because reset_data zeroes ctrl, qvel, act, userdata and sensordata and restores qpos to qpos0 for every world it resets, so any action must be written after the reset. The push lives in a device array created before capture, so the graph reads it on every replay.

    Three details are worth copying into your own code. First, reset_data zeroes d.userdata, so the per-episode step counter restarts by itself, while the lifetime episode count lives in the separate reason array that no reset touches. Second, the random stream is seeded with worldid * 100003 + episode, so every world and every episode gets a different angle and a replay of the whole run is reproducible. Third, nothing in env_post branches in Python on device data: the done decision is a bool array, and reset_data applies it as a mask inside its kernels, which is exactly what lets the graph contain it.

    3The callback catalogue: seven sockets in the pipeline

    Recall from Ch 8

    m.callback.control = fn makes MJWarp call fn(m, d) inside every forward, step and step1, after the velocity sensors and before actuation; fn launches a kernel that writes d.ctrl, and a captured graph records that launch like any other (Ch 8 §9).

    Kernels launched after mjw.step (§2) can only see the state between steps. When your code must run between stages of a step, for example to add a force before the solver or to edit contacts before constraints are built, you use a callback. types.py::Callback is a dataclass of seven optional Python functions, stored as m.callback:

    @dataclasses.dataclass
class Callback:
  passive: Callable | None = None        # writes Data.qfrc_passive
  control: Callable | None = None        # writes Data.ctrl
  act_dyn: Callable | None = None        # writes Data.act_dot
  act_gain: Callable | None = None       # writes Data.actuator_force
  act_bias: Callable | None = None       # writes Data.actuator_force
  sensor: Callable | None = None         # writes Data.sensordata, called as sensor(m, d, stage)
  contactfilter: Callable | None = None  # writes Data.contact

    A callback is plain Python, called with (m, d) (or (m, d, stage) for sensor) at a fixed line of the pipeline. It should do nothing but launch kernels: any .numpy() inside it breaks graph capture, and any Python side effect (a counter, a print) runs once per eager call but only once in total when the step is captured.     Pitfall: callbacks are Python, read at call time

    m.callback is consulted with an ordinary Python if every time the stage runs. In eager mode you can switch a callback on and off between steps. Inside a captured graph the decision was made once, at capture: setting m.callback.passive = None after capture does not remove the recorded launches, and setting one after capture does not add them. Recapture after changing callbacks (the Ch 24 knob board rule).

    4Force callbacks: passive and the actuator trio

    Passive forces: add, never overwrite

    passive.py::passive launches several kernels that write d.qfrc_spring, qfrc_damper, qfrc_gravcomp, qfrc_fluid and qfrc_adhesion, then _qfrc_passive_kernel sums them into d.qfrc_passive, and only then calls m.callback.passive(m, d). So when your callback runs, qfrc_passive already holds everything MuJoCo computed, and your kernel must use +=. Writing = would silently delete every joint damper and spring in the model.

    The force is in generalized coordinates (one entry per DOF). For a free joint the first three DOFs are the linear velocity of the body in the world frame, so a world-frame force on the body's centre maps directly onto qfrc_passive[worldid, dofadr + 0..2]. For anything else (a force at a point, on a hinge chain) you would multiply by the Jacobian transpose, as support.py::xfrc_accumulate (through apply_ft) does for xfrc_applied.

    Example 26.4 adds quadratic air drag F = -c\,\lVert v\rVert\, v to a falling ball, with a different c per world. Drag balances gravity at the terminal speed v_t = \sqrt{m g / c}.

    The three heavier-drag worlds sit exactly at their terminal speed after 2.5 s; the lightest one (c = 0.25, v_t = 6.26 m/s) is still 0.08% short, because its time constant v_t / g is the longest. The callback ran once per step, and in qfrc_passive[:, 2] you can read the drag force balancing m g = 9.81 N.

    Actuator callbacks run after the force kernel

    The three actuator callbacks are the easiest to misuse, because their position in fwd_actuation is not where MuJoCo C calls its mjcb_act_* function pointers. Figure 6 shows the order in the 4.0.1 wheel. The _actuator_force kernel does everything at once: it reads (and clamps) ctrl, computes act_dot, evaluates \text{force} = \text{gain}\cdot\text{ctrl} + \text{bias} and clamps it to forcerange, and writes d.act_dot and d.actuator_force. Only then does Python call act_dyn, act_gain and act_bias, which write those same arrays: act_dyn and act_gain typically overwrite them, while act_bias runs last and should add to d.actuator_force (an assignment there would discard the act_gain result).

    The consequence for a gaintype="user" actuator follows directly from the source comment "GainType.USER: gain stays 0, modified by act_gain_callback": the kernel computes 0 \cdot \text{ctrl} + 0, clamps that zero to the force range, and your act_gain callback is expected to write the final force. It is not "a gain" in the MuJoCo C sense, where mjcb_act_gain returns a gain that MuJoCo multiplies by ctrl and then clamps. Example 26.5 shows both behaviours side by side.

    With forcerange="-1 1", MJWarp happily applies 6.9 N·m because the callback runs after the clamp, while C MuJoCo clamps the same computation to ±1. If you want the limit, apply it yourself inside the callback kernel (read m.actuator_forcerange[worldid % shape[0], uid]). Play with the widget to see where the two paths diverge.

    Pitfall: the callback sees the raw ctrl

    The _actuator_force kernel clamps ctrl into a local variable; d.ctrl itself is not modified. A callback that reads d.ctrl therefore sees the unclamped value (Example 26.5 reads it raw). Clamp with m.actuator_ctrlrange in your kernel if your formula needs it, and remember that with actuator delays (Ch 14) the kernel used the delayed ctrl, not d.ctrl.

    5Sensor and contact-filter callbacks

    User sensors and Stage

    A <user> sensor reserves dim slots in d.sensordata and declares the stage it needs (needstage="pos", "vel" or "acc"). MuJoCo does not know how to compute it; that is your callback's job. MJWarp calls m.callback.sensor(m, d, stage) at the end of each of the three sensor stages with stage equal to Stage.POS, Stage.VEL or Stage.ACC (an IntEnum whose values are mujoco.mjtStage: 1, 2, 3). Stage is not exported by mujoco_warp; import it from mujoco_warp._src.types private API. Note that d.sensordata.zero_() runs at the start of each forward, so a sensor you fill at the POS stage keeps its value through VEL and ACC.

    Your sensor's slots are found with mjm.sensor_adr[uid], exactly like a built-in one, so my_env.sensor_slices and the observation kernel of §2 pick it up without changes. The user sensor is written after history.apply_sensor_delay for that stage, so MuJoCo's sensor delay/interval/cutoff machinery (Ch 14) does not touch it.

    Dropping contacts: clear a bit, keep the slot

    The contact pool is append-only during a collision pass: narrowphase threads reserve slots with wp.atomic_add on d.nacon (Ch 9), and nothing ever compacts it. A filter therefore cannot delete a contact. What it can do is change the contact's type bits (types.ContactType: CONSTRAINT = 1, SENSOR = 2, PASSIVE = 4). Every constraint-building kernel in constraint.py starts with

        if not (type_in[conid] & ContactType.CONSTRAINT):
      return

    so a contact without the CONSTRAINT bit gets no efc rows and produces no force, while contact sensors (SENSOR) can still see it. The filter kernel is launched over d.naconmax, the pool capacity, and threads past nacon return immediately: the same launch pattern MJWarp uses for its own contact kernels (atlas layout 2 of Ch 7), and the only one that works inside a graph, where the host cannot read nacon.

    Note: when the filter runs, and how often

    It runs inside collision, so not at all when collision is skipped (next section). With sleep enabled (Ch 21), fwd_position runs two collision passes, and the filter is called twice per forward; determinism_test.py::test_hooks asserts exactly that count. Filters should therefore be idempotent: clearing a bit twice is fine, toggling it is not.

    6User-populated contacts: run_collision_detection=False

    Sometimes you already know the contacts: a tactile-sensor model, a terrain query from another engine, a learned contact model, or a scene where collision detection is simply too expensive and the geometry is trivial. m.opt.run_collision_detection is a Warp-only Option field (default True) for exactly this. Its docstring in types.py: "if False, skips collision detection and allows user-populated contacts during the physics step (as opposed to DisableBit.CONTACT which explicitly zeros out the contacts at each step)". In forward.py::fwd_position the whole call to collision_driver.collision sits under if m.opt.run_collision_detection:, and constraint.make_constraint runs right after it either way. So whatever you wrote into d.contact.* and d.nacon is what the solver gets.

    Which fields must a user contact contain? Read the consumers: the constraint builder uses dist and includemargin (active when dist - includemargin < 0), dim (condim), geom (to find the two bodies and their DOFs for the Jacobian), worldid, type, pos and frame (rows: normal from geom[0] to geom[1], then two tangents), friction (5 entries: tangent 1, tangent 2, spin, roll 1, roll 2), solref, solreffriction ((0, 0) means "use solref") and solimp. efc_address is an output of make_constraint: do not write it. Also write adhesion when the model has adhesion actuators (m.flg_adhesion), and surfacevel when geoms have surface velocity (m.flg_surfacevel). Collision normally fills both, but with run_collision_detection=False nothing does.

    Never write flex, elem or vert without flexes

    d.contact.flex, elem and vert are allocated with shape (0,) when m.nflex == 0 (Example 26.8 prints it). Writing to them is an out-of-bounds write: on Warp's CPU device it segfaulted the process (exit 139) in the course's tests, and on a GPU it silently corrupts whatever memory lies there. While you develop a kernel like this, set wp.config.mode = "debug" before the first launch: Warp then compiles bounds checks into every array access.

    The user contact reproduces MuJoCo C's own sphere-plane contact to 10^{-6}: four pyramid rows of 2.9549 N, whose sum (11.82 N) is the normal force needed to push the 1 mm penetration back out while holding the 9.81 N weight. After mjw.step, nacon is still 2: nobody cleared the pool. That is the feature (contacts persist) and the trap (the dist you wrote is now stale, because the ball moved). A real user-contact pipeline therefore refills the pool every step, from the current qpos, right before mjw.step, inside the function you capture:

    def step_with_contacts(m, d):     # capture this function (Ch 24), not mjw.step alone
    fill(m, d, mjm)               # Example 26.8's kernel: contacts from the current qpos
    mjw.step(m, d)                # forward skips collision and solves with them

    An equivalent layout launches fill as the post hook of each replay: after the integrator, qpos already holds the state the next step starts from, so the contacts are the right ones for that step. The only difference is the very first step, which then needs one eager fill before the first replay (as Example 26.8 does before its forward).

    Pitfall: contactfilter cannot refill contacts

    m.callback.contactfilter is called from inside collision_driver.collision, so it is never called when m.opt.run_collision_detection = False. With user contacts, the filter never runs; refill the pool with your own launch as above.

    7Specialization: factories, wp.static and cache_kernel

    MJWarp compiles many variants of the same kernel: one for sparse and one for dense Jacobians, one per tile size, one with sleep and one without, one deterministic and one not. It never branches on those choices at run time. Instead it writes a kernel factory: a Python function that takes the compile-time parameters and returns a freshly defined kernel, inside which wp.static(expr) evaluates expr during compilation. A for _ in range(wp.static(n)) loop is unrolled, and an if wp.static(flag): branch disappears entirely from the variant that does not need it.

    Defining a kernel is expensive (a new Warp module, a compile, a cache lookup), and doing it while a graph is being captured with conditional nodes crashes. So every factory is wrapped in warp_util.cache_kernel private API, whose source comment says why: "caching kernels to avoid crashes in graph_conditional code". The whole implementation:

    _KERNEL_CACHE = {}

def cache_kernel(func):
  # caching kernels to avoid crashes in graph_conditional code
  @functools.wraps(func)
  def wrapper(*args):
    def _hash_arg(a):
      if hasattr(a, "size"):
        return a.size
      if isinstance(a, list):
        return hash(tuple(a))
      return hash(a)

    key = tuple(_hash_arg(a) for a in args) + (func.__module__, func.__name__)
    if key not in _KERNEL_CACHE:
      _KERNEL_CACHE[key] = func(*args)
    return _KERNEL_CACHE[key]

  return wrapper

    Four key rules fall out of these twelve lines, and each one is a bug waiting in your own factories:

    1. Positional only. wrapper(*args) has no **kwargs: a keyword call raises TypeError. (A factory parameter with a default, like _tendon_armature(nv, deterministic=False), is fine as long as callers pass it positionally.)
    2. Anything with .size is keyed by its size. That is how a TileSet (whose size is the tile size) selects a tile kernel. But it also means two different arrays of the same length give the same key: never bake array contents into a cached factory.
    3. hash() equality is key equality. hash(1) == hash(True) == hash(1.0), so make(2, 1) and make(2, True) share a kernel. Harmless for bools and ints, surprising for floats you meant to distinguish from ints.
    4. The function's module and name are part of the key, so two factories never collide, and a factory redefined in a notebook cell under the same name in __main__ returns the old kernels until you restart the runtime (or _KERNEL_CACHE.clear()).

    Two decorator options always go with factories: module="unique" gives each specialization its own Warp module (the analyzer requires it for nested kernels, MissingModuleUnique, and module options such as deterministic are per module), and enable_backward=False skips generating adjoint code that MJWarp never uses (Ch 29 explains what that means for wp.Tape).

    Look at the make_offset line: the second call asked for an offset of 100, got the cached kernel that adds 10, and nothing warned. The fix is to pass such values as kernel arguments (they are cheap) or to key the factory on the scalar itself (make_offset(float(table[0]))). The final count is 4 because (2, 1) created a fourth key that (2, True) then hit.

    Going deeper: how MJWarp passes a flag into a factory

    forward.py::_qfrc_smooth(enable_sleep) is a typical factory: the call site computes a Python bool from m.opt.enableflags, passes it positionally, and the kernel tests if wp.static(enable_sleep):. Changing m.opt.enableflags therefore selects a different cached kernel on the next eager call, and in a graph only after recapture. determinism_test.py even asserts cache keys directly, e.g. (hash(False), "mujoco_warp._src.smooth", "_transmission"). The same mechanism explains Ch 24's knob board: options read through wp.static recompile, options read as kernel arguments stay live.

    8Tiles: a block of threads per world

    Every kernel so far gave each thread its own little job. Some jobs are naturally shared: summing all the contact forces of a world, factorizing a world's mass-matrix block, reducing a world's constraint rows. With one thread per world, that thread walks the whole list alone. With one thread per element, the results must be combined with atomics (nondeterministic for floats, §11). Tiles are Warp's third option: a tile is a small array that all threads of one block hold together, and tile operations (load, sum, matrix multiply, Cholesky) are cooperative: every thread of the block must reach the call, and the block does the work together.

    • wp.launch_tiled(kernel, dim=nworld, block_dim=B) launches nworld blocks of B threads; inside, worldid, lane = wp.tid() and wp.block_dim() is B. This is atlas layout 6 of Ch 7 (block per world).
    • wp.tile_load(a, shape=N, offset=...) copies N elements of a global array into a tile; N must be a compile-time constant, which is why tile kernels are factories (make_gather_sum(k) in Example 26.10, smooth.py::_tile_cholesky_factorize_block(tile) keyed by TileSet.size). Out-of-range elements read as zero with the default bounds_check=True.
    • wp.tile(x) builds a tile from one per-thread value (shape (block_dim,)), the bridge from scalar code to cooperative code.
    • wp.tile_sum(t) reduces a tile to a one-element tile; wp.tile_store(a, t, offset=...) writes a tile back.
    • wp.tile_load_indexed(a, idx, shape=...) gathers a[idx[k]] through a tile of indices; an index past the end (or negative) reads as zero. _tile_cholesky_factorize_block uses it to gather a dense diagonal block of M out of its CSR storage, with absent entries pointing out of bounds (Ch 11).

    One block sums one world's contact forces

    ex10_tile_contact_force.py::world_normal_forceIllustrative values, 32 lanes
    worldid, lane = wp.tid()
partial = float(0.0)
for cid in range(lane, nacon_in[0], wp.block_dim()):
    if contact_worldid_in[cid] == worldid:
        partial += force_in[cid][0]
s = wp.tile_sum(wp.tile(partial))
wp.tile_store(total_out, s, offset=worldid)

    On a GPU the 32 lanes in the stepper are one warp, and the strided loop gives coalesced reads: lane k reads contact k, k+32, ... On Warp's CPU device a block has exactly one lane (wp.block_dim() is 1, as a comment in solver.py notes), so the same kernel degrades into one thread per world that walks the whole pool. That is why tile kernels run unchanged on CPU, and why their CPU speed tells you nothing about the GPU.

    Coalescing is not the whole cost, though. Per-world tile reductions suit data already laid out per world (efc rows, qpos, blocks of M). For the shared contact pool, every world's block scans all nacon slots, so the total work is O(nworld × nacon). One thread per contact writing to per-world outputs (handled deterministically, as in §11), or per-world contact ranges, scale better. This is reasoning from the loop structure, not a measurement.

    All three reductions agree with NumPy, and the physics checks out: a resting stack of three 8 kg boxes puts (3 + 2 + 1)\,m g = 470.88 N of normal force through its contacts, scaled by each world's mass factor. The efc.force row sum equals the same number because, for the pyramidal cone, the normal force of a contact is the sum of its pyramid-row forces (Ch 9), and the stack has no other constraints. The kernel sums only rows i < nefc[w]: MJWarp does not clear efc rows past nefc, so they keep stale values from earlier steps, and a whole-row tile_load of njmax entries is only safe after masking. (Here nefc stays 48 every step, so the unmasked sum would happen to agree; in a scene where contacts come and go it would not.) The tile_load_indexed sum gathers columns 2, 9 and 16 of qpos: the z coordinates of the three free joints.

    Pitfall: every lane must reach every tile call

    A tile operation is a collective. If some lanes return early or skip a tile_* call inside a divergent if, the block deadlocks on a GPU (and runs fine on CPU, where there is one lane). Put the per-lane work in ordinary scalar code (the strided loop), and call tile functions unconditionally. MJWarp's own solver kernels use a "uniform trip count" for exactly this reason (comment in solver.py: "a divergent range(rank, nC, bd) deadlocks").

    9Per-world custom state: d.userdata

    Your environment needs state that MuJoCo does not have: an episode step counter, a goal position, the last action, a running maximum. You can keep it in your own wp.arrays, and for things that must survive resets you should. But MuJoCo also has a built-in place for it. <size nuserdata="N"/> in the MJCF gives every world N free floats: m.nuserdata == N and d.userdata has shape (nworld, nuserdata). Nothing in the physics reads or writes it, but the library treats it as state:

    • reset_data zeroes it (the for i in range(nuserdata): userdata_out[worldid, i] = 0.0 loop in io.py), with or without a per-world mask. Good for per-episode values; wrong for lifetime counters.
    • mjw.State.USERDATA is a state component (size nuserdata), so get_state/set_state snapshots include it when you ask for it. Note it is part of State.USER (with ctrl, applied forces, mocap and eq_active), not of State.PHYSICS; Ch 8's snapshot(m, d, mjm, sig) takes the signature you need.
    • get_data_into copies it to MjData.userdata, so a world exported for debugging in C MuJoCo keeps your values.

    Tip: what to put where

    Per-episode values that should start at zero after a reset (step counters, accumulated reward of this episode, a "goal reached" latch) fit d.userdata perfectly, and they travel with snapshots, so MPC rollouts (Ch 29) restore them too. Values that must survive resets (lifetime episode count, RNG episode id, statistics) go in your own arrays, like reason in Example 26.3. Values that change the physics (a per-world target that a passive force pulls toward) can live in either; userdata is convenient because any kernel that already gets d's fields can read it.

    10Reusing MJWarp internals, and testing your kernels like MJWarp does

    Most of MJWarp's math is written as @wp.funcs, device functions that any kernel can call: in math.py (quat_to_mat, rot_vec_quat, mul_quat, axis_angle_to_quat, quat_integrate, quat_sub, make_frame, eig3, ...), in collision_primitive_core.py (pure colliders such as plane_sphere, sphere_sphere, capsule_capsule, that return distances, points and normals as values, without touching the contact pool), and in util_misc.py (muscle and DC-motor curves, wrapping). Importing them saves you from re-deriving MuJoCo's conventions, in particular the (w, x, y, z) quaternion order that differs from wp.quat's own (Ch 4).

    Pitfall: private API

    Everything under mujoco_warp._src is internal. Names and signatures can change in any release without notice (several did between the 4.0.1 wheel and the dev tree, see the plan's dev-only list). Pin your version, import from _src in one module of your own, and cover every reused function with a test like the one below, so an upgrade fails loudly instead of silently.

    MJWarp's tests follow fixed conventions (CONTRIBUTING.md, "Writing Tests"), and they are good conventions for your kernels too:

    • Build the scene with mujoco_warp.test_data.fixture(xml="""..."""), which ships in the wheel and returns (mjm, mjd, m, d) with C MuJoCo's state already in d (it seeds NumPy with 42, applies optional noise, steps C MuJoCo 10 times when noise is used, calls mj_forward, and builds m/d with put_model/put_data).
    • Pre-fill the outputs you test with wp.inf (floats) or -1 (ints), so a kernel that forgot to write an element fails the comparison instead of passing on stale values.
    • Parameterize over nworld 1 and 2; with 2 worlds, perturb world 1, compute a per-world C reference, and assert that the two worlds' outputs differ (otherwise a kernel that always reads row 0 passes).
    • Compare with the matching mujoco.mj_* / mju_* function at rtol=1e-5, atol=1e-5 (float32 on the device vs float64 in C).

    The test runs twice through absl.testing.parameterized (the library MJWarp's own tests use). With two worlds, world 1's ball and box have new orientations and the arm a new hinge angle, so its tilts differ from world 0's, and the assertion that they differ guards against a worldid bug. The kernel calls quat_to_mat exactly like a NumPy function, but it is compiled into the kernel: there is no call overhead on the device.

    11Determinism in your own kernels

    Recall from Ch 22

    Float atomics sum in arbitrary order, so low bits can change; MJWarp's m.opt.deterministic bitmask has three bits (CONTACTS, CONSTRAINT, ATOMICS), but in the 4.0.1 wheel only ATOMICS changes any kernel: the CONTACTS and CONSTRAINT sorts are stubs (Ch 22 §3).

    m.opt.deterministic covers MJWarp's kernels, not yours. A custom kernel decides for itself. Three patterns, from best to worst:

    1. One writer per output element (every kernel in §2, §4, §5): thread worldid computes reward_out[worldid] by itself, in a fixed loop order. Deterministic by construction, no cost.
    2. Block reductions with tiles (§8): the reduction happens inside the block without float atomics. Note, however, that world_normal_force sums the pool in slot order, and the contact slot order itself can change from run to run on a GPU. In the 4.0.1 wheel, DeterminismType.CONTACTS and CONSTRAINT are accepted but do nothing: collision_driver._sort_contacts and constraint._sort_constraints are pass stubs, so the slot order is not canonical (Ch 22 §3). If your reduction must be bit-reproducible, sort or key the contacts yourself (for example by geom pair) before you sum.
    3. Float atomics (wp.atomic_add on a float into a shared accumulator): fast and nondeterministic in the last bits. If you need them, do what MJWarp does: make the kernel a factory with a deterministic argument and set Warp's module option module_options["deterministic"] = wp.DeterministicMode.RUN_TO_RUN (and "deterministic_max_records" for atomics inside loops), as smooth.py::_tendon_armature(nv, deterministic) does. The analyzer enforces this pattern (MissingDeterministicFactory).

    Integer atomics are a special case: integer addition is associative, so wp.atomic_add on an int counter always gives the same total (only which thread got which slot can vary). MJWarp marks such lines with # kernel_analyzer: ignore[atomic], for example the efc-row allocation wp.atomic_add(nefc_out, worldid, ndim) in constraint.py. Exercise 26.1 uses one.

    Version note

    The development tree at commit 8f5b9f1 implements both sorts: collision_driver.collision calls sort.contacts(d) when m.opt.deterministic & DeterminismType.CONTACTS is set, and constraint.make_constraint calls sort.constraints(m, d, efc_nnz) for CONSTRAINT. Once a release ships them, setting CONTACTS makes the slot order of pattern 2 canonical. With the 4.0.1 wheel it does not.

    12The kernel analyzer and the contributing workflow

    contrib/kernel_analyzer is a small static checker that parses Python files with ast, finds every @wp.kernel and @wp.func, and checks them against the field names and types it reads from types.py. It ships three ways: a CLI (kernel_analyzer/cli.py, used in pre-commit and GitHub CI with --output=github), a language server (lsp_server.py) and a VS Code extension (kernel-analyzer-0.9.0.vsix). It is not in the pip wheel, so you need a clone of the repository. The CLI takes file paths, a --types path to types.py, and --check_atomic (on by default); it prints one file:line:message per issue to stderr and exits with 1 if it found any.

    Point --types at the installed wheel's types.py (mujoco_warp._src.types.__file__) so your kernels are checked against the field names and types of the version you actually run. Lines can opt out: a bare # kernel_analyzer: ignore on a line, or an off/on block, suppresses every issue there. The bracketed form is only honoured for the determinism and atomic checks (ignore[atomic]); any other rule name, such as ignore[InvalidWrite], is ignored at this commit (ast_analyzer.py::_is_ignored); CONTRIBUTING.md asks for a comment explaining why whenever you do.

    Note: the contributing workflow, in short

    From CONTRIBUTING.md: develop with uv sync --all-extras and uv run; run single tests with uv run pytest path/to/test.py -k name and the suite with uv run pytest -n 8 before a PR; run uv run pre-commit run --all-files, which includes the kernel analyzer; add a test that fails before your change and passes after it (with the fixture conventions of §10); include before/after throughput numbers with identical nworld and zero overflow for hot-path changes; sign the CLA. The file also says not to add AI assistants as commit co-authors.

    Version note

    The analyzer is versioned with the repository, not with the wheel. The listing above is for commit 8f5b9f1. The notebook clones the tag that matches the installed wheel, v4.0.1 (git clone --depth 1 --branch v4.0.1 ...); its analyzer files are identical to 8f5b9f1 and its types.py matches the installed wheel. If you clone main instead, new issue classes may appear.

    13Check yourself

    Quiz

    A factory is decorated with cache_kernel. You call make(2, 1) and then make(2, True). What happens on the second call?

    The key is (hash(2), hash(True), module, name), and hash(True) == 1. Example 26.9 prints True for this identity.

    You pass a NumPy array of 3 offsets to a cached factory that bakes table[0] into the kernel, first with [10, 0, 0], then with [100, 0, 0]. The second kernel adds...

    _hash_arg returns a.size for objects with a size attribute. Pass values as kernel arguments, or key the factory on the scalar.

    You set m.opt.run_collision_detection = False, fill one contact per world with your kernel, and call mjw.step twice without refilling. In the second step...

    Example 26.8 prints nacon 2 after a step. The flag only skips collision_driver.collision; refill your contacts every step.

    An actuator has gaintype="user" and forcerange="-1 1". Your act_gain callback writes 3.0 into d.actuator_force. Which force reaches qfrc_actuator (gear 1, no joint limits)?

    The callbacks run after the kernel and overwrite its output; only tendon and joint actfrcrange clamps run later (Example 26.5: 6.9091 with forcerange ±1).

    Your contactfilter wants to drop contact slot 5. What is the correct way?

    constraint.py skips every contact with if not (type_in[conid] & ContactType.CONSTRAINT); nacon stays the same (Example 26.7: 16 with and without the filter, nefc 32 → 16).

    How many times is m.callback.sensor called during one mjw.forward (sensors enabled)?

    Example 26.6 prints ['POS', 'VEL', 'ACC']. Check stage and fill your sensor once.

    A passive callback writes qfrc_passive_out[worldid, i] = f[i] (assignment, not +=). The model has joint dampers. What happens?

    m.callback.passive(m, d) is the last line of passive.py::passive; always add.

    What does mjw.reset_data(m, d, reset=mask) do to d.userdata of the masked worlds?

    The reset kernel in io.py loops for i in range(nuserdata): userdata_out[worldid, i] = 0.0. Example 26.2 prints [0, 50, 0, 50] after resetting the even worlds.

    With integrator="RK4", how many times per mjw.step is m.callback.control called?

    Each _forward calls control (unless ACTUATION is disabled). A controller with internal state (a counter, a filter in userdata) must account for this.

    A tile kernel launched with wp.launch_tiled(..., block_dim=64) runs on Warp's CPU device. What is wp.block_dim() inside it?

    Comment in solver.py: "wp.block_dim() is 1 on the CPU backend, so lane 0 then covers every entry". Example 26.10 uses BLOCK = 64 if ON_GPU else 1.

    Stretch

    Show a starting point 
    K, ANCHOR = 50.0, (0.0, 0.0, 0.6)

@wp.kernel
def spring_field(
    # Data in:
    qpos_in: wp.array2d[float],
    qvel_in: wp.array2d[float],
    # In:
    k: float,
    anchor: wp.vec3,
    # Data out:
    qfrc_passive_out: wp.array2d[float],
):
    worldid = wp.tid()
    p = wp.vec3(qpos_in[worldid, 0], qpos_in[worldid, 1], qpos_in[worldid, 2])
    v = wp.vec3(qvel_in[worldid, 0], qvel_in[worldid, 1], qvel_in[worldid, 2])
    f = k * (anchor - p) - 2.0 * wp.sqrt(k) * v          # critically damped for mass 1
    for i in range(3):
        qfrc_passive_out[worldid, i] += f[i]

m.callback.passive = lambda m, d: wp.launch(spring_field, dim=d.nworld,
    inputs=[d.qpos, d.qvel, K, wp.vec3(*ANCHOR)], outputs=[d.qfrc_passive])
for _ in range(1000):
    mjw.step(m, d)
print("rest height:", d.qpos.numpy()[:, 2], "| predicted", f"{ANCHOR[2] - 9.81 / K:.4f}")

    15Summary

    Key takeaways

    • Write kernels in MJWarp's style: grouped parameters, _in/_out, field names and types from types.py, worldid % shape[0] for "*" Model fields, typed locals, no defaults. The kernel analyzer checks all of it.
    • RL environments are kernels with one thread per world, preallocated outputs, no host reads, captured together with mjw.step and the masked reset in one graph (my_env: pack_obs, site_reward, accumulate, count_userdata).
    • Seven callbacks plug into fixed lines: passive adds; act_dyn/act_gain overwrite and act_bias adds after the force kernel, so forcerange is not reapplied; sensor is called at every stage; contactfilter clears the CONSTRAINT bit because nacon cannot shrink.
    • run_collision_detection=False skips collision and keeps your contacts (refill them every step; never touch flex/elem/vert without flexes); DisableBit.CONTACT zeroes them.
    • cache_kernel keys are positional hashes plus module and name; objects with .size are keyed by size. Factories use wp.static, module="unique" and enable_backward=False.
    • Tiles give each world a cooperating block (launch_tiled, tile, tile_load, tile_load_indexed, tile_sum, tile_store); every lane must reach every tile call; on CPU a block is one lane.
    • d.userdata is per-world state that resets to zero and travels in State.USERDATA. Reused _src functions are private: pin, wrap and test them against MuJoCo C with test_data.fixture at 1e-5.

    Stuck? See Troubleshooting or the course map. Next: Ch 27 uses custom kernels over ray results; Ch 28 hands the observation buffer to PyTorch and JAX without copies.
