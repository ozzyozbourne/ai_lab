Chapter 10

Project: Boids with a Spatial Hash

A million birds, each one looking only at the few birds within one wingspan. The obvious program asks every bird about every other bird: a trillion distance checks per step, of which about fourteen million matter. This chapter builds the flock in Rust, Zig and Odin, and makes it fast in the order the earlier chapters taught. First the algorithm, then the layout, then the branches, then the lanes, then the cores. Each step is measured. One step that looks like it should help turns out to be slower, and the chapter explains why.

A flock in three rules

Craig Reynolds' 1987 boids paper gave each simulated bird (a "bird-oid", or boid) three local rules and no global plan[1]. Cohesion: steer toward the average position of your neighbours. Alignment: steer toward their average velocity. Separation: steer away from neighbours that are too close. Flocking emerges from these rules; nobody wrote it down. For this book the interesting part is the word neighbours. Each rule is a sum over the boids within some radius, so every step asks, for every boid, "who is near me?" That question is the whole cost of the simulation.

Our version is a 2D boids step with fixed constants, so all three languages compute exactly the same thing:

  • The neighbour radius is 1.0, so a boid j is a neighbour of i when dx² + dy² < 1. A boid counts as its own neighbour, so the neighbour count is never zero and we never divide by zero.
  • The separation radius is 0.25 (d² < 0.0625).
  • Velocity change: cohesion 0.02 × mean offset, alignment 0.05 × (mean velocity − own velocity), separation 0.5 × the summed push-away. The speed is clamped to 2, the time step is 0.05, and boids bounce off the walls.
  • The world is a square of side × side unit cells with side = round(√(N/4)). Boids start uniformly at random, so there are four boids per cell on average at every N. The density stays fixed while the world grows, which is what makes the problem interesting: the useful work per boid stays constant, and only the wasted work changes.

The random numbers come from SplitMix64, written out by hand in Rust and Odin and taken from std.Random.SplitMix64 in Zig. Each f32 is built from the top 24 bits of a draw, so every starting value is exactly representable and the three programs start from bit-identical states. This matters later, when we check that they also finish in bit-identical states.

The arithmetic of "near"

With four boids per unit area and a radius of 1, the expected number of other boids inside the circle is π × 1² × 4 ≈ 12.6. Add the boid itself and you get 13.6. The program measures 14,217,542 neighbour pairs for 1,048,576 boids, which is 13.56 per boid. That is the useful work. The naive search does N² = 1,099,511,627,776 distance tests to find those 14 million pairs, so it throws away 99.9987% of them. Matthias Müller makes the same point for 100,000 particles: the naive test is 10¹⁰ pairs per step (cited)[2].

A uniform grid with cell size 1 tests each boid against the boids in its own cell and the eight around it. With four boids per cell, how many distance checks per boid should that be, and what fraction of them find a neighbour?

Nine cells × 4 boids ≈ 36 checks per boid. The program counts 36.9 at N = 1M (edge cells have fewer neighbours, and random clumps add a little). 13.56 of them are neighbours, so 37% of the checks are useful, against 0.0013% for naive. A circle of radius 1 has area π; the 3 × 3 block has area 9; π / 9 ≈ 35%. The grid's waste is just the corners of the square that the circle does not cover.

From O(n²) to a uniform grid

The fix is old and simple: cut the world into square cells with the same side as the neighbour radius. Then every neighbour of a boid lies in the boid's own cell or one of the eight cells around it, because a boid more than one cell away is more than one radius away. The question "who is near me?" becomes "who is in these nine cells?" To answer that cheaply we need, for each cell, the list of boids in it.

Set the slider to 2,000 boids. Before you look: about how much bigger is the naive checks counter than the grid one?

In a 16 × 10 world, 2,000 boids are 12.5 per cell, so the grid does about 9 × 12.5 ≈ 110 checks per boid (somewhat fewer at the walls), and naive does 2,000. The ratio is roughly 20×. It is far below the 454× drop in checks the benchmark sees at 16,384 boids, because this world is tiny: the 3 × 3 block covers 9 of 160 cells. The grid wins by the ratio of world area to block area, which is why it gets better as the world grows.

The naive version is the baseline for correctness and nothing else. It loops over every pair, so it is also the most obviously correct code in the file:

fn step_naive(w: World, cur: &Boids, next: &mut Boids) -> u64 {
    let n = cur.n;
    let mut out = next.out();
    let mut total = 0;
    for i in 0..n {
        let mut acc = Acc::default();
        visit_span(&mut acc, cur, 0..n, cur.x[i], cur.y[i]);
        total += acc.n as u64;
        out.set(i, acc.integrate(w, cur.x[i], cur.y[i], cur.vx[i], cur.vy[i]), cur.id[i]);
    }
    total
}

    for i in 0 ..< n {
        acc: Acc
        visit_span(&acc, c, 0, n, c.x[i], c.y[i])
        total += u64(acc.n)

}

Note the shape: it reads cur and writes next. Every variant in this chapter double-buffers the boid state. If we updated boids in place, boid 7 would see boid 3's new position and boid 2's old one, and the result would depend on the loop order. With two buffers, every boid reads the same frozen snapshot, so the order of the outer loop no longer matters. That is what lets us sort it, split it across threads, and still get the same answer. The driver swaps the roles of the buffers between frames (the benchmark reruns one step from the same input, so it keeps them fixed).

The grid as a counting sort

"For each cell, a list of boids" tempts you toward Vec<Vec<u32>>, a HashMap<Cell, Vec<u32>>, or a linked list per cell. All three put a small allocation or a pointer chase behind every cell, and a million-boid world has 262,144 cells. The data-oriented version is three flat arrays, rebuilt from scratch every step in O(n + cells) time with no allocation at all [2][3][8]:

  • cell[i]: the cell of boid i.
  • start[c]: where cell c's boids begin in order. It has cells + 1 entries, so cell c is always start[c] .. start[c+1], the last cell included.
  • order[p]: boid indices, sorted by cell.

Building them is a counting sort in three passes. Count: one pass over the boids increments start[cell]. Prefix sum: one pass over the cells turns counts into running totals. Scatter: one more pass over the boids, back to front, decrements start[cell] and writes the boid into that slot. Going back to front has two benefits. Each start[c] ends exactly at the first slot of its cell, so no second array or shifted copy is needed. And the sort is stable: boids keep their spawn order inside a cell, which makes the result deterministic. Step through it on a small example:

/// `start[c]..start[c + 1]` is the slice of `order` holding the boids of cell c.
struct Grid {
    start: Vec<u32>, // cells + 1 entries
    cell: Vec<u32>,  // cell of each boid
    order: Vec<u32>, // boid indices sorted by cell
}

impl Grid {
    fn new(cells: usize, n: usize) -> Self {
        Grid { start: vec![0; cells + 1], cell: vec![0; n], order: vec![0; n] }
    }

    /// Counting sort by cell key: count, prefix sum, scatter. O(n + cells), no allocation.
    fn build(&mut self, xs: &[f32], ys: &[f32], key: impl Fn(f32, f32) -> u32) {
        // 1. count: start[c] = boids in cell c
        self.start.fill(0);
        for ((c, &x), &y) in self.cell.iter_mut().zip(xs).zip(ys) {
            *c = key(x, y);
            self.start[*c as usize] += 1;
        }
        // 2. inclusive prefix sum: start[c] = boids in cells 0..=c
        let mut sum = 0;
        for s in &mut self.start {
            sum += *s;
            *s = sum;
        }
        // 3. scatter back to front: each boid takes the last free slot of its cell, so start[c]
        //    ends at the first slot of cell c and boids keep their spawn order inside a cell.
        for (i, &c) in self.cell.iter().enumerate().rev() {
            let s = &mut self.start[c as usize];
            *s -= 1;
            self.order[*s as usize] = i as u32;
        }
    }

    /// Positions in `order` of cells first..=last (consecutive cell numbers).
    fn span(&self, first: u32, last: u32) -> Range<usize> {
        self.start[first as usize] as usize..self.start[last as usize + 1] as usize
    }
}
/// `start[c]..start[c + 1]` is the slice of `order` holding the boids of cell c.
const Grid = struct {
    start: []u32, // cells + 1 entries
    cell: []u32, // cell of each boid
    order: []u32, // boid indices sorted by cell

    fn init(gpa: std.mem.Allocator, cells: usize, n: usize) !Grid {
        return .{ .start = try gpa.alloc(u32, cells + 1), .cell = try gpa.alloc(u32, n), .order = try gpa.alloc(u32, n) };
    }
    fn deinit(g: *Grid, gpa: std.mem.Allocator) void {
        gpa.free(g.start);
        gpa.free(g.cell);
        gpa.free(g.order);
    }

    /// Counting sort by cell key: count, prefix sum, scatter. O(n + cells), no allocation.
    fn build(g: *Grid, w: World, xs: []const f32, ys: []const f32, comptime key: fn (World, f32, f32) u32) void {
        // 1. count: start[c] = boids in cell c
        @memset(g.start, 0);
        for (g.cell, xs, ys) |*c, x, y| {
            c.* = key(w, x, y);
            g.start[c.*] += 1;
        }
        // 2. inclusive prefix sum: start[c] = boids in cells 0..=c
        var sum: u32 = 0;
        for (g.start) |*s| {
            sum += s.*;
            s.* = sum;
        }
        // 3. scatter back to front: each boid takes the last free slot of its cell, so start[c]
        //    ends at the first slot of cell c and boids keep their spawn order inside a cell.
        var i = g.cell.len;
        while (i > 0) {
            i -= 1;
            const c = g.cell[i];
            g.start[c] -= 1;
            g.order[g.start[c]] = @intCast(i);
        }
    }

    /// Positions in `order` of cells first..=last (consecutive cell numbers).
    fn span(g: *const Grid, first: u32, last: u32) [2]usize {
        return .{ g.start[first], g.start[last + 1] };
    }
};
// Counting sort by cell key: count, prefix sum, scatter. O(n + cells), no allocation.
grid_build :: proc(g: ^Grid, w: World, xs, ys: []f32, key: proc(w: World, x, y: f32) -> u32) {
    start, cell, order := g.start, g.cell, g.order // hoisted out of the struct
    // 1. count: start[c] = boids in cell c
    for &s in start {
        s = 0
    }
    #no_bounds_check for &c, i in cell {
        c = key(w, xs[i], ys[i])
        start[c] += 1
    }
    // 2. inclusive prefix sum: start[c] = boids in cells 0..=c
    sum: u32
    for &s in start {
        sum += s
        s = sum
    }
    // 3. scatter back to front: each boid takes the last free slot of its cell, so start[c]
    //    ends at the first slot of cell c and boids keep their spawn order inside a cell.
    #no_bounds_check #reverse for c, i in cell {
        start[c] -= 1
        order[start[c]] = u32(i)
    }
}

// Positions in `order` of cells first..=last (consecutive cell numbers).
span :: #force_inline proc(g: ^Grid, first, last: u32) -> (int, int) {
    return int(g.start[first]), int(g.start[last + 1])
}

The three versions differ in small, telling ways. Rust passes the cell function as a closure (impl Fn(f32, f32) -> u32), and the compiler inlines it into the counting loop. Zig takes it as a comptime function parameter, which specialises build for each key in the same way. Odin passes a plain procedure value; it is called through a pointer unless the optimiser can see through it. Each language writes the back-to-front scatter its own way: Rust with .iter().enumerate().rev(), Zig with a manual countdown, since its for has no reverse form, and Odin with the #reverse for directive. Odin's version also copies g.start, g.cell and g.order into locals first; reading slices through a struct pointer inside a hot loop forces a reload on every iteration (the pitfall from Chapter 4).

With the grid built, the query is three spans per boid. Because cells are numbered row by row, the three cells of one row of the 3 × 3 block have consecutive numbers, so their boids form one contiguous run of order: start[row·side + x0] .. start[row·side + x1 + 1]. Nine cells become three slices:

        let j = j as usize;
        acc.visit(xi, yi, cur.x[j], cur.y[j], cur.vx[j], cur.vy[j]);
    }
}
for (b[2]..b[3] + 1) |row_| {
    const row: u32 = @intCast(row_);
    // three cells of one row are consecutive in `order`, but the boids they name are anywhere
    const r = g.span(row * w.side + b[0], row * w.side + b[1]);
    for (g.order[r[0]..r[1]]) |j| acc.visit(xi, yi, c.x[j], c.y[j], c.vx[j], c.vy[j]);
}
for row in y0 ..= y1 {
    // three cells of one row are consecutive in `order`, but the boids they name are anywhere
    lo, hi := span(g, row * w.side + x0, row * w.side + x1)
    #no_bounds_check for j in order[lo:hi] {
        visit(&acc, xi, yi, c.x[j], c.y[j], c.vx[j], c.vy[j])
    }
}

SoA boids, and the cost of a gather

The boid state is struct-of-arrays, exactly as in Chapter 4: one column each for x, y, vx, vy and id, 20 bytes per boid. id is the spawn index. It is never read by the physics, but it survives reordering, and it is how the correctness check lines up outputs that come out in different orders.

/// The boid state as hand-written SoA: one Vec per field. `id` is the spawn index, which survives
/// reordering. Every column has LANES spare elements at the end so 8-wide loads never run off it.
#[derive(Clone)]
struct Boids {
    n: usize,
    x: Vec<f32>,
    y: Vec<f32>,
    vx: Vec<f32>,
    vy: Vec<f32>,
    id: Vec<u32>,
}
/// One boid. std.MultiArrayList(Boid) stores each field as its own column in one allocation.
/// `id` is the spawn index, which survives reordering.
const Boid = struct { x: f32, y: f32, vx: f32, vy: f32, id: u32 };

/// The column slices of a MultiArrayList, fetched once and passed by value (no reloads in hot loops).
const Cols = struct {
    x: []f32,
    y: []f32,
    vx: []f32,
    vy: []f32,
    id: []u32,

    fn of(list: *const std.MultiArrayList(Boid)) Cols {
        const s = list.slice();
        return .{ .x = s.items(.x), .y = s.items(.y), .vx = s.items(.vx), .vy = s.items(.vy), .id = s.items(.id) };
    }
};
// One boid. #soa[]Boid stores each field as its own column; `id` is the spawn index,
// which survives reordering.
Boid :: struct {
    x, y, vx, vy: f32,
    id:           u32,
}

// The column slices of a #soa slice, taken once (Odin pitfall: hoist them out of hot loops).
Cols :: struct {
    x, y, vx, vy: []f32,
    id:           []u32,
}

// n boids plus LANES zeroed spare elements at the end, so 8-wide loads never run off a column.
Boids :: struct {
    n:    int,
    soa:  #soa[]Boid,
    c:    Cols,
}

boids_make :: proc(n: int) -> (b: Boids) {
    b.n = n
    b.soa = make(#soa[]Boid, n + LANES) // zeroed
    m := n + LANES
    b.c = Cols{b.soa.x[:m], b.soa.y[:m], b.soa.vx[:m], b.soa.vy[:m], b.soa.id[:m]}
    return
}

Rust spells the columns out by hand. Zig declares a plain Boid struct and lets std.MultiArrayList(Boid) build the columns in one allocation. Odin writes #soa[]Boid and gets the same thing from the compiler. Zig and Odin both reach the columns through a small Cols struct of plain slices, fetched once per call, so the hot loops never go back through the container. Every column also has eight spare zeroed elements at the end, which the SIMD variant needs (more on that below).

Now look again at the grid query. order gives us boid indices, and the boids they name are wherever they happened to spawn. Boid 17 and boid 900,341 may share a cell, so the inner loop reads x[17], then x[900341]: a gather across 4 MiB columns. The grid fixed the algorithm, and left the memory access as random as a hash table's. At a thousand boids the columns fit in L1 and nobody notices. At a million, each of the four columns the query reads is 4 MiB, 16 MiB in total. That is far bigger than this machine's 1.25 MiB L2, and spread over more 4 KiB pages than the TLB can map (Chapter 2).

Sort the boids, not just the indices

The fix costs one more pass. After building the grid, copy all five columns into cell order: s.x[k] = cur.x[order[k]] and so on. Now cell c's boids are not just listed together, they are together: s[start[c] .. start[c+1]]. The three spans of the query are three contiguous runs of the boid columns, read front to back, and the three rows above and below a boid are only side × 4 boids apart. That is the "spatially close is close in memory" property the Freiburg uniform-grid report describes [4].

fn step_sorted(w: World, g: &mut Grid, cur: &Boids, s: &mut Boids, next: &mut Boids) -> u64 {
    let n = cur.n;
    g.build(&cur.x[..n], &cur.y[..n], |x, y| w.row_major(x, y));
    s.gather_from(cur, &g.order); // now cell c is s[start[c]..start[c + 1]]
    let mut out = next.out();
    let mut total = 0;
    for k in 0..n {
        let (xi, yi) = (s.x[k], s.y[k]);
        let (x0, x1, y0, y1) = w.block(xi, yi);
        let mut acc = Acc::default();
        for row in y0..=y1 {
            visit_span(&mut acc, s, g.span(row * w.side + x0, row * w.side + x1), xi, yi);
        }
        total += acc.n as u64;
        out.set(k, acc.integrate(w, xi, yi, s.vx[k], s.vy[k]), s.id[k]);
    }
    total
}
fn stepSorted(w: World, g: *Grid, cur: *const Boids, s: *Boids, next: *Boids) u64 {
    const n = cur.n;
    g.build(w, cur.c.x[0..n], cur.c.y[0..n], World.rowMajor);
    s.gatherFrom(cur, g.order); // now cell c is s[start[c]..start[c + 1]]
    const c = s.c;
    var total: u64 = 0;
    for (0..n) |k| {
        const xi = c.x[k];
        const yi = c.y[k];
        const b = w.block(xi, yi);
        var acc: Acc = .{};
        for (b[2]..b[3] + 1) |row_| {
            const row: u32 = @intCast(row_);
            const r = g.span(row * w.side + b[0], row * w.side + b[1]);
            visitSpan(&acc, c, r[0], r[1], xi, yi);
        }
        total += acc.n;
        setOut(next.c, k, acc.integrate(w, xi, yi, c.vx[k], c.vy[k]), c.id[k]);
    }
    return total;
}
step_sorted :: proc(w: World, g: ^Grid, cur, s, next: ^Boids) -> (total: u64) {
    n := cur.n
    grid_build(g, w, cur.c.x[:n], cur.c.y[:n], row_major)
    gather_from(s, cur, g.order) // now cell c is s[start[c]..start[c + 1]]
    c, out := s.c, next.c
    for k in 0 ..< n {
        xi, yi := c.x[k], c.y[k]
        x0, x1, y0, y1 := block(w, xi, yi)
        acc: Acc
        for row in y0 ..= y1 {
            lo, hi := span(g, row * w.side + x0, row * w.side + x1)
            visit_span(&acc, c, lo, hi, xi, yi)
        }
        total += u64(acc.n)
        set_out(out, k, integrate(acc, w, xi, yi, c.vx[k], c.vy[k]), c.id[k])
    }
    return
}

The output stays in cell order too. Next frame, the boids arrive almost sorted, because boids move at most 0.1 units per step, so few of them change cells. The benchmark feeds the sorted variants exactly that: an input that is already in the cell order of the previous frame, as a real simulation loop would. The plain grid variant gets the spawn-order input, as it would if it never reordered. Re-sorting an almost-sorted array still costs the full three passes plus the gather, and it is still cheap: those are a few linear passes over the boids, while the neighbour pass that follows does about 37 distance checks per boid.

Sorting adds a full copy of the boid state every step. At 1,024 boids, where everything fits in L1, will "sorted" be faster or slower than "grid"? At 1M boids?

Faster at both sizes. At 1,024 boids sorted is only about 1.1×–1.2× faster (Odin–Rust), because even in L1 it saves the indirect index load per neighbour, and by 4,096 boids, where the columns leave L1, the gap is already 1.2×–1.6× (Zig–Odin). At 1M boids, sorted is about 6.8× faster in Rust (see the chart below): the same algorithm, the same number of distance checks, and one extra pass. The whole difference is where the bytes are.

The branch that ate the speedup

The first version of the inner loop looked like the rules read (the source keeps it as a comment):

//     if d2 < NEIGHBOR_R2 {
//         self.n += 1;
//         self.sx += dx;
//         // ...
//         if d2 < SEPARATION_R2 { self.qx -= dx; self.qy -= dy; }
//     }

About 37% of the candidates are neighbours, and which ones they are depends on positions that look random to the branch predictor. That is close to the worst case from Chapter 7: a branch that is taken a third of the time with no pattern. The final code computes both outcomes and selects between them:

fn visit(&mut self, xi: f32, yi: f32, xj: f32, yj: f32, vxj: f32, vyj: f32) {
    let dx = xj - xi;
    let dy = yj - yi;
    let d2 = dx * dx + dy * dy;
    // About a third of the candidates are neighbours, so a branch here mispredicts all the time
    // (Chapter 7). The first version branched the way the rules read:
    //     if d2 < NEIGHBOR_R2 {
    //         self.n += 1;
    //         self.sx += dx;
    //         // ...
    //         if d2 < SEPARATION_R2 { self.qx -= dx; self.qy -= dy; }
    //     }
    // select_unpredictable asks for a conditional move/blend instead; a plain
    // `if near { dx } else { 0.0 }` was compiled back into a jump.
    let near = d2 < NEIGHBOR_R2;
    let close = d2 < SEPARATION_R2;
    self.n += near as u32;
    self.sx += select_unpredictable(near, dx, 0.0);
    self.sy += select_unpredictable(near, dy, 0.0);
    self.ax += select_unpredictable(near, vxj, 0.0);
    self.ay += select_unpredictable(near, vyj, 0.0);
    self.qx -= select_unpredictable(close, dx, 0.0);
    self.qy -= select_unpredictable(close, dy, 0.0);
}
/// `v` when `c` holds, else 0. The hint tells LLVM the condition is a coin flip,
/// so it emits a conditional move/blend instead of a jump (Rust: select_unpredictable).
inline fn pick(c: bool, v: f32) f32 {
    if (c) {
        @branchHint(.unpredictable);
        return v;
    }
    return 0.0;
}

/// What one boid accumulates over its neighbours (itself included, so n >= 1).
const Acc = struct {
    n: u32 = 0,
    sx: f32 = 0, // sum of offsets to neighbours (cohesion)
    sy: f32 = 0,
    ax: f32 = 0, // sum of neighbour velocities (alignment)
    ay: f32 = 0,
    qx: f32 = 0, // push away from very close neighbours (separation)
    qy: f32 = 0,

    inline fn visit(self: *Acc, xi: f32, yi: f32, xj: f32, yj: f32, vxj: f32, vyj: f32) void {
        const dx = xj - xi;
        const dy = yj - yi;
        const d2 = dx * dx + dy * dy;
        const near = d2 < NEIGHBOR_R2;
        const close = d2 < SEPARATION_R2;
        self.n += @intFromBool(near);
        self.sx += pick(near, dx);
        self.sy += pick(near, dy);
        self.ax += pick(near, vxj);
        self.ay += pick(near, vyj);
        self.qx -= pick(close, dx);
        self.qy -= pick(close, dy);
    }
// `v` when `c` holds, else 0, without a jump: AND the bits with an all-ones or all-zeros mask.
// Odin has no select hint, and `c ? v : 0` may compile to a branch that mispredicts here.
pick :: #force_inline proc "contextless" (c: bool, v: f32) -> f32 {
    return transmute(f32)(transmute(u32)v & -u32(c))
}

// What one boid accumulates over its neighbours (itself included, so n >= 1).
Acc :: struct {
    n:      u32,
    sx, sy: f32, // sum of offsets to neighbours (cohesion)
    ax, ay: f32, // sum of neighbour velocities (alignment)
    qx, qy: f32, // push away from very close neighbours (separation)
}

visit :: #force_inline proc(a: ^Acc, xi, yi, xj, yj, vxj, vyj: f32) {
    dx := xj - xi
    dy := yj - yi
    d2 := dx * dx + dy * dy
    near := d2 < NEIGHBOR_R2
    close := d2 < SEPARATION_R2
    a.n += u32(near)
    a.sx += pick(near, dx)
    a.sy += pick(near, dy)
    a.ax += pick(near, vxj)
    a.ay += pick(near, vyj)
    a.qx -= pick(close, dx)
    a.qy -= pick(close, dy)
}

Writing it as a plain select is not enough. In Rust, if near { dx } else { 0.0 } looks branch-free, but the disassembly of that build still had a ucomiss followed by a conditional ja in the inner loop: LLVM turned the selects back into a jump around the adds. Switching to std::hint::select_unpredictable (stable since Rust 1.88)[7] removed the jump, and the scalar sorted step got noticeably faster in our run from that one hint. Zig has the same hint as @branchHint(.unpredictable) inside the taken branch. Odin has no select hint, so its pick ANDs the float's bits with a mask made from the bool (-u32(c) is all ones or zero), and there is nothing left to turn back into a branch. Check your compiler's output before you trust either spelling, as Chapter 7 recommends.

Eight lanes over a span

After the sort, each of the three row spans is a contiguous run of about 12 boids in four columns. That is SIMD food, with two complications. First, the spans are short and their lengths vary, so a scalar tail loop would run on almost every span. Instead the SIMD loop always loads 8 lanes and masks off the lanes past the end of the span. Those lanes read the next cell's boids, or the 8 zeroed padding elements at the end of the column, and the mask throws their contribution away. That is why every column has n + 8 elements. Second, a SIMD sum adds in a different order than a scalar one. Each lane keeps its own partial sums for elements l, l+8, l+16, …, and the eight lanes are added at the end, in lane order 0..7 in all three languages, so the languages agree with each other bit for bit. They do not agree with the scalar variants, and the check below has to allow for that.

fn visit_span(&mut self, b: &Boids, r: Range<usize>, xi: f32, yi: f32) {
    let mut j = r.start;
    while j < r.end {
        let x = b.x[j..].first_chunk::<LANES>().unwrap();
        let y = b.y[j..].first_chunk::<LANES>().unwrap();
        let vx = b.vx[j..].first_chunk::<LANES>().unwrap();
        let vy = b.vy[j..].first_chunk::<LANES>().unwrap();
        for l in 0..LANES {
            let dx = x[l] - xi;
            let dy = y[l] - yi;
            let d2 = dx * dx + dy * dy;
            let live = (j + l < r.end) & (d2 < NEIGHBOR_R2);
            let close = live & (d2 < SEPARATION_R2);
            self.n[l] += live as u32;
            self.sx[l] += select_unpredictable(live, dx, 0.0);
            self.sy[l] += select_unpredictable(live, dy, 0.0);
            self.ax[l] += select_unpredictable(live, vx[l], 0.0);
            self.ay[l] += select_unpredictable(live, vy[l], 0.0);
            self.qx[l] -= select_unpredictable(close, dx, 0.0);
            self.qy[l] -= select_unpredictable(close, dy, 0.0);
        }
        j += LANES;
    }
}
inline fn visitSpan(self: *Acc8, b: Cols, a: usize, e: usize, xi: f32, yi: f32) void {
    const zero: V = @splat(0);
    const none: @Vector(LANES, bool) = @splat(false);
    var j = a;
    while (j < e) : (j += LANES) {
        const x: V = b.x[j..][0..LANES].*;
        const y: V = b.y[j..][0..LANES].*;
        const vx: V = b.vx[j..][0..LANES].*;
        const vy: V = b.vy[j..][0..LANES].*;
        const dx = x - @as(V, @splat(xi));
        const dy = y - @as(V, @splat(yi));
        const d2 = dx * dx + dy * dy;
        const in_span = lane_index < @as(VU, @splat(@intCast(e - j)));
        const live = @select(bool, in_span, d2 < @as(V, @splat(NEIGHBOR_R2)), none);
        const close = @select(bool, live, d2 < @as(V, @splat(SEPARATION_R2)), none);
        self.n += @select(u32, live, @as(VU, @splat(1)), @as(VU, @splat(0)));
        self.sx += @select(f32, live, dx, zero);
        self.sy += @select(f32, live, dy, zero);
        self.ax += @select(f32, live, vx, zero);
        self.ay += @select(f32, live, vy, zero);
        self.qx -= @select(f32, close, dx, zero);
        self.qy -= @select(f32, close, dy, zero);
    }
}
visit_span8 :: #force_inline proc "contextless" (a: ^Acc8, b: Cols, lo, hi: int, xi, yi: f32) {
    zero: V
    lane := simd.indices(U)
    #no_bounds_check for j := lo; j < hi; j += LANES {
        // slice elements are only 4-byte aligned and #simd[8]f32 wants 32: unaligned loads
        x := intrinsics.unaligned_load((^V)(&b.x[j]))
        y := intrinsics.unaligned_load((^V)(&b.y[j]))
        vx := intrinsics.unaligned_load((^V)(&b.vx[j]))
        vy := intrinsics.unaligned_load((^V)(&b.vy[j]))
        dx := x - V(xi)
        dy := y - V(yi)
        d2 := dx * dx + dy * dy
        live := simd.lanes_lt(lane, U(u32(hi - j))) & simd.lanes_lt(d2, V(NEIGHBOR_R2)) // all-ones or 0
        close := live & simd.lanes_lt(d2, V(SEPARATION_R2))
        a.n += live & U(1)
        a.sx += simd.select(live, dx, zero)
        a.sy += simd.select(live, dy, zero)
        a.ax += simd.select(live, vx, zero)
        a.ay += simd.select(live, vy, zero)
        a.qx -= simd.select(close, dx, zero)
        a.qy -= simd.select(close, dy, zero)
    }
}

The three spellings show three attitudes. Rust 1.100 still has no stable portable SIMD type (std::simd is nightly-only), so the Rust version writes the lanes as plain [f32; 8] arrays and a fixed 8-iteration inner loop, then trusts LLVM's loop and SLP vectorizers to turn it into vector code. first_chunk::<8>() gives a bounds-checked &[f32; 8] once per block, so there are no per-lane checks. Zig writes @Vector(8, f32) and @select directly. Odin writes #simd[8]f32, loads with intrinsics.unaligned_load because a slice element is only 4-byte aligned while #simd[8]f32 wants 32, and builds the masks with simd.lanes_lt, which returns all-ones or all-zeros lanes. Chapter 8 covers these tools in depth.

Zig 0.17.1 has its loop vectorizer switched off (Chapter 4 explains why)[6], so the Rust-style fixed lane loop would stay scalar in Zig. That is why Acc8 writes @Vector, and why the Zig file is the only one whose SIMD code looks like SIMD.

The three SIMD versions are not running the same instructions. zig build-exe and zig run target the host CPU by default, so the Zig binary uses 256-bit ymm registers on this AVX-512 machine. Cargo (x86-64) and Odin (x86-64-v2) target portable baselines without AVX by default. The Rust and Odin binaries contain cmpltps on 128-bit xmm registers and no ymm at all, so each 8-lane step is two 4-wide halves. That, more than language, is why Zig's SIMD speedup over its own scalar loop is larger. Building Rust with -C target-cpu=native or Odin with -microarch:native should narrow the gap. We did not measure that, because the book's numbers use each toolchain's defaults.

Two cores

Double buffering pays off here. The neighbour pass reads s (the sorted snapshot) and the grid, and writes only next[k] for its own k. Splitting k into two halves gives two threads disjoint outputs and shared read-only inputs: no locks and no atomics. The build and gather stay serial; we come back to that.

/// Build and gather stay serial; the neighbour pass is split into THREADS disjoint output ranges.
fn step_threads(w: World, g: &mut Grid, cur: &Boids, s: &mut Boids, next: &mut Boids) -> u64 {
    let n = cur.n;
    g.build(&cur.x[..n], &cur.y[..n], |x, y| w.row_major(x, y));
    s.gather_from(cur, &g.order);
    let (g, s) = (&*g, &*s);
    let chunk = n.div_ceil(THREADS);
    thread::scope(|scope| {
        let mut rest = next.out();
        let mut handles = Vec::with_capacity(THREADS);
        for t in 0..THREADS {
            let k0 = t * chunk;
            let (mine, tail) = rest.split_at(chunk.min(n - k0));
            rest = tail;
            handles.push(scope.spawn(move || simd_range(w, g, s, mine, k0)));
        }
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    })
}
/// One thread's share of the output. Padded to a cache line so the two `total`s never share one.
const Job = struct {
    w: World,
    g: *const Grid,
    s: Cols,
    out: Cols,
    k0: usize,
    k1: usize,
    total: u64 align(std.atomic.cache_line) = 0,

    fn run(j: *Job) void {
        j.total = simdRange(j.w, j.g, j.s, j.out, j.k0, j.k1);
    }
};

/// Build and gather stay serial; the neighbour pass is split into THREADS disjoint output ranges.
fn stepThreads(w: World, g: *Grid, cur: *const Boids, s: *Boids, next: *Boids) u64 {
    const n = cur.n;
    g.build(w, cur.c.x[0..n], cur.c.y[0..n], World.rowMajor);
    s.gatherFrom(cur, g.order);
    const chunk = std.math.divCeil(usize, n, THREADS) catch unreachable;
    var jobs: [THREADS]Job = undefined;
    var threads: [THREADS]std.Thread = undefined;
    for (&jobs, &threads, 0..) |*j, *t, i| {
        j.* = .{ .w = w, .g = g, .s = s.c, .out = next.c, .k0 = @min(i * chunk, n), .k1 = @min((i + 1) * chunk, n) };
        t.* = std.Thread.spawn(.{}, Job.run, .{j}) catch @panic("thread spawn failed");
    }
    var total: u64 = 0;
    for (threads, &jobs) |t, *j| {
        t.join(); // read j.total only after the join
        total += j.total;
    }
    return total;
}
// One thread's share of the output. Aligned to 128 B so the two `total`s never share a line pair.
Job :: struct #align (128) {
    w:      World,
    g:      ^Grid,
    s, out: Cols,
    k0, k1: int,
    total:  u64,
}

run_job :: proc(j: ^Job) {
    j.total = simd_range(j.w, j.g, j.s, j.out, j.k0, j.k1)
}

// Build and gather stay serial; the neighbour pass is split into THREADS disjoint output ranges.
step_threads :: proc(w: World, g: ^Grid, cur, s, next: ^Boids) -> (total: u64) {
    n := cur.n
    grid_build(g, w, cur.c.x[:n], cur.c.y[:n], row_major)
    gather_from(s, cur, g.order)
    chunk := (n + THREADS - 1) / THREADS
    jobs: [THREADS]Job
    pool: [THREADS]^thread.Thread
    for &j, i in jobs {
        j = Job{w = w, g = g, s = s.c, out = next.c, k0 = min(i * chunk, n), k1 = min((i + 1) * chunk, n)}
        pool[i] = thread.create_and_start_with_poly_data(&j, run_job)
    }
    thread.join_multiple(..pool[:])
    for t, i in pool {
        thread.destroy(t)
        total += jobs[i].total // read only after the join
    }
    return
}

Rust's borrow checker turns "disjoint outputs" into a type-level fact. Out::split_at splits all five output columns with split_at_mut, and thread::scope lets the threads borrow the grid and the sorted boids without Arc. If the ranges overlapped, the program would not compile. Zig and Odin hand each thread a Job by pointer, and the disjointness is the programmer's promise. Both align the Job (Zig the total field to std.atomic.cache_line, which is 128 here; Odin the struct to 128 B) so the two threads' result slots cannot share a cache line pair. That is the false-sharing rule from Chapter 8. Zig uses std.Thread.spawn rather than io.async, because io.async may run the function inline and would not guarantee two cores.

The first Zig version of this function printed a neighbour total of 0 for the threaded variant, and the check caught it. The collect loop was for (threads, jobs) |t, j|, which copies jobs by value when the loop starts, before any join, so it summed results the threads had not written yet. Iterating &jobs with |t, *j| reads each job after its thread is joined. This is the kind of bug a strict result check exists for.

Threads are spawned on every step. At 1,024 boids a whole step takes about 0.09 ms (Rust), and starting and joining two threads costs a sizeable fraction of that. In all three languages the threaded variant is slower than the single-threaded one at that size: 1.6× slower in Rust, 1.3× in Odin and 4.9× in Zig. As N grows the second core pays off, and in Rust the gain rises to about 1.8× from a quarter-million boids up, on two physical cores. It cannot reach 2×, because the build and gather still run on one core.

Morton order: a good idea that loses here

Row-major cell numbers have a weakness: the row above a boid is side cells away in memory. Locality is good along x and poor along y. The usual fix is a space-filling curve. Number the cells along a Z-order (Morton) curve by interleaving the bits of x and y[5], so every aligned 2 × 2, 4 × 4, 8 × 8 square of cells is a contiguous range of numbers. Sort by that key and boids that are close in both directions tend to be close in memory. The chapter's fourth variant does exactly this, reusing the same counting sort with a different key function.

/// Interleaves the bits of x and y (x in the even bits): the Z-order curve.
fn morton(cx: u32, cy: u32) -> u32 {
    fn spread(v: u32) -> u32 {
        let mut v = v & 0xFFFF;
        v = (v | (v << 8)) & 0x00FF_00FF;
        v = (v | (v << 4)) & 0x0F0F_0F0F;
        v = (v | (v << 2)) & 0x3333_3333;
        (v | (v << 1)) & 0x5555_5555
    }
    spread(cx) | (spread(cy) << 1)
}
/// Interleaves the bits of x and y (x in the even bits): the Z-order curve.
fn morton(cx: u32, cy: u32) u32 {
    const spread = struct {
        fn f(v0: u32) u32 {
            var v = v0 & 0xFFFF;
            v = (v | (v << 8)) & 0x00FF_00FF;
            v = (v | (v << 4)) & 0x0F0F_0F0F;
            v = (v | (v << 2)) & 0x3333_3333;
            return (v | (v << 1)) & 0x5555_5555;
        }
    }.f;
    return spread(cx) | (spread(cy) << 1);
}
// Interleaves the bits of x and y (x in the even bits): the Z-order curve.
morton :: #force_inline proc(cx, cy: u32) -> u32 {
    spread :: #force_inline proc(v0: u32) -> u32 {
        v := v0 & 0xFFFF
        v = (v | (v << 8)) & 0x00FF_00FF
        v = (v | (v << 4)) & 0x0F0F_0F0F
        v = (v | (v << 2)) & 0x3333_3333
        return (v | (v << 1)) & 0x5555_5555
    }
    return spread(cx) | (spread(cy) << 1)
}

On this machine Morton order is consistently slower than row-major, at every size and in every language: at a million boids by 1.3× in Rust, 1.3× in Odin and 1.4× in Zig, and by 1.3–1.5× across all the sizes we ran. The reason is in the figure. The win that Morton order offers is cache locality across rows. But with row-major sorting, the three rows a boid reads are only side × 4 × 20 bytes apart, about 40 KiB at N = 1M. Worse, the next boid reads almost the same rows, so the working set of the sweep is a band of three rows of boids, roughly 120 KiB, that slides along as the sweep proceeds. That fits comfortably in L2, and the hardware prefetchers see three sequential streams. Row-major sorting already has the locality; Morton cannot add more. What Morton does add is cost: nine short spans of about four boids instead of three of about twelve, nine Morton encodings per boid, and nine loop setups with their own branch exits. The extra work is real and the locality gain is zero.

Morton order earns its keep when the band of rows does not fit in cache: a much wider world, 3D (where a 3 × 3 × 3 query touches nine rows spread over three planes), or bigger records. It is also cheap to try, since it is only a different key for the same sort. But this is a good place to repeat the book's rule: measure, because the textbook improvement does not always apply to your data.

Checking that six programs agree

The variants must compute the same step, but "the same" needs a careful definition for floats. Floating-point addition is not associative, and each variant adds the neighbour terms in a different order. Naive adds them in spawn order. Grid and sorted add them cell by cell. The SIMD variants add eight interleaved partial sums. So the check has three layers:

  1. Neighbour counts must match exactly. Each variant returns the total number of neighbour pairs it found. That is an integer, and the comparison d² < 1 is computed the same way in every variant, so any difference means the search missed or double-counted someone. This is the check that catches real bugs, like the Zig thread total above.
  2. The state must match within a tolerance. Each output is re-indexed by spawn id, and the largest difference in any of x, y, vx, vy must be at most 1e-4. Positions go up to 512 at N = 1M, where one f32 step (ulp) is 2⁻¹⁵ ≈ 3.05e-5. The largest difference the program reports there is exactly 3.05e-5: the SIMD sums land one ulp away from the scalar sums. 1e-4 allows about three ulps at the largest world, and catches anything bigger.
  3. The languages must match exactly. The programs print an FNV-1a hash of the bits of the state after the naive and grid steps. Rust, Zig and Odin print identical hashes at every N (for example c9356f9c3691824d for the grid step at 1M boids). That shows the three implementations are the same algorithm down to the order of every addition, and that none of the three compilers fused a multiply-add or reassociated anything.
/// The state indexed by spawn id, so outputs stored in different orders can be compared.
fn by_id(b: &Boids) -> Vec<[f32; 4]> {
    let mut v = vec![[0.0; 4]; b.n];
    for k in 0..b.n {
        v[b.id[k] as usize] = [b.x[k], b.y[k], b.vx[k], b.vy[k]];
    }

}

/// FNV-1a over the bits of the state in spawn order: equal only if every float is bit-identical.
fn checksum(v: &[[f32; 4]]) -> u64 {
    v.iter().flatten().fold(0xCBF2_9CE4_8422_2325, |h, f| (h ^ f.to_bits() as u64).wrapping_mul(0x100_0000_01B3))
}

/// Largest difference in any position or velocity component.
fn max_diff(a: &[[f32; 4]], b: &[[f32; 4]]) -> f32 {
    let d = |p: &[f32; 4], q: &[f32; 4]| p.iter().zip(q).map(|(u, v)| (u - v).abs()).fold(0.0, f32::max);
    a.iter().zip(b).map(|(p, q)| d(p, q)).fold(0.0, f32::max)
}

}

    };
    return h;
}

/// Largest difference in any position or velocity component.
fn maxDiff(a: []const [4]f32, b: []const [4]f32) f32 {
    var m: f32 = 0;
    for (a, b) |p, q| for (p, q) |u, v| {
        m = @max(m, @abs(u - v));
    };
    return m;
}

        }
    }
    return
}

The check covers one step. Boids are a chaotic system: run a thousand steps and a one-ulp difference grows until two variants show visibly different flocks, even though both are correct. For long runs, compare statistics (neighbour counts, mean speed, a histogram of positions) or, if you need bit-equality, fix the summation order everywhere, as the three languages do here against each other.

Measured

Every variant runs once to warm up and then seven timed times (the harness from Chapter 2), from N = 1,024 to 1,048,576 in steps of 4×. Naive stops at 16,384, where one step already takes most of a second. The runs are pinned to CPUs 0 and 2, two separate physical cores; only the threaded variant uses the second. Times are per boid per step, so a flat line means linear scaling.

Read the chart from the top of the stack down. Naive against grid, at the largest size where both run (16,384), is about 180× in Rust. That is a lot, but less than the 454× drop in distance checks (268 million against 591,348), because a grid check costs more than a naive one: an index load, an indirect gather, and the per-step build. Grid against sorted is the layout lesson. Both do the same 38.7 million checks per step at N = 1M. Sorted is 6.8× faster in Rust, 7.5× in Zig and 6.3× in Odin, and the ratio grows with N, from about 1.1–1.2× at 1,024 boids, as the unsorted gather falls out of each cache level. The SIMD lanes give 1.8× in Rust and 1.7× in Odin (two 4-wide halves) and about 2.6× in Zig (one 8-wide register). The second core adds about 1.7× more in Zig. All together, the fastest variant at a million boids is roughly 34× faster than the plain grid in Zig (21× in Rust, 20× in Odin), and incomparably faster than naive, whose single step at that size would be about a trillion checks.

Caveats and what we left out

  • Uniform density is the friendly case. The grid assumes boids spread out. Real flocks clump: a thousand boids in one cell make that cell's 3 × 3 query quadratic again. Fixes include a cell size tuned to density, hierarchical grids, or a tree, at the cost of the simplicity that makes this version fast.
  • A bounded world. Our grid is dense: start has one entry per cell. An unbounded or very sparse world would hash cell coordinates into a fixed-size table, Müller's "spatial hash". Hash collisions only add candidates that the distance test then rejects[2]. The counting sort is the same.
  • Serial build. The count, prefix sum, scatter and gather run on one thread. They are a small slice of the step here, but Amdahl's law caps the speedup of the threaded variant, and with more cores the build would dominate. The parallel version (per-thread counts, a parallel prefix sum, then a parallel scatter) is a standard exercise.
  • Threads per step. Spawning threads every step is the simplest correct code, and it is visible as overhead at small N. A long-running simulation would keep a pool of worker threads and hand them work each frame.
  • Morton result is machine- and size-specific. We showed it losing on a 2D world whose three-row band fits in L2. Do not read that as "Morton order is slow".

Make the algorithm stop asking useless questions (a grid), then put the answers next to each other in memory (sort the boids by cell), then remove the branches and use the lanes and cores. Each step is only safe because double buffering and a strict check keep the result fixed.

Exercises

Why must the grid's cell size be at least the neighbour radius? What goes wrong if you make cells half the radius but still search only the 3 × 3 block?

With cells of side r/2, a neighbour can be up to two cells away, so the 3 × 3 block misses some of them. The neighbour counts would be too low, and the exact count check would fail. With half-size cells you must search a 5 × 5 block (25 cells of area r²/4, total 6.25 r², less than 9 r²). That can be a net win: fewer wasted checks, but more spans per boid.

The scatter pass runs back to front. Write the front-to-back version and say what else you need.

Use an exclusive prefix sum (start[c] = boids in cells before c), then for each boid in order: order[cursor[c]] = i; cursor[c] += 1, where cursor is a copy of start. You need that second array (or a second prefix-sum pass to restore start), because the scatter destroys the values it increments. Back to front with an inclusive sum leaves start correct with no copy.

The neighbour totals are compared exactly, but positions only within 1e-4. Why would an exact position check fail even though every variant is correct?

Each variant adds the neighbour terms in a different order (spawn order, cell order, or eight interleaved lane sums), and float addition is not associative, so the sums differ in the last bits. The program reports differences up to one ulp (3.05e-5 at positions near 512). Integer neighbour counts have no rounding, so they can and must be exact.

Estimate the memory traffic of the unsorted grid at N = 1M. Each distance check reads x, y, vx and vy of a random boid. How many cache lines per check, and how many bytes per step?

Four columns, each a separate 4 MiB array, so a random boid is about four cache-line misses (some neighbours share lines by chance). 38.7 M checks × 4 lines × 64 B ≈ 9.9 GB per step if nothing hit in cache. In practice many neighbours recur from boid to boid, but that is the scale of what sorting removes. Sorted, the same checks stream through about three rows of boids, and the whole step touches each 20 MiB buffer a few times.

Build the Rust program with RUSTFLAGS="-C target-cpu=native" and compare "sorted simd" with the default build. What changed in the binary?

On this AVX-512 machine LLVM may use 256-bit (or 512-bit) ymm/zmm registers for the 8-lane loop, as Zig does by default, instead of two 128-bit halves. Check with objdump -d target/release/ch10_boids_spatial_hash | grep -c ymm. We did not measure the speedup; expect the Rust SIMD ratio to move toward Zig's. The binary then no longer runs on CPUs that lack this one's features (here, AVX-512).

Make the build parallel: give each of T threads its own counts, then combine them. What does the scatter need to know so threads never write the same slot?

Each thread counts its slice of boids into count[t][c]. The prefix sum runs over cells and, within a cell, over threads: thread t's first slot in cell c is the total of all cells before c plus thread 0..t−1's counts in c. Each thread then scatters its own boids using its own cursors. The slots are disjoint by construction, and the result is still stable if threads own contiguous slices of the boids in order.

Under what change to this benchmark would you expect Morton order to beat row-major sorting?

When the band of rows a sweep touches no longer fits in cache: a 3D world (a 3 × 3 × 3 query spans three planes that are side² cells apart), much larger records per boid, a very wide world, or a smaller cache. You could also keep row-major cells but traverse boids in Morton order of their cells, so the band stays small. Measure before you believe any of these.
