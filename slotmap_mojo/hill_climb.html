The climb

The score is the geometric mean of Mojo/Rust time over 12 workloads at 3 sizes. Below 1.00 means Mojo is faster. The first five scores were taken with a nanosecond protocol that turned out to be too noisy to trust (the same binary scored 1.03 and then 1.16), so they are drawn hollow and not connected.

Key findings

  • The data structure beat the compiler. The three largest gains (free stack, run iterator, region allocator) are design changes Rust's crate could also make. Code generation tuning was worth 5 to 25% per workload; design was worth 2× to 34×.
  • At cache-resident sizes, instruction count decides. These loops retire about 4.2 micro-operations per cycle, so one extra shl or one extra store per operation is visible in the score.
  • Rust's remaining edge is loop unrolling. rustc's LLVM pipeline unrolled the lookup loop 4×; Mojo 1.2.0 did not unroll any loop I inspected. Hand-unrolling the Mojo driver closed that gap exactly (2.10 to 1.72 cycles, Rust 1.73).
  • Return types leak into hot loops. Optional[V] by value left a tag byte and a cmov in the caller; raises and Optional[Pointer] did not.
  • The benchmark was wrong three times. Frequency drift, a harness call that forced a store, and a branch predictor that memorized a fixed seed each produced convincing, false numbers.

What a slot map is

A slot map is an array of slots with stable keys. A key is a slot position plus a version number. Removing an element bumps the slot's version, so old keys stop matching. An odd version means occupied.

Rust · Slot<u64> · 16 bytes

The value and the next-free index share the same 8 bytes (a union). A vacant slot stores the index of the next vacant slot. Bytes 12 to 15 are padding.

Key

idx: u32, version: NonZeroU32. Address = base + (idx << 4).

Mojo final · slot for UInt64 · 16 bytes

Same size. The 4 padding bytes become a cell of the free stack: cell i holds the i-th free handle. It is unrelated to the value in the same slot.

Key

slot: UInt32 is the index already multiplied by 2, version: UInt32. Address = base + slot*8, which x86 encodes in the addressing mode.

Free list versus free stack

This is the 34× cell. After random removals, Rust's free list visits vacant slots in a scattered order, and the only place the next free index is written is inside the vacant slot itself. Each insert must finish loading one slot before it knows the address of the next. At 2,000,000 elements every one of those loads misses the cache and the TLB, and they cannot overlap.

The stack keeps free handles in consecutive cells. Popping reads the top cell, whose address depends only on a counter. The slot it points to still misses, but nothing waits on that miss, so the CPU runs many inserts ahead and the misses overlap.

Why the stack ended up inside the slots

The first stack (v3) was a separate UInt32 array. Remove timings became bimodal: the same binary was fast or slow depending on where malloc placed the two blocks. The stack's stores and the slot and key loads sat at matching offsets within 4 KiB pages, and the CPU's store-to-load disambiguation only compares the low 12 address bits, so it kept suspecting a conflict. Moving each stack cell into the 4 padding bytes of a slot (v6) gave the stack the same stride and page offsets as the slots, removed the second allocation, and made the timing stable.

The iterator: per slot, per bit, per run

Rust tests one slot per loop iteration. On a half-empty map that is one unpredictable branch per slot, about 12 to 17 cycles each. The Mojo iterator reads 64 version bytes into one mask, then decides per chunk how to walk it.

The run trick is two instructions of bit arithmetic. With start = tzcnt(m), the run length is tzcnt(~(m >> start)), and m & (m + (1 << start)) clears exactly that run because the add carries through it. The chunk rule is popcnt(m) >= 8 * popcnt(m & ~(m << 1)): the second popcount counts 0→1 transitions, which is the number of runs.

Allocation patterns and the custom allocator

Mojo has no allocator trait or parameter. Its List and Dict call alloc, which goes to a bundled TCMalloc and has no realloc: growth is allocate, copy, free. Rust's Vec calls the global allocator's realloc, which for glibc can extend in place. So the first allocator change was parity: call libc directly with external_call["realloc", Int].

How the region is made: mmap(bytes + 2 MiB, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS|MAP_NORESERVE), round the address up to 2 MiB, munmap the unaligned head and tail, then madvise(…, MADV_HUGEPAGE). If mmap fails the reservation halves down to the exact size, then falls back to malloc. The branch is behind comptime if CompilationTarget.is_linux().

Same LLVM underneath, different front ends

Both compilers lower to LLVM IR and share its instruction selection, register allocation and most scalar optimizations. For the same loop written the same way, the two produced the same instructions in almost the same order. The differences came from what each front end hands to LLVM and which passes it schedules.

Where they came out the same

  • Monomorphized generics. SlotMap<u64> and SlotMap[UInt64] each compile to one specialized copy with all sizes and offsets as constants.
  • Full inlining of the map into the benchmark loop (#[inline] plus fat LTO in Rust, @inline(.always) in Mojo). Neither listing contains a call in a hot loop except growth.
  • Identical instruction choices: scaled-index addressing, cmp/jcc fusion pairs, tzcnt/popcnt/blsr/shlx from BMI when given bit intrinsics, and with target-cpu=native both use AVX-512.
  • Same aliasing behaviour. Once the map's address has escaped, both reload struct fields after a store through a pointer, and both write counters back every iteration.
  • Destructor elision at compile time: mem::needs_drop in Rust, comptime if not IsTriviallyDeinitable[V] in Mojo.

The dials that moved the score

  • What a key stores. Index → pre-scaled handle. Removes a shift and an add per access.
  • What a miss returns. Optional[V] → raises.
  • Where free slots are recorded. In the vacant slot → separate array → the slot's padding.
  • How many counters are written. Three fields per remove → one.
  • Counter width. UInt32 fields → Int, so no zero-extension before addressing.
  • Iteration unit. Slot → bit → run, chosen per 64-slot chunk.
  • Allocator threshold. 2 MiB hurt; 8 MiB did not.
  • Reservation factor. 16× means one copy per 16× of growth.

Final results

Mojo cycles ÷ Rust cycles per operation, u64 values, nine paired rounds. Teal is Mojo ahead, copper is Rust ahead. Small print is Mojo / Rust cycles.

Removal rows time pop(key) raises. With remove(key) → Optional[V] the remove rows are 1.00 to 1.10 and churn is 0.62 to 0.73. Geometric mean by size: 0.64 at 1,000, 0.60 at 100,000, 0.48 at 2,000,000.

Open ends

  • Five cells are above 1.00. Mixed hit/miss lookups at 1,000 and 100,000 (1.06, 1.09) are dominated by branch mispredictions on both sides and I did not find the cause of the difference. Sequential lookups at 100,000 (1.10) sit where results vary with physical page placement. The other two are within 2%, inside noise.
  • Only u64 values were timed. For 4-byte-aligned values the stack cell adds 4 bytes per slot (12 against Rust's 8 for a u32).
  • Key semantics changed. key_to_ffi and key_from_ffi convert to Rust's encoding. Index space is 231 slots for 16-byte slots.
  • The region allocator is Linux-only and relies on madvise huge pages.
  • One virtual machine. Calibration removes clock drift but not the hypervisor's effect on page faults, which dominate the 2,000,000-element insert rows.
  • Compiler-version tricks. The inline-assembly barrier and the source shapes that steer block layout were validated on Mojo 1.2.0 only.
  • Not tried: struct-of-arrays versions for SIMD scanning, a pooled allocator for short-lived maps, a branch-free get(key, default).
