Chapter 12

Measure, and Know When Not To

On the machine this book was measured on, a Rust benchmark reported summing the squares of a million numbers at about ten thousand elements per clock cycle, from a core that can do a handful of additions per cycle. The number was not fast. It was wrong, and the benchmark had no way to tell. This last chapter is about the ways a benchmark lies, how to catch each lie with a cheap check, the tools that see what a stopwatch cannot, and the harder question that measuring finally lets you answer honestly: whether the data-oriented rewrite is worth doing at all.

Every earlier chapter leaned on the harness from Chapter 2: one warm-up run, the median of seven, a keep-alive on every result, and a checksum that every variant must match. Here we take that harness apart on purpose. We break the keep-alive in two ways and see what the stopwatch reports. We time one tiny kernel 41 times and look at the spread instead of the median. We compare a function with itself, where any difference is an error of method. Then we turn to the critics, and end with a checklist and a language table.

The machine (details in Chapter 2): one 4-vCPU KVM Xeon (Ice Lake) shared with other work, with no hardware performance counters and no perf, valgrind or pahole. Benchmarks ran pinned with taskset -c 2, and the numbers are noisy, so read ratios and ranges.

The 0 ns benchmark

Chapter 2 warned about this trap in one paragraph. Now we spring it deliberately. The kernel is a wrapping sum of squares over n numbers, v[i] = i. We time it three ways with otherwise identical code, plus a fourth "benchmark" that does nothing at all, so we know what the clock itself costs:

  • empty (timer only): a function that returns 0. Its time is the floor: two clock reads and nothing between them.
  • result discarded: the harness, but the result goes to _ instead of the black box.
  • input visible: the result is kept, but the loop is written over 0..n, so the optimizer can see every input.
  • kept alive: the real harness, with the result kept (Rust also passes the slice through black_box).

The broken harness differs from the real one by one token per line. In Rust it is let _ = f() instead of black_box(f()); in Zig _ = f(ctx) instead of std.mem.doNotOptimizeAway(f(ctx)); in Odin _ = f(ctx) instead of keep(f(ctx)):

/// A broken harness: identical to `bench_runs`, except that the result is dropped.
fn bench_runs_discarding<R>(mut f: impl FnMut() -> R) -> [Duration; RUNS] {
    let _ = f();
    let mut t = [Duration::ZERO; RUNS];
    for slot in &mut t {
        let t0 = Instant::now();
        let _ = f(); // nothing reads this, so the optimizer may delete the call
        *slot = t0.elapsed();
    }
    t.sort_unstable();
    t
}
/// A broken harness: identical to `benchRuns`, except that the result is thrown away.
fn benchRunsDiscarding(io: Io, comptime f: anytype, ctx: anytype) [RUNS]u64 {
    _ = f(ctx);
    var t: [RUNS]u64 = undefined;
    for (&t) |*slot| {
        const t0 = nowNs(io);
        _ = f(ctx); // nothing reads this, so the optimizer may delete the call
        slot.* = @intCast(nowNs(io) - t0);
    }
    std.mem.sort(u64, &t, {}, std.sort.asc(u64));
    return t;
}
// A broken harness: identical to bench_runs, except that the result is thrown away.
bench_runs_discarding :: proc(f: proc(ctx: $C) -> u64, ctx: C) -> (t: [RUNS]time.Duration) {
	_ = f(ctx)
	for &d in t {
		t0 := time.tick_now()
		_ = f(ctx) // nothing reads this, so the optimizer may delete the call
		d = time.tick_since(t0)
	}
	slice.sort(t[:])
	return
}
At n = 1,048,576 the honest run takes about 0.4 ms in all three languages. What will "result discarded" show?

The same as timing nothing: 42 ns in Rust, 36 ns in Zig and 137 ns in Odin. The call is pure (it reads memory and returns a number), nothing reads the number, so the optimizer removes the call. What remains between the two clock reads is nothing. The honest run is about 9,850× slower in Rust.

The program prints its own verdict on every line, and this is the habit worth copying. Two sanity checks catch almost every deleted benchmark before anyone looks at a ratio. First, is it slower than timing nothing? The program measures the empty function first and flags anything under twice that floor. Second, is the time per element physically possible? At 2.6 GHz, 0.05 ns per element would mean eight squared-and-added 64-bit numbers per cycle, which this loop cannot sustain; anything faster is flagged. Both checks fire on the broken rows, in all three languages, at every size:

(a) sum of squares over 1048576 u64, median of 7:
    empty (timer only)           42 ns     0.0000 ns/elem  (the floor: two clock reads)
    result discarded            42 ns     0.0000 ns/elem  <- SUSPICIOUS: no slower than timing nothing
    input visible               36 ns     0.0000 ns/elem  <- SUSPICIOUS: no slower than timing nothing
    kept alive              413715 ns     0.3946 ns/elem  plausible
    checksum: kept alive 384306618446643200, input visible 384306618446643200

(Those are the Rust lines of the run the charts show; Zig and Odin print the same checksums.) The checksum line matters too. "Input visible" computed the right answer, so a checksum alone would not have caught it. Checksums catch variants that are fast because they are wrong; the timer floor catches variants that are fast because they are gone. You need both.

Deleted, or turned into a formula

"Result discarded" and "input visible" fail for different reasons, and the difference matters when you fix them. The first is dead-code elimination: nobody reads the value, so no instruction computes it. The second is subtler. The result is kept, and the loop did run, in a sense. LLVM's scalar evolution pass recognized Σ i² as a polynomial in n and replaced the loop with the closed form. Here is what rustc -O --emit asm produces for the stand-alone function (Zig 0.17.1 emits the same closed form in Intel syntax, using BMI2 mulx and keeping a frame pointer):

sum_squares_range:
	testq	%rdi, %rdi
	je	.LBB0_1
	leaq	-1(%rdi), %rax
	leaq	-2(%rdi), %rcx
	mulq	%rcx
	leaq	-3(%rdi), %rcx
	imulq	%rax, %rcx
	shrq	%rcx
	movabsq	$6148914691236517206, %rsi
	shldq	$63, %rax, %rdx
	imulq	%rcx, %rsi
	leaq	(%rdx,%rdx,2), %rax
	addq	%rdi, %rax
	decq	%rax
	addq	%rsi, %rax
	retq

No loop, no branch back, no memory access: a dozen multiplies and shifts that compute (n−1)n(2n−1)/6 modulo 264 (the large constant is the modular inverse trick for dividing by 3). The fix is not "keep the result", which this version already did; it is hide the input. That is why the harness passes black_box(&v) into the closure in Rust and why every chapter builds its inputs from a runtime seed. A benchmark whose input is a compile-time constant measures the compiler's algebra, not your loop.

An early Odin probe, and why Odin's floor is higher

While preparing this book, an early Odin probe (recorded in our research notes) summed the health field of four million entities with time.Stopwatch around a call written as _ = sum_health_soa(soa). At the default optimization level it took about 17 ms. At -o:speed it printed 313 ns, faster than reading one cache line from DRAM per thousand entities. LLVM had deleted the call, exactly as in our "result discarded" row. Odin has no black_box, so the fix is the harness's keep, a volatile store into a file-private global[13]:

// Odin has no black_box: a volatile store into a file-private global keeps results alive.
@(private = "file")
sink: u64

keep :: proc "contextless" (v: $T) where size_of(T) <= 8 {
	intrinsics.volatile_store((^T)(&sink), v)
}

A volatile store must happen, so the value must be computed. It is a stronger promise than Rust's black_box, which the standard library documents as "best-effort"[11], and Zig's doNotOptimizeAway, which "tries to prevent" the optimization[12], but it only covers the value you store. In all three languages, the keep-alive protects the result; nothing protects work whose result does not flow into it.

The figure also shows a quieter difference. Odin's empty benchmark costs about 137 ns, several times Rust's (42 ns) and Zig's (36 ns). On Linux, Odin's time.tick_now calls clock_gettime(CLOCK_MONOTONIC_RAW) through a raw syscall instruction (core/time/time_linux.odin[14]), so every clock read enters the kernel. Rust's Instant and Zig's Io.Clock.awake go through libc or the vDSO, which reads the clock without a system call. The floor sets the smallest thing you can time: loop a short kernel inside the timed region until each sample is far above it.

The nightly-only #[bench] attribute is now a hard error without #![feature(custom_test_frameworks)] (it had been a deny-by-default lint since 1.77)[15]. On stable Rust the std-only answer is the one this book uses: Instant plus std::hint::black_box. The Rust Performance Book lists Criterion, Divan and Hyperfine as the usual crates and tools[16].

Noise: warm-up, medians and the coefficient of variation

Once a benchmark measures the right thing, the next question is how much to trust one number. The program's part (b) times the same tiny kernel, a sum of u32 into a u64, 41 times after one warm-up, at two sizes: 16 KiB, which lives in L1, and 16 MiB, which spills past L2 into the shared L3 and DRAM. It prints every sample. The minimum, median, maximum and coefficient of variation (CV = standard deviation ÷ mean) summarize them:

(b) noise, 41 timed runs each:                                            (Rust, pinned to CPU 2)
    16 KiB (L1)       min        627 ns  median        629 ns  max        747 ns  CV   4.4%
    16 MiB (L3/DRAM)  min     711005 ns  median     743725 ns  max    1621692 ns  CV  23.2%

(The Rust lines of the run the charts show. Across the three languages the CV was about 1–4% at 16 KiB and 16–24% at 16 MiB.)

The harness's usual seven samples already hint at this. Here are the seven behind each "kept alive" median in the figure above, drawn with the book's shared run-spread chart:

Three lessons sit in the 41-sample histogram. Warm-up is not the main source of noise here: after the discarded first run, the slow samples are scattered through the sequence, not bunched at the start.

The distribution is not symmetric. A run can be slowed by an interrupt, a neighbour, a migration or a cache flush, but nothing makes it faster than the hardware allows. Timings therefore pile up near a floor and trail off to the right. The mean is pulled toward the tail; the median is not. The minimum is a fair second statistic for small CPU-bound kernels, but optimistic for anything that touches DRAM, where some interference is part of the real cost.

The CV tells you the smallest difference worth discussing. With a CV around 3%, a 10% difference between two variants is far outside the noise. With a CV of 20%, a 10% difference from seven runs is close to a coin flip. A rule of thumb: if two medians differ by less than the CV of either, do not report a winner; add runs, or make the kernel bigger, or stop. The next figure lets you check that rule against a model.

B is truly 5% faster than A, the noise is 5% CV, and you compare one run of each. How often does A win?

Roughly one time in four. The difference between two noisy runs has about √2 × 5% ≈ 7% spread, and the true gap is 5%, so a wrong verdict needs only a bit less than one standard deviation of bad luck. The median of seven runs cuts that to about 6%, and the figure shows how many runs push it under 5%.

Try two things. Set the noise to 20% (our 16 MiB row) and the effect to 5%: even with 51 runs the median picks the wrong winner about one time in seven, and the "runs needed" counter climbs past a hundred. Then switch on spikes at a low CV: the mean of seven gets visibly worse than the median, because one 3× outlier moves a mean by almost 30% and a median not at all.

Compare a thing with itself: the A/A test

The most useful benchmark you can run is one where you already know the answer. In an A/A test, "A" and "B" are the same code on two identical 256 KiB buffers (both fit in L2 together), so the true ratio is exactly 1.000. Any difference you measure is the error of your method. The program runs it two ways, seven rounds each, 31 timed runs per side:

  • Sequential: all 31 runs of A, then all 31 runs of B. This is what most hand-written comparisons do.
  • Alternating: A, B, A, B, … so anything that drifts over time (a neighbour waking up, the host shuffling vCPUs, thermal or power limits) lands on both sides equally.
/// A/A test, alternating: A, B, A, B, ... so slow drift hits both sides equally.
fn aa_alternating(a: &[u32], b: &[u32]) -> ([Duration; AA], [Duration; AA]) {
    black_box(sum_u32(black_box(a)));
    black_box(sum_u32(black_box(b)));
    let (mut ta, mut tb) = ([Duration::ZERO; AA], [Duration::ZERO; AA]);
    for i in 0..AA {
        let t0 = Instant::now();
        black_box(sum_u32(black_box(a)));
        ta[i] = t0.elapsed();
        let t0 = Instant::now();
        black_box(sum_u32(black_box(b)));
        tb[i] = t0.elapsed();
    }
    ta.sort_unstable();
    tb.sort_unstable();
    (ta, tb)
}
/// A/A test, alternating: A, B, A, B, ... so slow drift hits both sides equally.
fn aaAlternating(io: Io, a: []const u32, b: []const u32) Pair {
    std.mem.doNotOptimizeAway(sumU32(a));
    std.mem.doNotOptimizeAway(sumU32(b));
    var p: Pair = undefined;
    for (&p.a, &p.b) |*ta, *tb| {
        var t0 = nowNs(io);
        std.mem.doNotOptimizeAway(sumU32(a));
        ta.* = @intCast(nowNs(io) - t0);
        t0 = nowNs(io);
        std.mem.doNotOptimizeAway(sumU32(b));
        tb.* = @intCast(nowNs(io) - t0);
    }
    std.mem.sort(u64, &p.a, {}, std.sort.asc(u64));
    std.mem.sort(u64, &p.b, {}, std.sort.asc(u64));
    return p;
}
// A/A test, alternating: A, B, A, B, ... so slow drift hits both sides equally.
aa_alternating :: proc(a, b: []u32) -> (p: Pair) {
	keep(sum_u32(a))
	keep(sum_u32(b))
	for i in 0 ..< AA {
		t0 := time.tick_now()
		keep(sum_u32(a))
		p.a[i] = time.tick_since(t0)
		t0 = time.tick_now()
		keep(sum_u32(b))
		p.b[i] = time.tick_since(t0)
	}
	slice.sort(p.a[:])
	slice.sort(p.b[:])
	return
}

Zig iterates the two arrays in lockstep with for (&p.a, &p.b) |*ta, *tb|; Odin uses a named result and a bare return. The program prints the B/A ratio of medians for every round; the chart below shows the 31 samples per side from the first round of the final benchmark run. Here are the medians of that round:

  • Zig: sequential A 12.0 µs against B 12.9 µs, a false difference of several percent; alternating A 15.1 µs against B 15.1 µs, identical.
  • Odin: sequential 7.97 µs against 7.87 µs, about a percent apart; alternating 7.98 µs against 7.98 µs.
  • Rust did the opposite: sequential 10.8 µs against 10.8 µs agreed, while alternating 9.68 µs against 10.8 µs reported a false difference of about a tenth.

Two of the three languages show the textbook picture: a sequential comparison of a function with itself finds a "winner", and alternation removes it. Rust's round shows that one A/A round is itself a noisy sample: the error landed on the alternating pair, whose A side has a long tail of slow runs in the chart, and in earlier runs the big sequential error moved between languages. Without counters we cannot say why, and that is the point: you rarely know. Alternation spreads noise evenly on average, so read the spread across all seven rounds, not one ratio.

"I ran the old version, then the new, and it was 10% faster" says nothing until old against old has been run the same way. Build both into one binary and interleave them; if the A/A error is 5%, nothing under 5% is a result.

Worked example: is a 6% win real?

Suppose a hot/cold split of a particle struct (Chapter 4) makes your update loop 6% faster on a cloud VM, median of seven, measured A-then-B. Apply the chapter:

  1. Floor and plausibility. The loop takes 2.1 ms for a million particles, 2.1 ns each: far above the timer floor and below nothing physical. The checksums match. The measurement is of the right thing.
  2. Noise. Print the samples: the CV is 8%. A 6% difference is smaller than the noise of either side. With 8% CV and a 6% effect, the simulator's estimate is that the median of seven picks the wrong winner about 12% of the time (a single run, about 29%), and it asks for about 15 runs per side to get under 5%.
  3. Method error. Run an A/A test with the same harness. If sequential A/A shows 5% on this machine, the 6% is mostly method.
  4. Fix the method. Interleave A and B, 31 runs each, and pin. Suppose the alternating result is 9% with an A/A error of 1%: now you have a result.
  5. Explain it. The split cut the bytes read per particle from 32 to 24, so a memory-bound loop should gain up to 25%. A 9% gain says the loop is partly compute-bound. On a machine with counters, perf stat would confirm it with a cache-miss count that falls by about a quarter.
  6. Weigh it. 9% of a loop that is 5% of the frame is under half a percent of the frame. Is the split worth the two arrays? If the particles are the 3%, yes. If they are not, Gray and Nethercote would revert.

(The numbers in steps 1, 2, 4 and 6 are illustrative inputs to the method, not measurements; the step-2 estimates are what the simulator figure reports for those settings.)

The machine you are measuring on

A benchmark result is a fact about a program on a machine. Cloud VMs like this orb add four sources of error that a desktop mostly lacks, and each has a cheap mitigation.

Scheduling and pinning. The kernel may move a thread between cores mid-run, which throws away its warm L1 and L2. Pinning with taskset -c 2 ./bench forbids that. Here CPUs 0/1 and 2/3 are hyperthread pairs (lscpu -e), so single-threaded runs use CPU 2, away from the interrupts on CPU 0, and two-thread runs use 0 and 2. Inside a VM that pins a virtual CPU, which the host can still move.

Steal time. When the hypervisor runs someone else on "your" core, the guest's clock keeps ticking. Linux counts that time as steal, the eighth number on the cpu line of /proc/stat[17], and vmstat 1 shows it in the st column. On this orb it was 1,901 ticks out of about four million at the time of writing: small on average, but steal arrives in bursts, which is what the long right tails above look like.

Frequency. Modern cores change their clock with temperature, power and how many cores are busy. On bare metal, fix the governor (cpupower frequency-set -g performance) and disable turbo. This guest exposes no cpufreq directory at all, so the frequency is whatever the host decides and we cannot even read it. That is another reason to alternate: a frequency change between the A block and the B block becomes a "speed-up".

Shared caches and memory. The 54 MiB L3 belongs to the host, and only a few MiB of it behave like ours in practice (Chapter 2), so a neighbour streaming through memory evicts our lines and competes for bandwidth. That is the 16–24% CV on the 16 MiB kernel against about 1–4% at 16 KiB.

One mitigation covers all of these: report the machine. code/bench_all.sh writes code/results/machine.txt (CPU, topology, caches, hypervisor, compilers, pinning, date) first. A number without its machine is not wrong, but nobody can check it.

Look at your own machine before you benchmark on it:

lscpu -e=CPU,CORE,SOCKET,L1d:L1i:L2:L3      # which logical CPUs share a core
head -1 /proc/stat                           # cpu user nice system idle iowait irq softirq steal ...
vmstat 1 5                                   # the st column is steal time
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor 2>/dev/null
cd code && taskset -c 2 cargo run --release -q -p ch12_measure_and_know_when_not_to

Tools that see what a stopwatch cannot

A stopwatch tells you how long, not why; every hardware explanation in this book has been an inference from timings. This orb has no counters and none of these tools, so the commands below are for you to run; no output is shown because we could not produce honest output here.

perf stat: count the events

perf stat runs a program and reads the CPU's counters for it[18]. For layout work, the useful events are cycles, instructions (their ratio is IPC) and cache misses at each level:

perf stat -e cycles,instructions,cache-references,cache-misses,L1-dcache-load-misses,LLC-load-misses \
    taskset -c 2 ./target/release/ch04_aos_soa_hot_cold
perf stat -r 10 ./bench          # ten repetitions; prints mean and ± spread for each counter
perf record -g ./bench && perf report   # where the cycles went, by function

If SoA beats AoS because it moves fewer bytes, its miss count should fall by about the ratio of bytes read; if it does not, your explanation is wrong. Many VMs report these events as "not supported".

Cachegrind: counts that barely move with noise

Valgrind's Cachegrind runs the program under instrumentation and counts the instructions executed (Ir) per line of source[19]. It is tens of times slower than native, but instruction counts are nearly deterministic: the same binary gives almost the same counts on a noisy VM, a laptop or CI (disable address-space randomisation with setarch -R, which the manual says perturbs results). That makes it the right tool for "did this change reduce instructions?" when wall-clock time is too noisy to answer. Its optional cache simulation is off by default, and the manual itself warns that it is "basic and unlikely to reflect the behaviour of a modern machine", ignores kernel activity, and recommends a hardware-counter profiler such as perf for real miss counts.

valgrind --tool=cachegrind --cache-sim=yes ./bench --quick
cg_annotate cachegrind.out.<pid>                  # per-function and per-line Ir, D1mr, DLmr ...
cg_diff cachegrind.out.before cachegrind.out.after # what a change did, event by event

pahole, -Zprint-type-sizes, and compile-time size checks

Layout bugs are cheaper to catch at build time than with a profiler. pahole reads the DWARF debug info of any binary (C, Zig, Odin or Rust) and prints each struct with its offsets, holes and cache-line boundaries[20]. Linux kernel developers use it constantly: Eric Dumazet found and removed 24 bytes of holes in tcp_sock with it, and pahole --reorganize proposes a better order[21].

pahole -C Particle ./zig-out/bin/app     # one struct: offsets, sizes, /* XXX 2 bytes hole */, cachelines
pahole --reorganize -C Particle ./app    # suggested field order with the bytes saved
cargo +nightly rustc --release -- -Zprint-type-sizes   # Rust: every type's size, padding and enum variants (nightly only)
objdump -d --no-show-raw-insn -M intel ./bench | less  # read the machine code the loop became
cargo rustc --release -- --emit asm      # or: zig build-obj -O fast -femit-asm=out.s main.zig

On stable Rust the tool you can rely on is the language itself: all three languages can assert a size at compile time, so a hot record cannot silently grow, and print offsets at run time. Chapter 3 introduced these asserts; here they guard a 28-byte particle:

/// A layout guard: the build fails if someone grows the hot record.
#[allow(dead_code)] // only its layout matters in this program
#[derive(Clone, Copy)]
struct Particle {
    pos: [f32; 3],
    vel: [f32; 3],
    alive: bool,
    kind: u8,
}
const _: () = assert!(size_of::<Particle>() == 28);
/// A layout guard: compilation fails if someone grows the hot record.
const Particle = struct { pos: [3]f32, vel: [3]f32, alive: bool, kind: u8 };
comptime {
    std.debug.assert(@sizeOf(Particle) == 28);
}

test "Particle stays 28 bytes" {
    try std.testing.expectEqual(28, @sizeOf(Particle));
    try std.testing.expectEqual(4, @alignOf(Particle));
}
// A layout guard: compilation fails if someone grows the hot record.
Particle :: struct {
	pos:   [3]f32,
	vel:   [3]f32,
	alive: bool,
	kind:  u8,
}
#assert(size_of(Particle) == 28)

Zig adds a second form: a test block, run with zig test main.zig, which reports a size change as a failing test rather than a compile error. The programs also print the offsets, and they disagree:

rust  (d) Particle: 28 B, align 4; pos @0, vel @12, alive @25, kind @24
zig   (d) Particle: 28 B, align 4; pos @0, vel @12, alive @24, kind @25
odin  (d) Particle: 28 B, align 4; pos @0, vel @12, alive @24, kind @25

Same size, different order. Rust's default representation promises nothing about field order and here placed kind before alive; Zig and Odin kept declaration order for this struct (Zig is allowed to reorder plain structs but had no reason to; Odin always keeps declaration order). If any code depends on the order, say a file format or a GPU buffer, that is a bug waiting in Rust until you write #[repr(C)], and in Zig until you write extern struct. Size asserts catch growth; only offset_of checks catch reordering.

Reading the assembly also explains a gap in this chapter's own numbers: the 16 KiB u32 sum takes 810 ns in Zig against 680 ns in Rust and 750 ns in Odin, because Zig 0.17.1's loop vectorizer is off (Chapter 4 explains why[22]), so its loop is scalar; Chapters 4, 8 and 10 use @Vector where SIMD matters.

Know when not to

Measurement cuts both ways. It is how you prove that a data-oriented rewrite won, and it is how you find out that it did not, or that it won something you did not need. The strongest critiques of DOD come from people who practise it.

"Not worth the extra hassle"

Niklas Gray, who built the Bitsquid and Our Machinery engines around data-oriented ideas, finds SoA "not worth the extra hassle" in most cases[2] (Chapter 4 quotes him in full). His AoS is still a flat array with stable indices; what he declines is only the last step, splitting every struct into columns by default.

Modifiability

Lucian Radu Teodorescu's ACCU essay revisits Acton's principles and states the trade-off precisely: "the more data-oriented a system becomes, the harder it is to make a change when the data needs to change; the less data-oriented a system is, the more difficult it is to make a change when data remains the same."[3] A layout tuned to today's access pattern encodes that pattern, so a feature that needs a field the hot loop never read touches every array. Noel Llopis, who named the approach in 2009, argued that transform-focused code is small functions with few dependencies[23]. Both are right, about different phases of a project: restructure data once its shape has settled.

The abandoned change

Nicholas Nethercote has spent a decade shrinking the Rust compiler's types, with real wins, and he documents the failures too. In 2018, after a Token had gone from 32 to 24 bytes for a small win, he took it to 16: "That change reduced it to 16 bytes, but produced a negligible speed-up and made the code uglier, so I abandoned it."[4] That sentence is the whole method of this chapter: he made the change, measured it, weighed the cost in code, and reverted. Not every byte saved is worth keeping.

Algorithm first

Aras Pranckevičius's toy mesh path tracer records every optimization step as a branch[5]. Going multi-threaded took the teapot scene to 18.9 Krays/s. A simple bounding volume hierarchy took it to 6,978: about 370× from changing the algorithm. Naive SIMD on top added 1.28×.

Zig's self-hosted compiler makes the same point from the other side. Zig 0.10 replaced the C++ bootstrap compiler with one built on the data-oriented AST, ZIR and AIR of Chapter 11. Building the compiler itself, peak memory fell from 9.6 GiB to 2.8 GiB, 3.5× less, but wall-clock time went from 43 to 40 seconds, only 7% faster, because, as the notes imply, LLVM code generation dominated the build[6]. DOD fixed what it touched. It did not touch the bottleneck. Layout work multiplies whatever the algorithm leaves; make the big division first.

Same patch, different hardware

In 2023 Coco Li at Google reorganized the hot fields of tcp_sock, net_device and other core networking structs into read-mostly cache-line groups, with build-time checks so they stay grouped; it shipped in Linux 6.8[7]. The cover letter reports CPU seconds per tcp_rr round trip:

The same patch saved 40% of CPU on one vendor's servers and cost 3% at low load on another's. A layout result is a result about a machine; if you ship to several, measure on several.

Batching moves the cost

TigerBeetle's batches (Chapter 7) had a cost at low load. One user loaded a million transfers in 1,000 batches of 1,000, and each replica wrote about 27 GB; a thousand one-transfer batches after that, about 10 KB of data, wrote another 17 GB, so each lone transfer cost roughly 600 times the bytes of a transfer in a full batch, because a partly full batch still paid for whole storage writes[8]. The fix, PR #2592, made small batches cheaper: at 256 transfers per batch it raised throughput 4.25× while writing a twelfth of the bytes. Batching does not make per-item costs vanish; it moves them into latency, into the API, and into the code that handles the partly full batch.

Muratori's own caveats

Casey Muratori's shapes benchmark[9], which Chapter 1 cites and partly reproduces, was "a demonstration and not an explanation"[10]: the fastest layout is not available when types cannot be segregated into separate arrays (Chapter 1 has his caveats).

Knuth, in full

Every argument about optimization eventually quotes six words of Knuth. Here is the passage they come from, from "Structured Programming with go to Statements" (1974)[1]:

"We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%. A good programmer will not be lulled into complacency by such reasoning, he will be wise to look carefully at the critical code; but only after that code has been identified. It is often a mistake to make a priori judgments about what parts of a program are really critical, since the universal experience of programmers who have been using measurement tools has been that their intuitive guesses fail."

Read whole, it is an argument for measurement, written by someone who spent the rest of the paper optimizing loops. Data-oriented design fits it: its claim is not "optimize everything early" but "know your data", which is how you find the critical 3%. Some decisions, like a pointer graph across a whole compiler, are expensive to change later, so the data's shape deserves thought before the profile exists and a check after it does.

A DOD checklist

Everything in this book compressed into the questions to ask before, during and after a data-oriented change:

  1. Find the 3%. Profile the real workload. Name the loop that matters and how much of the time it takes.
  2. Check the algorithm. A better complexity class or less work beats any layout (BVH 370× vs SIMD 1.28×).
  3. Count the things. Where there is one, there are many: if there are only a few, leave them simple.
  4. Know what the loop reads. Bytes used per byte fetched; fields touched per record; is the data streamed or chased? (Ch 2, 4)
  5. Shrink before you split. Remove padding, narrow types, out-of-band bools, assert the size. (Ch 3)
  6. Replace pointers with indices and allocate by lifetime, in arenas and pools. (Ch 5, 6, 11)
  7. Split hot from cold, or go SoA, when the hot loop reads a few fields of many records. (Ch 4)
  8. Process by kind, in batches, instead of branching per item. (Ch 7, 9)
  9. Vectorize and parallelize last, on data that is already contiguous. (Ch 8, 10)
  10. Measure honestly: keep-alive, hidden inputs, warm-up, median, checksum, timer floor, A/A test, alternation, the machine written down.
  11. Weigh the code. If the gain is inside the noise or the code got uglier, revert. Nethercote did.

Caveats

  • One noisy VM. The A/A errors change from run to run; the lesson is that they exist and alternation shrinks them.
  • The simulator's noise is independent. Real noise is correlated in time, which hurts sequential comparisons more; the A/A test measured that.
  • No counters. The tool sections show commands we could not run here. The "why" behind the A/A drift and the 16 MiB tail is an inference.
  • Cited numbers are cited. The path tracer, Zig 0.10, netdev and TigerBeetle figures are from their authors, on their hardware.

Exercises

Your benchmark of a 4096-element loop reports 41 ns in Rust. The timer floor is 44 ns. Name the two distinct ways the optimizer might have produced that number, and the fix for each.

Dead-code elimination (the result is unused): fix by passing the result through black_box. Constant folding or closed-form replacement (the inputs are visible at compile time): fix by passing the input through black_box or building it from a runtime seed. The second one survives a checksum, because the answer is still correct.

Odin's timer floor here is about 137 ns. You want to time a function that takes about 50 ns. How do you design the measurement?

Put a loop of, say, 10,000 calls inside each timed region (with each result fed into keep, and inputs that vary per call), divide by 10,000, and take the median over runs. Each sample is then about 0.5 ms, so the floor is a few hundredths of a percent of it.

Seven runs give 100, 101, 101, 102, 103, 104 and 190 µs. Compute the mean, the median and roughly the CV. Which would you report, and what else would you say?

Mean ≈ 114.4 µs, median 102 µs. The standard deviation is about 33 µs, so the CV is about 29%, all from one outlier. Report the median, and say that one run in seven was nearly 2× slow: on a VM that is likely steal or a neighbour, and it is worth checking whether it recurs.

In the simulator figure, set the effect to 2% and the noise to 10%. How many runs per side does the counter ask for, and what does that tell you about chasing 2% wins on a cloud VM?

About 209. Even with 51 runs per side, the simulator's median verdict is still wrong about one time in five. Two-percent effects on a 10% CV machine are not practically measurable by wall clock; use instruction counts (Cachegrind, perf stat), a quieter machine, or a bigger kernel.

Why does alternating A and B help against frequency changes and noisy neighbours, but not against a difference in where the two buffers sit in memory?

Alternation spreads anything that varies over time evenly across both sides. A difference in placement (alignment, which cache sets or physical pages a buffer uses) is fixed for the life of the process and always hits the same side. To cancel that, swap which buffer is "A" in a second run, or allocate fresh buffers per round.

The Rust Particle printed alive @25, kind @24. Write the one-line change that makes Rust match Zig and Odin, and the assert that would catch a future reorder.

Add #[repr(C)] above the struct. Then const _: () = assert!(std::mem::offset_of!(Particle, alive) == 24); turns any reorder into a compile error.
