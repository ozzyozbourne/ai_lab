    Part VI · Chapter 24

    CUDA Graphs: Capture, Replay and What Gets Baked

    One mjw.step is about a hundred kernel launches, each issued by Python. A CUDA graph records those launches once and replays all of them with a single call. That is the standard way to run MJWarp on a GPU, and it comes with one rule you must understand exactly: the graph freezes every decision Python made while recording, and it remembers the addresses of your arrays, not their values.

    Expert About 75 min· Prerequisites: Ch 6, Ch 7 (Ch 20 recommended)

    You will learn

    • How to capture mjw.step (and your own kernels) with wp.ScopedCapture and replay it with wp.capture_launch.
    • What is baked into a graph (Python branches on m.opt.*, sizes, array addresses) and what stays live (array contents).
    • The knob board: which Option fields update live, which compile new kernels, and which need a recapture, measured on a real run.
    • How conditional graph nodes (wp.capture_while, wp.capture_if) let the GPU loop the solver by itself, and the fallback for CUDA older than 12.4.
    • How to measure eager vs graph throughput correctly, and the reusable my_env.capture_step helper.

    In Colab: Runtime > Change runtime type > GPU, then run the first cell. Every example also runs on CPU: Warp 1.19 can record and replay graphs on its CPU device. CPU timings in this chapter are CPU numbers, never GPU performance.

    Before you start: recap

    • A CUDA graph records launches once and replays them; conditional nodes loop on device; Ch 7 §10. This chapter owns the topic: the code, the rules and the measurements.
    • arr.assign(x) changes the contents of an existing array; d.qpos = wp.array(x) replaces the object with new memory (Ch 6 §5).
    • An eager mjw.step of a tiny model is about 100 launches with a fixed cost each (Example 24.1 counts 104 for the pendulum; Ch 6's model needs ≈95), so throughput grows with nworld until the device is full (Ch 6 §11).
    • The first call compiles every kernel (JIT, then a disk cache); a value used through wp.static is a compile-time constant, so a new value means a new kernel (Ch 4 §7, §8).
    • GPU launches are asynchronous: call wp.synchronize() before you stop a clock (Ch 4 §10).
    • The solver iterates until every world converged or m.opt.iterations is reached, and writes d.solver_niter per world (Ch 20).

    1Why graphs: the cost is in the launching

    Every MJWarp function you call from Python, from mjw.step down to smooth.kinematics, ends in calls to wp.launch or wp.launch_tiled. Each launch is a small piece of Python work: Warp checks and packs the arguments, finds the compiled kernel and hands it to the driver. That costs a few microseconds on the host, whatever the kernel does. Example 24.1 counts the launches in one step of the double pendulum: 98 wp.launch + 6 wp.launch_tiled.

    Now think about a small model on a big GPU. A kernel over a few thousand worlds may finish in a few microseconds too. So the GPU spends much of its time waiting for Python to issue the next launch: the kernels are cheap, the launching is not. The repository's own tutorial notebook says it plainly: mjw.step "dispatches hundreds of Warp function calls to the GPU serially, each with a small dispatch overhead cost". The solver adds a second, worse cost: to decide whether to run one more iteration it needs a counter that lives on the GPU, and copying it to the host means waiting for the GPU to finish, every iteration.

    A CUDA graph removes both costs. You run one step while Warp is recording. The result is a graph: a list (in general a DAG) of kernel nodes with their arguments filled in. Replaying it is one host call; the driver then feeds the GPU node after node with no Python in between. The widget below is a cartoon of the two timelines. Move the slider: more worlds make each kernel longer, and at some point the GPU is busy even in eager mode.

    Two consequences follow, and they organize this chapter:

    1. Graphs are the normal way to run MJWarp on a GPU. mjwarp-testspeed times exactly this: _src/cli.py::unroll captures the function once inside wp.ScopedCapture and then calls wp.capture_launch(graph) per step.
    2. A graph is a recording. Whatever Python decided while recording (which kernels, which branches, how many iterations, which arrays) is frozen. Only the numbers inside the arrays are read again on every replay. Most bugs with graphs come from forgetting this.

    2The canonical pattern: warm up, capture, replay

    The whole API is two names: the context manager wp.ScopedCapture() and the function wp.capture_launch(graph). Here is the pattern every MJWarp GPU program uses:

    mjw.step(m, d)                        # 1. warm-up: compile (or load) every kernel
with wp.ScopedCapture() as capture:   # 2. record one step: launches are recorded, not run
    mjw.step(m, d)
graph = capture.graph

for _ in range(1000):                 # 3. replay: one call runs the whole recorded step
    wp.capture_launch(graph)
wp.synchronize()                      # wait for the device before reading results or clocks

    Look at the three phases through d.time, which mjw.step advances by m.opt.timestep (0.01 s for the pendulum). The warm-up step runs, so time becomes 0.01. Capturing does not run the step, so time stays 0.01. Each replay runs it, so five replays give 0.06. Think of a video recorder: capture is REC, replay is PLAY.

    Walk through the same run one state at a time. The tape at the top fills during capture; the counter only moves on warm-up and replay.

    Warm up, record, replay

    Pitfall: no host reads inside a capture

    Inside the with block, do not call .numpy(), .item(), print(arr) or anything else that copies device data to the host. On a GPU such a copy needs the device to finish, which is not possible while a stream is being recorded. The repository's CONTRIBUTING.md makes this a rule for MJWarp itself ("Avoid CPU-GPU synchronization (.numpy(), .item(), D2H copies) during simulation steps"). Read results after wp.capture_launch, outside the block. wp.printf inside kernels is fine.

    Going deeper: is the warm-up step needed? What does capture do on CPU?

    Warm-up. The warm-up is a habit, not a law. _src/cli.py::unroll (the core of mjwarp-testspeed) captures without one, and reports the capture time as jit_duration: on CUDA 12.3+ drivers Warp can load modules while a stream is being captured. On older drivers Warp may need to load modules before capture (see the force_module_load argument of wp.ScopedCapture). The course examples warm up because it keeps JIT time out of the capture and makes Example 24.1 easy to read. The helper my_env.capture_step does not warm up, so calling it never advances your simulation.

    CPU. Warp 1.19's ScopedCapture docstring says it "works on both CPU and CUDA devices". On CPU the launches are recorded into Warp's API capture (APIC) stream, and capture_launch "replays recorded operations in a C++ loop inside Warp". That is why every example in this chapter runs here, and why a replayed graph is much faster than eager stepping even on CPU: the Python per-launch work disappears. The CPU device still runs the kernel threads one after another, so CPU numbers say nothing about GPU speed.

    Allocations. Some integrators allocate inside the step (forward.py::rungekutta4 clones qpos and qvel; euler allocates scratch for implicit damping). Those allocations are recorded with the graph as well. What you cannot do is allocate inside the body of a conditional node (§5): the source says so in several places ("inside wp.capture_while, where memory cannot be allocated"), which is why MJWarp preallocates solver scratch.

    3Baked vs live: what a graph remembers

    While you record, mjw.step runs as ordinary Python. It reads m.opt.integrator and picks a function (forward.py::step branches with if m.opt.integrator == IntegratorType.EULER: euler(m, d) elif ... RK4 ...); it reads sizes like m.nv and d.nworld to choose launch dimensions; it calls kernel factories with Python values; and it passes array objects to wp.launch. A recorded launch stores two kinds of things:

    • Baked (frozen at capture time): which kernels are in the graph and in which order (every Python if and for already ran), each launch's dimensions, every scalar argument (a Python int or float passed as an input, such as m.opt.iterations), every compile-time constant inside the kernels (values read through wp.static or used to build a kernel), and the device address of every array argument.
    • Live (read from memory on every replay): the contents of those arrays. That includes all of d.* and every model field that is an array: d.ctrl, d.qpos, d.mocap_pos, m.body_mass, m.geom_friction, and the array-valued options m.opt.timestep, m.opt.gravity, m.opt.tolerance, ...

    The picture: the graph is a circuit board soldered at capture time. Arrays are sockets: you can change what flows through a socket (assign new contents), and the circuit sees it. Python ifs are switches that were soldered in one position. And if you replace an array object, you plug in a new socket somewhere else, but the board is still wired to the old one.

    Example 24.2 tests three changes after capture. Each line restarts all worlds from the same state, runs 20 steps eagerly and 20 replays, and compares.

    Read part 3 carefully. After m.opt.integrator = RK4, eager stepping really uses RK4 (the positions change), but the replay is bit-for-bit the old Euler result (max |graph - eager with OLD value| = 0). Nothing warns you. Also note the order in the script: restart() uses .assign() and .zero_() on the existing arrays, never new ones, precisely so that the graph keeps working.

    Recall from Ch 6

    Ch 6 §5 owns replace vs assign: d.qpos.assign(x) writes into the existing memory, while d.qpos = wp.array(x) rebinds the attribute to a new array. Eagerly both work. With a graph only one does, as Example 24.3 shows.

    The replaced array still says z = 2.0 after 50 replays: the graph never touched it. The old array, which d no longer points to, kept falling (from about 1.0, where the warm-up left it, to 0.95). The two fixes give the same answer, 1.95 m after 50 steps of 2 ms. In practice: after a capture, write inputs with .assign(), .fill_(), .zero_(), wp.copy() or your own kernels, and recapture whenever you replace an array. Helpers from earlier chapters were written this way on purpose: my_env.randomize (Ch 10) keeps its seed in a one-element device array, so a captured graph that contains it uses the current seed, and my_env.reset_done (Ch 8) resets in place.

    4The knob board: live, recompile or recapture

    The Option dataclass in _src/types.py tells you most of the answer by its field types. Eleven fields are declared as arrays with a "*" (batchable) leading dimension: timestep, tolerance, ls_tolerance, noslip_tolerance, ccd_tolerance, sleep_tolerance, gravity, wind, magnetic, density, viscosity, plus the warp-only impratio_invsqrt. Kernels read them as opt_timestep[worldid % opt_timestep.shape[0]], so they are live, and they can even differ per world (Ch 10). Everything else is a Python int or bool: integrator, cone, solver, iterations, ls_iterations, ccd_iterations, disableflags, enableflags, broadphase, graph_conditional, warn_overflow, deterministic, ... A captured graph never sees a change to those. Among them there are two different costs:

    • Recapture only. The value is used by Python control flow or passed as a plain scalar launch argument. Eager stepping picks up the change at once, with the kernels that are already compiled. Example: iterations is passed to _solve_done and _solve_beta_finalize_tiled (4.0.1 wheel; _solve_search_update_cg_tiled at the dev commit) as the scalar input opt_iterations; integrator is a branch in forward.py::step.
    • Recompile and recapture. The value is a compile-time constant of some kernel: it goes into a kernel factory (often @cache_kernel) or through wp.static. A new value means a new kernel, compiled on first use. Example: solver.py::_linesearch_iterative_kernel(ls_iterations, cone_type, ...) sets LS_ITERATIONS = ls_iterations and unrolls for _ in range(LS_ITERATIONS); forward.py::_next_time_builder(warn_overflow) tests wp.static(bool(warn_overflow & OverflowType.NEFC)). A Python branch can cost a compile too: when it leads to kernels whose module has not been loaded yet, the first step after the change compiles them. Switching solver or broadphase does that, and so do some disableflags bits (others only change which already-loaded kernels launch).

    Example 24.6 measures this instead of trusting the reading. For each knob it captures a step of box_stack(3) with the CG solver, changes the knob, and runs 10 steps three ways from the same saved state: replaying the old graph, stepping eagerly with the new value, and stepping eagerly with the old value. It also counts how many Warp modules the first eager step after the change had to load: a non-zero count means new compiled code.

    How to read the columns: |g-new| is the largest difference between the replay and eager stepping with the new value, |g-old| the same against the old value, and |new-old| tells you the change matters at all. timestep, gravity and tolerance are live: the replay equals eager stepping with the new value exactly. iterations and integrator are baked but need no new code: the replay equals the old run, and the eager step loaded no new module. ls_iterations loaded one new module (the linesearch kernel built for LS_ITERATIONS = 1), and warn_overflow loaded four (it is a wp.static constant in several kernel factories). warn_overflow only changes printed warnings, so there is no physics to compare (|new-old| = 0), but the compile count proves the graph cannot contain the new kernels.

    Note: the "+mod" column depends on history

    A module is compiled (or loaded from the disk cache) once per Python process. If an earlier cell already stepped with warn_overflow = ALL (the default that put_model sets), those modules are loaded and the count is 0. That is why Example 24.6 starts every knob from warn_overflow = 0 and why the notebook runs it with !python in a fresh process. The verdict "recapture" is always right for a baked knob; "recompile" tells you the first eager step after the change will also pay a compile.

    Pitfall: m.opt.timestep = 0.005

    Do not assign a Python float to an array option. m.opt.timestep = 0.005 replaces the array with a float. The next eager mjw.step fails (verified: RuntimeError: Error launching kernel ..., argument 'opt_timestep' expects an array ... but passed value has type float), and an existing graph silently keeps reading the old array. Write m.opt.timestep.fill_(0.005) (or .assign([0.005])) instead.

    Going deeper: why does cache_kernel exist?

    _src/warp_util.py::cache_kernel wraps kernel factories and memoizes them on their arguments; its only comment is "caching kernels to avoid crashes in graph_conditional code". A factory that builds a new wp.kernel object on every call would create a new module during recording, including inside the body of a capture_while (§5). Caching returns the same kernel object for the same arguments, so a recorded launch always refers to a kernel that already exists. Note its key: arrays are hashed by .size alone, so two different arrays of the same size share one kernel, and the wrapper accepts positional arguments only: a keyword argument raises TypeError (warp-perf research, pitfall 13). Pass scalars positionally if you use it for your own factories (Ch 26).

    5Conditional nodes: loops and branches that run on the device

    A plain graph is a fixed list. But the solver's work is not fixed: how many iterations it needs depends on the state, and it changes every step. Eagerly, the loop lives in Python and asks the GPU "is anyone still solving?" after each iteration, which costs a device-to-host copy and a wait. CUDA 12.4 added conditional nodes: graph nodes that read an integer in device memory and decide, on the device, whether to run a sub-graph (an if node) or to keep running it (a while node). Warp exposes them as two functions:

    • wp.capture_while(condition, while_body, **kwargs): run while_body(**kwargs) as long as condition[0] is non-zero. "The while_body callback is responsible for updating the condition value so the loop can terminate" (Warp docstring).
    • wp.capture_if(condition, on_true=None, on_false=None, **kwargs): run one of two callbacks depending on condition[0].

    Both also work without a capture (they then evaluate the condition on the host, with a sync), and inside a capture they record a conditional node. MJWarp uses them only when m.opt.graph_conditional is true, which io.py::put_model sets by default. The main use is the constraint solver, in solver.py::_solve:

    nsolving = wp.full(shape=(1,), value=d.nworld, dtype=int)   # worlds not converged yet
...
if m.opt.iterations != 0 and m.opt.graph_conditional:
    # the iteration kernel (while_body) is repeatedly launched as long as nsolving is not zero;
    # when solver_niter reaches m.opt.iterations all worlds are marked converged
    wp.capture_while(nsolving, while_body=_solver_iteration, m=m, d=d, ctx=ctx, nsolving=nsolving,
                     compact=compact)
else:
    # "mostly for when JAX is used as it is currently not compatible with CUDA graph conditional"
    for _ in range(m.opt.iterations):
        _solver_iteration(m, d, ctx, nsolving, compact=compact)

    (Abridged from the 4.0.1 wheel; the comments paraphrase the source comments.) The done kernel of each _solver_iteration (_solve_done for Newton, the last launch; _solve_beta_finalize_tiled for CG, followed by the CG search-direction update) marks converged worlds as done and decrements nsolving; a world that reaches m.opt.iterations is marked done too, which guarantees the loop ends.     The physics is identical on this CPU run (difference 0): the loop exits early, and skipping converged worlds inside unrolled copies changes nothing. That is the price of the fallback on an old CUDA: lower m.opt.iterations to what your scene really needs (look at d.solver_niter, Ch 20) when you must run without conditional nodes.

    In the dev tree (commit 8f5b9f1) forward.py has more capture_if nodes for sleeping and waking (for example wp.capture_if(woke, on_true=sleep.update_sleep, m=m, d=d) and wp.capture_if(nslept, on_true=_on_slept)), and derivative.py calls capture_while(efm_nsolving, ...) whenever graph_conditional is set, without the wheel's and wp.get_device().is_cuda.     Going deeper: three rules for code inside a conditional body
    1. No allocation. The body is recorded once and replayed any number of times; a wp.zeros inside it cannot give you fresh memory per iteration. MJWarp preallocates: the SolverContext scratch, "effective-metric scratch for the solver iterations, which may run inside wp.capture_while" (solver.py), and passive.py/derivative.py take scratch arguments "when calling inside wp.capture_while, where memory cannot be allocated".
    2. No profiling scopes. warp_util.event_scope walks the Python stack and, if it is called from capture_while or capture_if, runs the function without recording events. That is why an EventTracer tree (Ch 7, Ch 25) shows the solver loop as one block.
    3. The body must end the loop. The condition is just an integer in device memory; a body that never writes it loops forever on the GPU. The solver guarantees termination by marking worlds done at m.opt.iterations; your own loops (Ch 26) need the same kind of cap.

    6CUDA 12.4 and the fallback

    Conditional nodes need CUDA 12.4 or newer, twice: Warp must be built with a 12.4+ toolkit and the driver must support 12.4+. wp.is_conditional_graph_supported() checks both (runtime.toolkit_version >= (12, 4) and runtime.driver_version >= (12, 4)). On a machine with no CUDA driver it returns False (it checks the process-wide toolkit and driver, not the current device); CPU graphs do not need conditional-node support.

    MJWarp checks once, in io.py::put_model, which calls warp_util.check_toolkit_driver():

    def check_toolkit_driver():
  wp.init()
  if wp.get_device().is_cuda:
    if not wp.is_conditional_graph_supported():
      warnings.warn("""
        CUDA version < 12.4 detected
        - graph capture may be unreliable for < 12.3
        - conditional graph nodes are not available for < 12.4
          Model.opt.graph_conditional should be set to False
        """, stacklevel=2)

    It only warns. Further down, the same put_model sets opt.graph_conditional = True regardless. So on an old toolkit the default model still asks for conditional nodes, and the capture fails. The course's fallback idiom (plan rule G), used in every capture example and inside my_env.capture_step:

    if wp.get_device().is_cuda and not wp.is_conditional_graph_supported():
    m.opt.graph_conditional = False     # fixed iteration counts instead of device-side loops

    Set it before capturing: graph_conditional is a Python flag read while recording, so it is itself a baked knob. (You can also pass it on the command line of the CLI tools, since io.py::override_model accepts "opt.graph_conditional=False".) Which case are you in? Colab's GPUs normally have recent drivers, so the check is silent there. Pick a scenario:

    This is the helper the running project gains in this chapter (examples/24-cuda-graphs/my_env_step24.py, embedded in the notebook with %%writefile). It applies the graph-conditional fallback, records nsub steps and an optional post(m, d) hook, and does not advance the simulation:

    def needs_conditional_fallback(device=None):
    """True when `device` is a CUDA device whose toolkit or driver is older than CUDA 12.4."""
    device = wp.get_device(device)
    return device.is_cuda and not wp.is_conditional_graph_supported()


def capture_step(m, d, nsub=1, post=None, verbose=True):
    """Record `nsub` calls of mjw.step(m, d), then `post(m, d)` if given, into one graph."""
    assert nsub >= 1, "nsub must be >= 1"
    device = d.qpos.device
    if needs_conditional_fallback(device) and m.opt.graph_conditional:
        m.opt.graph_conditional = False     # fixed iteration counts instead of device-side loops
        if verbose:
            print("capture_step: CUDA < 12.4, set m.opt.graph_conditional = False")
    with wp.ScopedCapture(device=device) as capture:
        for _ in range(nsub):
            mjw.step(m, d)
        if post is not None:
            post(m, d)
    return capture.graph

    7Measuring eager vs graph throughput

    Timing GPU code has three traps, and graphs add none: (1) the first call compiles, so warm up; (2) launches return before the work is done, so call wp.synchronize() before reading the clock; (3) report world-steps per second (nworld × steps / seconds), the number that matters for batched simulation. Example 24.4 does this for BALL_DROP over a sweep of nworld, with the ball resting on the floor so that every timed step has a live contact, eagerly and with a graph built by my_env.capture_step (§6). It takes the best of three runs to reduce noise from other processes.

    Read the two curves. Eager time per step is nearly flat (about 2.6 to 3.0 ms) from 1 to 64 worlds: it is Python launching about 100 kernels, and the kernels themselves are a small part. Only at 256 worlds does the kernel work show (4 to 6 ms across our runs). So eager world-steps/s grows almost linearly with nworld, the launch-overhead regime from Ch 6. Graph replay removes the Python part: at 1 world it is about 150x faster on this CPU. As nworld grows, the graph time grows too, because the CPU device runs kernel threads one after another, and the speedup shrinks to about 3 to 5x at 256 worlds (it varies from run to run on this shared CPU). On a GPU the graph curve behaves differently: the step time stays nearly flat while the GPU has idle lanes, then grows once the GPU is full. Where that happens depends on your GPU and model, which is exactly what the stretch exercise asks you to find.

    Tip: eager and graph can mix

    A graph replay goes into the same stream as ordinary launches, in order. When a control trajectory (--replay) or a keyframe is given, _src/cli.py::unroll launches its control-noise kernel _ctrl_noise eagerly before each wp.capture_launch(graph); that eager launch is synchronized and kept outside the timed region. Anything you do not want to record (a rare reset, a logging read) can stay outside the graph, as long as it does not replace arrays the graph uses.

    8One graph per control step: substeps and your own kernels

    A graph can hold anything you launch while recording, not just mjw.step. In reinforcement learning a control step is usually several physics steps (the "frame skip") followed by your kernels: observation, reward, done flags, maybe an auto-reset (Ch 8) and a re-randomization (Ch 10). Recording all of it makes a whole control step one host call:

    This is my_env.capture_step, the helper from §6: it applies the graph-conditional fallback, records nsub steps and an optional post(m, d) hook, and does not advance the simulation. Example 24.7 uses it for 4 substeps of CARTPOLE plus a reward kernel, and checks the result against the same work done eagerly.

    The difference is exactly zero on CPU: a graph runs the same kernels with the same inputs in the same order. On a GPU, a contact-free model like this one also replays identically; with contacts, the slot order of atomics can differ between any two runs, graph or not (Ch 22). Notice how the reward array is preallocated once and zeroed in place by restart(), and that reward reaches the kernel through the post closure: the graph holds its address.

    Pitfall: capturing a function that allocates its output

    A hook like def post(m, d): r = wp.zeros(n); wp.launch(k, ..., outputs=[r]); return r records a launch into memory allocated during capture, which your Python code never sees again. Allocate outputs before capturing and pass them in, as Example 24.7 does with reward.

    11Summary

    Key takeaways

    • with wp.ScopedCapture() as c: mjw.step(m, d) records about 100 launches without running them; wp.capture_launch(c.graph) replays them with one call. Warm up first or let the capture compile.
    • Baked: kernels and their order, Python branches on m.opt.*, launch sizes, scalar arguments, compile-time constants and array addresses. Live: array contents.
    • After capture, change inputs in place (.assign, .fill_, wp.copy, kernels). Replacing an array or changing a Python-valued option means recapture.
    • Knob board (measured): timestep, gravity, tolerance live; iterations, integrator recapture; ls_iterations, warn_overflow recompile + recapture.
    • graph_conditional=True makes the solver a capture_while loop on the device; False unrolls m.opt.iterations copies (same physics, many more launches).
    • Conditional nodes need CUDA ≥ 12.4 (toolkit and driver). put_model only warns; apply if wp.get_device().is_cuda and not wp.is_conditional_graph_supported(): m.opt.graph_conditional = False.
    • One graph can hold a whole control step: my_env.capture_step(m, d, nsub, post).
    • Warp 1.19 records graphs on CPU too; CPU timings are CPU numbers, never GPU performance.

    Stuck? See Troubleshooting (graph recapture, CUDA < 12.4 and graph_conditional, recompiles when changing static options) or the course map.
