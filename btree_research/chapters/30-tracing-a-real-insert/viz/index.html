Every earlier chapter taught one piece. This page puts the pieces in the order in which a real INSERT meets them, in two engines at once, and then shows why the production code that does it is written as a state machine.

1. One insert, two engines, six stages

Both trees below hold the same keys. A page holds at most four entries here (real pages fill up by bytes), so a few inserts are enough to see everything. Type a key from 1 to 99, or follow the suggestions in order: 27 makes PostgreSQL split a leaf while Turso only shuffles cells between neighbours; then 33 makes PostgreSQL's split climb to a new root while Turso's leaf simply has room; then 60 fits in both; then 12 finds all three Turso siblings full, so Turso allocates a page. A key that is already there stops at stage 2.

Both lanes are small models written for this page: four entries per page, single integer keys, the index only (not the table the row goes into, and not the commit record). Block numbers, split points and the number of steps are the models'. The order of the steps, the function names and the WAL record names are the engines'; "Turso" means its default WAL journal mode, in which one write transaction runs at a time.

2. The same insert when every page read may suspend it

This is the chapter's own code: the disk B+tree of chapter 12 with its put rewritten as an object that is called again and again. It never waits for the disk. When a page is missing it returns Io(page); when called again it continues from the state it recorded. The pool has few frames on purpose, so that pages are missing often. Between them the five inserts of the list reach all seven states: the first is the only one that enters push_root_leaf, and the last is the one in which the split climbs (insert_separator, push_root_interior, split_interior, and insert_separator again). That last tree uses the 128-byte toy pages of chapter 12's page, which are not a real format: with 4096-byte pages a full root has hundreds of children. Tick "drop unpinned pages" to make every state wait for its page.

What to take away

  • The stages are the same. Find the leaf, check uniqueness, make room, restructure, tell the parent, make it durable. Any B-tree engine has these six.
  • The answers differ because the concurrency differs. PostgreSQL lets many writers into the tree, so it needs high keys, right links and a flag for the moment between "split" and "parent knows". Turso, in the WAL journal mode traced here, admits one write transaction at a time, so its tree needs none of them and can afford to rewrite three siblings at once. (Its second journal mode, mvcc, lets transactions write concurrently, but into row versions kept outside the B-tree; the B-tree is still written by one pager transaction at a time.)
  • The log differs for the same reason. PostgreSQL logs each small step as it happens (so each step is recoverable alone); Turso logs whole pages at commit (so the transaction is all or nothing).
  • A resumable operation is the blocking code with its stack moved into an object. The state enum is the program counter, the path and the carry are the local variables, and their memory must outlive every call.
