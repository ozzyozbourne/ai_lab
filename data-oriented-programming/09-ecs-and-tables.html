Chapter 9

ECS and Thinking in Tables

Open any game's save file, or any compiler's symbol table, and squint. You will see rows, columns and keys. Somewhere along the way that data was turned into a forest of objects that point at each other, and the program spends its time chasing those pointers. An entity-component system (ECS) is what you get if you put the tables back: an entity is a key, a component is a table keyed by entities, and a system is a query that joins a few tables. This chapter builds a small ECS twice, once with sparse sets and once with one table per combination of components (archetypes), in Rust, Zig and Odin, and measures where each one wins. Then it lets the critics speak, because an ECS is one thing data-oriented design can produce, not the thing itself.

Your program is already a database

Richard Fabian's book has a chapter called "Relational Databases" that starts from an unlikely place: the setup script of a small dungeon level, full of calls like CreatePickup, AddDoor and SetRoomAsSpecial[1]. He pours all of that into one big table per kind of thing, and immediately the tables are full of holes. Only keys have an animation, and the armour has no colour tint, so those cells hold NULL. A room can have several doors and several pickups, so some cells hold lists.

Then he normalises it. First normal form says that "every cell contains one and only one atomic value. That is, no arrays of values, and no NULL entries"[1]. Each optional attribute moves into its own table keyed by the same id (PickupTints, PickupAnims), with rows only for the pickups that have one, and lists become many rows. Second and third normal form then store each fact once.

Fabian is candid that this looks wasteful at first: "normalisation appears to create more tables and fewer columns in each table". The payoff is the second observation in the same sentence: "there are only rows for things which matter". A loop over PickupTints never asks whether a tint is NULL, because the rows that would have held NULL do not exist. This is Chapter 7's existence-based processing, arrived at from the database side: whether a thing has a property is decided by which table it is in, not by a flag inside it. Adding monsters later means adding a Monsters table "without touching any of the original level data"[1].

Now rename the pieces. The PickupID column is an entity: a key that has no data of its own, which Fabian describes as "an alias ... it contains no data in and of itself, but merely acts as a handle". Each narrow table keyed by it is a component. A loop such as "for every pickup that has both a tint and an animation" is a join on the key, and the code that runs it is a system. Catherine West put it in one line in her RustConf 2018 keynote write-up: "ECS is just SQL for games"[2].

The one thing SQL does not tell you is how to lay the tables out in memory so that the join is fast. That is the whole engineering problem of an ECS, and there are two classic answers.

A world has 1,000,000 entities with Pos, 500,000 of them also have Vel, and 10,000 have Burning. A system needs Pos and Burning. If each component is its own keyed table, which table should the join loop walk, and how many lookups does it do in the other one?

Walk Burning, the smallest, and look each of its 10,000 entities up in Pos: 10,000 probes. Walking Pos instead would do a million probes to find the same 10,000 rows. Join order matters in an ECS for the same reason it matters in a database, and the sparse-set query below always drives from the smallest set.

An entity is a key with a generation

Before either storage, we need the keys. An entity id has the same problem as any index: it can outlive the thing it names, and the slot gets reused. Chapter 5 solved that with a generation counter per slot. An ECS uses exactly that pool, minus the values: the "values" are spread across the component tables. Our Entity is an index plus a generation, 8 bytes, and the allocator keeps one generation and one live bit per index and a LIFO free list of indices. Catherine West's version splits it the same way, into a "GenerationalIndexAllocator" and one "GenerationalIndexArray" per component, which is the ECS shape in miniature[2].

/// A generational entity id, as in Chapter 5: the index names a slot, the generation says
/// which occupant of that slot this id means.
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct Entity {
    pub index: u32,
    pub generation: u32,
}

    pub fn alive(&self, e: Entity) -> bool {
        let i = e.index as usize;
        i < self.live.len() && self.live[i] && self.generations[i] == e.generation
    }

    /// Caller checks `alive` first. Bumps the generation: every copy of `e` goes stale.
    pub fn despawn(&mut self, e: Entity) {
        let i = e.index as usize;
        self.live[i] = false;
        // Out of generations: retire the slot, as Chapter 5's pool does (wrapping would revive old ids).
        if let Some(g) = self.generations[i].checked_add(1) {
            self.generations[i] = g;
            self.free.push(e.index);
        }
    }
/// The index names a slot, the generation says which occupant of that slot this id means.
/// A packed struct compares with `==` as one 64-bit integer.
pub const Entity = packed struct(u64) {
    index: u32,
    generation: u32,
};

    pub fn alive(self: *const Entities, e: Entity) bool {
        return e.index < self.live.items.len and self.live.items[e.index] and
            self.generations.items[e.index] == e.generation;
    }

    /// Caller checks `alive` first. Bumps the generation: every copy of `e` goes stale.
    pub fn despawn(self: *Entities, gpa: Allocator, e: Entity) Allocator.Error!void {
        const g = &self.generations.items[e.index];
        self.live.items[e.index] = false;
        // Out of generations: retire the slot, as Chapter 5's pool does (wrapping would revive old ids).
        if (g.* == std.math.maxInt(u32)) return;
        g.* += 1;
        try self.free.append(gpa, e.index);
    }

// Caller checks entities_alive first. Bumps the generation: every copy of `e` goes stale.
entities_despawn :: proc(es: ^Entities, e: Entity) {
	g := &es.generations[e.index]
	es.live[e.index] = false
	// Out of generations: retire the slot, as Chapter 5's pool does (wrapping would revive old ids).
	if g^ == max(u32) {
		return
	}
	g^ += 1
	append(&es.free, e.index)
}

One small difference shows up already. Zig's Entity is a packed struct(u64), so e == other is a single 64-bit compare, and Zig does not let you write == on an ordinary struct at all. Rust derives PartialEq, and Odin compares structs field by field with == out of the box. All three compile the comparison to the same thing. Generations start at 1, so a zeroed Entity is never alive, and a slot whose counter would overflow is retired rather than wrapped, exactly as Chapter 5's pool does: it never goes back on the free list, so no old id can come back to life.

Storage one: a sparse set per component

A sparse set is three arrays. sparse is indexed by entity index and holds a position. dense holds the entities that have the component, packed with no holes. data holds their component values in the same order as dense. To find entity e's component, read d = sparse[e.index], check that dense[d] == e, and read data[d]. Michele Caini, the author of EnTT, gives the membership test as dense[sparse[element]] == element[4]. The structure is old: it is usually credited to Briggs and Torczon's 1993 paper "An efficient representation for sparse sets" [3], whose trick is that the check against dense makes it safe even if sparse was never initialised.

  • Insert appends: sparse[e.index] = dense.len, then push e and its value. O(1).
  • Remove is Chapter 5's swap-and-pop: move the last element into the hole, fix the moved element's sparse slot, pop. O(1), and the dense arrays stay packed. Caini notes that clearing the removed entity's sparse slot is optional, since the dense check fails anyway[4]; we clear it, so a miss is a single load.
  • Iterate is a straight walk over dense and data. It never sees a hole and never touches sparse.

This is where Chapter 5 left off: "Put swap-and-pop together with an id → index table and you have a sparse set". The difference from Chapter 5's pool is the direction of the promise. A pool promises that an item stays where it is, and a sparse set promises that iteration is dense. Try it below: tap an id in the top row to select it, then insert, remove or look it up.

/// Sparse array indexed by entity index -> position in the packed arrays.
/// `dense[i]` is the entity whose component is `data[i]`.
pub struct SparseSet<T> {
    sparse: Vec<u32>,
    dense: Vec<Entity>,
    data: Vec<T>,
}

impl<T> Default for SparseSet<T> {
    fn default() -> Self {
        Self { sparse: Vec::new(), dense: Vec::new(), data: Vec::new() }
    }
}

impl<T> SparseSet<T> {
    pub fn len(&self) -> usize {
        self.dense.len()
    }

    /// Two dependent loads: sparse, then dense. Comparing the whole Entity (with its
    /// generation) means a stale id fails here even if its index was reused.
    fn position(&self, e: Entity) -> Option<usize> {
        let d = *self.sparse.get(e.index as usize)? as usize;
        (self.dense.get(d) == Some(&e)).then_some(d)
    }

    pub fn get(&self, e: Entity) -> Option<&T> {
        self.position(e).map(|d| &self.data[d])
    }

    pub fn get_mut(&mut self, e: Entity) -> Option<&mut T> {
        self.position(e).map(|d| &mut self.data[d])
    }

    /// O(1): append to the packed arrays and point the sparse slot at the new position.
    pub fn insert(&mut self, e: Entity, value: T) {
        if let Some(d) = self.position(e) {
            self.data[d] = value;
            return;
        }
        let i = e.index as usize;
        if i >= self.sparse.len() {
            self.sparse.resize(i + 1, NONE);
        }
        self.sparse[i] = self.dense.len() as u32;
        self.dense.push(e);
        self.data.push(value);
    }

    /// O(1) swap-and-pop: the last element moves into the hole and its sparse slot is fixed.
    pub fn remove(&mut self, e: Entity) -> Option<T> {
        let d = self.position(e)?;
        let last = *self.dense.last()?;
        self.sparse[last.index as usize] = d as u32;
        self.sparse[e.index as usize] = NONE;
        self.dense.swap_remove(d);
        Some(self.data.swap_remove(d))
    }
/// Sparse array indexed by entity index -> position in the packed arrays.
/// `dense[i]` is the entity whose component is `data[i]`.
pub fn SparseSet(comptime T: type) type {
    return struct {
        const Self = @This();
        sparse: std.ArrayList(u32) = .empty,
        dense: std.ArrayList(Entity) = .empty,
        data: std.ArrayList(T) = .empty,

        pub const empty: Self = .{};

        pub fn deinit(s: *Self, gpa: Allocator) void {
            s.sparse.deinit(gpa);
            s.dense.deinit(gpa);
            s.data.deinit(gpa);
        }

        pub fn len(s: *const Self) usize {
            return s.dense.items.len;
        }

        /// Two dependent loads: sparse, then dense. Comparing the whole Entity (with its
        /// generation) means a stale id fails here even if its index was reused.
        fn position(s: *const Self, e: Entity) ?u32 {
            if (e.index >= s.sparse.items.len) return null;
            const d = s.sparse.items[e.index];
            if (d >= s.dense.items.len or s.dense.items[d] != e) return null;
            return d;
        }

        pub fn get(s: *const Self, e: Entity) ?*T {
            const d = s.position(e) orelse return null;
            return &s.data.items[d];
        }

        /// O(1): append to the packed arrays and point the sparse slot at the new position.
        pub fn insert(s: *Self, gpa: Allocator, e: Entity, value: T) Allocator.Error!void {
            if (s.position(e)) |d| {
                s.data.items[d] = value;
                return;
            }
            if (e.index >= s.sparse.items.len) {
                const old = s.sparse.items.len;
                try s.sparse.resize(gpa, e.index + 1);
                @memset(s.sparse.items[old..], none);
            }
            s.sparse.items[e.index] = @intCast(s.dense.items.len);
            try s.dense.append(gpa, e);
            try s.data.append(gpa, value);
        }

        /// O(1) swap-and-pop: the last element moves into the hole and its sparse slot is fixed.
        pub fn remove(s: *Self, e: Entity) ?T {
            const d = s.position(e) orelse return null;
            const last = s.dense.last().?;
            s.sparse.items[last.index] = d;
            s.sparse.items[e.index] = none;
            _ = s.dense.swapRemove(d);
            return s.data.swapRemove(d);
        }
// Sparse array indexed by entity index -> position in the packed arrays.
// `dense[i]` is the entity whose component is `data[i]`.
Sparse_Set :: struct($T: typeid) {
	sparse: [dynamic]u32,
	dense:  [dynamic]Entity,
	data:   [dynamic]T,
}

sparse_destroy :: proc(s: ^Sparse_Set($T)) {
	delete(s.sparse)
	delete(s.dense)
	delete(s.data)
}

// Two dependent loads: sparse, then dense. Comparing the whole Entity (with its
// generation) means a stale id fails here even if its index was reused.
sparse_position :: #force_inline proc(s: ^Sparse_Set($T), e: Entity) -> (int, bool) {
	if int(e.index) >= len(s.sparse) {
		return 0, false
	}
	d := int(s.sparse[e.index])
	if d >= len(s.dense) || s.dense[d] != e {
		return 0, false
	}
	return d, true
}

sparse_get :: #force_inline proc(s: ^Sparse_Set($T), e: Entity) -> ^T {
	d, ok := sparse_position(s, e)
	return &s.data[d] if ok else nil
}

// O(1): append to the packed arrays and point the sparse slot at the new position.
sparse_insert :: proc(s: ^Sparse_Set($T), e: Entity, value: T) {
	if d, ok := sparse_position(s, e); ok {
		s.data[d] = value
		return
	}
	if int(e.index) >= len(s.sparse) {
		old := len(s.sparse)
		resize(&s.sparse, int(e.index) + 1)
		for &x in s.sparse[old:] {
			x = NONE
		}
	}
	s.sparse[e.index] = u32(len(s.dense))
	append(&s.dense, e)
	append(&s.data, value)
}

// O(1) swap-and-pop: the last element moves into the hole and its sparse slot is fixed.
sparse_remove :: proc(s: ^Sparse_Set($T), e: Entity) -> (value: T, ok: bool) {
	d := sparse_position(s, e) or_return
	last := s.dense[len(s.dense) - 1]
	s.sparse[last.index] = u32(d)
	s.sparse[e.index] = NONE
	value = s.data[d]
	unordered_remove(&s.dense, d)
	unordered_remove(&s.data, d)
	return value, true
}

Comparing the whole Entity, generation included, gives stale-id detection for free. If entity 2v1 is despawned and its index is reused by 2v2, sparse[2] may point at a live row, but dense[d] holds 2v2, which is not equal to 2v1. Every program checks this at start-up and prints "despawned 2v1, respawn reused it as 2v2; the old id resolves to nothing in both storages".

Real sparse sets add two things this one leaves out. EnTT pages the sparse array, so that a huge entity index allocates one page rather than a giant array, at the cost of one more indirection on lookup that Caini says "has never shown up so far in profiling bottlenecks"[4]. And when a component needs stable addresses, EnTT can leave a tombstone instead of swapping, which keeps references valid but makes every iteration check for tombstones (Chapter 5 has the trade-off table)[22].

A query: walk the smallest set, probe the others

Each set is dense on its own, but a system that needs Pos, Vel and Hp has three sets in three different orders. The standard sparse-set query, as Sander Mertens' ECS FAQ describes it, "iterates all entities in one of the queried for components (usually the one with the least entities) and tests for each subsequent component if the entity has it"[8]. That is a nested-loop join with an index on the inner tables, and the outer table is the smallest one, as in the prediction above.

/// Join of three sets, driven by the smallest; the other two are probed per entity.
pub fn query3<A, B, C>(
    a: &SparseSet<A>,
    b: &SparseSet<B>,
    c: &mut SparseSet<C>,
    mut f: impl FnMut(&A, &B, &mut C),
) {
    let smallest = a.len().min(b.len()).min(c.len());
    if c.len() == smallest {
        for (e, vc) in c.iter_mut() {
            if let (Some(va), Some(vb)) = (a.get(e), b.get(e)) {
                f(va, vb, vc);
            }
        }
    } else if a.len() == smallest {
        for (e, va) in a.iter() {
            if let Some(vb) = b.get(e)
                && let Some(vc) = c.get_mut(e)
            {
                f(va, vb, vc);
            }
        }
    } else {
        for (e, vb) in b.iter() {
            if let Some(va) = a.get(e)
                && let Some(vc) = c.get_mut(e)
            {
                f(va, vb, vc);
            }
        }
    }
}
/// Join of three sets, driven by the smallest; the other two are probed per entity.
pub fn query3(a: anytype, b: anytype, c: anytype, ctx: anytype, comptime f: anytype) void {
    const smallest = @min(a.len(), b.len(), c.len());
    if (c.len() == smallest) {
        for (c.dense.items, c.data.items) |e, *vc| {
            const va = a.get(e) orelse continue;
            const vb = b.get(e) orelse continue;
            f(ctx, va, vb, vc);
        }
    } else if (a.len() == smallest) {
        for (a.dense.items, a.data.items) |e, *va| {
            const vb = b.get(e) orelse continue;
            const vc = c.get(e) orelse continue;
            f(ctx, va, vb, vc);
        }
    } else {
        for (b.dense.items, b.data.items) |e, *vb| {
            const va = a.get(e) orelse continue;
            const vc = c.get(e) orelse continue;
            f(ctx, va, vb, vc);
        }
    }
}
// Join of three sets, driven by the smallest; the other two are probed per entity.
query3 :: proc(
	a: ^Sparse_Set($A),
	b: ^Sparse_Set($B),
	c: ^Sparse_Set($K),
	ctx: $C,
	$f: proc(ctx: C, a: ^A, b: ^B, c: ^K),
) {
	smallest := min(len(a.dense), len(b.dense), len(c.dense))
	switch smallest {
	case len(c.dense):
		dense, data := c.dense[:], c.data[:]
		for e, i in dense {
			va, vb := sparse_get(a, e), sparse_get(b, e)
			if va != nil && vb != nil {
				f(ctx, va, vb, &data[i])
			}
		}
	case len(a.dense):
		dense, data := a.dense[:], a.data[:]
		for e, i in dense {
			vb, vc := sparse_get(b, e), sparse_get(c, e)
			if vb != nil && vc != nil {
				f(ctx, &data[i], vb, vc)
			}
		}
	case:
		dense, data := b.dense[:], b.data[:]
		for e, i in dense {
			va, vc := sparse_get(a, e), sparse_get(c, e)
			if va != nil && vc != nil {
				f(ctx, va, &data[i], vc)
			}
		}
	}
}

The outer walk is sequential, but every probe is two dependent loads into another set's arrays at a position chosen by that set's history. Dennis Gustafsson makes the point bluntly: components "are only packed tighly in memory if you read from one component type. As soon as you read from multiple, this is no longer the case", and a movement system reading three components has "three potential cache misses instead of one"[16]. When the sets happen to be in the same order (for instance right after spawning), the probes walk forward too and the prefetcher keeps up. After enough adds and removes the orders diverge, and the probes become random. EnTT's answer is groups, which sort several pools so that the entities they share sit at the front at the same positions, with the limitation that a component "can only appear in one group"[10]. Our version keeps the plain query, because that is what most sparse-set code does and it is the honest baseline.

Rust's borrow checker shapes this function. query3 takes the set it mutates as &mut and the others as &, which is why Hp is the mutated component: the caller passes &w.pos, &w.vel, &mut w.hp, three disjoint fields, and the compiler is satisfied. Write a query that mutates two components from the same set, or wants to read and write the same set, and you are into split_at_mut or get_disjoint_mut territory. Zig and Odin let you alias and trust you not to.

Storage two: one table per component combination

The other answer is to stop keeping one table per component and keep one table per set of components. Every entity with exactly {Pos, Vel} lives in the {Pos, Vel} table, which has a Pos column and a Vel column with aligned rows. An entity with {Pos, Vel, Hp} lives in a different table. This set is called the entity's archetype. Unity's DOTS blog describes it exactly that way: "ECS groups all entities that have the exact same set of components together in memory. It calls such a set an archetype", and stores them in "chunks of 16k. Each chunk will only contain the component data for entities of a single archetype" [9].

A query becomes a filter over tables rather than over entities. To run "Pos and Vel" you find every table whose type contains both, and in each one you zip two columns. There are no probes at all, because a row in a table has every component the table has. Sander Mertens, the author of flecs, builds this up in his "Building an ECS" series: an entity index maps each entity to its archetype and row, and a component index keeps "a set per component that has archetype ids", because "the number of components is always way less than the number of archetypes" [5]. Part 2 stores the columns as type-erased buffers and caches the move targets as edges of an archetype graph, so that "add Health to an entity in [Position, Velocity]" is one O(1) lookup [6]. Part 3 draws the whole thing[7].

The price is structural change. Adding a component changes the entity's type, so its whole row has to move. Mertens lists the steps: find the destination archetype, "insert a new row into the destination archetype", "move overlapping components over", "remove the entity from the current archetype"[6]. Unity: "We move it from its current chunk to a chunk of the new archetype, and back swap the last entity of the previous chunk to 'fill the hole'"[9].

Our minimal version has three component types, so a combination fits in three bits and the "archetype graph edge" for adding Vel is just mask | VEL. The eight tables live in an array indexed by mask, and every table has all three columns, of which only the ones in its mask are used. A general ECS cannot do that. It does not know the component types when it is compiled, so it needs type-erased columns, a hash map from type to table, and the cached edges. Keep that in mind when you read the benchmark: this archetype storage is the best case for its family.

/// One archetype: SoA columns with aligned rows. Columns for components outside `mask` stay empty.
#[derive(Default)]
pub struct Table {
    pub mask: u8,
    pub entities: Vec<Entity>,
    pub pos: Vec<Pos>,
    pub vel: Vec<Vel>,
    pub hp: Vec<Hp>,
}

    /// Appends a row to the table that matches exactly the components present.
    fn put(&mut self, e: Entity, r: Row) {
        let mask = r.pos.map_or(0, |_| POS) | r.vel.map_or(0, |_| VEL) | r.hp.map_or(0, |_| HP);
        let t = &mut self.tables[mask as usize];
        self.loc[e.index as usize] = Location { table: mask, row: t.entities.len() as u32 };
        t.entities.push(e);
        t.pos.extend(r.pos);
        t.vel.extend(r.vel);
        t.hp.extend(r.hp);
    }

    /// Swap-and-pops the entity's row out of its table, column by column, and fixes the
    /// location of the entity that moved into the hole.
    fn take(&mut self, e: Entity) -> Row {
        let Location { table, row } = self.loc[e.index as usize];
        let (t, row) = (&mut self.tables[table as usize], row as usize);
        t.entities.swap_remove(row);
        if let Some(moved) = t.entities.get(row) {
            self.loc[moved.index as usize].row = row as u32;
        }
        Row {
            pos: (table & POS != 0).then(|| t.pos.swap_remove(row)),
            vel: (table & VEL != 0).then(|| t.vel.swap_remove(row)),
            hp: (table & HP != 0).then(|| t.hp.swap_remove(row)),
        }
    }

    /// Adding a component is a move: the whole row is copied to the table for `mask | VEL`.
    pub fn add_vel(&mut self, e: Entity, v: Vel) {
        let mut r = self.take(e);
        r.vel = Some(v);
        self.put(e, r);
    }

        const t = &w.tables[mask];

        try t.entities.append(gpa, e);
        if (r.pos) |p| try t.pos.append(gpa, p);
        if (r.vel) |v| try t.vel.append(gpa, v);
        if (r.hp) |h| try t.hp.append(gpa, h);
    }

    /// Swap-and-pops the entity's row out of its table, column by column, and fixes the
    /// location of the entity that moved into the hole.
    fn take(w: *ArchWorld, e: Entity) Row {
        const l = w.loc.items[e.index];
        const t = &w.tables[l.table];
        _ = t.entities.swapRemove(l.row);
        if (l.row < t.entities.items.len) w.loc.items[t.entities.items[l.row].index].row = l.row;
        return .{
            .pos = if (l.table & POS != 0) t.pos.swapRemove(l.row) else null,
            .vel = if (l.table & VEL != 0) t.vel.swapRemove(l.row) else null,
            .hp = if (l.table & HP != 0) t.hp.swapRemove(l.row) else null,
        };
    }

    /// Adding a component is a move: the whole row is copied to the table for `mask | VEL`.
    pub fn addVel(w: *ArchWorld, gpa: Allocator, e: Entity, v: Vel) !void {
        var r = w.take(e);
        r.vel = v;
        try w.put(gpa, e, r);
    }
// One archetype: SoA columns with aligned rows. Columns for components outside `mask` stay empty.
Table :: struct {
	mask:     Mask,
	entities: [dynamic]Entity,
	pos:      [dynamic]Pos,
	vel:      [dynamic]Vel,
	hp:       [dynamic]Hp,
}

// Appends a row to the table that matches exactly the components present.
@(private = "file")
arch_put :: proc(w: ^Arch_World, e: Entity, r: Row) {
	mask: Mask
	if r.pos != nil {mask += {.Pos}}
	if r.vel != nil {mask += {.Vel}}
	if r.hp != nil {mask += {.Hp}}
	t := &w.tables[transmute(u8)mask]
	w.loc[e.index] = {transmute(u8)mask, u32(len(t.entities))}
	append(&t.entities, e)
	if p, ok := r.pos.?; ok {append(&t.pos, p)}
	if v, ok := r.vel.?; ok {append(&t.vel, v)}
	if h, ok := r.hp.?; ok {append(&t.hp, h)}
}

// Swap-and-pops the entity's row out of its table, column by column, and fixes the
// location of the entity that moved into the hole.
@(private = "file")
arch_take :: proc(w: ^Arch_World, e: Entity) -> (r: Row) {
	l := w.loc[e.index]
	t := &w.tables[l.table]
	row := int(l.row)
	unordered_remove(&t.entities, row)
	if row < len(t.entities) {
		w.loc[t.entities[row].index].row = l.row
	}
	if .Pos in t.mask {
		r.pos = t.pos[row]
		unordered_remove(&t.pos, row)
	}
	if .Vel in t.mask {
		r.vel = t.vel[row]
		unordered_remove(&t.vel, row)
	}
	if .Hp in t.mask {
		r.hp = t.hp[row]
		unordered_remove(&t.hp, row)
	}
	return
}

// Adding a component is a move: the whole row is copied to the table for `mask + {.Vel}`.
arch_add_vel :: proc(w: ^Arch_World, e: Entity, v: Vel) {
	r := arch_take(w, e)
	r.vel = v
	arch_put(w, e, r)
}

The systems show the payoff. In archetype storage a system is a loop over tables, and inside a table a loop over columns zipped together, which is Chapter 4's SoA loop with nothing in the way. In sparse-set storage the same system is a call to the query with a small function for one entity.

fn sparse_move(w: &mut SparseWorld) -> u64 {
    let mut s = 0u64;
    query2(&mut w.pos, &w.vel, |p, v| {
        p.x = p.x.wrapping_add(v.x);
        p.y = p.y.wrapping_add(v.y);
        s = s.wrapping_add(p.x as u32 as u64);
    });
    s
}

fn arch_move(w: &mut ArchWorld) -> u64 {
    let mut s = 0u64;
    for t in w.tables_with(POS | VEL) {
        for (p, v) in t.pos.iter_mut().zip(&t.vel) {
            p.x = p.x.wrapping_add(v.x);
            p.y = p.y.wrapping_add(v.y);
            s = s.wrapping_add(p.x as u32 as u64);
        }
    }
    s
}
fn moveOne(s: *u64, p: *Pos, v: *const Vel) void {
    p.x +%= v.x;
    p.y +%= v.y;
    s.* +%= bits(p.x);
}

fn sparseMove(w: *SparseWorld) u64 {
    var s: u64 = 0;
    sparse.query2(&w.pos, &w.vel, &s, moveOne);
    return s;
}

fn archMove(w: *ArchWorld) u64 {
    var s: u64 = 0;
    for (&w.tables) |*t| {
        if (t.mask & (POS | VEL) != POS | VEL) continue;
        for (t.pos.items, t.vel.items) |*p, v| {
            p.x +%= v.x;
            p.y +%= v.y;
            s +%= bits(p.x);
        }
    }
    return s;
}
move_one :: proc(s: ^u64, p: ^Pos, v: ^Vel) {
	p.x += v.x
	p.y += v.y
	s^ += bits(p.x)
}

sparse_move :: proc(w: ^Sparse_World) -> (s: u64) {
	query2(&w.pos, &w.vel, &s, move_one)
	return
}

arch_move :: proc(w: ^Arch_World) -> (s: u64) {
	for &t in w.tables {
		if !({.Pos, .Vel} <= t.mask) {
			continue
		}
		pos, vel := t.pos[:], t.vel[:]
		for &p, i in pos {
			p.x += vel[i].x
			p.y += vel[i].y
			s += bits(p.x)
		}
	}
	return
}

Where the three languages differ

The algorithm is identical in all three programs, down to the random stream (splitmix64, seeded the same way as Chapter 5) and the order of operations, so the final checksum is the same 64-bit number in every language. How each language expresses "run this function inside the join loop" is where they part.

  • Rust passes a closure, impl FnMut(&A, &B, &mut C), monomorphised and inlined per call site. The probe-and-test reads as a let-chain (if let Some(vb) = b.get(e) && let Some(vc) = ..., stable since 1.88), and the archetype loop is iter_mut().zip(..), which elides bounds checks.
  • Zig passes comptime f: anytype plus a context pointer, the std.sort idiom. The archetype loop is a multi-object for (t.pos.items, t.vel.items) |*p, v|, whose lengths must match. The unmanaged std.ArrayList takes an allocator per call, so insert can fail with error.OutOfMemory.
  • Odin passes $f: proc(ctx: C, a: ^A, ...), a compile-time proc parameter, so it also specialises the loop per system. The archetype type is a bit_set[Component; u8], so "the table contains every queried component" is literally {.Pos, .Vel} <= t.mask, a subset test.

Zig's archetype loops stay scalar, because Zig 0.17.1 ships with LLVM's loop vectorizer off (Chapter 4); we did not rewrite them with @Vector, since this chapter compares storages, not SIMD.

Odin's sparse-set query copies the slices into locals (dense, data := a.dense[:], a.data[:]) before the loop. Indexing a.data[i] through the pointer inside the loop can make the compiler reload the slice header after every store through f, because it cannot always prove the store did not change a (Chapter 4's lesson). The same reasoning is why the archetype loops hoist t.pos[:] and t.vel[:].

Measuring both

The benchmark builds the same world in both storages: N entities, each with Pos, every second one with Vel, every fourth with Hp. Components are small integer structs (Pos and Vel are two i32, 8 B; Hp is one i32), so the checksum is exact. Then it times three things with the harness from Chapter 2 (one warm-up, median of 7):

  1. Churn. N/16 times, pick a random entity and toggle its Vel: remove it if present, add it otherwise. In the sparse-set world that touches one set. In the archetype world it moves a row. Eight runs including the warm-up means N/2 toggles in total, which also scrambles the order of the Vel set.
  2. Move, a 2-component query: Pos += Vel for every entity that has both.
  3. Damage, a 3-component query: read Pos and Vel, write Hp.

Each system folds what it wrote into a sum that goes to black_box, doNotOptimizeAway or Odin's volatile sink. At the end the program walks every live entity in both worlds and hashes its components with an order-independent sum. The storages hold rows in completely different orders, so the only way the two sums can match is if both worlds contain the same components with the same values. They do, in all three languages:

Before you look at the charts: which storage wins the 2-component query, and by roughly how much? Which wins churn?

Archetypes win iteration by more than an order of magnitude here, and sparse sets win churn by a few times. The rest of this section explains why the iteration gap is so large in this particular test.

In our runs the archetype move query was about 20× faster in Rust, about 18× in Zig and about 14× in Odin. Churn went the other way: archetype toggles cost about 4× as much as sparse-set toggles in Rust, about 4× in Zig and about 2.4× in Odin.

Worked example: why the gap is that large

Take the charted run, N = 1,048,576. The churn toggles Vel on random entities, so afterwards it is on about half of them, roughly 524,000, spread over the {P,V} and {P,V,H} tables. Count the bytes the move query touches.

  • Archetype: it visits {P,V} and {P,V,H}, about 524,000 rows in total. Per row it reads 8 B of Pos and 8 B of Vel and writes 8 B back, all in two sequential streams. That is about 524,000 × 16 B ≈ 8 MiB read, in two strides the prefetcher understands. Nothing else is touched.
  • Sparse set: the smallest set is Vel (about 524,000 vs 1,048,576 for Pos), so the query walks Vel.dense (8 B per entity) and Vel.data (8 B) in order. Then, per entity, it reads Pos.sparse[e.index] (4 B), Pos.dense[d] (8 B) and Pos.data[d] (8 B). That is 36 B per entity instead of 16 B, already 2.25× more. But the real cost is where those last three loads land. The Pos arrays together are 1,048,576 × 20 B = 20 MiB, sixteen times this orb's 1.25 MiB L2 and far more than the few MiB of L3 it really gets, and the churn has shuffled Vel's order, so the probes jump around inside those 20 MiB. Each probe is two dependent misses, as Chapter 2's pointer chase showed.

Sequential streams against dependent random loads into data far larger than the caches is exactly the gap Chapter 2 measured between an array walk and a pointer chase, and that is the size of gap we see. Shrink N so everything fits in L1 and L2 and the gap shrinks with it; run the program in quick mode (N = 4,096) to see it. Turn the churn off, so that Vel stays in entity order, and the gap also shrinks (Exercise 9.3).

The churn numbers follow from counting too. A sparse-set toggle touches one set: on remove, two sparse slots, one dense slot and one data slot. An archetype toggle reads the entity's location, swap-and-pops every column of the source table (entity, Pos, maybe Hp), appends to every column of the destination, and fixes two locations. That is two to three times the memory traffic, spread over twice as many arrays.

What a controlled study found

Our result agrees in direction with the one peer-reviewed comparison we know of. Cox, Williams, Vickers, Ward and Headleand at the University of Staffordshire wrote two minimal C++20 ECSes, one sparse-set (with paged sparse arrays) and one archetype-based, and ran Conway's Game of Life with one entity per cell, single-threaded, for 5,000 frames [13]. At 100 and 1,000 entities there was no statistically significant difference. At 10,000 and 50,000 the archetype version was significantly faster, "nearly twice the performance of the sparse-set equivalent" at 50,000, which they attribute to "the cache-coherent nature of archetypal storage". The sparse-set version created entities "by an average factor of 6.6×" faster.

The authors' own caveat applies to us too: "these findings are dependent on the specific implementations used" [13]; the caveats section below lists how ours is idealised. Library benchmark suites (for example abeimler's ecs_benchmark[23]) put mature sparse-set and archetype libraries within a small factor of each other for typical workloads, and every one of them warns you to benchmark your own access pattern.

Choosing per component: Bevy

Because the trade-off is per component rather than per program, Bevy lets you choose per component. Its default is table (archetype) storage, and #[component(storage = "SparseSet")] opts a component into a sparse set. The Bevy Cheat Book explains the rule: tables are "optimized for fast query iteration", while adding or removing a table component "requires copying the data of all table components for the entity to a different location in memory"; sparse sets are "optimized for fast adding/removing of a component to existing entities, at the cost of slower querying"[11]. Its examples are exactly the components our churn benchmark toggles: a CanSeePlayer marker added and removed every frame, and a temporary Bleeding effect, which would otherwise "fragment tables". Bevy 0.5 introduced this hybrid as part of a rewrite of its ECS [12]. Having two storage paths has its own cost in complexity.

Overwatch: an ECS for complexity, not speed

The most cited production ECS talk is not about cache misses at all. In "Overwatch Gameplay Architecture and Netcode" (GDC 2017), Blizzard's Tim Ford described an ECS in which an entity is a 32-bit id, components hold state but no behaviour, and systems hold behaviour but no state[14]. The client had about 46 systems and 103 components. The lesson they learned the hard way was that system state which looked private was nearly always shared, so they moved it into components with exactly one instance. In the English translation of the talk: "the singleton pattern was so prevalent that 40% of the components in our entire game were singletons" [14].

Ford says up front that the techniques are for "reducing the complexity of an ever-growing code base", that "ECS architecture could manage rapidly increasing code complexity", and that the hardest problem they used it for was netcode: prediction and rollback need to know exactly which state a system reads and writes, and a component tuple says so by construction[14]. Forty per cent singletons means 40% of the "tables" have one row, which is the opposite of what a cache-friendly design needs. The win was knowing who touches what. That is a data-oriented argument, but it is about the shape of dependencies rather than the layout of bytes.

The database people got here first

Everything in this chapter has a database name, usually an older one. Storing each column contiguously is a column store, and Abadi, Madden and Hachem showed that its advantage on analytical queries comes from more than layout: per-column compression, late materialisation and processing a block of values at a time[20]. Block-at-a-time is MonetDB/X100's vectorised execution[18], whose vector-size curve Chapter 7 reproduced; DuckDB still processes 2,048 rows at a time[19], 16 KiB at 8 B per value, the same size Unity chose for a chunk. X100's selection vectors, positions that matched instead of copies, are the dense id list of a sparse set used as a filter, and Apache Arrow standardises such columns in memory[21].

The mapping onto an ECS is direct. An archetype table is a column store with one table per schema. A system is a query plan. A Unity chunk is an X100 vector. A sparse-set query is an index nested-loop join, and EnTT's groups are a co-clustered index. Knowing the database names gives you access to forty years of work on join order, partitioning and vectorised operators.

ECS is not data-oriented design

Chapter 1 promised to look at ECS critically, and the strongest critiques come from people who like data-oriented design. Sebastian Schöner, writing at a time when Unity's DOTS made "DOD" a buzzword among his co-workers, titled a section of his essay "Data-Oriented Design is not just ECS and fewer cache misses". He describes the usual story (OOP causes cache misses, ECS has nice access patterns, "That's DOD for you! Apply this pattern everywhere") and rejects it: "You probably do not need a full-blown ECS in your custom engine, because that is most likely not the problem that you are solving", and "ECS is something that you can arrive at when using DOD with a specific set of requirements in mind. It's a consequence of, not a prerequisite for DOD" [15].

Dennis Gustafsson (Teardown) lists the costs in his 2025 "Thoughts on ECS": "Added complexity", lookups between entities and components whose cost is "difficult to detect, since they are scattered all over the code", and "Hard to debug", because a debugger can follow pointers but not an integer id through an indirection table, and archetype data sits in "a memory blob with no debug info whatsoever"[16]. His alternative, if your game does not need to change an entity's composition at run time, is to compose entity types statically, one plain array per type, so the code "literaly does exactly what it says from top to bottom"[16]. That is the per-kind arrays of Chapter 1 and Chapter 7, and it is exactly what our archetype storage turns into when there are few combinations and they are known in advance.

Niklas Gray's Our Machinery posts, which Chapter 5 leaned on, make a related point from the engine side: most bulk data is better off as a plain array with holes and stable indices, and packed SoA is worth it only for the few hot, SIMD-friendly systems[17]. And Catherine West, after building an ECS in Rust, said that ECS is great "because it forces you to think about your data rather than be stuck in OO mode, not because of the magic of 'structs of arrays'"[2].

Put together, the critiques do not say "never use an ECS". They say: know which problem you have. If your entities change shape at run time, and many systems compose behaviour over the same entities, a general ECS buys flexibility and clear dependencies, as at Blizzard. If you have a few kinds of thing that never change shape, a struct of arrays per kind is simpler, faster to compile, easier to debug, and at least as fast.

Caveats, and when not to build one

  • Our benchmark favours archetypes on iteration. The loop body is two additions, so memory access is all there is to measure, and the churn has scrambled the sparse sets. A system that does real work per entity, or sets that stay in the same order, narrows the gap, as the Staffordshire numbers show.
  • Our archetype storage is idealised. Three component types and eight tables known at compile time. Real archetype ECSes pay for type erasure, table lookup and graph edges, and suffer when the number of distinct combinations explodes into many tiny tables (the "table fragmentation" the Bevy Cheat Book warns about [11]).
  • Memory. A sparse set's sparse array is as long as the largest entity index, per component. With a million entities and 50 components that is 200 MB of 4-byte slots unless you page it, as EnTT does.
  • Address stability. Both storages move components: swap-and-pop in a sparse set, row moves in an archetype. A pointer or reference into either is valid only until the next structural change. Keep the entity id, as Chapter 5 taught, and look it up again.
  • Small worlds. At a few hundred entities, both storages are fast and the difference is noise (the Staffordshire study found none at 100 or 1,000). Pick on design grounds.

An ECS is a small in-memory database: entities are keys, components are tables, systems are joins; store one table per component (sparse sets) when composition changes often and one table per combination (archetypes) when iteration dominates, and do not build either if a struct of arrays per kind of thing will do.

Exercises

In the sparse-set figure, remove an id that is already the last element of dense. How many elements move, and how many sparse slots change?

None move: swap-and-pop with the last element is just a pop. One sparse slot changes (the removed id's, cleared to empty). In the code, last equals e, so the first store writes d into the removed entity's own slot and the second store immediately overwrites it with NONE. That is harmless, and cheaper than a branch.

A {Pos, Vel, Hp} entity loses Vel. How many bytes does the archetype storage copy, with this chapter's sizes, and how many does the sparse-set storage move in the worst case?

Archetype: the row keeps its entity id (8 B), Pos (8 B) and Hp (4 B), so 20 B are copied into the {Pos, Hp} table, plus the source table's last row (8 + 8 + 8 + 4 = 28 B) moves into the hole. Sparse set: only the Vel set changes, and its last entity (8 B) and value (8 B) move into the hole, 16 B in total, plus two 4-byte sparse slots.

Change the program so the Vel toggle never happens (k = 0) and run it at full size. Predict what happens to the sparse-set move query, then try it. Why?

Expect it to get several times faster, and the gap to the archetype query to shrink to a small multiple; we did not record this variant, so the measurement is yours to make. Without churn, Vel.dense is in increasing entity order, which is also Pos's order, so the probes into Pos.sparse, Pos.dense and Pos.data walk forward with a stride of two and the prefetcher hides most of the latency. The archetype query does not change much. The point is that a sparse-set ECS's speed depends on its history, which is why EnTT offers sorting and groups.

Mertens keeps a set of archetypes per component, not a set of components per archetype. Why is that the better direction for queries?

There are far fewer components than archetypes, so the index is smaller. More importantly, a query starts from the components it needs: intersect the archetype sets of Pos and Vel and you have the matching tables directly, without scanning every archetype. Our version scans all eight tables, which is fine for eight.

Overwatch had about 40% singleton components. Which storage would you choose for a singleton such as the input state, and does it matter?

Neither. A singleton has one row, so there is nothing to iterate and nothing to lay out. Overwatch attached them to one anonymous entity and accessed them directly through the world object[14]. In a hand-written program it is a global or a field of the world struct. The storage question only matters for components with many instances.

DuckDB's default vector is 2048 rows. A query reads five 8-byte columns and writes two. How big is one batch's working set, and where does it fit on this orb?

7 columns × 2048 × 8 B = 112 KiB. That is more than the 48 KiB L1d but well inside the 1.25 MiB L2, which is the regime X100's Figure 10 says works well. At X100's extreme of 4M rows it would be 224 MiB, far past any L3 (this orb's usable share of its 54 MiB host L3 is only a few MiB), and every operator would stream from DRAM.
