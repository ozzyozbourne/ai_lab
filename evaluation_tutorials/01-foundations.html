Chapter 1

Why Evals: Foundations, Taxonomy and Eval-Driven Development

In January 2026 Anthropic's engineering team summed up what happens to agent teams that ship without evaluations: “it’s easy to get stuck in reactive loops—catching issues only in production, where fixing one failure creates others”[1]. Two years earlier Hamel Husain had described the same trap from the inside. Rechat’s real-estate assistant, Lucy, improved quickly with prompt engineering, then plateaued: fixing one failure mode surfaced others, “resembling a game of whack-a-mole”, there was no visibility “beyond vibe checks”, and the prompts grew into long, unwieldy lists of edge cases[2]. The way out, in both accounts, was the same: a systematic evaluation practice. This chapter gives you the vocabulary, the mental map and the habits that the other nine chapters build on.

1.1Why evals?

Anthropic’s definition is a good place to start because it is short: an evaluation (“eval”) is “a test for an AI system: give an AI an input, then apply grading logic to its output to measure success”[1]. Everything else in this book elaborates one of the three parts of that sentence: which inputs (the task distribution, Chapter 3), which system (a model alone, or a model inside a harness with tools and retrieval, Chapters 6 and 7), and which grading logic and aggregation (Chapters 2, 4 and 5).

Traditional tests are not enough

A unit test checks a deterministic function: sort([3,1,2]) == [1,2,3] holds or it does not, today and tomorrow. An LLM system breaks both assumptions. Its output is a sample from a distribution, and the space of acceptable outputs is usually huge (there are many correct summaries of a contract), so equality checks are often the wrong instrument. OpenAI’s guide makes this the core motivation for evals[3]. The consequences run through the whole book:

  • Because outputs vary, one run proves little. You run several trials per task and report a rate with an uncertainty, not a single pass/fail (sections 1.2 and 1.6).
  • Because acceptable outputs vary, you need graders that tolerate valid variation without accepting invalid output, and those graders can themselves be wrong (sections 1.4 and 1.5).
  • Because agents act over many turns, “mistakes can propagate and compound”[1], so you grade the end state of the world, not just the last message.

Setting the temperature to 0 does not remove the first problem on a served API, and agents add nondeterministic tools, web pages and environments on top.

He and colleagues at Thinking Machines trace run-to-run variation at temperature 0 to inference kernels that are not batch-invariant: the numerics depend on which other requests share the batch, so your output depends on other users’ traffic[51]. Silent updates behind undated aliases add more drift. In practice: pin dated model snapshot IDs rather than aliases, record the decoding parameters, and run repeated trials and report the variance anyway. Section 5.10 treats nondeterminism and reproducibility in depth.

The improvement loop

Husain’s central claim is blunt: unsuccessful AI products “almost always share a common root cause: a failure to create robust evaluation systems”[2]. The argument is about iteration speed. Improving an AI product means cycling through three activities: evaluate quality, debug the failures, change the system. Without evals, the first step is a human skimming a few outputs: slow, inconsistent and blind to regressions nobody looked at. Anthropic describes the breaking point: users say the agent “feels worse”, the team is “flying blind”, and debugging becomes “wait for complaints, reproduce manually, fix the bug, and hope nothing else regressed”[1].

A vibe check, an informal look at a few outputs, is “useful, but not enough”[2]: it shows what to measure, but it is not repeatable, not comparable across versions and has no error bars.

The cost of having none

The Rechat story is the canonical cost: progress stopped, and the prompt became a pile of patches[2]. Without a fixed task set you cannot tell a regression from noise, evaluate a new model release in an afternoon, or hand a failure to a teammate as a reproducible test. Anthropic notes that the value of evals “compounds over the lifecycle of an agent”: a team with a suite adopts a new frontier model in days[1]. Husain and Shankar report that 60–80% of development time in their projects went to error analysis and evaluation[7].

What evals cannot do

An eval score is evidence for a claim, and only for the claim it was designed to support. Three limits recur:

  • Validity. A score can be precise and still measure the wrong thing (construct validity, section 1.7).
  • Grader error. The eval can be wrong rather than the model. Anthropic reports that Claude Opus 4.5 initially scored 42% on CORE-Bench until a researcher found rigid grading (it penalised “96.12” when expecting “96.124991…”), ambiguous task specifications and stochastic tasks that could not be reproduced; after fixes and a less constrained scaffold the score was 95%[1].
  • Coverage. An offline eval only covers the inputs you thought of. Real users find others, which is why online evaluation exists. Barnett et al., reporting on three RAG case studies, conclude that “validation of a RAG system is only feasible during operation”[8].

Think of an eval as a measurement instrument: does it read the right quantity (validity), how much does the reading jump around (reliability), and was it calibrated against a reference (judge validation)? Wallach et al. frame generative-AI evaluation as a social-science measurement problem[9].

Two distinctions in this table deserve emphasis because they cause most real-world confusion.

Transcript vs outcome. “A flight-booking agent might say ‘Your flight has been booked’ at the end of the transcript, but the outcome is whether a reservation exists in the environment’s SQL database”[1]. What the agent says it did is a claim; the outcome is the fact. τ-bench is built on this idea: it grades a customer-service agent by comparing the final database state with an annotated goal state[12]. When you can check the outcome, check the outcome.

Eval harness vs agent harness, and the unit under test. The eval harness is the measuring apparatus; the agent harness is part of the thing being measured. “When we evaluate ‘an agent,’ we’re evaluating the harness and the model working together”[1]. The same model in two scaffolds can score very differently (the CORE-Bench jump from 42% to 95% came partly from a less constrained scaffold). So the unit under test of an agent eval is model + harness + tools + prompt, and every report should name all of them (Kapoor et al.’s model-vs-system distinction, section 1.3[13]).

A harness in 180 lines

code/ch01/mini_harness.py is the smallest harness that has every part, in the standard library only. The “model” is a seeded mock that answers correctly with a per-task probability, which stands in for task difficulty.

Lines 26–52: records. Task is frozen because a task edited silently between runs makes two scores incomparable. Trial.passed combines graders the simplest way (all must pass), and status separates infrastructure failures from model failures.

@dataclass(frozen=True)
class Task:                      # one test: input + success criteria
    id: str
    input: str
    target: str | list[str]
    metadata: dict = field(default_factory=dict)


@dataclass
class Grade:                     # one grader's verdict on one trial
    grader: str
    passed: bool
    detail: str = ""


@dataclass
class Trial:                     # one attempt at a task, with its transcript
    task_id: str
    trial: int
    output: str
    grades: list[Grade]
    status: str = "ok"           # "ok" or "error": did the INFRASTRUCTURE work?
    error: str = ""

    @property
    def passed(self) -> bool:    # combine graders: every grader must pass
        return self.status == "ok" and all(g.passed for g in self.grades)


class MockModel:
    """Seeded stand-in for an LLM: answers correctly with a per-task probability."""

    def __init__(self, seed: int = 0, error_rate: float = 0.0):
        self.rng = random.Random(seed)
        self.err_rng = random.Random(seed + 1)          # separate stream: errors leave answers unchanged
        self.error_rate = error_rate

    def generate(self, task: Task) -> str:
        p_correct = task.metadata["p_correct"]          # per-task difficulty
        good = task.target if isinstance(task.target, str) else ", ".join(task.target)
        if self.rng.random() < p_correct:
            out = self.rng.choice([f"The answer is {good}.", f"{good}", f"Sure! {good}"])
        else:
            out = self.rng.choice(["I am not sure.", "The answer is 41.", "Paris, maybe Lyon"])
        if self.err_rng.random() < self.error_rate:     # mock provider timeout / 5xx
            raise TimeoutError("mock API timeout")
        return out


def exact_match(task: Task, out: str) -> Grade:
    ok = out.strip().lower() == str(task.target).strip().lower()
    return Grade("exact_match", ok)


def regex_number(task: Task, out: str) -> Grade:
    nums = re.findall(r"-?\d+(?:\.\d+)?", out.replace(",", ""))
    ok = bool(nums) and float(nums[-1]) == float(task.target)   # last number wins
    return Grade("regex_number", ok, nums[-1] if nums else "no number")


def contains_all(task: Task, out: str) -> Grade:
    missing = [t for t in task.target if t.lower() not in out.lower()]
    return Grade("contains_all", not missing, f"missing={missing}")

Lines 55–88: mock and graders. The mock phrases correct answers three ways, as real models do, and its optional error_rate draws from a separate seeded stream so that turning errors on changes no answer. The three graders are three different definitions of correct; the output shows the consequence.

def run_eval(tasks: list[Task], graders: dict[str, list[Callable]], model: MockModel,
             n_trials: int, log_path: pathlib.Path) -> list[Trial]:
    trials: list[Trial] = []
    log_path.parent.mkdir(parents=True, exist_ok=True)
    with log_path.open("w") as log:
        for task in tasks:
            for k in range(n_trials):                  # repeated trials: outputs vary
                try:
                    out = model.generate(task)
                    grades = [g(task, out) for g in graders[task.metadata["kind"]]]
                    trial = Trial(task.id, k, out, grades)
                except Exception as e:                 # infrastructure failed, not the model
                    trial = Trial(task.id, k, "", [], status="error", error=f"{type(e).__name__}: {e}")
                trials.append(trial)
                log.write(json.dumps({**asdict(trial), "passed": trial.passed}) + "\n")
    return trials


# Two-sided 95% t quantiles by degrees of freedom; the standard library has no t quantile function.
T95 = {4: 2.776, 9: 2.262, 11: 2.201, 19: 2.093, 29: 2.045}


def summarize(trials: list[Trial]) -> dict:
    by_task: dict[str, list[int]] = {}
    ok_by_task: dict[str, list[int]] = {}
    for t in trials:
        by_task.setdefault(t.task_id, []).append(int(t.passed))       # errors count as fails
        if t.status == "ok":
            ok_by_task.setdefault(t.task_id, []).append(int(t.passed))
    task_means = [sum(v) / len(v) for v in by_task.values()]
    n = len(task_means)                                # the unit of sampling is the TASK
    mean = sum(task_means) / n
    var = sum((m - mean) ** 2 for m in task_means) / (n - 1)
    se = math.sqrt(var / n)
    naive_se = math.sqrt(mean * (1 - mean) / len(trials))   # pretends trials are independent
    t_crit = T95.get(n - 1, 1.96)                      # z fallback: only valid for large n
    excl = [sum(v) / len(v) for v in ok_by_task.values()]
    return {"n_tasks": n, "n_trials": len(trials), "accuracy": mean, "se": se,
            "ci95_t": (mean - t_crit * se, mean + t_crit * se),
            "ci95_z": (mean - 1.96 * se, mean + 1.96 * se), "naive_se": naive_se,
            "error_rate": sum(t.status == "error" for t in trials) / len(trials),
            "acc_excl_errors": sum(excl) / len(excl)}

Exceptions become status="error" trials instead of aborting the run. A real agent harness would also start each trial from a clean environment, because shared state causes correlated failures or inflated scores[1].

Trials are averaged within each task, and the mean and SE are taken across tasks: the task is the unit of sampling, and five trials of one task are not five independent pieces of evidence. Four lessons sit in that output.

  1. The interval is wide. Twelve tasks give a 95% interval from 21% to 72%, so “46.7%” versus a colleague’s “55%” means nothing. The z interval [0.239, 0.695] is too narrow at this n (Bowyer et al.[33]; section 1.6, Chapter 5).
  2. The naive SE is too small by almost half (0.064 vs 0.116), because repeated trials of one task are not independent: the clustering problem of Chapter 5.
  3. The grader dominates some results. Exact-match tasks are answered correctly 44.5% of the time but only 20% of trials pass, because “The answer is Paris.” is not “Paris”. The number tasks’ 0.70 vs 0.598 is sampling noise; the exact-match gap is a grader defect that would persist with a million trials.
  4. The error policy moves the headline. With 10% of calls failing (7 of 60 trials), counting errors as failures gives 0.417 and excluding them 0.471.

Separate “the model failed” from “the infrastructure failed” (timeout, rate limit, crashed sandbox), and state the policy for the second: retry, count as failure, or exclude. Excluding errors can flatter a model that triggers more of them, for example one whose long outputs hit timeouts on exactly the hard tasks, so report the error rate next to the score whatever you choose. Inspect implements this choice with Task(fail_on_error=...) and sample-level retries[10]; Chapter 9 compares how harnesses handle it (9.4).

Whenever a pass rate looks surprisingly low, read a sample of failing transcripts before you change the system. Anthropic’s advice is direct: “You won’t know if your graders are working well unless you read the transcripts and grades from many trials”[1]. A 0% pass rate over many trials (their example is 0% pass@100) “is most often a signal of a broken task, not an incapable agent”.

Store this with every eval run, so that two numbers can be compared months later[27]:

  • model snapshot ID (dated, not an alias) and provider or serving stack;
  • decoding parameters: temperature, top_p, max tokens, stop sequences, and for reasoning models the reasoning effort or thinking-token budget;
  • prompt and agent-harness version (a commit hash);
  • agent limits: max turns, per-trial timeout, tool-call and token or cost budgets;
  • tool set and sandbox policy: which tools are enabled, internet on/off, git history sealed or not (section 1.7 shows this alone moved a SWE-bench Pro score by 14 points[50]);
  • dataset version or content hash;
  • grader versions, and for LLM judges the judge model and prompt;
  • seeds and n_trials;
  • date of the run;
  • error and retry policy, and the observed error rate;
  • tokens and cost per task (see Ch 6.7).

1.3A taxonomy of evals

“We have evals” can mean a quarterly benchmark run, a pytest file checking JSON validity, or a judge scoring 1% of traffic: different instruments for different decisions. Use the taxonomy as a checklist: which cells must your decision cover?

Axis 1: what is measured

  • Capability: what the system can do when asked. MMLU, GPQA and SWE-bench are capability evals.
  • Alignment / propensity: what the system tends to do when it could do otherwise. Shevlane et al. separate “dangerous capability evaluations” from “alignment evaluations”, which measure a model’s propensity to apply its capabilities for harm[6].
  • Safety: harm and misuse risk. Weidinger et al. argue that capability testing alone is not enough and add two further layers, human interaction and systemic impact[15]. Chapter 8 covers safety evals.
  • Non-functional properties: cost, latency, calibration, robustness, fairness, efficiency. HELM made the case for multi-metric evaluation by measuring seven metrics (accuracy, calibration, robustness, fairness, bias, toxicity, efficiency) across its core scenarios[16]. For agents, Kapoor et al. argue that accuracy-only leaderboards produce needlessly costly agents, and that cost must be reported and optimised jointly with accuracy[13].

Axes 2–4: when, how stable, and against what

Offline vs online. Offline evals run on fixed datasets before deployment (CI suites, benchmarks). Online evals run on production traffic: judges on sampled traces, A/B tests, user feedback. The Husain–Shankar FAQ draws the line: CI evals “protect against known regressions before deployment”, while online monitoring finds failures in production and estimates how often they occur[7].

Static vs dynamic. A static benchmark is a fixed test set (MMLU, GSM8K); it eventually saturates and leaks into training data. A dynamic benchmark keeps changing: Dynabench collects adversarial examples with humans and models in the loop[17]; LiveBench releases frequently updated questions with objective answers to limit contamination[18]; Chatbot Arena collects live crowdsourced pairwise votes[19]; GSM-Symbolic generates variants of GSM8K questions from templates and finds notable variance across instantiations of the same question[20].

Reference-based vs reference-free. A reference-based grader compares with a gold answer (exact match, unit tests); a reference-free one checks properties such as faithfulness, format or a rubric. Reference-free evals “can be used as guardrails too”[21], since they need nothing unavailable at inference time.

Axes 5–7: purpose, granularity and scope

Unit vs regression vs capability suites. Husain’s “Level 1” evals are unit tests: assertions in the pytest style, such as “no UUIDs leak into the output”, cheap enough to run on every code change[2]. Anthropic distinguishes two kinds of larger suites[1]. Capability evals ask “What can this agent do well?” and “should start at a low pass rate”, giving teams “a hill to climb”. Regression evals ask “Does the agent still handle all the tasks it used to?” and “should have a nearly 100% pass rate”. Capability tasks that reach high pass rates graduate into the regression suite: tasks that measured “Can we do this at all?” then measure “Can we still do this reliably?”

Eval as reward or selection signal. In RL post-training a grader becomes the reward (unit-test verifier, answer checker, rubric judge), and checkpoint-selection evals pick which snapshot to keep. The grader must then be cheap enough to run millions of times and robust to a policy searching for its blind spots (section 1.7, Chapter 7).

Outcome vs process grading. Grade the end state or grade the path? Anthropic found that checking that agents followed very specific steps (a fixed sequence of tool calls) is “too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn’t anticipate”, so “it’s often better to grade what the agent produced, not the path it took”[1]. Process checks remain valuable for diagnosis: OpenAI’s guide lists tool selection, argument precision and (for multi-agent systems) handoff accuracy as step-level checks[3], and section 1.8 builds a transition-failure matrix.

Model eval vs system eval. A model eval holds the harness fixed and varies the model; a system eval tests the whole product on its own distribution to make a deployment decision. Kapoor et al. argue the two have been conflated, so model benchmarks that ignore cost reward needlessly expensive agents no developer would deploy[13].

Practitioners agree on the order: code wherever code can check the criterion, a model grader only for what code cannot catch, and humans to define quality and validate the model graders[2][1]. Combining graders and partial credit

A task often has several graders (tests, static analysis, a rubric judge). Anthropic lists three ways to combine them[1]:

  • Binary: all graders must pass. Simple and strict; our Trial.passed does this.
  • Weighted: combined grader scores must reach a threshold. Allows trade-offs, but the weights are a policy choice you must defend.
  • Hybrid: some graders are gates (tests must pass), others contribute to a weighted quality score.

For multi-step tasks, build in partial credit. In Anthropic’s example, “a support agent that correctly identifies the problem and verifies the customer but fails to process a refund is meaningfully better than one that fails immediately”[1]. Report the fraction of sub-outcomes achieved next to the binary pass rate: “how far does it get?” and “how often does it finish?” are different questions.

For every task, create a known-good output that passes all graders. It proves the task is solvable and that the graders are configured correctly[1]. A good task is one where “two domain experts would independently reach the same pass/fail verdict”; if they would not, the task specification needs work before the model does.

Preview: the always-pass judge

An LLM judge is itself a classifier, so validate it like one against human labels. Raw agreement misleads when classes are imbalanced, as they are in any decent product. A judge that says PASS to everything, on a set humans marked 95% PASS and 5% FAIL, agrees 95% of the time and has never caught a failure.

Report chance-corrected agreement and per-class rates instead, with FAIL as the positive class, since catching failures is the judge’s job:

TPR = TPTP + FN,   TNR = TNTN + FP,   κ = po − pe1 − pe (1.1) where po is the observed agreement and pe = Phuman(FAIL)·Pjudge(FAIL) + Phuman(PASS)·Pjudge(PASS) is the agreement expected by chance from the two marginal rates. κ is Cohen’s kappa.

Always-PASS judge on 190 PASS / 10 FAIL: po = 190/200 = 0.95. The judge says PASS with probability 1, so pe = 0.05·0 + 0.95·1 = 0.95, and κ = (0.95 − 0.95)/(1 − 0.95) = 0. TPR = 0/10 = 0.

A realistic judge that catches 8 of the 10 failures and wrongly flags 19 of the 190 passes: po = (8 + 171)/200 = 0.895, pe = 0.05·0.135 + 0.95·0.865 = 0.8285, κ = 0.0665/0.1715 = 0.388, TPR = 0.80, TNR = 0.90. Its raw agreement is lower than the always-PASS judge, yet it is the only one of the two that does any work.

Dossier example: 100 items, 20 human FAILs, TP = 15, FN = 5, FP = 10, TN = 70 gives po = 0.85, pe = 0.2·0.25 + 0.8·0.75 = 0.65 and κ = 0.571. All three are reproduced by code/ch01/judge_always_pass.py.

def confusion(human: list[str], judge: list[str]) -> tuple[int, int, int, int]:
    tp = sum(h == "FAIL" and j == "FAIL" for h, j in zip(human, judge))
    fn = sum(h == "FAIL" and j == "PASS" for h, j in zip(human, judge))
    fp = sum(h == "PASS" and j == "FAIL" for h, j in zip(human, judge))
    tn = sum(h == "PASS" and j == "PASS" for h, j in zip(human, judge))
    return tp, fn, fp, tn


def agreement(human: list[str], judge: list[str]) -> Agreement:
    tp, fn, fp, tn = confusion(human, judge)
    n = tp + fn + fp + tn
    p_o = (tp + tn) / n
    # chance agreement: both say FAIL by chance + both say PASS by chance
    p_e = ((tp + fn) / n) * ((tp + fp) / n) + ((fp + tn) / n) * ((fn + tn) / n)
    kappa = 0.0 if p_e == 1 else (p_o - p_e) / (1 - p_e)
    tpr = tp / (tp + fn) if tp + fn else float("nan")
    tnr = tn / (tn + fp) if tn + fp else float("nan")
    prec = tp / (tp + fp) if tp + fp else float("nan")
    return Agreement(n, p_o, kappa, tpr, tnr, prec)

Husain therefore recommends precision and recall (or TPR and TNR) over raw agreement[2][22], and Yan recommends prioritising recall on the fail class. Yan reads κ of 0.4–0.6 as substantial and notes that humans often agree only at 0.2–0.3[23]; on the stricter Landis and Koch bands, 0.21–0.40 is “fair” and 0.41–0.60 “moderate”[52], so the realistic judge’s 0.388 is “fair”. The validation set is itself a small sample. With 10 human FAILs, TPR = 0.80 has a 95% Wilson interval of [0.49, 0.94]: this judge might miss half of all failures. Yan advises 50–100 fail cases, because “a dataset with hundreds of labels but only five failures isn’t useful”[23]. Enrichment changes the base rate, so on an enriched set report TPR and TNR, which do not depend on prevalence. And note the precision column: on a 95/5 set the realistic judge flags 27 items, only 8 of them real (0.30).

1.5Metrics in one page

Chapter 2 is devoted to metrics. Here we need only three ideas, because they shape every later chapter.

Accuracy is the fraction of tasks (or trials) graded as passing. It is the right headline number only when the tasks are a sensible sample of what you care about and the classes are not wildly imbalanced.

Precision and recall on the failure class. When the eval is a detector (judge, guardrail, toxicity filter), the interesting class is the rare one. Recall (TPR) asks “of the real problems, how many did we catch?”; precision asks “of the flagged items, how many were real?”. A detector with 99% accuracy on a 1% failure class can have zero recall. Yan recommends precision, recall, ROC-AUC and PR-AUC over a single accuracy for classification-style LLM tasks[26].

The parser is part of the metric. Before any grader runs, something extracts the “answer” from free-form text. When you run n trials of a task and c pass, two summaries answer opposite questions. pass@k asks “if I draw k attempts, does at least one pass?” (useful when a verifier can pick the good one, as with unit tests). pass^k asks “do all k attempts pass?” (what a customer talking to your agent k times experiences). Their unbiased estimators are[28][12]:

pass@k = 1 − C(n − c, k)C(n, k),    pass^k = C(c, k)C(n, k) (1.2)

With n = 10 and c = 3: pass@3 = 1 − 35/120 = 0.708 while pass^3 = 1/120 = 0.008. The same agent is “71% likely to get it within three tries” and “less than 1% likely to get it right three times in a row”. Anthropic’s example: a 75% per-trial success rate gives (0.75)3 ≈ 42% for three consecutive passes[1]. 1.6An eval score is an estimate

Your eval set is a sample: a few hundred draws from the universe of tasks your system will face, each trial one draw from its output distribution. Miller (Anthropic) treats eval questions as drawn from a “super-population” and reports the score with a standard error[31][32]. This section previews two day-one tools; Chapter 5 is the full treatment.

Standard error and the normal interval

For per-item scores s1, …, sn with mean s̄, the standard error of the mean and the central-limit-theorem (CLT, or Wald) interval are:

SE = sd(s)√n,    95% CI = s̄ ± 1.96 · SE,    for 0/1 scores: SE = √(p̂(1 − p̂)/n) (1.3)

A model scores 78% on 200 items. SE = √(0.78 · 0.22 / 200) = 0.0293, so the 95% interval is 78 ± 5.7 points, i.e. [72.3%, 83.7%]. A second model scoring 80% on the same items is not shown to be better by these numbers alone. (Pairing, which compares the two models item by item, narrows the comparison considerably; see Chapter 5.5.) Reproduced by code/ch01/wilson_defects.py.

Small samples and rates near 0 or 1: Wilson

The normal interval misbehaves when n is small or p̂ is near 0 or 1: it can extend below 0 and under-covers. Bowyer, Aitchison and Ivanova argue that CLT error bars dramatically underestimate uncertainty below a few hundred datapoints and recommend Wilson or Bayesian intervals[33]. The Wilson score interval with z = 1.96 is:

centre = p̂ + z²/2n1 + z²/n,    half-width = z · √( p̂(1 − p̂)/n + z²/4n² )1 + z²/n (1.4)

Here is the case that makes the point memorable, from Eugene Yan’s “Product Evals in Three Simple Steps”[23]. A requirement says the defect rate must be at most 5%. You label 200 outputs and find 6 defects, a 3% rate. Can you sign off?

Normal interval: 3% ± 1.96·√(0.03·0.97/200) = 3% ± 2.4 points = [0.6%, 5.4%]. Wilson interval: [1.4%, 6.4%]. Both upper bounds exceed 5%. The data are consistent with a true defect rate above the limit, so 200 samples cannot certify it. The margin shrinks with √n, so halving it needs four times the data; Wilson’s upper bound first drops below 5% between 400 (5.17%) and 800 (4.43%) samples.

def normal_ci(p: float, n: int) -> tuple[float, float]:
    half = Z * math.sqrt(p * (1 - p) / n)
    return p - half, p + half


def wilson_ci(p: float, n: int) -> tuple[float, float]:
    denom = 1 + Z**2 / n
    centre = (p + Z**2 / (2 * n)) / denom
    half = Z * math.sqrt(p * (1 - p) / n + Z**2 / (4 * n**2)) / denom
    return centre - half, centre + half


def n_for_difference(var_d: float, delta: float) -> float:
    """Items needed to detect a mean difference delta (alpha=0.05 two-sided, power 0.8)."""
    return (Z + Z_POWER) ** 2 * var_d / delta**2

How many items do I need?

The reverse question, “how big must the eval be to detect a difference I care about?”, is a power calculation. For a two-sided test at α = 0.05 with 80% power, the number of items needed to detect a mean difference δ is approximately:

n ≈ (z0.975 + z0.8)² · Var(d)δ² = (1.96 + 0.84)² · Var(d)δ² (1.5) where di = sA,i − sB,i is the per-item score difference. Paired: Var(d) = VarA + VarB − 2ρ·SDA·SDB. Unpaired: drop the covariance term.

Assumptions (as in the chapter’s research dossier, following Miller’s framework[31]): per-item Bernoulli scores with the variances of a model at 80% (VarA = 0.16) and one at 75% (VarB = 0.1875), a correlation ρ = 0.5 between the two models’ item scores (Anthropic reports ρ between about 0.3 and 0.7 for frontier models on popular evals[32]), and a target difference δ = 3 points. Then Var(d) = 0.3475 − 2·0.5·0.4·0.433 = 0.1743, and n ≈ 7.84 · 0.1743 / 0.0009 ≈ 1,518 paired items; without pairing, n ≈ 7.84 · 0.3475 / 0.0009 ≈ 3,027.

1.7Validity: are you measuring what matters?

Error bars tell you how much a score would move if you re-ran the eval. They say nothing about whether the eval measures the right thing. A thermometer can be precise to 0.01° and still be measuring the radiator instead of the room.

Construct validity

Bean et al. (42 authors, NeurIPS 2025 Datasets and Benchmarks) reviewed 445 LLM benchmarks with 29 expert reviewers. They define construct validity as the degree to which a benchmark score provides evidence for claims about the target phenomenon, and they distil eight recommendations and an operational checklist[5]. Their review finds that 78.2% of articles defined the phenomenon they measure, and of those definitions 47.8% were contested (phenomena such as “reasoning” with many possible definitions); 38.2% of benchmarks drew items from human exams or other pre-existing sources, and 42.6% reused data from existing benchmarks; 27.0% used convenience sampling as part of their sampling strategy (another 12.3% relied on it exclusively); only 16.0% used statistical tests (see the “no error bars” pitfall in 1.6); and only 53.4% presented evidence for construct validity[5]. Two older lines of work set this up:

  • Raji et al. argue that benchmarks presented as “general” measures of progress cannot support that claim; the title, “AI and the Everything in the Whole Wide World Benchmark”, is the argument[35].
  • Wallach et al. import the measurement framework of the social sciences: a background concept (“helpfulness”) is made into a systematised concept (a precise definition), operationalised as a measurement instrument (the eval), and applied to produce instance-level measurements. For a product team: write down the claim the eval must support (“the assistant books showings correctly for our agents’ real requests”) and check that tasks, graders and aggregation support exactly that. Synthetic, cleanly phrased tasks support a weaker claim than real traces.

Benchmark quality checklists

Two checklists are worth keeping open when you build or adopt a benchmark:

  • BetterBench (Reuel et al., NeurIPS 2024): 46 best practices across the full benchmark lifecycle, a minimum checklist, and scores for 24 benchmarks; most were hard to replicate and did not report statistical significance[4].
  • The Agentic Benchmark Checklist (ABC) (Zhu et al., 2025) targets agent benchmarks. It documents that SWE-bench Verified uses insufficient test cases and that τ-bench counts empty responses as successes, flaws that can mis-estimate performance by up to 100% in relative terms; applying ABC to CVE-Bench cut its overestimation by 33%[36].

Label errors and curation

A benchmark’s answer key has errors, and they cap what you can measure. Gema et al. (“Are We Done with MMLU?”) estimate that 6.49% of MMLU questions contain errors, with 57% of the analysed Virology questions affected, and release a re-annotated subset, MMLU-Redux[37]. When frontier models differ by a point on a benchmark whose labels are 6% wrong, the ranking partly measures agreement with the errors. SWE-bench Verified is the agent-era response: OpenAI had 93 developers screen 1,699 samples (three labels each, most severe kept), leaving 500 problems that real engineers confirmed are solvable[38] (partially verified: the OpenAI post returned 403; facts from search snippets of openai.com and swebench.com). Even so, ABC found its tests insufficient for some tasks[36]. Curation reduces label noise; it does not remove the need to read failures.

Saturation and contamination

An eval at 100% “tracks regressions but provides no signal for improvement”[1]. Public benchmarks saturate: with frontier models above 90% on MMLU, the Humanity’s Last Exam team built 2,500 expert-written questions as a harder successor[39]. SWE-bench Verified went from 30% to >80% during 2025[1]. Near the ceiling, large gains show up as small increases: Qodo was initially unimpressed by Opus 4.5 because its one-shot evals missed gains on longer tasks, and built a new agentic eval[1]; Chapter 2 covers the benchmark lifecycle and difficulty-aware metrics. A second threat is contamination: test items leak into training data, inflating scores without any gain in the underlying ability[40]. Dynamic benchmarks such as LiveBench and template-based variants such as GSM-Symbolic are partial defences[18][20]; Chapter 3 covers detection and prevention (3.9–3.12).

Answer-reachable environments: when agents look up the answer

Agent benchmarks add a threat that static benchmarks do not have. Contamination means the answer is in the training data; in a leaky environment the answer can be reached at eval time from inside the environment: a repository whose git history contains the fix commit, an open internet connection, a mounted copy of the benchmark. An agent rewarded for passing tests will find that route. Cursor audited SWE-bench Pro trajectories with an agent and found that 63% of successful Opus 4.8 Max resolutions retrieved the fix (from git history or the web) rather than deriving it. Sealing git history and restricting internet access dropped Opus 4.8 Max from 87.1% to 73.0% (−14.1 points) and Cursor’s own Composer 2.5 from 74.7% to 54.0%[50]. HAL’s LLM-aided log inspection found a related behaviour: agents searching for the benchmark on HuggingFace instead of solving the task[49].

Two defences work together. Seal the environment: strip git objects newer than the task’s base commit and allow only the network access the task needs. Audit transcripts for answer lookup, as Cursor did: flag trials that fetched the fix, the upstream patch or the benchmark, whatever the tests say. A score that drops sharply when sealed was partly measuring retrieval (7.6).

Evaluation awareness and sandbagging

A final threat comes from the system under test itself. Evaluation awareness means the model infers that it is being tested and behaves differently from how it would in deployment. Sandbagging is strategic underperformance on an evaluation, for example hiding a dangerous capability. Cursor puts the point bluntly: “As models become more aware of when they are being evaluated, they may change their behavior in subtler ways that are not fixed by sealing git history or restricting internet access.” They frame this as part of a broader problem, building evals that “retain construct validity even when the model infers that it is being evaluated”[50].

One practical defence is realistic task framing: build tasks from real traces rather than exam-style prompts. Then compare behaviour on the same tasks with and without test-like cues. If the score or the behaviour moves when only the framing changes, the eval is partly measuring the model’s guess about its situation. Chapter 8 treats both problems in depth: sandbagging and elicitation checks in 8.11, and evaluation awareness in 8.11.

Goodhart’s law and the winner’s curse

“When a measure becomes a target, it ceases to be a good measure.” Manheim and Garrabrant distinguish four mechanisms: regressional, extremal, causal and adversarial Goodhart[41]. The regressional variant is the one every eval builder meets first, and it needs no bad intent at all: if you select the best of many noisy scores, the winner’s score is biased upward, because it was selected partly for its luck.

The Leaderboard Illusion (Singh et al., 2025) documents this at scale on Chatbot Arena. Undisclosed private testing let providers try many variants and publish only the best; the paper reports Meta testing 27 private variants before the Llama 4 release, and data-access asymmetries in which Google and OpenAI received an estimated 19.2% and 20.4% of all Arena data. Training on Arena-style data produced relative gains of up to 112% on the Arena distribution[42]. Kapoor et al. identify the same mechanism in agent benchmarks: holdout sets are often inadequate or missing, so agents overfit and take shortcuts[13].

code/ch01/goodhart_holdout.py shows the regressional version in miniature. There are 200 candidate “prompt configurations” whose true accuracies are almost identical (drawn from a normal distribution with mean 0.70 and SD 0.02). We tune on a 30-item dev set, try the first K configs, keep the one with the best dev score, and then score the winner on a 2,000-item held-out test set. The whole experiment is repeated 400 times.

def one_run(rng: np.random.Generator) -> dict:
    p_true = np.clip(rng.normal(0.70, 0.02, size=N_CONFIGS), 0, 1)
    dev = rng.binomial(N_DEV, p_true) / N_DEV
    test = rng.binomial(N_TEST, p_true) / N_TEST
    out = {}
    for k in KS:
        j = int(np.argmax(dev[:k]))              # winner among the first k configs tried
        out[k] = (dev[j], test[j], p_true[j])
    out["oracle"] = float(p_true.max())
    return out

The dev score of whatever you selected is not an estimate of its performance; only an untouched held-out set is. The bias grows with the number of things tried (prompts, seeds, checkpoints, private Arena variants), so that number belongs in any honest report. And with a dev set this small, tuning mostly selects noise: the winner’s true accuracy (0.711 at K = 200) is one point above a random pick, though a 0.755 config existed. A bigger dev set, not more search, is the cure.

When the grader becomes a reward. In RL post-training the policy is optimised directly against the grader, so the extremal and adversarial variants dominate[41]: the policy seeks the grader’s blind spots (special-cased tests, a judge that rewards confident tone, a reachable answer). This reward hacking means a grader good enough for offline reporting can be inadequate as a reward (7.5).

Every time you change something in response to the held-out score, the held-out set becomes a dev set. Keep an untouched test split, rotate it once it has driven decisions, and count the configurations you tried. The same holds for judge prompts: Husain recommends train/dev/test splits[22], Yan a 75/25 dev/test split[23].

1.8Eval-driven development

The previous sections described evals as instruments. This one is about the practice of building them, which practitioners call eval-driven development (EDD). The sources agree on a loop: look at data, name the failure modes, write targeted evals for them, change the system, gate changes in CI, monitor production, and feed new failures back into the dataset[7][3][1].

OpenAI’s guide recommends “adopt eval-driven development”: evaluate early and often[3]. Husain and Shankar answer “Generally no” to the same phrase, because they read it as writing evaluators before features: “write evaluators for errors you discover, not errors you imagine”, except for known hard constraints[7]. The disagreement is about the word. Here EDD means the loop in Figure 1.4, which starts with error analysis; define a provisional objective, look at data, and revise both.

Step 0: define success

Anthropic’s documentation asks for success criteria that are specific, measurable, achievable and relevant, and gives a sentiment-analysis example of what that looks like: an F1 of at least 0.85 on a held-out test set of 10,000 diverse posts, 99.5% of outputs non-toxic, and 95% of responses under 200 ms[14]. Note the three dimensions (quality, safety, latency), each with a threshold and a test set. OpenAI’s guide frames the process as define the objective, collect a dataset, define metrics, run and compare, and evaluate continuously[3]. Take the form, not the metrics: a criterion is a metric, a threshold and a held-out set. Generic scores such as ROUGE-L or coherence track task-specific quality poorly[26][7]; replace them with task-specific, usually binary, evaluators found through error analysis (2.3), and treat the first criteria as a draft.

OpenAI’s evaluation best-practices page notes that its hosted Evals platform is being retired: read-only from 31 October 2026 and shut down on 30 November 2026[3] (page accessed 20 November 2026), ten days after this book’s date. The guidance itself is platform-independent; the openai/evals repository remains a historical reference and dataset source. Chapter 9 surveys alternative tooling (9.1).

Error analysis: open coding, axial coding, counting

Husain and Shankar call error analysis “the most important activity in evals”[7]. The method is borrowed from qualitative research:

  1. Collect representative traces. Real production traces if you have them; otherwise synthetic inputs built systematically along dimensions (for example features × scenarios × personas), not ad-hoc prompts[7][22].
  2. Open coding. A domain expert reads each trace and writes a free-text note about what went wrong, focusing on the first failure, because upstream errors cause downstream ones. Annotate at least 30 traces yourself before letting an AI assistant propose labels[7].
  3. Axial coding. Group the notes into a small taxonomy of failure modes and count each one. An LLM can propose a first-pass grouping, but “always review and refine the clusters yourself”[7].
  4. Iterate to saturation. Keep reading until new traces stop revealing new failure modes (“theoretical saturation”). The FAQ recommends reviewing at least 100 traces[7].

The FAQ recommends a single domain expert, a “benevolent dictator”, as final arbiter rather than a committee[7]. And Husain’s first rule from Rechat applies throughout: “Remove ALL friction from looking at data”, with a trace viewer built for your data[2].

code/ch01/error_analysis.py mocks steps 1–2 for a four-stage real-estate assistant (parse → retrieve → tool_call → answer): 40 traces, each with its first failing stage and a reviewer note. A keyword codebook stands in for axial coding, Counter gives a Pareto table, and a transition-failure matrix (rows: last stage that succeeded; columns: first that failed) shows where the pipeline breaks, which the FAQ recommends for tool-using conversations “to find hotspots of errors”[7].

def axial_code(note: str) -> str:
    low = note.lower()
    for category, keys in CODEBOOK.items():
        if any(k in low for k in keys):
            return category
    return "UNCLASSIFIED"


def pareto(categories: list[str]) -> list[tuple[str, int, float, float]]:
    counts = Counter(categories).most_common()
    total, cum, rows = sum(c for _, c in counts), 0, []
    for cat, c in counts:
        cum += c
        rows.append((cat, c, c / total, cum / total))
    return rows


def transition_matrix(traces: list[Trace]) -> dict[tuple[str, str], int]:
    """Rows: last stage that succeeded. Columns: first stage that failed (Husain & Shankar FAQ)."""
    m: Counter = Counter()
    for t in traces:
        if t.failed_at is None:
            continue
        i = t.path.index(t.failed_at)
        last_ok = t.path[i - 1] if i > 0 else "START"
        m[(last_ok, t.failed_at)] += 1
    return dict(m)

From failure modes to evaluators

Each important failure mode gets its own evaluator, and each evaluator gives a binary pass/fail verdict. The FAQ’s argument against 1–5 Likert scales is practical: the difference between adjacent points is subjective and inconsistent across annotators, detecting differences needs larger samples, and annotators default to the middle value; to track gradual progress, break the quality into several binary checks (“4 out of 5 expected facts included”)[7]. Yan names the opposite anti-pattern the “God Evaluator”: one prompt asked to grade five to ten dimensions at once[23]. One evaluator per dimension is easier to validate, debug and act on.

Choose the cheapest evaluator that can catch the failure. The FAQ’s cost hierarchy: assertions and reference-based checks are cheap to build and maintain, while an LLM judge “requires 100+ labeled examples, ongoing weekly maintenance, and coordination between developers, PMs, and domain experts”[7]. Many failures are preferences you never told the model about, which a one-line prompt change removes. Research backs assertions first: SPADE synthesises assertion functions from a pipeline’s prompt-edit history, cutting the number of assertions by 14% and false failures by 21% versus simpler baselines[43]; its NLP ancestor CheckList helped users find about three times as many bugs[44].

For the failure modes that need a judge, Husain’s critique shadowing process builds one that matches the expert: the principal domain expert gives pass/fail verdicts with written critiques on a structured dataset; you fix obvious system errors; then you iterate the judge prompt, using the critiques as few-shot examples, until it agrees with the expert on held-out data. In the Honeycomb case the judge reached more than 90% agreement in three iterations[22]. Chapter 4.5 covers this in detail (4.5).

Criteria drift

Shankar et al. studied people building LLM-assisted evaluators with their EvalGen tool and found a chicken-and-egg problem they call criteria drift: users need criteria to grade outputs, but grading outputs is how they discover their criteria, and some criteria only emerge after seeing outputs[45]. This is why the rubric cannot be fixed in advance, why the success criteria in Step 0 are a draft, and why the loop in Figure 1.4 is a loop.

Start small; capability vs regression; graduation

“We see teams delay building evals because they think they need hundreds of tasks. In reality, 20–50 simple tasks drawn from real failures is a great start”[1]. Early changes have large effects, so small sets detect them; the set grows as differences shrink (section 1.6). Build balanced sets that test when a behaviour should and should not occur (“One-sided evals create one-sided optimization”), and isolate trials[1].

Keep separate suites with separate gates. A regression suite sits near 100% and any failure blocks a merge. A capability suite is gated statistically: is the candidate credibly at least as good as required? When capability tasks are reliably solved, they graduate into the regression suite. code/ch01/regression_gate.py implements this with a JSONL golden set (15 regression and 25 capability tasks), four mock releases, and a two-part rule: every regression task must pass every one of its 3 trials, and the 95% Wilson lower bound of capability accuracy must be at least the floor stored in data/baseline.json (0.40, set just below the shipped v1’s lower bound of 0.422).

def run_gate(version: str, tasks: list[dict], floor: float) -> GateResult:
    per_task: dict[str, float] = {}
    for t in tasks:
        k = TRIALS[t["suite"]]
        per_task[t["id"]] = sum(mock_system(version, t, i) == t["target"] for i in range(k)) / k
    reg_fail = [t["id"] for t in tasks if t["suite"] == "regression" and per_task[t["id"]] < 1.0]
    cap = [per_task[t["id"]] for t in tasks if t["suite"] == "capability"]
    acc = sum(cap) / len(cap)
    lower = wilson_lower(acc, len(cap))
    return GateResult(version, not reg_fail and lower >= floor, reg_fail, acc, lower, per_task)


def graduate(tasks: list[dict], results: list[GateResult]) -> list[str]:
    """Capability tasks solved on EVERY trial by every listed release move to the regression suite."""
    return [t["id"] for t in tasks if t["suite"] == "capability"
            and all(r.per_task[t["id"]] == 1.0 for r in results)]

Ten recommendations

Distilled from the sources in this chapter, in roughly the order you will need them:

  1. Start now and small: 20–50 tasks drawn from real failures[1]; read at least 100 traces yourself[7].
  2. Error analysis first: open coding, axial coding, counts; write evals for failures you found, not failures you imagined[7].
  3. Assertions before judges: code-based checks wherever possible; LLM judges only for what code cannot catch, each validated against expert labels on a held-out split, reporting TPR/TNR or κ.
  4. Binary, one dimension per evaluator; for pairwise judgments, swap the order and allow ties[21][23].
  5. Separate suites: capability (a hill to climb), regression (near 100%, gating CI) and online monitoring; graduate saturated capability tasks.
  6. Error bars on every number: paired comparisons, clustered SEs, power analysis, multiple trials and pass^k where consistency matters[31].
  7. Design tasks defensively: balanced positive and negative cases, isolated trials, outcome grading, reference solutions, guards against shortcuts.
  8. Track cost and latency alongside quality[13].
  9. Make looking at data frictionless: a trace viewer built for your data[2].
  10. Treat evals like code: owned, versioned, reviewed and maintained, with domain experts contributing tasks.

  • An eval is a test for an AI system: tasks, trials, graders, transcripts and outcomes, run by an eval harness; for agents the unit under test is model + harness.
  • Grade outcomes, not claims; read transcripts before trusting any surprising number, because graders fail as often as models do.
  • Classify every eval on the seven axes; a product needs offline and online, capability and regression, quality and cost.

  • The answer parser is part of the metric: the same 16 outputs score 31%, 62% or 88%.

  • Selecting the best of many configs on a small dev set inflates its score (0.91 dev vs 0.71 test in our simulation); keep a held-out set.
