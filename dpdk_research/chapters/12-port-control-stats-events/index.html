Chapter 12

Port Control, Statistics, Events, Live Reconfiguration and Composite PMDs

Chapter 8 taught you to bring a port up and move packets. This chapter covers everything else you do to a running port: change its MAC, MTU and filters, read the right counters, react to events, take one queue out of service, restart it safely, shut it down without leaking a single mbuf, recover from faults, and build one logical port out of several.

1The control surface of a port

In ch8 you used the data path of a port: rte_eth_rx_burst() and rte_eth_tx_burst(), called millions of times per second from a polling lcore. Everything else you can do to a port is the control path: setting addresses and filters, reading counters, changing the MTU, starting and stopping queues, reacting to the link going down. Control calls are slow (microseconds to milliseconds), are made rarely, and usually run on the main lcore or a control thread, not on the polling lcores.

Every control call follows the same route. The public function in lib/ethdev/rte_ethdev.c checks the port id and the arguments, then calls one entry of the driver's struct eth_dev_ops, a table of about 150 function pointers. A PMD fills in only the entries it can support. If the entry is NULL, ethdev returns -ENOTSUP without calling the driver. So -ENOTSUP is not an error in your program: it is the driver telling you "I do not have this feature". Your code must expect it.

2MAC, promiscuous mode, MTU, VLAN, link and packet types

MAC addresses

A port has one default MAC address (slot 0) and, on most NICs, extra slots for more unicast addresses it should accept. rte_eth_macaddr_get() reads slot 0, rte_eth_dev_default_mac_addr_set() replaces it, rte_eth_dev_mac_addr_add() / _remove() manage the extra slots (dev_info.max_mac_addrs says how many). On a real NIC these program the hardware receive filter. On net_tap they also change the kernel interface: the output below shows the kernel's /sys/class/net/ch12tap0/address following the DPDK call.

Promiscuous and all-multicast

A NIC normally drops, in hardware, every frame whose destination MAC is neither its own address, broadcast, nor a multicast group it joined. Promiscuous mode turns that filter off: every frame is delivered. All-multicast accepts every multicast frame but still filters unicast. A software switch, a bridge, a capture tool, or a router whose neighbours address frames to a virtual MAC all need promiscuous mode. DPDK ports usually start with promiscuous mode on for exactly this reason (testpmd enables it on every port).

MTU and the mbuf data room

The MTU is the largest L3 payload a frame may carry: 1500 bytes for standard Ethernet, so a full frame is 1500 + 14 (header) + 4 (FCS) = 1518 bytes. rte_eth_dev_set_mtu() changes what the port accepts and sends, within dev_info.min_mtu..max_mtu. It does not change your mbufs. A pool made with RTE_MBUF_DEFAULT_BUF_SIZE has 2048 bytes of data room after the headroom, so a 9000-byte jumbo frame does not fit in one mbuf. Either create the pool with a larger data room, or enable RTE_ETH_RX_OFFLOAD_SCATTER so the PMD chains several mbufs per frame (ch19 covers scatter and buffer split). If you do neither, a PMD that supports jumbo frames will drop them or refuse the MTU.

VLAN filter, link control, packet types

  • rte_eth_dev_vlan_filter(port, vid, on) adds a VLAN id to the hardware VLAN filter. The port must be configured with RTE_ETH_RX_OFFLOAD_VLAN_FILTER, otherwise ethdev returns -ENOSYS (you saw it in the matrix). VLAN stripping is an RX offload too, changed at runtime with rte_eth_dev_set_vlan_offload() only if the PMD lists it in rx_offload_capa.
  • rte_eth_dev_set_link_down() / _up() take the link administratively down, like ip link set dev X down. rte_eth_link_get() may wait up to several seconds for autonegotiation on a real NIC; on the data path or in a callback use rte_eth_link_get_nowait(), which returns the last known state immediately. rte_eth_link_to_str() formats it.
  • rte_eth_dev_get_supported_ptypes() lists the packet types the PMD can recognise and write into mbuf->packet_type (ch10). rte_eth_dev_set_ptypes() tells the PMD which ones you actually need, so it can skip work; when the PMD has no dev_ptypes_set op, ethdev quietly returns 0, which is why the matrix shows OK everywhere.

3The 26.11 statistics model

Statistics answer the first question of every incident: "where did my packets go?" DPDK has two layers.

Basic stats, rte_eth_stats_get(port, &stats), fill a small fixed struct of port totals. In DPDK 26.11 it has exactly eight fields:

fieldcountswhere it happens
ipackets, ibytespackets/bytes received and handed to the appPMD RX
imisseddropped by the NIC because the RX ring had no free descriptor (the app did not poll fast enough)NIC hardware
ierrorsreceived with errors (bad CRC, runt, too long)NIC hardware
rx_nombufRX mbuf allocation failures: the pool was empty when the PMD wanted to refillPMD RX
opackets, obytespackets/bytes the PMD accepted for transmissionPMD TX
oerrorspackets the PMD accepted but failed to sendPMD TX / NIC

Older DPDK versions also had per-queue arrays q_ipackets[], q_opackets[], q_ibytes[], q_obytes[], q_errors[] in this struct, limited to RTE_ETHDEV_QUEUE_STAT_CNTRS queues and steered with rte_eth_dev_set_rx_queue_stats_mapping(). 26.11 removed all of that, together with the rx_qN_errors xstat (see doc/guides/rel_notes/release_26_11.rst). Per-queue counters now exist only as extended statistics (xstats), for every queue.

xstats are name/value pairs. The names follow a pattern, direction first, then detail, then unit: rx_good_packets, rx_q0_packets, tx_q3_bytes, rx_size_128_to_255_packets. ethdev itself provides the 8 generic ones plus, for PMDs that set RTE_ETH_DEV_AUTOFILL_QUEUE_XSTATS, 4 per queue (rx_qN_packets, rx_qN_bytes, tx_qN_packets, tx_qN_bytes). That is the 12 you saw on a 1-queue port. Drivers add their own on top: a real NIC typically exposes hundreds (size histograms, per-priority pause frames, error kinds). In this chapter failsafe adds per-sub-device copies (section 9).

Reading xstats cheaply

The full API is two-step: rte_eth_xstats_get_names(port, NULL, 0) returns the count, then you allocate and call rte_eth_xstats_get_names() and rte_eth_xstats_get(). Each value carries an id that indexes the names array. That is fine for a dump, but a monitor that reads one counter every 100 ms should not copy hundreds of names each time. Look the id up once, then read only that id:

uint64_t id, val;
rte_eth_xstats_get_id_by_name(port, "rx_q0_packets", &id);   /* once, at start-up */
...
rte_eth_xstats_get_by_id(port, &id, &val, 1);               /* every 100 ms: one value */

The ids are stable while the port's configuration does not change; look them up again after a reconfigure that changes the queue count. rte_eth_stats_reset() and rte_eth_xstats_reset() zero the counters (PMDs that keep counters in hardware may implement the reset as "remember an offset").

Warning: a counter that does not move is not proof

A PMD counts only what it decides to count. In the failure lab (section 8) net_pcap with infinite_rx=1 runs out of mbufs and simply returns 0 packets with rx_nombuf still at 0, and net_ring never counts oerrors. When the counters and the traffic disagree, believe the traffic and read the PMD source.

4Events, hotplug and the device monitor

Some things happen to a port without you asking: the link goes down, a VM connects to a vhost port, a device is hot-unplugged, the NIC needs a reset. ethdev reports these as events. You register a function per event type with

int rte_eth_dev_callback_register(uint16_t port_id, enum rte_eth_event_type event,
                                  rte_eth_dev_cb_fn cb_fn, void *cb_arg);
typedef int (*rte_eth_dev_cb_fn)(uint16_t port_id, enum rte_eth_event_type event,
                                 void *cb_arg, void *ret_param);

Who calls your callback

A callback runs in the thread that noticed the event, never on your polling lcores. Interrupt-driven events (LSC from a NIC, events a PMD defers with an alarm) run in the EAL interrupt thread, dpdk-intr. A PMD with its own thread raises events from it (vhost uses dpdk-vhost-evt). NEW and DESTROY run synchronously in whatever thread called rte_dev_probe() or rte_eth_dev_close(). While the callback runs, your data-path lcores keep polling, so a callback touches the same port concurrently with them. The rules that follow:

  • Be short and never block: while you run, no other interrupt or alarm in the process is serviced.
  • Do not stop, close or reconfigure the port from its own callback. Record what happened (an atomic flag, a message on a ring) and do the work later, from the control thread or from an rte_eal_alarm_set() callback (an alarm runs outside the ethdev callback list).
  • In a NEW callback the port is not yet usable: it is announced before probing finishes. Our program shows ETHDEV: Invalid port_id=1 when it calls rte_eth_dev_get_name_by_port() from NEW. Attach and configure it later.

    Hotplug and unplug at runtime

    Ports do not have to exist at start-up. rte_dev_probe(devargs) takes the same string you would give to --vdev (or a PCI address) and probes it now: a new port id appears and NEW fires. Removing is a three-step sequence, in this order:

    1. rte_eth_dev_info_get() and keep dev_info.device: after close the port no longer knows its device.
    2. rte_eth_dev_stop(), then rte_eth_dev_close(): the port is released and DESTROY fires.
    3. rte_dev_remove(device): the bus driver detaches the device.

    The EAL can also watch the kernel for devices appearing and disappearing: rte_dev_event_monitor_start() opens a netlink uevent socket and rte_dev_event_callback_register(NULL, fn, arg) gets RTE_DEV_EVENT_ADD/_REMOVE for every device. It is built for PCI hot-unplug (with rte_dev_hotplug_handle_enable()), and the Linux implementation parses only uevents whose subsystem is pci, uio or vfio (lib/eal/linux/eal_dev.c). Our program creates a veth pair to prove the point: nothing is reported.

    5RX and TX burst callbacks

    Events tell you about the port. Burst callbacks let you see every burst of packets. rte_eth_add_rx_callback(port, queue, fn, arg) registers a function that ethdev calls inside rte_eth_rx_burst(), after the PMD has filled the array and before it returns to you. rte_eth_add_tx_callback() does the same inside rte_eth_tx_burst(), before the PMD. The callback gets the packet array and returns the new number of packets, so it can inspect, modify, timestamp, or filter. Typical uses are latency measurement (the examples/rxtx_callbacks sample, and lib/latencystats in ch13), packet capture (lib/pdump, ch16) and software classification for a PMD that lacks it.

    Callbacks are a per-queue list. rte_eth_add_rx_callback() appends to the tail; rte_eth_add_first_rx_callback() inserts at the head. They cost a function call per burst even when they do nothing, and they need RTE_ETHDEV_RXTX_CALLBACKS, which is enabled in the default build (config/rte_config.h).

    Pitfall: freeing a callback while another lcore runs it

    rte_eth_remove_rx_callback() unlinks the callback but does not free it, because another lcore may be executing it at that very moment. The program above removes its callbacks from the only thread that polls those queues, so it can rte_free() them immediately. With other polling lcores you must wait until each has finished at least one burst after the removal: a fixed delay, or properly, an RCU quiescent-state check (ch14). Exercise 3 asks you to do this.

    6Per-queue control and runtime queue setup

    Stopping a whole port to change one queue is heavy: every queue loses traffic. ethdev therefore lets you control queues one by one on a started port.

    • Deferred start. Set rx_deferred_start = 1 in the struct rte_eth_rxconf you pass to rte_eth_rx_queue_setup() (tx_deferred_start in rte_eth_txconf). rte_eth_dev_start() then leaves that queue stopped, and you start it later with rte_eth_dev_rx_queue_start(). Use it to bring a port up before the lcore that will poll a queue is ready.
    • Queue start/stop: rte_eth_dev_rx_queue_start/stop(port, q) and rte_eth_dev_tx_queue_start/stop(), only on a started port, and only if the PMD implements them.
    • Validity: rte_eth_rx_queue_is_valid() / rte_eth_tx_queue_is_valid() return 0 if the queue id exists and has been set up.
    • Queue state is recorded by ethdev as STOPPED (0) or STARTED (1). The public way to read it is rte_eth_rx_queue_info_get() (qinfo.queue_state), but that is -ENOTSUP on most vdevs, so our programs ask the process's own telemetry socket for /ethdev/info,N and read its rxq_state array (rxq_states() in ch12_common.h).
    • Runtime queue setup. Calling rte_eth_rx_queue_setup() on a started port is allowed only if dev_info.dev_capa has RTE_ETH_DEV_CAPA_RUNTIME_RX_QUEUE_SETUP (_TX_ for TX), and the queue is stopped. Otherwise it returns -EBUSY. Print capability bits by name with rte_eth_dev_capability_name(bit).

      9Composite PMDs: bonding, failsafe and hardware aggregation

      A composite PMD is a driver whose "hardware" is other ports. Your application sees one port; underneath, the composite forwards each call to its members. To stop the application from using the members directly, a composite takes ownership of them with rte_eth_dev_owner_new() / rte_eth_dev_owner_set(): owned ports disappear from RTE_ETH_FOREACH_DEV (you can still list them with RTE_ETH_FOREACH_DEV_OWNED_BY). Representor ports, which also form groups, are a different idea and belong to ch20.

      The bond watches a member's link with an LSC callback if the member sets RTE_ETH_DEV_INTR_LSC in dev_flags, and polls it only otherwise (drivers/net/bonding/rte_eth_bond_pmd.c). net_tap sets the flag but never raises the event, so the bond never learns that the link went down. The same trap catches your own code (section 8, fault 3). Test failover on the real NIC you deploy on.

      Hardware aggregated ports

      Some NICs (for example mlx5 in a bonding/LAG configuration) aggregate two physical ports in hardware and present one DPDK port. There is no member list to manage; instead, rte_eth_dev_count_aggr_ports(port) returns how many physical ports are behind it, and rte_eth_dev_map_aggr_tx_affinity(port, tx_queue, affinity) pins a TX queue to physical port affinity (1..n; 0 means "let the NIC choose"). Both are stable API in 26.11. Our bond and its tap members all returned 0, and the affinity call -ENOTSUP: software bonding is not hardware aggregation, and code that wants affinity must check for a count of at least 2 first.

      Common pitfalls

      • Treating -ENOTSUP as fatal: half the control API is optional. Probe once, record a capability, continue with a fallback.
      • Looking for stats.q_ipackets[]: gone in 26.11, along with queue-stats mapping and rx_qN_errors. Read rx_qN_packets as an xstat, by id.
      • Waiting for an LSC callback that never comes: net_tap (and any PMD that sets the flag without raising the event) needs link polling with rte_eth_link_get_nowait(). Bonding falls into the same trap.
      • Calling rte_eth_link_get() on the data path: it may block for seconds on a real NIC. Use _nowait.
      • Closing or reconfiguring a port inside its own event callback: set a flag, or rte_eal_alarm_set(), and do it outside.
      • Using the port id in a NEW callback: the port is not attached yet (Invalid port_id).
      • Freeing a removed RX/TX callback immediately while other lcores poll that queue: use-after-free. Wait for quiescence (RCU, ch14).
      • Trusting rx_deferred_start: tap and pcap ignore it; null and ring reject it with -ENOTSUP and the port still starts with the queue unset. Check the queue state after start.
      • Assuming rx_queue_stop() stops packets: on tap/pcap it is bookkeeping only. Stop polling first, drain, then stop; expect a backlog on restart.
      • Trusting a composite's dev_capa: failsafe advertises runtime queue setup that its sub-device refuses, and the failed attempt released the queue.
      • Reconfiguring while a worker still polls: pause the data path and wait for its acknowledgement before rte_eth_dev_stop().
      • Freeing the pool before closing the ports, or never draining software rings: rte_mempool_in_use_count() must be 0 at the end; 2,038 here when two drains were skipped.
      • Retrying tx_burst forever in a shared loop: head-of-line blocking of every other port. Bound retries; drop or buffer per destination.
      • Believing a flat counter: net_pcap infinite_rx fails allocations without counting, net_ring never counts oerrors, and no PMD counts what tx_burst refused.
      • Setting MTU 9000 with 2 KB mbufs: frames do not fit. Enlarge the data room or enable scatter.

      Summary
      • Every control call goes through an optional eth_dev_ops entry; -ENOTSUP means "this PMD lacks it", -EBUSY means "stop the port first", -ENOSYS here meant "offload not enabled".
      • Promiscuous mode turns off the destination-MAC filter (10/0/10 vs 10/10/10 on tap). MTU does not resize mbufs.
      • struct rte_eth_stats has 8 port totals in 26.11; per-queue counters are xstats, read by id. PMDs count only what they choose to count.
      • Event callbacks run in the thread that noticed the event; keep them short and defer real work. tap never raises LSC: poll.
      • RX/TX burst callbacks run inside the burst calls, in list order; removing one does not free it.
      • Deferred start, queue start/stop and runtime setup are PMD-specific: measured behaviour differed on all five ports.
      • A restart costs microseconds on software ports and much more on hardware; pause the data path around it. Teardown has an order, and the proof is in_use_count == 0.
      • Pool dry, TX full, link flap and reset each have a counter signature; passive vs proactive err_handle_mode decides who recovers.
      • Bonding and failsafe make one port from several in software (with real limits); hardware aggregation is one port with count_aggr_ports() >= 2.
