    Part VI · Chapter 25

    Profiling, Benchmarking and Tuning for Throughput

    A throughput number is only useful if you know what it measured. This chapter shows how MJWarp's own tools measure a step, how to read where the time goes, how the project benchmarks itself every night, and how to turn the knobs from earlier chapters into a faster simulation that still computes the same physics.

    Expert About 90 min· Prerequisites: Ch 24 (recommended: Ch 9, Ch 20, Ch 22)

    You will learn

    • How to time a step correctly (warm-up, synchronize, graphs) and convert between world-steps/s, ns per world-step and the realtime factor.
    • What m.block_dim controls, and how MJWarp sizes tiled and grid-stride launches.
    • How to profile a captured step with EventTracer and read its tree in ns per world-step.
    • How mjwarp-testspeed measures, all of its flags, and the defaults that change results: ctrl noise, --nworld 8192 and --function.
    • How the benchmark suite (run.py, sweep.py, the nightly systemd timer) and control trajectories (make_trajectory, load_trajectory, --replay) work.
    • How to size buffers and memory from measurements, and a tuning checklist with a worked study.

    In Colab: Runtime > Change runtime type > GPU, then run the first cell. Most tools in this chapter are GPU only; on CPU every example prints a skip note and runs a small stand-in.

    Before you start: recap

    • Kernel launches return to Python before the GPU has run them; time only after wp.synchronize(), and warm up first so JIT compilation is not timed (Ch 4 §10).
    • 32 lanes run in lockstep; branches serialize; contiguous reads coalesce; Ch 4 §4.
    • Most pipeline functions carry @event_scope; inside an EventTracer they record CUDA events and nest into a tree (Ch 7 §9).
    • A CUDA graph records launches once and replays them; conditional nodes loop on device; Ch 7 §10, owned by Ch 24.
    • nconmax is per world, naconmax is the total; overflow drops contacts or rows and sets bits in d.overflow (Ch 9 §8).
    • Solver knobs (solver, iterations, ls_iterations, tolerance) trade accuracy for time (Ch 20 §10); determinism has a price (Ch 22 §8).

    1What a throughput number means

    MJWarp advances nworld independent worlds per call. One world advanced by one timestep is a world-step. Every benchmark tool in the repository reports three views of the same measurement. If a rollout of nstep steps over nworld worlds took T seconds of device time:

    \text{world-steps/s} = \frac{n_\text{world}\, n_\text{step}}{T}
    \text{ns per world-step} = \frac{10^9\, T}{n_\text{world}\, n_\text{step}}
    \text{realtime factor} = \frac{n_\text{world}\, n_\text{step}\, \Delta t}{T}

    These are exactly the "Total steps per second", "Total time per step" and "Total realtime factor" lines that mjwarp-testspeed prints (testspeed.py::_main). ns per world-step is the unit of everything in this chapter, because it can be added up stage by stage. But it is not the latency of one call: a step at nworld = 8192 takes 8192 times longer than one world-step suggests, and that is the number a controller in the loop would feel. Play with the relation below.

    Where the stopwatch goes

    On a GPU, mjw.step only enqueues about a hundred kernels and returns. A timer read right after the call measures Python, not physics. Every correct measurement in MJWarp follows the same pattern, which cli.unroll uses for testspeed:

    1. Warm up. The first call JIT-compiles kernels (seconds to minutes); testspeed reports it separately as jit_duration, the time of the capture.
    2. Capture a graph so the per-launch Python overhead disappears (Ch 24).
    3. Bracket the replay with wp.synchronize(): t0 = perf_counter(); capture_launch(graph); synchronize(); t1 = perf_counter(). Anything else (the ctrl-noise kernel, host reads of nacon) runs outside the bracket.
    4. Keep the rest equal: same nworld, same model and sizes, zero overflow, every world converged (the rules in CONTRIBUTING.md).

    Pitfall: CPU numbers are not GPU numbers

    Every number printed by this chapter's examples on CPU (the course's verification box) is labelled "CPU". On CPU Warp runs kernels one thread after another and every launch costs Python time, so the ranking of two settings on CPU can be the opposite of the ranking on a GPU. Use CPU runs to check that a script works and that the physics is unchanged; rank settings with your own GPU numbers from the notebook.

    2Launch configuration: m.block_dim and occupancy

    Most MJWarp kernels are plain wp.launch(kernel, dim=(nworld, n)) calls: one thread per world and element, block size chosen by Warp. A second family is tiled: wp.launch_tiled(..., dim=nworld, block_dim=B) gives every logical index a whole block of B threads that cooperate on tile operations or stride over rows. The solver's loops look like this (solver.py):

    worldid, tid = wp.tid()                 # tid in 0 .. block_dim-1
nefc = wp.min(njmax_in, nefc_in[worldid])
for efcid in range(tid, nefc, wp.block_dim()):   # block-stride over this world's rows
    ...

    The block widths live in one dataclass, types.BlockDim, stored on the model as m.block_dim. Its docstring says "TODO(team): experimental and may be removed". These are its fields and defaults in the 4.0.1 wheel:

    Sizing grid-stride launches from occupancy

    Some launches do not use one thread per slot. The convex collider (collision_convex.py::_ccd_grid_size) launches a grid-stride kernel whose width is "a few device waves, capped at the contact capacity": max(1, min(naconmax, 2 * block_size * min_grid_size)), where (block_size, min_grid_size) = wp.get_suggested_block_size(kernel, device) is CUDA's occupancy suggestion. On CPU it returns naconmax ("Warp forces CPU block_dim to 1 and has no CUDA occupancy information"). The NXN broadphase caps its blocks the same way: max_blocks = 8 * block_size * min_grid_size // m.block_dim.nxn_broadphase (collision_driver.py::nxn_broadphase).

    Version note: dev tree only, not in 4.0.1

    The dev tree (commit 8f5b9f1) adds two helpers to warp_util.py that the 4.0.1 wheel does not have: side_stream(device), a second stream that exists only while a graph is being captured (so J @ search and M @ search become parallel branches of the graph), and efc_threads_per_world(nworld, njmax, device, kernel, num_waves=6), which returns 32 * min(njmax // 32, max(1, num_waves * block * grid // (32 * nworld))) on CUDA and njmax on CPU or when njmax <= 32. Its test table: (4096, 384) → 288, (8192, 384) → 128, (8192, 384, waves 1) → 32, (1, 384) → 384. The figure above evaluates the formula; course code never calls either name.

    Should you change m.block_dim?

    Rarely, and only with GPU measurements. The values are Python ints read when a launch is issued (a graph bakes them, Ch 24); convex_ccd is also compiled into the kernel as a module option and launch bound, so changing it compiles a new module. The defaults were picked by the developers on real GPUs. Sizes (nconmax, njmax) and solver settings matter far more.

    3The profiling workflow: event_scope and EventTracer

    Recall from Ch 7

    @event_scope wraps most pipeline functions; inside an EventTracer they record events and nest, so tracer.trace() returns {name: ((ms per call, ...), {child: ...})} (Ch 7 §9). This section adds the workflow: how the tree is built, how to profile a captured step, and how to turn milliseconds into ns per world-step.

    The wrapper (warp_util.py::event_scope) is short. When no tracer is active the module global _STACK is None and it just calls the function. With a tracer it swaps in a fresh dictionary for the children, records an event before and after the call, then merges what the children recorded under the function's name. Repeated calls with the same name append another event pair. Step through one mjw.step:

    Building the trace tree

    warp_util.py::event_scopeSimplified call tree
    def wrapper(*args, **kwargs):
  if _STACK is None:
    return fn(*args, **kwargs)
  if inside capture_while/capture_if:
    return fn(*args, **kwargs)
  saved_stack, _STACK = _STACK, {}
  wp.record_event(beg)
  res = fn(*args, **kwargs)
  wp.record_event(end)
  sub_stack, _STACK = _STACK, saved_stack
  events = prev_events + ((beg, end),)
  _STACK[name] = (events, merged sub_stack)
  return res

    Profiling a captured step

    The tool's own workflow is in cli.unroll: open the tracer, capture the function inside it (the recorded events become graph nodes), then replay and call tracer.trace() after each replay; testspeed adds the per-replay traces with _sum_trace. To report a stage, divide by both the number of replays and nworld: 1e6 * t_ms / (nstep * nworld) is ns per world-step (testspeed.py::_flatten_trace). Example 25.1 does exactly that on the GPU. On CPU the tracer is built with enabled=False (Rule G), so the example records the same tree a different way: it watches the event_scope wrapper with sys.setprofile (skipping conditional bodies, as the wrapper does) and times it with the wall clock.

    Reading the output

    The tree has the same names on CPU and GPU because both come from the same @event_scope wrappers. The numbers do not transfer: on CPU collision dominates because every narrowphase launch costs Python and serial C++ time; on a GPU the same stage may be a few percent. Notice also what is missing: _solver_iteration and _linesearch are scoped functions, but they run inside capture_while (the default graph_conditional=True path, also taken on CPU), so they never appear. Their time is inside solve. And the parent is a bit more than the sum of its children: the difference is unscoped work (small kernels launched directly by the parent).

    Going deeper: why the CPU stand-in is honest about structure

    All event_scope wrappers are closures over the same code object, so warp_util.event_scope(lambda: None).__code__ identifies every one of them. A profile hook sees each call and return of that code and reads the closure variable name from the frame, which is exactly the key EventTracer would use. Warp's CPU launches run before wp.launch returns, so the wall-clock interval of a wrapper covers its kernels. The hook itself costs time on every Python call, which is one more reason to read only proportions from it, and only as CPU proportions.

    4mjwarp-testspeed: the measurement tool

    mjwarp-testspeed is the command the project uses for every performance number. It is installed with the wheel (pyproject.toml: mjwarp-testspeed = "mujoco_warp.testspeed:main") and can also be run as python -m mujoco_warp.testspeed. The MJCF path falls back to the installed package (cli.load_model tries epath.resource_path("mujoco_warp") / path), so on Colab mjwarp-testspeed test_data/humanoid/humanoid.xml works without cloning anything.

    GPU only

    testspeed._main calls wp.init(), picks the device and raises ValueError("testspeed available for gpu only") on CPU, before it loads the model. Every testspeed example below runs it on a GPU and falls back to a hand-made loop on CPU.

    Ctrl noise: what --noise_std and --noise_rate do

    The ctrl noise kernel cli._ctrl_noise runs once per step with one thread per (world, actuator). With \rho = e^{-\Delta t/\tau} (\tau = noise_rate in seconds) and \sigma = noise_std:

    \begin{aligned} u &\leftarrow \rho\,u + (1-\rho)\,c + \sigma\sqrt{1-\rho^2}\,h\,(2s - 1) \\ s &= \mathrm{halton}\bigl((i+1)(w+1),\;a+2\bigr) \end{aligned}

    where c is the keyframe or replay ctrl (the kernel falls back to the middle of ctrlrange for an empty center, which testspeed never passes), s is the Halton sample (i = step, w = world, a = actuator), h is half the ctrl range (1 for unlimited actuators), and the result is clipped to the range. The samples come from a Halton sequence (util_misc.halton) indexed by step and world, so the noise is deterministic but different in every world. That is the point: with the default noise the 8192 worlds of a benchmark visit 8192 different states; with --noise_std 0 they are 8192 copies of world 0. The widget runs the exact formula.

    Going deeper: why some worlds drift below the center

    In Figure 25.8 worlds 1, 3 and 7 settle below the center. That is the formula, not the widget. Actuator 0 samples halton((i+1)(w+1), 2), the base-2 radical inverse of a multiple of w+1. For w+1 = 2^k every index ends in k zero bits, so every sample lies below 2^{-k}: the mean of 2h-1 is -0.5, -0.75, -0.875 for worlds 1, 3, 7 instead of 0. The OU filter turns that into a steady offset of about \sigma\sqrt{2/(1-\rho)} times that mean (with \sigma = 0.01 and \rho = e^{-0.05}, about 0.06 × 0.5 for world 1). Other actuators use bases 3, 4, 5, ... with the same effect for their own factors. For a benchmark this only means the worlds are not statistically identical, which is harmless; just do not read a testspeed run as an unbiased random sample of controls.

    The ncon/world column is computed the way testspeed computes ncon_mean, max(nacon, ncollision) / nworld, so the default row matches the 10.85 of Example 25.2 (same model, nworld and steps). Here d.ncollision (broadphase candidate pairs) outnumbers the contacts, so the column measures candidates, not contacts; d.nacon alone would be about 4.6 per world.

    Three facts from this run. First, --function accepts 34 names, and fwd_position, collision and fwd_acceleration are not among them, because the rule in testspeed._FUNCS is an exact match of the parameter names and those functions have an extra optional parameter. render qualifies through (m, d, rc); testspeed then builds a render context from the render flags and times refit_bvh plus render. Second, without noise every world ends bit-identical to world 0 (max|q_w - q_0| = 0): a benchmark of copies. Third, forward leaves d.time at 0: the same state is timed 50 times, which is fine for profiling one state but says nothing about a rollout.

    Pitfall: comparing testspeed with your own loop

    Your training loop applies your own ctrl; testspeed applies keyframe ctrl plus noise. If the two numbers differ, first rerun testspeed with --noise_std 0 (and the same nworld, sizes and overrides). Only then is the difference about the code path. Note also that the noise kernel only runs when there is a ctrl trajectory: a model with no keyframe and no --replay is simulated with ctrl = 0 whatever the noise flags say.

    Overrides: one flag per knob

    -o (--override, repeatable) takes "opt.field=value" strings parsed by io.override_model. Enum fields accept names and | combinations, and a leading ~ clears bits from the current value, as in -o "opt.warn_overflow=~ITERATIONS|~LS_ITERATIONS" (used by the Unitree G1 benchmarks). opt.deterministic also takes true/false. Two removed fields raise: opt.ls_parallel and opt.ls_parallel_min_step ("removed in MuJoCo Warp 3.9.1"). testspeed applies the overrides twice: to the MjModel in load_model (fields that exist only on mjw.Model, such as opt.broadphase, are skipped there) and to the mjw.Model after put_model.

    One trap when comparing solver settings: with the default --overflow_behavior error, testspeed checks d.overflow against the model's warn_overflow after every step and calls sys.exit(1) on any set bit. The solver sets the ITERATIONS bit whenever a world stops at the cap, so by default testspeed refuses unconverged settings such as CG at 10 iterations on the humanoid. The GPU branch of Example 25.4 adds -o "opt.warn_overflow=~ITERATIONS|~LS_ITERATIONS" to every row (the mask is read after the overrides are applied), so buffer overflows still abort while iteration caps only show up in its overflow column; a row that still aborts prints testspeed's "Simulation aborted" lines.

    Read the columns that do not depend on the device first. CG needed its full 10 iterations and set the ITERATIONS overflow bit (the solver stopped before reaching the tolerance), while Newton converged in under 2. iterations=5 changed nothing because Newton never needed more than 5: lowering a cap above the converged count saves no work. The elliptic cone produced fewer rows (22 vs 30 per world): 6 fewer contact rows, because each condim-3 contact needs condim = 3 rows instead of the pyramidal 2(condim-1) = 4 (the humanoid's geoms have condim 1 or 3, and both runs had 6 contacts per world), and 2 fewer joint-limit rows, because the trajectory differs. Which of these is fastest on your GPU is what the GPU branch of the example measures.

    5Control trajectories and --replay

    A benchmark of a manipulation task should replay the task's controls, not noise around a pose. Three helpers in _src/io.py private API handle control trajectories:

    • find_keys(mjm, prefix) returns the ids of keyframes whose names start with prefix.
    • make_trajectory(mjm, keys) builds an (nstep, nu) array by linear interpolation of the keyframes' ctrl at their time, one row per timestep. It raises ValueError("first keyframe must have time 0.0") and ValueError("keyframes must be in time order").
    • load_trajectory(npz_path, mjm, mjd) reads an NPZ with ctrl (nstep, nu) and times (one per control, or one more as interval boundaries), validates shapes, finiteness and strictly increasing times, sets mjd.qpos/mjd.qvel from optional qpos/qvel arrays, and resamples on the model timestep with a zero-order hold.

    --replay file.npz feeds the result of load_trajectory to the noise kernel as the center of every step and sets --nstep to its length unless you pass one. The repository ships three such files: benchmarks/aloha/lift_pot.npz, benchmarks/franka_threading/threading.npz and benchmarks/sharpa_wave/grasp_mug.npz (plus lift_cloth.npz, pick_clutter.npz and the Unitree G1's shuffle_dance.npz).

    Two details of make_trajectory show in the output. Each keyframe's ctrl is appended once at its time and the next segment starts again from that value, so key values appear twice (0, 0 and 4, 4). And time is accumulated by repeated += timestep, so float rounding can add one sample at the end (12 rows for 0.1 s at 0.01 s, the last -2 twice). Neither matters for a benchmark; both matter if you assert on the length.

    An exact replay needs two flags

    --noise_std 0 removes the random term but not the filter u = ρu + (1-ρ)c. To apply the trajectory as recorded, also make ρ vanish with a tiny rate. That is what the franka_threading benchmark does: "noise_std": 0.0, "noise_rate": 1e-6.

    Adding your own benchmark

    Make benchmarks/my_robot/__init__.py with BENCHMARKS = [{"name": "my_robot", "mjcf": "scene.xml", "nworld": 8192, "nconmax": ..., "njmax": ...}], put the MJCF (and an .npz replay for a dynamic task) next to it, and run uv run python3 benchmarks/run.py -f my_robot. Choose nconmax/njmax with the recipe of §7 and check zero overflow first.

    7Sizing buffers and memory for throughput

    Every MJWarp buffer is allocated once by make_data/put_data. Undersized buffers drop contacts or rows (wrong physics, Ch 9 §7); oversized buffers cost memory and time, because many kernels launch over the capacity (naconmax, njmax) and exit early on empty slots (Ch 9 §9). The defaults are a heuristic: io._default_nconmax and _default_njmax pick a size from a ladder 16, 24, 32, 48, ... 8192 using nv, heightfields, flexes and SDF geoms, and their docstrings say they "may need to be manually raised if MJWarp reports ncon overflow, or lowered in order to get the very best performance". The recipe is to measure.

    mjwarp-testspeed --measure_alloc splits the rollout into --num_buckets (10) groups of steps and prints, per bucket, the mean, std, min and max of nacon (over all worlds) and nefc (worst world). Pick the budgets from the high percentiles plus headroom, rerun, and confirm zero overflow. testspeed prints only these bucket summaries, not per-step values, so on a GPU Example 25.6 applies pick_budget to the bucket max column (an upper bound on the p95 rule) and then reruns testspeed with the default and the picked --nconmax/--njmax to compare steps/s. On CPU it does the same by hand on box_stack(5), with a slightly different start in every world.

    The stack settles at 20 contacts and 80 rows per world (4 pyramidal rows per contact). The default njmax = 64 is too small: the NEFC bit is set from the first steps and 16 rows per world are silently dropped. pick_budget gives nconmax = 32 and njmax = 104. All three runs move the top box about the same in 0.5 s, so the damage of the dropped rows is not visible yet; Example 25.8 shows what it does to a taller stack. The steps/s column is CPU timing noise.

    Memory versus nworld

    testspeed --memory lists Model and Data memory by field (the sum of every wp.array's capacity), the fields above 1% of the total, and "other" memory (the drop in free_memory not explained by the two). Example 25.7 computes the same sums.

    Data is a straight line through the origin: 39,396 bytes per humanoid world at nconmax 24, njmax 64, so 8192 worlds need about 308 MiB, and the Model (49 KiB) is shared. The constraint arrays scale with njmax (and efc.J with njmax × nv when dense), so njmax = 256 multiplies the per-world size by 1.88. Memory is rarely the throughput limit for small robots, but it is what stops you from raising nworld for cloth, clutter and large njmax.

    8A tuning checklist, and a worked study

    Tuning is a loop: measure, change one knob, check that the physics did not change, measure again. The board collects the knobs from Parts II-VI in roughly the order that pays off. Tick the ones you have checked for your scene (the ticks stay in this browser only).

    Example 25.8 applies the first knobs to box_stack(8), one row per change, with a correctness probe: the mean height of the top box after 60 steps. A settled stack keeps it near 1.5 m; a row that moves it, or sets an overflow bit, is not a speed-up, whatever its steps/s says.

    What the study shows does not depend on the device. With the default njmax = 64 the 8-box stack needs about 128 rows (the sized row's count), so half of the contact rows are dropped every step and the tower collapses: the top box falls from 1.50 m to 1.08 m in 0.3 s. Everything after row 1 is only meaningful because row 2 fixed the sizes. Lowering iterations and ls_iterations leaves the probe unchanged here because Newton converges in one iteration on this resting stack; sap_tile and deterministic also leave it unchanged. Row 6 goes too far: CG with 3 iterations stops before converging (ITERATIONS) and the boxes drift upward. On your GPU, the notebook's graph replay ranks rows 2-5; keep the fastest one that stays valid.

    Pitfalls that make tuning results lie

    • Comparing runs at different nworld, or with and without graphs.
    • Comparing testspeed (keyframe ctrl + noise) with your own loop (your ctrl, no noise).
    • Changing m.opt.warn_overflow, iterations, ls_iterations, solver, cone or broadphase after the first launch or after capture: some are wp.static constants (a recompile) and all are baked into a captured graph (recapture, Ch 24).
    • Timing the first call (JIT), or a rollout so short that noise dominates.
    • Accepting a faster row that overflows or changes the result.

    9Check yourself

    Quiz

    testspeed reports "Total time per step: 400.00 ns" at --nworld 8192. About how long does one replay of the step take?

    ns per world-step is 1e9 * runtime / (nworld * nstep), so one call takes 8192 × 400 ns ≈ 3.3 ms.

    You compare your own rollout loop (no noise) with mjwarp-testspeed on the same humanoid. Which flag makes the comparison fair?

    By default testspeed perturbs ctrl with OU noise (std 0.01, rate 0.1 s) around the keyframe ctrl, so every world visits different states (more or fewer contacts, other solver work).

    Which of these can you pass to --function in the 4.0.1 wheel?

    testspeed._FUNCS keeps the public functions whose parameter names are exactly {m, d} or {m, d, rc}; forward, step and render qualify.

    You replay a recorded trajectory with --replay traj.npz --noise_std 0 and nothing else. What ctrl does the simulation see?

    With the default noise_rate 0.1, \rho = e^{-\Delta t/0.1} is close to 1 and ctrl follows the trajectory slowly. Add --noise_rate 1e-6, as franka_threading does.

    A GPU trace of mjw.step shows solve but no _solver_iteration, although that function carries @event_scope. Why?

    event_scope walks inspect.stack() and skips recording when a caller is capture_while or capture_if; events cannot be recorded inside conditional graph bodies. The iterations' time is inside solve.

    What does ncon_mean in testspeed's JSON measure?

    The callback appends np.max([d.nacon.numpy()[0], d.ncollision.numpy()[0]]) every step; the JSON divides the mean by nworld. With many broadphase candidates it reflects ncollision, not contacts.

    A tuned setting gives 30% more steps/s, sets the ITERATIONS bit and the top box of a stack drifts upward. What do you conclude?

    A speed-up only counts when the physics is unchanged: zero overflow and an unchanged correctness probe (row 6 of Example 25.8).

    def pick_budget(maxima, headroom=1.25, multiple=8):
    p95 = float(np.percentile(maxima, 95))
    return int(np.ceil(p95 * headroom / multiple) * multiple)

    The 95th percentile of NEFC is 80 (the stack has settled for 92 of the 100 steps); 80 × 1.25 = 100 rounds up to 104.     Show solution 
    def parse_testspeed(json_text, nworld):
    m = json.loads(json_text.strip().splitlines()[-1])   # testspeed prints one JSON line
    sps = m["steps_per_second"]

    def children(prefix):
        depth = prefix.count(".") + 1
        return {k[len(prefix) + 1:]: v for k, v in m.items()
                if k.startswith(prefix + ".") and k.count(".") == depth}

    return {"sps": sps, "ns_per_world_step": 1e9 / sps, "ok": m["converged_worlds"] == nworld,
            "children": children}

    Trace keys are the tree flattened with dots (_flatten_trace); a scope called several times per step gets an index suffix (name[0], name[1]), which this simple parser keeps as part of the name.

    11Summary

    Key takeaways

    • Report world-steps/s or ns per world-step, measured after warm-up, on a captured graph, between two wp.synchronize()-bounded clock reads, at a stated nworld, with zero overflow.
    • m.block_dim sets the block width of tiled launches (experimental); grid-stride launches are sized from CUDA occupancy; on CPU every block is 1 thread.
    • EventTracer(enabled=ON_GPU) around a capture, trace() after each replay, divide by nstep × nworld: that is testspeed's per-stage report. Scopes inside capture_while do not appear.
    • mjwarp-testspeed is GPU only; its defaults (nworld 8192, OU ctrl noise around the keyframe, --function step, abort on overflow) are part of every number it prints. Use --noise_std 0 to compare with your loop, and --noise_rate 1e-6 as well for exact replays.
    • find_keys/make_trajectory build ctrl trajectories from keyframes; load_trajectory holds an NPZ log on the timestep; --replay uses it as the noise center.
    • The benchmark suite is BENCHMARKS dicts turned into testspeed flags; sweep.py and a systemd timer append one JSON line per benchmark and commit to gh-pages every night.
    • Size nconmax/njmax from measured percentiles plus headroom; Data memory is linear in nworld and its slope grows with njmax.
    • Tune one knob at a time and reject any faster row that overflows or changes a correctness probe.

    Stuck? See Troubleshooting or the course map.
