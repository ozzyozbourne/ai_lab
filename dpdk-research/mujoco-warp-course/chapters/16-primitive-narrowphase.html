    Part IV · Chapter 16

    Collision II: Geom Types and Primitive Colliders

    The broadphase hands over a list of geom pairs that might touch. This chapter follows one of those pairs all the way to a contact: which code path the pair's two geom types pick, how a single fused kernel serves every primitive pair in every world, how write_contact decides whether a contact exists and what material it has, and the closed-form geometry behind each primitive collider, up to box-box separating axes and face clipping.

    Advanced About 90 min· Prerequisites: Ch 15 (and through it Ch 9, Ch 11)

    You will learn

    • Read MJ_COLLISION_TABLE and predict PRIMITIVE, CONVEX or no collision for any geom-type pair, including box-box with NATIVECCD disabled.
    • Explain the real dispatch: one fused primitive kernel over pool slots whose static if-chain holds only the pair types the model has, versus one kernel per convex pair type (grid-stride for non-heightfield pairs).
    • Predict what write_contact keeps (strict <, margin, gap, adhesion) and how two geoms' materials mix.
    • Derive plane-sphere, capsule-capsule, plane-box, sphere-box and box-box (SAT + clipping) and check them against MJWarp and MuJoCo C.
    • Drive a conveyor belt with surface velocity and call MJWarp's pure colliders from your own Warp kernel.

    Before you start: recap

    • All worlds share one contact pool of d.naconmax slots; d.nacon is an atomic counter that can run past capacity (Ch 9 §2).
    • The contact normal frame[0] points from geom[0] to geom[1], and geom[0] is the geom with the lower GeomType (Ch 9 §3).
    • The broadphase writes candidate pairs into collision_pair / collision_pairid / collision_worldid with the count in d.ncollision (Ch 15 §2).
    • 32 lanes run in lockstep; branches serialize; contiguous reads coalesce (Ch 4 §4).
    • Every batched m.geom_* field is read with worldid % shape[0], so friction, margins and surface velocity can differ per world (Ch 10 §10).

    1Geom types and the dispatch table

    A geom has one of a handful of shapes. MJWarp names them in types.py::GeomType, with the same integer values as MuJoCo's mjtGeom: PLANE 0, HFIELD 1, SPHERE 2, CAPSULE 3, ELLIPSOID 4, CYLINDER 5, BOX 6, MESH 7, SDF 8 and FLEX 105, plus a Warp-only TRIANGLE = 999 used internally for mesh and flex triangles. A candidate pair from the broadphase is just two geom ids; the first thing the narrowphase does is look at their two types and choose an algorithm.

    The choice is a lookup in collision_driver.py::MJ_COLLISION_TABLE, the counterpart of MuJoCo C's mjCOLLISIONFUNC table. It is a Python dict keyed by an ordered pair (type1, type2) with type1 <= type2, and each value is a CollisionType:

    • PRIMITIVE: a closed-form primitive collider in collision_primitive.py. Twelve cells by default.
    • CONVEX: the general convex path (GJK, EPA and multi-contact, Ch 17), or the heightfield prism path for anything touching an HFIELD (Ch 18).
    • no entry: the pair never collides. Three cells: plane-plane, plane-hfield and hfield-hfield. Static geometry does not need to collide with static geometry.

    The widget below is generated from the library's own dicts by Example 16.1, not typed by hand. Toggle NATIVECCD to see the only cell that a flag can flip, and add the flex row from MJ_FLEX_COLLISION_TABLE.

    Three patterns make the table easy to remember:

    1. The plane row is all primitive. A plane against any convex shape needs only the shape's deepest point(s) along -n: one point for a sphere or ellipsoid, the two end spheres of a capsule, up to 8 corners of a box, up to 4 candidates for a cylinder and up to 4 hull vertices for a mesh.
    2. Spheres and capsules are segments with a radius. Sphere-sphere, sphere-capsule and capsule-capsule all reduce to "closest points between two segments, then subtract the radii". Sphere-box, capsule-box and sphere-cylinder have their own closed forms.
    3. Everything involving an ellipsoid (except the plane), a mesh (except the plane) or a heightfield is convex, and so are capsule-cylinder, cylinder-cylinder and cylinder-box. Those shapes have no compact closed form, so MJWarp uses support functions instead (Ch 17).

    Where SDF and flex go

    SDF geoms are not in MJ_COLLISION_TABLE at all. When m.has_sdf_geom is set, _narrowphase also runs collision_sdf.py::sdf_narrowphase (Ch 18). Flex (soft body) contacts are generated after the rigid narrowphase by collision_flex.py::flex_collision, which uses MJ_FLEX_COLLISION_TABLE: plane, sphere, capsule, box and cylinder against flex are primitive (triangle colliders such as sphere_triangle, box_triangle, capsule_triangle), mesh and ellipsoid are convex, and heightfield has no entry (Ch 23).

    Version note: (CYLINDER, FLEX)

    In the 4.0.1 wheel, (CYLINDER, FLEX) is PRIMITIVE and collision_primitive_core.py::cylinder_triangle exists. In the dev tree at 8f5b9f1 that cell is CONVEX and cylinder_triangle is gone. The rigid table and the _PRIMITIVE_COLLISIONS map are identical in both.

    2Pair ordering and the normal

    The table only has cells with type1 <= type2. The broadphase guarantees that order before any narrowphase code runs: collision_driver.py::_add_geom_pair reserves a candidate slot and stores (geom2, geom1) instead of (geom1, geom2) when type1 > type2. So every collider can assume its first argument is the lower type: plane_sphere_wrapper(plane, sphere, ...), sphere_box_wrapper(sphere, box, ...), and so on. A collider for (BOX, SPHERE) never has to exist.

    Recall from Ch 9

    The contact normal frame[0] points from geom[0] to geom[1]: pushing geom[1] along +normal separates the pair (Ch 9 §3). The swap is why geom[0] is the lower type and not the first geom in the XML.

    When both geoms have the same type (sphere-sphere, capsule-capsule, box-box), _add_geom_pair does not swap (it swaps only when type1 > type2), so the order is whatever the broadphase produced. With the NXN broadphase (the default for small models) that is geom-id order, and the normal points from the lower id to the higher id. With SAP (which put_model picks when the filtered pair count is at least 250,000) the two geoms come from the sweep sort (sort_index_in[worldid, i]), so the order is not guaranteed and can differ between worlds and steps. Code should read contact.geom rather than assume the lower id comes first.

    3From a candidate pair to two Geom structs

    A collider never reads Model or Data directly. The narrowphase kernel first packs each geom into a collision_core.py::Geom, a @wp.struct, with geom_collision_pair(...) (which calls geom_collision_pair_from_types). This is where batching happens: the pose comes from the world's row, the size from worldid % geom_size.shape[0], and the mesh tables from worldid % geom_dataid.shape[0].

    Next to the geometry, each thread also resolves the pair's contact parameters with collision_core.py::contact_params: margin and gap (contact_margin_gap) and the mixed material (contact_material_params). Sections 5 and 6 take those apart.

    4How the narrowphase is launched

    Here is the whole narrowphase driver in the 4.0.1 wheel. It splits the table into a list of convex pair types and a list of primitive pair types, then calls the two paths. Note the order: convex first, then primitive, then SDF.

    # collision_driver.py::_narrowphase (mujoco-warp 4.0.1)
def _narrowphase(m: Model, d: Data, ctx: CollisionContext):
  collision_table = MJ_COLLISION_TABLE
  if m.opt.disableflags & DisableBit.NATIVECCD:
    collision_table = collision_table.copy()
    collision_table[(GeomType.BOX, GeomType.BOX)] = CollisionType.PRIMITIVE

  convex_pairs = [key for key, value in collision_table.items() if value == CollisionType.CONVEX]
  primitive_pairs = [key for key, value in collision_table.items() if value == CollisionType.PRIMITIVE]

  # TODO(team): we should reject far-away contacts in the narrowphase instead of constraint
  #             partitioning because we can move some pressure of the atomics
  convex_narrowphase(m, d, ctx, convex_pairs)
  primitive_narrowphase(m, d, ctx, primitive_pairs)

  if m.has_sdf_geom:
    sdf_narrowphase(m, d, ctx)

    4.1 The primitive path: one fused kernel

    collision_primitive.py::primitive_narrowphase does not launch one kernel per pair type. It walks _PRIMITIVE_COLLISIONS (the 13 wrapper functions), keeps those whose type pair is in the table and occurs in this model, and builds one kernel from that list:

    # collision_primitive.py::primitive_narrowphase (4.0.1), abridged
primitive_collision_types = []
primitive_collision_func = []
for types, func in _PRIMITIVE_COLLISIONS.items():
  if types not in collision_table:
    continue
  idx = upper_trid_index(len(GeomType), types[0].value, types[1].value)
  if m.geom_pair_type_count[idx]:
    primitive_collision_types.append(types)
    primitive_collision_func.append(func)

wp.launch(
  _primitive_narrowphase(primitive_collision_types, primitive_collision_func),
  dim=d.naconmax,
  ...

    m.geom_pair_type_count is a tuple built by io.py::put_model: for every type pair (upper-triangular index including the diagonal, math.py::upper_trid_index) it counts how many pairs survive the static pre-filter of Ch 15. A type pair with count 0 cannot produce a candidate, so its branch is left out of the kernel. Inside the kernel, one thread per pool slot does this:

    # collision_primitive.py::_primitive_narrowphase (4.0.1), kernel body abridged
tid = wp.tid()
if tid >= ncollision_in[0]:            # threads past the candidate count do nothing
  return
geoms = collision_pair_in[tid]
worldid = collision_worldid_in[tid]
_, margin, gap, condim, friction, solref, solreffriction, solimp, adhesion = contact_params(...)
geom1, geom2 = geom_collision_pair(...)

for i in range(wp.static(len(primitive_collisions_func))):   # unrolled at compile time
  collision_type1 = wp.static(primitive_collisions_types[i][0])
  collision_type2 = wp.static(primitive_collisions_types[i][1])
  type1 = geom_type[geoms[0]]
  type2 = geom_type[geoms[1]]
  if collision_type1 == type1 and collision_type2 == type2:
    wp.static(primitive_collisions_func[i])(naconmax_in, geom1, geom2, worldid, margin, gap, ...)

    Because the loop bound and the types are wp.static, Warp unrolls it at code-generation time into a plain chain of ifs, one per present pair type, each calling one wrapper function that the compiler can inline. Every thread evaluates the chain and takes at most one branch: the one matching its own candidate's types. A candidate whose type pair is convex (cylinder-box below) matches no branch and the thread simply ends; the convex kernel handles it.

    4.2 The convex path: one kernel per present pair type

    collision_convex.py::convex_narrowphase is the opposite design. It returns early if no convex pair type occurs, then, for each convex pair type with a nonzero count, builds a specialized kernel and launches it. Non-heightfield pairs use ccd_kernel_builder(g1, g2, ...), a grid-stride loop over all candidates that skips the ones of other types. Heightfield pairs use ccd_hfield_kernel_builder instead, launched with dim = d.naconmax: one thread per pool slot, returning at collisionid >= ncollision, with no grid stride (Ch 18). The grid-stride loop looks like this:

    # collision_convex.py, inside ccd_kernel_builder's kernel (4.0.1)
tid = wp.tid()
for collisionid in range(tid, wp.min(ncollision_in[0], naconmax_in), grid_stride_in):
  geoms = collision_pair_in[collisionid]
  g1 = geoms[0]
  g2 = geoms[1]

  if geom_type[g1] != geomtype1 or geom_type[g2] != geomtype2:
    continue
  ...

    The launch width comes from _ccd_grid_size: on a GPU "a few device waves, capped at the contact capacity" (from wp.get_suggested_block_size), on CPU simply naconmax because "Warp forces CPU block_dim to 1". This is launch layout 4 of the shared atlas (grid-stride, T threads cover N items); Ch 17 owns it. Why separate kernels here? The source does not say. A plausible reading (ours, not the library's) is that each GJK/EPA instantiation is large and uses per-pair scratch rows, so fusing them into one kernel would make every thread carry the biggest one. Measure before you rely on it (Ch 25).

    Example 16.8 wraps wp.launch during one mjw.collision call on a scene with planes, spheres, boxes and cylinders in 2 worlds, then removes the spheres and does it again. The figure below replays exactly what it recorded.

    Read the output carefully, because it corrects a common mental model:

    • One primitive launch in both scenes, with dim = 48 = d.naconmax. Removing the spheres did not remove a launch.
    • The primitive kernel changed: Warp module 1c6ac76d versus 0ed9f8c9. The if-chain was built from a different list (four sphere branches dropped: PLANE-SPHERE, SPHERE-SPHERE, SPHERE-CYLINDER, SPHERE-BOX), so @cache_kernel produced and cached a second kernel. Its cache key is a hash of the arguments, here the two lists, plus the function's module and name (warp_util.py::cache_kernel).
    • The convex launch is identical (same module) because the CYLINDER-BOX pair is present in both scenes.
    • geom_pair_type_count lists SPHERE-SPHERE and SPHERE-CYLINDER in scene A, yet no thread takes those branches: the counts are a static upper bound; the broadphase found no such candidates this step. The branches are compiled in anyway.
    • Threads 3 and 8 hold CYLINDER-BOX candidates. In the primitive kernel no branch matches, so they finish immediately.

    Recall from Ch 4 §4.4

    As Ch 4 §4.4 put it, the convex narrowphase launches one kernel per pair type present in the model, while the primitive narrowphase is a single kernel with a short if-chain that wp.static prunes to the pair types present. Neighbouring lanes in a warp often hold different pair types, so they diverge, and the warp runs each taken branch in turn. The library's own reason for fusing, in the primitive_narrowphase docstring, is "avoiding unnecessary checks for non-existent collision pairs". A plausible further reading (ours) is that one launch saves a pass over the candidate list per pair type. Branch cost varies a lot: plane_sphere is a few lines, while capsule_box and box_box are each over 300 source lines, so do not assume divergence is cheap; measure it (Ch 25).

    Recompiles you can predict

    Anything that changes the branch list compiles a new primitive kernel the first time it is used: a model with a different set of geom types, a changed contype/conaffinity that empties a type pair, or toggling NATIVECCD (box-box moves between the lists). Changing geom sizes, poses, friction or margins does not: those are runtime array reads.

    5write_contact: detected, active, margin and gap

    Every primitive collider computes candidate contacts and hands each one to collision_core.py::write_contact, together with an index id_ (the i-th contact of this pair, stored as contact.geomcollisionid). The function makes three decisions:

    # collision_core.py::write_contact (4.0.1), abridged
active = (dist_in < margin_in) or ((adhesion_in != 0.0) and (dist_in < margin_in + gap_in))
detected = dist_in < margin_in + gap_in
condim = wp.where((adhesion_in != 0.0) and (dist_in >= margin_in), 1, condim_in)

# skip contact and no collision sensor
if (pairid_in[0] == -2 or not detected) and pairid_in[1] == -1:
  return 0

contact_type = 0
if pairid_in[0] >= -1 and detected:
  contact_type |= ContactType.CONSTRAINT
if pairid_in[1] >= 0:
  contact_type |= ContactType.SENSOR

cid = wp.atomic_add(nacon_out, 0, 1)
if cid < naconmax_in:
  contact_dist_out[cid] = dist_in
  ...
  contact_includemargin_out[cid] = margin_in
  contact_dim_out[cid] = condim
  contact_geomcollisionid_out[cid] = id_
  for i in range(contact_efc_address_out.shape[1]):
    contact_efc_address_out[cid, i] = -1
  return int(active)
return 0
    • Detected (dist < margin + gap, strict): the contact takes a slot in the pool. The margin and gap of the pair are the sums of the two geoms' values (contact_margin_gap), or the explicit <pair>'s values.
    • Active (dist < margin): the contact becomes constraint rows. The kernel returns this flag, but the decision that matters is made later: constraint.make_constraint builds rows for contacts with dist < includemargin, and includemargin is the margin. In the gap band a contact exists but exerts no force, unless it is adhesive.
    • Adhesion: with nonzero adhesion, a contact in the gap band is active too, but its condim is forced to 1 (normal force only).
    • Collision sensors (pairid[1] >= 0, Ch 14): such a pair always takes a slot, detected or not. contact.type has SENSOR set, and CONSTRAINT only when the contact is detected and the pair is not sensor-only (pairid[0] >= -1). So "detected means a slot" holds only for models without collision sensors.

    The slot comes from the same atomic counter for every world and every collider, so the pool order on a GPU is arbitrary (Ch 9), and a pair that produces several contacts (a box on a plane) may have them scattered between other pairs' contacts. geomcollisionid is how you tell them apart.

    Everything agrees with MuJoCo C except the one row at exactly dist = margin + gap. That row is not a rule difference so much as a rounding difference: in float32 the sphere centre 0.15 minus the radius 0.1 comes out a hair above 0.05, and MJWarp's comparison is strict, so the contact is dropped. C computes in float64, where the same subtraction lands a hair below 0.05. Never build a test or a controller that depends on a contact sitting exactly on the boundary.

    Pitfall: "resting exactly on the floor"

    A box placed with its bottom exactly at z = 0 has corner distance 0, and 0 < 0 + 0 is false: no contact on the first step. That is harmless in a simulation (gravity closes the gap within one step), but it surprises people who call mjw.collision on a hand-placed pose. The examples below place objects 0.5 to 1 mm into their support.

    6Material mixing

    A contact needs one friction vector, one condim, one solref and one solimp, but it touches two geoms that may disagree. collision_core.py::contact_material_params resolves this much like MuJoCo C's mj_contactParam, with one difference in 4.0.1 (rule 2):

    1. An explicit <contact><pair> (pair id > -1) overrides everything: its condim, friction (all five values), solref, solreffriction, solimp and adhesion are used as given (Ch 15), except that friction is still clamped to mujoco.mjMINMU (rule 4).
    2. Otherwise, if one geom has a higher priority, its condim, friction, solimp and adhesion win (mix = 1 or 0), and so does its solref when both solrefs are standard (timeconst > 0). In 4.0.1 the solref rule runs after the priority branches, so if either solref is "direct" (negative) the element-wise minimum of the two is used even with unequal priority. MuJoCo C's mj_contactParam uses the winner's solref in that case.
    3. With equal priority: condim = max, friction = element-wise max of the two 3-vectors, adhesion = a1 + a2, and the weight \text{mix} = \dfrac{\text{solmix}_1}{\text{solmix}_1 + \text{solmix}_2} (if a solmix is below mjMINVAL: 0.5 when both are, 0 when only \text{solmix}_1 is, 1 when only \text{solmix}_2 is) blends solimp, and solref when both solrefs are standard (timeconst > 0). If either solref is "direct" (negative), the element-wise minimum is used instead.
    4. The 3-vector friction (slide, torsion, roll) expands to the 5-vector the solver uses: (slide, slide, torsion, roll, roll).
    5. Every friction entry, from an explicit pair or from mixing, is then clamped to at least mujoco.mjMINMU = 1e-5; the clamp runs after both branches.

    All reads use worldid % shape[0], so per-world friction from Ch 10 flows through these rules unchanged. The calculator implements the same function; Example 16.5 checks a NumPy copy of it against what MJWarp wrote.

    Version note

    The dev tree at 8f5b9f1 moves the solref computation inside the priority branches, so the winning geom's solref is used directly, as in MuJoCo C. That changes results in exactly one case: unequal priority with at least one direct (negative) solref. 4.0.1 (shown here, and in the calculator) gives the element-wise minimum there; the dev tree gives the winner's solref. In every other case the two agree.

    7A tour of the primitive colliders

    The code is split in two files. collision_primitive_core.py holds the pure geometry: plain @wp.func functions that take positions, rotations and sizes and return distances, positions and normals. collision_primitive.py holds one *_wrapper per table cell: it unpacks the two Geom structs, calls the core function, builds the contact frame with math.py::make_frame (or uses the one the core returns) and calls write_contact once per candidate. One convention holds everywhere: contact.pos is the midpoint between the two surfaces, and dist is negative when they overlap.

    7.1 Plane-sphere

    With plane normal n through point p, sphere centre c and radius r:

    d = (c - p)\cdot n - r, \qquad \text{pos} = c - n\,\bigl(r + \tfrac{d}{2}\bigr)

    The sphere's deepest point is c - r n and the plane point below it is c - (r + d)n; the contact sits halfway between. Drag the sphere.

    The sphere has margin="0.2", so even the world at 0.25 m reports a contact (dist 0.139 < 0.2). That is a deliberate trick for testing a collider: a large margin makes every candidate visible in d.contact. It also makes those contacts active, so do not use it in a simulation you care about.

    7.2 Sphere-sphere and sphere-capsule

    sphere_sphere(pos1, r1, pos2, r2) is the building block for everything round: the normal is (p_2 - p_1)/\lVert p_2 - p_1\rVert (or +x if the centres coincide), d = \lVert p_2 - p_1\rVert - (r_1 + r_2), and \text{pos} = p_1 + n (r_1 + d/2). sphere_capsule clamps the sphere centre's projection onto the capsule axis to [-h, h] (h = half-length) and calls sphere_sphere with the clamped point.

    7.3 Capsule-capsule: closest points between segments

    Two capsules touch where their core segments are closest. _segment_weights(a, b, c, d), a port of MuJoCo's mjc_segWeights, returns barycentric weights (s, t) of the closest points a + s(b - a) and c + t(d - c), clamped to [0, 1]. It decides "parallel" with a relative test, \lVert ab \times cd\rVert^2 \le 10^{-8}\,\lVert ab\rVert^2 \lVert cd\rVert^2 (computed with Lagrange's identity to avoid cancellation). For non-parallel segments the closest pair is unique. For parallel segments every point of the overlap is equally close, so it returns two pairs, at both ends of the overlap. capsule_capsule then runs sphere_sphere on each pair, and the wrapper writes up to 2 contacts (geomcollisionid 0 and 1). Two contacts are what keep a capsule lying on another capsule from spinning about the single touching point.

    World 1 shows the "ends of the overlap" rule: the rod spans x from 0.1 to 0.5 and the rail from -0.3 to 0.3, so the overlap is [0.1, 0.3] and the two contacts sit at its ends. The notebook adds a sweep with one world per yaw angle: only yaw 0 gives 2 contacts.

    7.4 Plane-capsule, plane-ellipsoid, plane-cylinder

    • plane_capsule is two plane_sphere calls, one per end sphere, so a lying capsule gets 2 contacts. Both share one frame whose first tangent is aligned with the capsule axis projected into the plane. In the 4.0.1 wheel, when that projection is shorter than 0.5 (the axis is within 30° of the plane normal) the frame uses a fixed hint instead, (0,1,0) or (0,0,1) depending on the normal.
    • plane_ellipsoid finds the support point along -n: transform n into the ellipsoid frame, scale by the semi-axes, normalize, scale again and transform back. One contact.
    • plane_cylinder returns 4 candidates: the rim point of the cap nearest the plane, the matching rim point of the far cap, and two more points on the near cap at \pm 120^\circ around the rim (offset r\sqrt3/2). An upright cylinder resting on its cap keeps 3 of them (the far-cap point is high above the plane), a lying cylinder keeps the two rim points along its side line.

    Version note: plane_capsule's frame

    The dev tree at 8f5b9f1 builds the tangent with a double cross product, cross(n, cross(axis, n)), and falls back to a fixed axis only when the capsule axis is almost parallel to the plane normal.

    Version note: plane_cylinder's signature

    In the 4.0.1 wheel the core function takes the cylinder's axis: plane_cylinder(plane_normal, plane_pos, cylinder_center, cylinder_axis: wp.vec3, cylinder_radius, cylinder_half_height). The dev tree at 8f5b9f1 takes its rotation matrix instead (cylinder_mat: wp.mat33). Code that calls the private core functions directly (section 10) has to follow such changes.

    7.5 Plane-box: 8 corners in, up to 4 out

    plane_box computes the signed distance of all 8 corners, numbered by bits (bit 0 = +x, bit 1 = +y, bit 2 = +z in the box frame). The wrapper calls write_contact for all 8 with id_ = i, and write_contact drops those with dist >= margin + gap. There is no sorting or "pick 4": a box face resting flat keeps exactly its 4 bottom corners because the top 4 are a box height away. Rotate the box below and watch which corners survive.

    Corners within margin, not "bottom 4"

    The core function's comment says "test all corners, pick bottom 4", but the code returns all 8 distances, and the selection is purely the margin test in write_contact. With a large margin (say 0.3 m on a 0.2 m box) all 8 corners become contacts. That is exactly why huge margins on boxes waste contact slots.

    7.6 Sphere-box, capsule-box and sphere-cylinder

    sphere_box transforms the sphere centre into the box frame and clamps it to the box: the clamped point is the closest point of the box. If it differs from the centre, the normal is the direction from the sphere centre to that point and d = \lVert\text{clamped} - c\rVert - r. If the centre is inside the box, clamping does nothing; the code then picks the nearest face and reports d = -(\text{face distance}) - r. capsule_box is the longest primitive collider (about 330 lines): it finds the box features closest to the capsule segment and can return 2 contacts, as the vertical capsule leaning on a box side does in Example 16.11. sphere_cylinder classifies the sphere centre into three regions:

    7.7 Plane-mesh: plane_convex

    The one mesh collider in the primitive path lives in collision_primitive.py itself. It works in the mesh frame:

    1. Support vertex along -n: an exhaustive scan when the mesh has fewer than 10 vertices or no graph, otherwise hill-climbing on the vertex adjacency graph (geom.graph): start at a vertex, move to any neighbour with a larger support value, stop when none is larger. For a convex hull the local maximum is the global one.
    2. If the deepest vertex is farther than margin + gap (the wrapper passes that sum as the threshold), stop: write_contact would drop everything.
    3. Incident face: among the polygons touching that vertex (mesh_polymap), pick the one whose normal is most anti-parallel to the plane normal.
    4. _hull4 prunes that polygon to at most 4 vertices of maximal area, keeping the support vertex as an anchor (MuJoCo's hull4f). Vertices above the mesh centre along the plane normal are skipped. Up to 4 contacts.
    Going deeper: the triangle colliders for flex and meshes

    collision_primitive_core.py also holds sphere_triangle, box_triangle, capsule_triangle, capsule_tetrahedron (with helpers _segment_triangle, _tet_sep_axis) and tri_weights. They are not in _PRIMITIVE_COLLISIONS; the flex collision code (collision_flex.py) calls them for each flex element against a rigid geom, which is why the flex table can list plane, sphere, capsule and box as PRIMITIVE. In the 4.0.1 wheel there is also cylinder_triangle (dev tree: removed, see the version note in section 1). Ch 23 covers flex.

    8Box-box: separating axes and clipping

    By default box-box is CONVEX: GJK/EPA finds the penetration and multi-contact clips a polygon, then keeps at most 4 points (collision_gjk.py::_polygon_quad, Ch 17). Disable NATIVECCD and the cell flips to PRIMITIVE, so box_box_wrapper calls collision_primitive_core.py::box_box, a port of MuJoCo C's mjc_BoxBox. It works in box 1's frame and has two stages:

    1. Separating-axis test over 15 candidate directions: the 3 face normals of each box and the 9 cross products of edge directions. Along each axis, the separation is the centre distance minus both projected radii. If any separation exceeds the margin, return 0 contacts. Otherwise keep the axis of maximum separation (least penetration). Face axes are preferred on near-ties (an edge axis must beat the best face axis by a small relative bias, and a winning edge axis within about 8 degrees of the best face axis is replaced by it unless it is 5 % better), because a face gives a multi-point manifold.
    2. Manifold. Edge axis: one contact at the midpoint of the closest points of the two edges. Face axis: the box owning the face is the reference; the face of the other (incident) box most opposed to the reference normal is clipped against the four side planes of the reference face (Sutherland-Hodgman, _box_box_clip). Every clipped vertex within the margin band becomes a contact, up to _BOXBOX_MAXVERT = 8 (a quad clipped by 4 half-planes has at most 8 vertices).

    The stepper walks through the 2-D analogue (4 face axes, no edge axes, and a reference edge instead of a face). Move box B with the sliders, or drag it, and the frames are recomputed.

    Two numbers explain the face preference. If a 3-D box rests flat on another, the vertical face axis has penetration 1 mm, and some edge-edge axes have almost the same separation. An edge axis gives one contact point; a face gives four or more. The solver is far more stable with four, so box_box only lets an edge axis win when it is clearly better (_BOXBOX_EDGEBIAS = 1e-6 relative, plus the 5 % / 0.99-alignment substitution rule). Rounding slack septol = margin + _BOXBOX_SEPEPS * (sum of half-sizes) keeps a barely overlapping pair from being reported as separated.

    The yawed top box makes the difference visible. Its bottom square, rotated over the bottom box's top square, clips to an octagon: 8 vertices, so the PRIMITIVE path writes 8 box-box contacts, the same count MuJoCo C reports with or without the flag. The default CONVEX path computes the same polygon and reduces it to the maximum-area quad: 4 contacts. Aligned boxes give 4 either way. override_model(m, ["opt.disableflags = nativeccd"]) mutates the mjw.Model in place and returns None; setting mjm.opt.disableflags before put_model works too.

    When to flip NATIVECCD for boxes

    Box-heavy scenes (crates, stacks, blocky robots) can use the primitive box-box: it has no GJK/EPA iterations and no CCD scratch rows (naccdmax), and it matches C's contact set. The price is up to 8 contacts per pair instead of 4, so size nconmax/njmax for it. The flag only changes box-box; every other convex pair stays on GJK/EPA. Measure on your scene (Ch 25) before deciding.

    9Surface velocity: conveyor belts

    A conveyor belt's surface moves while the geom stays put. MuJoCo models this with surface velocity: <geom surfacevel="vx vy vz wx wy wz"/> in the geom's local frame. MJWarp handles it in two places, both only when m.flg_surfacevel (some geom has a nonzero value):

    1. After the narrowphase, collision_driver.py::_contact_surfacevel (one thread per contact slot) rotates each geom's surface velocity into world coordinates, adds the angular part's contribution at the contact point (_geom_surface_velocity: v + \omega \times (\text{pos} - x_\text{geom})), forms the relative value geom[1] minus geom[0], and projects it on the contact frame: contact.surfacevel = (dot(t1, v), dot(t2, v), dot(n, ω)).
    2. In constraint.make_constraint, constraint.py::_add_surface_vel adds those values to efc.Jqvel of the friction rows (scaled by the friction coefficient for pyramidal cones). The solver then drives the relative tangential velocity at the contact toward the belt speed instead of toward zero.

    geom_surfacevel is a batched field, so one model can hold a different belt speed in every world. The replay below is real data: one world per belt speed, the box starting at rest.

    Pitfall: per-world speeds on a model with no surfacevel

    m.flg_surfacevel is a plain Python bool copied from mjm.flg_surfacevel by put_model, and both _contact_surfacevel and _add_surface_vel are skipped when it is False. If no geom in the MJCF has a nonzero surfacevel, writing per-world values into m.geom_surfacevel afterwards is silently ignored: no error, the boxes just sit still. Example 16.9 works because its XML already gives the belt surfacevel=".5 0 0 0 0 0". Two remedies: give at least one geom a nonzero surfacevel in the MJCF (so MuJoCo's compiler sets the flag), or set m.flg_surfacevel = True after put_model, as constraint_test.py does.

    The box reaches the belt speed in about 0.2 to 0.4 s and holds it (0.49999997 for the 0.5 m/s belt: float32). contact.surfacevel shows the projection at work: the box-plane frame's first tangent happens to be +y and the second -x, so a belt moving in +x appears as (0, +speed, 0): the belt (geom[0]) moves +x relative to the box, so the box moves -x relative to the belt, and dot((-1, 0, 0), (-v, 0, 0)) = +v. The sign bookkeeping is the library's job; you only set surfacevel in the belt's own frame.

    Friction does the work

    Surface velocity acts only through friction rows: a contact with condim = 1 (frictionless) ignores it (_add_surface_vel returns for dim <= 1), and a low friction coefficient makes the box slip on the belt instead of riding it.

    10Calling a core collider from your own kernel

    The core functions take plain Warp values and return plain values, so any kernel can call them. That is useful for custom sensors (distance from a gripper sphere to many targets), for proximity rewards, and for testing. The library's own collision_primitive_core_test.py does the same.

    Private API

    mujoco_warp._src.collision_primitive_core is not exported by mujoco_warp/__init__.py. Signatures can change between releases (plane_cylinder takes the cylinder axis in 4.0.1 and its rotation matrix in the dev tree, see section 7.4). Pin the version and keep a test like Example 16.10 next to code that relies on it.

    11Checking against MuJoCo C

    The primitive colliders are ports of MuJoCo's C colliders, so on the same pose they should produce the same contacts to float32 precision. Example 16.11 puts eight pair types into one scene and compares contact by contact. Contacts are matched by geom pair and then by nearest position, never by index: the pool order is not part of the contract.

    Same counts, same normal directions (C also puts the lower type first), and differences of a few times 1e-8 m: float32 rounding. Note the counts: the upright cylinder keeps 3 of its 4 plane_cylinder candidates, the lying capsule 2, the box 4. This scene is a useful regression test when you change geometry code or upgrade MJWarp. For convex pairs (Ch 17) and heightfields (Ch 18), counts can legitimately differ from C; there you compare physics outcomes instead.

    Detected (0.035 < 0.05) but not active (0.035 ≥ 0.02): Example 16.6's 0.04 row shows nefc 0.

    Show a reference solution (dist and normal)

    Verified on CPU against 16 random poses (prints sphere_box matches on 16 contacts). The pair is (SPHERE, BOX), so the normal points from the sphere to the box.

    def my_sphere_box(c, r, bpos, bmat, half):
    local = bmat.T @ (c - bpos)                       # sphere centre in the box frame
    clamped = np.clip(local, -half, half)             # closest point of the box
    v = clamped - local
    L = np.linalg.norm(v)
    if L < 1e-15:                                     # centre inside the box: nearest face
        face = np.argmin(half - np.abs(local))
        nrm = np.zeros(3); nrm[face] = -np.sign(local[face])
        return -(half[face] - abs(local[face])) - r, bmat @ nrm
    return L - r, bmat @ (v / L)                      # normal points sphere -> box

    15Summary

    Key takeaways

    • MJ_COLLISION_TABLE maps each ordered type pair to PRIMITIVE (12 cells), CONVEX (21) or nothing (plane-plane, plane-hfield, hfield-hfield). NATIVECCD disabled flips only box-box to PRIMITIVE.
    • _add_geom_pair orders every candidate by type, so geom[0] is the lower type and the normal points from it to geom[1].
    • The primitive path is one launch over pool slots (dim = d.naconmax) with a static if-chain of the pair types the model has; lanes can diverge. The convex path launches one kernel per present convex pair type (grid-stride via _ccd_grid_size, except heightfield pairs: one thread per pool slot).
    • Changing which geom types exist recompiles the fused kernel (cache_kernel key); changing sizes, poses or materials does not.
    • write_contact: detected if dist < margin + gap (strict, float32), active if dist < margin (or in the gap with adhesion, then condim 1); geomcollisionid numbers a pair's contacts.
    • Materials: explicit pair, else higher priority wins (except that in 4.0.1 a direct solref on either side gives the element-wise min), else max condim, element-wise max friction, solmix-weighted solref/solimp, summed adhesion, friction clamped to mjMINMU.
    • Colliders put pos midway between surfaces. Capsule-capsule gives 2 contacts only when parallel to within the 1e-8 test (about 0.006°); plane-box keeps every corner inside the margin; primitive box-box keeps up to 8 clipped vertices and matches C.
    • Surface velocity is a batched geom field turned into contact.surfacevel and added to friction rows' efc.Jqvel.
    • The core colliders are plain @wp.funcs you can call from your own kernels (private API).

    Next, Ch 17 opens the other half of the table: support functions, GJK, EPA and the multi-contact polygon clipping that made box-box give 4 contacts here.

    Stuck? See Troubleshooting or the course map.
