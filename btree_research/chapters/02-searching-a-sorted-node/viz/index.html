A B-tree node is a small sorted array, and every tree operation starts by searching it. The search does not answer "is the key here?". It answers "how many keys are smaller?", which is an index from 0 to n that always exists: the place where the key is, or where it would be inserted. Text and code: chapter 02 README.

1. Lower bound and upper bound, one comparison at a time

The loop keeps one promise: everything left of lo is known to be too small, everything from hi on is known to be large enough. Faded keys are ruled out; each step looks at one key (mid) and moves one of the two markers. Type your own keys and key, switch to upper bound, or tick Predict to be asked which marker moves before each decision.

2. Ranges: inclusive and exclusive ends

Each end of a key range becomes one bound call, and the result is a half-open index range [start, end). Change the brackets and watch which bound is used. Try an end that equals a stored key, and a range like (7, 7).

3. Galloping: when the answer is near a known position

If the answer is at or after a cursor and probably close to it, jump 1, 2, 4, 8, … positions until a probe is large enough, then binary search between the last two probes. The counters compare it with a binary search over the whole array. Next probe continues from the answer with a larger key, the way a sorted batch of lookups does.
