Chapter 2

Benchmarks and Metrics for LLMs

Ask “what is this model’s MMLU score?” and the honest answer is “under which protocol?”. Changing only meaning-preserving details of prompt formatting (separators, casing, spacing) moved one open model’s few-shot accuracy by up to 76 points in one study[1], and changing the order of answer choices or the rule used to pick an answer moved models up to 8 places on a leaderboard[2]. A benchmark score is the output of a measurement pipeline, not a property of the model. This chapter takes a reported number apart into its layers, computes every common metric by hand, and ends with a protocol card that lets someone else reproduce the number.

2.1What a benchmark score really is

A benchmark is a fixed set of items, each an input plus a reference answer or a checker that decides whether an output is acceptable. That is the part people name in a table header (“MMLU”, “HumanEval”). The number in the cell is produced by four more layers that usually go unnamed, and each can move it by more than the gap between the models being compared. The maintainers of EleutherAI’s widely used harness list the ways evaluation setups silently differ between papers and recommend reporting the full setup and sharing code[3].

It helps to write the score as a composition of functions. For a model M and an item set D = {(xi, yi)}:

score(M, D) = Aggregatei ∈ D [ Score( Extract( M( Prompt(xi) ) ), yi ) ]  ±  uncertainty (2.1) where Prompt is the template plus few-shot examples, M(·) includes decoding settings, Extract is the answer parser, Score is the per-item metric and Aggregate is the mean (or pass@k, or a rating model) over items.

The five layers of this score stack are:

  1. Dataset. Which items, split and version. MMLU is not one thing: there is the original 57-subject test set[4], a re-annotated subset with corrected labels (MMLU-Redux)[5] and a harder ten-option successor (MMLU-Pro)[6].
  2. Elicitation. Prompt template, few-shot examples, whether the model reasons step by step (chain-of-thought, CoT), system prompt, decoding (greedy or sampled, temperature, maximum length, number of samples), and the choice between scoring log-probabilities and generating text.
  3. Scoring. The per-item rule: exact match after normalisation, token F1, n-gram overlap, unit tests, the most likely choice, or a judge. Answer extraction (the regex that pulls “42” out of a paragraph) belongs here too.
  4. Aggregation. Mean over items, macro or micro over subjects, pass@k over samples, chance-normalised, or a rating model over pairwise preferences.
  5. Uncertainty. Standard error from a finite item sample, variance from sampled decoding, clustering of related items, and the harder-to-quantify effects of label noise and contamination.

Two consequences recur through the book. First, a score is only comparable to another computed with the same stack: 5-shot log-likelihood and zero-shot CoT numbers do not mix. Second, each layer is a design decision that should follow from what you want to measure. For user-facing behaviour, generative zero-shot CoT is closer to reality, which is why OpenAI’s reference implementations use it[7]; for a cheap, low-variance signal while pre-training a 1B model, log-likelihood scoring on a cloze formulation is better[8].

Saturation is the normal life cycle

Every accuracy-era benchmark is now near its ceiling for frontier models. A study of 60 benchmarks found nearly half saturated, with saturation growing with benchmark age, and expert curation (more than keeping test data private) associated with a long useful life[47]. Epoch’s “Rosetta Stone” work draws the consequence: to track progress over a decade you must stitch short-lived benchmarks onto a common latent scale[48], the same idea as the item-response models in Section 5.12.

So a benchmark has a useful operating range. Near chance, differences are noise; near the label-noise ceiling, they are noise plus label errors. HellaSwag was filtered so that 2019 models scored under 48% while humans scored over 95%[10]: squarely in range then, far outside it now. Choose benchmarks whose range brackets the models you are comparing.

Before a comparison, check that the expected score is inside the operating range, whether a cleaned or fresh variant exists (MMLU-Redux, SimpleQA Verified, HumanEval+, LiveCodeBench after the cutoff), and whether there are enough items (Section 2.9).

2.3Scoring generated text

Suppose the model writes free text and the benchmark has a reference answer. How similar is “The cat sat on the mat.” to “A cat was sitting on the mat”? Every answer is a reference-based metric, on a spectrum from string identity to semantic similarity. They are still harness defaults, and their failure modes show up as silent score shifts.

Normalisation and exact match

Exact match (EM) is 1 if the prediction equals the reference. Raw equality is too strict (“Paris.” ≠ “paris”), so every EM metric comes with a normalisation function that is part of the metric. The most copied is the official SQuAD v1.1 script, reproduced in Hugging Face’s evaluate[49]:

def normalize_answer(s):
    """Lower text and remove punctuation, articles and extra whitespace."""

    def remove_articles(text):
        return re.sub(r"\b(a|an|the)\b", " ", text)

    def white_space_fix(text):
        return " ".join(text.split())

    def remove_punc(text):
        exclude = set(string.punctuation)
        return "".join(ch for ch in text if ch not in exclude)

    def lower(text):
        return text.lower()

    return white_space_fix(remove_articles(remove_punc(lower(s))))


def f1_score(prediction, ground_truth):
    prediction_tokens = normalize_answer(prediction).split()
    ground_truth_tokens = normalize_answer(ground_truth).split()
    common = Counter(prediction_tokens) & Counter(ground_truth_tokens)
    num_same = sum(common.values())
    if num_same == 0:
        return 0
    precision = 1.0 * num_same / len(prediction_tokens)
    recall = 1.0 * num_same / len(ground_truth_tokens)
    f1 = (2 * precision * recall) / (precision + recall)
    return f1

From the inside out: lowercase, strip punctuation, delete a, an, the, collapse whitespace; with several references, take the maximum. It does not handle numbers (“1,200” vs “1200”), units, synonyms or word order, so numeric benchmarks add their own extraction (Section 2.10), and MATH ships a LaTeX-aware checker, is_equiv[12].

Token F1

Token F1 gives partial credit. Treat the normalised prediction and reference as bags (multisets) of tokens, and compute precision and recall of the overlap:

P = |pred ∩ gold||pred|,   R = |pred ∩ gold||gold|,   F1 = 2PRP + R (2.2) where ∩ is the multiset intersection (Counter & Counter): a token that appears twice in both counts twice.

pred = “The cat sat on the mat.” normalises to [cat, sat, on, mat]; gold = “A cat was sitting on the mat” normalises to [cat, was, sitting, on, mat]. The overlap is {cat, on, mat}, 3 tokens. P = 3/4 = 0.75, R = 3/5 = 0.60, F1 = 2(0.75)(0.60)/1.35 = 0.667, while EM = 0. Reproduced by code/ch02/text_metrics.py.

BLEU: clipped n-gram precision with a brevity penalty

BLEU, designed for machine translation in 2002[50], asks what fraction of the candidate’s n-grams (n = 1 to 4) appear in the reference. Clipping credits a candidate n-gram at most as often as it occurs in the reference, so “the the the the” does not get perfect unigram precision against “the cat”. A brevity penalty stops very short outputs from winning on precision.

BLEU = BP · exp( Σn=14 wn log pn ),    BP = 1 if c > r, else exp(1 − r/c) (2.3) where pn is the clipped n-gram precision, wn = 1/4, c is the candidate length and r the reference length. At corpus level, numerators, denominators and lengths are summed over all sentences before the geometric mean.

Because the n-gram precisions enter through a geometric mean, a single zero kills the score. That gives the classic trap:

Candidate “the cat is sitting on the mat” (7 tokens), reference “the cat sat on the mat” (6 tokens). Unigrams: the ×2 (clipped to 2), cat, on, mat match, is and sitting do not: p1 = 5/7. Bigrams: the cat, on the, the mat: p2 = 3/6. Trigrams: only on the mat: p3 = 1/5. 4-grams: none of the four match: p4 = 0/4. The candidate is longer, so BP = 1. Sentence BLEU = 0.

Now ROUGE-L for the same pair. The longest common subsequence is “the cat on the mat”, 5 tokens. Plcs = 5/7 = 0.714, Rlcs = 5/6 = 0.833, F = 0.769. Two standard metrics, one sentence pair, scores of 0 and 0.769. A near-copy (“the cat sat on the red mat today” vs “the cat sat on the mat today”) has p = 7/8, 5/7, 3/6, 2/5 and BLEU = 0.595. All three numbers are asserted by code/ch02/text_metrics.py.

Sentence-level BLEU therefore needs smoothing (small added counts so a zero precision does not collapse the product); BLEU was meant for corpus level, where some sentence almost always contributes a 4-gram match. “BLEU” is also a family: tokenisation, casing, smoothing and reference count are parameters, and Post showed common configurations differ by up to 1.8 BLEU, more than many published improvements. His sacreBLEU prints a signature recording every parameter[51].

ROUGE-N and ROUGE-L

ROUGE, designed for summarisation[52], worries about the opposite failure, missing content: ROUGE-N is n-gram recall against the reference, and ROUGE-L uses the longest common subsequence (LCS), which rewards in-order overlap without contiguity:

Rlcs = LCS(cand, ref)|ref|,   Plcs = LCS(cand, ref)|cand|,   Flcs = 2 Plcs RlcsPlcs + Rlcs (2.4) The original paper uses a β-weighted F; most libraries report the balanced F1 shown here.

BERTScore: soft matching in embedding space

n-gram metrics cannot know that “sat” and “sitting” are close. BERTScore[53] embeds every token with a contextual encoder and greedily matches each token to its most similar counterpart:

RBERT = 1|x| Σxi ∈ x maxx̂j ∈ x̂ xi⊤ x̂j,   PBERT = 1|x̂| Σx̂j ∈ x̂ maxxi ∈ x xi⊤ x̂j,   FBERT = 2PRP + R (2.5) where x is the reference, x̂ the candidate, and the token vectors are unit-normalised so the dot product is the cosine.

Scores depend on the encoder, layer, idf weighting and baseline rescaling, so the bert_score package prints a hash of its configuration[53]. Our script uses hand-made vectors with cos(sat, sitting) = 0.9 and cos(mat, rug) = 0.8.

def ngrams(tokens: list[str], n: int) -> Counter:
    return Counter(tuple(tokens[i:i + n]) for i in range(len(tokens) - n + 1))


def clipped_counts(cand: list[str], ref: list[str], n: int) -> tuple[int, int]:
    c, r = ngrams(cand, n), ngrams(ref, n)
    matched = sum(min(cnt, r[g]) for g, cnt in c.items())   # clipping
    return matched, max(sum(c.values()), 0)


def bleu(pairs: list[tuple[str, str]], max_n: int = 4, smooth: bool = False) -> tuple[float, list[float], float]:
    """Corpus BLEU over (candidate, reference) pairs; one pair = sentence BLEU.
    smooth=True adds one to numerator and denominator for n > 1 (a simple add-one smoothing)."""
    match = [0] * max_n
    total = [0] * max_n
    c_len = r_len = 0
    for cand, ref in pairs:
        ct, rt = cand.split(), ref.split()
        c_len, r_len = c_len + len(ct), r_len + len(rt)
        for n in range(1, max_n + 1):
            m, t = clipped_counts(ct, rt, n)
            match[n - 1] += m
            total[n - 1] += t
    precisions = []
    for n in range(max_n):
        m, t = match[n], total[n]
        if smooth and n > 0:
            m, t = m + 1, t + 1
        precisions.append(m / t if t else 0.0)
    bp = 1.0 if c_len > r_len else math.exp(1 - r_len / c_len)
    if min(precisions) == 0:
        return 0.0, precisions, bp
    return bp * math.exp(sum(math.log(p) for p in precisions) / max_n), precisions, bp


# ---------- ROUGE (Lin 2004) ----------
def rouge_n(cand: str, ref: str, n: int = 1) -> tuple[float, float, float]:
    m, t_c = clipped_counts(cand.split(), ref.split(), n)
    t_r = sum(ngrams(ref.split(), n).values())
    p, r = m / t_c, m / t_r
    return p, r, (2 * p * r / (p + r) if p + r else 0.0)


def lcs_len(a: list[str], b: list[str]) -> int:
    dp = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i, x in enumerate(a, 1):
        for j, y in enumerate(b, 1):
            dp[i][j] = dp[i - 1][j - 1] + 1 if x == y else max(dp[i - 1][j], dp[i][j - 1])
    return dp[-1][-1]


def rouge_l(cand: str, ref: str) -> tuple[int, float, float, float]:
    c, r = cand.split(), ref.split()
    lcs = lcs_len(c, r)
    p, rec = lcs / len(c), lcs / len(r)
    return lcs, p, rec, 2 * p * rec / (p + rec)

chrF and learned metrics

chrF is the F-score over character n-grams with β = 2 (recall weighted twice as much as precision); chrF++ adds word bigrams, and sacreBLEU implements both with signatures[54]. COMET[55] and BLEURT[56] are neural regressors trained to predict human quality judgements (COMET also reads the source sentence). The WMT22 metrics shared task, subtitled “Stop Using BLEU”, found neural metrics better correlated with humans and more robust[57]. They fail like learned models: under domain shift, on error types they barely penalise (a wrong number or name), and across checkpoints, so name the exact one (for example Unbabel/wmt22-comet-da).

BLEU and ROUGE reward surface overlap with one reference. LLM answers are long, varied and often correct in words the reference never used, so n-gram metrics mostly measure similarity to the reference author’s style. Use them for constrained outputs and as cheap regression alarms; for open-ended output use a task-specific checker, a validated judge (Chapter 4) or humans.

Verifiable instructions: IFEval’s four numbers

IFEval[30] needs no reference: each of its ~500 prompts carries one or more verifiable instructions (“fewer than 100 words”, “wrap the answer in JSON”) checked by code. Prompt-level accuracy is the share of prompts whose instructions are all followed; instruction-level accuracy is the share of individual instructions followed. Strict checks the raw response; loose also tries it with markdown * removed and with the first and/or last line dropped (forgiving “Sure, here it is:”), and passes if any variant does.

Three prompts, two instructions each. Strict results [✓,✓], [✓,✗], [✗,✗]: prompt-level 1/3 = 0.333, instruction-level 3/6 = 0.500. Response 2, “**Yes**, the meeting moved…”, fails “start with Yes” only because of the markdown, which loose removes: 2/3 and 4/6. Asserted by code/ch02/text_metrics.py.

def loose_variants(resp: str) -> list[str]:
    """IFEval 'loose' check: also try the response with markdown '*' removed and/or its first
    and/or last line dropped; an instruction counts as followed if ANY non-empty variant passes."""
    lines = resp.split("\n")
    bases = [resp, "\n".join(lines[1:]), "\n".join(lines[:-1]), "\n".join(lines[1:-1])]
    return [v for b in bases for v in (b, b.replace("*", "")) if v.strip()]


def ifeval_scores(mock, loose: bool) -> tuple[float, float, list[list[bool]]]:
    results = [[any(chk(v) for v in (loose_variants(resp) if loose else [resp])) for _, chk in instrs]
               for resp, instrs in mock]
    prompt_level = float(np.mean([all(r) for r in results]))
    instruction_level = float(np.mean([x for r in results for x in r]))
    return prompt_level, instruction_level, results

2.4Scoring with probabilities

For multiple-choice benchmarks there is a second way to get an answer, with no generation or parsing: ask the model how likely each option is and pick the most likely. This log-likelihood scoring is lm-evaluation-harness’s default for ARC, HellaSwag and MMLU-style tasks[58]. It is cheap, deterministic and works on base models that cannot follow instructions, but it has biases that the normalisation variants exist to fix.

acc, acc_norm, acc_bytes and mutual information

For each choice cj, the harness sums the log-probabilities of its tokens as a continuation of the prompt: ℓj = Σt log p(cj,t | prompt, cj,<t). Every extra token adds a negative number, so long options are penalised for being long. The decision rules correct for that differently:

acc: argmaxj ℓj    acc_norm: argmaxj ℓj / chars(cj)    acc_bytes: argmaxj ℓj / bytes(cj)    acc_mutual_info: argmaxj [ ℓj − ℓjuncond ] (2.6) where ℓjuncond is the log-likelihood of the choice with an empty context (how likely the string is a priori). A fifth variant, per-token normalisation ℓj / tokens(cj), is used by OLMES[59]; unlike per-byte it depends on the tokenizer.

Cloze versus letter formulation

A second, independent choice is what string to score. In the cloze formulation (CF) the prompt ends with “Answer:” and each option’s full text is scored. In the multiple-choice formulation (MCF) the options are listed as A–D and only the letter is scored: closer to instruction-tuned use and free of the length problem, but small base models often cannot do it, and it adds a letter bias. Madaan et al. found cloze MMLU has far lower seed variance and a more monotone learning curve during 7B-scale pre-training[8]; Alzahrani et al. found that changing the answer-selection method, choice order or symbols moves models up to 8 ranks[2].

A more radical answer is to drop the options. Chandak, Goel, Prabhu et al. show that multiple-choice questions from popular benchmarks can often be answered without seeing the question, from the choices alone[89]. Their alternative, answer matching, gives the model the question without options, takes a free-form answer, and has an LLM compare it with the reference. On human-graded MMLU-Pro and GPQA-Diamond, answer matching with recent models, even small ones, reaches agreement in the range of inter-annotator agreement, while MC scoring and reference-free LLM-as-judge align poorly with humans, and several model rankings change. The grader then needs the validation described in Chapter 4; a cheap shortcut check for any MC benchmark is a choices-only baseline with the question removed.

OLMES, AI2’s open evaluation standard, turns these findings into rules[59]. It evaluates every model in both CF and MCF and reports the better, because MCF ability appears only at larger scale or after more training. It also fixes, per task, the normalisation (none, per-character, per-token or PMI, the mutual-information rule), the prompt format and a curated 5-shot set. Chapter 9 uses it as a tool.

The letter prior has a clean fix: present each item with the options rotated and average each option’s score over its positions. A constant preference for “A” then adds the same amount to every option and cancels.

def letter_eval(rng: np.random.Generator, n: int, prior: np.ndarray) -> tuple[float, float]:
    """Letter (MCF) scoring: log p(letter) = knowledge signal for the content + a position prior.
    Returns (accuracy in the original order, accuracy after averaging over 4 cyclic rotations)."""
    plain = debiased = 0
    for _ in range(n):
        gold = int(rng.integers(4))
        content_score = rng.normal(0, 1.0, size=4)
        content_score[gold] += 1.0                         # the model weakly knows the answer
        logits = content_score + prior                     # position j shows content j
        plain += int(np.argmax(logits) == gold)
        # rotate contents through positions; average each content's score over all positions
        avg = np.zeros(4)
        for shift in range(4):
            pos_of_content = (np.arange(4) + shift) % 4
            avg += content_score + prior[pos_of_content]
        debiased += int(np.argmax(avg / 4) == gold)
    return plain / n, debiased / n

Perplexity and bits-per-byte

For language modelling itself, the metric is how surprised the model is by held-out text. Perplexity is the exponentiated mean negative log-likelihood per token:

PPL = exp( −1T Σt=1T log p(xt | x<t) ),    BPB = −Σt log p(xt | x<t)B · ln 2 (2.7) where T is the number of tokens and B the number of UTF-8 bytes of the same text.

Four tokens with probabilities 0.5, 0.25, 0.125, 0.5 have log-probabilities −0.693, −1.386, −2.079, −0.693; the mean is −1.2130, so PPL = e1.2130 = 3.364: the model is, on average, as uncertain as a uniform choice among about 3.4 tokens. If those four tokens spell 9 bytes, BPB = 4.852 / (9 × 0.693) = 0.778. Reproduced by code/ch02/mock_mc_eval.py.

Token perplexity depends on the tokenizer (bigger tokens mean fewer, harder predictions), so models with different vocabularies cannot be compared on it; bits-per-byte divides by a tokenizer-independent length and can be. lm-evaluation-harness implements these as one-line aggregations[58]:

2.5Scoring with execution: pass@k

For code there is a much better grader than string similarity: run the program. HumanEval, introduced with Codex in 2021, has 164 hand-written Python problems, each a signature and docstring plus hidden unit tests (about 7.7 per problem); a completion is correct if it passes all of them[13]. This functional correctness generalises to any domain with an automatic checker: verifiable math answers, SQL, an agent’s final environment state. With sampled models, the probability that at least one of k samples is correct is pass@k. Its estimator is derived here.

Deriving the unbiased estimator

Fix one problem. Let p be the model’s true per-sample success probability on it. If samples are independent, the true pass@k for the problem is

pass@k(p) = 1 − (1 − p)k (2.8) the probability that not all k samples fail.

We do not know p. Drawing exactly k samples and recording whether any passes is unbiased but very noisy (one Bernoulli draw per problem). The Codex paper instead draws n ≥ k samples (n = 200, k ≤ 100), counts the c that pass, and asks: if I picked k of the n uniformly without replacement, what is the probability that at least one is correct?[13] The complement is that all k picks are among the n − c failures. There are C(n − c, k) ways to choose k failures and C(n, k) ways to choose any k, so

pass@k̂ = 1 − C(n − c, k)C(n, k),    pass@k = Eproblems [ pass@k̂ ] (2.9) with pass@k̂ = 1 whenever n − c < k (you cannot pick k failures).

Why it is unbiased. Treat the n samples as an ordered i.i.d. sequence. “The first k all fail” has probability (1 − p)k. Conditional on c, every arrangement of the successes is equally likely, so the conditional probability that the first k all fail is exactly C(n − c, k)/C(n, k). Averaging over c gives back (1 − p)k, so the estimator is unbiased per problem for every p, and its mean over problems is unbiased for the benchmark. It is the Rao–Blackwellised naive estimator: same expectation, lower variance, because it averages over every way of choosing k of the n.

The numerically stable product form

C(200, 100) is about 9 × 1058, and for larger n the ratio overflows floating point. Cancelling terms gives a product that never gets large:

C(n − c, k)C(n, k) = ∏i = n−c+1n ( 1 − ki ) (2.10)

This is exactly what the reference implementation does[60]:

def estimate_pass_at_k(
    num_samples: Union[int, List[int], np.ndarray],
    num_correct: Union[List[int], np.ndarray],
    k: int
) -> np.ndarray:
    """
    Estimates pass@k of each problem and returns them in an array.
    """

    def estimator(n: int, c: int, k: int) -> float:
        """
        Calculates 1 - comb(n - c, k) / comb(n, k).
        """
        if n - c < k:
            return 1.0
        return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

n = 10, c = 3. pass@1 = 1 − C(7,1)/C(10,1) = 1 − 7/10 = 0.300 (pass@1 is always just c/n). pass@5 = 1 − C(7,5)/C(10,5) = 1 − 21/252 = 0.9167. Product form: (1 − 5/8)(1 − 5/9)(1 − 5/10) = 0.375 × 0.444 × 0.5 = 0.0833, so 1 − 0.0833 = 0.9167.

n = 200, c = 10. pass@1 = 0.050, pass@10 = 0.4085, pass@100 = 0.9992. Reproduced by code/ch02/pass_at_k.py.

Why the plug-in estimator is biased low

A tempting shortcut plugs p̂ = c/n into Equation 2.8: 1 − (1 − c/n)k. Because f(p) = 1 − (1 − p)k is concave for k > 1, Jensen’s inequality gives E[f(p̂)] ≤ f(p): the plug-in is biased low. Intuitively it resamples with replacement, so the same failure can be drawn twice.

Take p = 0.1, n = 10, k = 5. The truth is 1 − 0.95 = 0.4095. Averaging each estimator over the exact Binomial(10, 0.1) distribution of c: the unbiased estimator’s expectation is 0.4095, the plug-in’s is 0.3485, six points low. Computed exactly (not by simulation) in code/ch02/pass_at_k.py.

def pass_at_k_comb(n: int, c: int, k: int) -> float:
    """1 - C(n-c, k) / C(n, k): P(at least one of k draws without replacement passes)."""
    if n - c < k:
        return 1.0
    return 1.0 - math.comb(n - c, k) / math.comb(n, k)


def pass_at_k_prod(n: int, c: int, k: int) -> float:
    """Product form used by openai/human-eval; never forms huge binomial coefficients."""
    if n - c < k:
        return 1.0
    return 1.0 - float(np.prod(1.0 - k / np.arange(n - c + 1, n + 1)))


def plug_in(n: int, c: int, k: int) -> float:
    """Biased: treats p_hat = c/n as the truth and samples WITH replacement."""
    return 1.0 - (1.0 - c / n) ** k


def binom_pmf(n: int, c: int, p: float) -> float:
    return math.comb(n, c) * p ** c * (1 - p) ** (n - c)


def expectation(estimator, n: int, k: int, p: float) -> float:
    """Exact E[estimator] when c ~ Binomial(n, p)."""
    return sum(binom_pmf(n, c, p) * estimator(n, c, k) for c in range(n + 1))

Temperature, coverage and the verifier problem

Temperature depends on k. The Codex paper found the best temperature was T* = 0.2 for pass@1 and T* = 0.8 for pass@100[13]: one likely program versus many diverse attempts. Report the temperature per k; tuning it on the test set is mildly optimistic.

Coverage. At large k, pass@k is often called coverage, the fraction of problems solved by at least one sample; “Large Language Monkeys” found it often grows log-linearly with the number of samples over four orders of magnitude[61]. It measures what is reachable.

pass@k needs a verifier to be realised. pass@100 = 0.9 does not mean users get a correct answer 90% of the time; it means a correct sample usually exists, and something must pick it out: tests runnable at inference time, a proof checker or a learned verifier. GSM8K was introduced to study learned verifiers that rerank samples[11]; without an oracle, majority voting and reward-model reranking plateau well below coverage[61]. Report pass@1 for anything user-facing, pass@k as potential.

Weak tests inflate pass@k. EvalPlus extended HumanEval’s tests 80× with LLM- and mutation-generated inputs (HumanEval+, and MBPP+ for MBPP); across 26 LLMs pass@k fell by up to 19.3–28.9%, and rankings changed: WizardCoder-CodeLlama and Phind-CodeLlama beat ChatGPT on HumanEval+ but not on HumanEval[37]. Read the drop as the test suite’s false-positive rate. Our buggy mean() passes three base tests and crashes on an added empty list. Once such a checker becomes an RL reward, the policy is paid to find its holes: reward hacking, Chapter 7.

The opposite question. For an agent serving many users you often care whether it succeeds every time. That metric, pass^k, estimated as C(c, k)/C(n, k), falls with k: with n = 10 and c = 3, pass^1 = 0.300 but pass^2 = 3/45 = 0.067. See Chapter 5 and Chapter 6.

2.6Calibration and abstention

A model that is right 70% of the time is more useful if you know which 70%. Calibration asks whether stated or implied confidence matches empirical accuracy: among answers given with 80% confidence, are 80% correct? HELM made calibration a core metric[15], and HLE reports frontier models poorly calibrated on it[23]. Guo et al. showed that modern deep networks are systematically over-confident and popularised the standard metric and fix[65].

ECE, MCE and the Brier score

Group predictions into M confidence bins Bm. In each bin compare mean confidence with accuracy. The expected calibration error is the weighted average gap; the maximum calibration error is the worst bin:

ECE = Σm=1M |Bm|N · | acc(Bm) − conf(Bm) |,    MCE = maxm | acc(Bm) − conf(Bm) |,    Brier = 1N Σi (pi − yi)2 (2.11) where yi ∈ {0, 1} is correctness and pi the confidence. For K classes the Brier score sums squared errors over all classes; lm-evaluation-harness computes it over the softmax of the choice log-likelihoods.

HLE’s calibration error

Humanity’s Last Exam reports a different binned statistic. Its system prompt asks the model to end with “Confidence: {your confidence score between 0% and 100% for your answer}”, so the confidence is verbalised, not a token probability; the judge extracts it (and puts 100 if none is given)[90]. Predictions are sorted by stated confidence and cut into equal-mass bins of β items (β = 100 in HLE, the final bin absorbing the remainder), and the error is a root-mean-square rather than a mean absolute gap:

    correct = correct[idxs]
    bins = [[i * beta, (i + 1) * beta] for i in range(len(confidence) // beta)]
    bins[-1] = [bins[-1][0], len(confidence)]

    total_examples = len(confidence)
    for i in range(len(bins) - 1):
        bin_confidence = confidence[bins[i][0]:bins[i][1]]
        bin_correct = correct[bins[i][0]:bins[i][1]]
        num_examples_in_bin = len(bin_confidence)

        if num_examples_in_bin > 0:
            difference = np.abs(np.nanmean(bin_confidence) - np.nanmean(bin_correct))

            if p == '2':
                cerr += num_examples_in_bin / total_examples * np.square(difference)
            elif p == '1':
                cerr += num_examples_in_bin / total_examples * difference
            elif p == 'infty' or p == 'infinity' or p == 'max':
                cerr = np.maximum(cerr, difference)
            else:

...

Two details are easy to miss. The loop for i in range(len(bins) - 1) never visits the last bin, which after sorting is the highest-confidence block (the remainder included), although its items still count in total_examples; and the value is rounded to two decimals before being multiplied by 100, so HLE calibration errors move in whole points. rms_calibration_error() in code/ch02/calibration.py reproduces the function: on the ten-prediction example with β = 2 it gives 0.2525 with the last bin skipped (reported as 25) and 0.3160 with every bin counted, a gap entirely due to the over-confident top bin (0.90 and 0.95, one of two correct). Compare HLE numbers only with other HLE numbers computed by the same code.

A reliability diagram plots accuracy against mean confidence per bin; over-confidence shows as points below the diagonal. Temperature scaling[65] divides all logits by one scalar T fitted on held-out data by minimising negative log-likelihood. It never changes the argmax, so accuracy is unchanged.

def bins_equal_width(conf: np.ndarray, m: int) -> list[np.ndarray]:
    edges = np.linspace(0, 1, m + 1)
    # right-closed bins (lo, hi]; confidence 0 goes in the first bin
    idx = np.clip(np.searchsorted(edges, conf, side="left") - 1, 0, m - 1)
    return [np.where(idx == b)[0] for b in range(m)]

    order = np.argsort(conf, kind="stable")
    return [chunk for chunk in np.array_split(order, m)]

def ece_mce(conf, correct, bins) -> tuple[float, float]:

    gaps = [abs(acc - c) for _, c, acc in rows]
    return sum(cnt / n * g for (cnt, _, _), g in zip(rows, gaps)), max(gaps)

Abstention: SimpleQA’s three-way grading

Calibration’s behavioural cousin is declining to answer when unsure. SimpleQA, short fact-seeking questions collected adversarially against GPT-4, grades every response correct, incorrect or not attempted[39], so “I don’t know” is not lumped with hallucination. The reference code[7] computes

aggregate_metrics["is_given_attempted"] = aggregate_metrics["is_correct"] + aggregate_metrics["is_incorrect"]
# Calculate accuracy_given_attempted
aggregate_metrics["accuracy_given_attempted"] = (
    aggregate_metrics["is_correct"]
    / aggregate_metrics["is_given_attempted"]
    if aggregate_metrics["is_given_attempted"] > 0
    else 0
)

and the F-score is the harmonic mean of overall accuracy and accuracy-given-attempted. A model that always answers (45 correct, 55 wrong) gets F = 0.450; one that abstains on 25 (40 correct, 35 wrong) gets 0.457. Report all three counts, not only F.

Scoring that rewards abstention

Under 0/1 grading, guessing always beats abstaining. Kalai et al. argue that this is a main reason hallucinations persist, and propose stating a confidence target t in the instructions: +1 for a correct answer, −t/(1 − t) for a wrong one, 0 for “I don’t know”[69]. Answering then pays only when the model’s probability of being right exceeds t, and t = 0 is ordinary accuracy.

Score = (#correct − t/(1 − t)·#wrong)/N. At t = 0: 0.45 vs 0.40, the guesser wins. At t = 0.75 the penalty is 3: (45 − 165)/100 = −1.20 vs (40 − 105)/100 = −0.65, the abstainer wins. Asserted by code/ch02/calibration.py:

2.7Ranking from preferences

Open-ended chat has no reference and no unit test. The workaround that came to dominate public leaderboards: show a person (or an LLM judge) two anonymous responses and ask which is better. Chatbot Arena fitted a statistical model to over 240,000 crowdsourced votes at the time of its paper[16]; MT-Bench and Arena-Hard use an LLM judge instead[17][18]. How votes become numbers is a metric choice with consequences.

Online Elo

Elo, borrowed from chess, keeps a rating R per model and updates it after every battle:

EA = 11 + 10(RB − RA)/400,    RA ← RA + K (SA − EA),   RB ← RB − K (SA − EA) (2.12) where SA = 1 if A wins, 0 if it loses, 0.5 for a tie, and K is the step size.

RA = 1200, RB = 1000: EA = 1/(1 + 10−0.5) = 0.760. If A wins with K = 4, RA rises by 4 × 0.240 = 0.961 points.

FastChat’s implementation uses exactly these constants: K = 4, base 10, scale 400, initial rating 1000[70]:

def compute_elo(df, k=4.0, base=10.0, init_rating=1000.0, scale=400.0):
    matchups, outcomes, models = preprocess_for_elo(df)
    alpha = math.log(base) / scale
    ratings = np.full(shape=(len(models),), fill_value=init_rating)
    for (model_a_idx, model_b_idx), outcome in zip(matchups, outcomes):
        prob = 1.0 / (1.0 + math.exp(alpha * (ratings[model_b_idx] - ratings[model_a_idx])))
        update = k * (outcome - prob)
        ratings[model_a_idx] += update
        ratings[model_b_idx] -= update
    return {model: ratings[idx] for idx, model in enumerate(models)}

Online Elo deliberately weights recent games because players’ skill changes. A released checkpoint does not change, so for LLMs the order-dependence is pure noise: the same battles in another order give different ratings.

Bradley–Terry by maximum likelihood

The Bradley–Terry (BT) model assumes each model has a fixed strength β and that

P(A beats B) = σ(βA − βB) = 11 + e−(βA − βB) (2.13) Fit all β at once by maximising the log-likelihood of every observed battle: a logistic regression whose design row has +1 for model A and −1 for model B. Ratings on the Elo scale are R = (400 / ln 10)·β + constant, so a 400-point gap means 10:1 odds.

Because the likelihood is a sum over battles, the fit is independent of order, uses every battle equally, and yields confidence intervals by resampling battles, refitting and taking percentiles. Chatbot Arena moved from online Elo to BT for these reasons[16]. FastChat minimises a weighted cross-entropy with L-BFGS, counting a draw as half a win and half a loss, then maps to the Elo scale and anchors a reference model[70]:

FastChat fits with alpha = log(base) = ln 10, so its scale is a plain 400; fitting in natural-log units, as we do, needs 400/ln 10 ≈ 173.7. Only rating differences are identified, so the anchor is arbitrary.

Style control and length control

Human and LLM raters both prefer longer, more formatted answers, somewhat independently of content, so a plain BT fit credits verbosity as strength. Style control adds style covariates, P = σ(X⊤β + Z⊤γ), where Z holds normalised differences (a − b)/(a + b) in length, markdown headers, bold elements and list items. LMSYS fitted 0.249 for length versus 0.031, 0.024 and 0.019 for lists, headers and bold, and ranks moved substantially: one model fell from 6th to 18th, another rose from 16th to 10th[71]. Length-controlled AlpacaEval fits a GLM with a length-difference term to judge win rates and reports the win rate at zero length difference, raising Spearman correlation with Chatbot Arena from 0.94 to 0.98[19]. LMArena has packaged BT and style-aware BT as an open-source library, Arena-Rank[72].

On 16 May 2025 LMArena made style control the default for its text and vision leaderboards, adjusting the offset so the style-controlled board sits on the same rating scale as the non-style-controlled one; on 23 July 2025 it added frequency-based re-weighting of battles[86]. Arena ratings from before and after these dates come from different rating models, so record the rating model (plain BT, style-controlled, re-weighted) and the leaderboard snapshot date with any Arena number. The same applies to Arena-Hard-Auto: v2.0 (23 April 2025) replaced v0.1’s prompts and its GPT-4-Turbo judge[18] with 500 fresh hard prompts plus 250 creative-writing queries judged by GPT-4.1 or Gemini-2.5. def fit_bt(a, b, y, z=None, iters=50, ridge=1e-6) -> tuple[np.ndarray, float]:
    """Bradley-Terry by Newton's method on the logistic log-likelihood.
    Design row: +1 for model a, -1 for model b, and optionally the style covariate z.
    Model 0 is pinned to 0 for identifiability (we re-anchor afterwards)."""
    m = len(MODELS)
    n = len(y)
    X = np.zeros((n, m - 1 + (z is not None)))
    for col in range(1, m):
        X[:, col - 1] = (a == col).astype(float) - (b == col).astype(float)
    if z is not None:
        X[:, -1] = z
    w = np.zeros(X.shape[1])
    for _ in range(iters):
        p = 1 / (1 + np.exp(-X @ w))
        grad = X.T @ (y - p) - ridge * w
        H = (X * (p * (1 - p))[:, None]).T @ X + ridge * np.eye(len(w))
        step = np.linalg.solve(H, grad)
        w += step
        if np.max(np.abs(step)) < 1e-10:
            break
    beta = np.concatenate([[0.0], w[: m - 1]])
    gamma = float(w[-1]) if z is not None else 0.0
    return beta, gamma

2.8Aggregating across tasks

An “average score” across a suite hides three choices: how to weight subtasks, how to put tasks with different chance levels on one scale, and whether averaging different metrics is meaningful at all.

Macro versus micro averages

A micro average pools items (each counts once); a macro average averages per-subject accuracies (each subject counts once). MMLU’s subjects range from about a hundred to over a thousand test items, so the two can disagree: in our script model X wins on macro (0.750 vs 0.703) and Y on micro (0.610 vs 0.593), because Y is better on the one large subject. They answer different questions (“typical subject” vs “typical item”); say which you report.

Chance normalisation

Guessing scores 25% on 4-way MC, 10% on MMLU-Pro and 0% on generative math, so raw averages reward easy-to-guess tasks. Open LLM Leaderboard v2 rescales each task so that chance is 0 and perfect is 100[75]:

norm = raw − lower1 − lower × 100, clipped below at 0 (2.14) where lower = 1/(number of choices) for MC tasks and 0 for generative tasks such as MATH and IFEval.

GPQA (4 choices, lower = 0.25), raw 0.60: (0.60 − 0.25)/0.75 × 100 = 46.67. MuSR is normalised per subtask, then averaged: murder mysteries (2 choices) raw 0.7 → 40.00, object placement (5 choices) raw 0.4 → 25.00, team allocation (3 choices) raw 0.6 → 40.00; mean 35.00. Both are the documentation’s own examples[75] and are asserted by code/ch02/normalize_scores.py.

def normalize(raw: float, n_choices: int | None) -> float:
    """(raw - lower) / (1 - lower) * 100, clipped at 0. Generative tasks use lower = 0."""
    lower = 0.0 if n_choices is None else 1.0 / n_choices
    if raw < lower:
        return 0.0
    return (raw - lower) / (1 - lower) * 100

2.9Error bars, signal and noise (preview)

Every number in this chapter is an estimate from a finite sample of items, and often of generations. This section previews the statistics; Chapter 5 treats them in full.

Error bars in two paragraphs

Miller frames a benchmark as a sample from a super-population of questions that could have been written[76]. For a mean of binary scores, SE = √(p̂(1 − p̂)/N) and a 95% interval is p̂ ± 1.96 SE: at 80% on 1,000 items, [77.5, 82.5]; on a 198-item set at 50%, about ±7 points, wider than many reported “wins”.

Two corrections matter. Items that share a passage or template are not independent, and Anthropic reports clustered SEs over three times the naive ones on popular evals[77]. And two models on the same items should be compared by the paired difference, whose variance subtracts their covariance; with the 0.3–0.7 correlations seen between frontier models, pairing shrinks the SE substantially[76].

Signal-to-noise: discrete versus continuous metrics

During development the question is whether a benchmark reliably tells similar models apart. Heineman et al. define signal as the relative dispersion of scores across models at similar compute (max gap over mean), noise as the relative standard deviation of one model’s score over its final checkpoints, and SNR as their ratio. Across 465 models and 30 benchmarks, SNR predicted whether small-scale experiments rank models like large-scale ones, and three interventions raised it: dropping noisy subtasks, averaging checkpoints, and switching from accuracy to a continuous metric such as bits-per-byte[78]. Choosing items with item response theory, or adaptively (“fluid benchmarking”), can also raise signal-to-noise and extend a benchmark’s useful life; see Section 5.12.

def checkpoint_scores(rng, ability: float, difficulty: np.ndarray, n_ckpt: int):
    """Scores of the last n_ckpt checkpoints of one training run.
    Each checkpoint jitters the ability a little (training-step noise); accuracy also has
    Bernoulli sampling noise, while the continuous metric (mean NLL of the gold answer) does not."""
    acc, nll = [], []
    for _ in range(n_ckpt):
        a = ability + rng.normal(0, 0.05)
        p = sigmoid(a - difficulty)                       # P(gold answer ranked first)
        acc.append(float(np.mean(rng.random(len(p)) < p)))
        nll.append(float(np.mean(-np.log(p))))           # lower is better
    return np.array(acc), np.array(nll)


def snr(finals: np.ndarray, ckpts: list[np.ndarray]) -> tuple[float, float, float]:
    signal = (finals.max() - finals.min()) / abs(finals.mean())          # relative dispersion
    noise = float(np.mean([c.std(ddof=1) / abs(c.mean()) for c in ckpts]))  # relative std over checkpoints
    return signal, noise, signal / noise


def pairwise_accuracy(ckpts: list[np.ndarray], abilities: np.ndarray, higher_better: bool, rng, trials=2000):
    """Fraction of (pair, random checkpoint) draws where the metric orders the two models correctly."""
    pairs = list(itertools.combinations(range(len(abilities)), 2))
    ok = 0
    for _ in range(trials):
        i, j = pairs[rng.integers(len(pairs))]
        si, sj = ckpts[i][rng.integers(len(ckpts[i]))], ckpts[j][rng.integers(len(ckpts[j]))]
        if not higher_better:
            si, sj = -si, -sj
        ok += int((si > sj) == (abilities[i] > abilities[j]))
    return ok / trials

The same distinction explains many “emergent” abilities. On six outputs, strict-match scores 1/6 and flexible-extract 4/6. Two failures are silent: “#### 1200.00” fails both (decimals are not canonicalised), and the simple-evals regex misses “The answer is (B).”. The strict–flexible gap measures format-following, not arithmetic. Log the extraction-failure rate separately from the error rate.

For answers that are mathematical objects rather than integers, string matching is not enough, and benchmarks use symbolic-equivalence graders. MATH’s own is_equiv normalises LaTeX strings; Hugging Face’s Math-Verify goes further: it extracts LaTeX or plain expressions, parses them with an ANTLR4 grammar into SymPy, and checks mathematical equivalence, so verify(parse("${1,3} \cup {2,4}$"), parse("${1,2,3,4}$")) returns True. Argument order matters (gold first), as the README warns. Its README compares graders on identical model outputs on MATH (as of November 2026): lm-evaluation-harness 0.0802, Qwen’s grader 0.1288, Math-Verify 0.1328[88], a relative change of about 65% from the grader alone. At the far end is an LLM grader: an LLM given the reference answer decides whether the response matches it. It is the most flexible checker and the one that most needs validating against humans (Chapter 4). Whatever you use, the equivalence checker and its version go on the protocol card.

The real harness (lm_eval --tasks gsm8k --log_samples) reports exact_match,strict-match and exact_match,flexible-extract separately; compare them before quoting either. Chapter 9 covers running it.

2.11When benchmarks break

Even a perfectly specified protocol measures the wrong thing when the dataset fails. Four failure modes account for most broken benchmarks.

Contamination

A public test set eventually appears in someone’s training data, verbatim or reworded. GSM1k, a fresh set matched to GSM8K, found drops of up to 8% for some model families, correlated with how likely the model was to generate GSM8K examples (r² = 0.36)[31]. n-gram overlap filtering misses paraphrased and translated copies, and a 13B model fine-tuned on rephrased test items reached GPT-4-level scores[81]; GSM-Symbolic shows drops when only numbers change[32]. Structural mitigations are fresh or dated items: LiveCodeBench after a model’s cutoff[21], LiveBench’s regular refreshes[82], MathArena’s post-release competitions[25], and unpublished FrontierMath and HLE items[22][23]. Detection and prevention are the subject of Chapter 3.

def ngrams(text: str, n: int = 13) -> set[tuple[str, ...]]:
    t = text.lower().replace("?", " ").replace(".", " ").split()
    return {tuple(t[i:i + n]) for i in range(len(t) - n + 1)}


def flagged(test_q: str, corpus_index: set, n: int = 13, threshold: float = 0.5) -> bool:
    g = ngrams(test_q, n)
    return bool(g) and len(g & corpus_index) / len(g) >= threshold


class Memoriser:
    """Answers perfectly anything it has seen (verbatim or paraphrased), else is right 35% of the time."""

    def __init__(self, seen_answers: dict[str, int], rng: random.Random):
        self.seen, self.rng = seen_answers, rng

    def answer(self, q: str, true: int) -> int:
        if q in self.seen:
            return self.seen[q]
        return true if self.rng.random() < 0.35 else true + 1

Label noise

Benchmarks contain mistakes. MMLU-Redux estimated that 6.49% of MMLU’s questions contain errors (57% of the analysed Virology questions), and rankings changed on corrected labels[5]. Vendrow et al. found label errors pervasive and proposed cleaned “platinum” versions[83]. GPQA’s experts scored 65%, or 74% after discounting mistakes they recognised in retrospect[20]. At the frontier, FutureHouse audited HLE’s 321 text-only chemistry and biology questions with a literature-search agent plus expert review and judged about 29% (±3.7 points) of reference answers wrong or contradicted by peer-reviewed literature[33]. The audit’s method is itself contested, and HLE’s authors point to the questions’ difficulty, but Epoch AI’s benchmark review rates HLE “Flawed”[84]. The mechanism is general: adversarial filtering keeps only items frontier models get wrong, and a mislabelled item is one every correct model gets “wrong”, so the filter enriches for label errors.

Label noise sets a ceiling (with 6.49% wrong labels a perfect model scores about 0.935, as our script prints), so gaps near the top may be about which wrong labels models agree with, and it hides real failures behind spurious ones. Audit a random sample of items, and the items every strong model gets “wrong”, before trusting the top of any leaderboard.

Saturation and gaming

Saturation (Section 2.2) and gaming are two sides of Goodhart’s law. Once a benchmark is a target, developers tune toward it: private variant testing on the Arena[41], the best of many prompt formats[1], the most flattering temperature. Dynamic benchmarks that keep collecting items with humans and models in the loop are one older answer[85]; expert curation appears to matter more than secrecy for longevity[47].

Two models score 62% and 66% on 200 items. Are the 95% intervals (Section 2.9) disjoint? How many items give ±2 points?

Solution

SE = √(0.62 × 0.38 / 200) = 0.034, so 62 ± 6.7 and 66 ± 6.6: heavy overlap. ±2 points at 64% needs 1.96² × 0.64 × 0.36 / 0.02² ≈ 2,213 items. Separate intervals are conservative; the paired SE of the difference is smaller (Chapter 5).

  • A benchmark score is the output of a five-layer stack (dataset, elicitation, scoring, aggregation, uncertainty); two numbers are comparable only if the whole stack matches.
  • Normalisation and extraction are part of the metric: the same outputs scored 1/6 or 4/6 under GSM8K’s strict and flexible extractors.
  • n-gram metrics can disagree completely (BLEU = 0, ROUGE-L = 0.769); use them for constrained outputs, and name the checkpoint of any learned metric.
  • Log-likelihood MC scoring depends on the decision rule (acc, acc_norm, MI) and the formulation (cloze vs letter); name both.
  • Estimate pass@k with the unbiased estimator from n > k samples; say whether pass@1 is greedy or avg@n; remember that pass@k needs a verifier and that weak tests inflate it.
  • Report calibration (ECE with its binning, plus Brier) and abstention (three counts, or a confidence-target penalty), not just accuracy.
  • Use Bradley–Terry with bootstrap intervals, a stated tie treatment and style control; online Elo is order-dependent, and leaderboards can be gamed.
  • Prompt format alone can swing scores by tens of points; report a range, an error bar and a protocol card with every headline number.
