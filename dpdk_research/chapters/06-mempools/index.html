rte_mempool and rte_stack: Fixed-Size Allocation at Line Rate

A 10 Gb/s port can deliver almost 15 million packets per second, and every one of them needs a buffer that is allocated and freed again. After this chapter you can create and inspect a mempool, explain exactly what its per-lcore cache does in DPDK 26.11, size a pool so it never runs dry, pick or write a mempool handler, and use rte_stack knowing why its lock-free variant needs a 128-bit compare-and-swap.

1Why fixed-size pools?

Think about what a forwarding loop does with memory. For every packet it receives, the NIC needs an empty buffer to write into; for every packet sent, the buffer must be released after the NIC has read it. At 14.88 million packets per second (10 Gb/s with 64-byte frames, ch1) that is a budget of about 67 ns, roughly 200 cycles at 3 GHz, for the whole packet. An allocator call that takes 100 cycles, or takes a lock that another core holds, does not fit.

General-purpose allocators (malloc, the kernel's slab) are built for objects of any size and for programs that allocate rarely. Packet processing allocates the same size, constantly, from many cores. A mempool exploits that:

  • All memory up front. The pool reserves room for N objects of one size when you create it, from the EAL's memory (ch4). It never grows and never returns memory to the OS. Allocation can never call into the kernel.
  • Allocation is a pointer pop. Free objects are tracked as a list of pointers. Getting an object means taking one pointer from that list; freeing means putting it back. No searching, no splitting, no coalescing: O(1).
  • The list is pluggable. By default the free list is the lock-free rte_ring of ch5. It can also be a stack, a bucket allocator or a hardware buffer manager on NICs that have one. The pool calls this the handler or mempool ops.
  • Each lcore has a private cache in front of it. Most gets and puts touch only a small per-lcore array of pointers, with no atomic instructions at all. This is the single biggest performance idea in this chapter (section 5).

	uint32_t uses;         /* incremented by the application */
	uint8_t  payload[OBJ_SIZE - 8];
};

static void
number_obj(struct rte_mempool *mp, void *arg, void *obj, unsigned int obj_idx)

	struct my_obj *o = obj;
	(void)mp;
	(void)arg;
	o->seq = obj_idx;
	o->uses = 0;
}

	    unsigned int idx)

	size_t *total = arg;
	(void)mp;
	(void)idx;
	*total += m->len;

3Object layout and the memory behind a pool

Every object in a pool is surrounded by bookkeeping that the pool adds. rte_mempool_calc_obj_size() in lib/mempool/rte_mempool.c decides the sizes:

  • Header. struct rte_mempool_objhdr holds a list link, the owning pool and the object's IOVA: 24 bytes on 64-bit, rounded up to 64 so the element starts on a cache line.
  • Element. Your elt_size, rounded up to a cache line.
  • Trailer and channel spreading. A DRAM system interleaves cache lines over several memory channels and ranks. Packet code mostly reads the first cache line of each buffer. If every object were 2 cache lines long and you have 4 channels, all object starts would land on channels 0 and 2 only. So, unless you pass RTE_MEMPOOL_F_NO_SPREAD, the pool grows the object (header + element) to a number of cache lines that has no common factor with channels × ranks (EAL options -n and -r; 4 × 1 is assumed when unknown). 128 bytes = 2 lines becomes 3 lines = 192 bytes: that is the 64-byte trailer above. A 2304-byte mbuf-sized element plus its header is 37 lines, already coprime with 4, so its trailer is 0. The DPDK docs note that Arm interconnects hash addresses over channels, so this padding is not applied there.
  • No object crosses a page. The NIC needs each buffer to be contiguous in IO address space. Unless the pool has RTE_MEMPOOL_F_NO_IOVA_CONTIG, the default populate step places objects so that none straddles a page boundary; the leftover space at the end of each page is wasted. With 2 MB hugepages that waste is tiny. With --no-huge, pages are 4 KB, and a 2368-byte object leaves 1728 bytes unused in every page.

4Getting and putting objects

The data-path API is small, and all of it is static inline in rte_mempool.h, so a get compiles into a handful of instructions in your loop:

CallWhat it does
rte_mempool_get(mp, &obj)One object. Returns 0 or a negative error.
rte_mempool_get_bulk(mp, objs, n)n objects or none at all. Returns 0 or a negative error.
rte_mempool_put(mp, obj), rte_mempool_put_bulk(mp, objs, n)Give objects back. Returns void: a put cannot fail in a correctly sized pool.
rte_mempool_generic_get/put(mp, objs, n, cache)The same with an explicit cache pointer: your own cache, or NULL to bypass caching (section 7).
rte_mempool_avail_count(mp), rte_mempool_in_use_count(mp)Free objects (ring + all caches) and objects handed out. Not on the fast path: they read every lcore's cache.
rte_mempool_full(mp), rte_mempool_empty(mp)avail == size, avail == 0.

Prefer bulk calls. A burst of 32 packets is handled with one get_bulk(32), and the per-call overhead is shared by 32 objects. This matches the burst API of ch8.

Pitfall: putting an object into the wrong pool, or twice

The pool cannot check what you give it (unless DPDK is built with RTE_LIBRTE_MEMPOOL_DEBUG, which adds cookies around objects). Putting the same object twice means it will later be handed to two users at once; putting an object from pool A into pool B corrupts both counts. The symptoms show up much later, as two packets that overwrite each other. Free each object exactly once, into the pool it came from: rte_mempool_from_obj(obj) tells you which.

5The per-lcore cache

The default handler is an MP/MC ring. Each get or put on it is at least one atomic compare-and-swap on the ring head, and when several lcores share the pool, the cache line holding that head moves between cores on every operation. The last part of this section measures what that costs here: about 70 cycles per object. The fix is the same as in any CPU: keep a small private stock.

Each lcore gets a cache: an array of object pointers used as a stack, plus a length. Because only that lcore ever touches it, no atomics are needed. In 26.11 the structure is:

struct __rte_cache_aligned rte_mempool_cache {
	uint32_t size;	      /* capacity, fixed at creation */
	uint32_t len;	      /* objects in the cache now */
	/* (per-lcore stats here if RTE_LIBRTE_MEMPOOL_STATS) */
	alignas(RTE_CACHE_LINE_SIZE) void *objs[];   /* variable size since 26.11 */
};

The per-lcore caches live right after the pool header (and its private data); rte_mempool_default_cache(mp, lcore_id) indexes them with the new mp->sizeof_cache_per_lcore stride. It returns NULL when the pool has no cache or when the caller is not an EAL lcore.

The 26.11 algorithm

Read rte_mempool_do_generic_put() and rte_mempool_do_generic_get() in lib/mempool/rte_mempool.h; they are short. Here is the decision table they implement, for a cache of capacity size holding len objects:

OperationConditionWhat happens
put(n)len + n ≤ sizeCopy the pointers on top of the cache. No ring access.
put(n)no room, n ≤ size/2Enqueue the bottom size/2 pointers (the oldest, least likely still in the CPU cache) to the ring, slide the upper part down, then push the n.
put(n)no room, n > size/2Bypass: enqueue the n straight to the ring. The cache is untouched.
get(n)n ≤ lenPop n from the top. No ring access.
get(n)n > len, remainder n − len ≤ size/2Take all len, refill exactly size/2 from the ring, serve the remainder from the refill.
get(n)n > len, remainder > size/2 (or the refill fails)Take all len, get the remainder straight from the ring. If that fails too, the cache is restored and the call returns an error.

Two properties follow: the cache never holds more than size, and it only ever talks to the ring in chunks of size/2 (or for requests too big to be worth copying twice). An lcore that alternates gets and puts of a burst keeps its cache between 0 and size and hits the ring once every size/2 objects at most.

What changed in 26.07 and 26.11

Version note: most blog posts describe the old cache

If you learned mempools from older material, three things are different now:

  • 26.07 changed the algorithm (release_26_07.rst, "Changed mempool cache behaviour"). The cache used to have a flushthresh of 1.5 × size, so its effective size was 50% larger than requested; now it holds exactly size and moves size/2 at a time. The release notes advise applications where each lcore only gets or only puts (pipelines whose Rx and Tx run on different lcores) to double their cache size, or their cache miss rate doubles. The animation below shows why.
  • 26.11 removed the size limit (release_26_11.rst, API changes). cache_size can be anything up to n; RTE_MEMPOOL_CACHE_MAX_SIZE (512) is kept only so that old code that passes it as a cache size still compiles.
  • 26.11 changed the structs. struct rte_mempool_cache lost flushthresh and unused, and objs[] became a flexible array; struct rte_mempool gained sizeof_cache_per_lcore. Code that did sizeof(struct rte_mempool_cache) or indexed mp->local_cache[lcore] directly must use rte_mempool_default_cache().

Pipelines: one lcore only gets, another only puts

In a pipeline (ch15), the Rx lcore allocates buffers and the Tx lcore frees them. The Rx lcore's cache only drains and the Tx lcore's cache only fills, so the "absorb gets and puts locally" benefit is gone; what remains is batching ring accesses. Under the 26.11 algorithm, each refill brings size/2 objects and each flush sends size/2. Under the old one, a refill brought size (plus the request) and a flush sent the whole cache, up to 1.5 × size. Same cache_size, roughly twice the ring traffic now: hence the advice to double it.

6Choosing the size: stranded objects

A cache is private. Objects in lcore 1's cache are free, they are counted by rte_mempool_avail_count(), but no other lcore can take them. The API documentation says it plainly: a get "can return -ENOENT when the local cache and common pool are empty, even if cache from other lcores are full". stranded_cache.c makes it happen with a pool of 256 and a cache of 128 on 3 lcores. Each worker runs a loop that frees everything it allocates:

code/stranded_cache.cC
/* A balanced worker: two bursts of 64 out, two bursts of 64 back. */
static int
worker_balanced(void *arg)
{
	void *a[64], *b[64];
	int i;
	(void)arg;

	for (i = 0; i < 1000; i++) {
		if (rte_mempool_get_bulk(mp, a, 64) != 0)
			continue;
		if (rte_mempool_get_bulk(mp, b, 64) != 0) {
			rte_mempool_put_bulk(mp, a, 64);
			continue;
		}
		rte_mempool_put_bulk(mp, a, 64);
		rte_mempool_put_bulk(mp, b, 64);
	}
	return 0;

So, for a pool that feeds NIC queues, count every place an object can be at the worst moment:

Sizing rule

n ≥ (Rx descriptors of all queues) + (Tx descriptors of all queues) + nb_lcores × cache_size + nb_lcores × burst + anything else the app holds

Rx descriptors are always loaded with empty buffers; Tx descriptors hold sent buffers until the driver frees them (ch8); each cache can be full; each lcore can hold a burst in its hands. Then round up to 2q − 1. Exercise 1 checks the formula on a real pool with 4 lcores.

7Caches for non-EAL threads

8Mempool handlers

The pool does not store free objects itself. It calls a table of function pointers, struct rte_mempool_ops, whose most important entries are alloc, free, enqueue, dequeue and get_count. Reading the columns:

  • Cost, one lcore, no contention. The rings and the locked stack cost 1.5–2.7 cycles per object for bursts of 32: the per-call work is shared by the burst. lf_stack is about four times slower than stack: it walks a linked list and does 128-bit compare-and-swaps where the locked stack does one lock and a memcpy. Lock-free means "no thread can block another", not "faster". pile recovers most of the gap by moving 32 pointers per list element.
  • Singles: FIFO vs LIFO. The program takes 5 objects, frees them in order, and takes 5 again. The rings hand out different, older objects (653.. after 648..); the stacks hand back the ones just freed, most recent first (2042 was freed last). LIFO reuse is cache-friendly: the object you get is probably still in L1/L2.
  • Bulks: the pile caveat. After get(64), put(64), get(64), a true stack returns the 64 in reverse (1983 first, which was got[63]). The pile returns the second 32-object bulk first, but in its original order inside the bulk (2014, 2013, ... is got[32..]). This is the documented 26.11 behaviour ("only LIFO at the bulk level, not at the object level"), not a bug.

9Writing your own handler

A handler is five functions and a struct. custom_ops.c implements a pointer array protected by a spinlock, the same idea as the built-in stack, so that every callback is visible:

code/custom_ops.cC
static int
array_alloc(struct rte_mempool *mp)
{
	struct array_store *st;

	st = rte_zmalloc_socket("ch06_array_store",
				sizeof(*st) + sizeof(void *) * mp->size,
				RTE_CACHE_LINE_SIZE, mp->socket_id);
	if (st == NULL)
		return -ENOMEM;
	rte_spinlock_init(&st->lock);
	st->size = mp->size;
	mp->pool_data = st;     /* every other callback finds it here */
	return 0;
code/custom_ops.cC
array_dequeue(struct rte_mempool *mp, void **obj_table, unsigned int n)
{
	struct array_store *st = mp->pool_data;
	unsigned int i;

	rte_spinlock_lock(&st->lock);
	st->n_deq++;
	if (n > st->len) {                 /* all or nothing */
		rte_spinlock_unlock(&st->lock);
		return -ENOBUFS;
	}
	for (i = 0; i < n; i++)            /* pop from the top: LIFO */
		obj_table[i] = st->objs[--st->len];
	rte_spinlock_unlock(&st->lock);
	return 0;
}

static unsigned int
array_get_count(const struct rte_mempool *mp)
{
	const struct array_store *st = mp->pool_data;
	return st->len;
}

static struct rte_mempool_ops ops_ch06_array = {
	.name = "ch06_array",
	.alloc = array_alloc,
	.free = array_free,
	.enqueue = array_enqueue,
	.dequeue = array_dequeue,
	.get_count = array_get_count,
	/* calc_mem_size, populate, get_info: NULL -> library defaults */
};

RTE_MEMPOOL_REGISTER_OPS(ops_ch06_array);
  • alloc runs during populate, before any object exists. It creates the store and saves it in mp->pool_data; use mp->size for the capacity and mp->socket_id for the NUMA node.
  • enqueue / dequeue must be safe for whatever threads will call them (here: a spinlock) and dequeue must be all-or-nothing. Return 0 or a negative errno.
  • get_count may be approximate under concurrency; it feeds rte_mempool_avail_count().
  • The optional calc_mem_size, populate, get_info and dequeue_contig_blocks stay NULL; the library's defaults (in rte_mempool_ops_default.c) apply.
  • RTE_MEMPOOL_REGISTER_OPS(ops) expands to an RTE_INIT constructor that calls rte_mempool_register_ops() before main().

/* ---- the handler's private store --------------------------------------- */
struct array_store {
	rte_spinlock_t lock;
	unsigned int len;      /* objects currently stored  */
	unsigned int size;     /* capacity = mp->size        */
	uint64_t n_enq, n_deq; /* calls, for the demo        */
	void *objs[];          /* LIFO: objs[len-1] is the top */
};

static int
array_alloc(struct rte_mempool *mp)
{
	struct array_store *st;

	st = rte_zmalloc_socket("ch06_array_store",
				sizeof(*st) + sizeof(void *) * mp->size,
				RTE_CACHE_LINE_SIZE, mp->socket_id);
	if (st == NULL)
		return -ENOMEM;
	rte_spinlock_init(&st->lock);
	st->size = mp->size;
	mp->pool_data = st;     /* every other callback finds it here */
	return 0;
}

static void
array_free(struct rte_mempool *mp)
{
	rte_free(mp->pool_data);
}

static int
array_enqueue(struct rte_mempool *mp, void * const *obj_table, unsigned int n)
{
	struct array_store *st = mp->pool_data;
	int ret = 0;

	rte_spinlock_lock(&st->lock);
	st->n_enq++;
	if (st->len + n > st->size) {
		ret = -ENOBUFS;            /* cannot happen in a healthy pool */
	} else {
		memcpy(&st->objs[st->len], obj_table, sizeof(void *) * n);
		st->len += n;
	}
	rte_spinlock_unlock(&st->lock);
	return ret;
}

static int
array_dequeue(struct rte_mempool *mp, void **obj_table, unsigned int n)
{
	struct array_store *st = mp->pool_data;
	unsigned int i;

	rte_spinlock_lock(&st->lock);
	st->n_deq++;
	if (n > st->len) {                 /* all or nothing */
		rte_spinlock_unlock(&st->lock);
		return -ENOBUFS;
	}
	for (i = 0; i < n; i++)            /* pop from the top: LIFO */
		obj_table[i] = st->objs[--st->len];
	rte_spinlock_unlock(&st->lock);
	return 0;
}

static unsigned int
array_get_count(const struct rte_mempool *mp)
{
	const struct array_store *st = mp->pool_data;
	return st->len;
}

static struct rte_mempool_ops ops_ch06_array = {
	.name = "ch06_array",
	.alloc = array_alloc,
	.free = array_free,
	.enqueue = array_enqueue,
	.dequeue = array_dequeue,
	.get_count = array_get_count,
	/* calc_mem_size, populate, get_info: NULL -> library defaults */
};

static struct rte_mempool *
make_pool(const char *name, unsigned int cache)
{
	struct rte_mempool *mp;
	int ret;

	mp = rte_mempool_create_empty(name, 1023, 64, cache, 0, rte_socket_id(), 0);
	if (mp == NULL)
		rte_exit(EXIT_FAILURE, "create_empty: %s\n", rte_strerror(rte_errno));
	ret = rte_mempool_set_ops_byname(mp, "ch06_array", NULL);
	if (ret != 0)
		rte_exit(EXIT_FAILURE, "set_ops_byname: %s\n", strerror(-ret));
	ret = rte_mempool_populate_default(mp);    /* calls alloc, then enqueue */
	if (ret < 0)
		rte_exit(EXIT_FAILURE, "populate: %s\n", strerror(-ret));

}

static void
workload(struct rte_mempool *mp)
{
	void *objs[32];
	int i;

	for (i = 0; i < 10000; i++) {
		rte_mempool_get_bulk(mp, objs, 32);
		rte_mempool_put_bulk(mp, objs, 32);
	}
}

main(int argc, char **argv)
{
	struct rte_mempool *mp;
	struct array_store *st;
	unsigned int i;
	void *a, *b, *big[1024];
	int ret;

	if (rte_eal_init(argc, argv) < 0)
		rte_exit(EXIT_FAILURE, "EAL init failed\n");

	printf("[1] registered mempool handlers (rte_mempool_ops_table, %u entries):\n  ",
	       rte_mempool_ops_table.num_ops);
	for (i = 0; i < rte_mempool_ops_table.num_ops; i++)
		printf("%u:%s ", i, rte_mempool_ops_table.ops[i].name);
	printf("\n");

	mp = make_pool("ch06_custom", 0);
	st = mp->pool_data;
	printf("[2] pool '%s' ops_index=%d ops=%s; store holds %u, enqueue calls=%" PRIu64
	       " (populate)\n", mp->name, mp->ops_index,
	       rte_mempool_get_ops(mp->ops_index)->name, st->len, st->n_enq);

	/* LIFO check: free a then b; the next get returns b (the hottest). */
	rte_mempool_get(mp, &a);
	rte_mempool_get(mp, &b);
	rte_mempool_put(mp, a);
	rte_mempool_put(mp, b);
	{
		void *c;
		rte_mempool_get(mp, &c);
		printf("[3] put a=%p, put b=%p, get -> %p (%s)\n", a, b, c,
		       c == b ? "b: LIFO" : "a: FIFO");
		rte_mempool_put(mp, c);
	}

	/* Exhaustion: our dequeue returns -ENOBUFS, the API passes it through. */
	ret = rte_mempool_get_bulk(mp, big, 1023);
	printf("[4] get_bulk(1023)=%d, then get_bulk(1)=", ret);
	ret = rte_mempool_get_bulk(mp, &a, 1);
	printf("%d (%s)\n", ret, strerror(-ret));
	rte_mempool_put_bulk(mp, big, 1023);

	/* Handler calls with and without a cache. */
	st->n_enq = st->n_deq = 0;
	workload(mp);
	printf("[5] cache 0 : 10000 x (get 32 + put 32) -> handler dequeue=%" PRIu64
	       " enqueue=%" PRIu64 " calls\n", st->n_deq, st->n_enq);
	rte_mempool_free(mp);

	mp = make_pool("ch06_custom2", 64);
	st = mp->pool_data;
	st->n_enq = st->n_deq = 0;
	workload(mp);
	printf("    cache 64: 10000 x (get 32 + put 32) -> handler dequeue=%" PRIu64
	       " enqueue=%" PRIu64 " calls\n", st->n_deq, st->n_enq);
	rte_mempool_free(mp);

	rte_eal_cleanup();
	return 0;
}

One lcore alone: the locked stack is cheapest, lock-free costs about twice as much per single object, and bursts amortise everything. Two lcores sharing one stack: every operation pulls the head's cache line from the other core, and costs explode to thousands of cycles per single object on this VM (with a wide min–max spread: cross-core latency in a VM is noisy). Even under contention the spinlock version stays in the same range as the lock-free ones. The case for the lock-free variants is preemption: if a thread holding the spinlock is descheduled, every other thread spins until it runs again; a lock-free stack keeps working. On isolated, pinned lcores (the normal DPDK setup) that rarely happens, which is why ring_mp_mc, not a lock-free stack, is the default.

The ABA problem, step by step

A lock-free pop reads the head, reads head->next, and then uses compare-and-swap (CAS) to replace the head with next, but only if the head is still what it read. CAS checks equality, not history. If, between the read and the CAS, other threads pop the element, reuse it and push it back, the head is "the same" pointer again and the CAS succeeds with a stale next. This is the ABA problem: the value went A → B → A and the CAS cannot tell. It is a real risk in a pool, where recycling the same few objects is the whole point.

DPDK's fix, in lib/stack/rte_stack_lf_c11.h: the head is struct rte_stack_lf_head { struct rte_stack_lf_elem *top; uint64_t cnt; }, 16-byte aligned, and every push and pop replaces both fields with one rte_atomic128_cmp_exchange() (the x86 cmpxchg16b instruction), incrementing cnt each time. A recycled pointer comes back with a different counter, so the stale CAS fails and the thread retries with fresh values. A 64-bit counter cannot wrap around during the few nanoseconds a thread is between its read and its CAS.

Common pitfalls

  • get fails but avail_count says objects are free: they are stranded in other lcores' caches. Size the pool with nb_lcores × cache_size on top (section 6), or flush caches on their owning lcores when they stop.
  • Pool creation fails with EINVAL: cache_size > n, an unknown flag, or a zero size. With ENOMEM under --no-huge: remember an mbuf-sized object costs a whole 4 KB page there (section 3).
  • Checking for -ENOENT: the error code comes from the handler; the ring returns -ENOBUFS. Test ret < 0.
  • Calling rte_mempool_cache_flush() on another lcore's cache while it runs: caches have no lock. Flush on the owner.
  • Freeing a user cache without flushing it: its objects are gone for good.
  • Non-EAL threads hammering a pool without a cache: every call is a ring CAS (section 7).
  • Using ring_sp_sc (or RTE_MEMPOOL_F_SP_PUT/_SC_GET) with several threads: no error, just silent corruption of the ring. That is why the exercise 2 solution leaves it out.
  • Old code that touches cache->flushthresh, cache->objs[RTE_MEMPOOL_CACHE_MAX_SIZE] or mp->local_cache[i]: these do not compile or are wrong in 26.11; use rte_mempool_default_cache() and cache->size.
  • Pipelines carried over from before 26.07: double the cache size, or the Rx and Tx lcores hit the ring twice as often (section 5).
  • Mixing handler registration order between processes: the pool stores an index into the ops table; secondary processes must register the same handlers in the same order (ch16).
  • Treating pile like a strict stack: objects within a 32-object bulk keep their order, and the count is capped at the capacity although it may hold more.

Summary
  • A mempool is N fixed-size objects allocated once; get and put are pointer moves. Each object is [header | element | trailer]; the trailer spreads object starts over memory channels, and no object crosses a page, which makes --no-huge pools of mbufs 1.7 times bigger.
  • rte_mempool_create() = create_empty + set_ops_byname + populate_default + obj_iter. Use the step-wise form to pick a handler.
  • Bulk gets are all or nothing; test ret < 0 (the ring returns -ENOBUFS).
  • The per-lcore cache (26.07 algorithm, 26.11 API) never exceeds size, refills and flushes size/2, and lets big requests bypass it. It took the shared-pool cost from about 70 to about 1.1 cycles per object here. cache_size is limited only by n since 26.11; pipelines should double it.
  • Cached objects are stranded from other lcores: n ≥ descriptors + lcores × cache + lcores × burst. Non-EAL threads need rte_mempool_cache_create() + generic_get/put, and a flush before freeing the cache.
  • Handlers: rings (FIFO), stack / lf_stack / pile (LIFO, pile per 32-object bulk), bucket, hardware pools. The pool stores an ops index; you add your own with RTE_MEMPOOL_REGISTER_OPS.
  • rte_stack offers a locked, a lock-free and a pile LIFO. Lock-free buys preemption tolerance, not speed, and it needs a {pointer, counter} 128-bit CAS to defeat ABA.
