    Domain Randomization with Batched Model Fields

    One model, thousands of slightly different worlds: every box a little heavier or lighter, every floor a little more or less slippery, every motor a little stronger or weaker. This chapter shows exactly which MJWarp model fields can differ per world, how to set them, which derived constants you must recompute with set_const, and how to draw new values on the device at every episode reset without breaking a CUDA graph.

    Intermediate About 75 min· Prerequisites: Ch 8, Ch 9

    You will learn

    • Make any "*" Model field per-world, by replacing the array or with put_model(batch_sizes=...).
    • Tell batchable numeric parameters from shared topology and compile-time options.
    • What each derived constant means, and how to recompute it with set_const and the right SetConstGroup, batching the outputs too.
    • Randomize mass, friction, geometry size, actuator gains, timestep, gravity, density and colours.
    • Re-randomize on the device between episodes, inside a captured graph.

    Before you start: recap

    • A batched field has a leading dimension B; a kernel reads row worldid % B, so values are dealt out round-robin, not in blocks (Ch 6).
    • Replace vs assign: m.x = wp.array(...) creates a new array object; m.x.assign(...) writes into the existing one (Ch 6).
    • mjw.reset_data(m, d, reset=mask) resets only the worlds whose mask entry is True (Ch 8).
    • nconmax is per world, naconmax is the total, njmax is per world; check d.overflow after a run (Ch 9).
    • solref = (timeconst, dampratio) of a spring-damper; solimp shapes impedance (Ch 2 §4).
    • A CUDA graph records launches once and replays them (Ch 7 §10).

    Highlighted: the stations that read the fields this chapter randomizes most often (body and geom poses and sizes in kinematics, contact materials in collision, gains and gears in actuation). In fact every station reads some "*" field.

    1Why randomize? Sim-to-real in one picture

    A simulator is a guess about the world. The box's mass in the XML is 1 kg, but the real box might be 0.93 kg. The floor's friction is 1.0 in the XML; the real floor is 0.7 when it is dusty and 1.1 when it is clean. A policy or controller trained on one guess learns to exploit that exact guess. When it meets the real world, which is a little different, it can fail badly. This mismatch is called the reality gap.

    Domain randomization (DR) closes the gap from the other side: instead of trying to guess the real parameters exactly, you train on many simulators whose parameters are drawn from ranges wide enough that the real world is just one more sample. A controller that works in all of them is likely to work in reality too.

    There are two kinds:

    • Physics DR changes how things move: masses, inertias, friction, contact softness (solref), joint damping, actuator gains and gears, timestep, gravity, fluid density, body and geom sizes.
    • Visual DR changes only how things look to a camera: geom and material colours, textures, lights, camera pose and field of view. It matters for policies that see pixels (Ch 27 renders them).

    DR needs no new kernels in MJWarp: the worlds are already batched (Ch 6), so each world gets its own parameters by giving a Model array one row per world, and one launch still steps all of them. What that costs on a GPU (B rows instead of one shared row means more memory traffic) is measured in Ch 25, not here.

    How wide should the ranges be?

    Too narrow and reality falls outside; too wide and the task becomes impossible (a box with friction 0 cannot be pushed, a robot with half its motor strength cannot stand up). A good start is the measured value plus or minus the measurement uncertainty, then widen until the controller's performance starts to drop. Section 13 runs exactly such a study.

    2The batching rule and the two ways to use it

    Recall from Ch 6

    Every "*" Model field has a leading batch dimension B. Kernels read field[worldid % field.shape[0], ...]. B = 1 (the default after put_model) means all worlds share one row.

    That one line of indexing is the whole mechanism. For example forward.py::_next_time advances the clock with time_out[worldid] = time_in[worldid] + opt_timestep[worldid % opt_timestep.shape[0]], and the contact code reads geom_friction[worldid % geom_friction.shape[0], g]. No kernel needs to know whether you randomized anything: with B = 1 the modulo is always 0.

    Because of the modulo, B does not have to equal nworld. With B = 2 and 8 worlds, even worlds get row 0 and odd worlds get row 1. This is round-robin batching. Play with it:

    There are two ways to get B > 1. Both are used in the library's own tests.

    With method 2, the array starts as B copies of the XML row, so you only change what you want to change:

    m = mjw.put_model(mjm, batch_sizes={"geom_friction": nworld})   # (nworld, ngeom) vec3
fr = m.geom_friction.numpy()          # host copy, shape (nworld, ngeom, 3)
fr[:, :, 0] = np.linspace(0.1, 1.0, nworld)[:, None]
m.geom_friction.assign(fr)            # write back into the SAME device array

    Pitfall: replacing after capture

    A captured graph stores the pointers of the arrays it read. If you replace m.opt.gravity after capturing, the replay still reads the old array (checked on a CPU dev box with Warp 1.19 CPU capture: the replay ignored a replaced gravity, and used an assigned one). Replace before capture; after capture only write into arrays. Ch 24 has the full list of what a graph bakes in.

    3Simple DR first: fields with no derived constants

    Some fields are read directly by the kernels every step and nothing else is computed from them. Change them and you are done: gravity, timestep, fluid density and viscosity, friction, solref and solimp, joint damping, actuator gains and gears, colours. Mass and size are different (Section 5).

    Gravity and fluid density (opt arrays)

    Recall from Ch 6

    Ch 6 Example 6.8 (ex07_gravity_round_robin.py) replaced m.opt.gravity with wp.array([g, -g], dtype=wp.vec3): with 4 worlds the ball's vertical speed after 5 steps alternated [-0.0981, 0.0981, -0.0981, 0.0981].

    Here is a field Ch 6 did not touch. m.opt.density is the density of the medium the scene sits in. With it, MuJoCo's inertia-box fluid model replaces each body by the box with the same inertia and applies a quadratic drag on each axis of the body's local inertia-box frame, F_i = -\tfrac12 \rho A_i |v_i| v_i, where A_i is the area of the face across that axis (A_x = b_y b_z and so on, with b the box dimensions; passive.py::_fluid_force). We give three worlds vacuum, air and water.

    The water world reaches its terminal speed of 1.808 m/s, exactly the value where drag balances weight. The vacuum world falls 4.95 m instead of the analytic 4.905 m because semi-implicit Euler with a 10 ms step overshoots a little (Ch 13).

    Pitfall: host flags that put_model derives from XML values

    put_model sets m.has_fluid = bool(mjm.opt.wind.any() or mjm.opt.density > 0 or mjm.opt.viscosity > 0) from the XML values (io.py::put_model), and the passive force pass skips the fluid kernel when it is False. The last line above shows the trap: with density="0" in the XML, the per-world density of 1000 is silently ignored. Put a non-zero density, viscosity or wind in the XML of any model you plan to randomize them on. Also note that the inertia-box model has no buoyancy term (passive.py::_fluid_force): it is drag and viscous resistance only.

    has_fluid is one case of a general rule: a few Python values are computed once from the XML values of fields that are themselves batchable, and code paths are switched on or off by them. In 4.0.1 (io.py):

    • m.has_fluid: wind, density or viscosity non-zero (the fluid kernel in passive.py).
    • m.has_tendon_stiffness: any tendon_stiffness or tendon_stiffnesspoly non-zero (put_model).
    • m.has_tendon_damping: any tendon_damping or tendon_dampingpoly, or the actuator_damping/actuator_dampingpoly of a tendon actuator, non-zero (put_model).
    • m.has_efm_actuator: an AFFINE gain or bias with a non-zero gainprm/biasprm entry 1 or 2, or a MUSCLE (also DCMOTOR, SO3) gain or bias (put_model). This flag and the two tendon flags decide whether derivative.py::eff_solve (used by the discrete integrator in 4.0.1) adds the tendon and actuator terms or takes the plain mass-matrix solve.
    • The default njmax_nnz of a sparse model (io.py::_default_njmax_nnz, called by make_data) counts one friction row per DOF and per tendon whose XML frictionloss is > 0.

    So the safe rule for all of these is: keep zero values zero and non-zero values non-zero when you randomize them, or put a small non-zero value in the XML so the flag is set.

    Timestep

    Timestep randomization is a cheap way to make a controller tolerant of control-rate jitter, but remember that the number of steps per second now differs between worlds: count episodes in simulated seconds (d.time), not in steps.

    Friction: the same box, sixteen floors

    Friction lives on geoms: geom_friction is (B, ngeom) of vec3 (sliding, torsional, rolling). A box on a 30 degree slope slides if the friction coefficient is below \tan 30^\circ = 0.577, and Coulomb's law predicts its distance after time t:

    s(t) = \tfrac12\, g\,(\sin\theta - \mu\cos\theta)\, t^2

    for \mu < \tan\theta, and s = 0 otherwise.

    The sliding worlds match Coulomb within 1 cm. The "stuck" worlds still move 4 to 22 mm: the box starts 1 mm above the plane and drops onto it, and MuJoCo's soft contacts allow a little creep, most where friction is closest to the threshold (world 13, mu = 0.58 against tan 30 = 0.577).     Pitfall: friction mixes with MAX

    Example 10.4 writes the same friction into the box and the slope. That is not decoration. When two geoms touch, collision_core.py::contact_material_params takes the element-wise maximum of their frictions (unless one geom has a higher priority). Randomize only the box's friction while the floor keeps its default 1.0, and every world sees 1.0. Section 10 has a widget for the full mixing rule.

    Actuator strength: gear and gain

    A motor's generalized force is \tau = \text{gear} \cdot \text{gain} \cdot \text{ctrl} (for a FIXED gain, gain = gainprm[0]). Both are "*" arrays. Randomizing them models motors and gearboxes that differ from unit to unit.

    Note where the two differ: d.actuator_force is the force before the gear, so a gain change shows up there and a gear change does not. Observations built from actuator_force (Ch 14) see the difference. The cart acceleration is \tau / M_\text{eff} with M_\text{eff} \approx 1.028 kg (cart plus the share of the pole it drags along). (Example numbers follow the example files, which other chapters cite, so 10.8 appears here, early: gains need no derived constants.)

    Colours (visual DR)

    Visual fields use the same mechanism. A snippet (the shapes were checked on CPU; Ch 27 renders the result):

    m = mjw.put_model(mjm, batch_sizes={"geom_rgba": nworld})   # (nworld, ngeom) vec4
rgba = m.geom_rgba.numpy()                                    # (nworld, ngeom, 4)
rgba[:, ball, :3] = np.random.default_rng(0).uniform(0, 1, (nworld, 3))
m.geom_rgba.assign(rgba)

    Note: camera intrinsics

    The batch renderer precomputes camera rays once by default. Its docstring says: "When using domain randomization for camera intrinsics, set to False" (render_util.py::create_render_context, argument use_precomputed_rays). Per-world cam_fovy is otherwise ignored. Ch 27 covers rendering.

    4What can vary, and what cannot

    Which fields have a "*"? You do not have to read types.py: put_model tags each such array with arr._is_batched = True (warp_util.py::mark_batched), so a loop over the dataclass fields finds them.

    The pattern behind the list: numeric parameters can vary, structure cannot. Every world runs the same kernels over the same index ranges, so anything that decides how many things exist, how they are connected or which code path runs must be shared.

    Batched does not mean "safe to randomize"

    A few "*" arrays are integer bookkeeping, not physics: actuator_historyadr and sensor_historyadr (addresses into the delay buffers, Ch 14), geom_dataid (which mesh a geom uses), geom_matid and mat_texid. They are batched so that advanced recipes can swap meshes or textures per world (Section 12, Ch 27), but random values in them index out of their tables. Treat them as "change only with a recipe".

    5Derived constants in plain language

    Some Model fields are not inputs at all. mj_setConst in the C compiler (and put_model, which copies the result) computes them from other fields, once, so that the simulation does not have to recompute them every step. If you change the inputs, these precomputed outputs go stale. Here is what each one means; Ch 11 and Ch 12 derive the quantities properly.

    The "invweight" quantities deserve one more sentence because they are the least obvious. MuJoCo makes every constraint (contact, limit, weld) soft. The softness is scaled by how heavy the things involved are, so that a contact on a 100 kg body and one on a 0.1 kg body behave alike. That scale is invweight0. If you make a body ten times heavier but keep its old invweight0, its contacts become ten times too stiff (or too soft, the other way round) relative to what MuJoCo intends. Nothing crashes. The physics is just quietly different from what the XML would produce.

    6set_const: recompute the derived constants on the device

    The function is mjw.set_const(m, d, groups=mjw.SetConstGroup.ALL, restore=True) (set_const.py::set_const). It needs d because the qpos0 groups run kinematics, and kinematics writes into Data. The docstring is the best reference there is, so here are its two tables, verbatim from the 4.0.1 wheel:

    Model fields that can be modified safely with set_const: ================================== ============================================== Field Notes ================================== ============================================== qpos0 body_mass, body_inertia, Mass and inertia are usually scaled together body_ipos, body_iquat since inertia is sum(m * r^2). body_pos, body_quat Unsafe for static bodies (invalidates BVH). dof_armature, tendon_armature actuator_armature, actuator_gear Actuator armature is added to joint and tendon armature. Not if changing from/to zero, since jnt_actuatorid and tendon_actuatorid are set by put_model. eq_data Connect anchors, marked weld poses. geom_size, hfield_size Bounds of primitive and height field geoms. cam_pos, cam_quat Camera pose in body frame. light_pos, light_dir Light position and direction in body frame. tendon_stiffness, tendon_damping Only if changing from/to zero. ================================== ==============================================
    For selective updates, pass SetConstGroup flags to groups: ==================== ================================================= Modified Field Groups ==================== ================================================= body_mass SetConstGroup.ALL geom_size SetConstGroup.FIXED (or ALL if tendon wraps geom) cam_pos, cam_quat SetConstGroup.KIN0 light_pos, light_dir SetConstGroup.KIN0 eq_data SetConstGroup.KIN0 body_inertia SetConstGroup.INERT0 dof_armature SetConstGroup.INERT0 qpos0 SetConstGroup.KIN0 | SetConstGroup.INERT0 ==================== =================================================

    Read the notes column carefully; each note is a real constraint:

    • body_pos/body_quat, unsafe for static bodies. Static bodies (welded to the world) are assumed never to move; the docstring warns that moving them invalidates the BVH, the bounding-volume hierarchy that the batch renderer and ray casts build over the scene (Ch 27).
    • actuator_armature/actuator_gear, not when changing from or to zero. The docstring gives the reason: jnt_actuatorid and tendon_actuatorid are set by put_model, so they describe the actuators as they were in the XML. Scaling a gear of 10 to 12 is fine; turning 0 into 5 is not.
    • tendon_stiffness/tendon_damping, "Only if changing from/to zero." That is the docstring's exact wording for this row, and it gives no reason. The reason is in io.py::put_model: it computes the host flags m.has_tendon_stiffness and m.has_tendon_damping from the XML values (has_tendon_damping also counts actuator_damping/actuator_dampingpoly on tendon actuators), and derivative.py::eff_solve skips the tendon terms when they are False. So zero must stay zero and non-zero must stay non-zero (the host-flag pitfall in Section 3 lists the other flags of this kind).

    The docstring also lists what set_const skips: actuator_length0 ("not in mjwarp"), dof_length, flexedge_length0, flexedge_invweight0 ("unbatched in mjwarp") and tendon_lengthspring ("SPRING group unsupported in mjwarp").

    Version note: wheel 4.0.1 vs dev tree 8f5b9f1

    In the 4.0.1 wheel _set_inertia0 loops on the host and calls smooth.solve_m once per DOF, six times per body, once per tendon and once per actuator. The dev tree replaces those loops with one smooth.inv_m call that computes the blocks of M^{-1} and reads them in single kernels; it also turns off the SLEEP enable flag on a copy of the model while it computes (the 4.0.1 wheel does not). Results are the same; only the cost differs.

    Deprecated aliases

    mjw.set_const_fixed(m, d) and mjw.set_const_0(m, d, restore=True) are still exported but emit a DeprecationWarning and carry # TODO(team): remove in future version. Use set_const(m, d, groups=SetConstGroup.FIXED) and set_const(m, d, groups=SetConstGroup.KIN0 | SetConstGroup.INERT0). Note that set_const_fixed calls set_const with restore=False. Example 10.7 shows the warning once.

    Per-world mass, done right

    For a single slide joint everything collapses to one number, 1/(m_\text{box} + m_\text{payload}), which makes the example a good test: actuator_acc0, dof_invweight0 and the actual acceleration under 1 N all agree, per world. Before set_const, body_subtreemass already had four rows (they were batched) but all four held the XML value 1.5.

    Pick the smallest group

    For friction or gains you need no set_const at all. For sizes, FIXED is cheap (no kinematics). Masses need ALL, the expensive one. For many worlds and big models, randomize mass at the start of a batch of episodes, not every reset.

    7The derived-field pitfall, and the fix

    Here is the single most common DR bug. You batch body_mass, call set_const, and everything looks fine. But the outputs of set_const still have batch size 1.

    Why world 0's value? Most set_const kernels size their launch by the output: _set_fixed launches _subtreemass with dim=(m.body_subtreemass.shape[0], m.nbody). With batch size 1 that is one world, world 0, which reads body_mass[0 % 4]. Every world then reads row worldid % 1 = 0. The same holds for body_invweight0, dof_invweight0, actuator_acc0, tendon_length0 and eq_data.

    Two groups of kernels are different. _set_bound (FIXED) launches over the largest batch size of geom_dataid, geom_size, geom_aabb and geom_rbound (np.max([...]) in set_const.py::_set_bound), and the camera and light pos0 kernels do the same over their three outputs only (not over cam_pos or light_pos), so they race only if those outputs have mixed batch sizes. So with geom_size batched and the bounds not, every world writes the one shared bounds row. That is a race: on CPU the last world wins (Example 10.7 shows world 2's radius), and on a GPU the winner is unspecified. Either way the bounds are wrong for the other worlds.

    The damage is subtle. qacc is right because crb reads body_mass directly. But smooth.py computes the subtree centre of mass as \sum_j m_j x_j / \text{body\_subtreemass}: with the stale denominator, world 3's box "centre of mass" is at x = 2.83 m although the box is at 0.5 m. Contacts on that box use world 0's body_invweight0, a muscle uses world 0's actuator_acc0. No error, no warning.

    The fix, as a rule

    For every input you randomize, batch the inputs and every output of the group that recomputes them, all with the same size:

    • mass: body_mass, body_inertia + body_subtreemass, body_invweight0, dof_invweight0, tendon_invweight0, actuator_acc0, and cam_poscom0, light_poscom0 if cameras or lights track a COM
    • size: geom_size + geom_rbound, geom_aabb
    • qpos0: qpos0 + every KIN0 and INERT0 output you use

    Sizes: the same rule, plus the broadphase

    Geometry sizes look like a "simple" field: the narrowphase reads geom_size[worldid % B] directly. But the broadphase first discards pairs whose bounding spheres or boxes cannot touch, and those bounds are the derived geom_rbound and geom_aabb.

    The second run is the instructive one. The 0.2 m ball's bounding sphere still says 0.1 m, so the plane-sphere broadphase filter believes the pair cannot touch until the ball's centre is about 0.1 m above the floor. The ball sinks halfway into the floor before any contact is generated, and rests at 0.108 instead of 0.1996. Too-large bounds (the 0.05 ball) are harmless, only slower; too-small bounds lose contacts.

    Run 2b is the more likely real mistake: you remember set_const(FIXED) but not the bounds. The shared row then holds 0.2, world 2's radius, not world 0's: _set_bound launched three worlds (the batch size of geom_size) and all three wrote row 0. On CPU the last one wins; on a GPU any of them may. Now the bounds are too large for worlds 0 and 1 (harmless) but would be too small in any world with a ball bigger than the winner's.

    Mass does not follow size

    MJWarp never recomputes body_mass or body_inertia from geom sizes: the compiler did that once from the XML density. A ball made twice as big per world keeps its XML mass. If you want constant density, scale body_mass by s^3 and body_inertia by s^5 yourself and call set_const with ALL.

    8set_length_range: actuator length ranges after DR

    Muscles (Ch 12) define their force-length curve over actuator_lengthrange, the range of lengths the actuator can reach. If you randomize the gear, or the joint or tendon range, that range must follow. mjw.set_length_range(m, d, index=-1) does this on the device (in 4.0.1 the index argument has no effect, see below). In 4.0.1 it is deliberately simple (set_const.py::set_length_range docstring): "For joint and tendon transmissions with limits, copies the range directly from jnt_range or tendon_range scaled by gear. Actuators without limits keep (0, 0)." There is no simulation-based computation like C MuJoCo's mj_setLengthRange.

    Three things to notice:

    1. The joint muscle's range scales with the gear per world, as intended.
    2. The tendon muscle had lengthrange="0 1" in the XML, but its tendon has no limits, so set_length_range overwrote it with (0, 0). Call it only when every actuator you care about has a limited joint or tendon. Passing index= does not help: in 4.0.1 the argument is accepted but ignored, because set_const.py::set_length_range launches over all nu actuators (index=1 still resets actuator 0 to (0, 0)). To keep some actuators, save their columns first: keep = m.actuator_lengthrange.numpy()[:, ids], call set_length_range, then write them back (lr = m.actuator_lengthrange.numpy(); lr[:, ids] = keep; m.actuator_lengthrange.assign(lr)).
    3. The C compiler's value (-0.2506) differs slightly from the plain copy (-0.25): the compiler ran its own simulation-based estimate, which MJWarp does not reproduce.

    Pitfall: batch actuator_lengthrange to nworld

    Unlike set_const, set_length_range launches dim=(d.nworld, m.nu) and its kernel writes actuator_lengthrange_out[worldid, actid] without the % batch wrap (set_const.py::_set_length_range). With the default batch size 1 and more than one world, worlds 1, 2, ... write past the end of the array. That is why Example 10.12 batches the output to NWORLD. Also recompute actuator_acc0 (group INERT0, batched) after a gear change if you use muscles.

    9m.opt arrays: replace, never batch_size

    m.opt.timestep, gravity, wind, density, viscosity, magnetic, the tolerances and impratio_invsqrt are "*" arrays too (Example 10.1 listed 12). But they live in the nested Option dataclass, and put_model only accepts top-level Model field names:

    The check in io.py::put_model is short: look the name up among the Model's array fields, require that its spec's first dimension is "*", require size ≥ 1. "opt.timestep" is not a Model field name; geom_type is a Model array but its spec starts with "ngeom"; nbody is an int. Because opt arrays can only be replaced, set them before you capture a graph, or keep a full-size array and write into it with .assign or a kernel afterwards.

    Tolerance is clamped

    put_model sets opt.tolerance = max(tolerance, 1e-6) because MuJoCo's default assumes float64. If you replace m.opt.tolerance per world, no clamp is applied to your values.

    10Contact materials per world

    Every contact carries its own friction, solref, solimp, condim and margin. They are not stored per contact in the Model: the narrowphase computes them when it writes the contact, from the two geoms' parameters, in collision_core.py::contact_params (which calls contact_margin_gap and contact_material_params). Every read uses the world:

    # collision_core.py::contact_material_params (4.0.1), geom branch, abridged
solmix_id = worldid % geom_solmix.shape[0]
friction_id = worldid % geom_friction.shape[0]
solref_id = worldid % geom_solref.shape[0]
...
max_geom_friction = wp.max(geom_friction[friction_id, g1], geom_friction[friction_id, g2])

    So geom_friction, geom_solref, geom_solimp, geom_solmix, geom_margin, geom_gap and geom_adhesion can all be randomized, and so can the explicit-pair versions (pair_friction, pair_solref, ...), which override the geom values when a <pair> exists. The mixing rule, the same as C MuJoCo's mj_contactParam:

    • If one geom has a higher geom_priority, its friction, condim and adhesion win outright.
    • Otherwise friction is the element-wise max, condim is the max, adhesion is the sum, and solref and solimp are blended with weight \text{mix} = \text{solmix}_1 / (\text{solmix}_1 + \text{solmix}_2) (solref is the element-wise min instead if either solref is non-standard, i.e. has a non-positive first entry).
    • Finally each friction entry is clamped to at least MJ_MINMU = 1e-5.

    11Re-randomize on the device at every episode reset

    Drawing values once is enough for a study. For training, every episode should see new values, and you do not want a host round trip (or a broken graph) at every reset. The answer is a small Warp kernel that writes new values into the batched arrays, driven by device arrays: a seed, a per-world episode counter, and the same reset mask that reset_data uses (Ch 8).

    The random numbers come from Warp's counter-based generator: wp.rand_init(seed, offset) makes a state, wp.randf(state, lo, hi) draws a float. Using offset = worldid * 7919 + episode * 104729 gives every (world, episode) its own stream, so the draw is reproducible from the seed and different every episode. Because every geom of one world uses the same offset, the box and the slope get the same friction, which sidesteps the max rule.

    Reset 2 only touched worlds 0 and 2, and only their episode counters advanced. The two graph replays drew new values because the seed is an array: the graph recorded its pointer, and seed.assign([11]) changed what lives there. If seed had been a Python int argument, its value would have been frozen into the graph at capture time and every replay would draw the same numbers. The function is now part of the running project as my_env.randomize(m, seed, episode, reset, lo, hi).

    Which fields are safe to re-draw inside a graph?

    Fields that need no derived recompute (friction, solref/solimp, damping, gear and gain, colours, gravity and density written in place) can be re-drawn in the captured episode-reset path. Mass, inertia, size and qpos0 need set_const. In a CPU-only check (Warp 1.19 CPU capture, mujoco-warp 4.0.1), set_const with FIXED and with ALL was captured, and replaying the graph after new masses and sizes were written in place gave the right subtree masses, actuator_acc0 and bounds. On a GPU it is unverified: INERT0 allocates arrays inside _set_inertia0 (capture then needs a memory pool) and records many launches per call in 4.0.1 (one solve per DOF, six per body, one per tendon and per actuator). Re-draw those eagerly, outside the graph, at the boundary between batches of episodes (Ch 30 follows this split).

    12Per-world geometry variants with MjSpec test helper, not public API

    Changing a sphere's radius is a size change. Giving world 3 a mug and world 4 a bowl is a shape change: a different mesh with a different number of vertices. Structure must be shared, so the trick is to build one superset model and choose per world which mesh each geom points at. geom_dataid (the mesh id of a mesh geom) is a "*" field, so it can differ per world.

    The library's own test helper io_test.py::per_world_mesh(spec, nworld) (shipped in the wheel, but a test, not an API) shows the full recipe:

    1. Describe variants in the MJCF with custom tuples: a geom-level tuple lists candidate meshes for one geom; a body-level tuple lists variant tuples, each a set of meshes for that body.
    2. Pad every body with extra mesh geoms (contype = conaffinity = 0) up to the largest variant's geom count, and recompile the MjSpec.
    3. Assign worlds to variants (_allocate_worlds, weighted by each candidate's tuple parameter) and fill a (nworld, ngeom) table of mesh ids; unused padded slots get -1 (disabled).
    4. Set m.geom_dataid = wp.array(dataid_table, dtype=int) (method 1, replace).
    5. Fill every dependent field per world from compiled variants (_populate_dependent_fields): geom_size, geom_rbound, geom_aabb, body_mass, inertias and so on. This is the "batch the derived outputs too" rule from Section 7, done by hand.

    Note

    Because this is a test helper, its name and its custom-tuple convention may change. Copy the pattern, not the import. The convex collision code reads the mesh of each geom through geom_dataid[worldid % B], which is why the table works without kernel changes.

    13Part II checkpoint project: "Robust slide"

    Time to put Part II together: batched worlds (Ch 6), resets and helpers (Ch 8), buffer sizing and overflow checks (Ch 9), and DR (this chapter). The question: for which frictions does a box reliably slide more than 0.5 m in one second, if the slope and the mass are uncertain?

    1. Randomize friction on the device with my_env.randomize, mass with batch_sizes + set_const (inputs and derived outputs batched), and the slope through a tilted gravity vector g = 9.81\,(\sin\theta, 0, -\cos\theta). For a box on an infinite plane this is the same physics as tilting the plane, and it keeps the geometry and the initial pose identical in every world.
    2. Size the buffers with a measurement rollout (the Ch 9 recipe): run with a generous budget, read d.nacon and d.nefc every 10 steps, then allocate 1.5 times the peak plus a small margin. d.nacon is the pooled total over all worlds (Ch 9), so the per-world contact budget is nconmax = ceil(1.5 * peak nacon / nworld) + 1; d.nefc is per world, so njmax = ceil(1.5 * peak nefc) + 4 rows.
    3. Run the study with the sized buffers and check d.overflow.

    The peak was 48 contacts over 16 worlds (3 per world on average, 4 while a box lies flat) and 16 constraint rows per world (4 contacts times 4 pyramid rows for condim 3). So nconmax = ceil(1.5 * 48 / 16) + 1 = 6 and njmax = ceil(1.5 * 16) + 4 = 28, and the sized run did not overflow. Every world obeyed the sliding criterion \mu < \tan\theta, and the distances match Coulomb's law within 11 mm. Mass made no systematic difference, as Coulomb friction predicts (both the driving force and the friction force scale with mass). That is a useful sanity check: a DR study should confirm the physics you expect before you trust it on the physics you do not know.

    Going deeper: what makes a DR study trustworthy

    Three habits. (1) Seed everything and print the seed: the numpy generator for host draws, the device seed array for randomize. (2) Check overflow every run, because a world that dropped contacts is not a sample of your distribution, it is a bug. (3) Compare against a closed form where one exists (here Coulomb), then extend to the cases where none exists (a robot foot on that slope). With 4096 worlds on a GPU the per-bin fractions become smooth curves; with 16 on a CPU they are only a smoke test.

    16Summary

    Key takeaways

    • Every "*" Model field (and the 12 m.opt arrays) can differ per world; kernels read row worldid % B, round robin.
    • Two methods: replace the array (the only way for m.opt.*), or allocate with put_model(batch_sizes=...) and edit in place (graph friendly).
    • Numeric parameters vary; sizes, topology, types, discrete options and host flags such as has_fluid are global.
    • Derived constants (subtree mass, invweight0, acc0, bounds, length0) are recomputed by set_const with the right group: mass ALL, size FIXED, inertia/armature INERT0, qpos0 KIN0|INERT0, cameras/lights/eq_data KIN0.
    • Batch the derived outputs too, or set_const writes one shared row: computed from world 0 for most outputs (camera/light references included, unless their three outputs have mixed batch sizes); the geom bounds are written by every world in a race because _set_bound's launch size includes geom_size.
    • Contact materials are mixed per contact with friction = max; set_length_range needs a per-world actuator_lengthrange and overwrites unlimited actuators with (0, 0).
    • Re-randomize with an in-place kernel driven by device arrays (seed, episode, mask); keep set_const outside the graph.
