Deleting a key can leave a node with too few keys. Watch the three repairs (borrow from a sibling, merge with a sibling, shrink at the root) and try to predict which one comes next.

This page belongs to Chapter 05: Deletion and rebalancing. The tree below is a B-tree of order M: every node holds at most M − 1 keys and, except the root, at least ⌈M/2⌉ − 1. Click a key button (or type a key from 0 to 999) to delete it. The key buttons always show the keys of the tree drawn below them. Every delete or insert, by button, by the key field or with Enter, is applied to the tree on screen, so all of them wait until the animation has reached its last step. Every frame is produced by a real JavaScript B-tree that follows the same rules as the chapter's Zig and Rust code: try the left sibling first, then the right one, otherwise merge.

Delete a key

What to look for

SituationRepair
The key is in a leaf that keeps enough keysNone.
The key is in an interior nodeOverwrite it with its predecessor (largest key of the left subtree), then delete that key from its leaf. The parent keeps all its keys.
A node is one key short and a direct sibling has a spare keyBorrow: the separator moves down, the sibling's nearest key moves up. The parent keeps all its keys, so the repair stops here.
A node is one key short and no direct sibling has a spare keyMerge: node + separator + sibling become one node. The parent loses a key, so it may be one key short now.
The root has no keys leftIts only child becomes the root: the tree is one level shorter.

Suggested experiments: play both scripted scenarios (they are parts 2 and 3 of the program output); switch to order 3, where every non-root node has exactly one or two keys and almost every delete needs a repair; then order 6, where repairs become rare. Tick Predict to be asked before each repair.
