Chapter 05

rte_ring: Lock-Free Queues Between Cores

Every time one DPDK core hands work to another, a ring is involved: mempools keep their free buffers in a ring, pipeline stages pass packets through rings, and the net_ring driver turns a ring into an Ethernet port. After this chapter you can create and use rings, explain exactly how two cores enqueue into the same ring without a lock, pick the right sync mode for your threads, and use the element, peek, zero-copy and staged-ordered variants.

  • Use element rings, the peek API and the zero-copy API, and know when the staged-ordered ring (SORING) is the better tool.

1Why DPDK needs its own queue

In ch3 you launched functions on several lcores. As soon as those lcores cooperate, one of them has to give work to another: an Rx core hands packets to a worker, the worker hands them to a Tx core, and every core returns used buffers to a shared pool. In a normal program you would use a queue protected by a mutex. At 10 to 100 million packets per second that does not work: taking and releasing a lock costs tens of nanoseconds even without contention, and if the thread holding the lock is descheduled, everyone else waits.

DPDK's answer is the rte_ring: a fixed-size, first-in first-out queue of pointers (or of small fixed-size elements) that several cores can use at the same time without a lock. Its design comes from FreeBSD's buf_ring.h. Its properties are:

  • Fixed size, chosen at creation. Nothing is allocated on the data path.
  • FIFO: objects come out in the order they went in.
  • Pointers, not data: a ring of mbufs moves 8-byte pointers. The packets themselves never move (ch7).
  • Lockless: producers coordinate with one atomic compare-and-swap per call, not per object.
  • Batched: one call can move 32 objects for little more than the cost of one. You will measure this.
  • Named: the ring lives in a memzone called RG_<name> (ch4), so another part of the program, or a secondary process (ch16), can find it with rte_ring_lookup().

2Your first ring: create, inspect, free

The ring API is declared in lib/ring/rte_ring.h (pointer rings) and lib/ring/rte_ring_elem.h (element rings). Most functions are static inline: the fast path is compiled into your program, with no function call into the library.

struct rte_ring *rte_ring_create(const char *name, unsigned int count,
                                 int socket_id, unsigned int flags);
void             rte_ring_free(struct rte_ring *r);
struct rte_ring *rte_ring_lookup(const char *name);
  • name must be unique. A second rte_ring_create() with the same name returns NULL with rte_errno = EEXIST.
  • count must be a power of two (up to 231), otherwise NULL and EINVAL. The usable capacity is count - 1: one slot always stays empty (section 5 explains why, and how RING_F_EXACT_SZ changes it).
  • socket_id is the NUMA node for the memory (SOCKET_ID_ANY or rte_socket_id()).
  • flags choose the default sync mode for each side (section 6). 0 means multi-producer, multi-consumer.

The status functions read the indexes and never block: rte_ring_count(), rte_ring_free_count(), rte_ring_full(), rte_ring_empty(), rte_ring_get_size(), rte_ring_get_capacity(), and rte_ring_dump(FILE *, r) for debugging. On a ring that other cores are using, their answers can be stale the moment they return; use them for statistics, not for decisions such as "the ring is not full, so my enqueue will succeed".

3Single, bulk and burst: three ways to call

Every enqueue and dequeue function name is built from three choices:

ChoiceOptionsMeaning
How many(none), _bulk, _burstOne object: returns 0 or -ENOBUFS (enqueue) / -ENOENT (dequeue). Bulk: exactly n or nothing, returns n or 0. Burst: as many as possible, returns 0..n.
Who(none), mp_/sp_, mc_/sc_No prefix: use the mode chosen by the flags at create time (recommended). A prefix forces a mode: rte_ring_sp_enqueue_burst() is only safe if you are the only producer.
What(none), _elemPointer ring (void * objects) or element ring (any size that is a multiple of 4 bytes; section 8).

So rte_ring_enqueue_burst(r, objs, n, &free_space) enqueues up to n pointers using the ring's default producer mode, and rte_ring_dequeue_bulk(r, objs, n, &available) dequeues exactly n or none. The last argument is optional (pass NULL): after the call it holds how much room (enqueue) or how many objects (dequeue) are left.

Use bulk when the objects belong together and a partial transfer would be harder to handle than a retry, for example when a mempool refills its per-core cache (ch6). Use burst on the packet path: take what is there, process it, come back. Try both on a 16-slot ring:

Pitfall: the two return conventions

Bulk and burst return a count (0 means failure for bulk). The single-object calls return 0 on success and a negative errno. Code such as if (rte_ring_enqueue_bulk(r, objs, n, NULL) < 0) never detects a failure, and if (!rte_ring_enqueue(r, obj)) treats success as failure.

Two lcores: a producer and a consumer

Part B of the same program is the shape of every ring user: the main lcore enqueues the numbers 1 to 8,000,000 (cast to void *: a pointer ring never dereferences what it carries) in bursts of 32; a worker lcore dequeues bursts and checks the order. When the ring is full the producer simply tries again; when it is empty the consumer calls rte_pause() and polls again. Neither ever sleeps.

code/ring_basics.c (consumer)C
static int
consumer(void *arg __rte_unused)
{
    void *burst[BURST];
    uint64_t expect = 1;

    while (cres.received < N_OBJS) {
        /* Burst: take whatever is there, up to BURST. */
        unsigned int n = rte_ring_dequeue_burst(pipe_ring, burst,
                            BURST, NULL);
        if (n == 0) {
            cres.empty_polls++;
            rte_pause();
            continue;
        }
        for (unsigned int i = 0; i < n; i++) {
            uint64_t v = P2U(burst[i]);
            if (v != expect)
                cres.out_of_order++;
            expect = v + 1;
            cres.sum += v;
        }
        cres.received += n;
    }
    return 0;
}

4Inside the ring: two heads and two tails

A struct rte_ring (in lib/ring/rte_ring_core.h) is a header followed directly by the slot table. The header has three parts, each on its own cache lines: the constant fields, the producer indexes and the consumer indexes. Keeping producer and consumer data apart means a producer core writing prod.head does not keep stealing the cache line that a consumer core is reading (that effect, false sharing, is covered in ch14).

Each side has two indexes. The head marks how far that side has reserved; the tail marks how far it has finished. Between head and tail are slots that some thread is busy writing (producer side) or reading (consumer side). An enqueue is three steps:

  1. Move the head: read prod.head and cons.tail, compute the free space, and advance prod.head by n. That reserves n slots.
  2. Copy the objects into the reserved slots.
  3. Move the tail: set prod.tail to the new head. Only now can consumers see the objects, because consumers compute what is available from prod.tail.

A dequeue is the mirror image with cons.head, prod.tail and cons.tail. With a single producer, step 1 is a plain store. With several, two producers may read the same head at the same time; they settle it with a compare-and-swap, and they must finish step 3 in the order they reserved. Atomics primer: just enough for rings (ch14 has the full story)

Compare-and-swap (CAS) is a single CPU instruction (lock cmpxchg on x86) that does, atomically: "if *p == expected, store desired and report success; otherwise copy the current *p into expected and report failure". Two cores can never both succeed in moving the head from 4 to 5. The loser gets the new value for free and retries. DPDK spells it rte_atomic_compare_exchange_strong_explicit(), a wrapper over C11 atomic_compare_exchange_strong_explicit().

Memory ordering. CPUs and compilers may reorder memory accesses that look independent. For a ring that would be fatal: if the store to prod.tail became visible before the store of the object into its slot, a consumer could read garbage. Two annotations prevent it:

  • a release store (to the tail) guarantees that every write before it in program order is visible to anyone who sees the new tail;
  • an acquire load (of the other side's tail) guarantees that reads after it in program order see everything the releasing thread wrote before its release.

A producer's release of prod.tail pairs with the consumer's acquire of prod.tail, and the consumer's release of cons.tail pairs with the producer's acquire of cons.tail. That is all the synchronisation a ring needs. DPDK 26.11 no longer has rte_smp_wmb()/rte_smp_rmb(): CPU-to-CPU ordering is written with rte_atomic_*_explicit(..., rte_memory_order_release/acquire) or rte_atomic_thread_fence().

And the tail update. In MP mode (single == 0) it first waits until the tail reaches this thread's old head, which is the "core 2 spins" step of the widget:

lib/ring/rte_ring_elem_pvt.hC
static __rte_always_inline void
__rte_ring_update_tail(struct rte_ring_headtail *ht, uint32_t old_val,
               uint32_t new_val, uint32_t single)
{
    /*
     * If there are other enqueues/dequeues in progress that preceded us,
     * we need to wait for them to complete
     */
    if (!single)
        rte_wait_until_equal_32((uint32_t *)(uintptr_t)&ht->tail, old_val,
            rte_memory_order_relaxed);

    /*
     * R0: Establishes a synchronizing edge with load-acquire of tail at A1.
     * Ensures that memory effects by this thread on ring elements array
     * is observed by a different thread of the other type.
     */
    rte_atomic_store_explicit(&ht->tail, new_val, rte_memory_order_release);

The whole enqueue is these three calls in a row (__rte_ring_do_enqueue_elem in the same file): __rte_ring_move_prod_head(), __rte_ring_enqueue_elems() (the copy, with wrap-around handled), __rte_ring_update_tail(). Notice that the CAS is done once per call, whatever n is. That is why bursts are cheap.

532-bit indexes that are never reset

A textbook circular buffer keeps its indexes between 0 and size-1 and wraps them by hand. DPDK does not. The four indexes are uint32_t values that only ever increase, overflowing from 4,294,967,295 back to 0. The slot is index & mask, where mask = size - 1; that is why size must be a power of two. Counting works because unsigned subtraction in C is modulo 232:

entries = prod_tail - cons_head;               /* what a consumer can take   */
free    = capacity + cons_tail - prod_head;    /* what a producer can add    */

Both stay correct when one index has wrapped and the other has not, as long as the distance between them never exceeds the size. And this is the reason for the empty slot: if the ring could hold size objects, "full" (prod - cons == size) and "empty" would be told apart only by the distance, and a capacity of size-1 keeps the arithmetic simple and branch-free. Tip: sizing a ring

Pass a power of two and accept capacity size-1, or pass RING_F_EXACT_SZ when the capacity itself must be exact (for example, "exactly as many entries as mbufs in my pool"). rte_ring_get_memsize(count) tells you the bytes needed if you want to place a ring in your own memory with rte_ring_init().

6Sync modes: SP/SC, MP/MC, RTS and HTS

The producer side and the consumer side each have a sync mode, chosen by flags at create time and reported by rte_ring_get_prod_sync_type() / rte_ring_get_cons_sync_type() as an enum rte_ring_sync_type. The two sides are independent: "many producers, one consumer" is RING_F_SC_DEQ alone.

Mode (enum value)FlagsHow the head and tail moveUse when
ST (1)RING_F_SP_ENQ / RING_F_SC_DEQPlain loads and stores, no CAS, no waiting.Exactly one thread on that side, ever.
MT (0, default)none32-bit CAS on head; then spin until the tail equals your old head; store tail.Several threads, each pinned to its own CPU (the normal DPDK setup).
MT_RTS (2)RING_F_MP_RTS_ENQ / RING_F_MC_RTS_DEQRelaxed tail sync: head and tail are 64-bit {pos, cnt} pairs, two 64-bit CAS per call. Why preemption hurts MP/MC

DPDK assumes each lcore owns a CPU. The MP/MC algorithm leans on that: a thread that has moved the head will finish its copy and its tail store within nanoseconds. But if the operating system deschedules it between step 1 and step 3, every producer that reserved after it has to wait for it at step 3, spinning on the tail for the rest of its own timeslice (milliseconds). The same applies to a thread that has reserved and is itself waiting: if it is preempted, everybody behind it waits too. This is the lock-waiter preemption problem, and RTS and HTS were added in DPDK 20.05 to avoid it:

  • RTS: nobody waits for a particular earlier thread, so producers that are not preempted keep completing operations (until head is htd_max ahead of tail). Their objects become visible to consumers once the preempted thread finishes.
  • HTS: a waiting thread has not reserved anything, so preempting a waiter blocks nobody. Only one operation is in flight at a time. If the thread inside the operation is preempted, the others still wait, exactly like a lock holder being preempted.

7Measuring the modes on this machine

ring_modes_bench.c creates a 1024-slot ring in each mode, runs it for a fixed 100 ms of TSC time, repeats every point 5 times and prints the median with min and max. A fixed time rather than a fixed number of objects matters for the overcommitted runs: with preempted MP/MC producers a fixed-count run could take minutes. Two workloads:

  • producer/consumer (default): every lcore but the last enqueues, the last lcore dequeues. SP/SC runs with one producer only, since an ST ring must not be shared.
  • symmetric (-- -s, the workload of DPDK's own app/test/test_ring_stress_impl.h): the ring starts half full and every lcore dequeues a burst and enqueues it back, so the ring never fills or empties and only synchronisation limits throughput.
code/ring_modes_bench.c (the two worker loops)C
static void
produce(void)
{
    wait_go();
    while (rte_rdtsc() < deadline) {
        /* Default call: dispatches on the sync mode set by the flags
         * at create time (SP, MP, RTS or HTS). */
        if (rte_ring_enqueue_burst(ring, objs, burst, NULL) == 0)
            rte_pause();
    }
    rte_atomic_fetch_add_explicit(&prod_done, 1, rte_memory_order_release);
}

static void
consume(void)
{
    void *out[MAX_BURST];
    uint64_t got = 0;

    wait_go();
    for (;;) {
        unsigned int n = rte_ring_dequeue_burst(ring, out, burst, NULL);
        got += n;
        if (n == 0) {
            if (rte_atomic_load_explicit(&prod_done,
                    rte_memory_order_acquire) == nprod &&
                rte_ring_empty(ring))
                break;
            rte_pause();
        }
    }
    consumed = got;
    rte_atomic_store_explicit(&cons_done, 1, rte_memory_order_release);
}

/* Symmetric worker: dequeue a batch, put it straight back. Bulk calls so
 * that what we take is exactly what we return. */
static void
both(void)
{
    void *tmp[MAX_BURST];
    uint64_t n_moved = 0;

    wait_go();
    while (rte_rdtsc() < deadline) {
        if (rte_ring_dequeue_bulk(ring, tmp, burst, NULL) == 0) {
            rte_pause();
            continue;
        }
        while (rte_ring_enqueue_bulk(ring, tmp, burst, NULL) == 0)
            rte_pause();
        n_moved += burst;
    }
    moved[rte_lcore_id()] = n_moved;
    rte_atomic_fetch_add_explicit(&sym_done, 1, rte_memory_order_release);
}

All lines use the default calls rte_ring_enqueue_burst()/rte_ring_dequeue_burst(), which dispatch on the sync type stored in the ring. That is the normal style: the ring's creator decides the mode once, and all users follow it. The explicit variants (rte_ring_mp_enqueue_burst(), rte_ring_sc_dequeue_burst(), rte_ring_mp_rts_enqueue_burst(), rte_ring_mc_hts_dequeue_burst(), ...) save one switch and are only correct if they match how the ring is really used.

What the numbers say (software-only, on a shared 4-core VM; your numbers will differ, the shape should not):

  1. Bursts dominate everything. In 3a, SP/SC goes from 304 cycles per object with burst 1 to 15 with burst 32: the fixed cost of a call (index loads, the cross-core cache-line transfer of the tail) is paid once per burst.
  2. SP/SC is the cheapest when you can guarantee one thread per side: 185 vs 116 Mobj/s for MP/MC at burst 32 in 3a, with the same single producer. The CAS is not free even when nobody competes.
  3. RTS and HTS cost a little more when every thread has its own CPU (3a, 3b): two 64-bit CAS instead of one 32-bit CAS. HTS's strong 3c result (120 vs 55 Mobj/s) comes from serialisation: with only one thread inside at a time there are fewer failed CAS and fewer cache-line ping-pongs. Do not generalise from one workload.
  4. Overcommitted, MP/MC collapses (3d): 40.6 Mobj/s with a min of 36 and a max of 120, the noisy signature of threads spinning away timeslices. RTS (287) and HTS (315) stay seven times faster.
  5. No sync mode fixes polling on a shared CPU (3e): with producers and consumer on one CPU the producer fills the ring in microseconds, then spins until the scheduler runs the consumer. About 1023 objects move per round of timeslices, whatever the mode, which is the 0.07-0.13 Mobj/s you see. A busy-polling DPDK thread must have a CPU to itself.
Warning: SP/SC is a promise

An ST side has no protection at all. Two threads enqueueing into an RING_F_SP_ENQ ring will both read the same head, both write the same slots and both store the same tail: objects are silently lost or duplicated. Nothing crashes, nothing logs. Use ST only when the code structure guarantees one thread per side, for example a ring owned by exactly one Rx lcore and one worker.

8Element rings, peek and zero-copy

Element rings: store values, not pointers

Sometimes the thing you want to pass is small: a flow ID and a length, a timer event, a (port, queue) pair. Allocating it and passing a pointer would add a mempool and a cache miss. An element ring stores the value itself:

struct rte_ring *rte_ring_create_elem(const char *name, unsigned int esize,
                                      unsigned int count, int socket_id, unsigned int flags);
unsigned int rte_ring_enqueue_burst_elem(struct rte_ring *r, const void *obj_table,
                                         unsigned int esize, unsigned int n, unsigned int *free_space);

esize must be a multiple of 4 bytes (8 and 16 have the fastest copy loops), and you pass the same esize to every *_elem call. A pointer ring is simply an element ring with esize = sizeof(void *); all of section 3 applies with an _elem suffix.

Peek: look before you take

The peek API in lib/ring/rte_ring_peek.h splits an operation in two. rte_ring_dequeue_bulk_elem_start() (or rte_ring_dequeue_bulk_start() for pointers) copies objects out and keeps the consumer side locked; then rte_ring_dequeue_elem_finish(r, k) / rte_ring_dequeue_finish(r, k) actually removes the first k of them (0 puts everything back). The enqueue side has rte_ring_enqueue_bulk_start(), which reserves space, and rte_ring_enqueue_finish(r, objs, n), which copies and publishes. Between start and finish no other thread can operate on that side, so peek is only available on ST or HTS sides; on an MP/MC side the start call returns 0 (and asserts in debug builds).

Zero-copy: write straight into the slots

The zero-copy API in lib/ring/rte_ring_peek_zc.h goes one step further: instead of copying from your array, rte_ring_enqueue_zc_burst_start() returns pointers into the ring's slot table in a struct rte_ring_zc_data { void *ptr1; void *ptr2; unsigned int n1; }. You write the objects there yourself (for example, let rte_eth_rx_burst() fill them directly) and call rte_ring_enqueue_zc_finish(r, n). Because the reserved region can run off the end of the table, it may come in two pieces:

code/elem_peek.c (peeking consumer)C
static int
peek_consumer(void *arg)
{
    struct taker *t = arg;
    struct item it;
    uint32_t last = 0;

    t->ordered = 1;
    while (t->taken < N_ITEMS / 2) {
        /* start: copies the head element into 'it', reserves it.
         * Until finish, no other consumer can dequeue from 'ring'. */
        if (rte_ring_dequeue_bulk_elem_start(ring, &it, ESZ, 1, NULL) == 0) {
            rte_pause();          /* ring empty */
            continue;
        }
        if (it.flow == t->flow) {
            rte_ring_dequeue_elem_finish(ring, 1);   /* take it */
            if (t->taken == 0)
                t->first_seq = it.len;
            else if (it.len <= last)
                t->ordered = 0;
            last = it.len;
            t->taken++;
            t->bytes += it.len;
        } else {
            rte_ring_dequeue_elem_finish(ring, 0);   /* leave it */
            t->put_back++;
            rte_pause();
        }
    }
    return 0;
}

9SORING: one ring, several ordered stages

A pipeline of three stages built from rings needs two rings and two copies of every pointer (exercise 2 builds one). If a stage runs on several threads, packets also get reordered, because a slow thread releases its batch late. The staged-ordered ring (lib/ring/rte_soring.h, added in 25.03, experimental) solves both: one ring, a producer, N stages and a consumer. Objects stay in their slot while each stage acquires a batch, works on it and releases it. Batches of one stage may be released in any order, but the next stage and the consumer only see objects in the original enqueue order. Typical users are IPsec-style pipelines where order must be kept (ch26); ch15 contrasts it with rte_reorder.

There is no rte_soring_create(): you fill a struct rte_soring_param (name, elems, elem_size, optional meta_size, stages, producer and consumer sync types), ask rte_soring_get_memsize(), allocate, and call rte_soring_init(). The data path is rte_soring_enqueue_bulk/burst(), rte_soring_acquire_bulk/burst(r, objs, stage, n, &ftoken, &avail), rte_soring_release(r, objs_or_NULL, stage, n, ftoken) and rte_soring_dequeue_bulk/burst(); the enqueux/acquirx/releasx/dequeux variants also carry per-object metadata. DPDK 26.07 added a peek-style rte_soring_dequeue_bulk_start()/_finish() for ST and HTS sides. soring_demo.c releases two batches of stage 0 in the wrong order on purpose:

Note: a ring can be a port

The net_ring driver (drivers/net/ring/rte_eth_ring.c, header rte_eth_ring.h) wraps rings in an ethdev: rte_eth_from_rings() makes a port whose Tx queue enqueues mbuf pointers into a ring and whose Rx queue dequeues them. ch8 uses it as a "ring cable" between two ports, and --vdev=net_ring0 creates one from the command line (ch9).

Common pitfalls

  • Objects silently lost or duplicated: an SP or SC ring used by two threads (for example, the ring was created SP/SC for an Rx lcore, and later a second Rx lcore was added). Create the ring MP/MC, or give each thread its own ring.
  • Bulk "never fails" or "always fails": mixing up the return conventions. Bulk/burst return a count; single-object calls return 0 or a negative errno.
  • A burst that drops objects: rte_ring_enqueue_burst() returned less than n and the caller ignored the rest. Either retry the remainder (as solutions/pipeline3.c does) or free/count them as drops. On the Tx side of a pipeline, forgetting this leaks mbufs.
  • rte_ring_create() returns NULL: EINVAL (count not a power of two without RING_F_EXACT_SZ, or esize not a multiple of 4), EEXIST (name already used, including by a previous run's secondary process, ch16), ENOSPC (no free memzone slot), ENOMEM. Print rte_strerror(rte_errno).
  • Creating rings from several threads at once: creation takes the EAL's tailq write lock and reserves a memzone; it is thread-safe but slow and not meant for the data path. Create all rings during initialisation, on the main lcore.
  • Peek on an MP/MC ring: the *_start() calls return 0 (assert in debug builds). Create the side as HTS or ST.
  • Collapse on a busy or virtual machine: more DPDK threads than CPUs, or an lcore list overlapping another busy process. Measure with the overcommit runs; use RTS/HTS where overcommit is unavoidable, and give polling threads their own CPUs.
  • Deciding from rte_ring_count(): the value is already stale when another core is active. Let the enqueue/dequeue call tell you what happened.

Summary
  • An rte_ring is a named, fixed-size, lock-free FIFO of pointers or of 4n-byte elements. Size is a power of two; capacity is size-1 unless you pass RING_F_EXACT_SZ.
  • Bulk moves all n or nothing; burst moves as many as possible; single-object calls return 0/-errno. Burst sizes of 8 to 32 cut the per-object cost by 10x or more.
  • Each side has a head (reserved) and a tail (finished). Enqueue = move head, copy, move tail with release; the other side reads the tail with acquire. MP heads move by CAS, and MP tails are published in reservation order.
  • Indexes are free-running uint32_t; slot = idx & mask; counts are unsigned differences that survive the 232 wrap.
  • SP/SC is fastest but only for one thread per side. MP/MC is right when each thread owns a CPU and collapses when threads are preempted; RTS and HTS are built for overcommitted systems. Polling threads still need their own CPUs.
  • Element rings carry small structs by value; peek (ST/HTS) lets you inspect before removing; zero-copy hands you pointers into the slots, possibly in two parts; SORING keeps order across multi-stage, multi-thread processing in a single ring.
