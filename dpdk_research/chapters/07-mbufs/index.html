Chapter 07

rte_mbuf: The Packet Buffer

Every packet a DPDK driver receives or sends is an rte_mbuf. After this chapter you can read its two cache lines field by field, move the data window with the helper functions, build chains, share data with clones and external buffers, set offload flags, add your own per-packet fields at run time, and tell who owns an mbuf at every moment.

1What an mbuf is

A NIC writes received bytes into memory by DMA, and reads bytes to send the same way. Software needs, next to those bytes, a little bookkeeping: where the data starts, how long it is, which port it came from, whether the NIC already verified the checksum, which buffer comes next if the packet did not fit in one. DPDK keeps both together in one object, the mbuf (message buffer, a name inherited from BSD).

The design decision that shapes everything else: metadata and data share a single mempool element. One rte_pktmbuf_alloc() gets both, one rte_pktmbuf_free() returns both, and they sit next to each other in memory. Each element of a pktmbuf pool holds, in order:

  1. struct rte_mbuf, exactly 128 bytes (two cache lines);
  2. an optional application private area of priv_size bytes;
  3. the data buffer of buf_len bytes, which starts with the headroom.

Every mbuf also stores a pointer to the pool it came from (m->pool), which is why freeing takes no pool argument. And an mbuf does not have to carry a packet: crypto operations, events and compression jobs (ch25-ch27) move data in mbufs too.

2The two cache lines

struct rte_mbuf is defined in lib/mbuf/rte_mbuf_core.h with __rte_cache_aligned, and its field order is a performance decision. On receive, a driver writes a handful of fields for every packet; on a 64-byte-line CPU it is far cheaper if they are all in one cache line. So:

  • Cache line 0 (bytes 0-63) holds everything the RX path needs: the buffer addresses, data_off, refcnt, nb_segs, port, ol_flags, packet_type, the lengths, VLAN, the RSS hash and pool. Two groups are laid out for single wide stores: the 8-byte rearm_data (data_off, refcnt, nb_segs, port), which a vector driver resets with one 64-bit write when it gives a buffer back to the NIC, and the 24-byte rx_descriptor_fields1 (packet type through buf_len), which it fills from the RX descriptor with one or two SIMD stores (ch23).
  • Cache line 1 (bytes 64-127) holds fields used on transmit or in slower paths: next (chains), the tx_offload bitfields, shinfo (external buffers), priv_size, timesync and 36 bytes of dynfield1 handed out at run time.

3Creating a pktmbuf pool

A pool of mbufs is an ordinary mempool (ch6) whose elements are initialised as mbufs. One call does it:

struct rte_mempool *
rte_pktmbuf_pool_create(const char *name, unsigned n,
        unsigned cache_size, uint16_t priv_size, uint16_t data_room_size,
        int socket_id);
  • n and cache_size mean exactly what they meant in ch6 (2q-1 elements is the most memory-efficient size).
  • priv_size is the private area per mbuf. It must be a multiple of RTE_MBUF_PRIV_ALIGN (8) or creation fails with EINVAL.
  • data_room_size is the size of the data buffer including the headroom. RTE_MBUF_DEFAULT_BUF_SIZE is 2048 + RTE_PKTMBUF_HEADROOM = 2176, so a default mbuf has 128 bytes of headroom and 2048 bytes for a frame. A pool for clones uses 0 (section 8).

Each element is sizeof(struct rte_mbuf) + priv_size + data_room_size bytes (2320 in our run). While creating the pool, rte_pktmbuf_init() runs once per element and writes the fields that never change: buf_addr, buf_iova, buf_len, pool, priv_size, refcnt = 1, nb_segs = 1. That is why allocation can be so cheap: rte_pktmbuf_alloc() is a mempool get plus rte_pktmbuf_reset(), which only resets the per-packet fields.

Pitfall: the data room includes the headroom

A pool created with data_room_size = 1518 to "fit a full frame" holds at most 1518 - 128 = 1390 bytes after the default headroom. A driver receiving a 1500-byte frame into it must scatter it over two mbufs or drop it (ch8). Size the room as headroom + largest frame, which is what RTE_MBUF_DEFAULT_BUF_SIZE does for 2048-byte frames.

4Headroom, data and tailroom

Inside the buffer, the packet occupies a window: it starts data_off bytes after buf_addr and is data_len bytes long. Everything before the window is headroom, everything after is tailroom. Packet processing is mostly moving the edges of that window, without copying the bytes in the middle:

Two lengths exist because packets can span several buffers (section 7): data_len is the bytes in this segment, pkt_len the sum over all segments, stored in the first one. For a single-segment packet they are equal, and every helper keeps them in step.

Why a headroom at all? Because protocol stacks build packets inside out. The payload is written first; then UDP, IP and Ethernet each prepend their header in front of what is there. With 128 bytes reserved in front, that is pointer arithmetic, not a copy. The same holds for encapsulation (adding a VLAN or a tunnel header) on a received packet.

	memset(head, 'H', 14);                  /* 14 bytes of "header" */
	show("prepend(14)", m);

	rte_pktmbuf_adj(m, 14);
	show("adj(14)", m);

	/* trim: drop bytes from the tail (cut a trailer). Returns 0 or -1. */
	rte_pktmbuf_trim(m, 10);

Warning: mtod does not check anything

rte_pktmbuf_mtod(m, struct foo *) is a cast of buf_addr + data_off. If the packet is shorter than struct foo, or the header continues in the next segment, you read past the data. Check data_len first, or use rte_pktmbuf_read() (section 7), which checks bounds and copes with segments.

5Building a payload, and the private area

Here is the "inside out" recipe with no network protocols yet (Ethernet/IP/UDP are ch10): a text payload is appended, then our own 8-byte application header is prepended in front of it. Multi-byte fields go in network byte order with rte_cpu_to_be_16/32. The header struct uses the 26.11 spelling for packed structs, struct __rte_packed_begin name { ... } __rte_packed_end; (the old __rte_packed attribute was removed).

The program also uses the private area: priv_size bytes between the mbuf and its buffer, reached with rte_mbuf_to_priv(m) (which is simply m + 1). It is for per-packet application data that must travel with the mbuf but never go on the wire: a creation timestamp, a flow id, a pointer to a session. Unlike the headroom, nothing in the library touches it.

	uint8_t  magic;        /* 0xD7 */
	uint8_t  version;      /* 1 */
	rte_be16_t length;     /* payload length, network order */
	rte_be32_t seq;        /* sequence number, network order */
} __rte_packed_end;

6Allocating and freeing, and the free-mbuf invariant

CallWhat it does
rte_pktmbuf_alloc(mp)One mbuf, reset: data_off = headroom, lengths 0, ol_flags 0, port invalid. NULL if the pool is empty.
rte_pktmbuf_alloc_bulk(mp, m[], n)All n or none: returns 0 or a negative errno. One mempool get for the whole array.
rte_pktmbuf_free(m)Drops one reference on every segment of the chain; segments that reach 0 go back to their own pool (m->pool). NULL is allowed.
rte_pktmbuf_free_bulk(m[], n)Same for an array, batching the pool puts per pool. NULL entries are allowed.
rte_pktmbuf_free_seg(m)Frees one segment only, without following next (section 13).
rte_mbuf_raw_alloc / rte_mbuf_raw_free (+ _bulk)Bare mempool get/put with no reset and no refcount logic. For drivers that keep the invariant themselves.

An mbuf sitting in its pool always satisfies the free-mbuf invariant: refcnt == 1, next == NULL, nb_segs == 1, and it is direct (not attached to another buffer). rte_pktmbuf_prefree_seg() restores those fields before an mbuf goes back, which is what lets alloc skip them. The raw functions do not, so they are only correct on mbufs you know are in that state, which in practice means inside a PMD.

Freeing also shows the payoff of m->pool: a packet received on one port from pool A and sent on another port is still returned to pool A, by whoever frees it.

7Chains: packets in several buffers

A packet larger than one buffer (a 9000-byte jumbo frame in 2 KB mbufs), or one assembled from parts (a header from one place, a payload from another), is a chain of mbufs linked through next. Each segment has its own buffer and its own data_off/data_len. The first segment is the packet: only it carries pkt_len, nb_segs, ol_flags, packet_type, port and the offload lengths; those fields in the other segments are ignored.

  • rte_pktmbuf_chain(head, tail) appends tail's segments to head, updating head->nb_segs and head->pkt_len. It returns -EOVERFLOW if nb_segs would exceed RTE_MBUF_MAX_NB_SEGS. After it, tail is no longer a packet of its own.
  • rte_pktmbuf_lastseg(m) walks to the last segment (append and trim work there).
  • rte_pktmbuf_is_contiguous(m) is true for a single segment.
  • rte_pktmbuf_read(m, off, len, buf) returns a pointer to len bytes at packet offset off: directly into the mbuf if they sit in one segment, otherwise after copying them into your buf; NULL if the range is past pkt_len.
  • rte_pktmbuf_linearize(m) copies all segments into the first one, if its tailroom is large enough, and frees the rest. 0 on success, -1 if it does not fit.
  • rte_pktmbuf_free(m) frees the whole chain.

8Reference counts, clones and copies

Sometimes several packets should carry the same bytes: multicast (one payload, a different header per receiver), mirroring a flow to a monitor port, keeping a packet for retransmission while it is also being sent. Copying 1500 bytes per receiver wastes memory bandwidth. Instead, mbufs can share a buffer.

Every mbuf has a 16-bit refcnt. rte_pktmbuf_free() does not really mean "free": it means "drop one reference". The mbuf goes back to its pool only when the count reaches 0. (When the count is 1, the common case, the free path skips the atomic operation entirely.)

rte_pktmbuf_clone(m, clone_pool) creates an indirect mbuf for each segment of m: a new struct rte_mbuf from clone_pool whose buf_addr/data_off/data_len point into m's buffer (it calls rte_pktmbuf_attach()), with the RTE_MBUF_F_INDIRECT flag set. The original, called the direct mbuf, gets refcnt + 1. Freeing a clone detaches it (rte_pktmbuf_detach()), which drops the direct mbuf's count, then returns the clone itself to its pool. Because a clone never uses its own buffer, its pool is created with data_room_size = 0: each element is just the 128-byte struct.

Clone or copy?

A clone is cheap but read-only by convention. Its bytes are the original's bytes, so writing into a clone changes the original and every other clone. Even rte_pktmbuf_prepend() on a clone writes into the shared headroom: two clones that each prepend a different header overwrite each other. (That is why the multicast pattern chains a separate header mbuf.) When you need private, writable bytes, use rte_pktmbuf_copy(m, pool, offset, length), which allocates new mbufs from a normal pool and copies the data (length = UINT32_MAX means "to the end"). Packet capture uses copy for exactly this reason (ch16). Exercise 2 demonstrates both effects with real output.

9External buffers

Sometimes packet data already lives somewhere that is not an mbuf pool: a guest's memory in vhost zero-copy (ch24), a big receive buffer that the NIC fills with many packets, a file mapped from disk. An mbuf can point at such memory with rte_pktmbuf_attach_extbuf(m, addr, iova, len, shinfo). Since the mbuf library does not own that memory, it needs two things from you, stored in a struct rte_mbuf_ext_shared_info: a reference count for the buffer, and a free_cb(addr, opaque) to call when the last reference is gone. rte_pktmbuf_ext_shinfo_init_helper() carves that struct out of the end of your buffer (shrinking the usable length) and fills it in.

Clones of an extbuf mbuf attach to the external buffer directly and increment the shinfo count, not the mbuf's; freeing the mbuf that carried it does not free the memory while clones exist.

10Offload flags, packet types and TX lengths

The 64-bit ol_flags word is the conversation between the application and the NIC driver. It holds three kinds of bits (all named RTE_MBUF_F_* since 21.11; the old PKT_* names are gone):

  • RX status bits (0-22), written by the driver: "the NIC checked the IP checksum and it is good", "hash.rss is valid", "a VLAN tag was stripped into vlan_tci". Some are 2-bit fields: the IP checksum status is UNKNOWN (neither bit), BAD, GOOD or NONE (both), so you test it with a mask: (m->ol_flags & RTE_MBUF_F_RX_IP_CKSUM_MASK) == RTE_MBUF_F_RX_IP_CKSUM_GOOD.
  • TX request bits (41-60), written by the application: "compute the IPv4 checksum", "segment this TCP packet", "insert vlan_tci". They only work if the port has the matching RTE_ETH_TX_OFFLOAD_* capability enabled (ch8, ch19), and they come with a contract: set l2_len/l3_len/l4_len in tx_offload, zero the IP checksum field, seed the L4 checksum with the pseudo-header sum.
  • Internal bits 61 (EXTERNAL) and 62 (INDIRECT), set by the library; and bits 23-40, which are not fixed at all but handed out at run time as dynamic flags (section 11).

NICs that parse headers report what they found in the 32-bit packet_type, built from 4-bit nibbles: L2 (bits 0-3), L3 (4-7), L4 (8-11), tunnel (12-15), then inner L2, L3, L4. 11Dynamic fields and flags

Before DPDK 20.11 the mbuf had fixed fields such as timestamp, seqn and userdata, used by a few libraries and wasting space for everyone else. They were replaced by a registry. The last 36 bytes of the struct (dynfield1) and the 18 ol_flags bits 23-40 are handed out at run time, by name:

  • rte_mbuf_dynfield_register(&(struct rte_mbuf_dynfield){ .name, .size, .align }) returns a byte offset inside struct rte_mbuf, or -1 with rte_errno (EEXIST if the name exists with other parameters, ENOENT if there is no room).
  • rte_mbuf_dynflag_register(&(struct rte_mbuf_dynflag){ .name }) returns a bit number in ol_flags.
  • RTE_MBUF_DYNFIELD(m, offset, type *) turns the offset into a typed pointer; rte_mbuf_dynfield_lookup() / rte_mbuf_dynflag_lookup() find an existing registration by name.
  • Registering the same name with the same parameters again returns the same offset, so independent modules can share a field. There is no unregister. Registrations are stored in shared memory, so secondary processes (ch16) see the primary's, but only a primary may register.
  • Names starting with rte_ are reserved for DPDK; well-known ones include rte_dynfield_timestamp, rte_flow_dynfield_metadata and the reorder library's sequence number.

The timestamp has helpers, because drivers and applications must agree on it: rte_mbuf_dyn_rx_timestamp_register(&offset, &rx_flag) registers the shared 8-byte field and an RX flag ("this mbuf has an RX timestamp"), and rte_mbuf_dyn_tx_timestamp_register(&offset, &tx_flag) the same field plus a TX flag ("send at this time"). ch19 (PTP and hardware timestamps) and ch22 (latency measurement) use them.

How does the TX driver give mbufs back? When the NIC reports descriptors done, the driver calls rte_pktmbuf_prefree_seg(m) on each transmitted segment. 14Debugging aids

mbuf bugs rarely crash where they happen. A double free puts the same pointer in the pool twice; a few microseconds later two different code paths get "their own" mbuf, which is the same memory. The library has three aids:

  • rte_mbuf_check(m, is_header, &reason) validates pool, addresses, refcnt, lengths and segment counts, returning a reason string. rte_mbuf_sanity_check() does the same but panics; with RTE_LIBRTE_MBUF_DEBUG defined at build time, the library itself calls it inside alloc, free, clone and the helpers.
  • rte_pktmbuf_dump() (sections 4-5) and rte_mempool_audit() (ch6).
  • mbuf history (new in 25.11): in a build with RTE_MBUF_HISTORY_DEBUG, each mbuf records its last 16 lifecycle events (alloc, RX, TX, free, plus your own marks via rte_mbuf_history_mark_bulk()) in a dynamic field. rte_mbuf_history_dump_all() writes them out and usertools/dpdk-mbuf-history-parser.py turns the dump into readable sequences and flags repeated events such as two frees in a row.

Common pitfalls

  • Touching an mbuf after tx_burst accepted it: the driver owns it and may already have freed it. Free only the unsent tail bufs[nb_tx..nb_rx-1].
  • Double free: no error, two owners later (section 14). Set pointers to NULL after freeing, and test with a RTE_LIBRTE_MBUF_DEBUG build.
  • Ignoring NULL from append/prepend/adj (or -1 from trim): the next write goes through a NULL pointer, or past the buffer.
  • Assuming one segment: mtod and data_len cover only the first segment. Use pkt_len for the packet length and rte_pktmbuf_read() for headers that may straddle segments.
  • Setting metadata on a non-first segment: ol_flags, pkt_len, nb_segs, packet_type are read from the head only.
  • Writing into a clone, including prepending: the bytes are shared with the original (exercise 2). Use rte_pktmbuf_copy() or a separate header mbuf.
  • Full-size pool for clones: a clone pool needs data_room_size = 0; otherwise each clone wastes 2 KB.
  • data_room_size without the headroom: the frame does not fit (section 3).
  • Unaligned private size: priv_size must be a multiple of 8, or pool creation fails with EINVAL.
  • Testing a 2-bit checksum status with &: m->ol_flags & RTE_MBUF_F_RX_IP_CKSUM_GOOD is also true for NONE. Mask first.
  • Setting TX offload flags the port did not enable: the NIC ignores them and sends wrong checksums (ch19).
  • Hard-coding a dynfield offset or flag bit, or trusting a dynfield without its flag: offsets differ between programs and fields survive reset.
  • Raw alloc/free on mbufs that break the invariant (refcnt not 1, chained, attached): pool corruption.
  • Freeing an external buffer yourself while mbufs still point at it: only the free_cb knows when the last reference is gone.

static int vlan_prepend(struct rte_mbuf *m, uint16_t vlan_id, uint8_t pcp)
{
	if (rte_pktmbuf_data_len(m) < 14)
		return -1;
	char *old = rte_pktmbuf_mtod(m, char *);
	char *new = rte_pktmbuf_prepend(m, 4);   /* NULL if headroom < 4 */
	if (new == NULL)
		return -1;
	memmove(new, old, 12);                   /* MACs go 4 bytes earlier */
	rte_be16_t tpid = rte_cpu_to_be_16(0x8100);
	rte_be16_t tci  = rte_cpu_to_be_16((uint16_t)(pcp << 13) | (vlan_id & 0x0fff));
	memcpy(new + 12, &tpid, 2);              /* the old type stays at +16 */
	memcpy(new + 14, &tci, 2);
	return 0;

Summary
  • An mbuf is one mempool element: a 128-byte struct rte_mbuf, an optional private area, and a buffer that starts with 128 bytes of headroom. m->pool lets anyone free it.
  • Cache line 0 holds everything the RX path writes (two groups designed for wide stores); cache line 1 holds TX, chain and dynamic-field data.
  • data_off and data_len define a window; append/prepend/adj/trim move its edges without copying and fail cleanly (NULL / -1) instead of clamping. mtod checks nothing.
  • Chains link segments through next; packet-wide metadata lives only in the head. rte_pktmbuf_read copies only when a range crosses segments.
  • free drops a reference. Clones share a direct mbuf's buffer and count there; external buffers count in their shinfo and call your free_cb. Clones are read-only; rte_pktmbuf_copy gives private bytes.
  • ol_flags carries RX status, TX requests (with the tx_offload lengths), internal bits and dynamic flags; packet_type carries the parsed layers.
  • Dynamic fields and flags are assigned by name at run time; store or look up the offset, and trust a field only with its flag. Timestamps have dedicated register helpers.
  • The pool handler comes from --mbuf-pool-ops-name, the platform, or ring_mp_mc; drivers return transmitted segments with prefree_seg + bulk put. Ownership passes at rx_burst and tx_burst; mbuf bugs are silent without the debug aids.
