Chapter 2

The Machine

Your program never reads "memory". It reads a cache line that may already be sitting next to the core, or may be a trip to DRAM away, and the code looks the same either way. On the machine this book was measured on, summing four million numbers stored in an array took 6.6 ms. Following the same numbers through a shuffled linked list took 580 ms. Nothing about the arithmetic changed. This chapter is about the hardware facts behind that gap, the ones every later chapter relies on, and about how to measure them without fooling yourself.

Chapter 1 argued that the data, not the code, is the problem. Here we put numbers on the hardware behind that: the latency table, cache lines, prefetchers, the TLB, bandwidth versus latency. Along the way we build the benchmark harness the rest of the book uses and run four experiments in Rust, Zig and Odin: an array against a linked list, a working-set sweep from 4 KiB to 512 MiB, four access orders over the same bytes, and a pointer chase split into independent chains.

The machine. Every number marked "measured" comes from an Amp orb: a KVM guest with 2 physical cores × 2 hyperthreads of an Intel Xeon (Ice Lake-SP) at a nominal 2.6 GHz. Per core: L1d 48 KiB and L2 1.25 MiB. L3 is 54 MiB, but it is shared with whatever else runs on the host. Lines are 64 B and pages 4 KiB, transparent huge pages are set to madvise, AVX-512 is present, and there are no hardware performance counters. In short: one 4-vCPU KVM guest on an Ice Lake Xeon. Its timings are noisy, so read ratios and shapes rather than exact nanoseconds. Every later chapter was measured on the same machine.

The latency ladder

Peter Norvig's table of operation timings, made famous by Jeff Dean[1], is best known from Jonas Bonér's gist, labelled "~2012"[2]. It gives an L1 cache reference as 0.5 ns, an L2 reference as 7 ns, a main-memory reference as 100 ns and reading 1 MB sequentially from memory as 250 µs. Google's current SRE handout revises these to 1, 4 and 100 ns, and sequential reads at about 100 GB/s[3]. A 2026 update by Omar Bohsali gives 1, 3, 15 and 80 ns for L1, L2, L3 and DDR5[4].

Measured numbers for current cores are in the table below[5]. An L1 hit costs a few cycles and a DRAM access costs hundreds: "70 ns of DRAM latency is nearly 400 cycles at 5.7 GHz, but only 210 cycles at 3 GHz"[6].

Two things have changed since the classic table. First, the 1 MB sequential read is now far faster than 250 µs: a single Zen 4 or Zen 5 core "can pull over 50 GB/s from DRAM, or well north of 100 GB/s from L3"[20], which is about 20 µs per MB. Second, DRAM latency in nanoseconds has barely moved. Chips and Cheese notes that the 9950X with DDR5-6000 "is just about able to match a Core i7-4770 with DDR3-1333"[5], a chip from 2013. Clocks went up while DRAM latency stayed at about 70–130 ns, so a cache miss costs more cycles now than it did when the classic table was written. Ulrich Drepper predicted this in 2007: "the limiting factor for most programs is now, and will be for some time, memory access"[8].

Before reading on: if one L1 hit took one second, how long would one DRAM access on this orb take?

Our sweep measured about 1.5 ns for an L1 hit and about 140 ns for a dependent DRAM load at 64 MiB, a ratio of roughly a hundred. So the DRAM access would take two or three minutes. A whole row of a table that misses on every access is a coffee break.

Cache lines: you pay per line, not per byte

Caches do not store bytes. They store lines: aligned blocks that are moved, cached and evicted as a unit. On every x86-64 CPU the line is 64 B. Drepper wrote in 2007: "In early caches these lines were 32 bytes long; now the norm is 64 bytes"[8]. AMD's Zen 5 guide states the consequence for alignment: a load that spans a 64-byte boundary "suffers, at minimum, a one cycle penalty"[7]. On this orb /sys/…/coherency_line_size reports 64.

The consequence for data layout is that reading one byte costs the same as reading the other 63 bytes of its line. Whether those other 63 bytes are useful is decided entirely by your data layout. Mike Acton's CppCon 2014 talk shows a loop that uses 4 of a line's 64 bytes and sums it up as "Waste 60 bytes / 64 bytes", "90% waste!"[28] (Chapter 1 walks through it). Igor Ostrovsky showed the flip side: touching every 16th int takes about as long as touching every one, because both touch every line[22].

The Apple 128-byte nuance

On Apple Silicon "64 bytes" is only half true. sysctl hw.cachelinesize returns 128 on an M1, and Apple's game-scheduling talk says "On Apple silicon, a cache line is 128 bytes long"[9]. Yet Wrenger et al. found that on Asahi Linux "getconf and the CTR_EL0 register … returns 64 B, which is also supported by our measurements"[10], and Apple's optimization guide, as quoted by jia.je, gives 64 B lines in L1D and 128 B in L2[11]. On x86, Rust's crossbeam_utils::CachePadded also aligns to 128 B, because "spatial prefetcher is now pulling pairs of 64-byte cache lines at a time"[12], and Zig's std.atomic.cache_line is 128 here too. So 64 B is the unit of fills and alignment, and 128 B the safe padding for data that cores fight over (Chapter 8).

Ask your own machine (reader commands; macOS also reports 16 KiB pages):

getconf LEVEL1_DCACHE_LINESIZE                              # Linux
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
sysctl hw.cachelinesize hw.pagesize                          # macOS

Lines live in sets

A cache is split into sets, each holding a few lines (its ways), and each address can live in only one set, chosen by the bits just above the line offset. Too many lines mapping to one set cause conflict misses (the reason power-of-two strides sometimes behave badly), and a working set that is simply too large causes capacity misses. the figure below is a toy cache small enough to watch. With LRU, a loop slightly too big evicts every line just before its reuse, which is why working-set curves have cliffs.

Measuring without fooling yourself

Before we measure anything, we need a harness we trust. Microbenchmarks fail in a few predictable ways, and the harness every chapter in this book copies (code/harness/, pasted verbatim between // ---- harness ---- markers) handles each of them:

  • Warm-up. The first run pays for page faults, cold caches and cold predictors, so the harness runs the function once and discards the time.
  • Median of 7. One run on a shared VM can double when a neighbour gets busy. The median ignores the three slowest and three fastest; the samples are printed too (Chapter 12 charts the spread).
  • Keep-alive. An unused result lets the optimizer delete the work. Every result goes through a "black box" the compiler must assume is read.
  • Checksums. Every variant must compute the same answer, which catches a variant that is fast because it is wrong. All three languages share one generator (splitmix64) and the same seeds, so they print identical checksums.
use std::hint::black_box;
use std::time::{Duration, Instant};

// …

/// Runs `f` once to warm up, then RUNS timed times. Returns the sorted timings.
fn bench_runs<R>(mut f: impl FnMut() -> R) -> [Duration; RUNS] {
    black_box(f());
    let mut t = [Duration::ZERO; RUNS];
    for slot in &mut t {
        let t0 = Instant::now();
        black_box(f());
        *slot = t0.elapsed();
    }
    t.sort_unstable();
    t
}
fn nowNs(io: Io) i96 {
    return Io.Clock.awake.now(io).nanoseconds;
}

/// Runs `f(ctx)` once to warm up, then RUNS timed times. Returns the sorted timings in ns.
fn benchRuns(io: Io, comptime f: anytype, ctx: anytype) [RUNS]u64 {
    std.mem.doNotOptimizeAway(f(ctx));
    var t: [RUNS]u64 = undefined;
    for (&t) |*slot| {
        const t0 = nowNs(io);
        std.mem.doNotOptimizeAway(f(ctx));
        slot.* = @intCast(nowNs(io) - t0);
    }
    std.mem.sort(u64, &t, {}, std.sort.asc(u64));
    return t;
}
// Odin has no black_box: a volatile store into a file-private global keeps results alive.
@(private = "file")
sink: u64

keep :: proc "contextless" (v: $T) where size_of(T) <= 8 {
	intrinsics.volatile_store((^T)(&sink), v)
}

// Runs f(ctx) once to warm up, then RUNS timed times. Returns the sorted timings.
bench_runs :: proc(f: proc(ctx: $C) -> u64, ctx: C) -> (t: [RUNS]time.Duration) {
	keep(f(ctx))
	for &d in t {
		t0 := time.tick_now()
		keep(f(ctx))
		d = time.tick_since(t0)
	}
	slice.sort(t[:])
	return
}

Rust has std::hint::black_box, an identity function the compiler is "encouraged to assume" can use its argument in any way. The docs add that it is only provided "on a 'best-effort' basis"[24]. Zig has std.mem.doNotOptimizeAway, which in its own words "tries to prevent the compiler from optimizing the computation away"[25]. Zig's timer is now Io.Clock.awake, and it needs the io that main receives. Odin has no black box at all. The idiom is an intrinsics.volatile_store into a file-private global. The optimizer may not remove a volatile store, so the value must be computed[26]. Odin times with the monotonic time.tick_now/tick_since. Rust benches any closure; Zig and Odin take a function plus a small context struct.

Zig 0.16 removed std.time.Timer and Instant. Clocks, like files and randomness, now hang off std.Io: Io.Clock.awake.now(io). Zig 0.17 renamed the optimization modes: -O ReleaseFast is now -O fast (the old flag is still accepted) and .ReleaseFast is .fast. std.lang.Optimize.ReleaseFast survives only as a deprecated declaration, so builtin.mode == .ReleaseFast no longer compiles; write .fast. Most Zig benchmark code online predates both changes.

The 0 ns benchmark. If a timing looks too good, suspect that the work was deleted: an unused sum or a computation folded at compile time shows up as nanoseconds. Keep-alive plus checksum is the defence. Chapter 12 comes back to this trap with an example.

Experiment 1: an array against a linked list

Here is the cleanest demonstration of why layout matters. Take 4·N 16-byte nodes, each with a value and a next index (indices instead of pointers keep the Rust version free of unsafe, and Chapter 5 argues they are better anyway). Sum the values three ways: as an array in memory order, as a list linked in memory order, and as a list linked in shuffled order. All three read exactly the same nodes and produce the same sum.

/// 16 bytes: 8 value + 4 next + 4 padding, so four nodes share a 64-byte line.
#[derive(Clone, Copy)]
struct Node {
    value: u64,
    next: u32,
}

// …

fn sum_list(nodes: &[Node], head: u32) -> u64 {
    let (mut s, mut i) = (0, head);
    while i != END {
        let n = nodes[i as usize];
        s += n.value;
        i = n.next; // the next address is only known when this load returns
    }
    s
}
/// 16 bytes: 8 value + 4 next + 4 padding, so four nodes share a 64-byte line.
const Node = struct { value: u64, next: u32 };

// …

fn sumList(l: List) u64 {
    var s: u64 = 0;
    var i = l.head;
    while (i != END) {
        const n = l.nodes[i];
        s += n.value;
        i = n.next; // the next address is only known when this load returns
    }
    return s;
}
// 16 bytes: 8 value + 4 next + 4 padding, so four nodes share a 64-byte line.
Node :: struct {
	value: u64,
	next:  u32,
}

// …

sum_list :: proc(l: List) -> (s: u64) {
	i := l.head
	for i != END {
		n := l.nodes[i]
		s += n.value
		i = n.next // the next address is only known when this load returns
	}
	return
}

The important line is the last one in the loop. The address of the next node is inside the current node, so the core cannot start the next load until the current one has returned. When the nodes are shuffled, almost every load is to a different line, and with 64 MiB of nodes almost every line comes from DRAM. the figure below steps through that with a model where a hit costs 1.5 ns and a miss 150 ns, round figures from the two ends of our own sweep.

Predict the three results at 64 MiB: array, in-order list, shuffled list. How far apart?

On this orb the array took about 1.6 ns per node, the in-order list about 3.0 ns and the shuffled list about 140 ns (Rust; Zig and Odin were within about a quarter). So the shuffled list was about 90× slower than the array, and the in-order list only about 2×.

The middle bar is the instructive one. A list whose nodes happen to be in memory order is only about twice as slow, because the addresses are sequential and the prefetcher already has the lines on their way. A freshly built list often looks like this; after an hour of inserts and deletes it becomes the third bar.

The array number, 1.6 ns per 16-byte node, is a bandwidth figure: on the order of 10 GB/s of reads from DRAM for one core running this loop. Experiment 3's sequential sum reaches a somewhat lower figure, so treat both as what these loops reached, not as the machine's bandwidth. Without next and padding it would move half the bytes; Chapter 3 is about that half.

Experiment 2: the working-set sweep

To see each cache level on its own, chase pointers through a buffer of a chosen size, from 4 KiB to 512 MiB, and plot the time per load. Two details make this measure latency and nothing else. First, one load per 64-byte line: only the first u32 of each line is used, so every hop is a new line. Second, the order is a single random cycle through all the lines, built with Sattolo's algorithm[23]. That is Fisher–Yates with the swap partner drawn from 0..i instead of 0..=i, which guarantees that following next from any line visits every line before coming back.

/// Sattolo's algorithm: like Fisher-Yates but j < i, never j == i. The result, read as
/// "next = p[i]", is ONE cycle through all n elements, so a chase can never get stuck in a short loop.
fn sattolo(n: usize, rng: &mut Rng) -> Vec<u32> {
    let mut p: Vec<u32> = (0..n as u32).collect();
    for i in (1..n).rev() {
        p.swap(i, rng.below(i));
    }
    p
}

// …

fn chase(buf: &[u32], hops: usize) -> u64 {
    let (mut s, mut i) = (0u64, 0usize);
    for _ in 0..hops {
        i = buf[i] as usize; // each load needs the previous one's result
        s += i as u64;
    }
    s
}
/// Sattolo's algorithm: like Fisher-Yates but j < i, never j == i. The result, read as
/// "next = p[i]", is ONE cycle through all n elements, so a chase can never get stuck in a short loop.
fn sattolo(gpa: Allocator, n: usize, rng: *Rng) ![]u32 {
    const p = try identity(gpa, n);
    var i = n - 1;
    while (i > 0) : (i -= 1) std.mem.swap(u32, &p[i], &p[rng.below(i)]);
    return p;
}

// …

fn chase(c: Chase) u64 {
    var s: u64 = 0;
    var i: usize = 0;
    for (0..c.hops) |_| {
        i = c.buf[i]; // each load needs the previous one's result
        s += i;
    }
    return s;
}
// Sattolo's algorithm: like Fisher-Yates but j < i, never j == i. The result, read as
// "next = p[i]", is ONE cycle through all n elements, so a chase can never get stuck in a short loop.
sattolo :: proc(n: int, r: ^Rng) -> []u32 {
	p := identity(n)
	for i := n - 1; i > 0; i -= 1 {
		slice.swap(p, i, rng_below(r, i))
	}
	return p
}

// …

chase :: proc(c: Chase) -> (s: u64) {
	i := 0
	for _ in 0 ..< c.hops {
		i = int(c.buf[i]) // each load needs the previous one's result
		s += u64(i)
	}
	return
}

Fisher–Yates is the wrong shuffle for a chase. A uniformly random permutation splits into several cycles, and the one containing your starting element can be short. A chase that starts there loops over a few kilobytes and reports L1 latency for a "512 MiB" buffer. Sattolo's one-character change (below(i) instead of below(i + 1)) rules that out. The program checks it, too: one trip of lines hops must sum to 16·(0 + 1 + … + lines−1).

Small buffers are walked many times, so that every size does at least 221 loads. The harness times the whole run, and the program divides each sample by the number of trips before printing BENCH. That way n is the number of lines and ns / n is the latency of one load:

Read the curve from left to right:

  • Up to 48 KiB: about 1.5 ns. That is L1, and it matches the L1d size exactly: the 48 KiB point is still flat and 64 KiB has already jumped. That is about 4 cycles at the nominal 2.6 GHz (or 5, the usually quoted Sunny Cove figure, at a ~3.3 GHz turbo; we cannot read the real clock inside this VM).
  • 64 KiB to about 1 MiB: about 4–8 ns. That is L2. It climbs gently past 256 KiB, the first hint of the TLB (see below).
  • 1.5 MiB to somewhere between 6 and 16 MiB: about 20–27 ns. That is L3. Every run is still at L3 latency at 6 MiB, and every run has reached DRAM by 16 MiB, far short of 54 MiB; where in between the step falls differs between the three runs.
  • Beyond that: about 130–200 ns. DRAM plus address translation. In Zig and Odin the cost keeps climbing toward 512 MiB (the TLB again); Rust's run stays roughly flat.

A host-shared L3 blurs the L3 → DRAM step. The 54 MiB that lscpu reports is the whole socket's L3. It is split into slices across the die and shared with the host's other tenants, so we see a usable L3 of roughly 6–8 MiB in our runs, and the edge moves from run to run. On a desktop the step lines up with the L3 size; on a cloud VM, do not infer the L3 size from a sweep. We also cannot separate "L3 miss" from "second-level TLB miss" at the L3 edge without performance counters, which this VM does not expose.

Prefetchers and the 4 KiB page boundary

If every DRAM access cost a full dependent-miss latency, the sequential array in Experiment 1 could not have run at 1.6 ns per node. It did, because the core does not wait to be asked. Intel's optimization manual describes several hardware prefetchers that guess the next line and fetch it early[13]:

  • the L1 streaming and stride prefetchers, which fetch the next line or detect "strides of up to 2K bytes";
  • the L2 spatial prefetcher, which "strives to complete every cache line fetched to the L2 cache with the pair line that completes it to a 128-byte aligned chunk" (this is crossbeam's reason for 128-byte padding);
  • the L2 streamer, which follows forward and backward streams, with one important limit: "Prefetched cache lines must be in the same 4K page."

The last limit exists because the next virtual page could be mapped anywhere or nowhere; the hardware cannot prefetch across pages because it "could initiate page table walks that are invalid"[8]. So a sequential stream has to retrain at every page boundary. A 2022 post on abertschi.ch confirmed the boundary experimentally on Coffee Lake[14].

With 200-cycle memory, 8 cycles of work per line and a prefetch distance of 16 lines, does sequential reading still stall after training?

Yes, a little. A line is requested 16 lines ahead, which is 16 × 8 = 128 cycles before it is needed, but it takes 200 cycles to arrive. So each line still waits about 72 cycles. Set the distance to 25 or more (200 ÷ 8) and the stalls after training disappear. Real streamers ramp their distance up when they see stalls for this reason.

Experiment 3: the same bytes in four orders

To see the prefetchers on real hardware, read the same 16·N u32s (64 MiB) and visit every element exactly once in different orders: sequential, at a 64 B stride (16 passes, each touching every line once), at a 4 KiB stride (1,024 passes, each load on a new page), and in random order through a shuffled index array. All four sum the same values, and the checksum confirms it.

/// Visits every element exactly once: `stride` passes, each touching every stride-th element.
fn sum_strided(a: &[u32], stride: usize) -> u64 {
    let mut s = 0;
    for off in 0..stride {
        s += a[off..].iter().step_by(stride).map(|&x| x as u64).sum::<u64>();
    }
    s
}
/// Visits every element exactly once: `stride` passes, each touching every stride-th element.
fn sumStrided(c: Strided) u64 {
    var s: u64 = 0;
    for (0..c.stride) |off| {
        var i = off;
        while (i < c.a.len) : (i += c.stride) s += c.a[i];
    }
    return s;
}
// Visits every element exactly once: `stride` passes, each touching every stride-th element.
sum_strided :: proc(c: Strided) -> (s: u64) {
	for off in 0 ..< c.stride {
		for i := off; i < len(c.a); i += c.stride {
			s += u64(c.a[i])
		}
	}
	return
}

Sequential is about 0.53 ns per element: every byte of every line is used. The 64 B stride is about 12× slower. Every line is fetched 16 times, once per pass: you pay per line. The 4 KiB stride costs about 1.9× the 64 B stride (Rust), since every load is on a new page: a TLB lookup per load and no stream within a page. In Rust and Zig it is even slower than random order. Random costs about 24× sequential. Yet at 12 ns per load it is still an order of magnitude faster than the dependent chase in Experiment 2 at the same size (140 ns). That gap is the subject of the next section.

TLB reach, and huge pages that are not used

Every load starts with a virtual address, and the page-number bits of that address have to be translated to a physical page. The TLB caches recent translations. When it misses, the core walks the page table, which on x86-64 is four levels deep, so a full walk can add up to four more dependent memory accesses[15]. The number that matters is the TLB's reach: entries × page size.

Cited: Chips and Cheese (Zen 4: "288 KB of memory with no latency overhead, or 12 MB with a slight 7-8 cycle penalty")[15]; jia.je (Zen 5: 96 and 4,096 entries, 4 cycles on an L1 DTLB hit and 11 on an L2 DTLB hit)[16]. Reach columns are entries × page size.

Our sweep shows this structure. The gentle climb inside L2, from 4.3 ns at 256 KiB to a little more at 512–768 KiB, starts just past 256 KiB, which is 64 entries × 4 KiB. That is consistent with a 64-entry L1 DTLB, the size usually reported for this core family (not verified for this exact part; without counters it is an inference from the shape). In Zig and Odin the DRAM region climbs further, to 180 ns and 200 ns at 512 MiB, probably because the page tables themselves leave the cache (Rust's run stays roughly flat, so the effect is small and noisy here): 512 MiB is 131,072 pages, 1 MiB of page-table entries. Without counters this is also an inference.

Huge pages fix this. One 2 MiB page has 512× the reach of a 4 KiB one. Linux can supply them transparently, but on this orb /sys/kernel/mm/transparent_hugepage/enabled reads always [madvise] never. In madvise mode the kernel only backs a region with huge pages if the program asks for it with madvise(MADV_HUGEPAGE)[17]. None of our programs asks (Rust's standard library has no call for it; Odin has linux.madvise(…, .HUGEPAGE) in core:sys/linux, but we did not use it), so every number here is a 4 KiB-page number. With THP set to always, the right half of the figure above would be lower and flatter.

Check your own settings, and (on a machine that has them) count the TLB misses directly. These are reader commands; this orb has no perf and no counters, so the book shows no output for them:

Bandwidth, latency and memory-level parallelism

Experiment 2 and Experiment 3 both did random loads into 64 MiB. The chase cost about 140 ns per load and the random sum about 12 ns. The difference is in the dependencies. In the chase the next address is the result of the current load; in the random sum the indices come from a sequentially read array, so the out-of-order core issues the next dozen loads together and waits for the group once. That is memory-level parallelism (MLP).

Latency and bandwidth are linked by Little's law: throughput = requests in flight ÷ latency. With one miss in flight and about 150 ns latency, a core moves 64 B per 150 ns, about 0.43 GB/s. With ten in flight it moves ten times that. Sequential code is fast because the prefetcher keeps many misses in flight, not because any miss got shorter. A pointer chase allows one, however much bandwidth the machine has.

Experiment 4: split the chase

We can measure MLP directly. Walk the same 64 MiB Sattolo cycle with K cursors spread evenly around it, advancing all K each round. The total number of loads is the same, and every line is still visited exactly once (the checksum is identical for every K), but within one round the K loads are independent.

/// K cursors spread evenly around the same cycle, advanced in lockstep. The K loads in one
/// round do not depend on each other, so the core can have K misses in flight at once.
fn chase_k<const K: usize>(buf: &[u32], starts: &[usize; K], hops_each: usize) -> u64 {
    let (mut cur, mut s) = (*starts, 0u64);
    for _ in 0..hops_each {
        for c in &mut cur {
            *c = buf[*c] as usize;
            s += *c as u64;
        }
    }
    s
}
/// K cursors spread evenly around the same cycle, advanced in lockstep. The K loads in one
/// round do not depend on each other, so the core can have K misses in flight at once.
fn chaseK(comptime K: usize) fn (Chains) u64 {
    return struct {
        fn run(c: Chains) u64 {
            var cur: [K]usize = c.starts[0..K].*;
            var s: u64 = 0;
            for (0..c.hops_each) |_| {
                inline for (&cur) |*p| {
                    p.* = c.buf[p.*];
                    s += p.*;
                }
            }
            return s;
        }
    }.run;
}
// K cursors spread evenly around the same cycle, advanced in lockstep. The K loads in one
// round do not depend on each other, so the core can have K misses in flight at once.
chase_k :: proc(c: Chains, $K: int) -> (s: u64) {
	cur: [K]int
	copy(cur[:], c.starts)
	for _ in 0 ..< c.hops_each {
		#unroll for j in 0 ..< K {
			cur[j] = int(c.buf[cur[j]])
			s += u64(cur[j])
		}
	}
	return
}

// The harness takes proc(ctx) -> u64, so each K gets a tiny wrapper.
chase_1 :: proc(c: Chains) -> u64 {return chase_k(c, 1)}
chase_2 :: proc(c: Chains) -> u64 {return chase_k(c, 2)}
chase_4 :: proc(c: Chains) -> u64 {return chase_k(c, 4)}
chase_8 :: proc(c: Chains) -> u64 {return chase_k(c, 8)}

K must be a compile-time constant so the cursors live in registers: a const generic in Rust, a function returning a function per comptime K with inline for in Zig, and a $K parameter with #unroll for in Odin (plus four small wrappers, because the harness wants a proc(ctx) -> u64).

Eight chains are about 7× faster than one, and the scaling is almost perfect. The random sum in Experiment 3, at 12 ns per load, corresponds to roughly ten or more overlapped misses. Past that, the core runs out of resources for tracking outstanding misses. The practical lesson for data layout: if you cannot avoid a miss, at least avoid making the next address depend on it. A list or pointer tree allows one miss in flight; an index array or a batch of independent lookups allows many.

Software prefetch, and Albrecht's PS3

In 2009 Tony Albrecht walked through a PS3 scene-tree update in "Pitfalls of Object Oriented Programming"[18]. Its profile counted "L2 Cache misses: 36,345 @ 400 cycles each ~= 4.54ms". Reordering memory took the update from 19.6 ms to 12.9 ms ("35% faster just by moving things around in memory!"). A linear traversal took it to 4.8 ms, and a software prefetch instruction, dcbt, issued ahead of use took it to 3.3 ms.

All three of our languages can issue the same hint. Rust exposes the x86 intrinsic _mm_prefetch[27], Zig has the builtin @prefetch with a std.lang.PrefetchOptions struct[25], and Odin has intrinsics.prefetch_read_data[26]. We added a prefetch 16 iterations ahead to the random sum:

/// Software prefetch hint (`prefetcht0`). Other targets get a no-op.
#[cfg(target_arch = "x86_64")]
fn prefetch(p: &u32) {
    use std::arch::x86_64::{_MM_HINT_T0, _mm_prefetch};
    // The check is a cached bit test, and always true: SSE is part of the x86_64 baseline.
    if is_x86_feature_detected!("sse") {
        // SAFETY: the CPU supports SSE (checked above), which is all `_mm_prefetch` requires.
        // A prefetch is only a hint: it never faults and does not change program behaviour.
        unsafe { _mm_prefetch::<_MM_HINT_T0>(std::ptr::from_ref(p).cast()) }
    }
}
#[cfg(not(target_arch = "x86_64"))]
fn prefetch(_: &u32) {}

// …

fn sum_gather_prefetch(a: &[u32], idx: &[u32]) -> u64 {
    let mut s = 0;
    for (k, &i) in idx.iter().enumerate() {
        if let Some(&ahead) = idx.get(k + PREFETCH_AHEAD) {
            prefetch(&a[ahead as usize]); // ask for a line we will need 16 iterations from now
        }
        s += a[i as usize] as u64;
    }
    s
}
fn sumGatherPrefetch(g: Gather) u64 {
    var s: u64 = 0;
    for (g.idx, 0..) |i, k| {
        if (k + PREFETCH_AHEAD < g.idx.len) {
            // ask for a line we will need 16 iterations from now (a no-op where unsupported)
            @prefetch(&g.a[g.idx[k + PREFETCH_AHEAD]], .{ .rw = .read, .locality = 3, .cache = .data });
        }
        s += g.a[i];
    }
    return s;
}
sum_gather_prefetch :: proc(g: Gather) -> (s: u64) {
	for i, k in g.idx {
		if k + PREFETCH_AHEAD < len(g.idx) {
			// ask for a line we will need 16 iterations from now (locality 3 = keep in all levels)
			intrinsics.prefetch_read_data(&g.a[g.idx[k + PREFETCH_AHEAD]], 3)
		}
		s += u64(g.a[i])
	}
	return
}

_mm_prefetch is a safe function marked #[target_feature(enable = "sse")], so since Rust 1.86 it is safe to call only from code that itself enables the feature. Otherwise the call needs unsafe, even though SSE is part of the x86-64 baseline: "the sse target feature being enabled in the build configuration does not remove the requirement". Zig's @prefetch and Odin's intrinsic are ordinary calls; Zig's builtin "has no effect on the behavior of the program".

And it did not help. The prefetching version measured about 1.0× the time of the plain random sum in Rust (within noise), 1.1× in Odin and 1.1× in Zig: no help, and in two languages a little slower. That is not a contradiction of Albrecht. An Ice Lake core is out of order: it already sees the next independent loads and issues them early, so the explicit hint only adds instructions and a second load of each index. Software prefetch pays off when the hardware cannot find the parallelism itself: in-order cores like the PS3's, or addresses known far earlier than the out-of-order window can see. It cannot replace the fix in the layout.

What a mispredicted branch costs

Memory is the big stall. Two smaller facts finish the picture: branches and vector width. When the branch predictor guesses wrong, the core throws away the work it started down the wrong path. Agner Fog puts the penalty at "approximately equal to the length of the pipeline", 15–25 cycles on current cores[19]. AMD's Zen 5 guide says 12–18, with a "common case penalty" of 15 cycles[7]. At this orb's clock that is roughly 5–7 ns, the same as an L2 hit and far below a DRAM miss. Albrecht's PS3 profile shows the proportion: 50,421 mispredicts cost about 0.36 ms and 36,345 L2 misses about 4.54 ms[18].

A mispredict is worth avoiding in a hot loop, but it is the smaller problem. Chapter 7 measures branchy against branchless code properly, including why the famous "sorted array is faster" demo often fails to reproduce on a modern compiler.

A 512-bit register holds 16 f32s, one cache line. If they are 16 consecutive x fields, one load fills it; if they are the x fields of 16 structs, the core must gather them from 16 places. Wider vectors make layout more important.

Worked example: a miss budget for one frame

Put the measured numbers together the way a game programmer would. A 60 Hz frame is 16.7 ms. On this orb a dependent DRAM miss costs about 150 ns; take 150 ns as a round figure, so a frame can afford about

16.7 ms ÷ 150 ns ≈ 111,000 dependent misses

and nothing else. Experiment 1's shuffled list of 4,194,304 nodes took 580 ms: dozens of frames. The same nodes as an array took 6.6 ms, under half a frame. Albrecht's PS3 spent 4.54 ms, over a quarter of a frame, on 36,345 misses for 11,111 objects. The two fixes from this chapter: make it a stream (1.6 ns per node instead of 140 ns), or, if the accesses must stay random, make them independent (eight chains: 20 ns per load instead of 150 ns).

Caveats

  • One VM, no counters. These timings came from one run per language on the shared guest described above, and every hardware explanation here is inferred from timing shapes and vendor documentation. A desktop has lower DRAM latency (about 70–80 ns), a usable L3 and often huge pages. Trust the shapes and ratios, not the nanoseconds.
  • Bounds checks differ. Rust and Odin check every index in these loops (Odin's -o:speed keeps them unless you add -no-bounds-check). Zig's -O fast drops safety checks. Next to a DRAM load the check is free; in the sequential loops it can matter a little. The three languages usually land within 10–40% of each other.
  • Models are models. The prefetch and chase figures teach the mechanism, not the cycle count.

Run the chapter's programs yourself (quick mode finishes in seconds; the full sizes take a minute or two per language and allocate up to 512 MiB):

cd code && ./run_all.sh ch02

cd ch02-the-machine/zig && zig run -O fast main.zig
cd ch02-the-machine && odin run odin -o:speed -vet -strict-style

A DRAM miss costs about a hundred times an L1 hit and the hardware hides it only when it can predict the next address, so lay data out as contiguous streams and, where you cannot, make the next address independent of the current load.

Exercises

A core has a 64-entry L1 DTLB and a 2,048-entry second-level TLB. What is the reach of each with 4 KiB pages, and with 2 MiB pages?

4 KiB pages: 64 × 4 KiB = 256 KiB and 2,048 × 4 KiB = 8 MiB. 2 MiB pages: 128 MiB and 4 GiB. That is why the gentle rise in our sweep begins just past 256 KiB, and why huge pages flatten the DRAM side of the curve.

Use Little's law. Assume DRAM latency is 140 ns and a core can keep 12 line misses in flight. What is the best bandwidth a random gather of whole lines can reach? What does a pointer chase reach?

12 × 64 B ÷ 140 ns ≈ 5.5 GB/s for the gather. The chase has one miss in flight: 64 B ÷ 140 ns ≈ 0.46 GB/s, and it uses only 4 of each 64 bytes, so about 0.03 GB/s of useful data.

The in-order linked list was only about 2× slower than the array, but the shuffled one was about 90× slower. What does that tell you about benchmarking a linked list right after building it?

A fresh list is often in allocation order, so the prefetcher makes it look almost like an array. Inserts, deletes and allocator reuse later scatter it toward the shuffled bar. Benchmarking a fresh list measures the allocator's luck.

In the figure above, set the latency to 300 cycles. What prefetch distance hides it completely, and why does page 1 still start with two red stalls?

The distance needs to be at least latency ÷ work = 300 ÷ 8 ≈ 38 lines, more than the slider's 32, so some stall remains at any setting. Page 1 starts with two demand misses because the streamer does not cross the 4 KiB boundary. It must see two ascending accesses in the new page before it trains again.

Software prefetch cut about 30% of the time from Albrecht's PS3 code but did not help our random sum. Name two situations on an out-of-order x86 core where a software prefetch could still help.

First, when the addresses are known much further ahead than the out-of-order window can reach, for example item i+64 of an index array with hundreds of instructions in between. Second, batched lookups: in a hash join, prefetch the buckets for a whole batch of keys before probing any of them.

Predict, then measure: the same 64 MiB array read at a 128-byte stride (32 passes, each touching every other line). Is it cheaper or dearer than the 64 B stride, and what does Intel's spatial (pair-line) prefetcher have to do with it?

Each pass reads only half the lines, so without the pair-line prefetcher the total traffic would equal the 64 B stride's: every line from DRAM 16 times. But the L2 spatial prefetcher completes each fetched line with its 128-byte partner, so each pass drags in the whole array and the traffic doubles: up to about twice the 64 B stride's cost. Where the result lands between those bounds tells you how hard the pair prefetcher works on this machine. We did not measure it; this is a prediction to check.
