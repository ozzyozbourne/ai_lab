Memory: Hugepages, Memzones, rte_malloc and IOVA

Every packet buffer, ring and table in DPDK lives in memory that the EAL prepared before main() got control back. After this chapter you can say why that memory is special, choose the right memory options, allocate from it, explain the address a NIC uses to write into it, and read the error when rte_eal_init() refuses to start.

1Why a NIC cares where your buffer lives

In ch1's two-lane race the DPDK lane started with "NIC DMA": the network card copies an arriving frame into RAM by itself, without the CPU. To do that the card needs an address. The driver gives it one by writing it into a receive descriptor. The card then writes the frame to exactly that address and the program reads the frame through its own pointer.

Those two addresses are not the same kind of address. Your C pointer is a virtual address (VA): the CPU's memory management unit (MMU) translates it, page by page, into a physical address (PA) in RAM. The NIC does not use your page tables. It sees addresses on the PCIe bus, which DPDK calls IOVA (I/O virtual address). For the frame to show up behind your pointer, the IOVA in the descriptor must lead to the same physical bytes as your VA. Figure 1 is the picture to keep in mind for the whole chapter.

That one picture explains the three things DPDK demands from its memory, and the rest of the chapter takes them one at a time:

  • Fast to translate for the CPU: few, large pages, so the TLB covers all packet buffers (Section 2).
  • Pinned: the kernel must never move a page or swap it out while a device may write to it. Hugepages are never swapped (Sections 3 and 4).
  • Known to the device: DPDK records the IOVA of every page so a driver can put it into a descriptor (Section 8, and the external-memory deep dive).

2Pages, the TLB, and why 4 KB pages hurt

The MMU does not translate byte by byte; it translates pages. On x86-64 the normal page is 4 KB. To translate an address the CPU walks a four-level tree of page tables (PML4, PDPT, PD, PT): four dependent memory reads before it can even start loading your data. That would be far too slow for every load, so the CPU keeps recent translations in a small cache, the TLB (translation lookaside buffer). A TLB hit costs nothing extra; a miss costs a page walk.

The TLB holds a fixed number of entries, typically a few dozen in the first level and one or two thousand in the second. What matters is its reach: entries × page size. With 4 KB pages, 1536 entries reach 6 MB. A packet application touches far more than that: a pool of 16384 mbufs of 2 KB each is 32 MB, plus rings, tables and statistics. Accesses land on random packets, so most of them would miss. A 2 MB hugepage is one TLB entry for 512 times more memory and needs one level less to walk; a 1 GB page saves another level. Try it.

Measure it: one pointer chase, two page sizes

tlb_bench.c builds a single random cycle through a 64 MB buffer that touches one cache line in each 4 KB page, and follows it with dependent loads (pos = mem[pos]). The 16384 lines it touches are only 1 MB, so the data stays in the CPU caches; what changes between the two runs is the translation: 16384 pages with 4 KB pages, 32 with 2 MB pages. Each run does 5 rounds of 4 million loads and prints the median, minimum and maximum.

3Hugepages on Linux

Linux keeps hugepages in a separate pool that you reserve in advance. Pages in the pool are never swapped and never moved, which also gives us the "pinned" property from Section 1. The kernel exposes the pool in three places:

  • /proc/meminfo: HugePages_Total, HugePages_Free and Hugepagesize (the default size).
  • /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages (and -1048576kB for 1 GB): write a number here to reserve pages. Per NUMA node it is /sys/devices/system/node/nodeN/hugepages/....
  • A hugetlbfs mount, usually /dev/hugepages. Every file you create there is backed by hugepages. This is how DPDK gets hugepage memory that another process can map too.

Transparent hugepages are a different thing

AnonHugePages counts transparent hugepages (THP): the kernel may merge ordinary memory into 2 MB pages when it feels like it, and split or move them later. DPDK does not rely on THP, because "may" and "move" are exactly what a DMA buffer cannot accept.

4EAL memory options and the files they create

Chapter 3 treated memory options as boilerplate (--no-huge -m 64). Now we can read them properly. The EAL reads the hugepage pool at start-up, reserves a large window of virtual addresses, and maps pages into it as needed. The options decide how much it maps up front, where the backing comes from, and what it leaves on disk.

Things to notice. The default mode maps the shared config at 0x100000000, then the fbarrays (Section 12), then the hugepages from 0x100200000. --single-file-segments maps the same addresses from one file. --in-memory prints the harmless "No free 1048576 kB hugepages" notice because memfd could create 1 GB pages, and its pages start at 0x1140000000, after a 64 GB window reserved for the (empty) 1 GB list. A clean exit (rte_eal_cleanup()) removes the files. A kill -9 does not: 16 files and their 16 hugepages stay taken until someone deletes them.

Hygiene on shared machines

Always pass a unique --file-prefix. Two primaries with the same prefix collide: the second one fails to start (error E3 in Section 11). Leftover <prefix>map_* files of a dead process hold hugepages forever; delete them only after checking that no process with that prefix is alive (fuser /dev/hugepages/<prefix>map_*). If no secondary process will ever attach, --in-memory leaves nothing behind at all.

5The memory layer cake

Before the APIs, the big picture. Everything you allocate in DPDK sits on the same stack of layers (Figure 3). You will normally use only the top two: rte_malloc and memzones here, and later the libraries built on them (rings in ch5, mempools in ch6, mbufs in ch7).

Why not plain malloc()? Because its memory is 4 KB pages that the kernel may move, the device cannot be told its address, and another process cannot map it. rte_malloc is for set-up time, though: it takes a lock and searches free lists. On the packet path you allocate fixed-size objects from mempools (ch6) instead.

int main(int argc, char **argv)
{
	int ret = rte_eal_init(argc, argv);
	if (ret < 0) {
		fprintf(stderr, "rte_eal_init failed: %s\n", rte_strerror(rte_errno));
		return 1;
	}

	/* 1. What did EAL set up? */
	printf("IOVA mode        : %s\n", iova_mode_str(rte_eal_iova_mode()));
	printf("hugepages        : %s\n", rte_eal_has_hugepages() ? "yes" : "no (--no-huge, 4 KB pages)");
	printf("physical addrs   : %s\n", rte_eal_using_phys_addrs() ? "readable" : "not used");
	printf("mapped memory    : %" PRIu64 " MB\n", rte_eal_get_physmem_size() >> 20);
	printf("NUMA nodes       : %u (this lcore is on node %u)\n", rte_socket_count(), rte_socket_id());

	/* 2. Allocate a few buffers and look at them. */
	printf("\nheap of node 0:\n");
	heap_line("before");

	char *a = rte_malloc("demo", 100, 0);      /* align 0 = cache line (64 B) */
	char *b = rte_malloc("demo", 100, 4096);   /* page aligned */
	char *z = rte_zmalloc("demo", 1500, 0);    /* zeroed, like calloc */
	int  *c = rte_calloc("demo", 256, sizeof(int), 0);
	heap_line("after 4 allocations");

	printf("\nbuffers:\n");
	show("rte_malloc(100, 0)", a);
	show("rte_malloc(100, 4096)", b);
	show("rte_zmalloc(1500, 0)", z);
	show("rte_calloc(256, 4, 0)", c);

	/* rte_zmalloc really zeroes: check every byte. */
	int nonzero = 0;
	for (int i = 0; i < 1500; i++)
		nonzero += (z[i] != 0);
	printf("  zmalloc'd bytes that are not zero: %d\n", nonzero);

	/* rte_realloc may move the block, exactly like realloc(). */
	strcpy(a, "kept across realloc");
	char *a2 = rte_realloc(a, 64 * 1024, 0);
	show("rte_realloc(a, 64K, 0)", a2);
	printf("  content after realloc: \"%s\" (%s)\n", a2, a2 == a ? "same address" : "moved");
	a = a2;

	/* 3. Ask for memory on NUMA node 1. This VM has one node, so there is no
	 * heap for node 1. An explicit socket never falls back to another one. */
	printf("\nNUMA:\n");
	rte_errno = 0;
	void *remote = rte_malloc_socket("demo", 4096, 0, 1);
	if (remote == NULL)
		/* rte_malloc*() report failure only through NULL: rte_errno
		 * is left untouched (we zeroed it above, it is still 0). */
		printf("  rte_malloc_socket(..., socket 1) = NULL  rte_errno=%d (not set by rte_malloc)\n",
		       rte_errno);
	else    /* with --no-huge EAL treats every socket as SOCKET_ID_ANY */
		printf("  rte_malloc_socket(..., socket 1) = %p  (accepted: no-huge memory has no node)\n",
		       remote);
	void *any = rte_malloc_socket("demo", 4096, 0, SOCKET_ID_ANY);
	printf("  rte_malloc_socket(..., SOCKET_ID_ANY) = %p (ok, node %d)\n",
	       any, rte_socket_id());

	/* 4. Free everything with rte_free (never with free()). */
	rte_free(any);
	rte_free(remote);                           /* NULL is fine */
	rte_free(a);
	rte_free(b);
	rte_free(z);
	rte_free(c);
	rte_free(NULL);                             /* allowed, like free(NULL) */
	heap_line("after rte_free");

	rte_eal_cleanup();
	return 0;
}

What an allocation really costs

Exercise 1 measures it: on DPDK 26.11 for x86-64 each block carries a malloc_elem header of 128 bytes (two cache lines) in front of your data. 100 × rte_malloc(1024) uses 1152 bytes each. Many tiny allocations waste a lot; put them in one array or a mempool.

7Memzones: named memory

A memzone is a heap allocation with a name and a descriptor (struct rte_memzone: name, VA, IOVA, length, page size, socket, flags) stored in a table in shared memory. Anyone who knows the name can find it with rte_memzone_lookup(), including a secondary process (ch16). DPDK libraries use memzones for everything that must be found by name or that hardware touches: a ring's memory, a mempool's objects, a NIC queue's descriptor ring.

  • rte_memzone_reserve(name, len, socket, flags): cache-line aligned.
  • rte_memzone_reserve_aligned(..., align): power-of-two alignment.
  • rte_memzone_reserve_bounded(..., align, bound): the zone must not cross a multiple of bound (some devices can only DMA within, say, a 4 GB window).
  • Flags: RTE_MEMZONE_IOVA_CONTIG (contiguous for the device too, Section 8), page-size hints RTE_MEMZONE_2MB/_1GB and RTE_MEMZONE_SIZE_HINT_ONLY.
  • rte_memzone_lookup, rte_memzone_free, rte_memzone_walk, rte_memzone_dump.
  • The table has a fixed size, 2560 by default; rte_memzone_max_set(n) changes it, before rte_eal_init().

8IOVA: the address a device uses

Back to Figure 1. When a driver gives a NIC a buffer, it gives it the buffer's IOVA: rte_mem_virt2iova(va), or for an mbuf the precomputed buf_iova. The EAL works in one of three IOVA modes (rte_eal_iova_mode()):

  • PA: IOVA = physical address. EAL reads every page's physical address from /proc/self/pagemap, which needs root (CAP_SYS_ADMIN). Used with UIO drivers and with VFIO when there is no IOMMU.
  • VA: IOVA = your virtual address. This needs an IOMMU: the kernel's VFIO driver programs it so that the device's address 0x100400000 is translated to the right physical page, exactly like the MMU does for the CPU. It works without root and it is the recommended mode.
  • DC ("don't care"): what a bus reports when it has no preference; EAL then picks one of the two.

How EAL decides (lib/eal/linux/eal.c, "IOVA Mode Detection" in the programmer's guide): every bus reports a preference after scanning its devices. If they agree, that wins. If all say DC, EAL picks VA when physical addresses are not available or when IOMMU groups exist, and PA otherwise. --iova-mode overrides the choice. On this VM there is no IOMMU (/sys/kernel/iommu_groups is empty) and we run as root, so the default is PA; --no-huge has no physical addresses, so it is VA.

The contiguity trap, live

The CPU is happy with memory that is contiguous in VA: the page tables glue the pages together. A device that is given one start address and a length (a descriptor ring, a large DMA buffer) needs the range to be contiguous in IOVA. In VA mode, VA-contiguous is IOVA-contiguous. In PA mode it is contiguous only if the kernel happened to hand out physically adjacent pages in the same order. The widget uses the real pages from the memseg_walk run below.

Pitfall: rte_malloc memory is not IOVA-contiguous

A block from rte_malloc is only VA-contiguous. If a device will DMA across it as one range, reserve a memzone with RTE_MEMZONE_IOVA_CONTIG (that is what PMDs do for descriptor rings, ch23), or keep each DMA buffer inside one page, which is what mempools arrange for mbufs (ch6).

9NUMA: memory has a location

A server with two CPU sockets has two memory controllers. Each socket reaches its own RAM directly and the other socket's RAM over the inter-socket link (UPI on Intel, Infinity Fabric on AMD), which costs extra latency and shares limited bandwidth. A PCIe NIC is attached to one socket too. Linux calls each socket with its memory a NUMA node; DPDK calls it a socket, and new options say numa.

  • rte_socket_id(): the node of the calling lcore; rte_lcore_to_socket_id(lcore); rte_socket_count().
  • SOCKET_ID_ANY (-1): "any node, prefer mine". It falls back to other nodes if the local one is full.
  • An explicit socket id never falls back. That is deliberate (you asked for local memory) and it is the classic failure on servers where hugepages were reserved on node 0 only: hello_memory's rte_malloc_socket(..., 1) above returns NULL. Virtual devices may report SOCKET_ID_ANY from rte_eth_dev_socket_id(); handle -1.

This VM has one node, so we cannot measure remote access; the code in this course is written to be correct on two-socket machines anyway.

10Sidebar: on real hardware

What you do once on a real server (details in ch29)
  • Reserve hugepages at boot, before memory fragments: kernel command line default_hugepagesz=1G hugepagesz=1G hugepages=16 (1 GB pages can only be reserved reliably at boot), or for 2 MB pages dpdk-hugepages.py --setup 2G (reserve and mount) or -p 2M -r 2G after boot. Reserve per node with --node or the /sys/devices/system/node/nodeN/ files.
  • Mount hugetlbfs for each page size (mount -t hugetlbfs -o pagesize=1G none /dev/hugepages1G) and point EAL at it with --huge-dir if needed.
  • Turn the IOMMU on: intel_iommu=on or amd_iommu=on, usually with iommu=pt (pass-through for host devices, so only VFIO-bound devices pay for translation). Bind the NIC to vfio-pci (ch9 sidebar). EAL then picks VA mode and DPDK can run without root.
  • Raise limits for non-root users: RLIMIT_MEMLOCK and the number of open files (one fd per hugepage in the default mode; --single-file-segments helps).

None of this is done here: the VM has no IOMMU and no NIC that may be bound, so the chapter uses virtual devices and PA/VA as EAL selects them.

12Deep dive: inside DPDK memory

12.1 Memseg lists, memsegs and the VA window

At start-up EAL reserves one huge window of virtual addresses per memory type (page size × NUMA node), mapped PROT_NONE so that nothing else can use it. That is a memseg list: here one list of 32768 slots of 2 MB, 64 GB of VA. Reserving VA costs nothing; only pages that are actually mapped use memory. Each mapped page becomes a memseg (struct rte_memseg in rte_memory.h: addr, iova, len, socket_id, flags), kept in an fbarray: a fixed array plus a used-bitmap, stored in a shared file (/run/dpdk/<p>/fbarray_memseg-2048k-0-0) so secondary processes see the same table. 12.2 The malloc heap: split, merge, grow, shrink

Each heap (struct malloc_heap, lib/eal/common/malloc_heap.h) is a list of elements in address order. Every element starts with a struct malloc_elem header (malloc_elem.h): neighbour pointers, its memseg list, a state (FREE, BUSY or PAD) and its size. Free elements also sit on one of 13 free lists by size class (powers of 4 from 256 bytes: malloc_elem_free_list_index()). Allocation (malloc_elem_alloc() in malloc_elem.c) takes the new block from the end of a free element, so the free element only shrinks and keeps its place; if alignment leaves a gap in front too small to be a free element, the gap becomes a PAD header that points to the real one. Freeing merges with free neighbours, so two free elements are never adjacent, and whole pages that are free and not pinned by -m are unmapped. Step through it, predicting first.

12.3 Dynamic memory, events and validators

Since DPDK 18.05 memory is dynamic by default: the heap grows and shrinks at run time as Section 12.2 showed. Two hooks let you watch and control that (rte_memory.h):

  • rte_mem_event_callback_register(name, cb, arg): cb(RTE_MEM_EVENT_ALLOC|FREE, addr, len, arg) runs whenever pages are mapped or unmapped. Drivers that keep their own DMA tables use it. The callback runs with the memory hotplug lock held, so it must not allocate, free or walk memsegs (that deadlocks).
  • rte_mem_alloc_validator_register(name, cb, socket, limit): cb is asked before the heap grows past limit and can say no (-1). --numa-limit installs such a limit for you.

With --legacy-mem (or --no-huge) all memory is mapped once at start-up and never changes, so both registrations fail with ENOTSUP. Legacy mode has one advantage: it sorts pages by physical address, so large IOVA-contiguous zones work even in PA mode.

12.4 External memory and rte_dev_dma_map

Sometimes the buffers come from somewhere else: your own allocator, a file, GPU memory. DPDK has two ways to use such external memory (programmer's guide, "Support for Externally Allocated Memory"):

  1. An external heap: rte_malloc_heap_create(name), rte_malloc_heap_memory_add(name, va, len, iovas, n_pages, page_sz), then allocate with rte_malloc_socket(..., rte_malloc_heap_get_socket(name)), or create a mempool or ring on that socket id. DPDK manages the memory. Part C of heap_events above did this: socket id 256, the pointer inside our mmap, and RTE_BAD_IOVA because we gave no IOVA table, which means no device may DMA there.
  2. Registered memory: rte_extmem_register(va, len, iovas, n_pages, page_sz) only tells EAL that the pages exist (an external memseg list), so rte_mem_virt2memseg() and the drivers can find them. You manage the memory yourself.

Neither step tells a device anything. With an IOMMU, the device can only reach pages that were mapped for it, and EAL maps only its own pages. For external memory that is a second, explicit step: rte_dev_dma_map(dev, va, iova, len) (lib/eal/include/rte_dev.h). It checks that the device is probed, that the bus has a dma_map hook and that the memory was registered, then calls the bus. On PCI with VFIO that creates the IOMMU mapping. Since 26.11 the rte_vfio_* functions are internal, so this is the only public way (ch23). Our VM has no VFIO device, so extmem_dma.c runs it on three virtual devices and shows what the API checks.

Common pitfalls

  • Two programs, same (default) --file-prefix: "Cannot create lock on '/var/run/dpdk/rte/config'". Give each its own prefix, or use --in-memory.
  • Hugepages slowly disappear: crashed or killed programs left <prefix>map_* files (also --legacy-mem without --huge-unlink). Check with fuser, then delete them; prefer --in-memory or --huge-unlink.
  • Thinking -m is a limit: it is a pinned minimum; the heap can grow far past it (testpmd's default mbuf pool grows to hundreds of MB, which is why this course always passes --total-num-mbufs). Use --numa-limit for a cap.
  • A large DMA area from rte_malloc: only VA-contiguous. Use RTE_MEMZONE_IOVA_CONTIG; in PA mode even that can fail when memory is fragmented.
  • Reading rte_errno after rte_malloc: the allocator does not set it; NULL is the only signal.
  • An explicit socket id on a node without hugepages: NULL, no fallback. Use SOCKET_ID_ANY or reserve memory on that node; --no-huge hides the bug because it ignores sockets.
  • Mixing free() and rte_free(): heap corruption or a crash, sometimes much later.
  • rte_malloc on the fast path: a lock and a list search per packet. Use mempools (ch6).
  • Allocating inside a memory event callback: deadlock on the hotplug lock.
  • Benchmarking with --no-huge: Section 2 measured 3.7× more cycles per load on a page-hopping workload. Use hugepages for any number you publish.
  • PA mode as non-root: physical addresses are not readable, and init fails. On real hardware use VFIO with an IOMMU (VA mode).

Summary
  • A NIC writes packets to an IOVA; your code reads them through a VA. DPDK memory is pinned, translated cheaply (hugepages, measured 42 vs 11 cycles per load here) and recorded with its IOVA so drivers can hand it to devices.
  • Hugepages are reserved in a kernel pool and used through hugetlbfs files or memfd. -m pins a minimum, --numa-limit caps, --in-memory leaves nothing behind, --no-huge is for tests. A unique --file-prefix keeps processes apart.
  • rte_malloc and friends are libc-like, cache-line aligned, NUMA-aware, and for set-up time only; each block has a 128-byte header. Memzones are named heap blocks that anyone can look up.
  • IOVA mode is PA (physical addresses, root, contiguity is luck) or VA (IOMMU, recommended). Ask for RTE_MEMZONE_IOVA_CONTIG when a device needs one range.
  • Explicit NUMA sockets never fall back; SOCKET_ID_ANY does. Put a port's memory on its node.
  • rte_eal_init() runs fixed phases; the log line tells you the phase, and the errno can mislead. Debug logging shows the detail.
  • Deep dive: memseg lists reserve VA, memsegs are pages in fbarrays, the heap splits from the end and merges on free, memory events and validators watch growth, and external memory needs rte_extmem_register and rte_dev_dma_map.
