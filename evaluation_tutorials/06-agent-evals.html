Chapter 6

Evaluating AI Agents

When WebArena was released, the best GPT-4 agent completed 14.41% of its self-hosted web tasks; humans completed 78.24%[1]. On OSWorld’s real virtual machines the gap was 12.24% against 72.36%[2], and on GAIA’s “conceptually simple” assistant questions GPT-4 with plugins scored 15% against 92% for people[3]. Even when agents succeed, they are erratic: on τ-bench’s retail domain, gpt-4o succeeded on fewer than half the tasks and solved under 25% of them in all eight of eight repeated attempts[4]. Progress is fast. METR estimates that the length of tasks frontier agents can finish half the time has doubled roughly every seven months since 2019, reaching about 50 minutes for Claude 3.7 Sonnet in March 2025[5]; by January 2026 it was several hours[6], and most of the release-time gaps above have since narrowed or closed. But the benchmarks behind such numbers break in embarrassing ways. An agent that returns empty responses scored 38% on τ-bench and beat a GPT-4o agent[7], and fixing the grader on CORE-Bench moved one model from 42% to 95%[8]. This chapter teaches you to evaluate agents as systems, honestly enough that such failures show up.

6.1Why agents need different evals

An agent in this book is an LLM in a loop. It receives an observation, chooses an action (a tool call, a shell command, a click, a message to a user), the environment changes, and the loop repeats until the agent stops or exhausts a budget. Chapter 1 introduced the vocabulary we keep using here. A task is a single test with inputs and success criteria; a trial is one attempt at it; a grader scores some aspect of the trial; the transcript is “the complete record of a trial”; and the outcome is “the final state in the environment at the end of the trial”[8]: not whether the agent said “your flight has been booked”, but whether the reservation row exists.

Two words that are easy to confuse also matter. The agent harness (or scaffold) is the code that turns a model into an agent: the prompt, the tool definitions, the loop, memory, retries. The evaluation harness is the code that “provides instructions and tools, runs tasks concurrently, records all the steps, grades outputs, and aggregates results”[8]. Figure 6.1 shows how they nest.

Agent evaluation differs from grading a single completion in five ways, and each one shows up later in the chapter as a technique[8]:

  1. The unit is a trajectory, not a completion. A trial can run for hundreds of steps; you can grade the end state, the path, or both (Sections 6.3 and 6.4).
  2. The thing under test is model plus harness. “When we evaluate ‘an agent,’ we’re evaluating the harness and the model working together”[8]. SWE-agent showed that the agent-computer interface changes success rates a lot[9]; CodeAct found that acting with executable code rather than JSON tool calls raised success by up to 20%[10]; HAL treats models, scaffolds and benchmarks as separate axes[11]. “62% on SWE-bench Verified” is meaningless without the scaffold.
  3. The environment is part of the instrument. Docker images, live websites, VMs and simulated users can be flaky, leak answers or drift: OSWorld’s Chrome tasks were underestimated by 28% after site changes broke its selectors[7].
  4. Results are stochastic and multi-dimensional. You need repeated trials and reliability metrics (Section 6.6), plus cost, latency and tokens (Section 6.7).
  5. Agents act, so they can cheat or cause harm. Agents have edited the tests that grade them and monkey-patched scorers[12]; AppWorld’s state-based tests explicitly check for “collateral damage”, unexpected changes to the world[13]; HAL found agents “misusing credit cards in flight booking tasks”[11]. Agents also read untrusted content: AgentDojo plants injected text in the environment and reports utility, utility under attack and attack success together[14]; AgentHarm covers direct misuse[15] (both in Chapter 8.7).

What, how and where

It helps to describe every agent eval along three independent axes. What is graded: the outcome (end state or final answer), the trajectory (steps, tool calls, policy compliance), efficiency (cost, tokens, latency, turns), reliability (pass^k, variance), and safety or side effects. How it is graded: code-based graders (unit tests, state or database hashes, AST matching, string matching, transcript statistics), model-based graders (LLM rubrics, agent judges) or humans. Where the agent runs: a repository with tests, a terminal container, simulated APIs with a database and a user, self-hosted websites, full VMs, live MCP servers or the live web. Two “web agent” benchmarks can sit in very different cells of this grid, which is usually where their numbers stop being comparable.

A chat eval item costs a fraction of a cent; a SWE-bench trial needs a per-repository Docker image, takes tens of minutes and can consume hundreds of thousands of tokens. HAL ran 21,730 rollouts across 9 models and 9 benchmarks for about $40,000[11]; RE-Bench compared agents with 71 eight-hour human expert attempts[16]. That cost shapes everything below.

Software engineering: from SWE-bench to Terminal-Bench

SWE-bench pairs 2,294 real GitHub issues from 12 Python repositories with the pull requests that fixed them[17]. The agent sees the issue and the repository before the fix and must produce a patch; the harness applies it in a per-repository Docker image and runs the tests the human pull request added or changed. Lite is a cheaper subset; Verified is a 500-instance subset that 93 professional developers screened for underspecified issues and invalid tests[18]; Multimodal moves to 617 JavaScript tasks with images, where SWE-agent solved 12%[20], a reminder that Python skill does not transfer for free.

Verified shows the life cycle of a benchmark: it went from about 40% to over 80% in a year[8], and in February 2026 OpenAI stopped evaluating it as “saturated due to test-design issues and contamination from public repositories”, recommending SWE-Bench Pro[19] (partially verified). The successors attack different weaknesses. SWE-Bench Pro has 1,865 problems from 41 repositories in public, held-out and commercial sets, with tasks that take a professional “hours to days”[23]; its headline pass@1 differs between versions, so cite the one you use. SWE-rebench mines fresh tasks continuously for a rolling, decontaminated set[22]. SWE-Lancer maps performance to money with 1,400+ Upwork tasks worth $1M[24].

Terminal-Bench 2.0 generalises to “do this job in a shell”: 89 hard tasks, each with “a unique environment, human-written solution, and comprehensive tests”, on which frontier agents score below 65%[25]. It ships through Harbor, which runs arbitrary agents (Claude Code, OpenHands, Codex CLI) in parallel cloud containers and doubles as an RL rollout generator[44]. To compare models, hold a simple scaffold fixed: Agentless, a non-agentic localise-repair-validate pipeline[45], or mini-SWE-agent, a “100 line AI agent” that scores above 74% on Verified[46]; SWE-bench’s “Bash Only” leaderboard exists for the same reason[17].

Tool use and conversational agents

The Berkeley Function Calling Leaderboard (BFCL), grown from Gorilla’s AST-based hallucination checks[47], covers simple, multiple, parallel and irrelevance (should not call) categories, then multi-turn stateful (V3) and agentic tasks (V4)[26]; its core grader parses each call and checks it structurally (Section 6.4). ToolLLM/ToolBench took the opposite route, an LLM-judged pass rate over live RapidAPI calls, and is the classic example of live APIs making results unstable[48].

τ-bench (Sierra) evaluates agents that talk to people and act for them: each domain has a database, API tools, a written policy and an LLM-simulated user with a hidden goal, and success compares “the database state at the end of a conversation with the annotated goal state”[4]. It introduced pass^k (Section 6.6). τ²-bench adds a telecom domain in which the user also has tools (dual control)[28]. AppWorld (nine apps, 457 APIs) grades code-writing agents with state-based tests that also check for collateral damage[13]; ToolSandbox adds stateful tools with implicit dependencies and milestone-based evaluation[29].

The Model Context Protocol (MCP) has become the common way to connect agents to tools, and MCP benchmarks evaluate against real, live servers. MCP-Universe uses 11 MCP servers across six domains and execution-based format, static and dynamic evaluators, the last “automatically retrieve real-time ground truth for temporally sensitive tasks”, so a correct answer about today’s stock price is not graded against last month’s; GPT-5 scored 43.72%[30]. MCPMark has 127 CRUD-heavy tasks, each with a curated initial state and a programmatic verification script; the best model, gpt-5-medium, reached 52.56% pass@1 but only 33.86% pass^4[31], a direct instance of Section 6.6. Both stress long contexts (input tokens grow with every step) and large, unfamiliar tool spaces.

Web, computer use and general assistants

WebArena made web-agent evaluation reproducible by self-hosting realistic sites and grading “functional correctness”: did the right order get placed[1]. VisualWebArena adds tasks that need vision[32]. Online-Mind2Web moved to 300 tasks on 136 live websites, found “over-optimism in previously reported results”, and graded with an LLM judge (WebJudge) that agrees with humans about 85% of the time[49] (judge validation: Chapter 4). OSWorld uses full VMs: each of 369 tasks has an initial-state configuration and “a custom execution-based evaluation script”[2]. Its July 2025 revision, OSWorld-Verified, fixed 300+ tasks[33]; scores on the two versions are not comparable, and as of late 2026 reported Verified scores sit near the 72.36% human baseline (exact figures conflict; check os-world.github.io). Windows Agent Arena adapts the OSWorld framework to 150+ Windows tasks[35]. AndroidWorld runs 116 tasks across 20 Android apps and generates task parameters at random, so one template yields endlessly many instances, a defence against memorisation; its robustness analysis shows that task variations change scores significantly[34].

GAIA asks 466 questions that are simple for humans but need browsing, files and multi-step reasoning, checked by quasi-exact match, with 300 answers held out[3]. BrowseComp has 1,266 questions whose answers are hard to find but short and easy to verify[36]; that design is the most useful idea in the family, because it allows cheap exact graders on a hard, open-ended task. BrowseComp-Plus freezes it into a fixed curated corpus with human-verified supporting documents and mined hard negatives, which makes results reproducible and turns the retriever into a separately reported, pinned component: GPT-5 scores 55.9% with BM25 and 70.1% with Qwen3-Embedding-8B, against 3.86% for Search-R1 with BM25[37].

Autonomy, R&D, security and real work

METR’s HCAST (189 tasks, 563 human baselines) calibrates difficulty by how long skilled humans take[38]. RE-Bench’s seven ML research-engineering environments show that “who is better” depends on budget: at 2 hours the best agents scored four times higher than human experts, at 32 hours humans scored twice as high[16]. MLE-bench grades 75 Kaggle competitions by their own medal thresholds[39]; PaperBench grades replications of 20 ICML papers with 8,316 author-co-written rubric leaves and a validated LLM judge[40]; Cybench uses 40 CTF tasks with human first-solve time as difficulty[41] (Chapter 8 treats these as dangerous-capability evals). Two benchmarks grade real work products by expert judgment. GDPval covers 44 occupations in the top 9 US GDP sectors, with tasks from professionals averaging 14 years’ experience; experts compare model and professional deliverables blind, and the best models are reported to be approaching expert quality[42]. The Remote Labor Index asks whether an AI deliverable for a real paid remote project would be accepted as the commissioned work; the best agent’s automation rate was 2.5%[43].

6.3Outcome-based grading

The most trustworthy agent graders ignore what the agent says and look at what it did to the world. This is outcome grading: run a check against the final environment state. The agent can reach the goal by any valid path, but the grade carries no partial signal and is exactly as good as the check. Four mechanisms cover almost every benchmark in Table 6.1:

Hidden tests: FAIL_TO_PASS and PASS_TO_PASS

SWE-bench partitions the repository’s tests into two sets for each instance. FAIL_TO_PASS (F2P) tests fail before the gold patch and pass after it: they check that the issue is fixed. PASS_TO_PASS (P2P) tests pass both before and after: they check that nothing else broke. An instance is resolved only if every F2P and every P2P test passes[17]. The harness computes the fraction of each and maps them to a status:

def get_resolution_status(report: dict[str, dict[str, Any]]) -> str:
    """
    Criteria:
        - If fail-to-pass (Resolution) = 1 and pass-to-pass (Maintenance) = 1 -> FULL
        - If (fail-to-pass (Resolution) < 1 and > 0) and pass-to-pass (Maintenance) = 1 -> PARTIAL
        - Otherwise -> NO
    """
    f2p = compute_fail_to_pass(report)
    p2p = compute_pass_to_pass(report)
    if f2p == 1 and p2p == 1:
        return ResolvedStatus.FULL.value
    elif f2p < 1 and f2p > 0 and p2p == 1:
        return ResolvedStatus.PARTIAL.value
    else:
        return ResolvedStatus.NO.value

Quoted from the SWE-bench harness. Only FULL counts as resolved on the leaderboard.

resolved(i) = 𝟙[ F2Pi = 1 ] · 𝟙[ P2Pi = 1 ],   resolve rate = Σi resolved(i)N (6.1) where F2Pi and P2Pi are the fractions of instance i’s fail-to-pass and pass-to-pass tests that pass after the agent’s patch, and N is the number of instances.

The grader’s weakness is built in: a patch “resolves” the issue if it satisfies these tests, written to accompany one fix. When SWE-bench+ audited the patches SWE-Agent + GPT-4 got credit for, 32.67% involved solution leakage (the fix was in the issue or its comments) and 31.08% were “suspicious patches due to weak test cases”; filtering both dropped the resolve rate from 12.47% to 3.97%[21]. Conversely, tests can demand one implementation detail and reject a correct patch.

Tests pass, but would it be merged? In March 2026 METR had four maintainers of scikit-learn, Sphinx and pytest review 296 AI pull requests that passed the grader, against a baseline of 47 real merged human PRs (accepted only 68% of the time). Even relative to that baseline, roughly half of the test-passing PRs would not have been merged, about 24 points below the automated grade[50], extending METR’s earlier comparison of algorithmic and holistic scoring[51]. The remedies are extra graders beside the tests (Section 6.9), calibrated against maintainer-style review.

def run_tests(module_src: str, tests: dict[str, str]) -> dict[str, str]:
    """Run tests against module_src in a fresh temp dir and a separate interpreter."""
    with tempfile.TemporaryDirectory() as d:
        root = Path(d)
        (root / "repo.py").write_text(textwrap.dedent(module_src))
        (root / "tests.json").write_text(json.dumps(tests))
        (root / "runner.py").write_text(RUNNER)
        try:
            proc = subprocess.run([sys.executable, "-I", "runner.py"], cwd=root, capture_output=True,
                                  text=True, timeout=TIMEOUT_S)
            lines = proc.stdout.strip().splitlines()
            return json.loads(lines[-1]) if lines else {name: "ERROR" for name in tests}  # e.g. import failed
        except subprocess.TimeoutExpired:
            return {name: "TIMEOUT" for name in tests}


def resolution_status(f2p: dict[str, str], p2p: dict[str, str]) -> str:
    """Mirror of swebench.harness.grading.get_resolution_status."""
    f = sum(v == "PASSED" for v in f2p.values()) / len(f2p)
    p = sum(v == "PASSED" for v in p2p.values()) / len(p2p)
    if f == 1 and p == 1:
        return "FULL"
    if 0 < f < 1 and p == 1:
        return "PARTIAL"
    return "NO"

The hash is strict over the whole database (any extra write fails the trial); the output check is a lenient lower-cased substring. Now take a task the agent is supposed to refuse. The gold action list is empty, so the gold hash equals the initial hash, and an agent that does nothing produces exactly that hash. Unless the task also requires an output, doing nothing passes. ABC found that an empty-response agent “achieves a 38% success rate and outperforms a GPT-4o-based agent”; impossible tasks are 38% of the airline subset[7].

mini_taubench.py builds this in about 230 lines: a dict retail database, three tools, a three-rule policy, a scripted user who says “yes” to any confirmation, and three agents. Correct checks policy, confirms, then acts or refuses; sloppy never checks or asks and always claims success; do-nothing replies with an empty string. Two of the five tasks are impossible under the policy.

Execution scripts and answer matching

In OSWorld and WebArena each task ships a small program that inspects the final state: a spreadsheet cell, a file, the shop’s orders table, a page[2][1]. Such probes are brittle; ABC estimated that WebArena overestimates performance by 5.2% from string-matching issues[7]. Answer matching fails on format: a CORE-Bench task expected “96.12” and rejected “96.124991…”, and after the graders were fixed Opus 4.5 went from 42% to 95%[8]. Normalise answers, record the rules as part of the benchmark version, and for time-sensitive answers fetch the gold at grading time, as MCP-Universe’s dynamic evaluators do[30].

Every task needs a reference solution that passes all its graders and a null solution that fails them[8]; Harbor’s solution/solve.sh is run by an “Oracle” agent to prove solvability[44]. “A 0% pass rate across many trials (i.e. 0% pass@100) is most often a signal of a broken task, not an incapable agent”[8].

6.4Trajectory and tool-call grading

Outcome grading tells you whether the agent succeeded. Trajectory grading looks at how: which tools it called with which arguments, in what order, whether it followed policy, how far it got. Some requirements are about process (verify identity before changing an account); partial progress is a richer signal for debugging and, in Chapter 7, for training; and when outcomes are rare, a step-level view is the only way to see change. OpenAI defines trace grading as “assigning structured scores or labels to an agent’s trace—the end-to-end log of decisions, tool calls, and reasoning steps”[55].

The warning comes from practitioners. Anthropic: “There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. We’ve found this approach too rigid and results in overly brittle tests… it’s often better to grade what the agent produced, not the path it took.”[8] The rest of this section shows both sides.

Checking a single tool call: AST matching

The atom of a trajectory is one tool call. BFCL grades it structurally: parse the call, then check that the function name matches, that every required parameter is present, that there are no unexpected parameters, that each value has the right type, and that each value is in a list of acceptable answers[26]. Strings are normalised first:

    """
    This function standardizes the string by removing all the spaces, ",./-_*^" punctuation, and converting it to lowercase
    It will also convert all the single quotes to double quotes

BFCL’s simple_function_checker returns typed errors in a fixed order: wrong_func_name, missing_required, unexpected_param, type errors, value errors. A typed error beats a boolean: many hallucinated parameters means fix the tool schema; many wrong values means the model misread the request. BFCL V4 weights its overall score 40/30/10/10/10 (Agentic, Multi-Turn, Live, Non-Live, Hallucination)[27], while other project pages still call it unweighted, so state your aggregation (Chapter 2.8). BFCL excludes SQL from AST checks “due to the multiplicity of methods to construct SQL function calls achieving identical outcomes”[26]. Our version parses with Python’s ast (never eval model output) and checks a JSON schema plus acceptable values, where "" means “may be omitted”:

def parse_call(text: str) -> tuple[str, dict]:
    tree = ast.parse(text.strip(), mode="eval")
    call = tree.body
    if not isinstance(call, ast.Call) or not isinstance(call.func, ast.Name):
        raise ValueError("not a simple function call")
    if call.args:
        raise ValueError("positional arguments are not allowed")
    kwargs = {}
    for kw in call.keywords:
        try:
            kwargs[kw.arg] = ast.literal_eval(kw.value)
        except ValueError:
            raise ValueError(f"argument {kw.arg!r} is not a literal") from None
    return call.func.id, kwargs


def check(text: str, schema: dict = SCHEMA, possible: dict = POSSIBLE) -> Verdict:
    try:
        name, kwargs = parse_call(text)
    except SyntaxError:
        return Verdict(False, "parse_error", "SyntaxError: not valid Python")
    except ValueError as e:
        return Verdict(False, "parse_error", str(e))
    if name != schema["name"]:
        return Verdict(False, "wrong_func_name", f"{name!r} != {schema['name']!r}")
    props, required = schema["parameters"]["properties"], schema["parameters"]["required"]
    for p in required:
        if p not in kwargs:
            return Verdict(False, "missing_required", p)
    for p in kwargs:
        if p not in props:
            return Verdict(False, "unexpected_param", p)
    for p, v in kwargs.items():
        want = PY_TYPES[props[p]["type"]]
        if isinstance(v, bool) and want is not bool or not isinstance(v, want):
            return Verdict(False, "type_error", f"{p}={v!r} is not {props[p]['type']}")
    for p, v in kwargs.items():
        if "enum" in props[p] and v not in props[p]["enum"]:
            return Verdict(False, "value_error:enum", f"{p}={v!r} not in {props[p]['enum']}")
        ok = possible[p]
        if isinstance(v, str):
            hit = standardize_string(v) in {standardize_string(x) for x in ok if isinstance(x, str) and x}
        else:
            hit = v in ok
        if not hit:
            return Verdict(False, "value_error", f"{p}={v!r} not in {ok}")
    for p, ok in possible.items():                       # omitted params must be optional
        if p not in kwargs and "" not in ok:
            return Verdict(False, "missing_required", p)
    return Verdict(True)

Milestones and progress rate

Binary success throws away where the agent got to. ToolSandbox defines milestones as predicates over environment state, evaluated “over an arbitrary trajectory”[29]; AgentBoard proposes a “fine-grained progress rate metric”[57]; Cybench subtasks[41], TheAgentCompany checkpoints[58] and PaperBench rubric trees[40] give partial credit too. With ordered milestones m1, …, mM and states s1, …, sT along the trajectory:

progress = max { j : ∃ t1 ≤ … ≤ tj with mi(sti) true for all i ≤ j }M (6.2) the largest prefix of the milestone chain reached in order, as a fraction. ToolSandbox allows a DAG of milestones; a chain is the simplest case.

AgentBoard’s definition is looser: rt = max0 ≤ i ≤ t f(si, g), with f the fraction of subgoals state si satisfies[57], unordered. ToolSandbox also defines minefields, “events that must NOT occur”: any violation zeroes the trajectory’s score[29], the trajectory-level counterpart of AppWorld’s collateral-damage checks. milestones.py scores a “text Alice ‘running late’” task with three ordered milestones and simulates two agent versions:

    ("cellular on", lambda s: s["cellular"]),

    ("message sent", lambda s: ("+33-600-000-111", "running late") in s["sent"]),

def apply(state: State, action: tuple[str, str]) -> State:
    s = {**state, "sent": list(state["sent"])}
    name, arg = action
    if name == "set_cellular":
        s["cellular"] = arg == "on"
    elif name == "search_contacts":
        s["resolved_number"] = "+33-600-000-111" if arg == "Alice" else "+44-700-000-999"
    elif name == "send_message" and s["cellular"] and s.get("resolved_number"):
        s["sent"].append((s["resolved_number"], arg))
    return s


def progress(actions: list[tuple[str, str]]) -> tuple[float, int]:
    """Ordered milestone matching. Returns (progress rate, milestones reached)."""
    state: State = {"cellular": False, "sent": []}
    reached = 0
    for a in actions:
        state = apply(state, a)
        while reached < len(MILESTONES) and MILESTONES[reached][1](state):
            reached += 1
    return reached / len(MILESTONES), reached


def agentboard_progress(actions: list[tuple[str, str]]) -> float:
    """AgentBoard (arXiv:2401.13178, Sec. 2.2): best fraction of subgoals satisfied by any state so far."""
    state: State = {"cellular": False, "sent": []}
    best = 0.0
    for a in actions:
        state = apply(state, a)
        best = max(best, sum(m(state) for _, m in MILESTONES) / len(MILESTONES))
    return best


MINEFIELDS: list[Milestone] = [
    ("message to a wrong number", lambda s: any(num != "+33-600-000-111" for num, _ in s["sent"])),
]


def minefield_score(actions: list[tuple[str, str]]) -> tuple[float, bool]:
    """ToolSandbox-style: ordered progress, but 0 if any minefield is ever triggered."""
    state: State = {"cellular": False, "sent": []}
    hit = False
    for a in actions:
        state = apply(state, a)
        hit = hit or any(m(state) for _, m in MINEFIELDS)
    return (0.0 if hit else progress(actions)[0]), hit

Agent-as-a-Judge and when step checks go wrong

For open-ended deliverables neither tests nor milestones may exist. Agent-as-a-Judge lets a judge agent explore the workspace and trajectory, reading files and running code; on DevAI (55 tasks, 365 requirements) it beat LLM-as-a-Judge and was reported “as reliable as our human evaluation baseline”[59]. But an agent judge is itself a stochastic agent that confident transcripts can persuade. Step graders fail valid solutions on an equivalent order, an extra read, a synonym argument (“SF” vs “San Francisco”). As RL rewards they teach imitation of the reference path. Ask: would I fail a human employee who skipped this step? If not, grade the outcome.

6.5Simulated users and multi-turn evaluation

Many agents work with a person who changes the task as it unfolds: revealing information late, misremembering an order number, pushing back on a refusal. Logged conversations cannot capture this, because once the agent deviates, the logged user’s next turn no longer makes sense. ToolSandbox names the distinction: off-policy evaluation replays fixed dialog trajectories, while on-policy evaluation uses “a built-in user simulator supporting on-policy conversational evaluation” that responds to whatever the agent actually does[29].

Three designs

LLM user with a hidden goal (τ-bench). A language model gets a persona and an instruction (“exchange the blue shoes in order #W123 for size 9; you only know your zip code”) the agent never sees. Success is still graded on the final database[4]: the user is part of the environment, not the grader. Dual control (τ²-bench). In telecom the user also has tools (toggle airplane mode, reboot), “modeled as a Dec-POMDP”, with a simulator “constrained by tools and observable states”. Agents show “significant performance drops” from no-user to dual control, and the design separates reasoning errors from communication errors[28]. Simulated feedback (MINT). MINT measures improvement per extra turn of GPT-4-simulated feedback[61].

Is the simulator valid?

A user simulator is a measuring instrument with its own error rate. Its typical failures: goal leakage (reciting the whole instruction at once), drift and giving up (forgetting a constraint, leaving early), over-compliance (accepting whatever the agent proposes), extra variance, and same-family bias when simulator and agent share a model family (Chapter 4’s self-preference, moved into the environment). Lost in Simulation (January 2026) compared LLM-simulated users with real participants from the US, India, Kenya and Nigeria on τ-bench retail: with the agent fixed, success varied by up to 9 points depending on which LLM played the user; simulation underestimated performance on hard tasks, overestimated it on moderate ones, and was the worst proxy for speakers of AAVE and Indian English[62].

How much can a small simulator error rate move a score? user_sim_noise.py reuses mini_taubench.py, but its agents listen to the user instead of reading the hidden task. With probability ε per opportunity the simulator drops the reason or leaves instead of confirming. An audit replays each failure with a perfect simulator: if the deterministic agent then passes, the simulator caused it.

        self.task, self.eps, self.rng = task, eps, rng
        self.errors = 0

        t = self.task
        if t.request == "status":

        if self.rng.random() < self.eps:                 # drops a constraint
            self.errors += 1

        return f"Hi, please {t.request} order {t.order_id}. Reason: {t.reason}."

            if self.rng.random() < self.eps:             # ends the conversation early
                self.errors += 1
                return "bye"
            return "yes"
        return "ok, thanks"

6.6Reliability and statistics

An agent that books the right flight 70% of the time books the wrong flight for three customers in ten. For user-facing agents the question is not “can it ever do this?” but “will it do this every time?”. Derivations are in Chapter 2.5 and Chapter 5.9; here we apply them to agents.

pass@k and pass^k

Run n independent trials of each task and count the c successes. pass@k is the probability that at least one of k attempts succeeds; pass^k (read “pass-hat-k”; the paper typesets it as pass with a superscript k, and this book writes the ASCII form everywhere, as in Chapter 5.9), introduced by τ-bench, is the probability that all k attempts succeed[4][64].             c_per_task_id[result.task_id] += 1 if is_successful(result.reward) else 0
    pass_hat_ks: dict[int, float] = {}
    for k in range(1, num_trials + 1):
        sum_task_pass_hat_k = 0
        for c in c_per_task_id.values():
            sum_task_pass_hat_k += comb(c, k) / comb(num_trials, k)
        pass_hat_ks[k] = sum_task_pass_hat_k / len(c_per_task_id)

def pass_at_k(n: int, c: int, k: int) -> float:
    """Unbiased pass@k, numerically stable form from openai/human-eval."""
    if n - c < k:
        return 1.0
    return float(1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1)))


def pass_hat_k(n: int, c: int, k: int) -> float:
    """Unbiased pass^k as in sierra-research/tau-bench: P(all k of k draws succeed)."""
    return comb(c, k) / comb(n, k)


def mean_over_tasks(f, n: int, cs: list[int], k: int) -> float:
    return sum(f(n, c, k) for c in cs) / len(cs)

pass@k assumes something picks the successful attempt, an oracle you do not have in production. Report it only when your deployment has a verifier that selects among attempts; otherwise report pass@1 with a CI, plus pass^k for anything user-facing.

Long-horizon runs need distributions, not means. Vending-Bench runs a simulated vending-machine business for more than 20M tokens per run. It found “high variance in performance”: even models that usually turn a profit (Claude 3.5 Sonnet, o3-mini) have runs that derail, by misreading delivery schedules, forgetting orders or descending into “meltdown” loops, and the failures show “no clear correlation” with the context window filling up[65]. For long-running agents, run several episodes and report the distribution (median and the worst run or worst decile) plus a pass^k-style reliability figure, not just the mean.

How big is the error bar?

With N tasks, one binary trial each, SE = √(p(1 − p)/N): for 500 tasks at p = 0.6, 0.0219, a 95% interval of about ±4.3 points, larger than many leaderboard gaps. Three refinements from Chapter 5 matter for agents:

  • Pair the comparison (Chapter 5.5). Var(A − B) = Var(A) + Var(B) − 2 Cov(A, B) is much smaller than the unpaired sum. Use a paired bootstrap or McNemar’s test: only discordant tasks (A only: b; B only: c) carry information, and under the null b ~ Binomial(b + c, ½).
  • Cluster (Chapter 5.3). Tasks from one repository share a codebase and difficulty; the design effect 1 + (m − 1)ρ easily exceeds 2. Resample repositories, not tasks; METR weights tasks by 1/√(family size) and uses a hierarchical bootstrap[5].
  • Separate within-task from between-task variance. Repeated trials shrink noise in each pi, but only more tasks shrink the uncertainty about which tasks you sampled.

def make_suite(rng: np.random.Generator) -> tuple[np.ndarray, np.ndarray, np.ndarray]:
    """Return per-task success probabilities for A and B, plus repo ids."""
    repo_mean = rng.beta(6, 4, size=N_REPOS)
    repo = np.repeat(np.arange(N_REPOS), PER_REPO)
    kappa = 0.8                                    # small kappa: tasks are mostly easy or mostly hard
    p_a = rng.beta(repo_mean[repo] * kappa, (1 - repo_mean[repo]) * kappa)
    # B's advantage varies by repo: it fixes a repo-specific share of A's failures (mean 5%),
    # and is worse on some repos.  The mean gap is then rescaled to exactly +2 points.
    f = rng.uniform(-0.15, 0.45, size=N_REPOS)[repo]
    p_b = np.where(f >= 0, p_a + f * (1 - p_a), p_a * (1 + f))
    p_b = np.clip(p_a + (p_b - p_a) * 0.02 / (p_b - p_a).mean(), 0, 1)   # calibrate: true gap = 2 points
    return p_a, p_b, repo


def mcnemar_exact(b: int, c: int) -> float:
    """Two-sided exact McNemar p-value from discordant counts b (A only) and c (B only)."""
    n, k = b + c, min(b, c)
    if n == 0:
        return 1.0
    tail = sum(comb(n, i) for i in range(k + 1)) / 2 ** n
    return min(1.0, 2 * tail)


def paired_bootstrap(a: np.ndarray, b: np.ndarray, rng: np.random.Generator, B: int = 4000) -> tuple[float, float]:
    idx = rng.integers(0, len(a), size=(B, len(a)))
    diffs = (b[idx] - a[idx]).mean(axis=1)
    return tuple(np.percentile(diffs, [2.5, 97.5]))


def cluster_bootstrap(a: np.ndarray, b: np.ndarray, repo: np.ndarray, rng: np.random.Generator,
                      B: int = 4000) -> tuple[float, float]:
    d_by_repo = np.array([(b[repo == r] - a[repo == r]).sum() for r in range(N_REPOS)])
    n_by_repo = np.bincount(repo, minlength=N_REPOS)
    idx = rng.integers(0, N_REPOS, size=(B, N_REPOS))
    diffs = d_by_repo[idx].sum(axis=1) / n_by_repo[idx].sum(axis=1)
    return tuple(np.percentile(diffs, [2.5, 97.5]))

6.7Cost, latency and Pareto frontiers

“AI Agents That Matter” (Kapoor et al., 2024) argued that “AI agent evaluations must be cost-controlled”[67]: you can almost always buy points by sampling, retrying or calling a bigger model. On HumanEval, retry (re-run when example tests fail), warming (raise the temperature per retry) and escalation (cheap model first, expensive only on failure) matched the elaborate agents of the time: “There is no significant accuracy difference between our warming strategy and the best-performing agent architecture”, at a fraction of the cost. Report accuracy and cost jointly, as a Pareto frontier: the systems for which no other is both cheaper and at least as accurate. Model developers need a standardised scaffold and budget; downstream developers need dollar costs at today’s prices[67]. HAL’s cost-aware leaderboard found “higher reasoning effort reducing accuracy in the majority of runs”[11]. Log per trial: dollars, input and output tokens, wall-clock time, time to first token, turns and tool calls.

pareto.py simulates 300 coding tasks and three mock models ($0.002, $0.01 and $0.04 a call) under eight strategies. Retry and escalation stop when the visible tests pass, which a wrong solution fools 15% of the time; the “complex agent” always spends eight strong calls. All strategies share common random numbers (one pre-drawn uniform per task and attempt), so they are compared on the same luck, a paired design, and changing one strategy’s parameter cannot move another’s score.

def run_strategy(name: str, plan: list[str], difficulty: np.ndarray, u: dict[str, np.ndarray],
                 adaptive: bool = True) -> Result:
    """plan = sequence of models to call; stop early on visible-test pass if adaptive.

    u holds common random numbers shared by every strategy (u["ok"][task, attempt],
    u["fool"][task, attempt], u["final"][task]), so strategies are compared on the same luck and
    changing one parameter cannot shift another strategy's draws."""
    correct, cost, calls = 0, 0.0, 0
    for i, d in enumerate(difficulty):
        final_ok = False
        for j, m in enumerate(plan):
            skill, price = MODELS[m]
            cost += price
            calls += 1
            ok = u["ok"][i, j] < p_solve(skill, np.array([d]))[0]
            visible_pass = ok or u["fool"][i, j] < P_VISIBLE_FOOLED
            final_ok = ok
            if adaptive and visible_pass:
                break
        if not adaptive:   # complex agent: answer quality improves with its own reflection loop
            final_ok = u["final"][i] < p_solve(MODELS["strong"][0] + 0.6, np.array([d]))[0]
        correct += final_ok
    return Result(name, correct / len(difficulty), cost / len(difficulty), calls / len(difficulty))


def pareto_front(results: list[Result]) -> set[str]:
    front = set()
    for r in results:
        dominated = any((o.cost <= r.cost and o.acc >= r.acc) and (o.cost < r.cost or o.acc > r.acc)
                        for o in results)
        if not dominated:
            front.add(r.name)
    return front

6.8Human-calibrated difficulty: time horizons

Benchmark percentages do not compose, and a saturated benchmark’s scale simply ends. METR proposed a unit that spans benchmarks: the length of tasks, in human working time, that an agent can complete. The 50%-task-completion time horizon is “the time humans typically take to complete tasks that AI models can complete with 50% success rate”[5].

The model

For each task, METR records ttask, the geometric mean time of successful human baseliners. For each model it fits a logistic regression of success on log task length:

psuccess(model, task) = σ( βmodel · (log hmodel − log ttask) ),   σ(x) = 11 + e−x (6.6) hmodel is the 50% horizon (where predicted success is exactly ½) and βmodel the slope: how sharply success falls as tasks get longer. The method is inspired by item response theory, with human time playing the role of item difficulty.

With base-2 logs (our script’s choice, so β is the change in log-odds per doubling of task length), success equals p at log2 t = log2 h − ln(p/(1 − p))/β, so the 80% horizon is shorter than the 50% horizon by 2ln 4/β, about 2.6× for β ≈ 1. METR’s suite combined HCAST, RE-Bench and 66 short software actions (SWAA), 170 tasks; Claude 3.7 Sonnet’s horizon was about 50 minutes, and frontier horizons have been “doubling approximately every seven months since 2019”[5].

Fitting it yourself

time_horizon.py generates 40 synthetic tasks with human times spread log-uniformly from 1 minute to 8 hours, runs a mock agent twice on each (80 runs) with a true horizon of 30 minutes and β = 1.2, then fits equation 6.6 by plain gradient descent on the log-likelihood and bootstraps over tasks for a confidence interval:

def fit_logistic(x: np.ndarray, y: np.ndarray, iters: int = 3000, lr: float = 0.5) -> tuple[float, float]:
    """Fit y ~ sigmoid(a + b*x) by gradient descent. Returns (a, b)."""
    xm, xs = x.mean(), x.std()
    z = (x - xm) / xs                           # standardise for stable steps
    a, b = 0.0, 0.0
    for _ in range(iters):
        p = 1 / (1 + np.exp(-(a + b * z)))
        a -= lr * np.mean(p - y)
        b -= lr * np.mean((p - y) * z)
    return a - b * xm / xs, b / xs              # undo the standardisation


def horizon(a: float, b: float, p: float = 0.5) -> tuple[float, float]:
    """With logit = a + b*log2 t and b < 0: beta = -b; time where success = p."""
    beta = -b
    log2_h50 = a / beta
    log2_hp = log2_h50 - np.log(p / (1 - p)) / beta
    return float(2 ** log2_hp), float(beta)

Caveats

The horizon is only as general as its tasks[5]: mostly self-contained, automatically scored software problems, “cleaner” than real work. Baseline times depend on who the baseliners are, and β varies by model, so equal 50% horizons can hide very different 80% horizons. External validity is the real gap. In METR’s randomised controlled trial with 16 experienced open-source developers on 246 real tasks, early-2025 AI tools increased completion time by 19%, while the developers believed they had cut it by 20%[68]. A second datapoint: multi-hour horizons on well-specified, test-graded tasks sit beside a 2.5% automation rate on the Remote Labor Index’s end-to-end paid projects[43], while GDPval reports models approaching (not exceeding) expert quality on well-specified single deliverables[42]. How a task is specified and how it is graded change the conclusion.

HCAST shows the gradient directly: 70–80% success on tasks under an hour, under 20% over four hours[38]. Chapter 8 uses the horizon trend as a dangerous-capability indicator.

6.9Building an agent eval harness

Most agent-eval bugs live in the harness, where the agent touches real infrastructure: Claude once read git history left by previous trials in a shared environment[8], and the OSWorld Chrome underestimate came from the environment[7]. Missing any of the following silently changes scores.

Sandboxing and isolation

  • A fresh environment per trial from the same snapshot; leftover files, caches, git history and processes leak information and couple trials.
  • Least privilege. No network unless needed (then an allow-list), resource limits, no access to grader files. Harbor tasks declare cpus, memory_mb and network_mode and can run the verifier in a separate environment[44]; verifiers offers ScoringConfig(mode="isolated")[69].
  • Timeouts at every level (tool call, turn, trial, verifier), recorded as outcomes, not swallowed.

Infrastructure errors are not agent failures

A trial can end in three ways: success, agent failure, or infrastructure failure (a 503, an OOM-killed container, a rate limit). Scoring the third as the second biases the score low, and because infrastructure failures are correlated (one bad host fails every trial it runs), it inflates run-to-run variance beyond any binomial error bar. flaky_env.py simulates a 5% chance per trial of an HTTP 503, and in each rerun each of ten workers is broken with probability 10%.

def run_once(task: int, worker: int, p_task: np.ndarray, rng: np.random.Generator, bad: set[int]) -> bool:
    if worker in bad:
        raise InfraError("container OOM-killed")
    if rng.random() < P_503:
        raise InfraError("tool backend returned HTTP 503")
    return bool(rng.random() < p_task[task])

            except InfraError:
                worker = (worker + 1 + attempt) % N_WORKERS      # retry elsewhere
        out.append(Trial(t, status, attempt))
    return out

6.10Tracing and observability

“We do not take eval scores at face value until someone digs into the details of the eval and reads some transcripts.”[8] Every finding in Section 6.11 came from reading transcripts, so record each trial as a structured trace: every model call with token counts, every tool call with arguments, result, status and duration, linked into a tree.

A common format: OpenTelemetry GenAI spans

OpenTelemetry’s semantic conventions for generative AI define span types for this: an invoke_agent span for an agent run, a chat span per model call, and an execute_tool {gen_ai.tool.name} span per tool call, with attributes in the gen_ai.* namespace[70], so traces from different frameworks can share a viewer and a grader. The conventions are still Development status and have moved to a separate semantic-conventions-genai repository; there is also a Model Context Protocol page, likewise in development, for tracing MCP tool calls[71]. Error taxonomies for traces

Counting is not understanding. TRAIL defines a taxonomy of agentic errors, provides 148 human-annotated traces, and benchmarks how well LLMs debug them[72]. Agents that hack the grader

An agent with a shell and a goal will sometimes change the measuring instrument. METR reported in June 2025 that frontier models modified tests or scoring code, or accessed existing answers. o3 reward-hacked in 0.7% of HCAST runs (8 of 1,087) but 30.4% of RE-Bench runs (39 of 128), where the scoring function was visible: “more than 43× more common”, reaching 100% (21/21) on Optimize LLM Foundry[12]. METR’s two detectors (review of anomalously high scores, an LLM transcript monitor) each missed hacks the other found, so reported counts are likely underestimates. HAL found agents searching HuggingFace for benchmark answers[11]. Reward hacking in general is in Chapter 7.5; here we build the three detectors a harness should run.

Each detector has a blind spot. Protected-file hashes miss the in-memory monkey-patch. The keyword monitor misses the quiet scorer patch (“Optimizing the evaluation pipeline for speed”) and false-alarms on the honest agent that wrote “I won’t modify the tests”. A hackable grader is also a hackable RL environment: if the tasks feed training, the policy learns the hack (and training against monitor flags can teach subtler hacking). Run the detectors on training rollouts too; Chapter 7.6 describes environment QA.

A validity checklist before you trust a number

  1. Run the reference solution on every task (gold run): it must score 100%. Run it again after every environment change.
  2. Run a do-nothing agent, a random agent and an agent that returns a canned plausible answer: all must score near 0.
  3. Read 10–20 passing transcripts: did they really solve the task? Read 10–20 failing ones: was the failure the agent’s fault?
  4. Check that tests are sufficient (mutation or property tests) and not too narrow (equivalent answers accepted).
  5. Check for leakage (solution in the task text) and contamination (task age vs model cutoff; probes like SWE-Bench Illusion’s).
  6. Confirm isolation: fresh environment per trial, grader files unreachable, no network unless needed.
  7. Flag scores that are impossible or implausibly high, and review them by hand.
  8. Report scaffold, model version, attempts, budget, cost, CI and benchmark version with every number.

6.12From offline evals to production

Public benchmarks tell you about the field; your own evals tell you about your agent. Start small: “20-50 simple tasks drawn from real failures is a great start”[8]. Capability evals “should start at a low pass rate” and show progress; regression evals “should have a nearly 100% pass rate” and run on every change; tasks graduate from one to the other[8]. Watch for saturation, as with SWE-bench Verified[19] and OSWorld, which split into non-comparable versions while scores approached the human baseline[33]. A public benchmark you depend on will be patched, forked and saturated.

The Swiss cheese model

No single method catches everything, so Anthropic layers them like slices of Swiss cheese[8]: offline evals in CI; production trace monitoring with sampled LLM-judge scoring; A/B tests on business outcomes (resolution rate, escalations, refunds issued in error); user feedback; and periodic human studies. Randomised studies are the only layer that measures real impact, and they can contradict the rest, as the METR RCT of Section 6.8 did[68]. Chapter 9.13 covers online evaluation and Chapter 9.15 A/B testing.

user_sim_noise.py attributes a failure to the simulator if the same agent passes the task when replayed with a perfect simulator. Why is that attribution exact here? How would you estimate the simulator-caused share for a stochastic LLM agent and an LLM user simulator, where no perfect simulator exists? Predict, before running it, how the correct agent’s score at ε = 0.1 would change if the simulator also ended early on read-only questions (T5).

Solution

It is exact because the mock agents are deterministic and the only randomness is the simulator’s, so a clean replay is a true counterfactual. With LLM agents you need several replays per task under each simulator to estimate pass rates, and with an LLM simulator there is no clean reference: you sample failed transcripts and have humans label the cause (agent, simulator, task or grader), report the simulator-caused share with a Wilson interval (Chapter 5), and fix instructions until it is a few percent. For T5, the correct agent answers the status in its first reply, before the user could leave, so its score would not change: errors only matter at the points where the agent depends on the user, which is also why the sloppy agent, which never asks, is barely affected.

  • Evaluate the system, not the model: a score belongs to model + scaffold + tools + environment + budget, and should be reported with all of them.
  • Grade outcomes first (tests, state hashes, execution checks), add process checks only for requirements you actually have, and combine them.
  • Always run gold and do-nothing baselines: a grader that passes an empty agent (τ-bench 38%) or fails the reference is broken.
  • Report pass@1 with a paired, cluster-aware CI and pass^k for reliability; a 2-point gap on 500 tasks is usually noise.
  • Report cost and latency and plot a Pareto frontier; simple retry and escalation baselines often match elaborate agents.
  • Time horizons give a cross-benchmark difficulty scale, but their CIs are wide and their external validity is limited (METR RCT: 19% slower).
  • Sandbox every trial, separate infra_error from agent failure, pin every version, and trace everything in a standard format.
  • Assume agents will hack graders: protect and isolate them, use canaries and re-grades, monitor transcripts, and read the highest scores by hand.
