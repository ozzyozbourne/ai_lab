Chapter 11

Capstone: A Compiler Front End the Zig Way

A compiler's front end makes millions of tiny objects, reads them back mostly in order, and throws them away. That is the most data-oriented workload there is, and in 2021 the Zig compiler's front end was rebuilt around that fact: tokens went from 64 bytes to 5, syntax nodes from about 120 bytes to 13, and the parser got 22% faster. This chapter builds a small front end the same way, in Rust, Zig and Odin. It has a tokenizer that writes two parallel arrays, a Pratt parser that writes four more plus one shared extra array, string interning, and an evaluator that runs the result. It is measured against the textbook design with one heap allocation per node, and the arrays are written to disk and read back without parsing. Almost every idea from Chapters 3 to 6 shows up here.

Why a compiler, and why Zig's

Most of this book's examples are particles, monsters and boids, data you would expect to put in arrays. A syntax tree looks like the opposite: it is a tree, a recursive structure that every compiler textbook draws with boxes and arrows. If DOD only worked on data that already looks like a table, a tree would be the place to find out. It turns out to be one of the clearest wins. Andrew Kelley's account in the Zig 0.8.0 release notes says why[1]. His premise was that "using less memory will make things faster, because of fewer allocations and better cache utilization. Also using less memory is valuable in and of itself." His key observation was that a node needs nothing except indices: "The only purpose of an AST is to bring a tree structure to a list of tokens."

The numbers are some of the best documented in the DOD literature. The parser rewrite (176 commits, +20,800/−16,573 lines) gave 15% fewer cache misses, 28% fewer instructions, 26% fewer cycles and 22% faster wall-clock time[1]. The same treatment for the next stage, ZIR (Zig's untyped intermediate representation, which AstGen produces from the AST), cut another 39% of wall time and 40% of peak memory[1]. Carbon's toolchain was designed this way from the start, with a lex+parse goal of 10 million lines per second[3]. Our language is far smaller, so the comparison is about the shape: bytes per token, bytes per node, nodes per token, and how the flat tree does against boxes and pointers on the same input.

The language and the pipeline

The language has integers, identifiers, the binary operators == < + - * / % in four precedence levels, unary minus, parentheses, let x = e;, fn name(a, b) { ... }, calls, if/else (including else if), return and blocks. A program is a list of functions, and running it means calling main. Integers are wrapping i64s, and dividing by zero gives zero, so every generated program has exactly one result. That gives the three languages and the two tree layouts a single number to agree on.

fn f1(a, b) {
    let v0 = a * 3 + -b;
    if v0 < 50 { return f0(v0); } else { let v1 = v0 % 7; }
    return v0 - b;
}

Each program in code/ch11-capstone-flat-ast-compiler/ runs this pipeline:

  1. generate a deterministic source text of about N tokens (default 220; --quick uses 4,096);
  2. tokenize it into two parallel arrays, tag: []u8 and start: []u32;
  3. parse the tokens into four parallel arrays tag, main_token, lhs, rhs plus extra: []u32, interning every identifier;
  4. evaluate the flat tree by walking it, children first;
  5. parse the same tokens again into a boxed tree, one allocation per node, and evaluate that;
  6. write the flat arrays to a file, read them back, and evaluate what was read.

All three evaluations must give the same number. The generator is byte-identical in the three languages, so they must also agree with each other. They do: at the default size all nine evaluations (three languages × flat, boxed, reloaded) print 5749108524495203818.

Tokens: five bytes each

A conventional lexer emits a token struct with a kind, a start offset, an end offset, a line, a column, and often a copy of the text or a pointer to it. Zig's old tokens were 64 bytes[2]. Kelley stored two things instead: a one-byte tag and a four-byte start offset. The release notes give the reason for dropping the end[1]: for most tokens the length follows from the tag (( is one byte, == is two), and for the rest you can run the tokenizer again from the start offset. A string literal has to be scanned again later anyway, so re-tokenizing it costs nothing. Line and column are not stored either. An error message can count newlines up to the offset, and an error message is rare.

The generated source averages about 3.1 bytes per token. Storing end: u32 as well would make tokens 9 bytes. How much bigger than the source would the token arrays be?

At 5 bytes per token the token arrays are already 5 / 3.1 ≈ 1.6× the source. At 9 bytes they would be ≈ 2.9×. Real code has longer tokens and comments: Zig's std/os.zig is 238 KB of source and 35,023 tokens[1], about 6.8 source bytes per token, so there the 5-byte tokens are smaller than the text they describe.

"Calculate instead of store" needs one function that recomputes a token's text from its tag and start. All three programs have it, and it is the only place that knows how long each kind of token is:

/// The token's text, recomputed from its tag and start ("calculate instead of store").
fn token_text(src: &[u8], tag: Tok, start: u32) -> &[u8] {
    let s = start as usize;
    let end = match tag {
        Tok::Int => scan_while(src, s, |c| c.is_ascii_digit()),
        Tok::Ident | Tok::KwFn | Tok::KwLet | Tok::KwIf | Tok::KwElse | Tok::KwReturn => scan_while(src, s, is_ident),
        Tok::EqualEqual => s + 2,
        Tok::Eof => s,
        _ => s + 1,
    };
    &src[s..end]
}
/// The token's text, recomputed from its tag and start ("calculate instead of store").
fn tokenText(src: []const u8, tag: Tok, start: u32) []const u8 {
    const end = switch (tag) {
        .int => scanDigits(src, start),
        .ident, .kw_fn, .kw_let, .kw_if, .kw_else, .kw_return => scanIdent(src, start),
        .equal_equal => start + 2,
        .eof => start,
        else => start + 1,
    };
    return src[start..end];
}

As one struct, {tag: u8, start: u32} is 8 bytes because of the 3 padding bytes after the tag (see Chapter 3). Stored as two arrays it is 5. This is Chapter 4's struct of arrays, and the three languages spell it the way that chapter showed. Rust has no built-in SoA, so Tokens is two Vecs. Zig uses std.MultiArrayList(Token), the container Kelley added to the standard library in the same release for this purpose. Odin uses #soa[dynamic]Token. Each version pins the size at compile time:

The Zig assert is the most direct of the three: MultiArrayList(Token).capacityInBytes(1) == 5 asks the container itself what one element costs. The SoA layout has a second benefit that the release notes point out[1]: the parser mostly needs only the tags, so peeking ahead reads a dense byte array and never touches the offsets.

The tokenizer is a plain loop over bytes that switches on the first byte. Keywords are looked up after scanning an identifier (Zig uses std.StaticStringMap(Tok).initComptime, as std.zig.Tokenizer does), and every program reserves about one token per four source bytes up front.

Nodes: thirteen bytes and an index

Every node in the flat tree has the same four fields, stored as four parallel arrays[1]:

  • tag: u8, which says what kind of node it is and how to read the other three fields;
  • main_token: u32, an index into the token arrays (the operator of a + b, the ( of a call, the let of a declaration). This is the node's source location, and the neighbouring tokens can be found from it;
  • lhs: u32 and rhs: u32, two words whose meaning depends on the tag: a child node, a symbol, an integer value, or an index into extra.

That is 13 bytes per node in SoA form, against 16 as an aligned struct. No field is a pointer, so all four arrays can move, grow and go to disk unchanged, as in Chapter 5. Node 0 is the root, and since nothing can point at the root, 0 works as "no node" in every other field. This is Zig's convention too (Node.Index in std.zig.Ast is enum(u32) { root = 0, _ }[5]), and it means no field needs an Option.

Before you pick the block preset: main has four statements. Which tag will its body get, and how many extra words will the body use?

Four statements do not fit in lhs/rhs, so the body is a block whose lhs..rhs is a range of four statement indices in extra: 4 words, 16 bytes. The function's prototype uses two more ({name, 0 params}). With two statements or fewer the body would be a block_two and would use no extra at all.

Encodings instead of polymorphism

A call can have any number of arguments, a block any number of statements. A pointer tree handles that with a growable list per node. Kelley's answer is that there is no need for one canonical tag per construct[1]: foo(bar) is encoded as a call with one parameter, with the callee in lhs and the argument in rhs, while foo(bar, baz) is a different tag whose rhs indexes extra_data, where extra_data[rhs] and extra_data[rhs+1] are the start and end of the argument list. "You only have to pay for the extra bytes if the AST actually requires it." The cost is a limit of 256 encodings, since the tag is one byte, and a tag-specific accessor for each construct.

Our language uses five pairs of encodings and one construct that always spills:

constructsmall encoding (fits in the node)large encoding (uses extra)
callcall_one: lhs = callee, rhs = argument or 0call: rhs → {start, end} → argument list
blockblock_two: lhs, rhs = up to two statementsblock: lhs..rhs = statement range
ifif_simple: lhs = condition, rhs = thenif_else: rhs → {then, else}
fnfn_decl: lhs → {name, n, param...}, rhs = body (always uses extra)
literals, namesint_literal keeps its value in lhs; identifier keeps its symbol. No children, no extra.

A node never changes size. When a construct outgrows the small encoding, the parser picks the other tag and moves the children into extra. The next figure shows that step one child at a time, with the boxed tree's cost for the same construct next to it.

The interesting code is how a list of unknown length gets into extra in one contiguous piece. The arguments of f(g(1, 2), 3) are parsed recursively, and the inner call writes its own list while the outer list is half built. If both wrote straight into extra they would interleave. The fix, which the Zig parser uses too (0.8.0's "shared scratch buffer to avoid allocating and freeing many small lists"[1]), is one scratch stack. Each list pushes its elements on top, and when the list is done its slice of the stack is copied to the end of extra and popped:

    /// Moves scratch[top..] into `extra` and returns the range: lists are built in one shared
    /// scratch stack, then copied once into their final, contiguous place.
    fn list_to_extra(&mut self, top: usize) -> (u32, u32) {
        let start = self.extra.len() as u32;
        self.extra.extend_from_slice(&self.scratch[top..]);
        self.scratch.truncate(top);
        (start, self.extra.len() as u32)
    }

    /// Two encodings of one construct: `f()` and `f(x)` fit in the node; `f(x, y, ...)` spills to extra.
    fn parse_call(&mut self, callee: u32) -> PResult<u32> {
        let lparen = self.next();
        let top = self.scratch.len();
        if self.peek() != Tok::RParen {
            loop {
                let a = self.parse_expr(0)?;
                self.scratch.push(a);
                if self.peek() != Tok::Comma {
                    break;
                }
                self.next();
            }
        }
        self.expect(Tok::RParen, "`)`")?;
        if self.scratch.len() - top <= 1 {
            let arg = self.scratch.get(top).copied().unwrap_or(0);
            self.scratch.truncate(top);
            return Ok(self.add(Tag::CallOne, lparen, callee, arg));
        }
        let (s, e) = self.list_to_extra(top);
        let range = self.extra.len() as u32;
        self.extra.extend([s, e]);
        Ok(self.add(Tag::Call, lparen, callee, range))
    }
    /// Moves scratch[top..] into `extra` and returns the range: lists are built in one shared
    /// scratch stack, then copied once into their final, contiguous place.
    fn listToExtra(p: *Parser, top: usize) Error![2]u32 {
        const start: u32 = @intCast(p.extra.items.len);
        try p.extra.appendSlice(p.gpa, p.scratch.items[top..]);
        p.scratch.shrinkRetainingCapacity(top);
        return .{ start, @intCast(p.extra.items.len) };
    }

    /// Two encodings of one construct: `f()` and `f(x)` fit in the node; `f(x, y, ...)` spills to extra.
    fn parseCall(p: *Parser, callee: u32) Error!u32 {
        const lparen = p.next();
        const top = p.scratch.items.len;
        if (p.peek() != .r_paren) while (true) {
            const a = try p.parseExpr(0);
            try p.scratch.append(p.gpa, a);
            if (p.peek() != .comma) break;
            _ = p.next();
        };
        _ = try p.expect(.r_paren, "`)`");
        if (p.scratch.items.len - top <= 1) {
            const arg = if (p.scratch.items.len > top) p.scratch.items[top] else 0;
            p.scratch.shrinkRetainingCapacity(top);
            return p.add(.call_one, lparen, callee, arg);
        }
        const r = try p.listToExtra(top);
        const range: u32 = @intCast(p.extra.items.len);
        try p.extra.appendSlice(p.gpa, &r);
        return p.add(.call, lparen, callee, range);
    }
// Moves scratch[top:] into `extra` and returns the range: lists are built in one shared
// scratch stack, then copied once into their final, contiguous place.
list_to_extra :: proc(p: ^Parser, top: int) -> (start, end: u32) {
	start = u32(len(p.extra))
	append(&p.extra, ..p.scratch[top:])
	resize(&p.scratch, top)
	return start, u32(len(p.extra))
}

// Two encodings of one construct: `f()` and `f(x)` fit in the node; `f(x, y, ...)` spills to extra.
parse_call :: proc(p: ^Parser, callee: u32) -> (n: u32, err: Error) {
	lparen := next(p)
	top := len(p.scratch)
	if peek(p) != .R_Paren {
		for {
			a := parse_expr(p, 0) or_return
			append(&p.scratch, a)
			if peek(p) != .Comma {
				break
			}
			next(p)
		}
	}
	expect(p, .R_Paren, "`)`") or_return
	if len(p.scratch) - top <= 1 {
		arg := len(p.scratch) > top ? p.scratch[top] : 0
		resize(&p.scratch, top)
		return add(p, .Call_One, lparen, callee, arg), nil
	}
	s, e := list_to_extra(p, top)
	rng := u32(len(p.extra))
	append(&p.extra, s, e)
	return add(p, .Call, lparen, callee, rng), nil
}

The scratch stack never shrinks, so after the first few functions the parser stops allocating for lists; all the growth is in a few big arrays, amortized as in Chapter 6.

The Pratt parser

Statements are parsed by plain recursive descent: look at the current token's tag and call the matching function. Expressions use Vaughan Pratt's top-down operator precedence[8], in the form Bob Nystrom made popular[9]. Parse a prefix (a literal, a name, a parenthesized expression, or - followed by a prefix). Then, while the next token is a binary operator that binds more tightly than the caller's minimum, consume it and parse its right operand with that operator's precedence as the new minimum. Passing prec (not prec - 1) as the minimum for the right side is what makes a - b - c group as (a - b) - c.

    /// Pratt loop: operators that bind tighter than `min_prec` extend the left operand.
    fn parse_expr(&mut self, min_prec: u8) -> PResult<u32> {
        let mut lhs = self.parse_prefix()?;
        while let Some((prec, tag)) = binary_op(self.peek())
            && prec > min_prec
        {
            let op = self.next();
            let rhs = self.parse_expr(prec)?;
            lhs = self.add(tag, op, lhs, rhs);
        }
        Ok(lhs)
    }
    /// Pratt loop: operators that bind tighter than `min_prec` extend the left operand.
    fn parseExpr(p: *Parser, min_prec: u8) Error!u32 {
        var lhs = try p.parsePrefix();
        while (binaryOp(p.peek())) |op| {
            if (op.prec <= min_prec) break;
            const tok = p.next();
            const rhs = try p.parseExpr(op.prec);
            lhs = try p.add(op.tag, tok, lhs, rhs);
        }
        return lhs;
    }
// Pratt loop: operators that bind tighter than `min_prec` extend the left operand.
parse_expr :: proc(p: ^Parser, min_prec: u8) -> (lhs: u32, err: Error) {
	lhs = parse_prefix(p) or_return
	for {
		op, ok := binary_op(peek(p))
		if !ok || op.prec <= min_prec {
			break
		}
		tok := next(p)
		rhs := parse_expr(p, op.prec) or_return
		lhs = add(p, op.tag, tok, lhs, rhs)
	}
	return
}

Two details matter for the data. First, parentheses produce no node: (a + b) * c is just a mul whose lhs is an add, because the tree's shape already records the grouping. Second, nodes are appended in post-order: a binary node is added after both operands, so every child has a smaller index than its parent. Carbon's parse tree is designed around that property: it is a postorder array with close to one node per token, and its checker walks it front to back instead of chasing edges[3]. Our evaluator still recurses from the root, but the order is why a node's subtree sits in a nearby block of memory, which the next sections rely on.

The Rust Pratt loop is while let Some((prec, tag)) = binary_op(self.peek()) && prec > min_prec. Combining a let pattern with a boolean condition is a let chain, stable since Rust 1.88 in edition 2024; Zig and Odin unwrap the optional and break inside the loop.

String interning

Identifiers appear thousands of times: every let, every use, every call. If the parser stored strings, the evaluator would compare strings on every variable lookup. Instead the parser interns each identifier once: it looks the text up in a hash table and gets back a small integer, the symbol. Equal names get equal symbols, so the rest of the compiler compares u32s. Each symbol's bytes are stored once, back to back in one byte buffer, with a starts array giving each symbol's offset. Zig's AstGen does the same for ZIR string literals: its string_table is a std.HashMapUnmanaged(u32, void, StringIndexContext, ...) whose keys are offsets into string_bytes, not strings[5].

    fn intern(&mut self, s: &[u8]) -> u32 {
        let mask = self.table.len() - 1;
        let mut h = fnv1a(s) as usize & mask;
        loop {
            match self.table[h] {
                0 => break,
                e if self.strings.get(e - 1) == s => return e - 1,
                _ => h = (h + 1) & mask,
            }
        }
        let sym = self.strings.len() as u32;
        self.strings.bytes.extend_from_slice(s);
        self.strings.starts.push(self.strings.bytes.len() as u32);
        self.table[h] = sym + 1;
        if 2 * self.strings.len() > self.table.len() {
            self.grow();
        }
        sym
    }
    fn intern(in: *Interner, gpa: Allocator, s: []const u8) Allocator.Error!u32 {
        const mask = in.table.len - 1;
        var h = fnv1a(s) & mask;
        while (in.table[h] != 0) : (h = (h + 1) & mask) {
            if (std.mem.eql(u8, in.strings().get(in.table[h] - 1), s)) return in.table[h] - 1;
        }
        const sym: u32 = @intCast(in.strings().len());
        try in.bytes.appendSlice(gpa, s);
        try in.starts.append(gpa, @intCast(in.bytes.items.len));
        in.table[h] = sym + 1;
        if (2 * in.strings().len() > in.table.len) try in.grow(gpa);
        return sym;
    }
intern :: proc(in_: ^Interner, s: []u8) -> u32 {
	mask := u32(len(in_.table) - 1)
	h := fnv1a(s) & mask
	for in_.table[h] != 0 {
		if strings_get(interner_strings(in_), in_.table[h] - 1) == string(s) {
			return in_.table[h] - 1
		}
		h = (h + 1) & mask
	}
	sym := u32(strings_len(interner_strings(in_)))
	append(&in_.bytes, ..s)
	append(&in_.starts, u32(len(in_.bytes)))
	in_.table[h] = sym + 1
	if 2 * strings_len(interner_strings(in_)) > len(in_.table) {
		table := make([]u32, 2 * len(in_.table))
		m := u32(len(table) - 1)
		for k in 0 ..< strings_len(interner_strings(in_)) {
			g := fnv1a(transmute([]u8)strings_get(interner_strings(in_), u32(k))) & m
			for table[g] != 0 {
				g = (g + 1) & m
			}
			table[g] = u32(k + 1)
		}
		delete(in_.table)
		in_.table = table
	}
	return sym
}

The table is hand-written in all three programs: open addressing, slots holding symbol + 1 (0 means empty), FNV-1a hashing, linear probing, and doubling when it is half full. A library map would have worked, but this way the table is a flat []u32 with no pointers, the same in every language, and the symbols come out in first-seen order. That order is part of the file format: the JavaScript port in the figure above numbers symbols the same way.

Do not let names back into the evaluator: its environment is a stack of (symbol, value) pairs searched from the top, so looking up a variable never touches a string.

Running the flat tree

The evaluator is a post-order walk: evaluate the children, then combine. It uses no node pointers, only indices into four slices. In Rust the slices are fields of a small FlatEval struct, built once. In Zig and Odin they are a Flat struct of slices that can come either from a parsed Ast or from a file mapped back into memory, so the same evaluator runs both, which is how the serialization test checks its result.

    /// Expressions, children first (post-order).
    fn eval(&mut self, n: u32) -> i64 {
        let (l, r) = (self.lhs[n as usize], self.rhs[n as usize]);
        match self.tag[n as usize] {
            Tag::IntLiteral => l as i64,
            Tag::Identifier => self.env.lookup(l),
            Tag::Negate => self.eval(l).wrapping_neg(),
            Tag::CallOne => {
                let nargs = if r != 0 {
                    let v = self.eval(r);
                    self.env.args.push(v);
                    1
                } else {
                    0
                };
                self.call_sym(self.lhs[l as usize], nargs)
            }
            Tag::Call => {
                let (s, e) = (self.extra[r as usize] as usize, self.extra[r as usize + 1] as usize);
                for k in s..e {
                    let v = self.eval(self.extra[k]);
                    self.env.args.push(v);
                }
                self.call_sym(self.lhs[l as usize], e - s)
            }
            op => {
                let a = self.eval(l);
                let b = self.eval(r);
                apply(op, a, b)
            }
        }
    }
    /// Expressions, children first (post-order).
    fn eval(e: *FlatEval, n: u32) Allocator.Error!i64 {
        const l = e.f.lhs[n];
        const r = e.f.rhs[n];
        switch (e.f.tag[n]) {
            .int_literal => return l,
            .identifier => return e.env.lookup(l),
            .negate => return 0 -% try e.eval(l),
            .call_one => {
                if (r != 0) try e.env.args.append(e.gpa, try e.eval(r));
                return e.callSym(e.f.lhs[l], @intFromBool(r != 0));
            },
            .call => {
                const s = e.f.extra[r];
                const end = e.f.extra[r + 1];
                for (e.f.extra[s..end]) |a| try e.env.args.append(e.gpa, try e.eval(a));
                return e.callSym(e.f.lhs[l], end - s);
            },
            else => |op| {
                const a = try e.eval(l);
                const b = try e.eval(r);
                return apply(op, a, b);
            },
        }
    }
// Expressions, children first (post-order).
flat_eval :: proc(e: ^Flat_Eval, n: u32) -> i64 {
	f := &e.flat
	l, r := f.lhs[n], f.rhs[n]
	#partial switch op := f.tag[n]; op {
	case .Int_Literal:
		return i64(l)
	case .Identifier:
		return lookup(&e.env, l)
	case .Negate:
		return -flat_eval(e, l)
	case .Call_One:
		if r != 0 {
			append(&e.env.args, flat_eval(e, r))
		}
		return flat_call(e, f.lhs[l], r != 0 ? 1 : 0)
	case .Call:
		s, end := f.extra[r], f.extra[r + 1]
		for a in f.extra[s:end] {
			append(&e.env.args, flat_eval(e, a))
		}
		return flat_call(e, f.lhs[l], int(end - s))
	case:
		a := flat_eval(e, l)
		b := flat_eval(e, r)
		return apply(op, a, b)
	}
}

Each case reads its node's encoding exactly as the tag comment says. That is the cost Kelley warned about: with several encodings per construct, every consumer of the tree needs tag-specific accessors. std.zig.Ast has a family of them (fullCall, fullVarDecl, ...) that turn the encodings back into one uniform view[5]. At our size a switch in the evaluator is enough.

A tree-walking interpreter is the slowest reasonable way to run a program (Exercise 11.2 compiles the flat tree to bytecode); here its job is to prove that both trees, and the file, contain the same program.

Recursion depth is the program's nesting depth, so a hostile input like ----...--1 with a million minus signs would overflow the stack. A production front end limits nesting or uses an explicit stack, as Carbon's parser does[3].

The baseline: one allocation per node

The comparison is the tree you would write without thinking about memory. It uses the same grammar, the same tokens, the same interner and the same integer semantics. Only the representation differs: a tagged union per node, children behind owning pointers (Box<Node>, *BNode, ^B_Node), and each list as its own exactly sized heap slice. Each node keeps its token index, as the flat tree's main_token does, so the two trees hold the same information.

All three languages land on the same size. The largest variant, if with a token and three pointers, is 4 + 4 (padding) + 24 = 32 bytes, and the discriminant plus alignment makes the union 40 bytes in each language. This baseline is not a strawman, and it is smaller than the pre-0.8 Zig AST. The tree has no parent pointers and no line or column fields, the token index is a u32, and a call stores its callee's symbol directly instead of pointing at an identifier node. That last point is why the boxed tree has about 3% fewer nodes than the flat one. The benchmark frees the tree inside the timed region, because a compiler that drops the AST after lowering pays for that too. The flat tree frees five arrays. In all three languages the boxed grammar functions are line-for-line parallel to the flat ones, so the timing difference is the representation, not the algorithm.

Writing the tree to disk and reading it back

A flat tree has no pointers, so its in-memory form is a file format. Zig uses this for its incremental cache. ZIR is stored as four arrays (instruction tags, 8-byte instruction data, string bytes, extra), and when a source file has not changed the compiler loads its ZIR instead of tokenizing, parsing and running AstGen again[1]. The code that does it, saveZirCache and loadZirCacheBody in src/Zcu.zig, writes a small header and then hands the arrays to one vectored write, writeVecAll(&vecs). On load it allocates the arrays at their final size and fills them with one readVecAll[6]. Our format is the same idea for our arrays: an eight-word header with magic number, counts and main's symbol, then every column in order, each byte column padded to a multiple of four so every u32 column starts aligned.

fn serialize(ast: &Ast) -> Vec<u8> {
    let (nt, nn) = (ast.tokens.tag.len(), ast.nodes.tag.len());
    let mut out = Vec::with_capacity(32 + 5 * nt + 13 * nn + 4 * ast.extra.len() + ast.strings.bytes.len() + 16);
    let s = &ast.strings;
    put_u32s(&mut out, &[MAGIC, nt as u32, nn as u32, ast.extra.len() as u32, s.bytes.len() as u32, s.len() as u32, ast.main_sym, 0]);
    out.extend(ast.tokens.tag.iter().map(|&t| t as u8));
    pad4(&mut out);
    put_u32s(&mut out, &ast.tokens.start);
    out.extend(ast.nodes.tag.iter().map(|&t| t as u8));
    pad4(&mut out);
    put_u32s(&mut out, &ast.nodes.main_token);
    put_u32s(&mut out, &ast.nodes.lhs);
    put_u32s(&mut out, &ast.nodes.rhs);
    put_u32s(&mut out, &ast.extra);
    out.extend_from_slice(&s.bytes);
    pad4(&mut out);
    put_u32s(&mut out, &s.starts);
    out
}

impl<'a> Reader<'a> {
    fn bytes(&mut self, n: usize) -> Result<&'a [u8], String> {
        let end = self.at.checked_add(n).filter(|&e| e <= self.b.len()).ok_or("file too short")?;
        let s = &self.b[self.at..end];
        self.at = end.next_multiple_of(4);
        Ok(s)
    }
    fn u32s(&mut self, n: usize) -> Result<Vec<u32>, String> {
        let (chunks, _) = self.bytes(4 * n)?.as_chunks::<4>();
        Ok(chunks.iter().map(|c| u32::from_le_bytes(*c)).collect())
    }
    fn tags<T: Copy>(&mut self, n: usize, table: &[T]) -> Result<Vec<T>, String> {
        self.bytes(n)?.iter().map(|&b| table.get(b as usize).copied().ok_or_else(|| format!("bad tag {b}"))).collect()
    }
}
fn writeAst(io: Io, ast: *const Ast, path: []const u8) !void {
    const s = ast.strings;
    const header = [8]u32{
        MAGIC,                 @intCast(ast.tokens.len), @intCast(ast.nodes.len), @intCast(ast.extra.len),
        @intCast(s.bytes.len), @intCast(s.len()),        ast.main_sym,            0,
    };
    const tok_tags: []const u8 = @ptrCast(ast.tokens.items(.tag));
    const node_tags: []const u8 = @ptrCast(ast.nodes.items(.tag));
    var vecs = [_][]const u8{
        std.mem.sliceAsBytes(&header),
        tok_tags,
        pad4(tok_tags.len),
        std.mem.sliceAsBytes(ast.tokens.items(.start)),
        node_tags,
        pad4(node_tags.len),
        std.mem.sliceAsBytes(ast.nodes.items(.main_token)),
        std.mem.sliceAsBytes(ast.nodes.items(.lhs)),
        std.mem.sliceAsBytes(ast.nodes.items(.rhs)),
        std.mem.sliceAsBytes(ast.extra),
        s.bytes,
        pad4(s.bytes.len),
        std.mem.sliceAsBytes(s.starts),
    };
    var file = try Io.Dir.createFileAbsolute(io, path, .{});
    defer file.close(io);
    var buf: [4096]u8 = undefined;
    var fw = file.writer(io, &buf);
    try fw.interface.writeVecAll(&vecs);
    try fw.interface.flush();
}

const Cursor = struct {
    b: []align(4) const u8,
    at: usize = 0,

    fn bytes(c: *Cursor, n: usize) ![]align(4) const u8 {
        if (c.at > c.b.len or n > c.b.len - c.at) return error.FileTooShort;
        const s: []align(4) const u8 = @alignCast(c.b[c.at..][0..n]);
        c.at = std.mem.alignForward(usize, c.at + n, 4);
        return s;
    }
    fn words(c: *Cursor, n: usize) ![]const u32 {
        return std.mem.bytesAsSlice(u32, try c.bytes(4 * n));
    }
    /// Checks every byte before the bytes are viewed as an exhaustive enum.
    fn tags(c: *Cursor, comptime T: type, n: usize) ![]const T {
        const raw = try c.bytes(n);
        for (raw) |b| if (b >= @typeInfo(T).@"enum".field_names.len) return error.BadTag;
        return @ptrCast(raw);
    }
};
write_ast :: proc(a: ^Ast, path: string) -> os.Error {
	f := os.create(path) or_return
	defer os.close(f)
	zeros: [4]u8
	pad := proc(n: int) -> int { return (4 - n % 4) % 4 }
	nt, nn, s := len(a.tokens), len(a.nodes), a.strings
	header := [8]u32{MAGIC, u32(nt), u32(nn), u32(len(a.extra)), u32(len(s.bytes)), u32(strings_len(s)), a.main_sym, 0}
	parts := [?][]u8 {
		slice.to_bytes(header[:]),
		slice.to_bytes(a.tokens.tag[:nt]), zeros[:pad(nt)],
		slice.to_bytes(a.tokens.start[:nt]),
		slice.to_bytes(a.nodes.tag[:nn]), zeros[:pad(nn)],
		slice.to_bytes(a.nodes.main_token[:nn]),
		slice.to_bytes(a.nodes.lhs[:nn]),
		slice.to_bytes(a.nodes.rhs[:nn]),
		slice.to_bytes(a.extra[:]),
		s.bytes, zeros[:pad(len(s.bytes))],
		slice.to_bytes(s.starts),
	}
	for part in parts {
		os.write(f, part) or_return
	}
	return nil
}

	b, ok := take(c, 4 * n)
	return slice.reinterpret([]u32, b), ok
}

// Checks every byte before the bytes are viewed as an enum.
take_tags :: proc(c: ^Cursor, $T: typeid, n: int) -> ([]T, bool) where intrinsics.type_is_enum(T) {
	b, ok := take(c, n)
	for x in b {
		if int(x) >= len(T) {
			return nil, false
		}
	}
	return slice.reinterpret([]T, b), ok
}

This is where the three languages differ the most, and the difference is about trust in bytes, not speed. Zig reads into a u32-aligned buffer (readFileAllocOptions(..., .of(u32), null)) and views each column in place with std.mem.bytesAsSlice. Odin reads into a []u32 and views the columns with slice.reinterpret. Both check the tag columns byte by byte first, because a byte outside an exhaustive enum would be undefined behaviour; after that nothing is copied. Rust without unsafe cannot view &[u8] as &[u32] (bytemuck and zerocopy wrap that unsafe, but this book uses std only), so it decodes each column in one tight pass with as_chunks::<4>() and u32::from_le_bytes, and a bad tag byte is a returned error.

"Zero-copy" means the file's bytes become the program's arrays, so the file must be trusted. The tag check protects the enums, but nothing checks that every lhs, rhs and extra index is in range. A corrupt file makes Rust panic on a bounds check and Odin trap on its bounds check (on by default, also at -o:speed). In Zig at -O fast it is undefined behaviour. Zig's own cache stores the source file's size, inode and mtime in the header and treats the cache as its own output; a cache you download needs a checksum and a validation pass. The format is also native-endian (little-endian here) and has no version field beyond the magic number.

The Odin writer uses the rewritten core:os: os.create returns (^os.File, os.Error), os.write, os.read_full and os.file_size all take that ^File. or_return passes the os.Error straight up, so write_ast is a straight line of calls.

The input: a seeded generator

The benchmark needs a large program that is the same in all three languages and that terminates. The generator is the same splitmix64 sequence used since Chapter 1, driving the same choices in the same order, so the three programs write byte-identical source (3,750,573 bytes and 170,470 lines at the default size). Function i may only call the two functions before it, so the call graph is acyclic and evaluation always finishes. Each function has 1–3 parameters and 2–4 statements, and main folds every function's result into one accumulator, so one wrong operator anywhere changes the final number.

Generated code is not real code. It has short names, no comments and no strings, so its lines are short (22 bytes and 7.1 tokens on average) and its tokens are short (3.1 bytes). That affects every "per line" and "per byte" number below.

Our 14.19 B/node average is a little below Zig's 15.6 because our language has fewer constructs with more than two children. Zig's 0.50 nodes per token for std/os.zig (17,397 nodes for 35,023 tokens[1]) is lower than ours because much of Zig's syntax (., :, const) never gets a node of its own. Carbon reports about one parse node per token at 12 bytes each[4], a different trade: more nodes, but each node is close to its token.

Now the timings. "Tokenize+parse" includes building the tree and, for the boxed tree, freeing it again. Both variants tokenize, so the difference between them is parsing into the two representations.

The parse ratio runs from about 1.8× to 2.9×. Zig's boxed parser (init.gpa at -O fast is smp_allocator) runs level with Rust's, which uses glibc malloc directly, while Odin's is markedly slower: its default heap allocator goes to libc malloc with extra alignment bookkeeping (see Chapter 5). Zig's ratio is the smallest mainly because its flat parser is the slowest of the three. The flat parsers are within about 35% of each other. The tokenizer alone is about 40–45% of the flat pipeline. Notice what this means: on the flat side, building the AST costs about as much as tokenizing.

The evaluation numbers are the most interesting ones, because the two evaluators execute the same algorithm with the same branches. They differ only in where the node data is. At the --quick size (3,000 nodes, a few dozen KiB) they tie, since both trees fit in L1 and L2. At full size the flat evaluator touches about 9 bytes per node plus extra, laid out in post-order, while the boxed one fetches 40-byte nodes plus separate slices, roughly five times as many bytes, through dependent loads. This is Chapter 2's array-versus-linked-list experiment with a real workload on top.

Reading the file back is several times faster than tokenizing and parsing again (compare the two charts), even though the file is 4.6× the size of the source. With real code the file would be closer to the source's size: Kelley measured source + tokens + AST at about 1.3× the ZIR. Rust's decode pass did not make it the slowest reader: at this size the read is dominated by copying 17 MB out of the page cache, and one more streaming pass over data already in cache is cheap, a reasonable price for not writing unsafe. Writing is slower than reading in all three because it creates and truncates the file each time.

Worked example: one megabyte of tokens, in lines per second

Take the Rust run: 3,750,573 bytes, 170,470 lines, flat tokenize+parse in 37 ms. Dividing gives 4.6 M lines/s on one core, and at 22 bytes per line roughly 110 MB/s. Zig's and Odin's flat parsers land at 3.7 M lines/s and 3.4 M lines/s; the boxed parsers between 1.2 M lines/s (Odin) and 2.2 M lines/s (Rust, with Zig just behind).

Do not put this next to Zig's 8.9 M lines/s or Carbon's 10 M. Zig's figure is AstGen (tokenize, parse and lowering to ZIR) over the whole standard library on an 8-core i9-9980HK, with files processed in parallel; the same release notes give 1.8 M lines/s for AstGen of a single file of about a million lines (0.57 s), a job that does not run in parallel[1], for more work per line on far more varied code. Carbon's 10 M is a goal, not a measured result[3], and its lexer is being built for it with SIMD scanning and tail-call dispatch[7], while ours is a byte-at-a-time loop over short generated lines. The flat layout puts this simple front end in the same order of magnitude as production compilers; the next factor would come from the tokenizer, not the tree.

Caveats, and what this cost

  • The flat tree is append-only. Building it in one pass is easy. Inserting a node in the middle, or rewriting a subtree in place, is not: indices would shift. Compilers get away with it because each stage builds a new array (AST → ZIR → AIR in Zig; AIR is the typed, analysed IR that code generation consumes) instead of mutating the old one. An IDE that edits the tree in place has different needs.
  • Encodings spread knowledge. Every reader of the tree has to know every encoding. Zig's parser rewrite was 176 commits, and std.zig.Ast needs a set of full* accessors to undo the encodings for code that does not care[5]. Mitchell Hashimoto, walking through the Zig parser, warns that "the AST node structures can be confusing because there is a lot of indirection"[5].
  • Requested bytes are not resident bytes. The boxed 42 B/node counts what the parser asked for. glibc adds an 8-byte header and rounds to 16, so a 40-byte Box<Node> occupies a 48-byte chunk; the real footprint is higher, but we did not measure resident memory here (/usr/bin/time -v reports max RSS if you want it).
  • Fresh heaps flatter the baseline. The boxed tree is built into an almost empty heap, so consecutive nodes land next to each other (Chapter 5). A fragmented heap would make it worse.

An AST only adds structure to a token list: store tokens as a byte of tag and a u32 offset, nodes as a tag, a token and two u32s, put anything bigger in one shared extra array under a different tag, and the tree becomes a few flat arrays that are three times smaller, parse up to three times faster, evaluate 1.4–2× faster, and can be written to disk as they are.

Exercises

Add while cond { ... } to the language. How many encodings does it need, and does it use extra?

One encoding fits: while_loop with lhs = condition and rhs = body block. It uses no extra, because the body is already one node (a block_two or block). You would add a second encoding only if while grew more parts, for example Zig's while (c) : (step), which is why Zig has both while_simple and while_cont. The tokenizer needs a kw_while tag, the evaluator one more case, and the boxed tree one more variant.

Compile the flat tree to bytecode: one post-order pass that writes push_int v, load sym, add, call f n, jump_if_zero, ... into a []u32. What is the order of the instructions for a * (b + 1), and what does the interpreter loop look like?

load a; load b; push_int 1; add; mul: exactly the post-order of the nodes. The interpreter is a while (pc < code.len) switch (code[pc]) over an operand stack of i64s. if needs forward jumps patched once the then-block's length is known (write a placeholder, remember its index, fill it in), and calls need a frame stack of return addresses and variable bases. It is one more flat array and one more pass, the same move Zig makes from AST to ZIR.

Store end: u32 in the tokens as well. Using this chapter's numbers, how much memory does it add at the default size, and what code gets simpler?

4 bytes × 1,214,430 tokens ≈ 4.9 MB, taking the token arrays from 6.07 MB to 10.9 MB. token_text becomes a slice instead of a re-scan, but it runs once per identifier and integer, so no hot path gets faster.

Remove call_one so every call uses call. How many extra bytes per call does that cost for zero and one arguments? Which other tag pair would you remove first if you had to free up tag values?

A call always uses the {start, end} pair (8 B) plus 4 B per argument, so a zero-argument call grows from 13 to 21 B and a one-argument call from 13 to 25 B. Our generator's functions take 1–3 parameters, so about a third of calls would pay 12 B each. if_simple/if_else is a cheaper pair to merge: an if without else would cost 8 B more, and there are fewer ifs than calls in this workload. Measure before choosing: count each tag in the node array.

Why can 0 mean "no node" in lhs, rhs and extra? What would break if the root were the last node, as post-order would naturally make it?

Node 0 is the root, and nothing points at the root, so the index 0 is free to mean "none" everywhere else, without an Option or a sentinel like u32::MAX. If the root were last, index 0 would be the first leaf of the first function, a real node. You would need another sentinel and a comparison against it in every block_two and call_one. The parser reserves slot 0 up front with add(.root, 0, 0, 0) and fills in its range at the end.

Make the Rust reader zero-copy with std only and no unsafe. Is it possible? What would you change in the file format instead?

Not for u32 columns: safe std cannot view &[u8] as &[u32] (align_to is unsafe). Keep the decode pass, use zerocopy or bytemuck, or change what you read: the tag columns are bytes and can be borrowed directly, and an evaluator could decode lhs/rhs with u32::from_le_bytes at each access.

Each generated function only refers to symbols and to other functions by name. How would you tokenize and parse the input on two threads, and how would you merge the results into one set of arrays?

Split the source at a fn keyword at the start of a line near the middle. Each thread tokenizes and parses its half into its own arrays with its own interner. To merge, append the second thread's arrays to the first, adding offsets: token indices shift by the first half's token count, node indices by its node count, extra indices by its extra length, and symbols are remapped through a small table built by interning the second interner's strings into the first. The merge needs the tag table to know which fields to shift. Zig avoids the merge by keeping one AST per file and parallelizing over files[1].
