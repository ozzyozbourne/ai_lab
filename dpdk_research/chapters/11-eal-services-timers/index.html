1Why an app needs background work

Chapter 10 ended with mini_l2fwd: a loop that receives a burst, rewrites the MAC addresses and transmits it on the other port, forever. On this VM, with two net_ring loopback ports, that loop moves around 80 million frames per second in software. At 2.7 GHz that is about 32 CPU cycles per frame. Now ask what else a real application must do:

  • Periodic statistics: rates per port every second, for a dashboard or a log.
  • Housekeeping: flush half-full TX buffers, age out flow table entries, refresh ARP entries, rotate counters.
  • A watchdog: notice that a forwarding lcore is stuck in an endless loop. A stuck lcore does not crash; it silently stops forwarding.
  • A control plane: let an operator ask "how are you doing?" and change a setting without a restart.
  • Configuration: typed command-line options with help text and a config file.

None of this may cost the poll loop much. A single printf() of a stats line takes tens of microseconds: hundreds of thousands of cycles, or thousands of frames that were not forwarded. The EAL and a few small libraries give you four places to put this background work, and this chapter uses all four:

2Step 1: periodic stats with rte_timer

The simplest way to run something every second is to check the clock in the poll loop. Chapter 10's drain timer did exactly that with one TSC compare. That works for one job, but it gets messy with ten jobs, with one-shot jobs, or with jobs that should run on another lcore. The timer library (lib/timer) packages the pattern: you arm timer objects, and one call, rte_timer_manage(), runs every callback that is due.

The API in five calls

CallWhat it does
rte_timer_subsystem_init()Once per process, after rte_eal_init(). Allocates one pending list per lcore (in shared memory, so secondaries can use it). Without it rte_timer_manage() returns -EINVAL.
rte_timer_init(&tim)Puts a struct rte_timer in the STOPPED state with no owner. Do this once before the first reset; the struct must stay alive (static or heap) while the timer is armed.
rte_timer_reset(&tim, ticks, type, tim_lcore, cb, arg)Arms (or re-arms) the timer: expire = now + ticks. type is SINGLE (one shot) or PERIODICAL (re-armed automatically). tim_lcore is the lcore whose rte_timer_manage() will run cb(tim, arg); LCORE_ID_ANY picks a different worker lcore round-robin. Returns 0, or -1 if the timer is RUNNING or being configured on another lcore.
rte_timer_manage()Call it often from the lcore's loop. Runs every timer of this lcore whose expiry has passed, in expiry order.
rte_timer_stop(&tim)Disarms. Like reset it can fail with -1 if the callback is running right now on another lcore. rte_timer_reset_sync() and rte_timer_stop_sync() spin until they succeed (never call them from a timer callback to reset another timer: they can deadlock).

Ticks are cycles of the timer clock, rte_get_timer_hz() per second. On x86 that is the TSC (2.7 GHz here), so "one second" is rte_get_timer_hz() and "100 ms" is rte_get_timer_hz() / 10. Other useful calls: rte_timer_pending(), rte_timer_next_ticks() (ticks until this lcore's next timer, 0 if one is due, -ENOENT if none) and rte_timer_dump_stats(), which only has numbers in a build with RTE_LIBRTE_TIMER_DEBUG.

How the pending list works: a skiplist per lcore

Each lcore's pending timers sit in a skiplist sorted by expiry time. A skiplist is a linked list with extra "express lanes": every timer has between 1 and 10 forward pointers (sl_next[MAX_SKIPLIST_DEPTH]), and the number is drawn at random when the timer is inserted. Insertion walks the express lanes first and drops a level whenever it would overshoot, which costs about log(n) steps. Expiry is even cheaper: the earliest timer is always first, so rte_timer_manage() only looks at the head. Step through it and answer the two predictions.

The code: step1_timer.c

Step 1 keeps everything on one lcore (-l 0). Two timers: a PERIODICAL one that prints the per-port deltas every second, and a SINGLE one that ends the run. The poll loop calls rte_timer_manage() at most every 100 microseconds, using one TSC compare as a rate limiter, and measures how long each call takes.

	if (ret < 0)
		rte_exit(EXIT_FAILURE, "rte_timer_subsystem_init: %d\n", ret);

	rte_timer_init(&stats_tim);
	rte_timer_init(&stop_tim);

	/* 3. arm them. Ticks are TSC cycles; tim_lcore = the lcore whose
	 *    rte_timer_manage() will run the callback (here: ourselves). */
	hz = rte_get_timer_hz();

			      stats_cb, &tick);
	if (ret == 0)
		ret = rte_timer_reset(&stop_tim, seconds * hz, SINGLE,
				      rte_lcore_id(), stop_cb, NULL);
	if (ret != 0)
		rte_exit(EXIT_FAILURE, "rte_timer_reset failed\n");

	       "rte_timer_manage every %u us\n", hz, seconds, manage_us);

	prev_manage = rte_get_timer_cycles();

	while (!force_quit) {
		uint64_t now;

		app_forward_once(32);

		/* 4. drive the timers. Calling rte_timer_manage() on every loop
		 *    pass would work too, but it reads the clock and touches the
		 *    skiplist head each time: rate-limit it with one TSC compare. */

			rte_timer_manage();

Tip: precision is your call rate

A timer cannot fire earlier than its expiry, but it fires late by up to the time between two rte_timer_manage() calls, plus whatever the loop was doing. Calling it every 100 us gives 100 us precision for a cost of about 0.05% of a core here. l2fwd and the course programs rate-limit the call with one TSC compare; calling it on every loop pass is also legal, just wasteful.

3Step 2: moving the stats onto a service lcore

In step 1 the stats callback still ran on the forwarding lcore: every second the loop stopped for a printf(). We would rather give that work to another core. You could launch your own function on a spare lcore with rte_eal_remote_launch() (ch3), and for one job that is fine. The service cores framework in the EAL standardises the idea so that many jobs, including jobs written by drivers, can share a few dedicated cores.

The model: component, application, service lcore

A service is a function that does a small amount of work per call: "schedule one batch of events", "print the stats if a second has passed". Two parties are involved:

  • The component (a driver, a library, or your own code) registers the service with rte_service_component_register(&spec, &id) and says when it is ready with rte_service_component_runstate_set(id, 1). The event_sw software event device, the eventdev Rx/Tx/timer/crypto/DMA/vector adapters, the dispatcher library, softnic and failsafe all register services this way.
  • The application decides where and whether it runs: it maps the service to one or more service lcores with rte_service_map_lcore_set(id, lcore, 1) and switches it on with rte_service_runstate_set(id, 1).

A service lcore runs the EAL's service_runner_func(): a loop that calls every service mapped to it, again and again, as fast as it can. A service runs only when all four conditions hold: component runstate 1, application runstate 1, mapped to the lcore, and the lcore started.

Service lcores on the command line: -S (not -s)

You declare service lcores with -S <corelist>, for example -l 0,2 -S 2. The service lcore must also be in -l: EAL takes it out of the worker set and gives it the role ROLE_SERVICE, so RTE_LCORE_FOREACH_WORKER and rte_get_next_lcore() skip it. The old -s <coremask> still works in 26.11 but prints a deprecation warning (captured below); never use it in new code.

Two things happen inside rte_eal_init() that surprise people. First, rte_service_init() runs before the bus probe, so vdevs like event_sw0 can register their service during probing. Second, at the end of init the EAL calls rte_service_start_with_defaults(): it maps every service registered so far to the service lcores and starts them. So by the time your main() continues, the service lcores are already running and rte_service_lcore_start() returns -EALREADY. Services you register later must be mapped by you.

MT safety and running a service yourself

A service registered without RTE_SERVICE_CAP_MT_SAFE in spec.capabilities must never run on two lcores at the same time. If you map it to two service lcores anyway, the runner protects it with a spin trylock: one lcore runs it and the other skips it for that iteration. You lose nothing in correctness but gain nothing in throughput. An MT-safe service mapped to two lcores really runs twice in parallel.

You can also run one iteration of a service from an ordinary lcore with rte_service_run_iter_on_app_lcore(id, serialize_mt_unsafe). With serialize_mt_unsafe = 1 it takes the same trylock and returns -EBUSY if a service lcore is running it; with 0 you promise that nobody else runs it and save the atomic operation. It returns -ENOEXEC if a runstate is 0. Unit tests and apps that cannot spare a whole core use it (exercise 2).

code/evolve/step2_service.c: the service callbackC
stats_service(void *userdata)
{
	struct stats_svc *s = userdata;
	uint64_t now = rte_get_timer_cycles();
	char tag[24], where[64];

	if (now < s->next)
		return -EAGAIN;
	s->next += s->hz;
	snprintf(tag, sizeof(tag), "t=%us", ++s->tick);
	app_print_delta(tag, 1.0);
	if (s->tick == 1)
		printf("      (stats_service runs in %s)\n", app_where(where, sizeof(where)));
	return 0;
}

Pitfall: a service that never returns

A service callback must do a bounded amount of work and return. A while (1) inside a service starves every other service mapped to the same lcore, and rte_service_lcore_stop() can never complete. If your work really is an endless loop, it is not a service: launch it on its own lcore.

4Step 3: a keepalive watchdog

Step 3 moves forwarding to worker lcore 1 and turns the main lcore into a control lcore. That opens the door to a classic failure: the worker gets stuck (a lock that is never released, a driver call that never returns, a bug in a loop). The process is alive, the other lcores are fine, but one port stops forwarding and nothing crashes. The keepalive helper in the EAL (rte_keepalive.h) detects it with two cheap actions:

  • The watched lcore calls rte_keepalive_mark_alive(ka) from its poll loop. It is one store of ALIVE into this lcore's own slot; each slot has its own cache line (alignas(RTE_CACHE_LINE_SIZE)), so cores do not false-share.
  • A periodic timer calls rte_keepalive_dispatch_pings(timer, ka). Each ping moves every watched core one step through the state machine below. A core that keeps marking is pushed back to ALIVE before the next ping; a core that stopped marking slides to DEAD and then GONE.

Count the pings. Ping 1 after the last mark finds ALIVE and sets MISSING (that is normal; a healthy core re-marks right away). Ping 2 finds MISSING: the EAL logs "Core MIA" and sets DEAD. Ping 3 finds DEAD: it logs "Core died", sets GONE and calls your failure callback. So the callback fires 2 to 3 ping periods after the core stopped marking. The "last seen" time is the time of the first ping after the last mark, so it has the ping period as its resolution.

The sample examples/l2fwd-keepalive "restarts" a dead lcore with rte_eal_remote_launch(). 5Step 4: a control shell with lib/cmdline

Restarting the app to change the burst size is not acceptable in production. Step 4 gives the main lcore a control shell, the same library testpmd's prompt is built on (ch9). lib/cmdline is small and a little old-fashioned: you describe each command as a list of typed tokens, and the library parses, completes and dispatches.

Tokens, instructions and a context

  • A result struct has one field per word of the command.
  • A token parses one word into one field, located with offsetof() by the TOKEN_*_INITIALIZER(struct, field, ...) macros. TOKEN_STRING_INITIALIZER(s, f, "show") accepts exactly show; "stats#keepalive" accepts either word; TOKEN_NUM_INITIALIZER(s, f, RTE_UINT16) parses a number (decimal, 0x hex, 0b binary) and rejects one that does not fit. There are also tokens for IPv4/IPv6 addresses and prefixes, MAC addresses, port lists, booleans and TOKEN_STRING_MULTI (the rest of the line).
  • An instruction (cmdline_parse_inst_t) is a NULL-terminated token list, a handler f(parsed_result, cl, data) and a help string.
  • The context (cmdline_parse_ctx_t[]) is a NULL-terminated array of instructions.

For each input line, cmdline tries every instruction. If exactly one matches all its tokens with nothing left over, its handler runs. If none does, it prints Bad arguments when some instruction matched at least its first token, otherwise Command not found; two full matches give Ambiguous command. Type into the matcher below, which models the step 4 instructions with the same rules (lib/cmdline/cmdline_parse.c).

6Step 5: real options with rte_argparse and rte_cfgfile

Steps 1 to 4 parsed a few options with getopt_long() after rte_eal_init() (ch2). That is fine, but you write the type conversion, the error messages and the help text yourself, and nothing ties an option to its documentation. The final app uses two DPDK libraries instead.

rte_argparse: options described by a table

You describe the program in a struct rte_argparse and each option in an args[] entry ending with ARGPARSE_ARG_END(). Each entry has:

  • name_long ("--burst"; a name without dashes is a positional argument) and an optional name_short ("-b");
  • help, which must not be NULL: it becomes the generated --help text;
  • value_required: RTE_ARGPARSE_VALUE_NONE (a flag), _REQUIRED or _OPTIONAL;
  • value_type: _TYPE_INT, _U8/_U16/_U32/_U64, _STR, _BOOL or _CORELIST;
  • val_saver: where to store the converted value (autosave). If it is NULL, argparse calls obj->callback(index, value, opaque) instead, with index = (uint32_t)val_set;
  • val_set: for a flag, the value stored when it is present; flags: RTE_ARGPARSE_FLAG_SUPPORT_MULTI to allow repeats.

rte_argparse_parse(&obj, argc, argv) returns the number of arguments parsed or a negative errno, skipping argv[0]; after argc -= ret; argv += ret from rte_eal_init(), argv[0] is still the program name, so this just works. -h/--help is built in: it prints the help and calls exit(0). With exit_on_error = true an error calls exit(ret) with a negative number (an exit status of 234 for -EINVAL), skipping your cleanup, so the final app sets it to false and handles the error. The API is still __rte_experimental in 26.11: build with -DALLOW_EXPERIMENTAL_API.

7Side demo: EAL alarms

An EAL alarm is the simplest delayed call: rte_eal_alarm_set(us, cb, arg) runs cb(arg) once, at least us microseconds from now. You do not poll anything. The EAL's interrupt thread (dpdk-intr, created by rte_eal_init()) waits on a timerfd together with all device interrupt file descriptors and runs the callback itself. Drivers use alarms for "check the link again in 100 ms" and for delayed device reset handling. rte_eal_alarm_cancel(cb, arg) removes pending alarms that match both; (void *)-1 as arg matches any argument.

Four facts. The callback runs in dpdk-intr and rte_lcore_id() there is LCORE_ID_ANY, so per-lcore APIs (an mbuf pool's per-lcore cache, rte_timer_reset with "this lcore") do not behave as on an lcore. Re-arming from the callback gives periodic work that drifts a little (the period is measured from when the callback ran). And one callback that sleeps 300 ms delays the next alarm by 250 ms: the thread is shared by every alarm and every interrupt and device event callback of the process (link-state events in ch12 arrive there too).

Pitfall: blocking in dpdk-intr

Never block in an alarm or an interrupt callback: no sleep, no waiting for a lock that a data-plane lcore holds, no rte_eth_dev_stop() of a port whose interrupt you are handling. If the work is slow, have the callback set a flag or post to a ring, and do the work on a control thread or lcore.

8jobstats: where does the loop's time go?

Common pitfalls

  • Timers never fire: nobody calls rte_timer_manage() on the lcore named in rte_timer_reset(). A timer armed for lcore 2 is invisible to lcore 0's manage(). Also check that rte_timer_subsystem_init() ran (manage() returns -EINVAL otherwise).
  • A timer on the stack: struct rte_timer is linked into a shared list. If it goes out of scope while pending, the list points into a dead stack frame. Make timers static or heap-allocated, and stop them before freeing.
  • Ignoring rte_timer_reset()'s return value: it returns -1 while the timer's callback is running on another lcore. Check it, or use rte_timer_reset_sync() outside callbacks.
  • Service never runs: one of the four switches is off. Component runstate, application runstate, mapping, lcore started. rte_service_dump() and rte_service_runstate_get() tell you which.
  • Service lcore not in -l: -S 2 with -l 0-1 is not rejected in 26.11: EAL warns "Not all service cores were in the coremask" and makes lcore 2 a service lcore anyway (captured above). Keep -S inside -l so the lcore list says what really runs. And -s is deprecated.
  • rte_service_lcore_stop() returns -EBUSY: a running service is mapped only to that lcore. Set its runstate to 0 first, then stop, then rte_eal_wait_lcore(), then unmap and unregister.
  • Cycle counters stay 0: service cycle statistics are off until rte_service_set_stats_enable(id, 1).
  • Keepalive callback "too late": it fires on the third ping after the last mark, so detection takes 2 to 3 ping periods. Shorter periods detect faster and cost more pings; a core that legitimately blocks longer than that (a long rte_flow operation) must call rte_keepalive_mark_sleep() first.
  • Registered cores show UNUSED forever: a core is UNUSED until its first rte_keepalive_mark_alive(). A core that hangs before its first mark is never detected.
  • The shell freezes the timers: cmdline_interact() blocks its thread. Anything that thread used to drive (timers, keepalive pings) must move to another lcore first, as in step 4.
  • Blocking in an alarm: all alarms and interrupt callbacks share dpdk-intr; one slow callback delays them all (250 ms in our demo).
  • exit_on_error = true in rte_argparse: errors call exit() with a negative value, skipping your cleanup; the shell sees exit status 234 or similar.

Summary
  • Background work must not sit inline in the poll loop. DPDK gives four places for it: timers (on the lcore that manages them), services (on service lcores), alarms (in the interrupt thread) and control threads (which may block).
  • rte_timer: init the subsystem once, init each timer, rte_timer_reset() with SINGLE or PERIODICAL and a target lcore, and call rte_timer_manage() there. Per-lcore skiplists make manage() cost the same (~42 cycles here) for 10 or 100,000 pending timers; precision is your call interval.
  • Services split "what" (component: register, component runstate) from "where" (application: map, app runstate, -S lcores). EAL init already starts the service lcores. Return -EAGAIN when idle, enable stats for cycle counts, stop services before their lcores.
  • Keepalive: mark alive from the loop, dispatch pings from a timer; the failure callback fires on the third ping after the last mark. You can detect a hung lcore, but you cannot revive it in-process.
  • cmdline builds a shell from typed tokens, instructions and a context; cmdline_interact() blocks, so move timers away from that thread. dpdk-cmdline-gen.py writes the boilerplate.
  • rte_argparse turns an option table into parsing, conversion and help; rte_cfgfile reads INI files as strings. Apply defaults < file < command line, then semantic checks.
  • Know your toolbox: rte_rand_max, bitsets and bitmaps, rte_reciprocal, rte_errno, rte_strscpy/strsplit, and the 26.11 forms of RTE_PTR_ADD and packed structs.
